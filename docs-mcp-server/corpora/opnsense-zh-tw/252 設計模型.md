為 OPNsense 建立模型分為兩個單獨的區塊：

1.  一個 PHP 類，描述對我們資料的操作（也充當我們資料的包裝器），
    
2.  資料的定義及其應適用的規則。
    

每個模型的類別都應該從 OPNsense\\Base\\BaseModel 派生，一個非常簡單的模型，沒有任何（附加）邏輯，定義如下：

```php
<?php
namespace myVendorName\myModule;

use OPNsense\Base\BaseModel;

class myModel extends BaseModel
{
}
```

這個類別應該放置在我們專案的模型目錄中，在這種情況下，我們的類別檔案的完整路徑是

-   /usr/local/opnsense/mvc/app/models/**myVendorName/myModule/myModel.php**
    

當您設計模型時，接下來要做的就是弄清楚哪些資料與您的應用程式或模組相關，並考慮它應該遵守的規則（例如，如果您需要電子郵件地址，您可能需要驗證輸入）。設計實際模型就像建立 xml 檔案並放入您的結構一樣簡單，我們的 XML 檔案的名稱應該與我們模型的基本名稱相同，後綴為 .xml。

使用相同的模型，我們將建立以下文件：

-   /usr/local/opnsense/mvc/app/models/**myVendorName/myModule/myModel.xml**
    

並開始描述我們的（資訊）模型，如下所示：

```xml
<model>
    <mount>//myManufacturer/myModule</mount>
    <description>A description of this model (metadata)</description>
    <version>1.0.0</version>
    <items>
        <exampleNumber type="TextField">
            <Mask>/^([0-9]){0,1}$/</Mask>
            <Default>5</Default>
            <ValidationMessage>you should input a number from 0 to 9</ValidationMessage>
        </exampleNumber>
        <contacts>
            <entity type="ArrayField">
                <email type="EmailField">
                    <ValidationMessage>you should input a valid email address!</ValidationMessage>
                </email>
                <name type="TextField"/>
            </entity>
            <someText type="TextField"/>
        </contacts>
    </items>
</model>
```

現在讓我們一次一個標籤地解釋一下這裡發生了什麼。

1.  <model>標籤用於識別文件。 （這是一個模型檔）
    
2.  接下來是<mount>標籤，它告訴系統此資訊在設定檔中的位置，在本例中為ROOT\_tag/myManufacturer/myModule
    
3.  如果需要，可以保留一些空間來解釋模型的用法，<description>標籤
    
4.  新增版本標籤，用於支援遷移。這些在[遷移](<257 遷移.md>)主題中有更詳細的描述
    
5.  我們清單頂部的最後一項是<items>標籤，這就是魔法開始的地方。
    

items 標籤的內容描述了保存資料的完整的基於樹的結構，理論上它可以像您想要的那樣大，但請記住，模型的內容應該是合乎邏輯且易於理解的。樹中的每個節點都可以有一個類型，它定義其行為，沒有類型的節點只是容器。

從上到下，我們在樹中找到以下節點：

-   exampleNumber，定義為 TextField
    
    -   掩碼，驗證可以透過正規表示式執行，這設定了表達式
        
    -   默認，該欄位預設填入數字：5
        
    -   ValidationMessage，驗證失敗時傳回該訊息
        
-   聯絡人，這是一個容器
    
-   實體，被定義為重複項目，其中包含下一個項目
    
-   電子郵件，定義為 EmailField
    
    -   驗證失敗時，返回**ValidationMessage**
        
-   名稱，定義為沒有任何驗證的 TextField
    
-   someText，不是實體標籤的一部分，也定義為未經驗證的文本
    

欄位類型可以在基礎系統中輕鬆擴展，所有常見欄位類型都位於派生自 *BaseField* 的 *OPNsense\\Base\\FieldTypes* 中自己的命名空間中。

注意事項

設計應用程式特定的欄位類型時，您可以使用完整或部分路徑指向應用程式命名空間內的欄位類型。

例如，當從應用程式模型本身連結時，使用 *Vendor\\Component\\FieldTypes\\MyFieldType* 指向特定的非公共欄位類型或 *.\\MyFieldType* （假設存在名稱空間 FieldTypes）

## [易失性字段](#id2)

在某些情況下，定義充當標準欄位的欄位可能很實用，但不會保留在配置中。此類範例包括用於產生其他類型內容的字段，例如證書或反映儲存在其他位置的資料的字段。

若要讓欄位可變，只需在 xml 子句中新增標籤 `volatile="true"` 即可，例如：

```xml
<serial type="IntegerField" volatile="true"/>
```

## [記憶體模型](#id4)

在相同的情況下，使用所有標準模型工具可能是可行的，但會阻止資料被持久化。為此目的，可以使用記憶體模型。此類應用程式的範例是診斷工具，它確實需要使用者輸入，但僅與該特定呼叫相關。

若要使用這些模型，請使用以下安裝點：`<mount>:memory:</mount>`

## [舊包裝](#id5)

在遷移遺留元件時，有時當前情況（使用原始 xml 存取）與所需情況（經過充分驗證的模型）之間的距離很難克服。並不總是清楚正在使用哪種類型的數據，並且當在新模型中移動數據並更改其存取路徑時，必須進行適當的驗證。

當資料存在於它自己易於區分的“容器”中時，可以覆蓋標準模型。這種情況的一個例子是靜態路由組件。下面看起來像這樣（沒有有效負載）：

```xml
<staticroutes>
   <route/>
   <route/>
</staticroutes>
```

另一種情況是項目集合不在唯一容器內，例如以下有效負載：

```xml
<cert/>
<cert/>
<cert/>
```

在這種情況下，舊模組將迭代`$config['cert']`。由於`cert`沒有模型能夠完全控制的上層容器（因為它是`config.xml`的根），因此我們無法覆蓋標準模型來指定所使用的字段及其約束。

這就是我們的遺留包裝器發揮作用的地方。為了使用此功能，您必須使用以下安裝點格式：

> `/tag+` << 以精確路徑 \[`/`\] 開始，以加號 \[`+`\] 結束

在「cert」範例中，我們的安裝點希望：`<mount>/cert+</mount>`

注意事項

所有使用的欄位仍需要指定，模型中未包含的欄位將以與常規模型相同的方式從配置中刪除。

注意事項

由於舊包裝器無法進行版本控制，因此不適用遷移。從長遠來看，使用完整模型總是更好，但這些結構提供了「軟著陸」的選擇。

當目標欄位包含結構時，可以使用自訂（特定於應用程式）欄位類型套用內聯轉換。這種模式可能最好用一個例子來解釋。

下面是一個範例實現，它將每個使用者物件解壓縮多個 `<priv>` 標籤並將它們轉換為逗號分隔的清單。

第一個區塊`actionPostLoadingEvent()`僅收集可用選項，它是`BaseListField`類型的一部分。 `setValue()` 是神奇發生的地方，當輸入是 `SimpleXMLElement` 類型時，我們知道這是由載入器設定的，如果在這種情況下底層配置包含多個值，我們將它們合併到一個清單中。

```php
class PrivField extends BaseListField
{
   protected $internalIsContainer = false;
   private static $priv_list = null;

   protected function actionPostLoadingEvent()
   {
      if (self::$priv_list === null) {
            self::$priv_list = [];
            foreach ((new \OPNsense\Core\ACL())->getPrivList() as $aclKey => $priv) {
               self::$priv_list[$aclKey] = $priv['name'];
            }

      }
      $this->internalOptionList = self::$priv_list;
   }

   /**
   * {@inheritdoc}
   */
   public function setValue($value)
   {
      if (is_a($value, 'SimpleXMLElement') && $value->count() > 1) {
            return parent::setValue(implode(',', (array)$value));
      } else {
            return parent::setValue($value);
      }
   }
}
```

## [快取資料](#id6)

在某些情況下，存取模型資料需要在使用者願意等待的時間內進行過多的處理，在這些情況下，可以將快取的資料提供給模型的使用者。

為此，配置中的每個模型節點都包含一個具有最近更新時間的`persisted_at`字段，在這種情況下，可以使用靜態函數`getCachedData()`來獲取資料。這可以快速檢查物件是否已更改（透過 xpath 表達式），並以數組結構傳回模型的資料。

注意事項

儘管快取將包含使用`ArrayField`中的`getStaticChildren()`以程式設計方式產生的行，但它無法自動確定該內容是否已更改。

如果您需要確保這些記錄也被更新，您確實需要在靜態模型上呼叫`flushCacheData()`。 （例如`OPNsenseFirewallAlias::flushCacheData()`）
