# 小隊

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>)

由一名 leader 協調多名智慧體或成員，把工作交給合適的人。

小隊由一名 leader 智慧體和若干成員組成。把任務分配給小隊後，不會同時執行所有智慧體。Multica 會先喚醒 leader，由它閱讀上下文並決定下一步交給誰。

小隊解決的是把工作交給誰的問題。它不會把多個智慧體合併成一個新的智慧體，也不會自動提高併發。

## 適用場景

當工作需要多種能力，而且不能在建立任務時就確定具體負責人，可以使用小隊。例如，一個產品交付小隊可以包含前端、後端和測試智慧體，由 leader 根據每條任務的內容進行分配。

工作範圍明確時，直接分配給對應的[智慧體](/docs/zh/agents)即可。

## 小隊的組成

| 配置 | 作用 |
| --- | --- |
| **leader** | 必須是一名智慧體。接收分配給小隊的工作，並決定如何處理。 |
| **成員** | 可以是智慧體，也可以是人類成員。同一成員可以加入多個小隊。 |
| **角色說明** | 告訴 leader 每個成員適合處理什麼工作。它只是上下文，不會授予許可權或自動觸發成員。 |
| **小隊指令** | 儲存路由規則、協作方式和需要貫穿全隊的背景，只會提供給 leader。 |

建立小隊時需要填寫名稱並選擇 leader。小隊 leader 會自動成為成員；之後可以繼續新增成員、填寫角色說明和小隊指令。

## 分配後的執行流程

非 backlog 狀態的任務分配給小隊後，Multica 會立刻給**隊長智慧體**入隊一次執行（不是給每個成員都入一個）：

1.  **隊長的執行時領走執行**，和普通智慧體的分配流程一樣。
2.  **隊長拿到 briefing。** 領走的瞬間，Multica 會在隊長的指令後面追加三段內容，見下文隊長每次執行看到的內容。
3.  **隊長髮一條派活評論。** 評論裡用花名冊給好的 mention markdown `@` 選中的成員——這個 `@` 會觸發被派的成員入隊新執行。
4.  **隊長記錄 evaluation**：`multica squad activity <issue-id> <outcome> --reason "..."`。這一行會寫進任務的 activity 時間線，方便人類回溯隊長的每次評估。
5.  **派活輪讓父任務處於 `in_progress`。** 和直接分配給智慧體同一套狀態約定：協調小隊就是在推進父任務本身的工作，所以父任務從 `todo` 進入 `in_progress`；派活不等於交付，小隊幹活期間保持不變。
6.  **隊長停下。** 派完活，隊長不親自動手。被派成員有回覆時，隊長會被自動喚醒，決定下一步：繼續派活、上拋給人類、在整體目標達成後把父任務推到 `in_review`，或保持沉默。`done` 留給人工確認或既有整合（例如帶 close intent 的 PR merge）。

如果任務仍在 `backlog`，分配本身不會觸發隊長。移出 `backlog` 後才會開始執行。

### 隊長每次執行看到的內容

每次隊長被觸發，三段內容會附加到它的指令上：

-   **Squad Operating Protocol（小隊工作規範）**——一段硬編碼的規則集：讀任務 → 用 `@` 派活 → 保持簡潔（不復述任務內容，被派的成員自己能讀）→ 每次記 evaluation → 派完就停（派活輪結束時父任務處於 `in_progress`）→ 整體目標達成後才推 `in_review`。這段由系統管理，不可編輯。

其中狀態相關的規則只對"確實分配給本小隊"的任務生效。隊長被別人任務裡的 `@小队` 喚醒時，同樣拿到花名冊和派活規則，但會被明確告知不要改動那條任務的狀態——狀態仍歸它自己的負責人。

-   **Squad Roster（小隊花名冊）**——隊長一行 + 每個未歸檔成員一行，每行帶可直接複製的 mention markdown（`[@Name](mention://agent/<uuid>)`）。純文本 `@name` 不會觸發任何人。
-   **Squad Instructions（小隊指令）**——你為這個小隊寫的自定義內容：路由規則（"資料庫相關派給 Alice，前端派給 Bob"）、上報策略，或任務本身不會有的背景。

## 隊長的再次觸發時機

第一次派活之後，大多數後續評論會自動喚醒隊長：

| 事件 | 觸發隊長 |
| --- | --- |
| 非小隊成員（人類、外部智慧體）發評論 | 會 |
| 小隊成員發進展更新，不帶任何 `@` | 會——隊長重新評估下一步 |
| 任何評論裡顯式 `@` 了智慧體、成員、小隊或 `@all` | 不會——顯式 `@` 就是路由訊號，隊長讓位 |
| 隊長自己發的評論 | 不會——防自觸發 |
| 評論裡只有任務互鏈 | 會——任務引用不算路由 |

在這些規則之上還有去重：如果隊長在這條任務上已有處於排隊或已領取狀態的執行，新觸發不會重複入隊。

成員發的 `@` 評論不喚醒隊長，是因為直接 `@` 已經是明確的交接，再喚醒隊長只會多一輪空轉。例外：智慧體髮結果時順手 `@` 了另一個智慧體，隊長仍會被喚醒，以便協調整條執行緒。

## 分配小隊和 @小隊

| 操作 | 是否改變負責人 | 結果 |
| --- | --- | --- |
| **把任務分配給小隊** | 是 | 小隊成為負責人，並觸發 leader。 |
| **在評論中 @小隊** | 否 | 只讓 leader 處理這條評論，原負責人不變。 |

直接 @某名成員時，工作會交給該成員處理。Multica 也會合並重復觸發並阻止 leader 的評論再次觸發自己，避免形成執行迴圈。

## 小隊與 Access

把智慧體加入小隊不會繞過它的 [Access](/docs/zh/agents#%E6%9D%83%E9%99%90%E4%B8%8E-access)。普通成員建立或管理小隊時，只能選擇自己有權執行的智慧體。

成員能否分配或 @某個小隊，也取決於其是否有權執行小隊的 leader。若 leader 已歸檔，或當前成員無權執行它，這個小隊就無法被分配或 @提及。

## 建立與管理許可權

任何工作區成員都可以建立小隊。建立者可以修改和歸檔自己建立的小隊；工作區 `owner` 和 `admin` 可以管理所有小隊。

小隊名稱不要求在工作區中唯一。更換 leader 時，新 leader 會自動加入小隊；當前 leader 不能直接移除，需要先指定另一名 leader。

## 歸檔小隊

歸檔後，小隊會從列表、負責人選擇器和 @選單中消失，也不能恢復。

為避免現有工作失去負責人，當前分配給小隊的任務和自動化會轉給原 leader 智慧體。歷史評論和活動記錄仍然保留。如果之後還需要相同的路由，需要重新建立小隊。

歸檔操作無法撤銷。

## 使用 CLI

```
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
 --member-id <agent-or-member-id> \
 --type agent \
 --role "负责前端实现"
```

完整命令見 [使用 CLI](/docs/zh/cli)。
