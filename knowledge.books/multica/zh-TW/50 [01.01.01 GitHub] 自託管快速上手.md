# 自託管快速上手

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>) › [GitHub](<000 目錄.md#c-3>)

用 Docker Compose 啟動 Multica，完成登入，並連線第一臺執行電腦。

自託管 Multica 分成兩部分：

| 部分 | 執行什麼 | 放在哪裡 |
| --- | --- | --- |
| **Multica 服務** | Web、API 和 PostgreSQL | 一臺安裝了 Docker 的機器 |
| **執行電腦** | Multica 守護程序和 AI 程式設計工具 | 開發者實際工作的電腦 |

它們可以是同一臺機器，也可以分開。自託管替換的只是 Multica Cloud 部分。

這篇文件使用 Docker Compose。Kubernetes 部署見倉庫中的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

## [開始前](#%E5%BC%80%E5%A7%8B%E5%89%8D)

執行 Multica 服務的機器需要：

-   Docker Engine 或 Docker Desktop，並且 `docker compose` 可以執行
-   Git、Make、curl 和 OpenSSL
-   本機的 `3000`、`8080` 埠未被佔用

先確認 Docker 和 Compose 可用：

```bash
docker info
docker compose version
```

Multica 使用 Compose v2，也就是 `docker compose`。舊版的 `docker-compose` v1 不受支援。

執行電腦還需要至少一款已經安裝並登入的 [AI 程式設計工具](<69 [01.01.01 GitHub] AI 程式設計工具對照.md>)，例如 Claude Code、Codex 或 Cursor。第 5 步再安裝 Multica CLI。

## [1\. 啟動 Multica](#1-%E5%90%AF%E5%8A%A8-multica)

在準備執行服務的機器上執行：

```bash
git clone --depth 1 https://github.com/multica-ai/multica.git
cd multica
make selfhost
```

第一次執行時，`make selfhost` 會：

1.  從 `.env.example` 建立 `.env`
2.  隨機生成 `JWT_SECRET`、PostgreSQL 密碼和 `MULTICA_VCS_SECRET_KEY`（自託管 Git 整合的加密金鑰）
3.  拉取 PostgreSQL、Multica backend 和 Multica frontend 映象
4.  建立持久化資料卷並啟動三個容器
5.  等待 backend 開始響應健康檢查

之後再次執行 `make selfhost` 會繼續使用現有的 `.env` 和資料卷，不會重新生成金鑰。

`make selfhost` 拉取已釋出的映象，不會編譯當前 checkout 中的程式碼。需要測試本地原始碼時，使用 `make selfhost-build`。

已釋出的映象跟隨最新的 **release tag**，而直接 `git clone` 檢出的是 `main`，通常領先於發版。如果你要在這個 checkout 上構建任何東西——CLI，或通過 `make selfhost-build` 構建映象——先切換到與映象對應的 release tag，讓構建產物和執行中的容器保持同一版本：

```bash
git fetch --tags --depth 1
git checkout $(git tag -l 'v*' --sort=-v:refname | head -1)
```

## [2\. 確認服務已經就緒](#2-%E7%A1%AE%E8%AE%A4%E6%9C%8D%E5%8A%A1%E5%B7%B2%E7%BB%8F%E5%B0%B1%E7%BB%AA)

檢視容器狀態：

```bash
docker compose -f docker-compose.selfhost.yml ps
```

`postgres` 顯示為 `healthy`，`backend` 和 `frontend` 應處於執行狀態。然後檢查 backend、資料庫和 migration：

```bash
curl -fsS http://localhost:8080/readyz
```

正常響應是：

```json
{"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

Backend 容器每次啟動時都會先執行資料庫 migration，再啟動服務，不需要手動執行 migration 命令。

## [3\. 選擇訪問方式](#3-%E9%80%89%E6%8B%A9%E8%AE%BF%E9%97%AE%E6%96%B9%E5%BC%8F)

### [本機訪問](#%E6%9C%AC%E6%9C%BA%E8%AE%BF%E9%97%AE)

直接開啟 \[http://localhost:3000P172。后面运行 `multica setup self-host` 時也不需要傳 URL。

### [遠端訪問](#%E8%BF%9C%E7%A8%8B%E8%AE%BF%E9%97%AE)

Docker Compose 預設只把 `3000` 和 `8080` 繫結到 `127.0.0.1`。不要直接改成 `0.0.0.0` 暴露到公網；使用帶 HTTPS 的反向代理。

下面以兩個域名為例：

-   `app.example.com`：Multica Web
-   `api.example.com`：API、健康檢查和守護程序連線

先在 `.env` 中設定公開地址：

```
FRONTEND_ORIGIN=https://app.example.com
MULTICA_APP_URL=https://app.example.com
MULTICA_PUBLIC_URL=https://api.example.com
```

以上配置讓瀏覽器流量全部走 app 域，cookie 不跨域，因此不需要配置 `COOKIE_DOMAIN`。如果改為讓瀏覽器直接訪問 api 域，則必須配置它，見[環境變數](<81 [01.01.01 GitHub] 環境變數.md>)。

然後配置 DNS，並用 Caddy 代理本機埠：

```
app.example.com {
 # 浏览器的 WebSocket 直接交给 backend
 @ws path /ws /ws/*
 handle @ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # 其余路径交给 frontend；它会转发 API 和登录请求
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}

api.example.com {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
}
```

如果想讓所有流量走**單一 origin**（一個域名，或一臺主機一個埠——小伺服器上常見），把守護程序依賴的路徑顯式轉給 backend，其餘交給 frontend：

```
multica.example.com {
 # CLI 可达性探测：`multica setup` 会 GET <server-url>/health 并要求 200，
 # 旧版 frontend 不转发这个路径，直接路由到 backend
 handle /health {
 reverse_proxy 127.0.0.1:8080
 }

 # 网页端 realtime WebSocket——前端镜像代理不了 WS 升级，直通 backend
 handle /ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # daemon 长连接：拨的是 {server-url}/api/daemon/ws（不是 /ws）。
 # 缺了这条，握手失败后 daemon 会静默回退到轮询
 handle /api/daemon/ws {
 reverse_proxy 127.0.0.1:8080 {
 flush_interval -1
 }
 }

 # 其余路径交给 frontend；它会转发 API 和登录请求
 handle {
 reverse_proxy 127.0.0.1:3000
 }
}
```

單一 origin 模式下，兩個 URL 都指向它（`.env` 裡的 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL`，以及 `multica setup self-host` 的 `--server-url` 和 `--app-url`）。

Caddy 會申請 TLS 證書並轉發 WebSocket。修改 `.env` 後，用 `up -d` 重新建立容器，讓新配置生效：

```bash
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | grep -o '"daemon_server_url":"[^"]*"'
```

最後一條命令輸出 `daemon_server_url`——daemon 連線 API 用的地址：設了 `MULTICA_DAEMON_SERVER_URL` 時用它，其次是 `MULTICA_PUBLIC_URL`，否則用 app URL（`MULTICA_APP_URL`，未設定時回退到 `FRONTEND_ORIGIN`）。當 `MULTICA_APP_URL` 和 `FRONTEND_ORIGIN` 都沒設時，這個欄位會整個從響應裡省略（上面的 grep 無輸出）——即使設了 `MULTICA_DAEMON_SERVER_URL` 或 `MULTICA_PUBLIC_URL` 也是如此。如果輸出的是 `localhost`，說明 `.env` 裡還是本地預設值：不要依賴從 `.env.example` 複製來的 `${FRONTEND_PORT}` 引用，把 `FRONTEND_ORIGIN` 和 `MULTICA_APP_URL` 顯式設定為公網地址，然後重建容器。

`docker compose restart` 只重啟現有容器，不會重新讀取 `.env`。修改配置後，重新讀取 `.env` 需要執行 `docker compose -f docker-compose.selfhost.yml up -d`。

## [4\. 登入並建立工作區](#4-%E7%99%BB%E5%BD%95%E5%B9%B6%E5%88%9B%E5%BB%BA%E5%B7%A5%E4%BD%9C%E5%8C%BA)

開啟本機的 `http://localhost:3000`，或剛才配置的 `https://app.example.com`，輸入郵箱獲取驗證碼。

預設沒有配置郵件服務。請求驗證碼後，可以從 backend 日誌中讀取：

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
 | grep "Verification code"
```

日誌中會出現類似內容：

```
[DEV] Verification code for you@example.com: 123456
```

輸入驗證碼並建立第一個工作區。配置 Resend 或 SMTP 後，驗證碼通過郵件傳送，成員無需讀取容器日誌，具體見[登入與註冊配置](<82 [01.01.01 GitHub] 登入與註冊.md>)。

自託管部署預設使用 `APP_ENV=production`，不會啟用固定驗證碼。不要在公網例項上設定 `MULTICA_DEV_VERIFICATION_CODE`。

## [5\. 連線執行電腦](#5-%E8%BF%9E%E6%8E%A5%E6%89%A7%E8%A1%8C%E7%94%B5%E8%84%91)

下面的命令在**執行 AI 程式設計工具的電腦**上執行，不一定是執行 Docker 的伺服器。

每次執行都擁有守護程序所屬使用者的全部許可權——該使用者能讀寫的一切，執行都能讀寫。請用專用 Unix 使用者、容器或虛擬機器來執行守護程序，而不是你的個人賬號。詳見[安全模型](<80 [01.01.01 GitHub] 安全模型.md>)。

先安裝 Multica CLI：

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash
```

**Windows PowerShell**

```
irm https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.ps1 | iex
```

如果 Multica 服務也在這臺電腦上，執行：

```
multica setup self-host
```

如果 Multica 服務在另一臺機器上，傳入剛才配置的兩個地址：

```
multica setup self-host \
 --server-url https://api.example.com \
 --app-url https://app.example.com
```

這條命令會先檢查 `<server-url>/health`，再開啟瀏覽器完成登入。登入完成後，它會儲存本機憑據並啟動守護程序。這一步報 `Server not reachable`，說明 `/health` 沒有通過探測拿到 200：可能是代理把所有流量轉給了不轉發該路徑的舊版 frontend，可能是代理根本沒把 `/health` 路由到 backend，也可能是更底層的問題（DNS、TLS、防火牆、超時、backend 返回 5xx）——見[故障排查](<83 [01.01.01 GitHub] 故障排查.md#multica-setup-%E6%8A%A5%E5%91%8A%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%8D%E5%8F%AF%E8%BE%BE>)。

確認連線狀態：

```
multica daemon status
```

正常情況下，輸出中會顯示：

-   `Daemon: running`
-   `Agents` 中包含本機已安裝的 AI 程式設計工具
-   `Workspaces` 大於 `0`

## [6\. 完成第一次執行](#6-%E5%AE%8C%E6%88%90%E7%AC%AC%E4%B8%80%E6%AC%A1%E6%89%A7%E8%A1%8C)

回到 Multica。執行時列表中出現線上的執行時後，建立一個智慧體，並把第一個任務分配給它。

執行日誌變為"已完成"、時間線中出現智慧體的回覆，說明自託管服務、執行電腦和 AI 程式設計工具已經連通。詳細步驟見[快速上手](<46 [01.01.01 GitHub] 快速上手.md>)第 3-5 步。

## [常用管理命令](#%E5%B8%B8%E7%94%A8%E7%AE%A1%E7%90%86%E5%91%BD%E4%BB%A4)

以下命令都在 `multica` 倉庫目錄中執行：

```bash
# 查看状态
docker compose -f docker-compose.selfhost.yml ps

# 查看 backend 日志
docker compose -f docker-compose.selfhost.yml logs -f backend

# 应用 .env 变化
docker compose -f docker-compose.selfhost.yml up -d

# 停止服务，保留数据卷
docker compose -f docker-compose.selfhost.yml down
```

升級已釋出的映象：

```bash
git pull --ff-only
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS http://localhost:8080/readyz
```

Docker Compose 部署有兩種升級寫法。在已有部署上兩者**結果相同**——`Makefile` 裡的 `selfhost` target 跑的就是同一套 `docker compose pull` + `up -d`，只是額外多做了兩件事：`.env` 缺失時生成一份，以及等 `/health` 就緒後列印一段狀態彙總。用哪個都行：

```bash
cd multica
git pull
make selfhost
```

```bash
cd multica
git pull
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

### [`git pull` 到底更新了什麼](#git-pull-%E5%88%B0%E5%BA%95%E6%9B%B4%E6%96%B0%E4%BA%86%E4%BB%80%E4%B9%88)

`git pull` 更新的是 **`docker-compose.selfhost.yml` 本身**——新增的環境變數、新增的服務、改過的 healthcheck。它**不是**拉新版本 Multica 的機制。

真正決定你跑哪個版本的是 `docker compose pull`：它去 GHCR 查這個 tag 當前指向哪個映象。所以一個幾個月沒更新的 checkout 照樣能拉到今天的 `latest` 映象；反過來，只跑 `git pull` 而不拉映象、不重建容器，什麼都不會變。

**如果你在 `.env` 裡釘死了 `MULTICA_IMAGE_TAG`，兩種寫法都升不上去。** 兩個映象都寫成 `${MULTICA_IMAGE_TAG:-latest}`（`docker-compose.selfhost.yml:42`、`:125`），而 `.env.example` 裡預設是 `MULTICA_IMAGE_TAG=latest`。一旦你把它改成了具體版本，`pull` 只是把同一個 tag 重拉一遍，版本原地不動——不報錯，也沒有任何警告。升級前先確認：

```
grep MULTICA_IMAGE_TAG .env
# MULTICA_IMAGE_TAG=v0.4.5 ← 钉死了：先改成 latest（或你想要的版本）
```

### [`.env` 不會被覆蓋](#env-%E4%B8%8D%E4%BC%9A%E8%A2%AB%E8%A6%86%E7%9B%96)

`make selfhost` 只在 `.env` **不存在**的時候才生成它。在已有部署上重複跑，你的 `JWT_SECRET`、Postgres 密碼、郵件配置、`FRONTEND_ORIGIN` 都原樣保留。

### [升級前先備份 Postgres](#%E5%8D%87%E7%BA%A7%E5%89%8D%E5%85%88%E5%A4%87%E4%BB%BD-postgres)

migration 只往前走、不回滾，所以正式環境升級前先導一份：

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
 pg_dump -U multica multica > multica-backup.sql && gzip multica-backup.sql
```

**不要把 `pg_dump` 直接管道接給 `gzip`。** shell 取的是管道里**最後一條**命令的退出碼，所以 `pg_dump ... | gzip > backup.sql.gz` 在匯出失敗時照樣返回 `0`，留下一個格式完全合法、但裡面什麼都沒有的 20 位元組壓縮包。先重定向到檔案，`pg_dump` 自己的退出碼才算數，`&&` 也只會壓縮真正成功的那份匯出。

如果你改過 `POSTGRES_USER` / `POSTGRES_DB`，把 `multica` 換成 `.env` 裡的實際值。資料存在名為 `multica_pgdata` 的 volume 裡，`docker compose down` 不會刪它——但 `down -v` 會。

### [migration 自動執行](#migration-%E8%87%AA%E5%8A%A8%E6%89%A7%E8%A1%8C)

和[第 1 步](#1-%E5%90%AF%E5%8A%A8-multica)一樣，backend 容器啟動時會在對外提供服務之前先跑 `./migrate up`（`docker/entrypoint.sh`）。沒有單獨的升級命令——把新映象起起來，本身就是升級這一步。想看過程：

```bash
docker compose -f docker-compose.selfhost.yml logs -f backend
```

Migration 在 backend 啟動時自動執行；需要回填歷史資料的 migration（如 103）也會自動完成回填。自動回填極少數情況下失敗，報 `refusing to drop legacy daily rollups`，處理見[故障排查](<83 [01.01.01 GitHub] 故障排查.md#%E5%8D%87%E7%BA%A7%E6%97%B6-migration-103-%E6%8B%92%E7%BB%9D%E6%89%A7%E8%A1%8C>)。

### [用 `/readyz` 驗證，不要用 `/health`](#%E7%94%A8-readyz-%E9%AA%8C%E8%AF%81%E4%B8%8D%E8%A6%81%E7%94%A8-health)

`/health` 是 **liveness** 探針，只要程序還活著就返回 `{"status":"ok"}`，migration 失敗了它照樣是 ok。`/readyz`（`server/cmd/server/router.go:680`，`/healthz` 是它的別名）會真正檢查資料庫和已應用的 migration 集合，升級出問題能被它攔下來：

```bash
curl -s localhost:8080/readyz
# {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

只要不是 HTTP 200 且兩項都是 `ok`，就說明新版本沒把 migration 跑完，先去看 backend 日誌，別急著放流量進來。

### [Kubernetes](#kubernetes)

Helm 有自己的升級路徑：在 values 檔案裡把 `images.backend.tag` / `images.frontend.tag` 設成你要的版本，然後 `helm upgrade`。改 tag 就改了 pod spec，Kubernetes 會拉新映象並滾動更新——這是可靠的路徑。

`kubectl -n multica rollout restart` 本身**不是**升級。chart 預設 `pullPolicy: IfNotPresent`（`deploy/helm/multica/values.yaml`），節點上已經快取過這個 tag 的話，restart 只會用回舊映象，什麼都沒變——和釘死 `MULTICA_IMAGE_TAG` 是同一類坑。真要靠浮動 tag 走這條路，得先把 `images.backend.pullPolicy` / `images.frontend.pullPolicy` 設成 `Always`。詳見倉庫的 [Self-hosting guide](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative)。

`docker compose down` 會保留 `pgdata` 和 `backend_uploads`。加上 `-v` 會刪除這些資料卷，包括資料庫；除非確定要清空例項，否則不要執行 `docker compose down -v`。

## [常見問題](#%E5%B8%B8%E8%A7%81%E9%97%AE%E9%A2%98)

| 現象 | 先檢查什麼 |
| --- | --- |
| `/readyz` 沒有返回 `ok` | 執行 `docker compose -f docker-compose.selfhost.yml logs backend postgres`。 |
| 收不到驗證碼 | 請求一次驗證碼，再從 backend 日誌中查詢 `Verification code`。 |
| `setup self-host` 提示 server 不可達 | 在執行電腦上請求 `https://api.example.com/health`，確認 DNS、TLS 和反向代理都可達。返回 404 說明代理把 `/health` 轉給了不轉發該路徑的舊版 frontend——改為直通 backend（見[故障排查](<83 [01.01.01 GitHub] 故障排查.md#multica-setup-%E6%8A%A5%E5%91%8A%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%8D%E5%8F%AF%E8%BE%BE>)）。 |
| 守護程序沒有列出 `Agents` | 確認 AI 程式設計工具在 `PATH` 中並已登入，然後執行 `multica daemon restart`。 |
| 任務一直排隊 | 執行 `multica daemon status`，確認守護程序正在執行並連線了工作區。 |

更多情況見[故障排查](<83 [01.01.01 GitHub] 故障排查.md>)。
