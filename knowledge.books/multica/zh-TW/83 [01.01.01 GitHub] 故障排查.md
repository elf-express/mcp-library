# 故障排查

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>) › [GitHub](<000 目錄.md#c-3>)

排查連線、執行、即時更新、郵件和自託管服務中的常見問題。

先確認問題發生在哪一層：Multica 服務、守護程序、執行時，還是 AI 程式設計工具。下面幾條命令通常足以找到第一條有效錯誤：

```
multica version
multica auth status
multica daemon status --output json
multica daemon logs --lines 100
```

自託管例項還可以直接檢查服務：

```bash
curl -i https://api.example.com/health
curl -i https://api.example.com/readyz
```

`/health` 只說明 API 程序正在響應；`/readyz` 還會檢查資料庫和 migration。問題反饋包含報錯、相關日誌、CLI 版本和作業系統；令牌、郵箱等敏感資訊在提交前移除。

## [守護程序連線失敗](#%E5%AE%88%E6%8A%A4%E8%BF%9B%E7%A8%8B%E8%BF%9E%E6%8E%A5%E5%A4%B1%E8%B4%A5)

先執行：

```
multica auth status
multica daemon status --output json
multica daemon logs --lines 100
```

常見原因包括：

-   CLI 尚未登入，或本機儲存的令牌已經失效；
-   守護程序連線了錯誤的 Multica 服務；
-   執行電腦無法訪問 API，或 DNS、TLS、防火牆攔截了連線；
-   當前賬號已經不在目標工作區中；
-   本機沒有安裝任何受支援的 AI 程式設計工具，守護程序因此無法啟動。

重新登入並重啟守護程序：

```
multica login
multica daemon restart
```

自託管部署還需要從**執行電腦**請求 API 的 `/health`——伺服器本機測試無法暴露執行電腦側的 DNS、TLS 或防火牆問題。需要修改地址時，重新執行 `multica setup self-host`，或檢查當前 profile 的 `server_url`：

```
multica config show
```

## [任務未開始執行](#%E4%BB%BB%E5%8A%A1%E6%9C%AA%E5%BC%80%E5%A7%8B%E6%89%A7%E8%A1%8C)

開啟任務的**執行日誌**，先看執行的當前狀態和等待原因。

### [`queued` 狀態](#queued-%E7%8A%B6%E6%80%81)

`queued` 表示執行還在等待執行時領取。依次檢查：

1.  智慧體繫結的執行時是否線上；
2.  執行時是否檢測到了該智慧體配置的 AI 程式設計工具；
3.  智慧體是否還有可用併發額度；
4.  守護程序是否還有全域執行容量。

智慧體預設最多同時執行 6 次執行；單個守護程序預設最多同時執行 20 次。達到上限時，新執行會留在佇列中，等已有執行結束後再開始。執行時離線時，執行也會繼續排隊；只有該執行時心跳缺席超過重連寬限期、且該執行自己也已等滿這麼久時才會失敗；所以排在忙碌執行時後面的長佇列不會因為等太久而被判失敗，指派給已經離線的機器時也仍然留有完整一個寬限期把它喚醒。

```
multica daemon status --output json
multica agent get <agent-id>
multica issue runs <issue-id>
```

如果執行時列表缺少預期工具，先在同一個系統賬號和 `PATH` 中確認工具可以執行並且已經登入，再執行 `multica daemon restart`。

### [`waiting_local_directory` 狀態](#waiting_local_directory-%E7%8A%B6%E6%80%81)

這表示另一條在途執行正在使用同一個本地目錄。Multica 會等待目錄鎖釋放，避免兩個智慧體同時修改同一份檔案。

這種等待只存在於目錄的 `in_place`（“原地”）模式。如果這個目錄是 git 倉庫，把資源切到 `worktree`（“並行”）就沒有隊列了：每次執行拿到自己的 worktree，並以分支形式交回結果，誰都不用等誰。見[專案資源](<55 [01.01.01 GitHub] 專案資源.md#task-%E5%A6%82%E4%BD%95%E5%85%B1%E4%BA%AB%E8%BF%99%E4%B8%AA%E7%9B%AE%E5%BD%95>)。

否則通常只需等前一次執行結束。若前一次已經卡住，可以從它的執行日誌中停止；也可以為當前智慧體選擇其他本地目錄。這個目錄互斥由守護程序在記憶體中維護，不寫磁碟鎖檔案；懷疑鎖狀態異常時執行 `multica daemon restart` 即可釋放，沒有需要手動刪除的檔案。

## [AI 程式設計工具啟動失敗](#ai-%E7%BC%96%E7%A8%8B%E5%B7%A5%E5%85%B7%E5%90%AF%E5%8A%A8%E5%A4%B1%E8%B4%A5)

守護程序線上不代表工具本身可用。開啟這次執行的詳細記錄，重點檢查：

-   工具是否已經完成登入；
-   API key、額度或模型許可權是否可用；
-   智慧體選擇的模型和思考級別是否被該工具支援；
-   本地工作目錄是否存在並且可寫；
-   智慧體的自定義引數或環境變數是否有效。

先在執行電腦的終端中直接運行同一款工具。工具自身也無法開始時，先修復工具登入或配置，再從執行日誌重試執行。

## [升級 CLI 後 macOS 上的執行卡住](#%E5%8D%87%E7%BA%A7-cli-%E5%90%8E-macos-%E4%B8%8A%E7%9A%84%E8%BF%90%E8%A1%8C%E5%8D%A1%E4%BD%8F)

通過 Homebrew 安裝的 `multica` CLI 升級後（無論是 `brew upgrade`、`multica update`、**執行時**頁面上的**更新**，還是守護程序自動更新），讀取 `~/Desktop`、`~/Documents`、`~/Downloads`、iCloud 雲盤或其他受保護資料夾的執行可能停滯：智慧體程序不佔用 CPU，執行既不結束也不失敗。

這種情況出現在 macOS 把隱私權限（TCC）記在守護程序本身名下時，由 launchd 啟動的守護程序（例如 LaunchAgent）就是如此：等待中的彈窗顯示的是 `multica`，智慧體啟動的所有工具都沿用守護程序的授權。Homebrew 版 CLI 沒有使用固定身份簽名，macOS 只能把授權繫結到這一次構建及其解析後的路徑，例如 `/opt/homebrew/Cellar/multica/<version>/bin/multica`。升級後，macOS 把新二進位制當作另一個應用，重新請求授權；在有人處理之前檔案訪問會一直阻塞，守護程序也無法感知有授權彈窗在等待。

恢復訪問：

1.  在這臺 Mac 上找到等待中的"想要訪問"彈窗，點選**允許**，卡住的執行會繼續。
2.  無人值守的 Mac 請給新二進位制授予完全磁碟訪問許可權。用 `realpath "$(command -v multica)"` 列印路徑，然後在**系統設定 → 隱私與安全性 → 完全磁碟訪問許可權**中刪除舊的 `multica` 條目並新增該路徑（在檔案選擇器中按 ⌘⇧G 貼上路徑）。
3.  按啟動守護程序時的方式重啟它：`multica daemon restart`；LaunchAgent 則用 `launchctl kickstart -k gui/$(id -u)/<label>`。

每次升級 CLI 後都需要重複這些步驟。只有連線 Multica Cloud 的守護程序預設開啟自動更新；用 `--no-auto-update` 啟動守護程序後，只在你手動升級時更新。[桌面應用](<78 [01.01.01 GitHub] 桌面應用.md>)內建的 CLI 使用 Developer ID 簽名，授權在升級後依然有效。

## [即時更新失效](#%E5%AE%9E%E6%97%B6%E6%9B%B4%E6%96%B0%E5%A4%B1%E6%95%88)

執行仍能執行、但評論和狀態不能即時出現，通常是 WebSocket 沒有連通。

在瀏覽器開發者工具的 **Network → WS** 中檢視 `/ws` 連線。自託管部署重點檢查：

-   `FRONTEND_ORIGIN` 是否和瀏覽器實際開啟的地址一致；
-   HTTPS 頁面是否通過 `wss://` 連線；
-   反向代理是否轉發 WebSocket 的 Upgrade 請求；
-   瀏覽器登入是否已經過期。

直接用 `curl` 訪問 `/ws` 返回 HTTP 400 是正常現象：該端點要求帶 workspace 相關的查詢引數，裸握手在進入 WebSocket 升級之前就會被拒。所以 backend 日誌裡出現 400/401 記錄，只能說明普通 HTTP 路由已經到達 backend——並不能證明代理保留了 WebSocket `Upgrade` 頭。要驗證真正的連線，請開啟瀏覽器開發者工具的 Network → WS 面板（或用支援 WebSocket 的客戶端），看是否出現 `101` 握手。

自部署注意：daemon 的長連線撥的是 `/api/daemon/ws`（不是 `/ws`），同樣要直通後端；握手失敗時 daemon 會靜默回退到輪詢，backend 日誌裡該路徑反覆出現 `status=400` 即中招。

容器只在建立時讀取 `.env`，修改後需要重新建立：

```bash
docker compose -f docker-compose.selfhost.yml up -d
```

完整的反向代理示例見[自託管快速上手](<50 [01.01.01 GitHub] 自託管快速上手.md#3-%E9%80%89%E6%8B%A9%E8%AE%BF%E9%97%AE%E6%96%B9%E5%BC%8F>)。

## [`multica setup` 報告伺服器不可達](#multica-setup-%E6%8A%A5%E5%91%8A%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%8D%E5%8F%AF%E8%BE%BE)

CLI 的可達性探測會 GET `<server-url>/health` 並要求 200。backend 提供這個路徑。新版 web 前端會把 `/health` 轉發給 backend，舊版不會——把所有流量都轉給舊版 frontend 的反向代理會返回 404，於是 CLI 誤判服務不可用，而服務實際是健康的。

在代理裡把 `/health` 顯式轉給 backend（8080 埠），對所有版本都適用——[自託管快速上手](<50 [01.01.01 GitHub] 自託管快速上手.md#3-%E9%80%89%E6%8B%A9%E8%AE%BF%E9%97%AE%E6%96%B9%E5%BC%8F>)裡的兩個 Caddy 示例都包含這條。確認方法：

```bash
curl -fsS <server-url>/health
```

## [`multica login` 報告 TLS 握手超時](#multica-login-%E6%8A%A5%E5%91%8A-tls-%E6%8F%A1%E6%89%8B%E8%B6%85%E6%97%B6)

`multica login` 能開啟瀏覽器、網頁登入也能完成，但 CLI 仍以 "Sign-in did not complete" 或 "TLS 握手超時" 失敗。`multica --debug login` 在 `POST /api/tokens` 上顯示 `net/http: TLS handshake timeout`，而同一臺機器上的 `curl.exe -I https://api.multica.ai` 或瀏覽器都能正常連線。

TCP 連線已建立，但 TLS 握手始終沒有完成。Go 客戶端（包括 Multica CLI 和守護程序）預設在 TLS ClientHello 中攜帶後量子金鑰交換，報文約 1.5 KB，會拆成兩個包傳送。部分安全軟體、VPN、路由器和防火牆會丟棄這種握手；curl 的 ClientHello 小得多，所以能通過。

先關閉後量子金鑰交換重試，確認是否為此原因：

```powershell
$env:GODEBUG = 'tlsmlkem=0'
multica --debug login
```

```
GODEBUG=tlsmlkem=0 multica --debug login
```

如果這樣能成功，請為執行 CLI 和守護程序的使用者永久設定 `GODEBUG=tlsmlkem=0`——Windows 上執行 `[Environment]::SetEnvironmentVariable('GODEBUG', 'tlsmlkem=0', 'User')` 後重新開啟終端——然後重啟守護程序或桌面應用。調高 `MULTICA_HTTP_TIMEOUT` 無效，它不控制握手。根本解決需要在網路側處理：升級或重新配置丟棄分包 TLS 握手的裝置或軟體。

## [驗證碼與邀請郵件未送達](#%E9%AA%8C%E8%AF%81%E7%A0%81%E4%B8%8E%E9%82%80%E8%AF%B7%E9%82%AE%E4%BB%B6%E6%9C%AA%E9%80%81%E8%BE%BE)

先檢視 backend 啟動日誌。日誌會說明當前使用 `SMTP relay`、`Resend API` 還是 `DEV mode`：

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
 | grep "EmailService:"
```

-   **DEV mode**：郵件不會發出，驗證碼和邀請連結只寫入 backend 日誌；
-   **Resend**：確認 API key 有效，且發件地址的域名已經驗證；
-   **SMTP**：確認主機、埠、憑據和發件地址，並從錯誤日誌判斷失敗發生在連線、TLS、認證還是投遞階段。

`SMTP_HOST` 和 Resend 同時配置時，Multica 會優先使用 SMTP。配置方式見[登入與註冊](<82 [01.01.01 GitHub] 登入與註冊.md#%E9%82%AE%E7%AE%B1%E9%AA%8C%E8%AF%81%E7%A0%81>)。

生產環境不要依賴日誌中的驗證碼，也不要啟用固定本地測試驗證碼。

## [附件上傳或下載失敗](#%E9%99%84%E4%BB%B6%E4%B8%8A%E4%BC%A0%E6%88%96%E4%B8%8B%E8%BD%BD%E5%A4%B1%E8%B4%A5)

先檢查 backend 日誌和響應狀態碼。常見原因是：

-   反向代理限制了請求體大小；
-   本地上傳目錄不可寫或沒有掛載持久化卷；
-   S3 bucket、region、endpoint 或憑據不匹配；
-   下載地址經過代理後使用了錯誤的公開域名或協議。

使用 Docker Compose 時，預設的 `backend_uploads` volume 儲存本地附件。重建容器不會刪除它，但 `docker compose down -v` 會刪除資料卷。S3 相關配置見[環境變數](<81 [01.01.01 GitHub] 環境變數.md#%E9%99%84%E4%BB%B6%E5%AD%98%E5%82%A8>)。

## [用量（Usage）為 0](#%E7%94%A8%E9%87%8Fusage%E4%B8%BA-0)

Usage 頁面讀取按小時彙總的資料，不直接讀取每次執行的原始用量。先確認原始資料和彙總表：

```sql
SELECT count(*) FROM task_usage;
SELECT count(*) FROM task_usage_hourly;

SELECT plan_time, status, error_code, error_msg
FROM sys_cron_executions
WHERE job_name = 'rollup_task_usage_hourly'
ORDER BY plan_time DESC
LIMIT 20;
```

如果 `task_usage` 有資料、彙總表為空，並且排程記錄顯示失敗，先確認 migration 已經全部應用；升級被 migration 103 拒絕執行的情況見下一節。也可以手動執行一次彙總來區分 SQL 和排程問題：

```sql
SELECT rollup_task_usage_hourly();
```

手動執行後數字正常，說明彙總函式可用，問題在 backend 的定時排程；手動 SQL 只補一次彙總，不會恢復排程。按小時彙總由 backend 內建排程執行，不需要自行配置 pg\_cron。

## [升級時 migration 103 拒絕執行](#%E5%8D%87%E7%BA%A7%E6%97%B6-migration-103-%E6%8B%92%E7%BB%9D%E6%89%A7%E8%A1%8C)

正常升級不需要為 103 做任何事：`migrate up` 在應用它之前會自動回填歷史用量資料——空庫直接通過，有歷史資料的例項自動按月補齊後繼續。

如果 backend 啟動仍報 `refusing to drop legacy daily rollups`，說明自動回填沒有完成（例如回填中途失敗，或沒有通過 `migrate up` 而是直接應用了 SQL）。此時手動執行回填命令，完成後重啟 backend：

```bash
cd server
DATABASE_URL='postgres://...' go run ./cmd/backfill_task_usage_hourly
```

常用 flag：`--dry-run` 只預覽不寫入；`--sleep-between-slices` 在切片之間加間隔，降低對繁忙例項的讀壓。命令按月切片、冪等，中斷後可以直接重跑；它持有 advisory lock，與服務端的定時彙總互斥，不會產生重複或不一致的彙總資料。完成後重啟 backend，用 `/readyz` 確認 `migrations` 為 `ok`。

## [端口占用](#%E7%AB%AF%E5%8F%A3%E5%8D%A0%E7%94%A8)

本地常用埠包括 API 的 `8080`、Web 的 `3000` 和守護程序健康檢查埠。先找出佔用者：

```
lsof -nP -iTCP:8080 -sTCP:LISTEN # macOS / Linux
netstat -ano | findstr :8080 # Windows
```

如果它是另一個 Multica checkout，先在那個目錄執行 `make stop`。否則正常停止佔用埠的程式，或修改當前服務埠。公網 80/443 由 Caddy、Nginx 等反向代理監聽。

## [日誌位置](#%E6%97%A5%E5%BF%97%E4%BD%8D%E7%BD%AE)

| 元件 | 檢視方式 |
| --- | --- |
| 後臺守護程序 | `multica daemon logs --lines 100` |
| 即時跟隨守護程序日誌 | `multica daemon logs --follow` |
| 預設 profile 的日誌檔案 | `~/.multica/daemon.log` |
| 預設 profile 的啟動或崩潰日誌 | `~/.multica/daemon.err.log` |
| 命名 profile | `~/.multica/profiles/<name>/` 下的對應日誌 |
| Docker backend | `docker compose -f docker-compose.selfhost.yml logs -f backend` |
| 瀏覽器 | 開發者工具中的 Console 和 Network |

哪個檔案是當前活躍的日誌，取決於守護程序啟動時使用的 profile；早前守護程序殘留的舊日誌同樣能正常讀出來，最容易讓人調錯檔案。不要靠猜去開檔案：`multica daemon logs` 會在輸出日誌內容前先列印它解析到的絕對路徑。讀命名 profile 的日誌時加上 `--profile <name>`。

需要直接觀察守護程序啟動過程時，可以改為前臺執行：

```
multica daemon stop
multica daemon start --foreground
```

仍然無法定位時，到 [GitHub 任務](https://github.com/multica-ai/multica/issues) 搜尋已有問題或提交新的任務。
