# 環境變數

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>)

自託管 Multica 常用的服務端、儲存、整合和執行時配置。

Multica 在程序啟動時讀取環境變數。修改後通常需要重啟對應的 API、Web 或守護程序。Docker Compose 的 `docker compose restart` 不會重新讀取 `.env`，要用 `up -d` 重建容器才能生效。

本頁只列面向部署者的配置；測試變數和內部執行變數不在這裡展開。本頁是分組參考；完整部署步驟見[自託管快速上手](/docs/zh/self-host-quickstart)。

## 生產環境最小配置

```
DATABASE_URL=postgres://user:password@postgres:5432/multica?sslmode=require
JWT_SECRET=<long-random-secret>
APP_ENV=production
FRONTEND_ORIGIN=https://multica.example.com
MULTICA_APP_URL=https://multica.example.com
MULTICA_PUBLIC_URL=https://api.multica.example.com
```

還需要選擇一種郵件服務，否則驗證碼和邀請只會寫入服務端日誌。

`JWT_SECRET` 在生產環境為必填：當 `APP_ENV=production` 時，後端會在金鑰為空或等於已知佔位值時拒絕啟動（用 `openssl rand -hex 32` 生成）。也不要在生產環境設定 `MULTICA_DEV_VERIFICATION_CODE`。

## API 與資料庫

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `DATABASE_URL` | 本地 `multica` 資料庫 | PostgreSQL 連線地址 |
| `DATABASE_MAX_CONNS` | `25` | 單個 API 程序的最大數據庫連線數 |
| `DATABASE_MIN_CONNS` | `5` | 單個 API 程序保留的最小連線數 |
| `DATABASE_SEARCH_WORK_MEM_MB` | `64` | 每個搜尋計劃運算元的 PostgreSQL `work_mem` 上限（MB）；設為 `1`–`64` 可調低，設為 `0` 則沿用資料庫/會話預設值 |
| `DATABASE_REPLICA_URL` | 空 | 可選的 PostgreSQL 只讀從庫連線地址；新連線會強制校驗只讀狀態，業務仍需在程式碼中顯式選擇最終一致讀取 |
| `DATABASE_REPLICA_MAX_CONNS` | `10` | 單個 API 程序的最大從庫連線數 |
| `DATABASE_REPLICA_MIN_CONNS` | `0` | 單個 API 程序保留的最小從庫連線數 |
| `MULTICA_DATABASE_STARTUP_TIMEOUT` | `3m` | 容器啟動過程中，migration 與 API 共享的暫時性資料庫故障重試時長；設為 `0` 時每個階段只嘗試一次 |
| `MULTICA_DATABASE_CONNECT_TIMEOUT` | `5s` | 啟動期間單次資料庫連線的兜底超時；pgx 原生 `connect_timeout`、`PGCONNECT_TIMEOUT` 或 service 配置優先 |
| `PORT` | `8080` | API 監聽埠 |
| `JWT_SECRET` | 生產環境必填 | 登入 JWT、部分簽名流程使用的金鑰；生產環境對空值或已知佔位值拒絕啟動 |
| `APP_ENV` | 空 | 生產環境設為 `production` |
| `AUTH_TOKEN_TTL` | `720h`（30 天） | 瀏覽器 JWT 與 cookie 有效期；接受 Go duration 或正整數秒數。會話會滑動續期：剩餘有效期過半後，持續使用的會話會被續期而不是到期。低於 `60s` 的取值會按 `60s` 處理 |
| `LOG_LEVEL` | 應用預設 | 日誌級別 |
| `MULTICA_SHUTDOWN_HOLD_DURATION` | `0` | 收到終止訊號後，開始優雅退出前等待多久 |
| `MULTICA_RUNTIME_RECONNECT_GRACE` | `3h` | 執行時離線後可重新連線且不終止在途執行的寬限時間；低於 `150s` 時按 `150s` 處理 |

在 Kubernetes 中設定 shutdown hold 時，`terminationGracePeriodSeconds` 要大於 hold 與實際退出所需時間之和。

主庫與從庫的連線上限彼此獨立，需要按全部 API 程序的連線數總和預留 PostgreSQL 叢集連線額度。從庫連線預設五分鐘回收一次，以便在提升後重新校驗只讀狀態。從庫連線失敗時，基礎設施會透明回退主庫並短暫開啟被動熔斷器，不會增加後臺資料庫探測。應用不保證從庫資料的最大陳舊時間；請在資料庫層監控複製延遲，一致性敏感的讀取繼續走主庫。

## 對外地址與瀏覽器訪問

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `FRONTEND_ORIGIN` | 空 | 使用者訪問的前端 origin；用於 CORS、cookie 和邀請連結 |
| `MULTICA_APP_URL` | 回退到 `FRONTEND_ORIGIN` | 使用者可訪問的 Web 地址；CLI 登入和賬號繫結連結使用它 |
| `MULTICA_PUBLIC_URL` | 空 | 公網 API 地址；用於 webhook URL 和執行時連線說明 |
| `MULTICA_DAEMON_SERVER_URL` | 回退到 `MULTICA_PUBLIC_URL`，再回退到 `MULTICA_APP_URL` / `FRONTEND_ORIGIN` | API 程序寫入 `multica setup self-host` 命令的服務端地址；守護程序訪問 API 的地址與公網 webhook 地址不同時設定 |
| `CORS_ALLOWED_ORIGINS` | 空 | 額外允許的 HTTP origin，逗號分隔 |
| `ALLOWED_ORIGINS` | 回退到 CORS / 前端地址 | WebSocket origin 白名單，逗號分隔 |
| `COOKIE_DOMAIN` | 空 | 前後端不同 host 且瀏覽器直接訪問 API 域時必須設定；單域部署保持為空 |

`MULTICA_DAEMON_SERVER_URL` 會由無需認證的 `/api/config` 介面返回，客戶端可以讀取。請將它視為公開配置，切勿填入憑據、令牌或其他金鑰。

前端和 API 使用不同 host、且瀏覽器直接訪問 API 域時，必須設定 `COOKIE_DOMAIN`，否則瀏覽器讀不到 CSRF cookie——所有寫請求返回 `403 CSRF validation failed`，而讀請求一切正常。取值用能同時覆蓋兩個 host 的最窄父域（`.agent.example.com` 優於 `.example.com`）。它會把登入會話 cookie 擴散到該域下的所有 host，只有這些 host 都由同一可信主體運維時才可用。修改後需要在兩個 host 上清除舊 cookie 並重新登入。若採用[自託管快速上手](/docs/zh/self-host-quickstart#3-%E9%80%89%E6%8B%A9%E8%AE%BF%E9%97%AE%E6%96%B9%E5%BC%8F)的同源配方（瀏覽器只訪問 app 域），保持為空即可。不要填寫 IP 地址，瀏覽器會忽略帶 IP Domain 的 cookie。

自託管部署需要設定 `FRONTEND_ORIGIN`。缺少它時，邀請連結、cookie 安全屬性和 WebSocket origin 校驗都可能與實際域名不一致。

## Redis 與限流

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `REDIS_URL` | 空 | 所有 Redis 功能共用的唯一連線地址，包括共享限流、即時事件、頻道 WebSocket 租約和 token cache |
| `REDIS_CLUSTER_MODE` | `false` | 設為 `true` 後強制使用 Redis Cluster 客戶端，單配置地址也適用；叢集模式只能使用資料庫 0，且要求 `REALTIME_RELAY_MODE=sharded` |
| `REDIS_DISABLE_CLIENT_NAME` | `false` | 託管 Redis 禁止 `CLIENT SETNAME` 時設為 `true` |
| `RATE_LIMIT_AUTH` | `5` | 單 IP 每分鐘傳送驗證碼或發起 Google 登入的次數 |
| `RATE_LIMIT_AUTH_VERIFY` | `20` | 單 IP 每分鐘驗證驗證碼的次數 |
| `RATE_LIMIT_INVITATION_ACTOR_10M` | `10` | 每位邀請人在 10 分鐘滑動視窗內可建立的工作區邀請數；設為 `0` 可關閉此項限流 |
| `RATE_LIMIT_INVITATION_WORKSPACE_24H` | `50` | 同一工作區內所有管理員在 24 小時滑動視窗內可建立的邀請總數；設為 `0` 可關閉此項限流 |
| `RATE_LIMIT_INVITATION_RECIPIENT_24H` | `6` | 同一規範化收件郵箱跨工作區在 24 小時滑動視窗內可收到的邀請數；設為 `0` 可關閉此項限流 |
| `RATE_LIMIT_TRUSTED_PROXIES` | 空 | 允許提供 `X-Forwarded-For` 的代理 CIDR，逗號分隔 |
| `MULTICA_TRUSTED_PROXIES` | 空 | 自動化 webhook 與即時連線使用的可信代理 CIDR |

反向代理後的部署需要填寫真實代理網段。不要直接信任所有來源，否則客戶端可以偽造轉發 IP。

認證限流需要配置 `REDIS_URL`；未配置時，啟動日誌會提示認證限流已關閉。邀請限流在沒有 Redis 時仍使用程序記憶體，配置 Redis 後則在多個副本間共享額度。如果已配置的 Redis 臨時不可用，認證限流仍選擇放行，而邀請建立會返回可重試的 `503`，不會在失去防護時傳送郵件。

## 服務端 LLM

這組配置用於服務端的輔助生成能力，例如對話標題；它不是智慧體執行時使用的 AI 程式設計工具憑據。

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `MULTICA_LLM_API_KEY` | 空 | OpenAI 相容 API key |
| `MULTICA_LLM_BASE_URL` | 空 | OpenAI 相容 endpoint |
| `MULTICA_LLM_DEFAULT_MODEL` | `gpt-5.6-luna` | 請求未指定模型時使用 |
| `MULTICA_LLM_MAX_RETRIES` | `2` | 單次呼叫的重試上限；`0` 表示停用重試，`1`–`5` 表示最多重試 N 次 |
| `MULTICA_LLM_DISABLE_THINKING` | `false` | 在每個請求中附帶 `chat_template_kwargs: {"enable_thinking": false}`，供支援該欄位的閘道器關閉模型思考 |

`MULTICA_LLM_MAX_RETRIES` 是重試策略的唯一配置源。不設定時使用預設的 2 次；設為 `0` 表示每次呼叫只發一個請求；設為 1–5 表示最多重試這麼多次。它是上限而不是配額：只有可重試的失敗才會消耗它，請求成功或呼叫方自身的超時都會讓呼叫提前結束。其它取值（負數、非數字、大於 5）會讓服務啟動失敗，而不是被靜默糾正。上限是一個延遲預算：退避從 0.5s 開始翻倍，上限 8s，更大的預算會超出呼叫方自身的超時，把可重試的失敗變成超時失敗。重試覆蓋連線失敗以及 HTTP 408、409、429 和 5xx；其餘 4xx 直接返回。服務啟動時會以 `llm retry policy` 列印生效策略，其中不包含任何憑據。

`MULTICA_LLM_DISABLE_THINKING` 面向"模型會先跑一段推理（thinking）並吃掉輔助呼叫延遲預算"的閘道器。設為 `true`（或 `1`）時，服務端會在每個請求體中附帶 `chat_template_kwargs: {"enable_thinking": false}`；支援透傳該欄位的閘道器（vLLM/sglang 類部署、部分 GLM/Qwen 系的 LiteLLM 路由）會因此跳過思考階段。標準 OpenAI 端點會拒絕未知的請求體欄位，所以僅在上游接受時啟用。GPT-5.6 系模型在後續提問建議請求中已由服務端附帶 `reasoning_effort: none`。會話自動命名不傳送推理欄位；只有當所配置的上游接受 `chat_template_kwargs` 時，此項才會影響它。可接受的取值為 `true`/`false` 和 `1`/`0`（不區分大小寫）；其它取值會讓服務啟動失敗。啟動日誌會在重試策略旁列印生效狀態。

有兩個功能會使用這一層，它們都會把聊天內容傳送到你配置的 endpoint：

-   **對話標題自動生成** —— 傳送新對話中使用者的第一條訊息，原文傳送。附件不會包含在內。
-   **後續提問建議**（智慧體回覆下方的按鈕）—— 傳送對話末尾的內容：最多 6 條訊息，其中被追問的那條回覆上限 3000 字元，更早的每條上限 800 字元。

API key 與 base URL 都為空時，這一層關閉，不會發出任何上游請求——上面兩個功能都不再發送內容。如果你的政策不允許這一層把聊天內容發到部署之外，這就是受支援的配置方式：對話繼續使用客戶端根據第一條訊息生成的標題，後續提問按鈕不再出現，其餘功能不受影響。

這隻覆蓋輔助生成這一層。智慧體執行是另一條資料路徑：智慧體回覆對話時，由你的守護程序呼叫該智慧體的 AI 程式設計工具，用的是那個工具自己的憑據，守護程序不會把上面的 `MULTICA_LLM_*` 配置傳給它。（智慧體自身需要的執行級 Multica 連線變數由守護程序單獨注入。）把上面的變數留空不影響這條路徑——它由智慧體的執行時配置決定。

## 守護程序配置

下面的變數在執行智慧體的電腦上讀取，不是在 API 容器中讀取。

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `MULTICA_SERVER_URL` | `ws://localhost:8080/ws` | Multica API / WebSocket 地址，也接受 `http(s)` |
| `MULTICA_DAEMON_DEVICE_NAME` | 主機名 | 執行時列表中的裝置名 |
| `MULTICA_AGENT_RUNTIME_NAME` | `Local Agent` | 執行時顯示名 |
| `MULTICA_DAEMON_POLL_INTERVAL` | `30s` | 沒有喚醒事件時的執行輪詢間隔 |
| `MULTICA_DAEMON_WS_CLAIM_POLL_INTERVAL` | `3m` | 健康 WebSocket 下 claim 安全輪詢的上限，與 `MULTICA_DAEMON_POLL_INTERVAL` 獨立配置；向下抖動後預設實際為 `2m30s`–`2m45s`，舊 Server 或結果不確定的 claim 仍使用普通輪詢間隔 |
| `MULTICA_DAEMON_HEARTBEAT_INTERVAL` | `15s` | 心跳間隔 |
| `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` | `20` | 單個守護程序的併發執行上限 |
| `MULTICA_AGENT_TIMEOUT` | `0` | 單次執行的絕對時限；`0` 表示不設定 |
| `MULTICA_AGENT_IDLE_WATCHDOG` | `2h` | 沒有輸出且沒有工具執行時的靜默上限；`0` 表示整套 watchdog 關閉 |
| `MULTICA_AGENT_TOOL_WATCHDOG` | 同 `MULTICA_AGENT_IDLE_WATCHDOG` | 單個工具呼叫持續靜默的上限；只有希望工具比模型有更多餘量時才單獨設定，`0` 表示工具執行期間永不強制停止。Cursor 的後臺 shell 在它啟動的程序退出前一直算作執行中；到達這個上限時，守護程序會停止這些程序，並給 Cursor 一段新的 watchdog 預算來產出終態結果。若程序歸屬或清理無法驗證，則回到普通的執行取消策略 |
| `MULTICA_OPENCODE_IDLE_WATCHDOG` | `10m` | OpenCode 專用靜默閾值 |
| `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` | 同 `MULTICA_AGENT_IDLE_WATCHDOG` | Codex 語義靜默閾值。Codex 自己的計時器看不到工具是否在執行，因此跟隨 idle / tool 預算中較大的那個，而不再單獨保留一個更短的上限 |
| `MULTICA_CODEX_FIRST_TURN_TIMEOUT` | `0` | 顯式覆蓋 Codex 首輪無進展上限；`0` 保持預設值。實際首輪等待仍受 `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` 和總執行超時限制——需將 `MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT` 設為嚴格大於此值（並留出餘量），否則等待會被截斷至該值，且會跳過模型目錄啟動重試。設為相等還不夠：語義計時器先啟動，兩者相等時仍可能丟失該重試 |
| `MULTICA_CODEX_HANDSHAKE_TIMEOUT` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 啟動握手上限；顯式設定後會統一覆蓋兩類預算 |
| `MULTICA_CODEX_TURN_INTERRUPT_TIMEOUT` | `2s` | 任務取消後等待 Codex app-server 確認 `turn/interrupt` 併發出 `turn/completed` 的寬限期，以便在強制清理程序前保留最終 token 用量。主機異常緩慢時，可根據 daemon 日誌記錄的中斷延遲調整 |
| `MULTICA_DAEMON_AUTO_UPDATE` | Cloud `true`；自託管 `false` | 是否自動檢查並更新 CLI |
| `MULTICA_DAEMON_AUTO_UPDATE_INTERVAL` | `6h` | 檢查更新的間隔 |
| `MULTICA_DAEMON_AUTO_RELOAD` | `true` | 是否在 `multica` 二進位制被帶外替換（`brew upgrade`、重新下載、本地構建）後重啟到新二進位制。與 `MULTICA_DAEMON_AUTO_UPDATE` 相互獨立 |
| `MULTICA_WORKSPACES_ROOT` | `~/multica_workspaces` | 執行工作目錄的根目錄 |
| `MULTICA_AGENT_TEMP_BASE` | `/tmp`（Linux/macOS） | 僅適用於 Linux/macOS。每次執行的私有臨時目錄的父目錄；必須是現有、可寫的絕對路徑，無效值會使執行啟動失敗，不會回退到 `/tmp`。請選擇較短的路徑——子工具可能會在其中繫結 AF\_UNIX socket；Linux 的 `sun_path` 上限為 108 位元組，macOS 為 104 位元組 |
| `MULTICA_KEEP_ENV_AFTER_TASK` | `false` | 保留執行目錄用於除錯 |

守護程序注入智慧體 task 的內部上下文見 [Task 執行時環境](/docs/zh/daemon-runtimes#task-%E8%BF%90%E8%A1%8C%E6%97%B6%E7%8E%AF%E5%A2%83)。

各 AI 程式設計工具可以使用 `MULTICA_<PROVIDER>_PATH` 覆蓋命令路徑；支援模型覆蓋的工具還可以使用 `MULTICA_<PROVIDER>_MODEL`。QwenPaw 和 MiniMax Code 沒有模型變數，因為 Multica 不會向它們傳模型；MiniMax Code 的路徑變數是 `MULTICA_MCODE_PATH`。詳見 [AI 程式設計工具對比](/docs/zh/providers#%E6%A8%A1%E5%9E%8B%E6%9D%A5%E6%BA%90)。DeepSeek Harness 支援 `MULTICA_DSH_PATH` 和 `MULTICA_DSH_MODEL`（取值為 dsh 模型目錄中的模型 id，例如 `deepseek-official/deepseek-chat`）。 DeepSeek Harness 另外支援 `MULTICA_DSH_PROFILE_BUNDLE`：當 `multica` profile 缺失時，用它指定要安裝的 bundle，多個候選用逗號分隔、按序嘗試，每項可以是 npm 包名、目錄或打包好的 tarball。該變數預設不設定；Multica 驅動的 `--stdio` 協議正是由這個 profile 提供，所以不設定時不會改動 DSH 的安裝，守護程序會報告缺少 profile，而不是註冊一個不可用的執行時。Multica 自己的橋接還沒有釋出到公共 npm registry，如何選取值見[安裝智慧體執行時](/docs/zh/install-agent-runtime)；這裡填的東西會在沒有二次確認的情況下裝進每一臺守護程序宿主的 DSH 家目錄，請當作供應鏈決策來對待。`MULTICA_DSH_PROFILE_BUNDLE` 開啟的安裝被刻意限制了範圍：每個守護程序生命週期最多執行一次，只在探測確認 profile 確實缺失時執行；失敗時會把包管理器自身的輸出記入日誌，且只有重啟守護程序後才會重試。探測超時、或返回本守護程序不支援的協議版本時，只做報告，絕不覆蓋安裝——守護程序不會覆蓋一個明顯是刻意裝上去的 profile。排查時在守護程序日誌中搜索 `DSH runtime profile`；要撤銷安裝，刪除 `$DSH_HOME/profiles/multica`（預設 `~/.dsh/profiles/multica`）。`MULTICA_DSH_PLUGIN_PATH` 用於覆蓋安裝時解析 pnpm 的目錄。`dsh plugin` 轉發到的那個 pnpm 由 DSH Desktop 放在它私有的 runtime-commands 目錄裡，macOS 和 Windows 都是如此，守護程序會自動找到並加到 PATH 最前——包括較新版 Desktop 採用的帶版本號目錄結構。所以只有守護程序找不到的安裝位置、或者你想讓安裝使用自己的 pnpm 時，才需要這個變數。一旦設定就完全取代自動查詢：目錄不存在時，安裝會退回使用守護程序 `PATH` 上的 pnpm，而不是內建的那個。Linux 上沒有 DSH Desktop，安裝始終使用 `PATH`。ZeroClaw 支援 `MULTICA_ZEROCLAW_PATH`，但沒有模型變數；模型由 ZeroClaw 的智慧體配置管理。全機預設引數 `MULTICA_<PROVIDER>_ARGS` 目前支援 Claude Code、Codex、CodeBuddy、Qwen Code 和 QwenPaw 五款工具。對應變數是 `MULTICA_CLAUDE_ARGS`、`MULTICA_CODEX_ARGS`、`MULTICA_CODEBUDDY_ARGS`、`MULTICA_QWEN_ARGS` 和 `MULTICA_QWENPAW_ARGS`。例如：

```
MULTICA_CLAUDE_PATH=/opt/bin/claude
MULTICA_CLAUDE_ARGS=--max-turns 40
```

Cursor 已驗證的後臺清理需要 Linux 6.9 及以上（程序組 pidfd）、macOS 核心對程序身份查詢與 audit token 發訊號的支援，或 Windows 上成功分配的巢狀 Job Object。在 macOS 上，每個程序都按核心校驗的 PID version 發訊號，不需要加入同一 session 的程序組；這些 macOS 介面是私有的，會在捕獲時做探測。無法認領的後臺啟動會返回它原本的工具結果並回到普通的 idle watchdog，工具 watchdog 為 `0` 時同樣如此。已經認領的工作在清理無法確認時會繼續算作執行中。當工具 watchdog 設為 `0` 時則完全沒有這個邊界：已認領的後臺工作只要還活著就一直讓執行處於執行中，此時執行僅受 `MULTICA_AGENT_TIMEOUT` 約束，而它預設也是 `0`。

執行正常結束時，被認領的 Cursor 後臺程序同樣會被停止，因此該次執行啟動的後臺服務不會有意地在收尾之後繼續存活。macOS 可以通過保留的原始父程序身份識別後期產生的子程序，但無法證明中間程序在被觀察到之前就已消失的那條鏈路。這類程序、離開被追蹤程序組的工作，以及持續的歸屬或發訊號錯誤，都可能留下殘餘的後臺工作。未確認的清理會被記錄下來，且永遠不會換取一次「清理成功」的恢復視窗；不會僅憑數字 PID 或程序組就去殺掉未知程序。

優先順序為命令列 flag → 環境變數 → `~/.multica/config.json` → 內建預設。watchdog 的行為見[守護程序與執行時](/docs/zh/daemon-runtimes)。

### 守護程序配置的持久化

守護程序側的常用配置也可以寫入 `~/.multica/config.json`，不必依賴 shell 環境變數；命名 profile 的配置檔案在 `~/.multica/profiles/<name>/config.json`：

```
multica config set poll_interval 10s
multica config show
```

支援的鍵：

| 鍵 | 預設值 | 說明 |
| --- | --- | --- |
| `server_url` | `ws://localhost:8080/ws` | Multica API / WebSocket 地址 |
| `app_url` | 空 | 瀏覽器登入使用的 Web 地址 |
| `workspace_id` | 空 | 預設工作區 |
| `device_name` | 主機名 | 執行時列表中的裝置名 |
| `runtime_name` | `Local Agent` | 執行時顯示名 |
| `workspaces_root` | `~` 下按 profile 區分的路徑 | 執行工作目錄的根目錄 |
| `max_concurrent_tasks` | `20` | 併發執行上限；`0` 或留空表示未設定 |
| `poll_interval` | `30s` | 執行輪詢間隔 |
| `ws_claim_poll_interval` | `3m` | 健康 WebSocket 下 claim 安全輪詢的上限，與 `poll_interval` 獨立配置；Daemon 會應用向下抖動 |
| `heartbeat_interval` | `15s` | 心跳間隔 |
| `agent_timeout` | 不限制 | 單次執行的絕對時限 |
| `codex_semantic_inactivity_timeout` | 派生 | Codex 語義靜默閾值。未設定時取 idle 與 tool watchdog 預算中較大的那個；tool 預算為 `0` 時回落到 idle 預算；只有整套 watchdog 關閉時才保留 Codex 自己的 `10m` |
| `codex_handshake_timeout` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 啟動握手上限；顯式設定後會統一覆蓋兩類預算 |
| `disable_auto_update` | 跟隨環境 | `true` 關閉自動更新；`false` 清除本地覆蓋，回到環境變數或預設 |
| `auto_update_check_interval` | `6h` | 檢查更新的間隔 |
| `disable_auto_reload` | 跟隨環境 | `true` 讓守護程序不再跟隨磁碟上被替換的二進位制；`false` 清除本地覆蓋。與 `disable_auto_update` 分開解析 |

幾條取值規則：

-   duration 類鍵接受正的 Go duration（如 `10s`、`2h`），`0s` 和負值會被拒絕。唯一例外是 `agent_timeout`：`0s` 合法，表示明確關閉執行時限。
-   傳空字串清除已持久化的值，回到環境變數或內建預設，例如 `multica config set poll_interval ""`。
-   `max_concurrent_tasks` 要求非負整數。
-   相對的 `workspaces_root` 值在儲存時會轉換為絕對路徑。

## 觀測與統計

| 變數 | 預設值 | 說明 |
| --- | --- | --- |
| `DO_NOT_TRACK` | 空（預設開啟遙測） | 設為 `1` 或 `true`（不區分大小寫）後，停止首方匿名自託管遙測的採集與傳送 |
| `ANALYTICS_DISABLED` | `false` | 設為 `true` 關閉 PostHog 上報 |
| `POSTHOG_API_KEY` | 空 | 不設定時統計上報關閉；接入自己的 PostHog 專案時填寫 |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog 地址 |
| `METRICS_ADDR` | 空 | Prometheus metrics 監聽地址；空表示不啟動 |
| `REALTIME_METRICS_TOKEN` | 空 | 保護 `/health/realtime` 的 bearer token |

首方自託管遙測每天按 UTC 傳送一份部署級快照，固定且不可配置的地址為 `https://telemetry.multica.ai/v1/telemetry/events`。快照只包含正式釋出版本、工作區數/去重成員數/活躍智慧體數/過去 24 小時活躍守護程序數的分桶，以及過去 24 小時執行的開始、完成、失敗和取消總數。不會發送名稱、郵箱或域名、IP、業務識別符號、主機或裝置資訊、程式碼倉庫、模型或 plugin、prompt/output、評論或聊天、檔案路徑、token/費用、憑據、錯誤文本、stack 或日誌。此資料只用於瞭解自託管版本採用、部署規模區間與聚合使用量，不用於計費、授權、認證或安全決策。

`DO_NOT_TRACK` 與 `ANALYTICS_DISABLED` 相互獨立：前者控制這份首方匿名快照，後者控制可選的 PostHog 整合。
