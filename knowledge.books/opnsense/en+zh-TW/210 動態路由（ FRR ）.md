Dynamic Routing (using routing protocols) is supported via an external plugin. Routing protocols support your network equipment in finding the best available path for your packets. We use Free Range Routing ([FRR](https://frrouting.org/)) to implement the various available protocols for dynamic routing.

動態路由（使用路由協定）透過外部插件提供支援。路由協定可協助您的網路裝置找到資料包的最佳可用路徑。我們使用自由範圍路由（[FRR](https://frrouting.org/) ）來實現各種可用的動態路由協定。

These routing protocols are used to:

這些路由協定用於：

-   Improve fault tolerance (if a connection breaks, a new route will be found if possible)  
    提高容錯能力（如果連線中斷，將盡可能尋找新的路由）
    
-   Simplify administration (you have to add fewer routes manually)  
    簡化管理（減少手動新增的路由數量）
    

It is not advisable to use dynamic routing in the following scenarios:

在以下情況下不建議使用動態路由：

-   When your network is small (it would be simpler to use static routes)  
    當你的網路規模較小時（使用靜態路由會更簡單）。
    
-   If you are working in a highly isolated environment, where you have to be in control of every route in your network  
    如果你在高度封閉的環境中工作，你需要掌控網路中的每一個路由，那麼你一定能夠勝任。
    

Routing Protocols supported by the plugin include:

該插件支援的路由協定包括：

-   RIPv1 and RIPv2  
    RIPv1 和 RIPv2
    
-   OSPFv2 and v3  
    OSPFv2 和 v3
    
-   BGPv4
    

Warning

警告

Not all routing protocols will work in any setup because they may have to be direct neighbors. Consider the limitations of a routing protocol before using it.

並非所有路由協定都能在所有環境中正常運作，因為它們可能需要是直接相鄰的節點。在使用路由協定之前，請考慮其限制。

Warning

警告

It’s strongly advised to increase the kern.ipc.maxsockbuf value via **Tunables**. Go to System ‣ Settings ‣ Tunables and check if there is already a tunable for maxsockbuf and set it to 33554432 if it is lower. Otherwise add a new one with name above and the specified value.

強烈建議透過**Tunables**設定增加 kern.ipc.maxsockbuf 的值。依序進入“系統”‣“設定”‣“Tunables”，檢查是否已存在 maxsockbuf 的調整項，如果值低於 33554432，則將其設為 33554432。否則，請新增一個名稱與上述相同的調整項，並設定其對應的值。

Warning

警告

Disabling a running routing daemon can be dangerous as it can lead to an inaccessible machine. If you want to disable a running routing daemon, make sure you do not lose routes which are required by your connection to this machine (for example when using SSH).

停用正在運行的路由守護程序可能很危險，因為它可能導致機器無法存取。如果要停用正在執行的路由守護進程，請確保不會遺失連接到該機器所需的路由（例如，使用SSH時）。

## [Installation](#id1)｜[安裝](#id1)

Go to System ‣ Firmware ‣ Plugins and select `os-frr` from the available plugins.

進入系統‣韌體‣插件，然後從可用插件中選擇`os-frr` 。

## [General setup](#id2)｜[通用設定](#id2)

To use one or more of the protocols included, the plugin must be enabled in Routing ‣ General. Without any other service enabled this makes sure the zebra service is being configured, which is the coordinating master service which handles generic features such as logging and access to kernel routing.

若要使用一個或多個內建協議，必須在「路由」‣「常規」中啟用該插件。在未啟用任何其他服務的情況下，這將確保配置 Zebra 服務，該服務是協調主服務，負責處理日誌記錄和核心路由存取等通用功能。

Tip

提示

By default logging should be enabled, which sends messages to the local logging and offers remote logging over syslog. Always make sure to choose a sensible log level (default is Notifications) and check the log in Routing ‣ Diagnostics -> Log

預設應啟用日誌記錄，這會將訊息傳送至本機日誌記錄，並透過 syslog 提供遠端日誌記錄。請務必選擇適當的日誌等級（預設為「通知」），並在「路由」‣「診斷」->「日誌」中查看日誌。

Note

筆記

The plugins supports seamless reloads since version os-frr-1.4.3. When using older versions, there is no configuration reloading. This means there might be a temporary loss of service when saving settings. Normally this is only a small glitch, but in high traffic areas it might be something to take under consideration when performing maintenance.

自 os-frr- 1.4.3版本起，外掛程式支援無縫重載。使用舊版本時，配置不會重新載入。這意味著在儲存設定時可能會出現短暫的服務中斷。通常這只是一個小故障，但在高流量區域，進行維護時可能需要考慮這一點。

## [Dynamic routing and high availability](#id3)｜[動態路由與高可用性](#id3)

In enterprise networks there is often a need to protect services against all sorts of failures. Dynamic routing helps to always provide a valid path for packets to travel. These nodes themselved might need to be configured more resilient to prevent single points of failures on the edges of your network.

企業網路中經常需要保護服務免受各種故障的影響。動態路由有助於始終為資料包提供有效的傳輸路徑。這些節點本身可能需要配置得更具彈性，以防止網路邊緣出現單點故障。

In OPNsense high availability and failover is organised around [carp](<96 高可用性.md>), which makes it a logical choice to combine both technologies here as well.

在 OPNsense 中，高可用性和故障轉移是圍繞 [carp](<96 高可用性.md>)組織的，因此在這裡將這兩種技術結合起來也是一個合乎邏輯的選擇。

There are different strategies ranging from disabling the daemon when in carp mode, to more fine grained control of route propagation when a machine is in backup mode.

有多種策略可供選擇，例如在 CARP 模式下停用守護進程，以及在機器處於備份模式時對路由傳播進行更精細的控制。

Note

筆記

Unicast CARP is available to use the protocol across router boundaries. This can enable the use of CARP on WAN interfaces peering with eBGP neighbors if they are not connected to the same switch.

單播CARP可用於跨路由器邊界使用此協定。如果WAN介面與eBGP鄰居建立對等連接，且這些鄰居不在同一交換器上，則可以使用CARP 。

### [CARP failover mode](#id4)｜[CARP故障轉移模式](#id4)

The most simple mode available. When a node becomes Backup it will stop the FRR services. When it returns to Master it will start the FRR services.

這是最簡單的模式。當節點變成備份節點時，它將停止FRR服務。當它恢復為主節點狀態時，它將啟動FRR服務。

Note

筆記

Due to the nature of this option, it cannot be combined with other available CARP options.

由於此選項的性質，它不能與其他可用的CARP選項組合使用。

### [OSPF\[6\]: CARP demote](#id5)｜[ OSPF \[6\]: CARP降級]( https://docs.opnsense.org/manual/dynamic_routing.html#id5 )

This option registers a [status monitor](<246 CARP狀態.md>) on top of the FRR logging feed to detect changes in link status. If OSPF cannot find its neighbors, it will make this machine less attractive by increasing the demotion factor.

此選項會在FRR日誌流之上註冊一個 [狀態監視器](<246 CARP狀態.md>)以偵測鏈路狀態的變化。如果OSPF找不到其鄰居，則會透過增加降級因子來降低該機器的吸引力。

The feature is inspired by OpenBSD’s handling of CARP demotion in ospfd ([https://man.openbsd.org/ospfd.conf.5](https://man.openbsd.org/ospfd.conf.5)) and can be enabled using the `CARP demote` checkbox in Routing: OSPF\[v3\].

此功能受 OpenBSD 對 ospfd 中CARP降級OSPF處理方式的啟發（[https://man.openbsd.org/ospfd.conf.5](https://man.openbsd.org/ospfd.conf.5) ），並且可以使用路由中的`CARP demote`複選框。

Note

筆記

Since the relevant neighbor negotiation messages are only being logged when the log level (in Routing ‣ General) is configured to debug, the log will be more chatty when using this feature. When using a lower log level the status monitor is not expected to catch any relevant events.

由於只有當日誌等級（在「路由」‣「常規」中）配置為「偵錯」時，才會記錄相關的鄰居協商訊息，因此使用此功能時日誌會更加冗長。如果使用較低的日誌級別，狀態監視器預計不會捕獲任何相關事件。

### [OSPF\[6\]: Influence interface cost based on CARP status](#id6)｜[ OSPF \[6\]: 基於CARP狀態的影響介面成本]( https://docs.opnsense.org/manual/dynamic_routing.html#id6 )

FRR does not natively support interaction with CARP status as the variant in OpenBSD does (carp note in “depend on” keyword [https://man.openbsd.org/ospfd.conf.5](https://man.openbsd.org/ospfd.conf.5)), this is where our next option comes into play.

FRR本身並不像 OpenBSD 中的變體那樣原生支援與CARP狀態進行交互（參見「依賴」關鍵字中的 carp 註釋 [https://man.openbsd.org/ospfd.conf.5](https://man.openbsd.org/ospfd.conf.5) ），這就是我們的下一個選擇發揮作用的地方。

Using the interface settings of an OSPF interface you can choose to adjust costs for that interface based on the CARP status of the selected virtual address. Go to Routing ‣ OSPF\[v3\] -> Interface and choose an interface, here you will find the following options that influence behaviour:

使用介面設置，您可以根據所選CARP OSPF調整該介面的成本。轉到“路由”‣ OSPF \[v3\] -> “接口”，然後選擇一個接口，您將在此處找到以下影響其行為的選項：

-   Depend on (carp):  
    取決於（鯉魚）：
    
    -   Select a virtual address that this interface relies on. When this target is not in **MASTER** mode, the selected interface is considered **demoted**  
        選擇此介面所依賴的虛擬位址。當此目標不在 **MASTER** 模式時，所選介面將被視為**降級**。
        
-   Cost (when demoted):  
    降級時的成本：
    
    -   Adjust the cost to this value when going to demoted state, usually one would use a high value here to prefer other routes first  
        降級狀態時，將成本調整為該值；通常情況下，此處會使用較高的值，以便優先選擇其他路徑。
        
-   Cost:  
    成本：
    
    -   The standard cost, when provided will be used when in normal conditions. If it’s left blank FRR defaults will be used, which it will also rollback to when going back to master mode.  
        如果提供標準成本，則在正常情況下將使用該成本。如果留空FRR則將使用預設值，並且在返回主模式時也會回滾到該預設值。

The Routing Information Protocol (RIP) is a basic distance-vector routing protocol that determines the best path to a network destination based on hop count. With a maximum limit of 15 hops, RIP is suitable only for smaller networks. To prevent routing loops, RIP employs techniques like split horizon, route poisoning, and holddown timers. While easy to configure, RIP has slow convergence and limited scalability, making it less popular in modern networks compared to more efficient protocols like OSPF. It should be considered a legacy protocol.

路由資訊協定 (RIP) 是一種基本的距離向量路由協議，它根據跳數確定到達網路目的地的最佳路徑。 RIP 的最大限制為 15 跳，僅適用於較小的網路。為了防止路由環路，RIP採用了水平分割、路由中毒和抑制定時器等技術。雖然易於配置，但RIP收斂速度慢且可擴展性有限，與OSPF等更高效的協定相比，它在現代網路中不太受歡迎。它應該被視為遺留協議。

**Neighbors** in BGP are external or internal peers with whom the router establishes BGP sessions. Neighbors exchange route information, and each neighbor can be configured individually or as part of a Peer Group.

BGP中的**鄰居**是指路由器與其建立BGP會話的外部或內部對等體。鄰居之間交換路由訊息，每個鄰居都可以單獨配置，也可以作為對等體組的一部分進行配置。

Note

筆記

A **Route Reflector** (RR) minimizes the need for a full mesh of BGP connections in the same AS by reflecting routes from its clients to other clients. In typical iBGP setups, all routers must directly peer with each other to avoid routing loops, but route reflectors allow clients to peer only with the RR. Clusters of RRs and clients prevent loops, and redundancy can be achieved with multiple RRs. This setup is crucial for scalability in large networks. For a small network, do not enable any of the RR specific options.

**路由反射器** ( RR ) 透過將客戶端的路由反射到其他客戶端，最大限度地減少了在同一AS中建立全網狀BGP連接的需求。在典型的 iBGP 設定中，所有路由器必須直接相互對等連接以避免路由環路，但路由反射器允許客戶端僅與RR建立對等連接。路由反射器和客戶端叢集可以防止環路，並且可以透過多個路由反射器實現冗餘。這種設定對於大型網路的可擴展性至關重要。對於小型網絡，請勿啟用任何RR特定選項。

A **Peer Group** in BGP simplifies configurations by grouping neighbors with similar settings. Another possibility is defining **Listen Ranges** to accept connections from multiple peers without configuring each of them as neighbor individually. This approach reduces management complexity and ensures uniform settings across peers. Peer Groups are especially useful in larger networks where multiple BGP peers require identical policy; not so much in small networks.

在BGP中，**對等組**透過將具有相似設定的鄰居分組來簡化配置。另一種方法是定義**監聽範圍**，以便接受來自多個對等體的連接，而無需將每個對等體單獨配置為鄰居。這種方法降低了管理複雜性，並確保對等體之間設定一致。對等組在大型網路中特別有用，因為多個BGP對等體需要相同的策略；但在小型網路中則較不適用。

Border Gateway Protocol (BGP) is an exterior gateway protocol used to exchange routing information between autonomous systems (AS) on the Internet. As a path-vector protocol, BGP makes routing decisions based on defined paths, network policies, or administrator-configured rules. BGP has two main types: iBGP, used for routing within a single AS (using private AS numbers from 64512 to 65534), and eBGP, which operates between different AS across the Internet (using public AS numbers 1 to 64511). BGP’s flexibility and scalability make it essential for global Internet routing and large network infrastructures.

邊界網關協定 (BGP) 是一種外部網關協議，用於在網際網路上的自治系統 (AS) 之間交換路由資訊。作為一種路徑向量協議，BGP 基於定義的路徑、網路策略或管理員配置的規則做出路由決策。 BGP 主要有兩種類型：iBGP，用於單一 AS 內部的路由（使用 64512 到 65534 的私人 AS 號）；以及 eBGP，用於互聯網上不同 AS 之間的路由（使用 1 到 64511 的公共 AS 號）。 BGP 的靈活性和可擴展性使其成為全球互聯網路由和大型網路基礎設施的關鍵組成部分。

A **BFD Neighbor** refers to a neighboring device configured to use BFD with BGP, OSPF or other protocols. BFD neighbors exchange small, frequent packets to rapidly detect link failures, reducing convergence time in routing; usually a whole lot faster than typical keepalive or hello mechanisms.

**BFD鄰居**是指配置為使用BFD與BGP, OSPF或其他協定的鄰居設備。 BFD 鄰居交換小而頻繁的資料包，以快速偵測連結故障，減少路由收斂時間；通常比典型的 keepalive 或 hello 機制快得多。

Bidirectional Forwarding Detection (BFD) is a lightweight protocol used to detect faults between routers or switches by sending periodic Hello packets (asynchronous mode). BFD quickly identifies failing links, making it a useful companion to routing protocols like OSPF and BGP for faster convergence.

雙向轉送偵測（BFD）是一種輕量級協議，用於透過發送週期性的 Hello 封包（非同步模式）來偵測路由器或交換器之間的故障。 BFD 快速識別故障鏈路，使其成為OSPF 和 BGP 等路由協議的有用伴侶，以實現更快的收斂。
