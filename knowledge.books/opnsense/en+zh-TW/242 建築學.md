# Architecture｜建築學

> 章節：[Development Manual](<000 目錄.md#c-52>)

The main focus of the OPNsense project is to provide a secure and manageable platform for all your security applications. This means high quality software that is easily maintainable and bug free. We think that having a framework with a clear separation of concerns is essential to achieving these goals.

OPNsense 專案的主要目標是為您的所有安全應用程式提供一個安全且易於管理的平台。這意味著高品質、易於維護且無漏洞的軟體。我們認為，擁有一個職責清晰分離的框架對於實現這些目標至關重要。

OPNsense is a fork of pfSense ®. The existing code base of pfSense ® does not always apply a clear separation of concerns. This means we need a transition of the old (legacy) code base to a new one with a clear separation. We have chosen a gradual transition to avoid a big bang and keep the product feature rich while increasing code quality. This enables simple addition of new features with less bugs and shorter time to market.

OPNsense 是 pfSense® 的一個分支。 pfSense® 現有的程式碼庫並非總是遵循清晰的職責分離原則。這意味著我們需要將舊的（遺留的）程式碼庫過渡到具有清晰職責分離的新程式碼庫。我們選擇逐步過渡，以避免重大變革，並在維持產品功能豐富性的同時提升程式碼品質。這使得增加新功能更加便捷，同時減少 bug 並縮短產品上市時間。

This article describes how this will be achieved.

本文將介紹如何實現這一目標。

## High-level architecture｜進階架構

[![OPNsense Components.svg](<../images/c053e4e1-OPNsense_Components.svg>)](https://docs.opnsense.org/_images/OPNsense_Components.svg)

As the above model shows there are two main areas in our stack, the frontend implemented with PHP/Phalcon and the backend using a custom service built in Python.

如上圖所示，我們的技術堆疊主要分為兩個部分：前端使用PHP /Phalcon 實現，後端使用 Python 建構的自訂服務。

The frontend handles user interaction and communicates with the backend service. Applying configuration changes, monitoring and controlling services offered by OPNsense is done by the backend service.

前端負責處理使用者互動並與後端服務通訊。後端服務負責應用設定變更、監控和控制 OPNsense 提供的服務。

By using a fully configurable backend service, we avoid hardcoding of services and ease the implementation of new features.

透過使用完全可配置的後端服務，我們避免了服務的硬編碼，並簡化了新功能的實現。

The frontend stack delivers a model driven approach to handle configuration data, including automatic validation.

前端技術堆疊採用模型驅動的方法來處理配置數據，包括自動驗證。

Manipulation of the core configuration file is handled at the frontend model; the backend service is merely a consumer of the information provided.

核心設定檔的操作由前端模型處理；後端服務只是所提供資訊的消費者。

## Frontend Architecture｜前端架構

[![OPNsense frontend.svg](<../images/9efba41d-OPNsense_frontend.svg>)](https://docs.opnsense.org/_images/OPNsense_frontend.svg)

### Routing｜路由

The OPNsense framework uses standard components where possible; the first layer initializes routing, which handles requests and delivers them to the controller based on its url. User content is generated using Volt templates (using Phalcon), which are picked by the controller.

OPNsense 框架盡可能使用標準元件；第一層初始化路由，處理請求並根據其 URL 將其傳遞給控制器。使用者內容使用 Volt 模板（基於 Phalcon）生成，並由控制器選擇。

For a detailed description on the routing principles used in OPNsense, visit Frontend [Routing](<259 路由.md>).

有關 OPNsense 中使用的路由原理的詳細說明，請造訪前端 [路由](<259 路由.md>) 。

### Controllers and views｜控制器和視圖

Not all parts of the framework are implemented, but by deriving all controllers from the base in the OPNsense project it’s easy to extend and adapt to future needs. Documentation on how to implement controllers, with the use of views, can be found at [Using controllers and views](<260 使用控制器和視圖.md>).

框架並非所有部分都已實現，但透過從 OPNsense 專案的基礎派生所有控制器，可以輕鬆擴展並適應未來的需求。有關如何使用視圖實作控制器的文檔，請參閱 [使用控制器和視圖](<260 使用控制器和視圖.md>) 。

### Models｜模型

All models are defined by a combination of a class and an XML containing a (nested) definition. More information on defining models can be found at the frontend model page [Creating Models](<251 創建模型.md>).

所有模型均由類別和包含（嵌套）定義的XML組合定義。有關定義模型的更多信息，請參閱前端模型頁面 [創建模型](<251 創建模型.md>) 。

### Communication｜溝通

Communication to the backend service is handled via a unix domain socket.

與後端服務的通訊透過 Unix 域套接字進行處理。

### Core system｜核心系統

The core of OPNsense is powered by an almost standard FreeBSD ® system extended with packages using the pkg system. GIT is used for version control and the repositories are split into 4 parts:

OPNsense 的核心由幾乎標準的 FreeBSD ® 系統提供支持，並使用 pkg 系統擴展了軟體包。 GIT用於版本控制，儲存庫分為4部分：

-   src : the base (FreeBSD ®) system  
    src：基礎（FreeBSD®）系統
    
-   ports : the ports collection containing third party software  
    連接埠：包含第三方軟體的連接埠集合
    
-   core : the OPNsense gui and system configuration parts  
    核心部分：OPNsense 圖形使用者介面和系統配置部分
    
-   tools : easy tools to build OPNsense  
    工具：用於建構 OPNsense 的簡易工具

For detailed information about the development workflow see:

有關開發工作流程的詳細信息，請參閱：

## Backend Architecture｜後端架構

### Middleware｜中介軟體

[![OPNsense backend.svg](<../images/3ec13bdf-OPNsense_backend.svg>)](https://docs.opnsense.org/_images/OPNsense_backend.svg)

Configd, is responsible for the core system interaction like starting and stopping of daemons and generating configuration files for used services and applications.

Configd 負責核心系統交互，例如啟動和停止守護進程，以及為使用的服務和應用程式產生設定檔。

The daemon listens on a unix domain socket and is capable of executing actions defined in it’s own configuration directory (“/usr/local/opnsense/service/conf/actions\_\*.conf”).

此守護程式監聽 Unix 網域套接字，並能夠執行在其自身配置目錄（“/usr/local/opnsense/service/conf/actions\_\*.conf”）中定義的操作。

Currently there are four types of services implemented in the daemon:

目前守護程式中實作了四種類型的服務：

-   script : execute external (rc) scripts, report back success or failure  
    腳本：執行外部（rc）腳本，並報告成功或失敗
    
-   script\_output: execute external scripts, report back their contents, usually in json format  
    script_output：執行外部腳本，並傳回其內容，通常以 JSON 格式傳回。
    
-   stream\_output: open streams to backend components  
    stream_output：開啟到後端組件的流
    
-   inline : perform inline actions which are part of configd, most notable template generation and maintenance.  
    inline：執行 configd 的一部分的內嵌操作，最值得注意的是範本產生和維護。
    

  

Template generation is handled by Jinja2 ([https://jinja.palletsprojects.com/en/stable/](https://jinja.palletsprojects.com/en/stable/)), more information on how to create application templates can be found at [Using Templates](<249 使用模板.md>).

模板生成由 Jinja2 處理（[https://jinja.palletsprojects.com/en/stable/](https://jinja.palletsprojects.com/en/stable/) ），有關如何創建應用程式模板的更多信息，請參閱 [使用模板](<249 使用模板.md>) 。

### Operating stages｜操作階段

[![OPNsense_operating_events.svg](<../images/074cd70c-OPNsense_operating_events.svg>)](https://docs.opnsense.org/_images/OPNsense_operating_events.svg)

As all earlier layers describe how user input can be persisted and service information can be exchanged, we still have a gap in our functionality when looking at the life of a firewall. Until this point we have means to manually manage services and devices, including ways to collect information on demand, but still in a rather isolated way (events triggered via the api layer).

儘管前面的各層都描述瞭如何持久化用戶輸入以及如何交換服務訊息，但在考慮防火牆的整個生命週期時，我們的功能仍然存在不足。目前，我們雖然可以手動管理服務和設備，包括按需收集信息，但這些方式仍然相當孤立（事件透過 API 層觸發）。

This is where [syshooks](<245 啟動自動運行選項.md>) and [plugins](<248 使用插件.md>) come into play, these offer mechanisms to ensure different types of services can cooperate with the shared functionality available.

這就是 [syshooks](<245 啟動自動運行選項.md>)和 [plugins](<248 使用插件.md>)發揮作用的地方，它們提供了確保不同類型的服務能夠與共享功能進行協作的機制。

Between starting and stopping our firewall, we can identify three stages. After power-on, we are booting, when this initial stage has been reached we end up with a running firewall with all configured services available. During time, various events can happen, for example, someone pulling an network cable and pushing it back in, this is the running stage. Eventually, if someone decides to power-down or reboot the machine, we are entering shutdown stage, letting services know we are ending operation.

從啟動到停止防火牆，我們可以將其分為三個階段。開機後，進入啟動階段。啟動完成後，防火牆即可運行，所有已設定的服務也都可用。在此期間，可能會發生各種事件，例如有人拔下網線再重新插上，這都屬於運行階段。最後，如果有人決定關閉電源或重新啟動計算機，則進入關機階段，並通知各項服務我們即將結束運行。

Further details of each stage can be found in the [overview](<244 概述.md>) document.

各階段的更多詳情可在[概述](<244 概述.md>)文件中找到。

To avoid endless dependency loops, services should prevent hooking on events that are not strictly required for operating. For example, forcing a restart of a component when a network interface has changed is usually a sign of not following best practices for designing network services.

為了避免陷入無休止的依賴循環，服務應該避免掛鉤那些並非運作所必需事件。例如，當網路介面發生變化時強制重啟組件，通常表示沒有遵循網路服務設計的最佳實踐。
