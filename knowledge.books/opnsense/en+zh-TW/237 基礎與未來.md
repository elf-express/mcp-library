# Basics and Future｜基礎與未來

> 章節：[Development Manual](<000 目錄.md#c-52>) › [Coding Guidelines](<000 目錄.md#c-53>)

This article explains the basic coding guidelines that apply and put the development effort into perspective by explaining the difficulties of legacy code and the interaction/migration to new [MVC-based](https://en.wikipedia.org/wiki/Model%E2%80%93view%E2%80%93controller) code. It also explains guideline differences between new and legacy code.

本文闡述了適用的基本編碼規範，並透過解釋遺留程式碼的難點以及與基於新 [MVC](https://en.wikipedia.org/wiki/Model%E2%80%93view%E2%80%93controller)程式碼的互動/遷移，幫助讀者更好地理解開發工作。此外，本文也解釋了新程式碼和遺留程式碼在規範上的差異。

## PHP code｜PHP代碼

For PHP code the [PSR-12](https://www.php-fig.org/psr/psr-12/) coding standard applies.

對於PHP代碼，適用 [PSR -12](https://www.php-fig.org/psr/psr-12/)編碼標準。

## Python

For Python code the Python Enhancement Proposals (PEPs) apply. See the [Python Developer’s Guide](https://www.python.org/dev/) for detailed information.

對於 Python 程式碼，Python 增強提案 (PEP) 適用。有關詳細信息，請參閱 [Python 開發者指南](https://www.python.org/dev/) 。

## Architecture｜建築學

Documentation is available about our [architecture](<242 建築學.md>) and used [components](<264 成分.md>).

我們提供了有關[架構](<242 建築學.md>)和使用的[組件](<264 成分.md>)的文檔。

## Safeguard user input｜保護使用者輸入

We aim to validate user input before injecting it in the configuration in order to provide a more user friendly interface and prevent bad things to happen in the future.

我們的目標是在將使用者輸入註入配置之前對其進行驗證，以便提供更友善的使用者介面，並防止將來發生不良事件。

Although we do understand that the perfect validation isn’t always possible at once (too much referential constraints, not always as easy to catch) it is a best practice to ask yourself if a specific input could be validated (if not now, what about the future).

雖然我們明白完美的驗​​證並非總是能夠一次性實現（參考約束太多，而且並不總是那麼容易發現），但最佳實踐是問問自己，某個特定的輸入是否可以被驗證（如果現在不能，將來呢？）。

The issue with user input impossible to validate is that it will bite you eventually, leading to future security issues waiting to happen (for example a non authorized user can write commands that will be executed with elevated privileges, we saw this with openvpn for example).

使用者輸入無法驗證的問題在於，它最終會給你帶來麻煩，導致未來出現安全問題（例如，未經授權的使用者可以編寫以提升的權限執行的命令，例如我們在 openvpn 中就看到了這種情況）。

For this reason we do not allow plain text configuration data to be stored in our configuration (although some legacy components still use this [opnsense/core#d62015](https://github.com/opnsense/core/commit/d62015df1cdb0c0711b488bd66ced631b9a4f37b) )

因此，我們不允許在配置中儲存純文字配置資料（儘管一些舊元件仍然使用這種方式 [opnsense/core#d62015](https://github.com/opnsense/core/commit/d62015df1cdb0c0711b488bd66ced631b9a4f37b) ）。

Note

筆記

Feature requests for custom user inputs will be declined in our public repositories, defining what a feature should do also helps designing the right feature.

在我們的公共儲存庫中，我們將拒絕自訂使用者輸入的功能請求，定義一個功能應該做什麼也有助於設計正確的功能。

Tip

提示

If custom input is needed, in most cases you can use hooks to include additional configuration data in the service, most services offer this type of support (either with predefined directories or via the template system).

如果需要自訂輸入，大多數情況下可以使用鉤子將額外的配置資料包含在服務中，大多數服務都提供這種類型的支援（透過預先定義的目錄或透過模板系統）。

This prevents arbitrary users from adding undefined configuration data.

這樣可以防止任意用戶新增未定義的設定資料。

The different field types in our model system are aimed to help the developer safeguard his or her code for unexpected input.

我們模型系統中的不同欄位類型旨在幫助開發人員保護其程式碼免受意外輸入的影響。

## Ideal Development｜理想發展

Our ideal OPNsense system looks like a standard FreeBSD system using our pluggable user interface for management, which supports both real users as “machine” users (REST).

我們理想的 OPNsense 系統看起來像一個標準的 FreeBSD 系統，使用我們可插拔的用戶介面進行管理，它既支援真實用戶，也支援「機器」用戶（ REST ）。

When developing we want the code to be clean and coded as DRY (Don’t Repeat Yourself) as possible and do not want to invent the wheel when not needed.

在開發過程中，我們希望程式碼簡潔明了，並儘可能遵循DRY （不要重複自己）原則，並且不希望在不需要的時候重新發明輪子。

The user interface should to be able to run as non-root user instead of root by restructuring the way commands are passed to the system (configd).

透過重構向系統（configd）傳遞命令的方式，使用者介面應該能夠以非 root 使用者身分執行，而不是以 root 使用者身分執行。

## Reality: Overdue Maintenance｜實際情況：維護工作逾期

In reality we forked a system that went without code maintenance for a very long time and we needed to transition that into something more structured.

實際上，我們從一個長期缺乏程式碼維護的系統分支而來，我們需要將其過渡到更結構化的系統。

One of the first things (on the programming part of the system) we did was build components around an existing framework ([Phalcon](https://phalcon.io/)) to create new modules, which could use validated configuration data (from the config.xml), supply a RESTful API and generate HTML output using standard templates (Volt).

在系統程式設計部分，我們做的第一件事就是圍繞現有框架（[Phalcon](https://phalcon.io/) ）建立元件，以建立新模組，這些模組可以使用經過驗證的設定資料（來自 config.xml），提供 RESTful API並使用標準範本（Volt）產生HTML輸出。

We created the configd system, which can generate system configuration and execute system calls using predefined templates. And then we started using those new components for our first newly designed modules (like the proxy and the traffic shaper). More information about the “to-be” architecture can be found in our [architecture](<242 建築學.md>) documentation.

我們創建了 configd 系統，它能夠產生系統配置並使用預定義模板執行系統呼叫。隨後，我們開始將這些新元件應用於我們首批新設計的模組（例如代理和流量整形器）。有關「未來」架構的更多信息，請參閱我們的 [architecture](<242 建築學.md>)文件。

## Strategy｜策略

Knowing we can’t change the world in a single day and having a lot of legacy to drag around with us, our strategy consists of three parts:

我們深知無法在一夜之間改變世界，而且肩負著沉重的歷史使命，因此我們的策略由三個部分組成：

**1)** Cleanup and maintenance

**1)** 清理與維護

Restructure old (legacy) code, basically all code in the src/www, src/etc/inc to make it better readable, easier to use and remove unused / unnecessary parts. By doing so we want to extend the lifetime of the old code a bit and make the transition in new code easier eventually.

重構舊程式碼（基本上是 src/www 和 src/etc/inc 目錄下的所有程式碼），使其更易讀、更易用，並移除未使用或不必要的部分。這樣做是為了延長舊程式碼的使用壽命，並最終使新程式碼的過渡更加順暢。

**2)** Detach

**2)** 分離

Move system configuration calls to configd where possible, which gives the administrator the advantage of running those commands from the command line and helps removing the need for root user access in the future. The ipsec VICI implementation is one example of this stage.

盡可能將系統設定呼叫移至 configd 服務，讓管理員可以直接從命令列執行這些命令，並有助於在未來消除對 root 使用者存取權限的需求。 ipsec VICI的實作就是這一階段的一個例子。

**3)** Moving on

**3)** 繼續

(re)build new parts, using our new modules, which provide a layered development system to automatically support API calls from other systems and XML based model templates to describe configuration data.

使用我們的新模組（重新）建立新部件，這些模組提供了一個分層開發系統，可以自動支援來自其他系統的API調用和基於XML的模型模板來描述配置資料。

*See also:*

*參見：*

-   [Hello World Module](<366 你好世界模組和插件.md>)  
    [Hello World 模組](<366 你好世界模組和插件.md>)
    
-   [Howto use the API](<370 使用API.md>)  
    [如何使用API](<370 使用API.md>)
    

Our guidelines somewhat depend of the stage the code is in, when writing new code, all actions should use the API system for actually changing configuration and performing configuration tasks. They should, of course, use the normal PSR coding standards for PHP code and follow the Python PEPs.

我們的指導原則在一定程度上取決於程式碼所處的階段。在編寫新程式碼時，所有操作都應使用API系統來實際更改配置和執行配置任務。當然，對於PHP代碼，它們應遵循標準的PSR編碼規範，並遵循Python PEP（Python開發者提案）。

When moving to the legacy part of the system, our goal is to stick as close to PSR1/2 as possible, knowing it will never be perfect.

在遷移到系統的遺留部分時，我們的目標是盡可能接近PSR1 /2，但我們知道它永遠不會完美。

Note

筆記

When building new (MVC based) code, its not allowed to include legacy parts directly. The main reason for this is preventing technical debt being stacked in new components and loosing oversight.

編寫新的（基於MVC的）程式碼時，不允許直接包含舊版元件。主要原因是防止技術債務堆積在新組件中，並導致監管不力。
