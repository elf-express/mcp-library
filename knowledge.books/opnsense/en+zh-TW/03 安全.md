## [Intro](#id15)｜[引言](#id15)

As a trusted open source security product, we do care a lot about security and, with our regular release schedule, we try to stay ahead of possible incidents. Even though we are cautious and stay informed, sometimes issues do occur, in which case it is good to know what to do.

作為一款值得信賴的開源安全產品，我們非常重視安全性，並透過定期發布更新來努力預防潛在安全事件的發生。儘管我們保持謹慎並密切關注安全動態，但有時問題仍然會發生，在這種情況下，了解應對措施至關重要。

## [Staying ahead](#id16)｜[保持領先](#id16)

Even though we always encourage people to update regularly, sometimes it is not possible to do so for various reasons.

儘管我們一直鼓勵大家定期更新，但有時由於各種原因，這是不可能的。

Luckily, OPNsense comes with an integrated security check for known vulnerabilities, which can be found in our firmware module. In which case you do have the opportunity to validate for yourself what the risk is to keep using the current version for a bit longer.

幸運的是，OPNsense 內建了已知漏洞的安全檢查功能，該功能位於我們的韌體模組中。因此，您可以自行驗證繼續使用目前版本一段時間的風險。

You can reach it via System -> Firmware in the status pane, the button “Run an Audit”（進行審核） will bring you right into the security report.

您可以透過狀態窗格中的「系統」->「韌體」存取它，按鈕“Run an Audit”（進行審核）將直接帶您進入安全性報告。

If all goes well, a report like the one below will be shown:

如果一切順利，將會顯示以下報告：

```
***GOT REQUEST TO AUDIT SECURITY***
Currently running OPNsense 22.1.8_1 (amd64/OpenSSL) at Tue May 31 09:01:04 CEST 2022
vulnxml file up-to-date
0 problem(s) in 0 installed package(s) found.
***DONE***
```

Note

筆記

We do not offer community support on assessing if incidents on older versions do warrant an immediate upgrade on your end as this often depends on features used and settings configured. Our advice always will be to upgrade into the latest community or business version.

我們不提供社群支持，幫助您評估舊版中出現的問題是否需要立即升級，因為這通常取決於您使用的功能和配置的設定。我們始終建議您升級到最新的社群版或企業版。

Warning

警告

Please do not report issues to us reported by the security health check, they are already known and highly likely a fix is pending for the next release.

請不要向我們報告安全健康檢查中發現的問題，這些問題我們已經知道，並且很可能會在下一個版本中修復。

## [Assessing risks](#id17)｜[風險評估](#id17)

As with all software, understanding how software is being developed helps a lot assessing the risks involved when using with it. Most software components are built on top of other components, which all have their own security challenges. From an architecture perspective, we do try to minimize the external dependencies as much as possible, but obviously need various software components for the broad spectrum of features that we offer.

與所有軟體一樣，了解軟體的開發方式對於評估其使用風險大有裨益。大多數軟體元件都建構在其他元件之上，而每個元件都存在自身的安全挑戰。從架構角度來看，我們力求盡可能減少外部依賴，但顯然，為了實現我們提供的廣泛功能，各種軟體元件不可或缺。

When we add functionality ourselves (supported under [tiers 1 and 2](<379 支援選項.md>)), we tend to ask ourselves at least the following questions:

當我們自行添加功能時（在 [第 1 層和第 2 層](<379 支援選項.md>)下支援），我們通常至少會問自己以下問題：

-   Does the new component we plan to add replace something we already use, and how are we going to make sure we don’t end up with just one more component?  
    我們計劃添加的新組件是否會替換我們已經使用的組件？我們如何確保最終不會只增加一個組件？
    
    -   A good example of this is the use of [tabulator](https://www.tabulator.info/) which gradually replaced bootgrid we used earlier  
        一個很好的例子就是[tabulator](https://www.tabulator.info/)的使用，它逐漸取代了我們之前使用的 bootgrid。
        
-   How active is the development of the component in question, and what level of support can be expected?  
    該組件的開發進度如何？可以獲得怎樣的支持？
    
-   What is the expected maintenance burden, and is it reasonable in relation to the added functionality?  
    預計維護負擔有多大？相對於新增功能而言是否合理？
    
    -   When a library offers minimal additional functionality compared to the tools already available in the language being used, it’s often better to build and maintain the functionality ourselves to keep dependencies more manageable.  
        當一個函式庫與所用語言中已有的工具相比，提供的功能微乎其微時，為了更好地管理依賴關係，通常最好自己建構和維護這些功能。
        
    -   Also, when we already have a component offering almost the same functionality, does adding another one make sense?  
        此外，既然我們已經有一個元件提供了幾乎相同的功能，那麼再增加一個元件還有意義嗎？
        
-   Could we \[easily\] replace a component with an alternative or maintain the software ourselves?  
    我們能否輕鬆地用替代品替換某個組件，或自行維護軟體？
    
    -   An example of this is our previous use of Phalcon to support most of our MVC code, which has since been largely rewritten using standard PHP code.  
        例如，我們之前使用 Phalcon 來支援我們的大部分MVC程式碼，而這些程式碼後來大多已使用標準的PHP程式碼重寫。
        

Although our development manual contains a lot of detail on how we work, it doesn’t hurt to explain our approach here at a high level, with more focus on its security aspects. Different components in the stack may take slightly different approaches to handling security issues. While planning and building releases, all these topics are taken under consideration.

雖然我們的開發手冊詳細介紹了我們的工作流程，但在這裡簡要概述我們的方法，並重點關注其安全性方面，也並無壞處。技術堆疊中的不同元件在處理安全問題時可能會採用略有不同的方法。在規劃和建造版本時，所有這些問題都會被納入考慮範圍。

### [\[FreeBSD\] Base system and kernel](#id18)｜[\[FreeBSD\] 基礎系統與核心]( https://docs.opnsense.org/security.html#id18 )

儘管我們更傾向於使用作業系統軟體的發布版本，但 OPNsense 和 FreeBSD 的發布節奏有所不同，這意味著我們在實際應用中會先使用一個發布版本（例如`15.1` ），並在規劃發佈時跟踪上游的安全問題。 FreeBSD 的安全公告已公開提供 [1](#id4) 。如有疑問，我們已實施的安全公告已在發布說明 [2](#id5)中提及，並記錄在我們公開的源代碼庫 [3](#id6)中。

### [\[ports\] External software](#id19)｜[\[埠\] 外部軟體]( https://docs.opnsense.org/security.html#id19 )

External software in most BSD’s is managed via a “ports collection”, which is more or less a recipe book describing how to construct different pieces of software. OPNsense hosts a (partial) mirror of the upstream collection with some specific software additions on top for binary software we maintain ourselves.

大多數BSD系統中的外部軟體都是透過「連接埠集合」進行管理的，它更像是一本配方手冊，描述如何建立不同的軟體元件。 OPNsense 託管上游連接埠集合的（部分）鏡像，並在此基礎上添加了一些我們自己維護的二進位軟體。

In order to track vulnerabilities, one can use VuXML [4](#id8) ., which can also be queried directly from the OPNsense interface using the “security audit” feature in the firmware section.

為了追蹤漏洞，可以使用 VuXML [4](#id8) .，也可以使用韌體部分的「安全審計」功能直接從 OPNsense 介面查詢。

Although not all security incidents on software installed may have impact on your setup, this information offers insights into the risks involved with your running configuration.

尽管并非所有已安装软件的安全事件都会影响您的设置，但此信息可让您深入了解与运行配置相关的风险。

Below an example of a report extracted via the audit feature.

下面是通过审核功能提取的报告示例。

```
 python313-3.13.15 is vulnerable:
   Python -- poplib module, when passed a user-controlled command, can have additional commands injected using newlines
   CVE: CVE-2025-15367
   WWW: https://vuxml.FreeBSD.org/freebsd/6d3488ae-2e0f-11f1-88c7-00a098b42aeb.html
```

The first line (1) explains which software package the jeopardy refers to, next (2) there are some details about the incident which helps assessing if this particular issue impacts you, when one or more CVE’s are attached you can find them in the following lines (3), followed by a link to more information (4).

第一行 (1) 解释了危险所指的软件包，接下来 (2) 有一些有关该事件的详细信息，有助于评估此特定问题是否影响您，当附加一个或多个 CVE 时，您可以在以下行 (3) 中找到它们，后面是更多信息的链接 (4)。

When planning releases, we use the same information to determine impact on our product.

在规划版本时，我们使用相同的信息来确定对我们产品的影响。

[https://vuxml.freebsd.org/freebsd/index.html](https://vuxml.freebsd.org/freebsd/index.html)

## [Upstream vulnerabilities](#id21)｜[上游漏洞](#id21)

Since OPNsense is a collection of open source software, when finding an issue, it is always a good idea to inspect where it should be fixed first. In case you do not know or are not sure, you can still ask on our end, just know that we do not have the manpower to act as an intermediary between various projects.

由于 OPNsense 是开源软件的集合，因此在发现问题时，最好首先检查应该修复的位置。如果您不知道或不確定，您仍然可以向我們詢問，只要知道我們沒有人力在各個專案之間充當中介即可。

## [Deployment considerations](#id22)｜[部署注意事項](#id22)

A firewall is a security tool and should be deployed and operated accordingly. While OPNsense provides mechanisms to help secure a network environment, no firewall can compensate for weak operational practices or excessive trust relationships.

防火牆是一種安全工具，應相應地部署和操作。虽然 OPNsense 提供了帮助保护网络环境的机制，但没有任何防火墙可以弥补薄弱的操作实践或过度的信任关系。

Users who are granted access to the firewall typically perform administrative or operational tasks and therefore require an elevated level of trust. Administrative access should be limited to users who require it for their role, and permissions should be assigned according to the principle of least privilege whenever possible.

被授予防火牆存取權限的使用者通常會執行管理或操作任務，因此需要更高的信任等級。管理访问权限应仅限于需要其角色的用户，并且应尽可能根据最小特权原则分配权限。

Trusted administrators only

僅限受信任的管理員

Some access control roles provide capabilities that effectively allow complete control over the system, either directly or indirectly, and should therefore only be assigned to fully trusted administrators or administrative peers.

某些访问控制角色提供的功能可以有效地直接或间接地完全控制系统，因此只能分配给完全信任的管理员或管理同级。

Examples include privileges such as `XMLRPC Library`, which can be used for remote configuration synchronisation and automation, and `System: Configuration: Backups`, which provides access to configuration exports containing sensitive information. In practice, any privilege that grants access to configuration data, remote management interfaces, backup material or automation mechanisms should be considered security-sensitive and assigned with care.

示例包括`XMLRPC Library`等权限，可用于远程配置同步和自动化，以及`System: Configuration: Backups`，可提供对包含敏感信息的配置导出的访问。在实践中，任何授予对配置数据、远程管理接口、备份材料或自动化机制的访问权限的权限都应被视为安全敏感的，并应谨慎分配。

Fine-grained permissions and trust

細粒度的權限和信任

Access control lists can provide fine-grained permissions for operational convenience, delegation and improved visibility. Depending on the use case, these permissions may also serve as effective security boundaries.

存取控制清單可以提供細粒度的權限，以實現操作便利、委派和提高可見性。根據用例，這些權限也可以充當有效的安全邊界。

Administrators should, however, consider the effective capabilities granted by a role rather than relying solely on the apparent scope of individual privileges. Some permissions may appear limited in scope while still allowing users to influence or bypass related security controls indirectly.

然而，管理員應該考慮角色授予的有效能力，而不是僅僅依賴個人特權的明顯範圍。某些權限可能看起來範圍有限，但仍允許使用者間接影響或繞過相關安全控制。

For example, a user who is permitted to manage port forwarding rules may be able to create access paths to systems or services that would otherwise remain inaccessible.

例如，被允許管理連接埠轉送規則的使用者可能能夠建立對系統或服務的存取路徑，否則這些系統或服務將無法存取。

Permission assignments should therefore reflect both the intended task and the level of trust placed in the user receiving them.

因此，權限分配應反映預期任務和接收它們的使用者的信任程度。

Legacy components

遺留組件

Some legacy components, identified by URIs ending in `.php`, originate from earlier parts of the codebase and may implement fewer validation and access control safeguards than newer components. Access to these pages should therefore be restricted to fully trusted administrators whenever possible.

一些遺留元件（由以 `.php` 結尾的 URI 標識）源自於程式碼庫的早期部分，並且可能比新元件實現更少的驗證和存取控制保護措施。因此，只要有可能，對這些頁面的存取應僅限於完全信任的管理員。

Access to the management interface should be restricted to trusted networks and secured using strong authentication mechanisms. Administrative accounts should use unique passwords and additional authentication factors where supported and appropriate.

對管理介面的存取應僅限於受信任的網絡，並使用強大的身份驗證機制進行保護。管理帳戶應在支援和適當的情況下使用唯一的密碼和其他身份驗證因素。

To reduce the attack surface, unnecessary services, plugins and user accounts should be disabled or removed. Systems should be kept up to date by installing security and maintenance updates in a timely manner.

為了減少攻擊面，應停用或刪除不必要的服務、外掛程式和使用者帳戶。應透過及時安裝安全性和維護更新來使系統保持最新狀態。

Regular reviews of firewall rules, user accounts, exposed services and remote access methods help ensure that configurations continue to reflect operational requirements and do not unintentionally introduce security risks.

定期審查防火牆規則、使用者帳戶、公開服務和遠端存取方法有助於確保配置繼續反映操作要求，並且不會無意中引入安全風險。

Configuration backups should be created regularly and stored securely to facilitate recovery from hardware failures, configuration errors or security incidents. Logging and monitoring should be enabled to assist with troubleshooting, auditing and the detection of unexpected behaviour.

應定期建立配置備份並安全存儲，以便於從硬體故障、配置錯誤或安全事件中恢復。應啟用日誌記錄和監控以協助故障排除、審核和偵測意外行為。

Security is not a single configuration option or deployment step, but an ongoing process of review, maintenance and adaptation to changing requirements and threats.

安全性不是單一的配置選項或部署步驟，而是一個持續的審查、維護和適應不斷變化的需求和威脅的過程。

## [Reporting an incident](#id23)｜[檢舉事件](#id23)

Security incidents on our product can be reported using our [GitHub repository](https://github.com/opnsense/core/security). You may also create a new issue and select “Report a security vulnerability”, which will redirect you to the same page. Alternatively, you can report security issues to our security team available at **security** @ **opnsense.org**.

可以使用我們的 [GitHub 儲存庫](https://github.com/opnsense/core/security) 報告我們產品的安全事件。您也可以建立一個新問題並選擇“報告安全漏洞”，這會將您重新導向到同一頁面。或者，您可以向我們的安全團隊報告安全性問題，網址為 **security**@**opnsense.org**。

All reports should contain at least the following information:

所有報告應至少包含以下資訊：

-   A clear description of the vulnerability at hand  
    對當前漏洞的清晰描述
    
-   Which versions of our product seem to be affected  
    我們產品的哪些版本似乎受到影響
    
-   Any known workaround  
    任何已知的解決方法
    
-   When possible, some example code  
    如果可能的話，一些範例程式碼
    

## [Information handling policies](#id24)｜[資訊處理政策](#id24)

As a general policy we do favor full disclosure of vulnerability information after a reasonable amount of time to permit safe analysis and correction as well as appropriate testing for the correction at hand.

作為一般政策，我們確實贊成在合理的時間後全面披露漏洞信息，以便進行安全分析和糾正，並對當前的糾正進行適當的測試。

In order to coordinate with other affected parties, we might share parts of the information provided to us to them as well or ask the reporter to do so.

為了與其他受影響方進行協調，我們也可能會向他們分享我們提供的部分信息，或要求報告者這樣做。

When the submitter is interested in a coordinated disclosure process, this should be indicated in any submission to avoid discussions later on.

當提交者對協調揭露流程感興趣時，應在提交的任何內容中註明這一點，以避免以後的討論。

## [Third party security verification](#id25)｜[第三方安全驗證](#id25)

### [Intro](#id26)｜[簡介](#id26)

Within the OPNsense team and community, we spend a lot of time safeguarding our software and keeping up with the latest threats, like checking used software against CVEs on every release, implementing best practices in our development methods and offering clear and transparent release engineering.

在 OPNsense 團隊和社群中，我們花費了大量時間來保護我們的軟體並跟上最新的威脅，例如根據每個版本的 CVE 檢查所使用的軟體、在我們的開發方法中實施最佳實踐以及提供清晰透明的發布工程。

To improve this even further, we decided to bring a third party on board and mold a process around our security verification by trained security professionals.

為了進一步改進這一點，我們決定引入第三方，並由經過培訓的安全專業人員圍繞我們的安全驗證制定流程。

### [Business Edition](#id27)｜[商業版](#id27)

As our Business Edition is aimed at professional users, it does make sense to offer additional safeguards, like even more extensive testing on this product. Looking at the lifecycle of our software, this is also the most mature stage of what we do have to offer:

由於我們的商業版面向專業用戶，因此提供額外的保護措施確實有意義，例如對此產品進行更廣泛的測試。看看我們軟體的生命週期，這也是我們所提供的最成熟的階段：

-   Development version  
    開發版
    
    -   Available at every release, it offers a glimpse of what to expect in the near future.  
        它在每個版本中都可用，讓您可以一睹在不久的將來會發生什麼。
        
-   Community version  
    社群版
    
    -   When changes survive the development version, these are included in the community version, these are internally tested and feedback has been offered by community members.  
        當變更在開發版本中倖存下來時，這些變更將包含在社群版本中，這些內容經過內部測試並由社群成員提供回饋。
        
-   Business Edition  
    商業版
    
    -   Functional changes are being included in a more conservative manner, more feedback has been collected from development and community, leading to a mission-critical version of the well-known OPNsense firewall.  
        功能變更以更保守的方式進行，從開發和社群收集了更多回饋，從而形成了著名的 OPNsense 防火牆的關鍵任務版本。
        

As security testing is quite time-consuming, we aim to offer a full qualification cycle for every major release.

由於安全測試非常耗時，我們力求為每個主要版本提供完整的認證週期。

### [Framework / Type of testing (LINCE)](#id28)｜[框架/測試類型 ( LINCE )](#id28)

In our quest for a framework to use, we found the LINCE methodology.

在尋找合適的框架時，我們發現了LINCE方法論。

LINCE is a lightweight methodology for evaluating and certifying ICT products, created by Spain’s National Cryptologic Center ([CCN](https://cpstic.ccn.cni.es/en/)), based on Common Criteria principles and oriented around vulnerability analysis and penetration tests.

LINCE是一種輕量級的評估和認證ICT產品的方法，由西班牙國家密碼中心 ([CCN](https://cpstic.ccn.cni.es/en/) ) 創建，基於通用準則原則，並圍繞漏洞分析和滲透測試展開。

LINCE’s strengths over other methodologies mainly consist of reduced effort and duration. However, the way in which it is applied also makes it possible to pay more attention to the critical points of each product, giving more weight to concrete and practical tests that combat real threats than to dense documentation or exhaustive functionality tests.

LINCE相較於其他方法的主要優點在於工作量和時間投入的減少。此外，其應用方式也使得我們能夠更加關注每個產品的關鍵點，更加重視針對實際威脅的特定實用測試，而非繁瑣的文檔編寫或詳盡的功能測試。

As most frameworks are not intended to be repeated very regularly, together with [jtsec](https://www.jtsec.es/) we came up with an approach which makes it possible to pass the test twice a year, which is needed to align with our Business Edition releases.

由於大多數框架並非旨在經常重複使用，因此我們與 [jtsec](https://www.jtsec.es/)一起提出了一種方法，使得每年進行兩次測試成為可能，這對於與我們的商業版發布保持一致是必要的。

During every cycle, there is always a chance that (small) issues appear which should be fixed, in close accordance with jtsec, the OPNsense team prepares fixes for the findings and makes sure that these are included in a future (minor) release.

在每個週期中，總有可能出現一些（小的）問題需要解決。根據 jtsec 的規定，OPNsense 團隊會針對發現的問題準備修復方案，並確保這些方案包含在未來的（次要）版本中。

### [Steps in the process](#id29)｜[流程步驟](#id29)

To better understand where a version of OPNsense is at in terms of verification, we distinguish the following stages in the process, which we will also note on the version at hand.

為了更了解 OPNsense 的某個版本在驗證方面的位置，我們將流程分為以下階段，我們也會在目前版本中註明這些階段。

1.  In testing - Software delivered to jtsec, in process (interaction between OPNsense and jtsec).  
    測試中 - 交付給 jtsec 的軟體，正在進行中（OPNsense 和 jtsec 之間的交互作用）。
    
2.  Tested - Software verified / tested, documentation not yet published.  
    已測試 - 軟體已驗證/測試，文件尚未發布。
    
3.  LINCE Compliant - Test complete including a summarised report (by jtsec).  
    LINCE符合標準 - 測試完成，包括一份總結報告（由 jtsec 提供）。
    
4.  Certification pending - Offered for formal certification.  
    認證待定 - 可提供正式認證。
    
5.  LINCE Certified - Certified by CCN.  
    LINCE認證 - 由CCN認證。
    

The certification steps are executed twice a year, once for each Business Edition release. This process is quite time consuming, but adds another independent party to the mix.

認證步驟每年執行兩次，每次針對商業版版本發布。這個過程相當耗時，但引入了另一個獨立的第三方機構。

### [Timeline](#id30)｜[時間軸](#id30)

The first fully certified product has been a community version (21.7.1), which offered us insights into the process and helped us improve the process which we would like to use for the Business Edition. We started this cycle with version 22.4 including full testing by jtsec.

第一款獲得全面認證的產品是社群版（ 21.7.1 ），它讓我們深入了解了整個流程，並幫助我們改進了流程，我們希望將這些改進應用於商業版。我們以版本22.4開啟了這一週期，該版本由jtsec進行了全面測試。
