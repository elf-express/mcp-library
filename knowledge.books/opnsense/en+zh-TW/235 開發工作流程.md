# Development Workflow｜開發工作流程

> 章節：[Development Manual](<000 目錄.md#c-52>)

![../_images/flow.png](<../images/7466132a-flow.png>)

It’s pretty hard to approach a larger repository you have never worked with. The biggest issue is that few projects have defined development (as in actual coding) workflow laid out for new contributors, so one is just going to be stabbing in the dark for a few days or weeks until things start making sense. Speaking of *sense*, let’s explain how we’ve designed the development experience for [OPNsense](https://opnsense.org/developers-invitation/) and how you can start contributing code in no time.

接近一個你從未使用過的更大的儲存庫是相當困難的。最大的問題是，很少有專案為新貢獻者定義了開發（如實際編碼）工作流程，因此人們只能在黑暗中摸索幾天或幾週，直到事情開始有意義。說到 *sense*，讓我們解釋一下我們如何設計 [OPNsense](https://opnsense.org/developers-invitation/) 的開發體驗，以及如何立即開始貢獻程式碼。

## Structure｜結構

Source, Ports, Core, Tools

原始碼、連接埠、核心、工具

The structure is pretty much FreeBSD: we have a [source code](https://github.com/opnsense/src) repository and a [ports tree](https://github.com/opnsense/ports). Historically, we also have a [core code](https://github.com/opnsense/core) and [tools repository](https://github.com/opnsense/tools). The tools repository is project shell code gluing all repositories together, producing final images, while the core is the important GUI and system configuration bits.

其結構與 FreeBSD 非常相似：我們有一個 [原始碼](https://github.com/opnsense/src)倉庫和一個 [端口樹](https://github.com/opnsense/ports)倉庫。歷史上，我們還有一個 [核心代碼](https://github.com/opnsense/core)倉庫和一個 [工具倉庫](https://github.com/opnsense/tools)倉庫。工具倉庫包含專案 shell 程式碼，用於將所有倉庫黏合在一起，產生最終鏡像；而核心程式碼則包含重要的GUI程式碼和系統配置部分。

Note

筆記

As of 16.1 there is also plugin support, the source repository is [plugins tree](https://github.com/opnsense/plugins) . Plugins are a modular way of easily extending the existing system.

從16.1開始，也支援插件，原始碼庫位於[plugins tree](https://github.com/opnsense/plugins) 。插件是一種模組化的方式，可以輕鬆擴展現有系統。

Why core is not a part of source

為什麼核心不是原始碼的一部分

The first thing that’s interesting is that the core is not part of the source repository, because it depends on third party software found in the ports. We can’t stick core into source, because ports are things that don’t fit into the base system. It also helps to keep source repository changes to the minimum to make major FreeBSD upgrades easier in the future.

首先值得注意的是，核心程式碼並不包含在原始碼庫中，因為它依賴連接埠中的第三方軟體。我們不能將核心程式碼直接放入原始碼庫，因為連接埠本身就不是基礎系統的一部分。這樣做也有助於將原始碼庫的改動降到最低，從而方便未來對 FreeBSD 進行重大升級。

Why core isn’t part of ports either

為什麼核心也不屬於連接埠的一部分？

Why is the core repository not in the ports? Well, we have a couple of custom ports in the ports tree, but these are small. The core repository as well as the ports tree itself are so big that it made sense to keep them separate. Another reason is that the core repository only contains scripts in Shell, Python and PHP. So the tools repository actually treats the core repository as a package that depends on all the ports it needs. This way, on the images, it looks like the core code is just another package. **That makes upgrading the core code very easy and fast without modifying base.** We can even upgrade to newer ports pages and add and remove them as we go forward.

為什麼核心程式碼庫不在 ports 樹中？嗯，我們在 ports 樹中確實有一些自訂端口，但它們都很小。核心程式碼庫以及 ports 樹本身都非常龐大，所以將它們分開存放更有意義。另一個原因是核心程式庫只包含 Shell、Python 和PHP的腳本。因此，工具庫實際上將核心程式碼庫視為依賴所有所需連接埠的軟體包。這樣，在鏡像中，核心程式碼看起來就像是另一個軟體包。 **這使得升級核心程式碼變得非常容易和快捷，而無需修改基礎程式碼。**我們甚至可以升級到更新的連接埠頁面，並根據需要隨時新增或刪除連接埠。

## Building｜大樓

Not Clobbering the Build System

不破壞建造系統

The tools repository is designed to run on a stock FreeBSD using [chroot mechanics](http://en.wikipedia.org/wiki/Chroot) to keep the build contained and consistent. There’s nothing worse than a build system that modifies the build system and at some point starts to dash out working images–only to stop working some time in the future. No, no, no.

此工具庫旨在利用 [chroot 機制](http://en.wikipedia.org/wiki/Chroot)在標準的 FreeBSD 系統上運行，以確保建置過程的封閉性和一致性。最糟糕的情況莫過於建置系統修改自身，然後突然開始發布可用的鏡像——但過不了多久又會停止工作。絕對不行，絕對不行，絕對不行。

You can also “cross-build” between FreeBSD versions. We’ve successfully built images on FreeBSD 10.1 when OPNsense was still running on FreeBSD 10.0. (version 16.1 now runs on FreeBSD 10.2) That’s not a huge gap and the [ABI](https://en.wikipedia.org/wiki/Application_binary_interface) is the same, but we expect this to work with FreeBSD 11 and beyond as well so that if you have a FreeBSD box you will always be able to produce your own images if you desire–without spinning up extra machines, jails or virtual machines.

您也可以在不同 FreeBSD 版本之間進行「交叉建置」。我們已成功在 FreeBSD 10.1上建立了鏡像，當時 OPNsense 仍在 FreeBSD 10.0上運行。 （版本16.1現在運行在 FreeBSD 10.2上。）雖然版本之間的差距並不大，[ABI](https://en.wikipedia.org/wiki/Application_binary_interface)情況也類似，但我們預計此功能也適用於 FreeBSD 11 及更高版本，因此如果您擁有一台更多版 FreeBSD系統，您始終可以根據需要創建自己的鏡像，而無需啟動額外的機器、jail 或虛擬機器。

Here are the [build instructions for OPNsense](https://github.com/opnsense/tools/blob/master/README.md).

以下是 [OPNsense 的建造說明](https://github.com/opnsense/tools/blob/master/README.md) 。

Tip

提示

As of November 2015 OPNsense is equipped with a tool that can completely reinstall a running system in place for a thorough factory reset or to restore consistency of all the OPNsense files. It can also wipe the configuration directory, but won’t do that by default. The [opnsense-bootstrap](https://github.com/opnsense/update) script is particularly useful if you want to convert a hosted FreeBSD system to OPNsense.

截至 2015 年 11 月，OPNsense 配備了一個工具，可以對正在運行的系統進行完全重裝，從而實現徹底的恢復出廠設定或恢復所有 OPNsense 文件的一致性。它還可以清除配置目錄​​，但預設不會執行此操作。 [opnsense-bootstrap](https://github.com/opnsense/update)腳本在將託管的 FreeBSD 系統轉換為 OPNsense 時特別有用。

## Virtual Machine for Development｜用於開發的虛擬機

Running: Use a Virtual Machine for Development

運作：使用虛擬機器進行開發

It’s just easier and less tedious if the kernel crashes, to revert to a previous state, or isolate and test different features. A VM can be set up easily using the ISO images. Also very good for testing installation and upgrades. Of course, at some point you will want to bring OPNsense to your actual target device—just make sure you know the system well enough before you attempt this.

如果核心崩潰，恢復到先前的狀態或隔離並測試不同的功能會更容易、更省事。使用ISO鏡像可以輕鬆設定VM 。它也非常適合測試安裝和升級。當然，最終您肯定希望將 OPNsense 部署到目標設備上——只需確保您在嘗試之前對系統足夠了解即可。

[VirtualBox](https://www.virtualbox.org/) is a solid tool for the job, but be sure to check out [FreeBSD’s Bhyve](http://bhyve.org/) as well (it was added in FreeBSD 10.0). However, If you are only interested in GUI coding, you can skip all the build parts and directly download an image and spin it up. Because…

(https://www.virtualbox.org/)是一個不錯的工具，但也要了解 FreeBSD 的(http://bhyve.org/) （它是在 FreeBSD 10.0中新增的）。不過，如果您只對GUI感興趣，您可以跳過所有建置步驟，直接下載鏡像並啟動它。因為…

## Packages｜包裹

It Gets Even Better

更精彩的還在後頭

Once you have a running instance, how to produce and push code? Well, there’s a couple optional of packages that help you to be productive:

一旦實例運行起來，如何編寫和推送程式碼呢？其實，有一些可選的軟體包可以幫助你提高效率：

```
# pkg install vim-console emacs-nox joe nano gnu-watch git tmux screen
```

The most important one is *git* for obtaining the code, the rest is optional if you need it—mostly editors and terminal wrappers. It is also possible to mount sshfs or do sftp to sync files from the repo if you would like to use a graphical editor from your own system. As the root user do the following:

最重要的一個是用於獲取程式碼的 *git*，如果您需要，其餘的都是可選的 - 主要是編輯器和終端包裝器。如果您想在自己的系統中使用圖形編輯器，也可以安裝 sshfs 或執行 sftp 來同步儲存庫中的檔案。以 root 使用者身分執行以下操作：

```
# cd
# git clone https://github.com/opnsense/core
```

Once you have the repository, you switch it live using:

取得儲存庫後，您可以使用以下命令將其切換到上線：

```
# cd core
# make mount
```

Yes, the changes that you make in the repository will show up directly in the GUI now! Unfortunately, this will mount the repo over */usr/local* so if you modify packages the changes will light up in git. Be careful. To prevent that from happening you can temporarily unmount using:

是的，您在倉庫中所做的更改現在會直接顯示在GUI中！但遺憾的是，這會將倉庫掛載到 */usr/local* 目錄下，因此如果您修改了軟體包，這些變更也會反映到 Git 中。請務必小心。為了避免這種情況，您可以使用以下命令暫時卸載倉庫：

```
# make umount
```

To finish that off the boot sequence will mount the core repository set up in */root/core* as early as possible (if it’s available) and will use its modifications for booting up (with the exception of /usr/local/etc/rc itself). This makes it possible to work on the backend configuration and boot sequence improvements without having out of sync system files and repositories.

最後，啟動序列會儘早掛載位於 */root/core* 的核心倉庫（如果可用），並使用其中的修改進行啟動（/usr/local/etc/rc 本身除外）。這樣，就可以在不影響系統檔案和倉庫同步的情況下，進行後端設定和啟動序列的改進。

## Summary｜概括

Easy Access is Key to Collaboration

便捷的存取是協作的關鍵

Although this is just a peek into OPNsense development workflow it brings to attention a key aspect: moving barriers out of the way to enable as many people as possible to produce quick results. Yes,there are barriers like [git](http://git-scm.com/book/en/v2/Git-Basics-Getting-a-Git-Repository) and [GitHub](https://guides.github.com/activities/contributing-to-open-source/) to deal with, maybe even learning FreeBSD intricacies, but once you have your code in the GUI and working fine, you’ll feel proud enough to endure the hardships of making sure your patch will have a place in our upstream repositories so the community as a whole can benefit from your dedication.

雖然這只是 OPNsense 開發工作流程的一個縮影，但它突出了一個關鍵方面：掃清障礙，讓盡可能多的人能夠快速產出成果。沒錯，確實存在一些障礙，例如 [git](http://git-scm.com/book/en/v2/Git-Basics-Getting-a-Git-Repository)和 [GitHub](https://guides.github.com/activities/contributing-to-open-source/)需要克服，甚至可能需要學習 FreeBSD 的一些複雜細節，但一旦你的程式碼提交到GUI並且運行良好，你就會感到無比自豪，並願意從而使你成功的整個程式碼

The OPNsense core team looks forward to your feedback; “We are seeking for more improvements in the build system and eagerly await your pull requests.” Take care and code responsibly. :)

OPNsense核心團隊期待您的回饋；「我們正在尋求對建置系統的更多改進，並熱切期盼您的拉取請求。」請謹慎編寫程式碼，並注意安全。 :)
