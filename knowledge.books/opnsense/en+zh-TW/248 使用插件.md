# Using plugins｜使用插件

> 章節：[Development Manual](<000 目錄.md#c-52>) › [Backend](<000 目錄.md#c-54>)

## General｜一般的

Plugins are located in the following location:

插件位於以下位置：

```
/usr/local/etc/inc/plugins.inc.d/
```

And contain files with the extension “.inc”.

並且包含副檔名為“.inc”的檔案。

All automatically registered functions start with the name of the file (without the extension), followed by the purpose. For example *vpn\_configure* would be the *configure* handle in a plugin file name vpn.inc.

所有自動註冊的函數都以檔案名稱（不含副檔名）開頭，後面接著函數用途。例如，*vpn\_configure* 表示插件檔案 vpn.inc 中的 *configure* 句柄。

With the use of these plugins, you have the ability to hook into different areas of the system, such as registration of new interface types and making sure services are shown in the regular service overview.

透過這些插件，您可以存取系統的不同區域，例如註冊新的介面類型，並確保服務顯示在常規服務概覽中。

Note

筆記

When plugins fail and cause PHP errors, these will be collected in `/tmp/PHP_errors.log`, these plugins are not registered and executed when emitting such errors

當插件發生故障並導致PHP錯誤時，這些錯誤將被收集到`/tmp/PHP_errors.log`中。這些插件在發生此類錯誤時不會被註冊和執行。

## Services｜服務

To register services, the `<plugin>_services()` function should return a structure containing its name, description and operating properties.

要註冊服務， `<plugin>_services()`函數應傳回一個包含其名稱、描述和運行屬性的結構。

```php
function myplugin_services()
{
    $service = array();
    $service['name'] = 'myservice';
    $service['description'] = gettext('My service');
    $service['configd']['restart'] = array('myservice restart');
    $service['configd']['start'] = array('myservice start');
    $service['configd']['stop'] = array('myservice stop');
    $services[] = $pconfig;
    return $services;
}
```

| **option**<br>**選項** | **Description**<br>**描述** |
| --- | --- |
| name<br>名稱 | Service identifier<br>服務標識符 |
| id | Optional identifier to suffix the service, only used in specific cases where one “service” can actually be a list of them (e.g. `openvpn`)<br>可選的標識符，用於附加到服務名稱後綴，僅在特定情況下使用，即一個「服務」實際上可以是多個服務的列表（例如`openvpn` ） |
| description<br>描述 | User friendly description<br>使用者友善描述 |
| pidfile<br>pid檔 | Validate running based on specified pid file (instead of “name”)<br>根據指定的pid檔（而非「名稱」）驗證運行情況 |
| nocheck | \[boolean\] ignore pid or process name and always report running<br>\[boolean\] 忽略進程 ID 或進程名稱，並且始終報告正在運行 |
| {type} | Type could be one of `configd`, `php`, `mwexec`<br>類型可以是`configd`, `php`, `mwexec` |
| {type}.start | Action to call when starting the service<br>啟動服務時要呼叫的操作 |
| {type}.stop | Action to call when stopping the service<br>停止服務時要呼叫的動作 |
| {type}.restart | Action to call when restarting the service<br>重啟服務時要呼叫的動作 |

To list all available services from the command line, you can use pluginctl (bundled with our core system).

若要從命令列列出所有可用服務，您可以使用pluginctl（與我們的核心系統捆綁在一起）。

```
pluginctl -s
```

The same tool can also be used to execute the \[re\]start/stop operations, for the example above, a restart would look like:

同一個工具也可以用來執行重啟/停止操作，例如，上面的重啟操作如下所示：

```
pluginctl -s myservice restart
```

## Configure｜配置

The configure plugin can be used to catch certain events, such as `bootup`, `newwanip` and others.

配置插件可用於捕捉某些事件，例如`bootup`, `newwanip`等。

A small sample of a registration is shown below, which registers the functions `myplugin_configure()` on bootup and `myplugin_configure_vpn()` on vpn state change where the latter is accepting two (:2) parameters at most. Note that the default number of arguments passed to the listeners is one (:1) which is the `$verbose` parameter steering whether the function is allowed to print progress or not. The maximum number of arguments passed depends on the particular event provider. For more details see below.

下面展示了一個註冊範例，它註冊了啟動時觸發的函數`myplugin_configure()`和VPN狀態改變時觸發的函數`myplugin_configure_vpn()` ，其中後者最多接受兩個(:2)參數。請注意，傳遞給監聽器的預設參數數量為1(:1)，即`$verbose`參數，此參數控制函數是否允許列印進度。傳遞的最大參數數量取決於特定的事件提供者。更多詳情請見下文。

```js
function myplugin_configure()
{
    return [
        'bootup' => ['myplugin_configure'],
        'vpn' => ['myplugin_configure_vpn:2'],
    ];
}
```

To list all available hooks, you can use `pluginctl` without parameters:

要列出所有可用的鉤子，可以使用不含參數的`pluginctl` ：

```
pluginctl -c
```

Below you will find an incomplete list of the most common used events that are handled at the moment:

以下是目前處理的部分最常用事件清單（不完整）：

| **Event**<br>**活動** | **When**<br>**時間** |
| --- | --- |
| early<br>早期 | Early in bootup process, before normal services are started (things like ssh and the webconfigurator use this spot)<br>在啟動過程的早期階段，在常規服務啟動之前（例如 SSH 和 Web 設定器等服務會在這個階段啟動） |
| bootup<br>啟動 | Bootup, normal legacy service configuration, when not using the `rc(8)` system (for example: unbound, ntpd)<br>啟動，常規傳統服務配置，當不使用`rc(8)`系統時（例如：unbound、ntpd） |
| newwanip<br>紐瓦尼普 | Triggered after configuration of a dynamic interface address, expects a maximum of three positional parameters (`$verbose` and `$interfaces` and `$family`). `$interfaces` is an array all relevant interfaces that require reloading or null for all. $:code:family is the address family type that triggered the event, either `inet` for IPv4 or `inet6` for IPv6.<br>配置動態介面位址後觸發，最多需要三個位置參數（`$verbose`、`$interfaces` 和`$family`）。 `$interfaces` 是一個數組，所有需要重新載入的相關介面或全部為空。 $:code:family 是觸發事件的位址族類型，對於 IPv4 為`inet`，對於 IPv6 為`inet6`。 |
| vpn<br>VPN | Triggered in multiple places that require a reload of the VPN based subsystems, expects a maximum of two parameters (`$verbose` and `$interfaces`). `$interfaces` is an array of all relevant interfaces that require reloading or null for all.<br>在需要重新載入基於VPN的子系統的多個位置觸發，最多需要兩個參數（`$verbose`和`$interfaces`）。 `$interfaces` 是所有需要重新載入的相關介面的數組，或全部為 null。 |

`pluginctl` can also be used to trigger a specific event, such as:

`pluginctl`也可用於觸發特定事件，例如：

```
pluginctl -c monitor
```

## Firewall｜防火牆

To register firewall rules, create a function called `<plugin>_firewall()`, this will pass a plugin object you can use to generate new firewall rules.

要註冊防火牆規則，請建立一個名為`<plugin>_firewall()`的函數，該函數將傳遞一個插件對象，您可以使用該對象產生新的防火牆規則。

A very simplified example of such a rule is included below:

下面給出一個非常簡化的此類規則範例：

```php
function myplugin_firewall(\OPNsense\Firewall\Plugin $fw) {
    $fw->registerFilterRule(500000, array("direction" => "in", "protocol" => "udp", "to_port" => 9999));
}
```

`configctl` can be used to reload the firewall and test your plugin:

`configctl`可用於重新載入防火牆並測試您的外掛程式：

```
configctl filter reload
```

This will generate a rule like (in /tmp/rules.debug):

這將產生類似這樣的規則（位於 /tmp/rules.debug 中）：

```
pass in quick proto udp from {any} to {any} port {9999}
```

## Interface｜介面

To register new (virtual) interfaces, create a function called `<plugin>_interfaces()`, which should return a named array containing the unique interface name as key (enc0 for ipsec for example).

若要註冊新的（虛擬）接口，請建立名為`<plugin>_interfaces()`的函數，該函數應傳回命名數組，其中包含唯一的介面名稱作為鍵（例如，ipsec 的 enc0）。

Every item should contain the following properties:

每個物品都應包含以下屬性：

| **Property**<br>**屬性** | **Syntax**<br>**語法** | **Description**<br>**描述** |
| --- | --- | --- |
| enable<br>啟用 | boolean<br>布林值 | interface enabled, if so it will be saved in the config<br>介面是否已啟用，如果已啟用，則會將配置儲存到配置中 |
| descr<br>描述 | text<br>文字 | User readable description<br>使用者可讀描述 |
| networks<br>網路 | array, \[network, mask\]<br>數組，\[網絡，遮罩\] | list of named arrays containing remote networks<br>包含遠端網路的命名數組列表 |
| type<br>類型 | text<br>文字 | “none”<br>“無” |
| if<br>如果 | text<br>文字 | physical interface (e.g. enc0)<br>實體介面（例如 enc0） |
| virtual<br>虛擬 | boolean<br>布林值 | Virtual interface, true/false<br>虛擬接口，真/假 |

Example:

例子：

```php
function myplugin_interfaces()
{
    global $config;

    $interfaces = array();
    if (isset($config['myplugin']['enable'])) {
        $oic = array("enable" => true);
        $oic['if'] = 'tun0';
        $oic['descr'] = 'myplugin';
        $oic['type'] = "none";
        $oic['virtual'] = true;
        $oic['networks'] = array();
        $interfaces['tun0'] = $oic;
    }

    return $interfaces;
}
```

## Device｜裝置

To register virtual network devices types which can be used verbatim or manually assigned to interfaces, the `<plugin>_devices()` function should return a structure containing such devices and additional definitions.

若要註冊可直接使用或手動指派給介面的虛擬網路設備類型， `<plugin>_devices()`函數應傳回一個包含此類設備和其他定義的結構。

Device registration covers a number of aspects such as interfaces assignment page presentation, external (re)configuration function, automatic configuration of assigned devices, and matching device name pattern amongst others. Available settings are described below:

設備註冊涵蓋多個方面，例如介面分配頁面顯示、外部（重新）配置功能、已分配設備的自動配置以及設備名稱匹配等。可用設定如下：

| **Property**<br>**屬性** | **Syntax**<br>**語法** | **Description**<br>**描述** |
| --- | --- | --- |
| function<br>函數 | text<br>文字 | Calls function of that name with device name as argument<br>呼叫該名稱的函數，並將裝置名稱作為參數 |
| volatile<br>易失性 | boolean<br>布林值 | This interface can disappear so do not attempt boot recovery<br>此介面可能會消失，因此請勿嘗試啟動恢復 |
| configurable<br>可設定 | boolean<br>布林值 | Assigned interface can set IPv4/IPv6 mode if true or missing<br>指派的介面可以設定 IPv4/IPv6 模式（若為真或缺失） |
| pattern<br>模式 | text<br>文字 | Regex to identify device names in bulk<br>用於批次識別設備名稱的正規表示式 |
| type<br>類型 | text<br>文字 | Unique type setting required for assignments page<br>作業頁面需要唯一的類型設定 |
| names<br>名稱 | array \[ see below \]<br>數組 \[見下文\] | List of devices with individual names as associative keys<br>設備列表，每個設備的名稱作為關聯鍵 |
| …descr | text<br>文本 | Descriptive text of device, e.g. for assignments page<br>設備描述文本，例如用於任務頁面 |
| …ifdescr | text<br>文字 | Verbatim description, e.g. as stored in config.xml<br>原文描述，例如儲存在 config.xml 中的描述 |
| …name<br>…名稱 | text<br>文字 | Device name same as array key for convenient access<br>設備名稱與陣列鍵相同，方便存取 |

Example:

例子：

```php
function myplugin_devices()
{
    $devices = [];

    $devices[] = [
        'function' => 'function_name_to_configure',
        'names' => ['dev0' => [
            'descr' => 'descriptive text',
            'ifdescr' => 'verbatim description',
            'name' => 'dev0',
        ]],
        'pattern' => '^dev',
        'volatile' => true,
        'type' => 'bridge',
    ];

    return $devices;
}
```

## Syslog｜系統日誌

To register syslog targets, the `<plugin>_syslog()` function should return a structure containing targets and definitions.

要註冊 syslog 目標， `<plugin>_syslog()`函數應傳回一個包含目標和定義的結構。

```php
function myplugin_syslog()
{
    $logfacilities = array();
    $logfacilities['myplugin'] = array(
        'facility' => array('myplugin'),
    );
    return $logfacilities;
}
```

Note

筆記

As of OPNsense 19.7 Syslog-NG is included in our base system, these files will only be used to identify applications for custom syslog remote targets in System->Settings->Logging / targets.

從 OPNsense 19.7 Syslog- NG開始，這些檔案將僅用於在「系統」->「設定」->「日誌記錄」/「目標」中識別自訂 syslog 遠端目標的應用程式。

To test if a service registration functions properly, just restart the syslog facility:

要測試服務註冊是否正常運作，只需重新啟動系統日誌服務：

```
pluginctl -s syslogd restart
```

Note

筆記

In order to define local targets for Syslog-NG you can just add **local** filters (e.g. by creating `src/opnsense/service/templates/OPNsense/Syslog/local/helloworld.conf`) which will be collected into one large syslog configuration. The readme on [GitHub](https://github.com/opnsense/core/blob/master/src/opnsense/service/templates/OPNsense/Syslog/local/README) describes the process. When running into issues, always make sure to manually restart syslog-ng first (`service syslog-ng restart`), definition errors won’t be written into any log. You will also have to restart the plugin (`pluginctl -s syslog-ng restart`) for the syslog-ng configuration files to be regenerated.

要為 Syslog 定義本地目標NG ，您可以新增**本地**過濾器（例如，建立`src/opnsense/service/templates/OPNsense/Syslog/local/helloworld.conf` ），這些過濾器將被收集到一個大型的 syslog 配置中。 [GitHub 上的 readme 檔案](https://github.com/opnsense/core/blob/master/src/opnsense/service/templates/OPNsense/Syslog/local/README)描述了此過程。遇到問題時，請務必先手動重新啟動 syslog-ng（ `service syslog-ng restart` ），否則定義錯誤將不會寫入任何日誌。您還需要重新啟動插件（ `pluginctl -s syslog-ng restart` ）才能重新產生 syslog-ng 設定檔。

Note

筆記

In case additional source sockets should be used by Syslog-NG you can add files in `/usr/local/opnsense/service/templates/OPNsense/Syslog/sources/` containing definitions. The [001-local.conf](https://github.com/opnsense/core/blob/22.1.7/src/opnsense/service/templates/OPNsense/Syslog/sources/001-local.conf#L5) file contains examples from jailed core services.

如果 Syslog 需要使用額外的來源套接字`/usr/local/opnsense/service/templates/OPNsense/Syslog/sources/` NG新增包含定義的檔案。 [001-local.conf](https://github.com/opnsense/core/blob/22.1.7/src/opnsense/service/templates/OPNsense/Syslog/sources/001-local.conf#L5)檔案包含來自受限核心服務的範例。

## XMLRPC (HA) sync｜XMLRPC ( HA ) 同步

When a configuration section should be exposed to High Availability sync, you can use the xmlrpc plugin hook.

當需要將配置部分暴露給高可用性同步時，可以使用 xmlrpc 插件鉤子。

If a plugin exposes a configuration section to ha sync, it can be enabled separately in the synchronization settings System->High Availability->Settings.

如果外掛程式向 ha sync 公開了設定部分，則可以在同步設定「系統->高可用性->設定」中單獨啟用它。

A simple example to expose the configuration section Myplugin within the OPNsense xml path looks like this:

以下是一個在 OPNsense XML 路徑中公開 Myplugin 配置部分的簡單範例：

```php
function myplugin_xmlrpc_sync()
{
    $result = array();
    $result[] = array(
        'description' => gettext('My Plugin'),
        'section' => 'OPNsense.Myplugin',
        'id' => 'myplugin',
        'services' => 'myplugin', // optional, in case a service with the same name exists
    );
    return $result;
}
```

Note

筆記

If your plugin depends on other components in the system, make sure you enable synchronization for those as well.

如果您的外掛程式依賴系統中的其他元件，請確保也為這些元件啟用同步功能。
