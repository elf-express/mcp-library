Server names are defined using the [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>) directive and determine which [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>) block is used for a given request. See also “[How nginx processes a request](<111 [01.01.03 http] nginx 如何處理請求.md>)”. They may be defined using exact names, wildcard names, or regular expressions:

伺服器名稱使用 `[server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>)指令定義，並決定給定請求使用哪個 `[server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>)程式碼區塊。另請參閱「[nginx 如何處理請求](<111 [01.01.03 http] nginx 如何處理請求.md>) 」。伺服器名稱可以使用精確名稱、通配符名稱或正規表示式定義：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  example.org  www.example.org;
>
>     伺服器名稱 example.org www.example.org;
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  *.example.org;
>
>     伺服器名稱 *.example.org;
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  mail.*;
>
>     伺服器名稱 mail.*;
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  ~^(?<user>.+)\.example\.net$;
>
>     server_name ~^(? <user> .+)\.example\.net$;
>     ...
> }
> ```

The search is performed in the following order of priority and terminates on the first matching variant:

搜尋按以下優先順序執行，並在找到第一個符合項目時終止：

1.  the exact name  
    確切名稱
2.  the longest wildcard name starting with an asterisk, e.g. “`*.example.org`”  
    以星號開頭的最長通配符名稱，例如“ `*.example.org` ”
3.  the longest wildcard name ending with an asterisk, e.g. “`mail.*`”  
    最長的通配符名稱以星號結尾，例如“ `mail.*` ”
4.  the first matching regular expression (in order of appearance in the configuration file)  
    第一個符合的正規表示式（按在設定檔中出現的順序）

#### Wildcard names｜通配符名稱

A wildcard name may contain an asterisk only on the name’s start or end, and only on a dot border. The names “`www.*.example.org`” and “`w*.example.org`” are invalid. However, these names can be specified using regular expressions, for example, “`~^www\..+\.example\.org$`” and “`~^w.*\.example\.org$`”. An asterisk can match several name parts. The name “`*.example.org`” matches not only `www.example.org` but `www.sub.example.org` as well.

通配符名稱只能在名稱的開頭或結尾包含星號，且星號只能位於點狀邊框內。名稱「 `www.*.example.org` 」和「 `w*.example.org` 」無效。但是，可以使用正規表示式指定這些名稱，例如「 `~^www\..+\.example\.org$` 」和「 `~^w.*\.example\.org$` 」。一個星號可以匹配名稱的多個部分。名稱「 `*.example.org` 」不僅符合`www.example.org` ，還符合`www.sub.example.org` 。

A special wildcard name in the form “`.example.org`” can be used to match both the exact name “`example.org`” and the wildcard name “`*.example.org`”.

可以使用特殊通配符名稱“ `.example.org` ”來匹配精確名稱“ `example.org` ”和通配符名稱“ `*.example.org` ”。

#### Regular expressions names｜正規表示式名稱

The regular expressions used by nginx are compatible with those used by the Perl programming language (PCRE). To use a regular expression, the server name must start with the tilde character:

nginx 使用的正規表示式與 Perl 程式語言 ( PCRE ) 使用的正規表示式相容。若要使用正規表示式，伺服器名稱必須以波浪號 (~) 開頭：

> ```
> server_name  ~^www\d+\.example\.net$;
>
> server_name ~^www\d+\.example\.net$;
> ```

otherwise it will be treated as an exact name, or if the expression contains an asterisk, as a wildcard name (and most likely as an invalid one). Do not forget to set “`^`” and “`$`” anchors. They are not required syntactically, but logically. Also note that domain name dots should be escaped with a backslash. A regular expression containing the characters “`{`” and “`}`” should be quoted:

否則，它將被視為精確名稱；如果表達式包含星號，則會被視為通配符名稱（很可能被視為無效名稱）。請務必設定「 `^` 」和「 `$` 」錨點。它們在語法上並非必需，但在邏輯上是必要的。另請注意，網域中的點號應使用反斜線進行轉義。包含字元「 `{` 」和「 `}` 」的正規表示式應使用引號括起來。

> ```
> server_name  "~^(?<name>\w\d{1,3}+)\.example\.net$";
>
> server_name "~^(? <name> \w\d{1,3}+)\.example\.net$";
> ```

otherwise nginx will fail to start and display the error message:

否則 nginx 將無法啟動並顯示錯誤訊息：

> ```
> directive "server_name" is not terminated by ";" in ...
>
> 指令“server_name”未以“;”結尾…
> ```

A named regular expression capture can be used later as a variable:

命名後的正規表示式捕獲結果可以稍後用作變數：

> ```
> server {
>
> 伺服器 {
>     server_name   ~^(www\.)?(?<domain>.+)$;
>
>     server_name ~^(www\.)?(? <domain> .+)$;
> 
>     location / {
>
>     地點 / {
>         root   /sites/$domain;
>
>         根 /sites/$domain;
>     }
> }
> ```

The captures can also be used in positional form:

捕獲也可以以位置形式使用：

> ```
> server {
>
> 伺服器 {
>     server_name   ~^(www\.)?(.+)$;
>
>     server_name ~^(www\.)?(.+)$;
> 
>     location / {
>
>     地點 / {
>         root   /sites/$2;
>
>         根 /sites/$2;
>     }
> }
> ```

However, such usage should be limited to simple cases (like the above), since positional captures are easily overwritten by other regular expressions. See “[Regular expression captures](https://nginx.org/en/docs/regex_captures.html)” for the named capture syntax and for details on how long captured values stay available.

然而，這種用法應僅限於簡單情況（如上例），因為位置捕獲很容易被其他正規表示式覆蓋。有關命名捕獲語法以及捕獲值保留時間的詳細信息，請參閱“[正則表達式捕獲](https://nginx.org/en/docs/regex_captures.html) ”。

#### Miscellaneous names｜雜項名稱

There are some server names that are treated specially.

有些伺服器名稱會被特殊處理。

If it is required to process requests without the “Host”（主持人） header field in a [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>) block which is not the default, an empty name should be specified:

如果需要在 [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>)區塊中處理不包含“Host”（主持人）標頭欄位（非預設值）的請求，則應指定一個空名稱：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  example.org  www.example.org  "";
>
>     server_name example.org www.example.org "";
>     ...
> }
> ```

If no [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>) is defined in a [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>) block then nginx uses the empty name as the server name.

如果 [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>)區塊中沒有定義 [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>) ，則 nginx 使用空名稱作為伺服器名稱。

> nginx versions up to 0.8.48 used the machine’s hostname as the server name in this case.
>
> 在這種情況下，nginx 版本0.8.48使用機器的主機名稱作為伺服器名稱。

If a server name is defined as “`$hostname`” (0.9.4), the machine’s hostname is used.

如果伺服器名稱定義為「 `$hostname` 」（ 0.9.4 ），則使用機器的主機名稱。

If someone makes a request using an IP address instead of a server name, the “Host”（主持人） request header field will contain the IP address and the request can be handled using the IP address as the server name:

如果有人使用IP位址而不是伺服器名稱發出請求，則“Host”（主持人）請求頭字段將包含IP位址，並且可以使用IP位址作為伺服器名稱來處理該請求：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  example.org
>
>     伺服器名稱 example.org
>                  www.example.org
>                  ""
>                  192.168.1.1
>                  ;
>     ...
> }
> ```

In catch-all server examples the strange name “`_`” can be seen:

在通用伺服器範例中，可以看到奇怪的名稱「 `_` 」：

> ```
> server {
>
> 伺服器 {
>     listen       80  default_server;
>
>     監聽 80 埠預設伺服器；
>     server_name  _;
>
>     伺服器名稱_;
>     return       444;
>
>     返回 444；
> }
> ```

There is nothing special about this name, it is just one of a myriad of invalid domain names which never intersect with any real name. Other invalid names like “`--`” and “`!@#`” may equally be used.

這個網域沒什麼特別的，它只是無數無效網域中的一個，這些無效網域永遠不會與任何真實名稱相交。其他無效域名，例如“ `--` ”和“ `!@#` ”，也可以使用。

nginx versions up to 0.6.25 supported the special name “`*`” which was erroneously interpreted to be a catch-all name. It never functioned as a catch-all or wildcard server name. Instead, it supplied the functionality that is now provided by the [server\_name\_in\_redirect](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name_in_redirect>) directive. The special name “`*`” is now deprecated and the [server\_name\_in\_redirect](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name_in_redirect>) directive should be used. Note that there is no way to specify the catch-all name or the default server using the [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>) directive. This is a property of the [listen](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>) directive and not of the [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>) directive. See also “[How nginx processes a request](<111 [01.01.03 http] nginx 如何處理請求.md>)”. It is possible to define servers listening on ports \*:80 and \*:8080, and direct that one will be the default server for port \*:8080, while the other will be the default for port \*:80:

nginx 版本直至0.6.25支援特殊名稱“ `*` ”，該名稱曾被錯誤地解釋為通配符名稱。它從未用作通配符或通用伺服器名稱。相反，它提供的功能現在由 [server_name_in_redirect](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name_in_redirect>)指令提供。特殊名稱「 `*` 」現已棄用，應使用 [server_name_in_redirect](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name_in_redirect>)指令。請注意，無法使用 [server_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>)指令指定通配符名稱或預設伺服器。這是 [listen](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>)指令的屬性，而不是 [server_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>)指令的屬性。另請參閱「[nginx 如何處理請求](<111 [01.01.03 http] nginx 如何處理請求.md>) 」。可定義監聽連接埠 \*:80 和 \*:8080 的伺服器，並指定其中一個伺服器為連接埠 \*:8080 的預設伺服器，而另一個伺服器作為連接埠 \*:80 的預設伺服器：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     listen       8080  default_server;
>
>     監聽 8080 預設伺服器；
>     server_name  example.net;
>
>     伺服器名稱 example.net；
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen       80  default_server;
>
>     監聽 80 埠預設伺服器；
>     listen       8080;
>
>     聽 8080；
>     server_name  example.org;
>
>     伺服器名稱 example.org；
>     ...
> }
> ```

#### Internationalized names｜國際化名稱

Internationalized domain names ([IDNs](https://en.wikipedia.org/wiki/Internationalized_domain_name)) should be specified using an ASCII (Punycode) representation in the [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>) directive:

國際化網域名稱（[IDN](https://en.wikipedia.org/wiki/Internationalized_domain_name) ）應在 [server\_name](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_name>)指令中使用ASCII （Punycode）表示形式指定：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  xn--e1afmkfd.xn--80akhbyknj4f;  # пример.испытание
>
>     server_name xn--e1afmkfd.xn--80akhbyknj4f; # example.test
>     ...
> }
> ```

#### Virtual server selection｜虛擬伺服器選擇

First, a connection is created in a default server context. Then, the server name can be determined in the following request processing stages, each involved in server configuration selection:

首先，在預設伺服器上下文中建立連線。然後，可以在以下請求處理階段確定伺服器名稱，每個階段都涉及伺服器設定選擇：

-   during SSL handshake, in advance, according to [SNI](<042 [01.01.03 http] 配置HTTPS伺服器.md#sni>)  
    在SSL握手期間，提前根據[SNI](<042 [01.01.03 http] 配置HTTPS伺服器.md#sni>)
    
-   after processing the request line  
    處理完請求行後
    
-   after processing the `Host` header field  
    處理完`Host`標頭欄位後
    
-   if the server name was not determined after processing the request line or from the `Host` header field, nginx will use the empty name as the server name.  
    如果在處理請求行或從`Host`標頭欄位中未確定伺服器名稱，nginx 將使用空名稱作為伺服器名稱。
    

At each of these stages, different server configurations can be applied. As such, certain directives should be specified with caution:

在每個階段，都可以套用不同的伺服器配置。因此，某些指令的指定應格外謹慎：

-   in case of the [ssl\_protocols](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_protocols>) directive, the protocol list can be applied from a virtual server configuration only if supported by the underlying library (OpenSSL 1.1.1 or higher, BoringSSL, AWS-LC). For the libraries not listed above, the protocol list is set before the server configuration could be applied according to SNI, thus, protocols should be specified only for a default server;  
    對於 [ssl\_protocols](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_protocols>)指令，協定清單只能在底層函式庫（OpenSSL 1.1.1或更高版本、BoringSSL AWS-LC ）支援的情況下，才能從虛擬伺服器設定中套用。對於未列出的庫，協議列表需要在應用伺服器配置之前根據SNI進行設置，因此，協議應該只針對預設伺服器指定；
-   in case of the [ssl\_session\_cache](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>), [ssl\_session\_tickets](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_tickets>), [ssl\_session\_timeout](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>), and, consequently, [ssl\_early\_data](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_early_data>) directives, SSL sessions are always resumed from the default server context, thus, the directives should be specified only for a default server;  
    對於 [ssl\_session\_cache](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>) 、[ssl\_session\_tickets](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_tickets>) 、[ssl\_session\_timeout](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>)以及對應的 [ssl\_early\_data](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_early_data>) SSL會話始終從預設伺服器上下文恢復，因此，這些指令應該只針對預設伺服器指定；
-   the [client\_header\_buffer\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#client_header_buffer_size>) and [merge\_slashes](<056 [01.01.03 http] 模組 ngx_http_core_module.md#merge_slashes>) directives are involved before reading the request line, thus, such directives use a default server configuration or the server configuration chosen by SNI;  
    [client\_header\_buffer\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#client_header_buffer_size>)和 [merge\_slashes](<056 [01.01.03 http] 模組 ngx_http_core_module.md#merge_slashes>)指令在讀取請求行之前執行，因此，此類指令使用預設伺服器設定或SNI選擇的伺服器設定；
-   in case of the [ignore\_invalid\_headers](<056 [01.01.03 http] 模組 ngx_http_core_module.md#ignore_invalid_headers>), [large\_client\_header\_buffers](<056 [01.01.03 http] 模組 ngx_http_core_module.md#large_client_header_buffers>), and [underscores\_in\_headers](<056 [01.01.03 http] 模組 ngx_http_core_module.md#underscores_in_headers>) directives involved in processing request header fields, it additionally depends whether the server configuration was updated according to the request line or the `Host` header field;  
    對於處理請求標頭欄位時涉及的 [ignore\_invalid\_headers](<056 [01.01.03 http] 模組 ngx_http_core_module.md#ignore_invalid_headers>) 、 [large\_client\_header\_buffers](<056 [01.01.03 http] 模組 ngx_http_core_module.md#large_client_header_buffers>)和 [underscores\_in `Host` (https://nginx.org/en/docs/http/ngx_http_core_module.html#underscores_in_headers)指示
-   an error response will be handled with the [error\_page](<056 [01.01.03 http] 模組 ngx_http_core_module.md#error_page>) directive in the server that currently fulfills the request.  
    錯誤回應將使用目前執行請求的伺服器中的 [error\_page](<056 [01.01.03 http] 模組 ngx_http_core_module.md#error_page>)指令進行處理。

#### Optimization｜最佳化

Exact names, wildcard names starting with an asterisk, and wildcard names ending with an asterisk are stored in three hash tables bound to the listen ports. The sizes of hash tables are optimized at the configuration phase so that a name can be found with the fewest CPU cache misses. The details of setting up hash tables are provided in a separate [document](<040 [01.01 文件] 設定哈希.md>).

精確名稱、以星號開頭的通配符名稱和以星號結尾的通配符名稱儲存在綁定到監聽連接埠的三個雜湊表中。哈希表的大小在配置階段進行最佳化，以便以最少的CPU未命中次數找到名稱。哈希表的設定詳情請參閱(https://nginx.org/en/docs/hash.html)的文件。

The exact names hash table is searched first. If a name is not found, the hash table with wildcard names starting with an asterisk is searched. If the name is not found there, the hash table with wildcard names ending with an asterisk is searched.

首先搜尋精確名稱哈希表。如果找不到該名稱，則搜尋以星號開頭的通配符名稱雜湊表。如果仍然找不到該名稱，則搜尋以星號結尾的通配符名稱雜湊表。

Searching wildcard names hash table is slower than searching exact names hash table because names are searched by domain parts. Note that the special wildcard form “`.example.org`” is stored in a wildcard names hash table and not in an exact names hash table.

搜尋通配符名稱哈希表比搜尋精確名稱哈希表要慢，因為名稱是按網域部分進行搜尋的。請注意，特殊通配符形式「 `.example.org` 」儲存在通配符名稱雜湊表中，而不是精確名稱雜湊表中。

Regular expressions are tested sequentially and therefore are the slowest method and are non-scalable.

正規表示式是按順序測試的，因此是最慢的方法，而且不具備可擴展性。

For these reasons, it is better to use exact names where possible. For example, if the most frequently requested names of a server are `example.org` and `www.example.org`, it is more efficient to define them explicitly:

因此，最好盡可能使用確切的名稱。例如，如果伺服器最常被要求的名稱是`example.org`和`www.example.org` ，那麼明確定義它們會更有效率：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  example.org  www.example.org  *.example.org;
>
>     server_name example.org www.example.org *.example.org;
>     ...
> }
> ```

than to use the simplified form:

而不是使用簡化形式：

> ```
> server {
>
> 伺服器 {
>     listen       80;
>
>     聽 80；
>     server_name  .example.org;
>
>     server_name.example.org;
>     ...
> }
> ```

If a large number of server names are defined, or unusually long server names are defined, tuning the [server\_names\_hash\_max\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_max_size>) and [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>) directives at the *http* level may become necessary. The default value of the [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>) directive may be equal to 32, or 64, or another value, depending on CPU cache line size. If the default value is 32 and server name is defined as “`too.long.server.name.example.org`” then nginx will fail to start and display the error message:

如果定義了大量伺服器名稱，或伺服器名稱異常長，則可能需要在 *http* 層級調整 [server\_names\_hash\_max\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_max_size>)和 [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>)指令。 [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>)指令的預設值可能等於 32、64 或其他值，取決於CPU快取行大小。如果預設值為 32 且伺服器名稱定義為“ `too.long.server.name.example.org` ”，則 nginx 將無法啟動並顯示錯誤訊息：

> ```
> could not build the server_names_hash,
>
> 無法建置 server_names_hash，
> you should increase server_names_hash_bucket_size: 32
>
> 您應該將 server_names_hash_bucket_size 的值增加到 32。
> ```

In this case, the directive value should be increased to the next power of two:

在這種情況下，指令值應該會增加到下一個 2 的冪：

> ```
> http {
>     server_names_hash_bucket_size  64;
>
>     server_names_hash_bucket_size 64;
>     ...
> ```

If a large number of server names are defined, another error message will appear:

如果定義了大量伺服器名稱，則會出現另一個錯誤訊息：

> ```
> could not build the server_names_hash,
>
> 無法建置 server_names_hash，
> you should increase either server_names_hash_max_size: 512
>
> 您應該增加 server_names_hash_max_size: 512
> or server_names_hash_bucket_size: 32
>
> 或 server_names_hash_bucket_size: 32
> ```

In such a case, first try to set [server\_names\_hash\_max\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_max_size>) to a number close to the number of server names. Only if this does not help, or if nginx’s start time is unacceptably long, try to increase [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>).

在這種情況下，首先嘗試將 [server\_names\_hash\_max\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_max_size>)設定為接近伺服器名稱數量的數字。只有當這沒有幫助，或 nginx 的啟動時間過長時，才嘗試增加 [server\_names\_hash\_bucket\_size](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server_names_hash_bucket_size>) 。

If a server is the only server for a listen port, then nginx will not test server names at all (and will not build the hash tables for the listen port). However, there is one exception. If a server name is a regular expression with captures, then nginx has to execute the expression to get the captures.

如果某個伺服器是監聽連接埠的唯一伺服器，那麼 nginx 將完全不會測試伺服器名稱（也不會為該監聽連接埠建立雜湊表）。但是，有一種例外情況。如果伺服器名稱是包含捕獲資訊的正規表示式，那麼 nginx 必須執行該表達式才能取得捕獲資訊。

#### Compatibility｜相容性

-   The special server name “`$hostname`” has been supported since 0.9.4.  
    自0.9.4以來，已支援特殊伺服器名稱「 `$hostname` 」。
-   A default server name value is an empty name “” since 0.8.48.  
    預設伺服器名稱值為空名稱“”，因為0.8.48 。
-   Named regular expression server name captures have been supported since 0.8.25.  
    自0.8.25起，已支援命名正規表示式伺服器名稱擷取。
-   Regular expression server name captures have been supported since 0.7.40.  
    自0.7.40起，已支援正規表示式伺服器名稱擷取。
-   An empty server name “” has been supported since 0.7.12.  
    自0.7.12起，已支援空伺服器名稱「」。
-   A wildcard server name or regular expression has been supported for use as the first server name since 0.6.25.  
    自0.6.25起，支援使用通配符伺服器名稱或正規表示式作為第一個伺服器名稱。
-   Regular expression server names have been supported since 0.6.7.  
    自0.6.7以來，一直支援正規表示式伺服器名稱。
-   Wildcard form `example.*` has been supported since 0.6.0.  
    自0.6.0起，已支援通配符形式`example.*` 。
-   The special form `.example.org` has been supported since 0.3.18.  
    自0.3.18起，已支持特殊形式`.example.org` 。
-   Wildcard form `*.example.org` has been supported since 0.1.13.  
    自0.1.13起，已支援通配符形式`*.example.org` 。
