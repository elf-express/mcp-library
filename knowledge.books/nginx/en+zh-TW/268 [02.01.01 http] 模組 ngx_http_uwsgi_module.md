Модуль `ngx_http_uwsgi_module` позволяет передавать запросы uwsgi-серверу.

`ngx_http_uwsgi_module`模組允許您向 uwsgi 伺服器傳遞請求。

#### Пример конфигурации｜配置範例

> ```
> location / {
>
> 地點/{
>     include    uwsgi_params;
>
>     包含 uwsgi_params；
>     uwsgi_pass localhost:9000;
> }
> ```

Задаёт локальный IP-адрес с необязательным портом (1.11.2), который будет использоваться в исходящих соединениях с uwsgi-сервером. В значении параметра допустимо использование переменных (1.3.12). Специальное значение `off` (1.3.12) отменяет действие унаследованной с предыдущего уровня конфигурации директивы `uwsgi_bind`, позволяя системе самостоятельно выбирать локальный IP-адрес и порт.

指定用於與 uwsgi 伺服器建立出站連接的本地位址（ IP ，可選連接埠1.11.2 ）。此參數值允許使用變數（ 1.3.12 ）。特殊值`off` （ 1.3.12 ）會覆寫從上一配置等級繼承的指令`uwsgi_bind` ，允許系統獨立選擇本地位址和連接埠IP ）。

Параметр `transparent` (1.11.0) позволяет задать нелокальный IP-aдрес, который будет использоваться в исходящих соединениях с uwsgi-сервером, например, реальный IP-адрес клиента:

`transparent` ( 1.11.0 ) 參數允許您指定一個非本地IP位址，該位址將用於與 uwsgi 伺服器建立出站連接，例如，客戶端的真實IP位址：

> ```
> uwsgi_bind $remote_addr transparent;
> ```

Для работы параметра обычно требуется запустить рабочие процессы nginx с привилегиями [суперпользователя](<285 [02.01 文件] 基本功能.md#user>). В Linux этого не требуется (1.13.8), так как если указан параметр `transparent`, то рабочие процессы наследуют capability `CAP_NET_RAW` из главного процесса. Также необходимо настроить таблицу маршрутизации ядра для перехвата сетевого трафика с uwsgi-сервера.

此參數通常要求以 [superuser 權限執行 nginx 工作進程](<285 [02.01 文件] 基本功能.md#user>) )。在 Linux 系統上則無需此操作 ( 1.13.8 )，因為如果指定了`transparent`參數，工作進程將從主進程繼承`CAP_NET_RAW`權限。此外，您還需要設定核心路由表以攔截來自 uwsgi 伺服器的網路流量。

Задаёт `*размер*` буфера, в который будет читаться первая часть ответа, получаемого от uwsgi-сервера. В этой части ответа находится, как правило, небольшой заголовок ответа; если его размер больше заданного, то такой ответ считается [неверным](#invalid_header). По умолчанию размер одного буфера равен размеру страницы памяти. В зависимости от платформы это или 4K, или 8K, однако его можно сделать меньше.

指定用於讀取從 uwsgi 伺服器接收到的回應第一部分的緩衝區`*размер*` 。響應的這一部分通常包含一個較小的響應頭；如果其大小大於指定值，則該響應被視為 [不正確](#invalid_header) 。預設情況下，一個緩衝區的大小等於一個記憶體頁的大小。根據平台的不同，該大小為 4K 或 8K，但可以減少。

Разрешает или запрещает использовать буферизацию ответов uwsgi-сервера.

啟用或停用 uwsgi 伺服器回應緩衝。

Если буферизация включена, то nginx принимает ответ uwsgi-сервера как можно быстрее, сохраняя его в буферы, заданные директивами [uwsgi\_buffer\_size](#uwsgi_buffer_size) и [uwsgi\_buffers](#uwsgi_buffers). Если ответ не вмещается целиком в память, то его часть может быть записана на диск во [временный файл](#uwsgi_temp_path). Запись во временные файлы контролируется директивами [uwsgi\_max\_temp\_file\_size](#uwsgi_max_temp_file_size) и [uwsgi\_temp\_file\_write\_size](#uwsgi_temp_file_write_size).

如果啟用緩衝，nginx 會盡快接收 UWSGI 伺服器的回應，並將其儲存在 [uwsgi\_buffer\_size](#uwsgi_buffer_size)和 [uwsgi\_buffers](#uwsgi_buffers)指令指定的緩衝區中。如果整個回應無法放入內存，則可以將其一部分寫入磁碟上的 [temporary file](#uwsgi_temp_path)暫存檔案。寫入暫存檔案由 [uwsgi\_max\_temp\_file\_size](#uwsgi_max_temp_file_size)和 [uwsgi\_temp\_file\_write\_size](#uwsgi_temp_file_write_size)指令控制。

Если буферизация выключена, то ответ синхронно передаётся клиенту сразу же по мере его поступления. nginx не пытается считать весь ответ uwsgi-сервера. Максимальный размер данных, который nginx может принять от сервера за один раз, задаётся директивой [uwsgi\_buffer\_size](#uwsgi_buffer_size).

如果停用緩衝，回應會在到達後立即同步傳輸給用戶端。 NGINX 不會嘗試讀取整個 UWSGI 伺服器回應。 NGINX 一次可以從伺服器接收的最大資料大小由 [uwsgi\_buffer\_size](#uwsgi_buffer_size)指令指定。

Буферизация может быть также включена или выключена путём передачи значения “`yes`” или “`no`” в поле “X-Accel-Buffering”（X-加速緩衝） заголовка ответа. Эту возможность можно запретить с помощью директивы [uwsgi\_ignore\_headers](#uwsgi_ignore_headers).

也可以透過在“X-Accel-Buffering”（X-加速緩衝）響應頭字段中傳遞值「 `yes` 」或「 `no` 」來啟用或停用緩衝。可以使用 [uwsgi\_ignore\_headers](#uwsgi_ignore_headers)指令停用此功能。

快取的回應首先寫入一個臨時文件，然後對其進行重新命名。從版本0.8.9臨時檔案和快取可以位於不同的檔案系統上。但是要注意的是，在這種情況下，檔案不是在一個檔案系統內進行簡單的重新命名操作，而是從一個檔案系統複製到另一個檔案系統。因此，最好將快取與包含暫存檔案的目錄放在同一個檔案系統上。暫存檔案所在的目錄由`use_temp_path` （ 1.7.10 ）參數決定。如果未指定此參數或將其設為“ `on` ”，則將使用[uwsgi\_temp\_path](#uwsgi_temp_path)指令為給定位置指定的目錄。如果將此參數設為“ `off` ”，則暫存檔案將直接位於快取目錄中。

Кроме того, все активные ключи и информация о данных хранятся в зоне разделяемой памяти, `*имя*` и `*размер*` которой задаются параметром `keys_zone`. Зоны размером в 1 мегабайт достаточно для хранения около 8 тысяч ключей.

此外，所有活動金鑰和資料資訊都儲存在共享記憶體區域`*имя*`和`*размер*`中，該區域由`keys_zone`參數定義。 1兆位元組的區域足以儲存約8000個密鑰。

> Как часть [коммерческой подписки](https://www.f5.com/products/nginx) в зоне разделяемой памяти также хранится расширенная [информация](https://nginx.org/ru/docs/http/ngx_http_api_module.html#http_caches_) о кэше, поэтому для хранения аналогичного количества ключей необходимо указывать больший размер зоны. Например зоны размером в 1 мегабайт достаточно для хранения около 4 тысяч ключей.
>
> 作為[商業訂閱](https://www.f5.com/products/nginx)共享記憶體區域也會儲存關於快取的擴充[資訊](https://nginx.org/ru/docs/http/ngx_http_api_module.html#http_caches_) ，因此，要儲存相同數量的鍵，需要更大的區域大小。例如，1兆位元組的區域足以儲存大約4000個鍵。

Если к данным кэша не обращаются в течение времени, заданного параметром `inactive`, то данные удаляются, независимо от их свежести. По умолчанию `inactive` равен 10 минутам.

如果快取資料在`inactive`指定的時間內未被訪問，則無論其新鮮度如何，資料都將被刪除。預設情況下， `inactive`為 10 分鐘。

Специальный процесс “cache manager” следит за максимальным размером кэша, заданным параметром `max_size`, а также за минимальным объёмом свободного места на файловой системе с кэшем, заданным параметром `min_free` (1.19.1). При превышении максимального размера кэша или недостаточном объёме свободного места процесс удаляет наименее востребованные данные. Удаление данных происходит итерациями, настраиваемыми параметрами (1.11.5) `manager_files`, `manager_threshold` и `manager_sleep`. За одну итерацию загружается не более `manager_files` элементов (по умолчанию 100). Время работы одной итерации ограничено параметром `manager_threshold` (по умолчанию 200 миллисекунд). Между итерациями делается пауза на время, заданное параметром `manager_sleep` (по умолчанию 50 миллисекунд).

一個特殊的「快取管理器」程序會監控由參數`max_size`指定的最大快取大小，以及由參數`min_free` （ 1.19.1 ）指定的包含快取的檔案系統上的最小可用空間。如果超過最大快取大小或可用空間不足，則該進程會刪除不常用的資料。資料刪除操作以迭代方式進行，迭代次數由參數1.11.5 、 `manager_files`, `manager_threshold`和`manager_sleep`配置。每次迭代最多載入`manager_files`個元素（預設為100個）。單次迭代的持續時間由參數`manager_threshold`限制（預設為200毫秒）。在兩次迭代之間，會暫停一段時間，暫停時間由參數`manager_sleep`指定（預設為50毫秒）。

Через минуту после старта активируется специальный процесс “cache loader”, который загружает в зону кэша информацию о ранее закэшированных данных, хранящихся на файловой системе. Загрузка также происходит итерациями. За одну итерацию загружается не более `loader_files` элементов (по умолчанию 100). Кроме того, время работы одной итерации ограничено параметром `loader_threshold` (по умолчанию 200 миллисекунд). Между итерациями делается пауза на время, заданное параметром `loader_sleep` (по умолчанию 50 миллисекунд).

啟動一分鐘後，一個名為「快取載入器」的特殊進程會被激活，將檔案系統中先前快取的資料資訊載入到快取區域。載入過程以迭代方式進行，每次迭代最多載入`loader_files`個元素（預設值為100）。此外，單次迭代的運行時間受`loader_threshold`參數的限制（預設值為200毫秒）。迭代之間會暫停一段時間，該時間由`loader_sleep`參數指定（預設值為50毫秒）。

決定在哪些情況下請求會傳遞給下一個伺服器：

`error`

произошла ошибка соединения с сервером, передачи ему запроса или чтения заголовка ответа сервера;

連接伺服器、向伺服器發送請求或讀取伺服器回應頭時發生錯誤；

`timeout`

произошёл таймаут во время соединения с сервером, передачи ему запроса или чтения заголовка ответа сервера;

連接伺服器、向伺服器發送請求或讀取伺服器回應頭時發生逾時；

`http_503`

сервер вернул ответ с кодом 503;

伺服器回傳了代碼為 503 的回應；

`http_403`

сервер вернул ответ с кодом 403;

`http_404`

сервер вернул ответ с кодом 404;

伺服器回傳了代碼為 404 的回應；

伺服器回傳了代碼為 429 的回應（ 1.11.13 ）；

обычно запросы с [неидемпотентным](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2) методом (`POST`, `LOCK`, `PATCH`) не передаются на другой сервер, если запрос серверу группы уже был отправлен (1.9.13); включение параметра явно разрешает повторять подобные запросы;

Необходимо понимать, что передача запроса следующему серверу возможна только при условии, что клиенту ещё ничего не передавалось. То есть, если ошибка или таймаут возникли в середине передачи ответа, то исправить это уже невозможно.

需要注意的是，只有在尚未向客戶端發送任何資料的情況下，才能將請求轉發到下一個伺服器。這意味著，如果在發送回應的過程中發生錯誤或逾時，則無法修復。

Случаи `http_500`, `http_503` и `http_429` считаются неудачными попытками, только если они указаны в директиве. Случаи `http_403` и `http_404` никогда не считаются неудачными попытками.

Разрешает сохранение на диск файлов. Параметр `on` сохраняет файлы в соответствии с путями, указанными в директивах [alias](<221 [02.01.01 http] 模組 ngx_http_core_module.md#alias>) или [root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>). Параметр `off` запрещает сохранение файлов. Кроме того, имя файла можно задать явно с помощью строки с переменными:

啟用檔案儲存到磁碟功能。參數`on`根據 [alias](<221 [02.01.01 http] 模組 ngx_http_core_module.md#alias>)或 [root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>)指令中指定的路徑儲存檔案。參數`off`禁用檔案保存。此外，也可以使用變數字串明確指定檔案名稱：

> ```
> uwsgi_store /data/www$original_uri;
> ```

Время изменения файлов выставляется согласно полученному полю “Last-Modified”（最後修改日期） в заголовке ответа. Ответ сначала записывается во временный файл, а потом этот файл переименовывается. Начиная с версии 0.8.9 временный файл и постоянное место хранения ответа могут располагаться на разных файловых системах. Однако нужно учитывать, что в этом случае вместо дешёвой операции переименовывания в пределах одной файловой системы файл копируется с одной файловой системы на другую. Поэтому лучше, если сохраняемые файлы будут находиться на той же файловой системе, что и каталог с временными файлами, задаваемый директивой [uwsgi\_temp\_path](#uwsgi_temp_path) для данного location.

文件修改時間根據回應頭中接收到的“Last-Modified”（最後修改日期）字段設定。回應首先寫入臨時文件，然後重新命名該文件。從版本0.8.9開始，回應的暫存檔案和永久儲存位置可以位於不同的檔案系統上。但是需要注意的是，在這種情況下，檔案不是在同一個檔案系統內進行簡單的重新命名操作，而是從一個檔案系統複製到另一個檔案系統。因此，最好將已儲存的檔案與 [uwsgi\_temp\_path](#uwsgi_temp_path)指令指定的暫存檔案目錄位於相同檔案系統上。
