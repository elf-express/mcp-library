Модуль `ngx_http_grpc_module` позволяет передавать запросы gRPC-серверу (1.13.10). Для работы этого модуля необходим модуль [ngx\_http\_v2\_module](<269 [02.01.01 http] 模組 ngx_http_v2_module.md>).

`ngx_http_grpc_module`模組可讓您向 gRPC 伺服器 ( 1.13.10 ) 傳遞請求。此模組需要 [ngx\_http\_v2\_module](<269 [02.01.01 http] 模組 ngx_http_v2_module.md>)模組。

#### Пример конфигурации｜配置範例

> ```
> server {
>
> 伺服器 {
>     listen 9000;
>
>     聽 9000；
> 
>     http2 on;
>
>     http2 已開啟；
> 
>     location / {
>
>     地點 / {
>         grpc_pass 127.0.0.1:9000;
>
>         grpc_pass 127.0.0.1:9000 ;
>     }
> }
> ```

Задаёт условия, при которых доступ к gRPC-серверу будет разрешён или [запрещён](#denied). Если все значения строковых параметров непустые и не равны “0”, то доступ разрешён. Задаёт локальный IP-адрес с необязательным портом, который будет использоваться в исходящих соединениях с gRPC-сервером. В значении параметра допустимо использование переменных. Специальное значение `off` отменяет действие унаследованной с предыдущего уровня конфигурации директивы `grpc_bind`, позволяя системе самостоятельно выбирать локальный IP-адрес и порт.

指定用於與 gRPC 伺服器建立出站連線的本機位址IP和選用連接埠。此參數的值允許使用變數。特殊值`off`會覆寫從上一配置層級繼承的指令`grpc_bind` ，允許系統獨立選擇本地位址IP和連接埠。

Параметр `transparent` позволяет задать нелокальный IP-aдрес, который будет использоваться в исходящих соединениях с gRPC-сервером, например, реальный IP-адрес клиента:

`transparent`參數可讓您指定一個非本地IP位址，該位址將用於與 gRPC 伺服器建立出站連接，例如客戶端的真實IP位址：

> ```
> grpc_bind $remote_addr transparent;
> ```

Для работы параметра обычно требуется запустить рабочие процессы nginx с привилегиями [суперпользователя](<285 [02.01 文件] 基本功能.md#user>). В Linux этого не требуется, так как если указан параметр `transparent`, то рабочие процессы наследуют capability `CAP_NET_RAW` из главного процесса. Также необходимо настроить таблицу маршрутизации ядра для перехвата сетевого трафика с gRPC-сервера.

此參數通常需要以超級使用者權限 ( (https://nginx.org/ru/docs/ngx_core_module.html#user) ) 執行 nginx 工作進程。在 Linux 系統上，則無需這樣做，因為如果指定了`transparent`參數，工作進程將從主進程繼承`CAP_NET_RAW`權限。此外，您還需要設定核心路由表以攔截來自 gRPC 伺服器的網路流量。

Задаёт `*размер*` буфера, в который будет читаться ответ, получаемый от gRPC-сервера. В первой части ответа находится, как правило, небольшой заголовок; если его размер больше заданного, то такой ответ считается [неверным](#invalid_header). Ответ синхронно передаётся клиенту сразу же по мере его поступления. По умолчанию размер одного буфера равен размеру страницы памяти. В зависимости от платформы это или 4K, или 8K, однако его можно сделать меньше.

指定一個緩衝區`*размер*` ，用於讀取從 gRPC 伺服器收到的回應。回應的第一部分通常包含一個較小的頭部；如果其大小大於指定值，則該回應被視為無效（ (https://nginx.org/ru/docs/http/ngx_http_grpc_module.html#invalid_header) ）。回應到達後會立即同步發送給客戶端。預設情況下，一個緩衝區的大小等於一個記憶體頁的大小。根據平台的不同，該大小為 4K 或 8K，但可以減少。

По умолчанию nginx не передаёт клиенту поля заголовка “Date”（日期）, “Server”（伺服器） и “X-Accel-...” из ответа gRPC-сервера. Директива `grpc_hide_header` задаёт дополнительные поля, которые не будут передаваться. Если же передачу полей нужно разрешить, можно воспользоваться директивой [grpc\_pass\_header](#grpc_pass_header).

預設情況下，nginx 不會將 gRPC 伺服器回應中的 “Date”（日期）, “Server”（伺服器） 和 “X-Accel-...” 標頭欄位傳遞給客戶端。 `grpc_hide_header`指令指定不會傳送的附加欄位。如果需要允許欄位傳輸，可以使用 [grpc\_pass\_header](#grpc_pass_header) 指令。

Запрещает обработку некоторых полей заголовка из ответа gRPC-сервера. В директиве можно указать поля “X-Accel-Redirect”（X-加速-重定向） и “X-Accel-Charset”（X-Accel-字元集）.

阻止處理 gRPC 伺服器回應中的某些標頭欄位。可以在此指令中指定“X-Accel-Redirect”（X-加速-重定向）和“X-Accel-Charset”（X-Accel-字元集）欄位。

Если не запрещено, обработка этих полей заголовка заключается в следующем:

除非法律禁止，否則這些標頭欄位的處理方式如下：

-   “X-Accel-Redirect”（X-加速-重定向） производит [внутреннее перенаправление](<221 [02.01.01 http] 模組 ngx_http_core_module.md#internal>) на указанный URI;  
    “X-Accel-Redirect”（X-加速-重定向）執行 [內部重定向](<221 [02.01.01 http] 模組 ngx_http_core_module.md#internal>)到指定的URI ;
-   “X-Accel-Charset”（X-Accel-字元集） задаёт желаемую [кодировку](<220 [02.01.01 http] 模組 ngx_http_charset_module.md#charset>) ответа.  
    “X-Accel-Charset”（X-Accel-字元集）指定回應的所需 [編碼](<220 [02.01.01 http] 模組 ngx_http_charset_module.md#charset>) 。

決定在哪些情況下請求會傳遞給下一個伺服器：

`error`

произошла ошибка соединения с сервером, передачи ему запроса или чтения заголовка ответа сервера;

`timeout`

произошёл таймаут во время соединения с сервером, передачи ему запроса или чтения заголовка ответа сервера;

伺服器回傳了代碼為 429 的回應；

`non_idempotent`

обычно запросы с [неидемпотентным](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2) методом (`POST`, `LOCK`, `PATCH`) не передаются на другой сервер, если запрос серверу группы уже был отправлен; включение параметра явно разрешает повторять подобные запросы;

通常情況下，如果請求已傳送到群組伺服器，則使用 [非冪等](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2)方法 ( `POST`, `LOCK`, `PATCH` ) 的請求不會傳遞給另一個伺服器；明確啟用此參數允許重複此類請求；

`off`

запрещает передачу запроса следующему серверу.

阻止請求傳遞給下一個伺服器。

Необходимо понимать, что передача запроса следующему серверу возможна только при условии, что клиенту ещё ничего не передавалось. То есть, если ошибка или таймаут возникли в середине передачи ответа, то исправить это уже невозможно.

需要注意的是，只有在尚未向客戶端發送任何資料的情況下，才能將請求轉發到下一個伺服器。這意味著，如果在發送回應的過程中發生錯誤或逾時，則無法修復。

Директива также определяет, что считается [неудачной попыткой](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#max_fails>) работы с сервером. Случаи `error`, `timeout`, `denied` и `invalid_header` всегда считаются неудачными попытками, даже если они не указаны в директиве. Случаи `http_500`, `http_502`, `http_503`, `http_504` и `http_429` считаются неудачными попытками, только если они указаны в директиве. Случаи `http_403` и `http_404` никогда не считаются неудачными попытками.

該指令也定義了什麼被視為操作伺服器的[失敗嘗試](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#max_fails>)。情況 `error`, `timeout`, `denied` 和 `invalid_header` 總是被視為失敗的嘗試，即使它們未在指令中指定。僅當指令中指定時，情況`http_500`, `http_502`, `http_503`, `http_504`和`http_429`才被視為失敗。案例 `http_403` 和 `http_404` 永遠不會被視為失敗。
