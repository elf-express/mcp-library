Чтобы настроить HTTPS-сервер, необходимо включить параметр `ssl` на [слушающих сокетах](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>) в блоке [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>), а также указать местоположение файлов с [сертификатом сервера](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate>) и [секретным ключом](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate_key>):

要設定 HTTPS-server，需要啟用此參數 `ssl` 在[監聽套接字上](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>) 在 [伺服器 區塊中](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>)，並以 [伺服器憑證 指示檔案的位置](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate>) 和[密鑰](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate_key>):

> ```
> server {
>
> 伺服器 {
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.crt;
>
>     ssl_證書www.example.com.crt；
>     ssl_certificate_key www.example.com.key;
>
>     ssl_certificate_key www.example.com.key；
>     ssl_protocols       TLSv1.2 TLSv1.3;
>
>     ssl_protocols TLSv1.2 TLSv1.3;
>     ssl_ciphers         HIGH:!aNULL:!MD5;
>
>     ssl_ciphers HIGH:!aNULL:!MD5;
>     ...
> }
> ```

Сертификат сервера является публичным. Он посылается каждому клиенту, соединяющемуся с сервером. Секретный ключ следует хранить в файле с ограниченным доступом (права доступа должны позволять главному процессу nginx читать этот файл). Секретный ключ можно также хранить в одном файле с сертификатом:

伺服器憑證是公開的。它被發送到連接到伺服器的每個客戶端。密鑰應儲存在存取受限的檔案中（權限應允許主 nginx 進程讀取此檔案）。私鑰也可以與憑證儲存在同一文件中：

> ```
>     ssl_certificate     www.example.com.cert;
>
>     ssl_certificate www.example.com.cert；
>     ssl_certificate_key www.example.com.cert;
>
>     ssl_certificate_key www.example.com.cert；
> ```

при этом права доступа к файлу следует также ограничить. Несмотря на то, что и сертификат, и ключ хранятся в одном файле, клиенту посылается только сертификат.

但是，文件存取權限也應該受到限制。儘管憑證和金鑰都儲存在同一個文件中，但只有憑證會傳送到客戶端。

С помощью директив [ssl\_protocols](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_protocols>) и [ssl\_ciphers](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_ciphers>) можно ограничить соединения использованием только “сильных” версий и шифров SSL/TLS. По умолчанию nginx использует “`ssl_protocols TLSv1.2 TLSv1.3`” и “`ssl_ciphers HIGH:!aNULL:!MD5`”, поэтому их явная настройка в общем случае не требуется. Следует отметить, что значения по умолчанию этих директив несколько раз [менялись](#compatibility).

使用 [ssl\_protocols](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_protocols>) 和 [ssl\_ciphers](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_ciphers>) 指令，您可以限制連線僅使用「強」版本和 SSL/TLS 密碼。預設情況下，nginx 使用“`ssl_protocols TLSv1.2 TLSv1.3`”和“`ssl_ciphers HIGH:!aNULL:!MD5`”，因此一般不需要明確配置它們。需要注意的是，這些指令的預設值已經[更改](#compatibility)多次。

#### Оптимизация HTTPS-сервера｜HTTPS伺服器優化

SSL-операции потребляют дополнительные ресурсы процессора. На мультипроцессорных системах следует запускать несколько [рабочих процессов](<285 [02.01 文件] 基本功能.md#worker_processes>), не меньше числа доступных процессорных ядер. Наиболее ресурсоёмкой для процессора является операция SSL handshake, в рамках которой формируются криптографические параметры сессии. Существует два способа уменьшения числа этих операций, производимых для каждого клиента: использование постоянных ([keepalive](<221 [02.01.01 http] 模組 ngx_http_core_module.md#keepalive_timeout>)) соединений, позволяющих в рамках одного соединения обрабатывать сразу несколько запросов, и повторное использование параметров SSL-сессии для предотвращения необходимости выполнения SSL handshake для параллельных и последующих соединений. Сессии хранятся в кэше SSL-сессий, разделяемом между рабочими процессами и настраиваемом директивой [ssl\_session\_cache](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>). В 1 мегабайт кэша помещается около 4000 сессий. Таймаут кэша по умолчанию равен 5 минутам. Он может быть увеличен с помощью директивы [ssl\_session\_timeout](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>). Вот пример конфигурации, оптимизированной под многоядерную систему с 10-мегабайтным разделяемым кэшем сессий:

SSL- 操作消耗額外的處理器資源。在多處理器系統上，您應該執行多個[工作進程](<285 [02.01 文件] 基本功能.md#worker_processes>)，不少於可用處理器核心的數量。處理器最消耗資源的操作是 SSL 握手，其中形成會話的加密參數。有兩種方法可以減少為每個客戶端執行的這些操作的數量：使用持久性（[keepalive](<221 [02.01.01 http] 模組 ngx_http_core_module.md#keepalive_timeout>)) 允許在一個連接內處理多個請求的連接，以及參數的重複使用 SSL- 會話以防止需要執行 SSL 並行和後續連接的握手。會話儲存在快取中 SSL-工作進程之間共用的會話並由 [ssl\_session\_cache 指令配置](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>)。 1 MB 快取可容納約 4000 個會話。預設快取逾時為 5 分鐘。可以使用 [ssl\_session\_timeout 指令增加它](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>)。以下是針對具有 10 MB 共享會話快取的多核心系統進行最佳化的範例配置：

> ```
> worker_processes auto;
>
> 自動worker_processes；
> 
> http {
>     ssl_session_cache   shared:SSL:10m;
>
>     ssl_session_cache 共享：SSL：10m；
>     ssl_session_timeout 10m;
>
>     ssl_session_timeout 10m；
> 
>     server {
>
>     伺服器 {
>         listen              443 ssl;
>
>         監聽 443 ssl；
>         server_name         www.example.com;
>
>         伺服器名稱 www.example.com；
>         keepalive_timeout   70;
>
>         keepalive_timeout 70；
> 
>         ssl_certificate     www.example.com.crt;
>
>         ssl_證書www.example.com.crt；
>         ssl_certificate_key www.example.com.key;
>
>         ssl_certificate_key www.example.com.key；
>         ssl_protocols       TLSv1.2 TLSv1.3;
>
>         ssl_protocols TLSv1.2 TLSv1.3;
>         ssl_ciphers         HIGH:!aNULL:!MD5;
>
>         ssl_ciphers HIGH:!aNULL:!MD5;
>         ...
> ```

#### Цепочки SSL-сертификатов｜SSL-憑證鏈

Некоторые браузеры могут выдавать предупреждение о сертификате, подписанном общеизвестным центром сертификации, в то время как другие браузеры без проблем принимают этот же сертификат. Так происходит потому, что центр, выдавший сертификат, подписал его промежуточным сертификатом, которого нет в базе данных сертификатов общеизвестных доверенных центров сертификации, распространяемой вместе с браузером. В подобном случае центр сертификации предоставляет “связку” сертификатов, которую следует присоединить к сертификату сервера. Сертификат сервера следует разместить перед связкой сертификатов в скомбинированном файле:

某些瀏覽器可能會發出有關由知名證書頒發機構簽署的證書的警告，而其他瀏覽器則接受相同的證書，沒有任何問題。發生這種情況是因為頒發證書的機構使用中間證書簽署了該證書，而該中間證書不在隨瀏覽器分發的眾所周知的受信任證書頒發機構的資料庫中。在這種情況下，CA 提供必須附加到伺服器憑證的憑證「捆綁包」。伺服器證書應放置在組合文件中的證書包之前：

> ```bash
>
> 『`bash
> $ cat www.example.com.crt bundle.crt > www.example.com.chained.crt
> ```

Полученный файл следует указать в директиве [ssl\_certificate](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate>):

產生的檔案應在 [ssl\_certificate](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl_certificate>) 指令中指定：

> ```
> server {
>
> 伺服器 {
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.chained.crt;
>
>     ssl_certificate www.example.com.chained.crt；
>     ssl_certificate_key www.example.com.key;
>
>     ssl_certificate_key www.example.com.key；
>     ...
> }
> ```

Если сертификат сервера и связка сертификатов были соединены в неправильном порядке, nginx откажется запускаться и выдаст сообщение об ошибке:

如果伺服器憑證和憑證包連線順序錯誤，nginx 將拒絕啟動並顯示錯誤訊息：

> ```
> SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") failed
>
> SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") 失敗
>    (SSL: error:05800074:x509 certificate routines::key values mismatch)
>
>    （SSL：錯誤：05800074：x509 憑證程式::金鑰值不符）
> ```

поскольку nginx попытается использовать секретный ключ с первым сертификатом из связки вместо сертификата сервера.

因為 nginx 會嘗試使用捆綁包中第一個憑證的私密金鑰而不是伺服器憑證。

Браузеры обычно сохраняют полученные промежуточные сертификаты, подписанные доверенными центрами сертификации, поэтому активно используемые браузеры уже могут иметь требуемые промежуточные сертификаты и не выдать предупреждение о сертификате, присланном без связанной с ним цепочки сертификатов. Убедиться в том, что сервер присылает полную цепочку сертификатов, можно при помощи утилиты командной строки `openssl`, например:

瀏覽器通常儲存它們收到的由受信任的 CA 簽署的中間證書，因此經常使用的瀏覽器可能已經擁有所需的中間證書，並且不會發出有關在沒有與其關聯的證書鏈的情況下發送的證書的警告。您可以使用命令列實用程式`openssl`確保伺服器傳送完整的憑證鏈，例如：

> ```bash
>

> ...

#### Единый HTTP/HTTPS сервер｜單一HTTP/HTTPS伺服器

Можно настроить единый сервер, который обслуживает как HTTP-, так и HTTPS-запросы:

您可以設定一個服務於 HTTP 和 HTTPS 請求的伺服器：

> ```
> server {
>
> 伺服器 {
>     listen              80;
>
>     聽80；
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.crt;
>
>     ssl_證書www.example.com.crt；
>     ssl_certificate_key www.example.com.key;
>
>     ssl_certificate_key www.example.com.key；
>     ...
> }
> ```

> До версии 0.7.14 SSL нельзя было включить выборочно для отдельных слущающих сокетов, как показано выше. SSL можно было включить только для всего сервера целиком, с помощью директивы [ssl](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl>), что не позволяло настроить единый HTTP/HTTPS сервер. Для решения этой задачи был добавлен параметр `ssl` директивы [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>). Поэтому использование директивы [ssl](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl>) в современных версиях не рекомендуется; директива упразднена в 1.25.1.
>
> 在版本0.7.14 SSL之前，不可能選擇性地為單一監聽套接字啟用此功能，如上所示。 SSL 只能使用 [ssl](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl>) 指令為整個伺服器啟用，該指令不允許設定單一 HTTP/HTTPS 伺服器。為了解決這個問題，新增了[listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>)指令的`ssl`參數。因此，不建議在現代版本中使用 [ssl](<260 [02.01.01 http] 模組 ngx_http_ssl_module.md#ssl>) 指令； 1.25.1 中廢除了指令。

#### Выбор HTTPS-сервера по имени｜依名稱選擇 HTTPS 伺服器

Типичная проблема возникает при настройке двух и более серверов HTTPS, слушающих на одном и том же IP-адресе:

當設定兩個或更多HTTPS伺服器偵聽相同IP位址時，會出現一個典型問題：

> ```
> server {
>
> 伺服器 {
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate www.example.com.crt;
>
>     ssl_證書www.example.com.crt；
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.org;
>
>     伺服器名稱www.example.org；
>     ssl_certificate www.example.org.crt;
>
>     ssl_憑證www.example.org.crt；
>     ...
> }
> ```

В такой конфигурации браузер получит сертификат сервера по умолчанию, т.е. `www.example.com`, независимо от запрашиваемого имени сервера. Это связано с поведением протокола SSL. SSL-соединение устанавливается до того, как браузер посылает HTTP-запрос, и nginx не знает имени запрашиваемого сервера. Следовательно, он лишь может предложить сертификат сервера по умолчанию.

在此配置中，無論請求的伺服器名稱為何，瀏覽器都會收到預設的伺服器證書，即`www.example.com`。這是由於SSL. SSL協定的行為造成的－連線是在瀏覽器發送HTTP請求之前建立的，而nginx不知道請求的伺服器的名稱。因此，它只能提供預設的伺服器憑證。

Наиболее старым и надёжным способом решения этой проблемы является назначение каждому HTTPS-серверу своего IP-адреса:

解決這個問題最古老、最可靠的方法是為每個HTTPS伺服器分配自己的IP位址：

> ```
> server {
>
> 伺服器 {
>     listen          192.168.1.1:443 ssl;
>
>     聽192.168.1.1:443 ssl；
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate www.example.com.crt;
>
>     ssl_證書www.example.com.crt；
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen          192.168.1.2:443 ssl;
>
>     聽192.168.1.2:443 ssl；
>     server_name     www.example.org;
>
>     伺服器名稱www.example.org；
>     ssl_certificate www.example.org.crt;
>
>     ssl_憑證www.example.org.crt；
>     ...
> }
> ```

#### SSL-сертификат с несколькими именами｜SSL-多名稱證書

Существуют и другие способы, которые позволяют использовать один и тот же IP-адрес сразу для нескольких HTTPS-серверов. Все они, однако, имеют свои недостатки. Одним из таких способов является использование сертификата с несколькими именами в поле SubjectAltName сертификата, например `www.example.com` и `www.example.org`. Однако, длина поля SubjectAltName ограничена.

還有其他方法可讓您同時對多個 HTTPS 伺服器使用相同的 IP 位址。然而，它們都有其缺點。其中一種方法是使用憑證的SubjectAltName 欄位中具有多個名稱的憑證，例如`www.example.com` 和`www.example.org`。然而，SubjectAltName 欄位的長度是有限的。

Другим способом является использование wildcard-сертификата, например `*.example.org`. Такой сертификат защищает все поддомены указанного домена, но только на заданном уровне. Под такой сертификат подходит `www.example.org`, но не подходят `example.org` и `www.sub.example.org`. Два вышеуказанных способа можно комбинировать. Сертификат может одновременно содержать и точное, и wildcard имена в поле SubjectAltName, например `example.org` и `*.example.org`.

另一種方法是使用通配符證書，例如`*.example.org`。此類憑證可以保護指定網域的所有子網域，但僅限於給定等級。 `www.example.org`適合此證書，但`example.org`和`www.sub.example.org`不適合。上述兩種方法可以結合。憑證的SubjectAltName 欄位中可以包含精確名稱和通配符名稱，例如`example.org` 和`*.example.org`。

Лучше поместить сведения о файле сертификата с несколькими именами и файле с его секретным ключом на уровне конфигурации *http*, чтобы все серверы унаследовали их единственную копию в памяти:

最好將多名憑證檔案及其私鑰檔案的詳細資訊放置在 *http* 配置級別，以便所有伺服器在記憶體中繼承它們的單一副本：

> ```
> ssl_certificate     common.crt;
>
> ssl_憑證通用.crt；
> ssl_certificate_key common.key;
>
> ssl_certificate_key common.key；
> 
> server {
>
> 伺服器 {
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ...
> }
> 
> server {
>
> 伺服器 {
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.org;
>
>     伺服器名稱www.example.org；
>     ...
> }
> ```

#### Указание имени сервера｜指定伺服器名稱

Более общее решение для работы нескольких HTTPS-серверов на одном IP-адресе — [расширение Server Name Indication протокола TLS](http://en.wikipedia.org/wiki/Server_Name_Indication) (SNI, RFC 6066), которое позволяет браузеру передать запрашиваемое имя сервера во время SSL handshake, а значит сервер будет знать, какой сертификат ему следует использовать для соединения. Сейчас SNI [поддерживается](http://en.wikipedia.org/wiki/Server_Name_Indication#Support) большинством современных браузеров и является обязательным расширением в TLSv1.3, однако может не использоваться некоторыми старыми или специализированными клиентами.

運行多個的更通用的解決方案 HTTPS-一台伺服器 IP-address - [伺服器名稱指示協定擴展 TLS](http://en.wikipedia.org/wiki/Server_Name_Indication) (SNI, RFC 6066），它允許瀏覽器在期間傳遞請求的伺服器名稱 SSL 握手，這意味著伺服器將知道應該使用哪個憑證進行連接。現在 SNI [支持](http://en.wikipedia.org/wiki/Server_Name_Indication#Support) 大多數現代瀏覽器，並且是 TLSv1.3 中必需的擴展，但某些較舊的或專門的用戶端可能不會使用。

> В SNI можно передавать только доменные имена, однако некоторые браузеры могут ошибочно передавать IP-адрес сервера в качестве его имени, если в запросе указан IP-адрес. Полагаться на это не следует.
>
> SNI只能傳遞域名，但如果請求指定了IP位址，某些瀏覽器可能會錯誤地將IP伺服器位址作為伺服器名稱傳遞。不應依賴這一點。

Чтобы использовать SNI в nginx, соответствующая поддержка должна присутствовать как в библиотеке OpenSSL, использованной при сборке бинарного файла nginx, так и в библиотеке, подгружаемой в момент работы. OpenSSL поддерживает SNI начиная с версии 0.9.8f, если она была собрана с опцией конфигурации “--enable-tlsext”. Начиная с OpenSSL 0.9.8j эта опция включена по умолчанию. Если nginx был собран с поддержкой SNI, то при запуске nginx с ключом “-V” об этом сообщается:

要在 nginx 中使用SNI，用於建置 nginx 二進位檔案的 OpenSSL 程式庫和執行時間載入的程式庫中必須存在適當的支援。如果 OpenSSL 是使用「--enable-tlsext」配置選項建構的，則從版本 0.9.8f 開始支援 SNI。自 OpenSSL 0.9.8j 起，此選項預設為啟用。如果 nginx 是支援 SNI 建構的，那麼當您使用「-V」開關啟動 nginx 時，會報告以下內容：

> ```bash
>
> 『`bash
> $ nginx -V
>
> $nginx -V
> ...
> TLS SNI support enabled
>
> TLS SNI 支援啟用
> ...
> ```

Однако если nginx, собранный с поддержкой SNI, в процессе работы подгружает библиотеку OpenSSL, в которой нет поддержки SNI, nginx выдаёт предупреждение:

但是，如果建置為支援SNI的nginx在運行期間載入不支援SNI的OpenSSL函式庫，nginx會發出警告：

> ```
> nginx was built with SNI support, however, now it is linked
>
> nginx 是使用 SNI 支援構建的，但是現在它已鏈接
> dynamically to an OpenSSL library which has no tlsext support,
>
> 動態地連線到不支援 tlsext 的 OpenSSL 函式庫，
> therefore SNI is not available
>
> 因此 SNI 不可用
> ```

#### Совместимость｜相容性

-   Статус поддержки SNI отображается по ключу “-V” начиная с версий 0.8.21 и 0.7.62.  
    從版本0.8.21和0.7.62開始，使用「-V」鍵顯示SNI的支援狀態。
-   Параметр `ssl` директивы [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>) поддерживается начиная с версии 0.7.14. До версии 0.8.21 его можно было указывать только совместно с параметром `default`.  
    從 0.7.14 開始支援 [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>) 指令的 `ssl` 選項。在0.8.21版本之前，只能與參數`default`一起指定。
-   SNI поддерживается начиная с версии 0.5.23.  
    從版本0.5.23開始支援SNI。
-   Разделяемый кэш SSL-сессий поддерживается начиная с версии 0.5.6.  
    從版本0.5.6開始支援SSL會話的共享快取。

-   Версия 1.27.3 и более поздние: протоколами SSL по умолчанию являются TLSv1.2 и TLSv1.3 (если поддерживается библиотекой OpenSSL). В противном случае, при использовании OpenSSL 1.0.0 и более старых версий, протоколами SSL по умолчанию являются TLSv1 и TLSv1.1.  
    版本 1.27.3 及更高版本：SSL 預設協定為 TLSv1.2 和 TLSv1.3（如果 OpenSSL 庫支援）。否則，當使用 OpenSSL 1.0.0 及更早版本時，預設 SSL 協定為 TLSv1 和 TLSv1.1。

    版本 1.23.4 及更高版本：預設 SSL 協定為 TLSv1、TLSv1.1、TLSv1.2 和 TLSv1.3（如果 OpenSSL 函式庫支援）。
-   Версия 1.9.1 и более поздние: протоколами SSL по умолчанию являются TLSv1, TLSv1.1 и TLSv1.2 (если поддерживается библиотекой OpenSSL).  
    版本 1.9.1 及更高版本：SSL 預設協定為 TLSv1、TLSv1.1 和 TLSv1.2（如果 OpenSSL 函式庫支援）。

    版本0.7.65, 0.8.19及更高版本：SSL預設協定為SSLv3、TLSv1、TLSv1.1和TLSv1.2（若OpenSSL函式庫支援）。
