設定與認證伺服器通訊的逾時時間。

#### Protocol｜協定

The HTTP protocol is used to communicate with the authentication server. The data in the response body is ignored, the information is passed only in the headers.

HTTP協定用於與認證伺服器通訊。響應體中的資料將被忽略，訊息僅透過回應頭傳遞。

Examples of requests and responses:

請求和回應範例：

Request:

要求：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: plain # plain/apop/cram-md5/external
>
> 身份驗證方法：plain # plain/apop/cram-md5/external
> Auth-User: user
>
> Auth-User：用戶
> Auth-Pass: password
>
> 授權碼：密碼
> Auth-Protocol: imap # imap/pop3/smtp
>
> 身份驗證協定：imap # imap/pop3/smtp
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> ```

Good response:

回覆良好：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: OK
>
> 身份驗證狀態： OK
> Auth-Server: 198.51.100.1
>
> 認證伺服器： 198.51.100.1
> Auth-Port: 143
>
> 認證埠：143
> ```

Bad response:

錯誤回覆：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: Invalid login or password
>
> 身份驗證狀態：登入名稱或密碼無效
> Auth-Wait: 3
>
> 授權等待：3
> ```

If there is no “Auth-Wait”（授權等待） header, an error will be returned and the connection will be closed. The current implementation allocates memory for each authentication attempt. The memory is freed only at the end of a session. Therefore, the number of invalid authentication attempts in a single session must be limited — the server must respond without the “Auth-Wait”（授權等待） header after 10-20 attempts (the attempt number is passed in the “Auth-Login-Attempt”（身份驗證登入嘗試） header).

如果沒有“Auth-Wait”（授權等待）標頭，則會傳回錯誤並關閉連線。目前實作會為每次身份驗證嘗試分配記憶體。記憶體僅在會話結束時釋放。因此，單一會話中的無效身分驗證嘗試次數必須受到限制－伺服器必須在 10-20 次嘗試後不包含“Auth-Wait”（授權等待）標頭（嘗試次數在“Auth-Login-Attempt”（身份驗證登入嘗試）標頭中傳遞）。

When the APOP or CRAM-MD5 are used, request-response will look as follows:

當使用APOP或CRAM-MD5時，請求-回應將如下所示：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: apop
>
> 身份驗證方法：apop
> Auth-User: user
>
> Auth-User：用戶
> Auth-Salt: <238188073.1163692009@mail.example.com>
>
> 驗證鹽：< 238188073.1163692009 @mail.example.com>
> Auth-Pass: auth_response
>
> 身份驗證密碼：auth_response
> Auth-Protocol: imap
>
> 身份驗證協定：IMAP
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> ```

Good response:

回覆良好：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: OK
>
> 身份驗證狀態： OK
> Auth-Server: 198.51.100.1
>
> 認證伺服器： 198.51.100.1
> Auth-Port: 143
>
> 認證埠：143
> Auth-Pass: plain-text-pass
>
> 身份驗證密碼：明文密碼
> ```

If the “Auth-User”（認證用戶） header exists in the response, it overrides the username used to authenticate with the backend.

如果回應中存在“Auth-User”（認證用戶）標頭，則會覆寫用於向後端進行身份驗證的使用者名稱。

For the SMTP, the response additionally takes into account the “Auth-Error-Code”（身份驗證錯誤代碼） header — if exists, it is used as a response code in case of an error. Otherwise, the 535 5.7.0 code will be added to the “Auth-Status”（身份驗證狀態） header.

對於SMTP ，回應也會考慮“Auth-Error-Code”（身份驗證錯誤代碼）標頭－如果存在，則將其用作錯誤時的回應碼。否則，將5.7.0程式碼加入“Auth-Status”（身份驗證狀態）標頭中。

For example, if the following response is received from the authentication server:

例如，如果從身份驗證伺服器收到以下回應：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: Temporary server problem, try again later
>
> 身份驗證狀態：伺服器暫時出現問題，請稍後重試。
> Auth-Error-Code: 451 4.3.0
>
> 驗證錯誤碼：451 4.3.0
> Auth-Wait: 3
>
> 授權等待：3
> ```

then the SMTP client will receive an error

然後SMTP客戶端將收到錯誤

> ```
> 451 4.3.0 Temporary server problem, try again later
>
> 451 4.3.0伺服器暫時出現問題，請稍後再試。
> ```

If proxying SMTP does not require authentication, the request will look as follows:

如果代理SMTP不需要身份驗證，則請求將如下所示：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: none
>
> 身份驗證方法：無
> Auth-User:
>
> Auth-User：
> Auth-Pass:
>
> 授權碼：
> Auth-Protocol: smtp
>
> 身份驗證協定：smtp
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> Auth-SMTP-Helo: client.example.org
>
> Auth- SMTP -Helo: client.example.org
> Auth-SMTP-From: MAIL FROM: <>
>
> 授權- SMTP -寄件者： MAIL FROM : <>
> Auth-SMTP-To: RCPT TO: <postmaster@mail.example.com>
>
> 授權- SMTP -至: RCPT TO: <postmaster@mail.example.com>
> ```

For the SSL/TLS client connection (1.7.11), the “Auth-SSL”（認證-SSL） header is added, and “Auth-SSL-Verify”（身份驗證-SSL驗證） will contain the result of client certificate verification, if [enabled](<123 [01.01.04 郵件] 模組 ngx_mail_ssl_module.md#ssl_verify_client>): “`SUCCESS`”, “`FAILED:``*reason*`”, and “`NONE`” if a certificate was not present.

對於 SSL/TLS 客戶端連線（1.7.11）， 這 “Auth-SSL”（認證-SSL） 添加標題，並且 “Auth-SSL-Verify”（身份驗證-SSL驗證） 如果啟用，將包含用戶端憑證驗證結果(https://nginx.org/en/docs/mail/ngx_mail_ssl_module.html#ssl_verify_client): “`SUCCESS`”, “`FAILED:``*reason*`“， 和 ”`NONE`“如果沒有證書的話。”

> Prior to version 1.11.7, the “`FAILED`” result did not contain the `*reason*` string.
>
> 在版本1.11.7之前，「 `FAILED` 」結果不包含字串`*reason*` 。

When the client certificate was present, its details are passed in the following request headers: “Auth-SSL-Subject”, “Auth-SSL-Issuer”（身份驗證 SSL 頒發者）, “Auth-SSL-Serial”, and “Auth-SSL-Fingerprint”（身份驗證 SSL 指紋）. If [auth\_http\_pass\_client\_cert](#auth_http_pass_client_cert) is enabled, the certificate itself is passed in the “Auth-SSL-Cert”（身份驗證 SSL 憑證） header. The protocol and cipher of the established connection are passed in the “Auth-SSL-Protocol”（身份驗證 SSL 協議） and “Auth-SSL-Cipher”（身份驗證 SSL 密碼） headers (1.21.2). The request will look as follows:

當客戶端憑證存在時，其詳細資訊會透過以下請求頭傳遞： “Auth-SSL-Subject”, “Auth-SSL-Issuer”（身份驗證 SSL 頒發者）, “Auth-SSL-Serial”和“Auth-SSL-Fingerprint”（身份驗證 SSL 指紋） 。如果啟用了 [auth\_http\_pass\_client\_cert](#auth_http_pass_client_cert) ，則憑證本身會透過“Auth-SSL-Cert”（身份驗證 SSL 憑證）標頭傳遞。已建立連線的協定和密碼套件會透過“Auth-SSL-Protocol”（身份驗證 SSL 協議）和“Auth-SSL-Cipher”（身份驗證 SSL 密碼）標頭（ 1.21.2 ）傳遞。請求將如下所示：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: plain
>
> 身份驗證方法：plain
> Auth-User: user
>
> Auth-User：用戶
> Auth-Pass: password
>
> 授權碼：密碼
> Auth-Protocol: imap
>
> 身份驗證協定：IMAP
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Auth-SSL: on
>
> 授權- SSL : 開啟
> Auth-SSL-Protocol: TLSv1.3
>
> 身份驗證SSL -協定：TLSv1.3
> Auth-SSL-Cipher: TLS_AES_256_GCM_SHA384
>
> 身份驗證SSL - 密碼：TLS_AES_256_GCM_SHA384
> Auth-SSL-Verify: SUCCESS
>
> 驗證： SSL -驗證： SUCCESS
> Auth-SSL-Subject: /CN=example.com
>
> 授權- SSL -主題: / CN =example.com
> Auth-SSL-Issuer: /CN=example.com
>
> 授權碼 - SSL - 發卡方：/ CN =example.com
> Auth-SSL-Serial: C07AD56B846B5BFF
>
> 授權碼： SSL -序號： C07AD56B846B5BFF
> Auth-SSL-Fingerprint: 29d6a80a123d13355ed16b4b04605e29cb55a5ad
>
> 驗證SSL -指紋： 29d6a80a123d13355ed16b4b04605e29cb55a5ad
> ```

When the [PROXY protocol](<117 [01.01.04 郵件] 模組 ngx_mail_core_module.md#proxy_protocol>) is used, its details are passed in the following request headers: “Proxy-Protocol-Addr”（代理協定地址）, “Proxy-Protocol-Port”（代理協定連接埠）, “Proxy-Protocol-Server-Addr”（代理協定伺服器位址）, and “Proxy-Protocol-Server-Port”（代理協定伺服器連接埠） (1.19.8).

當使用 [PROXY協議](<117 [01.01.04 郵件] 模組 ngx_mail_core_module.md#proxy_protocol>)時，其詳細資訊透過以下請求標頭傳遞： “Proxy-Protocol-Addr”（代理協定地址）, “Proxy-Protocol-Port”（代理協定連接埠）, “Proxy-Protocol-Server-Addr”（代理協定伺服器位址）和“Proxy-Protocol-Server-Port”（代理協定伺服器連接埠） ( 1.19.8 )。
