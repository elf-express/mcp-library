Модуль `ngx_http_upstream_hc_module` позволяет активировать периодические проверки работоспособности серверов в [группе](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#upstream>), указанной в содержащем location. Группа должна находиться в [зоне разделяемой памяти](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#zone>).

`ngx_http_upstream_hc_module`模組可對包含位置中指定的 [群組](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#upstream>)中的伺服器進行定期健康檢查。此群組必須位於 [共享記憶體區域](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#zone>)中。

Если проверка работоспособности была неуспешной, то сервер признаётся неработоспособным. Если для группы задано несколько проверок, то при любой неуспешной проверке соответствующий сервер будет считаться неработоспособным. На неработоспособные серверы и серверы в состоянии “checking” клиентские запросы передаваться не будут.

如果健康檢查失敗，則伺服器被視為不健康。如果為一組定義了多個健康檢查，則任何失敗的健康檢查都會導致相應的伺服器被視為不健康。客戶端請求將不會轉發到不健康的伺服器或處於「檢查中」狀態的伺服器。

> Обратите внимание, что при использовании проверок большинство переменных имеют пустые значения.
>
> 請注意，在使用檢查時，大多數變數的值為空。

> Модуль доступен как часть [коммерческой подписки](https://www.f5.com/products/nginx).
>
> 此模組作為[商業訂閱](https://www.f5.com/products/nginx)的一部分提供。

#### Пример конфигурации｜配置範例

> ```
> upstream dynamic {
>
> 上游動態
>     zone upstream_dynamic 64k;
>
>     區域 upstream_dynamic 64k；
> 
>     server backend1.example.com      weight=5;
>
>     伺服器 backend1.example.com 權重=5；
>     server backend2.example.com:8080 fail_timeout=5s slow_start=30s;
>
>     伺服器 backend2.example.com:8080 fail_timeout=5s slow_start=30s;
>     server 192.0.2.1                 max_fails=3;
>
>     伺服器192.0.2.1 max_fails=3;
> 
>     server backup1.example.com:8080  backup;
>
>     伺服器 backup1.example.com:8080 備份;
>     server backup2.example.com:8080  backup;
>
>     伺服器 backup2.example.com:8080 備份;
> }
> 
> server {
>
> 伺服器{
>     location / {
>
>     地點/{
>         proxy_pass http://dynamic;
>         health_check;
>
>         健康檢查；
>     }
> }
> ```

Каждому серверу группы `backend` с интервалом в 5 секунд посылаются запросы “`/`”. Если происходит ошибка или таймаут при работе с сервером, или код ответа проксируемого сервера не равен 2xx или 3xx, проверка считается неуспешной и сервер признаётся неработоспособным.

`backend`群組中的每個伺服器都會以5秒的間隔收到`/`請求。如果在與伺服器通訊時發生錯誤或逾時，或代理伺服器的回應代碼不是2xx或3xx，則檢查被視為失敗，且伺服器被視為不健康。

Проверки работоспособности могут тестировать код ответа, наличие или отсутствие определённых полей заголовка и их значений, а также содержимое тела ответа. Тесты настраиваются отдельно при помощи директивы [match](#match) и указываются в параметре `match`. Например:

健康檢查可以測試回應代碼、特定標頭欄位及其值是否存在，以及回應正文的內容。測試使用 [match](#match)指令單獨配置，並在`match`參數中指定。例如：

> ```
> http {
>
> http{
>     server {
>
>     伺服器{
>     ...
>         location / {
>
>         地點/{
>             proxy_pass http://backend;
>             health_check match=welcome;
>
>             健康檢查匹配=歡迎；
>         }
>     }
> 
>     match welcome {
>
>     比賽歡迎{
>         status 200;
>
>         狀態 200；
>         header Content-Type = text/html;
>         body ~ "Welcome to nginx!";
>
>         正文 ~ "歡迎使用 nginx！";
>     }
> }
> ```

В такой конфигурации успешный ответ на проверочный запрос должен иметь код 200, тип содержимого “`text/html`” и “`Welcome to nginx!`” в теле ответа.

在此配置中，對驗證請求的成功回應應具有代碼 200，內容類型為“ `text/html` ”，回應正文中應包含“ `Welcome to nginx!` ”。

|   |   |

| Умолчание:<br>預設值： | — |
| Контекст:<br>背景： | `location` |

Активирует периодические проверки работоспособности серверов в [группе](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#upstream>), указанной в содержащем location.

啟用對包含位置中指定的 [群組](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#upstream>)中的伺服器進行定期健康檢查。

Могут быть заданы следующие необязательные параметры:

可指定以下可選參數：

`interval`\=`*время*`

задаёт интервал между двумя последовательными проверками, по умолчанию 5 секунд.

設定兩次連續檢查之間的間隔，預設值為 5 秒。

`jitter`\=`*время*`

задаёт время, в пределах которого случайным образом задерживается каждая проверка, по умолчанию задержки нет.

指定每次檢查隨機延遲的時間；預設情況下，沒有延遲。

`fails`\=`*число*`

задаёт число последовательных неуспешных проверок для определённого сервера, после которых сервер будет считаться неработоспособным, по умолчанию 1.

指定給定伺服器連續檢查失敗的次數，超過該次數後伺服器將被視為不健康，預設值為 1。

`passes`\=`*число*`

задаёт число последовательных успешных проверок для определённого сервера, после которых сервер будет считаться работоспособным, по умолчанию 1.

指定對給定伺服器連續成功檢查的次數，超過該次數後伺服器將被視為健康，預設值為 1。

`uri`\=`*uri*`

задаёт URI, используемый в запросах, проверяющих работоспособность, по умолчанию “`/`”.

設定健康檢查查詢中使用的URI ，預設值為「 `/` 」。

`mandatory` \[`persistent`\]

устанавливает исходное состояние “checking” для сервера до завершения первой проверки работоспособности (1.11.7). На серверы в состоянии “checking” клиентские запросы передаваться не будут. Если параметр не указан, то исходно сервер будет считаться работоспособным.

將伺服器的初始狀態設定為“檢查中”，直到首次健康檢查 ( 1.11.7 ) 完成。客戶端請求將不會傳送到處於「檢查中」狀態的伺服器。如果省略此參數，則伺服器初始狀態將被視為健康。

Параметр `persistent` (1.19.7) устанавливает исходное состояние “up” для сервера после перезагрузки nginx в случае, если до перезагрузки сервер считался работоспособным.

如果伺服器在重新啟動前被認為是運作正常的，則`persistent` ( 1.19.7 ) 參數會在 nginx 重新啟動後設定伺服器的初始「運作」狀態。

`match`\=`*имя*`

указывает на блок `match` с условиями, которым должен удовлетворять ответ, чтобы результат проверки считался успешным. По умолчанию код ответа должен быть 2xx или 3xx.

指向`match`程式碼區塊，其中包含檢查成功所需的回應條件。預設情況下，回應代碼應為 2xx 或 3xx。

`port`\=`*число*`

задаёт порт, используемый при подключении к серверу для проверки его работоспособности (1.9.7). По умолчанию совпадает с портом [сервера](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#server>).

指定連接到伺服器以檢查其功能時使用的連接埠（ 1.9.7 ）。預設情況下，它與[伺服器連接埠](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#server>)匹配。

`type`\=`grpc` \[`grpc_service`\=`*имя*`\] \[`grpc_status`\=`*код*`\]

активирует периодические [проверки работоспособности](https://github.com/grpc/grpc/blob/master/doc/health-checking.md#grpc-health-checking-protocol) gRPC-сервера или службы gRPC, указанной при помощи необязательного параметра `grpc_service` (1.19.5). Если сервер не поддерживает протокол проверки работоспособности gRPC, то можно использовать необязательный параметр `grpc_status` для указания [статуса](https://github.com/grpc/grpc/blob/master/doc/statuscodes.md#status-codes-and-their-use-in-grpc) (например статус “`12`” / “`UNIMPLEMENTED`”) при получении которого сервер признаётся работоспособным:

啟用對使用選用參數`grpc_service` ( 1.19.5 ) 指定的 gRPC 伺服器或 gRPC 服務進行定期(https://github.com/grpc/grpc/blob/master/doc/health-checking.md#grpc-health-checking-protocol)健康檢查。如果伺服器不支援 gRPC 健康檢查協議，則可以使用可選參數`grpc_status`指定一個(https://github.com/grpc/grpc/blob/master/doc/statuscodes.md#status-codes-and-their-use-in-grpc) [狀態]（例如，“ `12` ” / “ `UNIMPLEMENTED` ”），該狀態在收到後被視為健康：

> ```
> health_check mandatory type=grpc grpc_status=12;
> ```

Параметр `type`\=`grpc` должен быть указан после остальных параметров директивы, `grpc_service` и `grpc_status` должны быть указаны после `type`\=`grpc`. Параметр несовместим с параметрами [`uri`](#health_check_uri) и [`match`](#health_check_match).

參數`type` \= `grpc`必須在指令的其他參數之後指定， `grpc_service`和`grpc_status`必須在`type` \= `grpc`之後指定。此參數與參數 [`uri`](#health_check_uri)和 [`match`](#health_check_match)不相容。

`keepalive_time`\=`*время*`

включает [keepalive](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#keepalive>) соединения в проверках работоспособности и задаёт время, в течение которого могут обрабатываться запросы в рамках keepalive соединения (1.21.7). По умолчанию keepalive соединения выключены.

啟用健康檢查中的 [keepalive](<266 [02.01.01 http] ngx_http_upstream_module 模組.md#keepalive>)連接，並指定在 keepalive 連接 ( 1.21.7 ) 內處理請求的時間。預設情況下，keepalive 連線處於停用狀態。

| Синтаксис:<br>文法： | ``**match** `*имя*` { ... }``<br>` `**match** ` *名稱* ` { ... }` ` |
| Умолчание:<br>預設值： | — |
| Контекст:<br>背景： | `http` |

Задаёт именованный набор тестов для анализа ответов на запросы проверки работоспособности.

指定一組用於分析健康檢查請求回應的測試。

В ответе могут быть протестированы следующие объекты:

回應中可能會測試以下物件：

`status 200;`

код ответа равен 200

回應代碼為 200

`status ! 500;`

код ответа не равен 500

回應代碼不是 500

`status 200 204;`

код ответа равен 200 или 204

回應代碼為 200 或 204

`status ! 301 302;`

код ответа не равен ни 301, ни 302

回應代碼既不是 301 也不是 302

`status 200-399;`

код ответа находится в диапазоне от 200 до 399

回應代碼範圍為 200 至 399。

`status ! 400-599;`

код ответа находится вне диапазона от 400 до 599

回應代碼不在 400 到 599 的範圍內

`status 301-303 307;`

код ответа равен 301, 302, 303 или 307

回應代碼為 301、302、303 或 307。

`header Content-Type = text/html;`

заголовок содержит “Content-Type”（內容類型） со значением `text/html`

標題包含“Content-Type”（內容類型） ，值為`text/html`

`header Content-Type != text/html;`

заголовок содержит “Content-Type”（內容類型） со значением, отличным от `text/html`

標題包含“Content-Type”（內容類型） ，其值與`text/html`不同。

`header Connection ~ close;`

заголовок содержит “Connection”（聯繫） со значением, совпадающим с регулярным выражением `close`

標頭包含“Connection”（聯繫） ，其值與正規表示式`close`匹配。

`header Connection !~ close;`

заголовок содержит “Connection”（聯繫） со значением, не совпадающим с регулярным выражением `close`

標頭包含“Connection”（聯繫）但其值與正規表示式`close`不符。

`header Host;`

заголовок содержит “Host”（主持人）

標題包含“Host”（主持人）

`header ! X-Accel-Redirect;`

заголовок не содержит “X-Accel-Redirect”（X-Accel-重定向）

標題不包含“X-Accel-Redirect”（X-Accel-重定向）

`body ~ "Welcome to nginx!";`

тело ответа совпадает с регулярным выражением “`Welcome to nginx!`”

響應體與正規表示式「 `Welcome to nginx!` 」匹配

`body !~ "Welcome to nginx!";`

тело ответа не совпадает с регулярным выражением “`Welcome to nginx!`”

響應體與正規表示式「 `Welcome to nginx!` 」不符。

`require` `*$переменная*` `...;`

все указанные переменные непустые и не равны “0” (1.15.9).

所有指定的變數均非空且不等於「0」（ 1.15.9 ）。

Если задано несколько тестов, то ответ должен удовлетворять всем тестам.

如果給出多個測試，答案必須滿足所有測試的要求。

> Проверяются только первые 256 Кбайт тела ответа.
>
> 僅檢查回應正文的前 256 KB。

Примеры:

例如：

> ```
> # код ответа 200, тип содержимого "text/html"｜回應代碼 200，內容類型“文本/html”
> # и тело ответа содержит "Welcome to nginx!"｜回應正文包含“歡迎使用 nginx！”
> match welcome {
>
> 比賽歡迎{
>     status 200;
>
>     狀態 200；
>     header Content-Type = text/html;
>     body ~ "Welcome to nginx!";
>
>     正文 ~ "歡迎使用 nginx！";
> }
> ```

> ```
> # код ответа не равен 301, 302, 303 и 307 и заголовок не содержит "Refresh:"｜回應代碼不是 301、302、303 或 307，且標頭不包含「Refresh:」。
> match not_redirect {
>
> 匹配 not_redirect {
>     status ! 301-303 307;
>
>     狀態！ 301-303 307；
>     header ! Refresh;
>
>     標題！重新整理;
> }
> ```

> ```
> # код ответа успешный и сервер не в сервисном режиме｜回應代碼為成功，伺服器未處於服務模式。
> match server_ok {
>
> 匹配 server_ok {
>     status 200-399;
>
>     狀態 200-399；
>     body !~ "maintenance mode";
>
>     身體！ ~「維護模式」；
> }
> ```

> ```
> # код ответа равен 200 или 204｜回應代碼為 200 或 204
> map $upstream_status $good_status {
>
> 映射 $upstream_status $good_status {
>     200     1;
>     204     1;
> }
> 
> match server_ok {
>
> 匹配 server_ok {
>     require $good_status;
>
>     需要 $good_status；
> }
> ```
