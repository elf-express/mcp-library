# Проксирование WebSocket｜WebSocket代理

> 章節：[ru](<000 目錄.md#c-9>) › [docs｜文件](<000 目錄.md#c-10>) › [http](<000 目錄.md#c-11>)

## Проксирование WebSocket｜WebSocket代理

Для превращения соединения между клиентом и сервером из HTTP/1.1 в WebSocket используется доступный в HTTP/1.1 механизм [смены протокола](https://datatracker.ietf.org/doc/html/rfc2616#section-14.42).

要將客戶端與伺服器之間的連線從HTTP/1.1轉換為 WebSocket，可以使用HTTP/1.1中提供的 [協定轉換 機制](https://datatracker.ietf.org/doc/html/rfc2616#section-14.42) 。

Но есть сложность: поскольку “Upgrade”（升級） является [hop-by-hop](https://datatracker.ietf.org/doc/html/rfc2616#section-13.5.1) заголовком, то он не передаётся от клиента к проксируемому серверу. При прямом проксировании клиенты могут использовать метод `CONNECT`, чтобы обойти эту проблему. Однако при обратном проксировании такой подход не работает, так как клиент ничего о проксирующем сервере не знает, и требуется специальная обработка на проксирующем сервере.

但這裡有個問題：由於“Upgrade”（升級）是逐跳(https://datatracker.ietf.org/doc/html/rfc2616#section-13.5.1)頭部，它不會從客戶端傳輸到代理伺服器。在正向代理中，客戶端可以使用`CONNECT`方法來規避這個問題。然而，在反向代理中，這種方法行不通，因為客戶端對代理伺服器一無所知，需要在代理伺服器上進行特殊處理。

Начиная с версии 1.3.13 в nginx предусмотрен особый режим работы, который позволяет установить туннель между клиентом и проксируемым сервером, если проксируемый сервер вернул ответ с кодом 101 (Switching Protocols), и клиент попросил сменить протокол с помощью заголовка “Upgrade”（升級） в запросе.

從1.3.13 nginx 具有一種特殊的運行模式，允許在客戶端和代理伺服器之間建立隧道，前提是代理伺服器回傳了代碼為 101（切換協定）的回應，並且客戶端在請求中使用“Upgrade”（升級）標頭請求更改協定。

Как уже отмечалось выше, hop-by-hop заголовки, включая “Upgrade”（升級） и “Connection”（聯繫）, не передаются от клиента к проксируемому серверу, поэтому, для того чтобы проксируемый сервер узнал о намерении клиента сменить протокол на WebSocket, эти заголовки следует передать явно:

如上所述，逐跳標頭（包括“Upgrade”（升級）和“Connection”（聯繫） ）不會從客戶端傳輸到代理伺服器，因此，為了讓代理伺服器知道客戶端打算將協定更改為WebSocket，應該明確地傳輸這些標頭：

> ```
> location /chat/ {
>     proxy_pass http://backend;
>     # proxy_http_version 1.1; # до версии 1.29.7｜proxy_http_version 1.1 ; # 最高支援版本1.29.7
>     proxy_set_header Upgrade $http_upgrade;
>     proxy_set_header Connection "upgrade";
>
>     proxy_set_header Connection "升級";
> }
> ```

一個更複雜的例子，其中發送到代理伺服器的請求頭中的“Connection”（聯繫）字段的值取決於客戶端請求頭中“Upgrade”（升級）字段是否存在：

> ```
> http {
>
> http{
>     map $http_upgrade $connection_upgrade {
>
>     映射 $http_upgrade $connection_upgrade {
>         default upgrade;
>
>         預設升級；
>         ''      close;
>
>         '' 關閉;
>     }
> 
>     server {
>
>     伺服器{
>         ...
> 
>         location /chat/ {
>             proxy_pass http://backend;
>             # proxy_http_version 1.1; # до версии 1.29.7｜proxy_http_version 1.1 ; # 版本1.29.7之前
>             proxy_set_header Upgrade $http_upgrade;
>             proxy_set_header Connection $connection_upgrade;
>         }
>     }
> ```

По умолчанию соединение будет закрыто, если с проксируемого сервера данные не передавались в течение 60 секунд. Этот таймаут можно увеличить при помощи директивы [proxy\_read\_timeout](<248 [02.01.01 http] ngx_http_proxy_module 模組.md#proxy_read_timeout>). Кроме того, на проксируемом сервере можно настроить периодическую отправку WebSocket ping-фреймов для сброса таймаута и проверки работоспособности соединения.

預設情況下，如果代理伺服器在 60 秒內沒有發送任何數據，連線將關閉。可以使用 `[proxy\_read\_timeout](<248 [02.01.01 http] ngx_http_proxy_module 模組.md#proxy_read_timeout>)指令增加此逾時時間。此外，還可以設定代理伺服器定期發送 WebSocket ping 幀來重置逾時時間並檢查連線狀態。
