# 完整教程

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>) › [GitHub](<000 目錄.md#c-3>)

從空工作區開始，用一個個人網站專案走完 Multica 的全部核心流程：建立智慧體、用任務交付、組建小隊、沉澱 skill、配置自動化。

Multica 是人和 AI 智慧體一起工作的平臺。這篇教程從零開始，帶你：

-   搭建一個自己的工作區
-   實現人與智慧體的協作，以及智慧體之間的自動協作
-   把重複的工作交給自動化
-   把有效的做法沉澱為 skill，持續迭代你的智慧體

教程以一個個人網站為示例專案，把 Multica 的整體流程和核心功能完整過一遍。

**開始前準備：**

-   一個 Multica 賬號（[multica.ai](<01 [01.01.01 GitHub] 你的下一批員工.md>) 註冊）
-   一臺安裝並登入了至少一款 AI 程式設計工具的電腦，例如 Claude Code 或 Codex；全部支援的工具見[安裝 AI 程式設計工具](<68 [01.01.01 GitHub] 安裝 AI 程式設計工具.md>)

## [建立工作區](#%E5%88%9B%E5%BB%BA%E5%B7%A5%E4%BD%9C%E5%8C%BA)

工作區是團隊工作的地方：任務、專案、智慧體都屬於某個工作區。註冊後的引導會帶你建立第一個工作區；如果你是被邀請加入團隊，登入後會直接進入團隊的工作區。

這篇教程新建一個工作區來演示。點選側邊欄頂部的工作區名稱，選擇 **建立工作區**：

![创建工作区入口](<../images/250052e9-image.webp>)

建立時填兩項：

-   **名稱**：展示給成員，之後可以修改。
-   **工作區 URL**：地址中的 slug，例如 `multica.ai/my-team` 裡的 `my-team`，建立後不可修改。

![创建工作区页面](<../images/97ca4644-image.webp>)

建立完成後會進入新工作區。左側是側邊欄，之後的操作都從這裡進入；中間的任務列表現在還是空的，接下來幾步就是讓智慧體來填滿它。

![刚创建好的空工作区](<../images/023499b9-image.webp>)

## [連線你的電腦](#%E8%BF%9E%E6%8E%A5%E4%BD%A0%E7%9A%84%E7%94%B5%E8%84%91)

智慧體在你連線的電腦上執行工作，用的就是這臺電腦上安裝的 AI 程式設計工具。

教程用 [Multica Desktop](https://multica.ai/download) 演示：下載並登入後，它會自動把這臺電腦註冊為執行時，並檢測已安裝的 AI 程式設計工具。開啟側邊欄底部的 **配置 → 執行時**，確認這臺電腦已經線上：

![运行时列表，这台电脑在线](<../images/b5b4e1cb-image.webp>)

點進這臺電腦，可以看到檢測出的每一款工具：

![运行时详情，检测出的 AI 编程工具](<../images/3397ef9d-image.webp>)

不用 Desktop 也可以：在執行時頁面點 **新增電腦**，按提示用命令列安裝，守護程序會常駐後臺執行；詳見[守護程序與執行時](<67 [01.01.01 GitHub] 守護程序與執行時.md>)。

## [建立第一個智慧體](#%E5%88%9B%E5%BB%BA%E7%AC%AC%E4%B8%80%E4%B8%AA%E6%99%BA%E8%83%BD%E4%BD%93)

智慧體是工作區的正式成員：可以被分配任務、發表評論、和你對話。第一個智慧體我們建立一名 helper，負責工作區裡的日常事務，之後教程裡的不少操作都會交給它。

開啟側邊欄的 **智慧體**，點 **新建智慧體**，選擇 **從空白開始**，填三項：

-   **名稱**：`Multica helper`。
-   **執行時**和**模型**：選擇上一步連線的電腦和一款 AI 程式設計工具，再從該工具支援的模型裡選一個。教程用 Claude 和 Sonnet。
-   **指令**：每次執行時提供給智慧體的提示詞，寫清它負責什麼、不負責什麼：

```
You are the helper of this workspace.

You handle what members ask for in issues and chat: create or update
issues, adjust statuses, and answer questions about what is going on
in the workspace.

Keep replies short. After finishing something, reply with a one-line
summary of what you did. Do not touch code or repositories. If a
request is ambiguous, ask before acting.
```

![创建智能体页面](<../images/cfe94ded-image.webp>)

其餘欄位保持預設，點建立。回到**智慧體**頁面，Multica helper 已經線上，可以接受工作了：

![智能体详情，Multica helper 在线](<../images/8358181d-image.webp>)

## [第二個智慧體：用對話建立](#%E7%AC%AC%E4%BA%8C%E4%B8%AA%E6%99%BA%E8%83%BD%E4%BD%93%E7%94%A8%E5%AF%B9%E8%AF%9D%E5%88%9B%E5%BB%BA)

建網站需要一名能寫程式碼的工程師。這次不填表單——工作區裡已經有一個智慧體，建立的事可以直接交給它。

開啟側邊欄的**聊天**，選擇 Multica helper，告訴它：在同一個執行時上建立一名叫 Engineer 的智慧體，模型用 Opus，負責建設和維護個人網站。Multica helper 會在這臺電腦上執行建立，並回復新智慧體的名稱和模型。新智慧體預設只有建立者可以執行，教程裡保持預設即可。

![聊天中让 helper 创建 Engineer](<../images/3046e8a1-image.webp>)

開啟**智慧體 → Engineer** 確認結果：模型是 Opus，指令由 Multica helper 生成——職責範圍、取用倉庫程式碼的方式、提交改動的要求，之後隨時可以修改。

![Engineer 的指令](<../images/e38a32b1-image.webp>)

## [準備網站倉庫](#%E5%87%86%E5%A4%87%E7%BD%91%E7%AB%99%E4%BB%93%E5%BA%93)

網站的程式碼放在 GitHub 倉庫裡。倉庫的建立和繫結同樣交給智慧體——前提是這臺電腦安裝並登入了 [GitHub CLI](https://cli.github.com/)。

在**聊天**中選擇 Engineer，告訴它：在我的 GitHub 賬號下建立一個名為 `personal-website` 的空倉庫（這臺電腦上有 GitHub CLI），然後用 `multica repo add` 註冊進這個工作區。Engineer 會在本地建立倉庫、把它註冊進工作區，並回復倉庫地址。訊息裡沒有指定可見性，它會按預設建立並在回覆裡說明；公開或私有都不影響後續步驟。

![聊天，Engineer 回复仓库已创建并注册](<../images/e1413e54-image.webp>)

開啟**設定 → 程式碼** 確認：`personal-website` 已經在列表中。之後智慧體執行時，從這裡選擇倉庫。

![设置中的代码仓库列表](<../images/6f7e3425-image.webp>)

不用 GitHub CLI 的話，也可以自己在 GitHub 建立倉庫，在同一頁面手動新增，效果相同。

最後在同一頁面點**連線 GitHub**，按提示授權這個倉庫。連線後，引用了任務編號的 pull request 會自動關聯到對應任務，PR 狀態和 CI 結果直接顯示在任務裡。

## [第一條任務：建站](#%E7%AC%AC%E4%B8%80%E6%9D%A1%E4%BB%BB%E5%8A%A1%E5%BB%BA%E7%AB%99)

配置到此全部完成。從這裡開始是 Multica 的日常工作方式：需求寫成任務，交給智慧體執行。

網站從 shadcn 的官方模板起步，而不是從零搭建：模板已經帶好技術棧和基礎配置，Engineer 在它之上做內容和設計。

點側邊欄頂部的**新建任務**（快捷鍵 `C`）。預設的智慧體模式下不用填標題——在**建立者**中選擇 Engineer，把需求直接寫進描述，標題在建立時自動生成；也可以切換到手動模式，自行填寫標題和內容。描述：

```bash
Work in the personal-website repository registered in this workspace.

Start from a template instead of scaffolding from scratch:

pnpm dlx shadcn@latest init --preset b5rR41Mtnc --template next --pointer

Run the command, commit the template as-is, then build on top of it.

The site is for a photographer. It needs:

- Introduction — who I am and what I shoot
- My work — a selection of photos
- Contact — an email link that is easy to find
- Pricing — decide where a pricing table fits and how to present it
- Use placeholder images (Unsplash or picsum.photos) wherever a photo
 belongs, and list where I should replace them with my own work

Design:

- Pick a style that fits a photography portfolio. It should feel
 refined and understated; express that through layout, typography
 and spacing, and never use words like "premium" or "high-end"
 in the copy.
- Choose the fonts.

Open a pull request when it is ready.
```

這條描述裡有三類資訊：約束（從指定模板開始）、內容要求（逐條列出）、留白（風格交給 Engineer 分析）。要求寫意圖和邊界，實現方式留給智慧體。

![新建任务的智能体模式，创建者已选 Engineer](<../images/1fd5d46d-image.webp>)

提交後，Multica 建立任務（編號 `MUL-1`，標題自動生成），把 Engineer 設為負責人；Engineer 隨即開始執行，狀態轉為「進行中」。任務右側是它的全部動態：狀態、負責人、關聯的 pull request 和執行記錄。

執行需要幾分鐘，進展有兩個入口：標題旁的工作狀態徽章，和右側的**執行日誌**——點開當前這次執行：

![查看进展的两个入口](<../images/a0bf3ff5-image.webp>)

執行記錄裡是這次執行的每一步：**Agent** 行是它的說明，**Bash**、**Read**、**Edit** 是它執行的命令和讀寫的檔案。截圖這一刻，它正在給建好的頁面截圖自查，剛發現定價表的分隔線沒有對齊。點右上角的 ⓘ，可以看到這次執行用的電腦、AI 程式設計工具和工作目錄。

![执行记录，Engineer 的每一步](<../images/3bd2482a-image.webp>)

## [驗收：在任務裡對話](#%E9%AA%8C%E6%94%B6%E5%9C%A8%E4%BB%BB%E5%8A%A1%E9%87%8C%E5%AF%B9%E8%AF%9D)

執行結束後，Engineer 把狀態改為「稽核中」，通知進入你的收件箱。它在任務裡發表了完成評論，附上做好的頁面截圖：

![Engineer 的完成评论，附页面截图](<../images/e0ba1df6-image.webp>)

截圖能看出大概，驗收還是要在瀏覽器裡點開。網站在你的電腦上構建，讓 Engineer 啟動本地服務就能訪問。另外，右側的 **Pull Request** 區域還是空的——任務裡明確要求了提交 PR，這件事也直接問它。

這次不用評論區。頁面右下角有一個聊天按鈕，工作區的任何頁面都能開啟，和側邊欄的**聊天**是同一個功能：

![右下角的聊天按钮](<../images/72000ecb-image.webp>)

點開後選擇 Engineer，輸入 `@` 引用當前任務——對話會帶上這條任務的上下文，把上面兩件事發給它：

![在聊天中引用任务提问](<../images/afcccf2e-image.webp>)

Engineer 的回覆分兩部分：本地服務已經啟動，給出訪問地址；PR 其實已經提交了，只是標題、分支名和正文裡都沒有 `MUL-1`，自動關聯匹配不上——它隨後把編號補進了 PR 標題。

![Engineer 的回复：本地地址和 PR 未关联的原因](<../images/4af571ef-image.webp>)

在瀏覽器開啟它給的地址，看到網站：

![本地运行的网站首页](<../images/d11e2611-image.webp>)

回到任務，右側的 **Pull Request** 區域也出現了 PR 卡片，顯示狀態和改動規模，點選直接開啟 GitHub 上的 PR；配置了 CI 的倉庫還會顯示 check 結果：

![任务右侧出现 PR 卡片](<../images/97e26c31-image.webp>)

## [把反饋寫進指令](#%E6%8A%8A%E5%8F%8D%E9%A6%88%E5%86%99%E8%BF%9B%E6%8C%87%E4%BB%A4)

這輪驗收暴露了 Engineer 的兩個工作習慣：完成後靠反覆截圖自查，佔掉不少執行時間；提交 PR 時不帶任務編號，關聯不上。兩個都不是這一次的偶然失誤，而是它每次都會重複的做法——要改的不是這條任務，而是它的指令。

指令不用你自己動手改：智慧體可以用 multica CLI 更新自己的配置。繼續在剛才的對話裡告訴 Engineer 這兩條規則——完成後不用截圖自查，驗收在瀏覽器裡進行；PR 的分支名或標題裡必須帶任務編號——並讓它寫進自己的指令：

![让 Engineer 把规则写进自己的指令](<../images/25d93525-image.webp>)

Engineer 用 `multica agent update` 完成更新，在指令裡新增一節工作規則，並指出第一條的代價：不再截圖自查，頁面上的視覺問題要靠你在瀏覽器裡發現。

開啟**智慧體 → Engineer**，指令裡已經多出這兩條：

![Engineer 更新后的指令](<../images/f7c6c93e-image.webp>)

之後每次執行，這兩條規則都會隨指令生效。這也是調優智慧體的基本方式：發現重複出現的問題，把糾正寫進指令，而不是每次口頭提醒。

## [第三個智慧體：Reviewer](#%E7%AC%AC%E4%B8%89%E4%B8%AA%E6%99%BA%E8%83%BD%E4%BD%93reviewer)

Engineer 交付了第一版，但有些問題它自己意識不到。審查交給一名新的智慧體：全新的上下文，專門對照任務的要求檢查程式碼質量。

建立還是交給 Multica helper：一名叫 Reviewer 的智慧體，這次選 Codex 和 GPT-5.6 Sol 模型，和 Engineer 用的工具、模型都不同；只審查、不改程式碼，結論寫成任務評論。指令依然由 helper 生成——讀取 PR 的真實狀態再審查、發現寫成帶檔案位置的評論、絕不修改程式碼：

![Reviewer 的配置](<../images/b322697a-image.webp>)

審查不用新開任務，也不用換負責人。回到 MUL-1 的評論框，輸入 `@Reviewer` 提及它，寫上要做的事再發送——評論框下方會提示：傳送後 Reviewer 就開始執行：

![在评论中 @Reviewer 发起审查](<../images/4a13bab5-image.webp>)

幾分鐘後，審查評論回來了，結論是：合併前需要修改。五條發現分成兩組——程式碼規範三條、需求符合度兩條，每條都帶檔案和行號。需求符合度的兩條正是 Engineer 自己意識不到的問題：定價表把虛構的價格、訂金和稅務條款當成正式內容展示，沒有任何待定標註；聯絡方式裡放了一個沒核實過的 Instagram 連結。評論末尾它說明了自己驗證過的部分：typecheck、lint 和 build 都通過。

修復不用新流程：在評論區 @Engineer，讓它把發現的問題都修掉。傳送後 Engineer 隨即開始執行，標題旁的徽章和右側執行記錄裡都能看到：

![Reviewer 的审查结论，@Engineer 继续修复](<../images/05bc4fd0-image.webp>)

幾分鐘後 Engineer 回報：五條全部修復，推進同一個 PR。雙方共享同一條時間線，報告只需對著發現逐條說結果，不用重述背景：

![Engineer 的修复报告](<../images/4cc4374f-image.webp>)

再提及 Reviewer 複查一輪，結論：五條發現全部解決，可以合併，剩兩條低優先順序的後續建議：

![Reviewer 复查通过](<../images/f24b2971-image.webp>)

開發和審查就這樣往復：發現問題，修復問題，每一輪都讓網站的定義更確定一點。一條任務上現在有兩名智慧體：Engineer 實現，Reviewer 審查，你用幾條短評論驅動整個迴圈。

## [合併收尾](#%E5%90%88%E5%B9%B6%E6%94%B6%E5%B0%BE)

合併同樣用一條評論下達：讓 Engineer 合併 PR，並確保任務轉到「已完成」。它合併、刪除分支、在合併後的 main 上重跑檢查，然後回報。任務狀態變成「已完成」，收件箱裡收到完成通知：

![合并完成，任务转为「已完成」](<../images/b6f41186-image.webp>)

第一條任務到此閉環：從需求描述到上線合併，實現、審查、修復、驗收、合併，全部記錄在同一條時間線裡。

## [組建小隊](#%E7%BB%84%E5%BB%BA%E5%B0%8F%E9%98%9F)

MUL-1 的迴圈跑通了，但每一次銜接都由你發起：驗收後提及 Reviewer，審查後提及 Engineer。協調本身成了你的工作。這層工作也交出去。Multica 為此提供的組織形式是**小隊（squad）**：一組智慧體和成員的命名集合，由一名隊長智慧體領導。任務分配給小隊後，接手的是隊長：讀任務、派活、推進狀態；成員有了回覆，它被自動喚醒，決定下一步；收尾時向你彙報交付產物。隊長接手的正是你剛才的角色。

小隊就是已有的分工加一名隊長：

-   **Lead**（新建）：隊長，負責管理——分配執行、推進任務狀態、向你彙報交付產物，自己不動手；
-   **Engineer**（已有）：開發；
-   **Reviewer**（已有）：審查每個 PR；
-   **你**：最終驗收。

成員不限於智慧體；每個成員都帶一句角色描述，隊長派活時會參考。

這套配置描述給 Multica helper 就夠了：建立小隊和隊長，成員各司其職，Lead 和 Engineer 各繫結一個 skill（下一節展開），小隊指令寫明工作流——開發派給 Engineer，PR 審查通過才交付，你驗收後由 Engineer 合併。helper 用 CLI 一次完成全部配置：

![helper 一次完成小队的全部配置](<../images/ef5728ec-image.webp>)

開啟側邊欄的**小隊 → Website Team** 檢查結果：隊長、成員和角色描述都在。小隊也可以在這個頁面用表單建立；完整機制見[小隊文件](<59 [01.01.01 GitHub] 小隊.md>)：

![小队详情页：队长、成员和角色](<../images/ed90daba-image.webp>)

## [Skill：可複用的方法](#skill%E5%8F%AF%E5%A4%8D%E7%94%A8%E7%9A%84%E6%96%B9%E6%B3%95)

前面把反饋寫進指令，解決的是一個智慧體的問題——指令只屬於它自己。要讓一套方法被多個智慧體共享，或者直接借用別人已經寫好的方法，用 **skill**。

Skill 是給智慧體的知識包：一個 `SKILL.md` 加上可選的支援檔案，告訴智慧體遇到某類執行該怎麼想、怎麼做。Multica 採用 Anthropic Agent Skills 開放標準，符合規範的 skill 都能直接匯入；掛到智慧體後，執行時自動同步到執行時。開啟 **Skills** 頁面，剛才匯入的兩個都在，右側是各自掛載的智慧體：

![工作区的 Skills 页面](<../images/e0be7639-image.webp>)

點開能看到 skill 的全部檔案：

![tdd skill 的文件结构](<../images/584fd16a-image.webp>)

這兩個 skill 一個管做事、一個管說話：

-   **tdd** 掛給 Engineer，是工程方法：先寫失敗的測試，再寫恰好讓它通過的實現；
-   **i-have-adhd** 掛給 Lead，是彙報風格：第一行永遠是可執行的下一步，多步驟編號，進度可見。隊長的產出全是發給你的彙報，這個 skill 決定你讀到的樣子。

團隊的工作方式沉澱成 skill，新智慧體掛上就能繼承。匯入也不是唯一來源，**新建 skill** 提供四種方式——手動新建、從本地匯入、從 URL 匯入、從本機執行時複製——這裡不展開，見 [Skills 文件](<58 [01.01.01 GitHub] Skills.md>)：

![新建 skill 的四种方式](<../images/037f11b4-image.jpg>)

匯入第三方 skill 前，先讀一遍它的檔案：Multica 不做沙盒隔離，skill 的內容會原樣交給 AI 程式設計工具。

## [第二條任務：交給小隊](#%E7%AC%AC%E4%BA%8C%E6%9D%A1%E4%BB%BB%E5%8A%A1%E4%BA%A4%E7%BB%99%E5%B0%8F%E9%98%9F)

給小隊一件完整的工作：把網站改成通用模板——真實姓名換成佔位的攝影師名字，真實郵箱換成 `hello@example.com`，佈局和內容結構不動。這次任務不用自己寫：在聊天裡把需求說給 Lead，用**通過智慧體建立**直接建立，負責人是小隊——小隊和智慧體、成員一樣，可以出現在任何負責人位置：

![在聊天中用「通过智能体创建」新建任务](<../images/a41816ba-image.webp>)

生成的任務裡，需求已經被整理成結構化描述；標題旁的徽章顯示隊長已經接手：

![MUL-2：Lead 创建任务并开始工作](<../images/99629d97-image.webp>)

接下來全是隊長的工作。它的派活評論不只是轉發：補上兩條任務裡沒有的約束（佔位身份全站統一、清查範圍列到後設資料和 README），再交給 Engineer。Engineer 完成後，把 PR 回報在同一條時間線裡：

![Lead 派活，Engineer 回报 PR](<../images/16977a71-image.webp>)

審查零發現，Lead 隨即交付：提及你驗收，第一行是結論，往下是 PR 連結、改動說明和兩個需要你判斷的點，結尾一句——你不點頭就不合並：

![Lead 的交付汇报](<../images/f7a4e425-image.webp>)

從整理需求、確認方案、開發、審查到交付彙報，這條任務沒有一步需要你銜接。驗收方式和 MUL-1 相同——也可以讓它啟動本地服務在瀏覽器裡看，不再展開。「已完成」仍然留給你：回覆合併，或手動改狀態。整條時間線的每一步都有記錄，和人類團隊的任務沒有區別——變的只是執行的人。

## [自動化](#%E8%87%AA%E5%8A%A8%E5%8C%96)

到目前為止的每次觸發都由你發起——分配、提及、對話。**自動化**是第四種觸發方式：按時間自動開工。

配置是一句話的事：告訴 Multica helper，每週一早上九點，讓 Reviewer 對網站程式碼庫做一次全面檢查——冗餘和死程式碼、不合理的結構、可以更規範的地方，發現寫進任務評論，不改程式碼：

![helper 创建自动化](<../images/f80ae0a8-image.webp>)

開啟**自動化**頁面，執行者、提示詞和排程（cron + 時區）都已配置好。執行模式有兩種：

-   **建立任務**（預設）：每次觸發先建一條任務，工作落在看板上，歷史、評論和普通任務完全一致；
-   **僅執行**：不建任務直接執行，只在自動化的執行歷史裡留記錄——這次沒發現問題的話，跑完就什麼都不留。

定期檢查用「建立任務」模式。不想等到週一，點**立即執行**觸發一次：

![自动化详情页：调度和立即运行](<../images/2c6dc8b5-image.webp>)

任務隨即建出來，Reviewer 開始檢查。之後每週一到點，同樣的檢查會自動建立新的任務，不再需要任何人觸發：

![自动化创建的任务](<../images/7ab517b2-image.webp>)

觸發器除了定時還支援 webhook，執行者也可以指向小隊，見[自動化文件](<70 [01.01.01 GitHub] 自動化.md>)。

## [多人協作](#%E5%A4%9A%E4%BA%BA%E5%8D%8F%E4%BD%9C)

到這裡，工作區裡的人類成員始終只有你一個。**設定 → 成員**裡用郵箱邀請其他人加入，他們和你一樣建立任務、@ 智慧體、加入小隊——多個人和多個智慧體在同一批任務上協同：

![用邮箱邀请成员加入工作区](<../images/ed9f3326-image.webp>)

## [結語](#%E7%BB%93%E8%AF%AD)

任務多起來之後還有組織它們的工具：**Project** 把相關的任務歸成一組、當成一個單元跟進（見[專案文件](<54 [01.01.01 GitHub] 專案.md>)）；類似的組織方式還在增加，**Space** 也即將就緒。

回頭看這條路徑：從空工作區開始，連上一臺電腦，建起四名智慧體，跑完兩條任務的完整生命週期，再把協調交給隊長、把週期檢查交給自動化。你的參與逐級後撤，最後只剩兩件事：描述需求，驗收結果。

智慧體是一等成員，一切協作都留在任務的時間線裡——這就是 Multica 提供的工作方式。它還在快速迭代，更多能力見[文件](<44 [01.01.01 GitHub] Multica 是人類與 AI 智慧體.md>)。
