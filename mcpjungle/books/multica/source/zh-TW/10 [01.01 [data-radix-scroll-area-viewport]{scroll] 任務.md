# 任務

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>)

任務儲存一項工作的上下文、負責人、狀態和執行記錄。

任務是 Multica 中安排工作的基本單位：一項功能、一個 bug、一次調研，任何需要成員或智慧體負責推進的工作。圍繞它的討論、狀態變化和每次執行都留在同一處，無需再從聊天記錄或終端日誌中拼接上下文。

## 任務的組成

| 內容 | 用途 |
| --- | --- |
| **標題和描述** | 目標、背景、要求和驗收條件。 |
| **狀態和優先順序** | 工作處於哪個階段，先處理什麼。 |
| **負責人** | 工作區成員、智慧體或小隊。 |
| **日期、標籤和自定義屬性** | 計劃、分類和團隊自己的欄位。 |
| **專案和父子關係** | 歸入更大的工作範圍，或拆成子任務。 |
| **動態和執行日誌** | 評論、狀態變化、執行和智慧體返回的結果。 |

## 建立任務

在**任務**頁面或專案中新建，填寫標題即可，其餘屬性隨時補充。

每個任務有一個編號，例如 `MUL-123`。數字在工作區內遞增；管理員修改工作區的任務字首後，編號會用新字首顯示。詳見[工作區](/docs/zh/workspaces#%E5%88%9B%E5%BB%BA%E5%B7%A5%E4%BD%9C%E5%8C%BA)。

## 選擇負責人

| 負責人 | 效果 |
| --- | --- |
| **成員** | 由這位成員負責跟進，不建立執行。 |
| **智慧體** | 為該智慧體建立一次執行。 |
| **小隊** | 由小隊 leader 接收，再決定交給誰處理。 |

分配給智慧體或小隊時，任務不在 `backlog` 就會立即入隊；執行時離線時，執行留在佇列中等待。已歸檔的智慧體和小隊不能被分配。

分配不會繞過智慧體的訪問範圍（Access）；分配給小隊時，校驗的是 leader 的 Access。詳見[分配任務給智慧體](/docs/zh/assigning-issues)。

## 狀態

每個工作區都自帶 7 個內建狀態，歸入 4 個生命週期分類：

| 分類 | 內建狀態 | 含義 |
| --- | --- | --- |
| `unstarted` | `backlog`、`todo` | 還沒開始的工作，不論是已規劃還是暫時擱置。 |
| `started` | `in_progress`、`in_review`、`blocked` | 已經開始、等待檢查，或暫時無法繼續。 |
| `done` | `done` | 順利完成，終態。 |
| `closed` | `cancelled` | 不再繼續，終態，但不算順利完成。 |

分類讓生命週期判斷保持簡單。看板、列表、篩選和排序都按具體狀態來，具體狀態也保留了智慧體和自動化依賴的那些更細的行為。

| 狀態 | 含義 |
| --- | --- |
| `backlog` | 暫不啟動。已分配給智慧體的任務需離開 `backlog` 後才會建立執行。 |
| `todo` | 已明確，等待開始。 |
| `in_progress` | 正在處理。 |
| `in_review` | 已有結果，等待檢查。 |
| `done` | 已完成。 |
| `blocked` | 暫時無法繼續。 |
| `cancelled` | 不再繼續，保留記錄。 |

狀態之間沒有固定流轉，成員和智慧體都可以直接修改。

智慧體隨著工作對任務的實際影響寫入狀態：開始產出任務本身要求的東西時立刻推到 `in_progress`——不論形式是程式碼、調研、設計，還是任務本身要求的 review——讓看板在工作進行中就能反映出來；交付後推到 `in_review`；工作跨輪繼續則保持 `in_progress`；沒有產出本任務交付物的輪次（答疑、給別處的工作做諮詢）則全程不改狀態。這些狀態變更由智慧體在執行中通過 Multica CLI 顯式寫入——執行開始或完成時，服務端不會自動改任務狀態（下面兩個系統例外除外）。`done` 通常留給人工確認，或在工作區設定合併後改為 `done` 時，由關聯 PR 全部合併後系統寫入。

兩個變化由系統執行：

-   執行失敗，且該任務沒有其他執行、也沒有觸發重試時，`in_progress` 回到 `todo`。
-   任務的所有關聯 PR 都合併時，任務改為工作區選定的狀態（預設 `done`），除非工作區設定為不改變，或該任務設定了合併後不改狀態。詳見 [GitHub 整合](/docs/zh/github-integration)。

### 自定義狀態

工作區的 owner 或 admin 可以在**設定 → 任務狀態**裡新增自己的狀態，比如 `Code Review`、`QA`、`Rework`。每個狀態都屬於 4 個生命週期分類之一：

| 分類 | 生命週期含義 |
| --- | --- |
| `unstarted` | 還沒開始，包含內建的 `backlog` 和 `todo`。 |
| `started` | 進行中，包括等待檢查和等待外部回應。 |
| `done` | 順利完成，終態。 |
| `closed` | 取消或不再繼續，終態，但不算順利完成。 |

自定義狀態只繼承生命週期語義，不繼承內建狀態的具體行為。`backlog` 的停車、`in_review` 結束[自動化](/docs/zh/autopilots)執行、`blocked` 的失敗處理、`in_progress` 的失敗回收，這些都不會被繼承——需要哪個行為，就用對應的那個內建狀態。以前建的自定義狀態也按同一套規則：Awaiting Response 算進行中的工作，不會自動結束檢查。分配和建立仍然走通用的智慧體觸發規則。

平臺自己寫入狀態時——失敗回滾到 `todo`、PR 合併置 `done`——寫的都是內建狀態，不會寫成某個自定義狀態。

對已安裝的客戶端，API 裡原有的分類欄位仍然返回 7 值的傳輸列舉。新客戶端會把它歸一成 4 個分類；傳輸值本身從不授予任何行為繼承。資料庫裡只存這 4 個生命週期值。

由此有四點：

-   **狀態一旦建立，分類就不能再改。** 改分類等於悄悄重寫所有已經在該狀態上的任務的行為，所以編輯時分類是隻讀的。先想清楚要什麼行為，再取名字。
-   **按狀態分組用的是具體狀態。** 看板的列、列表的分節、泳道的狀態列，都會把內建狀態和自定義狀態分開。`Code Review` 和 `QA` 各佔一列，即使兩者都屬於 `started`。分類是內部的生命週期劃分，不是用來替代列名的。
-   **內建狀態是鎖死的。** 名稱、顏色、分類都不能改，也不能歸檔——從不開啟這個頁面的工作區，看板和原來一模一樣。
-   **歸檔是停用，不是刪除。** 已經在該狀態上的任務保持不變，名稱、顏色和行為都不變，只是之後再設定狀態時不再出現這個選項。

內建狀態會按介面語言翻譯，自定義狀態則始終顯示你填的名字。API 和 CLI 通過 key 引用它：`multica issue status MUL-42 code_review`。設定頁裡的 key 由名字生成；API 可以顯式指定，省略時才自動生成。無論哪種方式，key 在建立時就定下來了——之後改名字不會改 key。

## 任務與執行

任務是持續存在的工作記錄；[執行](/docs/zh/tasks)是智慧體的一次具體執行。一個任務可以先後產生多次執行——第一次實現、補充修改、再次檢查。執行“已完成”只表示這一次執行結束；任務是否完成，以任務的狀態為準。

## 專案和子任務

一個任務最多屬於一個[專案](/docs/zh/projects)，專案為其中的執行提供共享說明和資源；移到另一個專案不會產生副本。

較大的工作可以拆成子任務：父任務保留整體目標，子任務各自獨立推進。父子狀態互不聯動。

子任務可以設定**階段**（stage），按 1、2、3 分批推進。當前最早未完成階段的全部子任務到達 `done` 或 `cancelled` 時，父任務會收到"子任務完成"通知；父任務的負責人是智慧體時，它會被喚醒並決定是否推進下一階段。未設定階段的子任務視為同一批，全部結束時通知一次。

## 切換檢視

任務頁面提供列表、看板、表格、甘特圖和泳道五種檢視，可按狀態、負責人、專案和其他屬性篩選、排序，展示的都是同一批任務。

## 刪除任務

任何工作區成員都可以刪除任務。

刪除不可恢復：任務及其評論、附件和關聯記錄會被永久移除，尚未結束的執行會被取消。不再繼續時把狀態改為 `cancelled`，討論和結果仍可查閱。
