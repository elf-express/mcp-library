# 自託管 Git 程式碼託管

> 章節：[多重文件](<000 目錄.md#c-1>) › [data-radix-scroll-area-viewport{scrollbar-width:none;-ms-o](<000 目錄.md#c-2>) › [GitHub](<000 目錄.md#c-3>)

為每個工作區連線自託管的 Forgejo、Gitea 或 GitLab 例項，使分支名或標題中帶有任務編號、或正文中在關閉關鍵字後帶有任務編號的 Pull Request / Merge Request 自動關聯到對應任務，在 PR 合併後將任務改為工作區選定的狀態，並展示 CI 狀態。

**僅適用於自部署的 Multica。** 此整合只在你**自己部署 Multica** 時可用，Multica 雲端不提供。這裡的「自託管」指的是 **Multica 本身自部署**——通常是為了讓它能訪問你自己網路內的 Git 例項。需要服務端運維開啟（`MULTICA_VCS_INTEGRATION_ENABLED=true`）並設定 `MULTICA_VCS_SECRET_KEY`；在此之前，設定 → 程式碼裡不會出現該行。

Multica 按工作區連線自託管的 Git 程式碼託管：**Forgejo**、**Gitea** 或 **GitLab**。連線後，任何在分支名或標題中包含任務編號（例如 `MUL-123`）、或在正文的關閉關鍵字後寫出該編號（`Closes MUL-123`）的 Pull Request（GitLab 為 Merge Request）都會**自動關聯**到對應的 [任務](<53 [01.01.01 GitHub] 任務.md>)，出現在任務側欄的 **Pull requests** 中；任務的所有關聯 PR 都合併後，任務會改為工作區選定的狀態（預設「完成」）。head commit 的 CI 會以檢查條的形式顯示在卡片上。

這些程式碼託管與 GitHub 並行工作：一個工作區可任意組合使用。

與 GitHub 不同，這些程式碼託管沒有「App」模型。每個工作區儲存自己的例項地址和訪問令牌，並在其倉庫或組織上註冊 Webhook。令牌和 Webhook 金鑰均加密儲存。

## [前置條件（服務端）](#%E5%89%8D%E7%BD%AE%E6%9D%A1%E4%BB%B6%E6%9C%8D%E5%8A%A1%E7%AB%AF)

先為該部署開啟此整合。它預設關閉，未開啟時該板塊不會出現：

```
MULTICA_VCS_INTEGRATION_ENABLED=true
```

官方自部署 `docker compose` 檔案（`docker-compose.selfhost.yml`）已為你設定好。

再設定一個 base64 編碼的 32 位元組金鑰，供服務端加密儲存的憑據。未設定時，連線表單將不可用。

```
openssl rand -base64 32
```

```
MULTICA_VCS_SECRET_KEY=<base64 32 字节密钥>
```

兩者都必需：開關決定是否提供該功能，金鑰用於加密儲存的令牌與 Webhook 金鑰。連線、Webhook、輪換都要求兩者同時滿足。

設定 `MULTICA_PUBLIC_URL` 為服務端的公網基礎地址，Multica 即可直接給出可貼上的 Webhook 地址；否則介面只顯示 Webhook 路徑，需自行拼接來源地址。

## [連線工作區](#%E8%BF%9E%E6%8E%A5%E5%B7%A5%E4%BD%9C%E5%8C%BA)

1.  在程式碼託管中建立具備倉庫讀取許可權的訪問令牌：

-   **Forgejo / Gitea**：設定 → 應用。
-   **GitLab**：具備 `read_api` 許可權的個人（或群組/專案）訪問令牌。

2.  在 Multica 中開啟 **設定 → 程式碼**，在 **自託管 Git** 一行點選 **連線**。
3.  選擇**提供方**，填寫例項地址（例如 `https://forgejo.example.com`）和訪問令牌，點選 **連線**。Multica 會先用該令牌訪問例項進行校驗，再儲存。
4.  複製連線後顯示的 **Webhook 地址** 與 **Webhook 金鑰**。

Webhook 金鑰只顯示一次，請在離開頁面前複製。重新連線同一例項會輪換令牌與金鑰。

### [例項使用私有 CA](#%E5%AE%9E%E4%BE%8B%E4%BD%BF%E7%94%A8%E7%A7%81%E6%9C%89-ca)

如果點選 **連線** 後提示提供方的證書 "is signed by a certificate authority this server does not trust"，說明例項的 HTTPS 證書由內部 CA 簽發（或是自簽名證書），而 Multica 服務端不信任這個 CA。需要由服務端管理員把該 CA 加入後端的信任庫：使用 Helm 時設定 `backend.extraCACerts.configMap`；使用 Docker Compose 時掛載 CA 並設定 `SSL_CERT_DIR`。具體步驟見 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)。

Multica 不提供跳過證書校驗的選項，因為連線請求會攜帶你的訪問令牌。如果提示證書與主機名不匹配，或證書校驗失敗（例如已過期），需要修復證書本身，信任 CA 解決不了。

## [註冊 Webhook](#%E6%B3%A8%E5%86%8C-webhook)

在倉庫（或組織/群組，以覆蓋所有倉庫）：

**Forgejo / Gitea** —— 設定 → Webhook → 新增 Webhook → Forgejo/Gitea：

-   **目標 URL**：上一步的 Webhook 地址。
-   **HTTP 方法** `POST`，**內容型別** `application/json`。
-   **金鑰**：Webhook 金鑰（用於校驗 `X-Gitea-Signature` HMAC）。
-   **觸發事件**：勾選 **Pull Request**，並勾選 **Commit Status** 以映象 CI。

**GitLab** —— 設定 → Webhooks：

-   **URL**：Webhook 地址。
-   **Secret token**：Webhook 金鑰（作為 `X-Gitlab-Token` 傳送並逐字比對）。
-   **觸發器**：啟用 **Merge request events**，並啟用 **Pipeline events** 以映象 CI。

Multica 會用儲存的金鑰校驗每次投遞，因此沒有匹配金鑰的 Webhook 會被拒絕。

## [映象的內容](#%E9%95%9C%E5%83%8F%E7%9A%84%E5%86%85%E5%AE%B9)

-   **Pull / Merge Request** —— open、closed、merged、draft 狀態，以及作者、分支和（在程式碼託管提供時）diff 統計。
-   **任務關聯** —— 標題或分支中的編號會將 PR 關聯到任務，正文中的編號只有緊跟關閉關鍵字時才會關聯；正文中的普通提及不會建立任何關聯。任務的所有關聯 PR（包括 GitHub 與自託管平臺上的）都合併後，任務會改為工作區選定的狀態，遵循與 [GitHub](<76 [01.01.01 GitHub] GitHub 整合.md>) 相同的設定和規則。連線平臺後，本頁也會顯示同一項 **PR 合併後，任務狀態改為** 設定。
-   **CI** —— Forgejo/Gitea 的提交狀態與 GitLab 的流水線會彙總為 head commit 的通過/失敗/進行中檢查條。

## [智慧體建立 Pull Request](#%E6%99%BA%E8%83%BD%E4%BD%93%E5%88%9B%E5%BB%BA-pull-request)

建立 PR 無需在 Multica 中進行任何程式碼託管配置。智慧體在執行時中檢出倉庫，並使用執行時主機自身的 Git 憑據推送分支和建立 PR。要讓智慧體在某個程式碼託管上工作，確保 daemon 主機能對其完成認證即可——例如 SSH 部署金鑰，或主機 Git 憑據助手中的令牌——再像往常一樣新增倉庫地址。倉庫檢出支援任意 Git URL，因此無需提供方專屬配置。
