 Stalwart 目前已在全球多個生產系統中應用。迄今為止，尚未收到任何因 Stalwart 而導致的資料遺失或系統崩潰的報告。這項記錄充分證明了 Stalwart 作為生產級郵件伺服器解決方案的穩定性和可靠性。

 Users who are considering Stalwart for their production environments are encouraged to join our Discord channel or Reddit. Here, they can directly engage with other users who are actively running Stalwart in their production environments.  然而，需要注意的是，Stalwart 目前仍處於 0.x 版本。任何軟體在早期階段都會經歷這樣的過程，某些方面仍在不斷改進和優化。在達到1.0版本里程碑之前，Stalwart 的資料佈局和設定檔可能會有所變更。這些變更可能需要進行資料遷移或調整設置，使用者應做好準備，以應對這些潛在的更新及其相關要求。

 Stalwart is built upon well-established and proven database systems such as RocksDB, FoundationDB and PostgreSQL. The use of these trusted database systems ensures that Stalwart has a strong and reliable foundation for data storage and management. These databases are widely recognized for their stability, security, and performance, contributing significantly to the overall safety of data within Stalwart.

 Stalwart 建構於成熟可靠的資料庫系統之上，例如 RocksDB、FoundationDB 和 PostgreSQL。這些值得信賴的資料庫系統確保了 Stalwart 擁有強大可靠的資料儲存和管理基礎。這些資料庫以其穩定性、安全性和高效能而廣受認可，為 Stalwart 的資料安全做出了重要貢獻。

 In addition to this, before each release, Stalwart undergoes extensive stress testing. This testing is crucial to identify and resolve any issues related to concurrency or other potential problems that could lead to data loss. The stress tests simulate various operational conditions, including high-load scenarios and concurrent access, to ensure that Stalwart can handle real-world demands without compromising data integrity or system stability.

 此外，每次發布前，Stalwart 都會進行全面的壓力測試。這項測試至關重要，它可以識別並解決任何與同時發生或其他可能導致資料遺失的潛在問題。壓力測試模擬各種運行條件，包括高負載場景和並發訪問，以確保 Stalwart 能夠應對實際應用需求，同時確保資料完整性和系統穩定性。

## Management｜管理

### How do I create and manage users?｜如何建立和管理使用者？

 It depends on the directory backend you are using. If you are using the internal directory, you can create and manage users using the web-admin interface. If you are using an external directory such as LDAP or SQL, you will need to use the tools provided by that directory server.

 這取決於您使用的目錄後端。如果您使用的是內部目錄 ，則可以使用Web管理介面建立和管理使用者。如果您使用的是外部目錄，例如LDAP或SQL ，則需要使用該目錄伺服器提供的工具。

### How do I add a new domain?｜如何新增網域？

 Domains are managed independently of the directory backend. A new domain is created from the web-admin interface \(Management › Domains › Domains\), which stores it as a Domain object and exposes the per-domain settings for recipient resolution, DKIM signing, TLS certificate issuance, and DNS record publication. The Domain record is required even when accounts are stored in an external LDAP or SQL directory; those backends provide account authentication only.

 網域的管理獨立於目錄後端。新網域透過 web-admin介面（管理 › 網域 › 網域）創建，該介面將其儲存為 Domain對象，並公開每個網域的收件者解析、 DKIM簽章、 TLS DNS 。即使帳戶儲存在外部 LDAP或 SQL目錄中，也需要網域記錄；這些後端僅提供帳戶驗證。

 Sending mail from a new domain does not require any additional configuration. To improve deliverability, a new DKIM key should be generated, published in DNS, and enabled for signing on the new domain.

 從新網域發送郵件不需要任何額外的配置。為了提高郵件送達率，需要\([https://stalw.art/docs/mta/authentication/dkim/sign#publishing-dkim-keys\)新網域上產生一個新的DKIM金鑰\(https://stalw.art/docs/mta/authentication/dkim/sign#generating-keys\)](https://stalw.art/docs/mta/authentication/dkim/sign#publishing-dkim-keys%2529%2525E6%252596%2525B0%2525E7%2525B6%2525B2%2525E5%25259F%25259F%2525E4%2525B8%25258A%2525E7%252594%2525A2%2525E7%252594%25259F%2525E4%2525B8%252580%2525E5%252580%25258B%2525E6%252596%2525B0%2525E7%25259A%252584DKIM%2525E9%252587%252591%2525E9%252591%2525B0%2528https://stalw.art/docs/mta/authentication/dkim/sign#generating-keys%2529) ，並在DNS中發布，並啟用簽署功能\([https://stalw.art/docs/mta/authentication/dkim/sign#multiple-domains](https://stalw.art/docs/mta/authentication/dkim/sign#multiple-domains)\) 。

## Encryption｜加密

### What is encryption at rest?｜什麼是靜態加密？

 Encryption at rest refers to the process of encrypting data when it is stored, or “at rest”, on the disk. In Stalwart, this feature provides the ability to automatically encrypt plain-text messages using either PGP or S/MIME before they are written to disk.

 靜態加密是指在資料儲存於磁碟（即「靜止」）時對其進行加密的過程。在 Stalwart 中，此功能允許在將明文訊息寫入磁碟之前，使用PGP或 S/ MIME自動對其進行加密。

### Is encryption at rest enabled by default?｜預設是否啟用靜態資料加密？

 Yes, encryption at rest is enabled by default and is activated when the user uploads their S/MIME certificate or PGP public key. However, it can be disabled by setting the `email.encryption.enable` attribute to `false`.

 是的，靜態資料加密預設為啟用，並在使用者上傳其 S/ MIME憑證或PGP公鑰時啟動。但是，可以透過將`email.encryption.enable`屬性設為`false`來停用它。

### How do I enable or disable encryption at rest?｜如何啟用或停用靜態資料加密？

 Users can enable or disable encryption at rest using a web interface that is available under “/crypto” on the same port where the JMAP server is listening. The interface asks for the login name, password, encryption method to use \(S/MIME or PGP\), and to select the file containing the certificates or public keys. To disable encryption, select the “Disable Encryption”（停用加密） option from the dropdown and then click “Update”（更新）.

 使用者可以透過位於伺服器監聽連接埠「/crypto」下的 Web 介面啟用或停用靜態資料加密。此介面會要求輸入登入名稱、密碼、加密方法（S/ MIME或PGP ），並選擇包含憑證或公鑰的檔案。若要停用加密，請從下拉式選單中選擇“Disable Encryption”（停用加密）選項，然後“Update”（更新） JMAP

### What happens when encryption at rest is enabled?｜啟用靜態資料加密會發生什麼情況？

 Once encryption at rest is enabled, all incoming emails are automatically encrypted before they are written to disk. Not even the system administrator is able to decrypt these messages as they are encrypted with the PGP public key or S/MIME certificate provided by the user.

 啟用靜態加密後，所有傳入的電子郵件在寫入磁碟之前都會自動加密。即使是系統管理員也無法解密這些郵件，因為它們是使用使用者提供的PGP公鑰或S/ MIME憑證加密的。

### What encryption methods are supported?｜支援哪些加密方式？

 Stalwart supports two encryption methods: PGP \(using either AES256 or AES128 symmetric encryption\) and S/MIME \(using either AES256-CBC or AES128-CBC symmetric encryption\).

 Stalwart 支援兩種加密方法： PGP （使用AES256或AES128對稱加密）和 S/ MIME （使用AES256-CBC或AES128-CBC對稱加密）。

### What format should the S/MIME certificates or PGP keys be in when uploaded?｜上傳時，S/ MIME憑證或PGP金鑰應採用何種格式？

 S/MIME certificates can be imported in DER or PEM formats. However, if importing multiple certificates, they must be in PEM format. PGP public keys can be imported in raw format or as an ASCII-armored text file containing one or multiple public keys.

 S/ MIME憑證可以以DER或PEM格式匯入。但是，如果匯入多個證書，則它們必須採用PEM格式PGP公鑰可以以原始格式匯入，也可以作為包含一個或多個公鑰的ASCII加密文字檔案匯入。

### I have enabled encryption at rest. How can I test if it’s working?｜我已經啟用了靜態資料加密。如何測試它是否生效？

 Once you have enabled encryption at rest, it is recommended that you send a test email to yourself. This allows you to confirm that your email client can properly decrypt the message.

 啟用靜態加密後，建議您傳送一封測試郵件給自己。這樣可以確認您的郵件用戶端能夠正確解密郵件。

## Spam & Phishing Filter｜垃圾郵件和釣魚過濾

### What makes Stalwart’s Spam filter different from other solutions?｜Stalwart的垃圾郵件過濾器與其他解決方案有何不同？

 Stalwart’s spam filter is built-in and doesn’t require any third-party software. It’s designed for speed and efficiency, keeping messages within the server during the filtering process. It offers filtering rules on par with popular solutions like RSpamd and SpamAssassin.

 Stalwart 的垃圾郵件過濾器是內建的，無需任何第三方軟體。它以速度和效率為設計目標，在過濾過程中將郵件保留在伺服器端。它提供的過濾規則與 RSpamd 和 SpamAssassin 等熱門解決方案不相上下。

### How does the spam classifier work?｜垃圾郵件分類器的工作原理是什麼？

 Our spam classifier uses the FTRL-Proximal algorithm and feature hashing. It automatically trains itself, ensuring improved accuracy over time.

 我們的垃圾郵件分類器採用FTRL近端演算法和特徵哈希技術。它能夠自動進行自我訓練，從而確保隨著時間的推移不斷提高準確率。

### How does Stalwart handle phishing attempts?｜Stalwart 如何處理網路釣魚攻擊？

 Stalwart provides phishing protection by checking against databases like OpenPhish and PhishTank, identifying homographic URL attacks, sender spoofing, and other deceptive techniques. It also detects and flags suspicious URL patterns.

 Stalwart 透過比對 OpenPhish 和 PhishTank 等資料庫，提供網路釣魚防護，辨識同形異義URL攻擊、寄件者欺騙和其他欺騙性技術。它還能偵測並標記可疑的URL模式。

### What are DNSBLs, and why are they important?｜什麼是DNSBL？它們為什麼重要？

 DNS Blocklists \(DNSBLs\) are databases that track IP addresses known for sending spam. Stalwart checks IP addresses, domains, and even hashes against several DNSBLs to filter out potential spam sources.

 DNS 阻止清單 \(DNSBL\) 是追蹤已知發送垃圾郵件的 IP 位址的資料庫。 Stalwart 根據多個 DNSBL 檢查 IP 位址、網域，甚至是哈希值，以過濾掉潛在的垃圾郵件來源。

### How can I customize the spam filter settings?｜如何自訂垃圾郵件過濾器設定？

 Administrators can easily customize settings from the web-admin or, for advanced users, the `spam-filter` Sieve script.

 管理員可以透過 web-admin輕鬆自訂設置，或者，對於高級用戶，可以使用`spam-filter` Sieve 腳本進行自訂。

### What is greylisting, and how does it help?｜什麼是灰名單？它有什麼作用？

 Greylisting temporarily defers emails from unknown senders. If the sender is legitimate, they’ll typically resend the email after a short delay, whereas most spammers won’t. This process helps in reducing spam.

 灰名單機制會暫時封鎖來自未知寄件者的電子郵件。如果寄件者是合法的，他們通常會在短暫延遲後重新發送郵件，而大多數垃圾郵件發送者則不會。此過程有助於減少垃圾郵件。

### How can I set up spam traps?｜如何設置垃圾郵件陷阱？

 You can set up decoy email addresses to catch and analyze spam. Any messages sent to these addresses are considered spam. The list of spamtrap email addresses can be managed from the web-admin.

 您可以設定誘餌電子郵件地址來捕獲和分析垃圾郵件。發送到這些地址的任何郵件都將被視為垃圾郵件。垃圾郵件陷阱電子郵件地址清單可以在 web-admin中進行管理。

### I’ve heard about sender reputation tracking. How does that work in Stalwart?｜我聽說過發件人信譽追蹤。它在 Stalwart 中是如何運作的？

 Stalwart tracks the previous spam scores of senders based on their IP address, ASN, domain, and email address. It uses this data to adjust the spam score of incoming messages, helping in more accurate spam identification.

 Stalwart 會根據寄件者的IP地址、 ASN地址、網域名稱和電子郵件地址追蹤其先前的垃圾郵件評分。它利用這些數據調整收到的郵件的垃圾郵件評分，從而幫助更準確地識別垃圾郵件。

### Does Stalwart support collaborative spam filtering mechanisms like Pyzor?｜Stalwart 是否支援像 Pyzor 這樣的協同垃圾郵件過濾機制？

 Yes\! Stalwart integrates with collaborative digest-based spam filtering tools like Pyzor to enhance its spam detection capabilities.

 是的！ Stalwart 可以與 Pyzor 等基於協作摘要的垃圾郵件過濾工具集成，以增強其垃圾郵件偵測能力。

## Setup & WebUI｜設定和 WebUI

### Why does `/admin` return `404 Not Found`?｜為什麼`/admin`會回`404 Not Found` ？

 The WebUI is delivered as a downloadable Application bundle that the server fetches from `https://github.com/stalwartlabs/webui/releases/latest/` on first start, then refreshes on a schedule. When that initial download fails \(no outbound HTTPS, GitHub blocked, restrictive proxy\), the bundle is never unpacked and every WebUI route returns 404. Verify the host can reach `github.com` and `objects.githubusercontent.com` on TCP/443. For air-gapped deployments, host the bundle on an internal HTTPS server and update the resourceUrl field on the WebUI’s Application record to point at it. After one successful download, subsequent failures are non-fatal: the previously installed bundle keeps serving until the next refresh succeeds.

 WebUI 以可下載的 Application包的形式提供，伺服器在首次啟動時從`https://github.com/stalwartlabs/webui/releases/latest/`獲取該包，然後按計劃刷新。如果初始下載失敗（無出站HTTPS連線、GitHub 被封鎖、代理限制），則該套件不會被解壓，所有 WebUI 路由均傳回 404 錯誤。請驗證主機是否可以透過TCP /443 存取`github.com`和`objects.githubusercontent.com` 。對於實體隔離部署，請將該套件託管在內部HTTPS伺服器上，並更新 WebUI 的 Application記錄中的 resourceUrl字段，使其指向該伺服器。一次成功下載後，後續的下載失敗不會造成致命後果：先前安裝的套件將繼續提供服務，直到下次刷新成功為止。

### Why does the root URL `/` return `404`?｜為什麼根URL `/`回傳`404` ？

 There is no page mounted at the root. The WebUI lives at `/admin`, the per-user portal at `/account`, and the JMAP endpoint at `/jmap`. Configure the reverse proxy or browser bookmark to point at `/admin` directly, or add a redirect from `/`.

 根目錄下沒有掛載任何頁面。 WebUI 位於`/admin` ，使用者入口網站位於`/account` ， JMAP端點位於`/jmap` 。請配置反向代理或瀏覽器書籤直接指向`/admin` ，或新增從`/`重定向。

### Why is sign-in stuck in a loop or showing a basic-auth dialog?｜為什麼登入頁面一直卡在循環中或顯示基本驗證對話框？

 Almost always one of the following:

 幾乎總是以下情況之一：

- The browser is on `http://` while the configured hostname is announced over `https://`. Open the page over HTTPS, or use `http://<host>:8080/admin` while TLS is being put in place.
瀏覽器位於`http://` ，而配置的主機名稱正在透過`https://`廣播。透過HTTPS開啟頁面，或在TLS就位時使用`http://<host>:8080/admin` 。
- The browser cached an earlier visit on the wrong scheme. Clear the site’s history or use a private window.
瀏覽器快取了先前使用錯誤協定的存取記錄。請清除網站記錄或使用隱私瀏覽視窗。
- A reverse proxy is terminating HTTPS but talking HTTP upstream and the discovery URLs end up pointing at the wrong scheme or port. See Reverse proxy › Overview for the supported patterns and the STALWART\_PUBLIC\_URL variable.
反向代理正在終止HTTPS連接，但仍在與上游通訊HTTP ，導致發現 URL 指向錯誤的協定或連接埠。請參閱 反向代理 › 概述以了解支援的模式和 STALWART\_PUBLIC\_URL變數。
### Can I reach the WebUI by IP address?｜我可以透過IP位址存取WebUI嗎？

 The OAuth flow used by the WebUI binds to the configured `defaultHostname` over HTTPS. Loading the WebUI by IP, by container name, or over plain HTTP appears to load the page but fails at the OAuth callback. Use the configured hostname over HTTPS, or sign in at `http://<host>:8080/admin` \(which is exempt from the hostname check\) until TLS is in place.

 WebUI 使用的 OAuth 流程透過HTTPS綁定到已配置的`defaultHostname` 。透過IP 、容器名稱或直接透過HTTP載入 WebUI 頁面看似已加載，但在 OAuth 回呼處失敗。請使用透過HTTPS配置的主機名稱登錄，或在`http://<host>:8080/admin`登入（該連接埠不受主機名稱檢查限制），直到TLS就緒。

### No log files appear under `/var/log/stalwart`. What’s wrong?｜`/var/log/stalwart`目錄下沒有出現日誌檔。這是怎麼回事？

 Three causes, in descending order of frequency:

 三種原因，依發生頻率降序排列：

1. The directory does not exist or is not writable by the service user. On the binary install, `/var/log/stalwart` is created at install time and owned by `stalwart:stalwart`. On Docker, mount a host directory and `chown 2000:2000 <dir>` before starting the container.
該目錄不存在或服務使用者無寫入權限。在二進位安裝中， `/var/log/stalwart`在安裝時創建，所有者為`stalwart:stalwart` 。在 Docker 中，啟動容器前，請掛載主機目錄和`chown 2000:2000 <dir>` 。
2. The configured tracer points at *Console* \(intentional in containers, so logs surface through the orchestrator’s log driver\). Inspect *Telemetry → Tracers* in the WebUI to confirm the destination.
配置的追蹤器指向 *控制台*（在容器中這樣做是有意為之，以便日誌能夠透過編排器的日誌驅動程式顯示出來）。請在 WebUI 中檢查 *遙測 → 追蹤器* 以確認目標位置。
3. The tracer’s path was misconfigured. Reset by deleting the tracer and recreating it from defaults at *Telemetry → Tracers → New*.
追蹤器的路徑配置錯誤。請刪除該追蹤器，然後從預設設定重新創建，路徑為：*遙測 → 追蹤器 → 新建*。
### My reverse proxy’s IP keeps getting banned. What do I do?｜我的反向代理伺服器IP一直被封鎖。我該怎麼辦？

 When the proxy does not forward the real client IP, every request appears to come from the proxy and Stalwart’s automatic banning then locks the proxy out, which in turn locks every user out. Either mark the proxy’s IP as a trusted network so banning is skipped for requests from that IP and configure the proxy to forward the real client IP via PROXY protocol or `X-Forwarded-For` \(then enable the matching reader on the listener\), or raise the auto-ban threshold for the HTTP listener. See Proxy Protocol for the recommended pattern.

 當代理程式不轉送真實客戶端IP請求時，所有請求都會顯示為來自代理，Stalwart 的自動封禁機制會鎖定該代理，進而導致所有使用者都被鎖定。您可以將代理程式的IP標記為受信任網絡，這樣來自該IP請求就不會被封禁，並將代理配置為透過PROXY協定或`X-Forwarded-For`轉發真實客戶端IP的請求（然後在監聽器上啟用匹配的讀取器），或提高HTTP監聽器的自動封禁閾值。有關建議的模式，請參閱 代理協議 。

### What outbound HTTPS does Stalwart need?｜Stalwart 需要多少出站HTTPS ？

 A fresh install reaches out to:

 新安裝的系統會連接到：

- `github.com` and `objects.githubusercontent.com`: for the WebUI bundle on first start and on the periodic refresh, and for the spam-filter rule list and Apple Push Notification \(APN\) endpoint list, both fetched from the same release storage.
`github.com`和`objects.githubusercontent.com` ：用於首次啟動和定期刷新時的 WebUI 包，以及垃圾郵件過濾器規則列表和 Apple 推送通知 \( APN \) 端點列表，兩者均從同一發布存儲中獲取。
- `acme-v02.api.letsencrypt.org` \(or whichever ACME directory is configured\): for TLS certificate issuance.
`acme-v02.api.letsencrypt.org` （或任何配置的ACME目錄）：用於TLS證書頒發。
- The DNS provider’s API: when *automatic DNS management* is enabled.
DNS提供者的API ：當啟用 *自動DNS管理* 時。
- The OIDC provider’s well-known and userinfo endpoints: when an OIDC directory is configured.
OIDC提供者的知名端點和使用者資訊端點：當配置OIDC目錄時。
In restricted-egress environments, allow at minimum the GitHub hosts above; otherwise the WebUI never appears, the spam classifier runs without its fetched rule lists, and APN-based push notifications stop working. See WebUI overview for the full list and for hosting the bundle internally.
 在限制出站存取的環境中，至少應允許上述 GitHub 主機；否則，WebUI 將不會顯示，垃圾郵件分類器將無法取得規則列表，並且基於APN的推播通知將停止運作。有關完整清單以及內部託管軟體包的信息，請參閱 WebUI 概述 。
