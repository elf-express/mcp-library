# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[cluster｜簇\\\]\\\(&lt;000 目錄.md#c-12&gt;\\\) › \\\[coordination｜協調\\\]\\\(&lt;000 目錄.md#c-14&gt;\\\)

Coordination is the process by which nodes in a distributed system exchange information, maintain consistency, and respond collectively to changes within the cluster. In Stalwart, coordination keeps every server instance aware of the state of the others, so the cluster behaves as a unified system even when composed of many independent nodes.

 協調是指分散式系統中節點交換資訊、維護一致性並對群集內部變化做出集體回應的過程。在 Stalwart 中，協調機制確保每個伺服器實例都能感知其他實例的狀態，因此即使叢集由許多獨立節點組成，也能作為一個統一的系統運作。

 When running in a clustered environment, Stalwart nodes must communicate to share internal updates and detect failures in real time. This communication keeps service responsive regardless of which node a user is connected to. For example, when a user is connected to an IMAP session via node A and a change occurs in their mailbox on node B, the change must reach node A so the user can be notified via an IDLE response. The IMAP IDLE command allows clients to maintain a persistent connection and receive immediate updates about mailbox changes without polling.

 在叢集環境中運行時，Stalwart 節點必須進行通訊以共享內部更新並即時檢測故障。無論使用者連接到哪個節點，這種通訊都能保持服務回應。例如，當使用者透過節點 A 連接到 IMAP 會話，且節點 B 上的郵箱發生變更時，該變更必須到達節點 A，以便可以透過 IDLE 回應通知使用者。 IMAP IDLE 指令允許客戶端保持持久連線並立即接收有關郵箱變更的更新，而無需輪詢。

 Push notifications work in a similar way. If a user is subscribed to notifications on one node, but their mailbox activity is processed on another, coordination routes and delivers the notification correctly.

 推播通知的工作原理類似。如果使用者在一個節點上訂閱了通知，但他們的郵箱活動是在另一個節點上處理的，協調機制會路由路由並正確傳遞通知。

 Coordination is also used for internal housekeeping across the cluster. When one server blocks an IP address because of suspicious activity, the update propagates to the rest of the cluster so security enforcement stays consistent. When a new ACME TLS certificate is issued, the cluster distributes it so every server reloads and applies the new certificate automatically.

 集群內部的協調機制也用於集群內部的日常維護。當一台伺服器因可疑活動而封鎖某個IP位址時，該更新會傳播到叢集中的其他伺服器，從而確保安全策略的一致性。當頒發新的ACME TLS憑證時，叢集會將其分發，以便每台伺服器自動重新載入並套用新憑證。

 These examples show why coordination matters for consistency, security, and real-time responsiveness in a distributed Stalwart deployment.

 這些例子表明，在分散式 Stalwart 部署中，協調對於一致性、安全性和即時回應能力至關重要。

## Coordination mechanisms｜協調機制

 Stalwart supports multiple coordination backends, so administrators can choose one that fits the environment and scale. The options are:

 Stalwart 支援多種協調後端，管理員可以根據環境和擴展需求選擇合適的後端。可選後端包括：

- Peer-to-peer: no central coordinator; each node communicates directly with its peers using a decentralised protocol powered by Eclipse Zenoh. This removes external dependencies while still providing real-time coordination across nodes.
點對點 ：無中央協調器；每個節點使用由 Eclipse Zenoh 提供支援的去中心化協定直接與其他節點通訊。這消除了對外部的依賴，同時仍能實現節點間的即時協調。
- Apache Kafka / Redpanda: a distributed event streaming platform suited to large volumes of messages. In a Stalwart cluster, Kafka acts as the message bus for update propagation and event coordination.
Apache Kafka / Redpanda ：一個適用於海量訊息的分散式事件流平台。在 Stalwart 叢集中，Kafka 充當訊息總線，用於更新傳播和事件協調。
- NATS: a lightweight and high-performance messaging system, well-suited to clusters that need real-time messaging without the complexity of Kafka. It provides publish/subscribe semantics with low latency and low overhead.
NATS ：一個輕量級、高效能的訊息系統，非常適合需要即時訊息但又不想使用 Kafka 的複雜系統的叢集。它提供發布/訂閱語義，具有低延遲和低開銷。
- Redis: commonly used as an in-memory key-value store, Redis also supports pub/sub messaging. Stalwart can use Redis for cluster coordination, especially in environments where Redis is already used to hold ephemeral state, avoiding an additional coordination service.
Redis ：Redis 通常用作內存鍵值存儲，也支援發布/訂閱訊息機制。 Stalwart 可以使用 Redis 進行叢集協調，尤其是在 Redis 已用於儲存臨時狀態的環境中，從而避免額外的協調服務。
Each backend corresponds to a variant on the Coordinator singleton \(found in the WebUI under Settings › Cluster › Coordinator\). Configuration details for each variant are covered in the dedicated subsections.
 每個後端對應於 Coordinator單例的變體（可在 WebUI 的「設定」&gt;「叢集」&gt;「Coordinator」中找到）。每個變體的配置詳情將在相應的子章節中介紹。

## Choosing a coordination mechanism｜選擇協調機制

 The choice of coordination mechanism depends on the size and nature of the deployment and on operational preferences.

 協調機制的選擇取決於部署的規模和性質以及操作偏好。

 Peer-to-peer coordination suits small clusters or environments where simplicity is a priority. It removes the need to provision or manage an external coordination service. Because the coordination duties are handled inside the mail server process, this approach adds a modest amount of processing to each node.

 點對點協調適用於小型群集或以簡潔性為優先考慮的環境。它無需配置或管理外部協調服務。由於協調任務在郵件伺服器進程內部處理，因此這種方法只會為每個節點增加少量的處理能力。

 For very large deployments, especially those processing millions of messages per second, Apache Kafka or Redpanda is preferred. These platforms are built for high-throughput, durable event streaming and offer strong delivery and partitioning guarantees across large clusters.

 對於超大規模部署，尤其是每秒處理數百萬條訊息的部署，Apache Kafka 或 Redpanda是首選。這些平台專為高吞吐量、持久化的事件流而構建，並可在大型叢集中提供強大的交付和分區保證。

 For medium-sized deployments, NATS balances performance with operational simplicity. It has lower latency and simpler configuration than Kafka while still scaling to handle high messaging volumes.

 對於中等規模的部署，NATS在效能和運維簡易性之間取得了平衡。它比 Kafka 具有更低的延遲和更簡單​​的配置，同時也能擴展以處理高訊息量。

 Redis is a viable coordination option for small to medium clusters, especially where Redis is already used by Stalwart for in-memory ephemeral data. Redis does not scale as well as Kafka or NATS in high-throughput environments, but reusing an existing component can reduce complexity.

 對於中小型叢集而言，Redis是一個可行的協調方案，尤其適用於 Stalwart 已經使用 Redis 來儲存記憶體中的暫存資料的情況。在高吞吐量環境下，Redis 的擴展性不如 Kafka 或NATS ，但重複使用現有元件可以降低複雜性。

 The choice of coordination mechanism should be guided by expected cluster size, message volume, operational overhead, and existing infrastructure.

 協調機制的選擇應以預期叢集規模、訊息量、操作開銷和現有基礎設施為指導。

## Topic name｜主題名稱

 Stalwart uses the `stwt.agora` topic name for all coordination messages. The same topic name applies to every coordination backend, including peer-to-peer, Kafka, NATS, and Redis. This topic name is not configurable, so it should not be reused by other services to prevent conflicts with Stalwart internal coordination messages.

 Stalwart 使用`stwt.agora`主題名來傳送所有協調訊息。此主題名適用於所有協調後端，包括對等網路、Kafka、 NATS和 Redis。此主題名稱不可配置，因此其他服務不應重複使用，以免與 Stalwart 內部協調訊息發生衝突。
