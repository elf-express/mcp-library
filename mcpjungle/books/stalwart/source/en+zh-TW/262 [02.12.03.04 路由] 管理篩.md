# ManageSieve｜管理篩

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[routing｜路由\\\]\\\(&lt;000 目錄.md#c-46&gt;\\\)

The ManageSieve listener lets clients manage Sieve scripts on the resolved backend. It is typically served with STARTTLS on port 4190. As with the other interactive protocols, the proxy answers the pre-authentication dialogue itself and bridges the session once the backend accepts the replayed authentication.

 ManageSieve 監聽器可讓客戶端管理已解析後端上的 Sieve 腳本。它通常透過STARTTLS在 4190 連接埠上提供服務。與其他互動式協定一樣，代理伺服器會自行回應預先身份驗證對話，並在後端接受重播身份驗證後建立會話。

## Pre-authentication｜預認證

 ManageSieve begins with the server announcing its capabilities, so on connection the proxy sends a capability block followed by an `OK` line. The block is built from `[capabilities.managesieve]` and reports the implementation string, the protocol version, the advertised SASL mechanisms, the supported Sieve extensions from the `sieve` list, and, on a STARTTLS listener before the upgrade, `STARTTLS`. Before authentication the proxy handles `CAPABILITY` \(re-sending the block\), `NOOP`, `LOGOUT`, and `STARTTLS`.

 ManageSieve 首先由伺服器宣告其功能，因此在連線建立時，代理程式會傳送一個功能區塊，後面跟著一行`OK` 。此功能塊由`[capabilities.managesieve]`建構而成，報告實作字串、協定版本、已通告的SASL機制、 `sieve`列表中支援的 Sieve 擴展，以及升級前的STARTTLS監聽器上，也會報告`STARTTLS` 。在驗證之前，代理程式會處理`CAPABILITY` （重新傳送功能區塊）、 `NOOP`, `LOGOUT`和`STARTTLS` 。

## Authentication｜驗證

 Authentication uses the `AUTHENTICATE` command with a SASL mechanism, one of `PLAIN`, `LOGIN`, `OAUTHBEARER` or `XOAUTH2`. The SASL initial response may be supplied inline, as a quoted string, or as a literal after the proxy’s continuation prompt, following the ManageSieve literal syntax. With `LOGIN`, the proxy issues the base64 `Username:` and `Password:` challenges as literals and reconstructs the answers as a `PLAIN` challenge, so the backend leg only ever sees `PLAIN`. Cleartext `PLAIN` and `LOGIN` authentication is gated on transport security and refused until the connection is encrypted unless `allow_plain_auth_without_tls` is set. The routing identifier is extracted from the credentials as described under Routing.

 驗證使用 `AUTHENTICATE` 指令和 SASL 機制，`PLAIN`, `LOGIN`, `OAUTHBEARER` 或 `XOAUTH2` 之一。 SASL 初始回應可以內聯提供，作為引號的字串，或作為代理繼續提示後的文字，遵循 ManageSieve 文字語法。使用`LOGIN`，代理將base64`Username:`和`Password:`挑戰作為文字發出，並將答案重建為`PLAIN`挑戰，因此後端腿只能看到`PLAIN`。明文 `PLAIN` 和 `LOGIN` 身份驗證在傳輸安全性上受到限制，並且在連接加密之前被拒絕，除非設定了 `allow_plain_auth_without_tls`。路由標識符是從憑證中提取的，如 路由 中所述。

## Backend handshake｜後端握手

 The proxy connects to the destination’s ManageSieve endpoint and reads the backend’s capability block. On a STARTTLS endpoint it confirms the backend advertises `STARTTLS`, issues the command, upgrades the connection, and reads the refreshed capabilities. It then verifies the backend leg is encrypted.

 代理連接到目標端的 ManageSieve 端點，並讀取後端的功能區塊。在STARTTLS端點上，它確認後端通告了`STARTTLS` ，發出命令，升級連接，並讀取更新後的功能。然後，它驗證後端連結是否已加密。

 When the destination uses `XCLIENT` forwarding and the backend advertised `XCLIENT`, the proxy issues an `XCLIENT` command carrying the client and destination addresses, a session identifier and the transport security before authenticating. It then replays the client’s `AUTHENTICATE` command, relays the result, and bridges the session on success.

 當目標伺服器使用`XCLIENT`轉發且後端伺服器通告了`XCLIENT`轉送時，代理伺服器會在進行驗證之前發出`XCLIENT`命令，該命令攜帶用戶端和目標位址、會話標識符以及傳輸安全訊息。然後，代理伺服器重播客戶端的`AUTHENTICATE`指令，轉送結果，並在成功後建立會話。
