# DATA stage｜DATA階段

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[mta｜捷運\\\]\\\(&lt;000 目錄.md#c-47&gt;\\\) › \\\[inbound｜入站\\\]\\\(&lt;000 目錄.md#c-51&gt;\\\)

The `DATA` command initiates the data transfer phase of message delivery. Once the sender has successfully completed the `MAIL FROM` and `RCPT TO` commands, the `DATA` \(or `BDAT` when chunking is used\) command begins transmission of the message. After the message has been transmitted, the server responds with a status code indicating whether it was accepted or rejected.

`DATA`指令啟動訊息傳遞的資料傳輸階段。發送方成功完成`MAIL FROM`和`RCPT TO`指令後， `DATA` （或使用分塊傳輸時為`BDAT` ）指令開始傳送訊息。訊息傳輸完成後，伺服器會傳回一個狀態碼，指示訊息是被接受還是被拒絕。

 DATA-stage behaviour is configured on the MtaStageData singleton \(found in the WebUI under Settings › MTA › Session › DATA Stage\).

 DATA -階段行為在 MtaStageData單例上配置（在 WebUI 的設定 › MTA › 會話 › DATA階段下找到）。

## Message filtering｜訊息過濾

 Once a message has been submitted with `DATA` or `BDAT`, it is possible to run Sieve scripts, Milter filters, or MTA Hooks that accept, reject, or modify the message. When multiple filter types are configured, Stalwart executes Milter filters first, then MTA Hooks, and finally Sieve scripts. The Sieve script receives the message with any changes made by Milter filters and MTA Hooks already applied.

 使用`DATA`或`BDAT`提交訊息後，即可執行 Sieve 腳本 、Milter 過濾器或 MTA鉤子來接受、拒絕或修改訊息。配置多種過濾器類型時，Stalwart 會先執行 Milter 過濾器，然後執行MTA鉤子，最後執行 Sieve 腳本。 Sieve 腳本接收的訊息已套用了 Milter 過濾器和MTA鉤子所做的任何變更。

### Sieve｜篩

 The script field selects the Sieve script to run for the DATA stage. Sieve can rewrite the message, add or remove headers, process each MIME part, and apply conditional actions using the full set of supported Sieve extensions.

 script字段選擇要為DATA階段運行的 Sieve 腳本可以重寫訊息、新增或刪除標頭、處理每個MIME部分，並使用所有支援的 Sieve 擴充應用條件操作。

 For example, setting script to the expression `"'data'"` runs a Sieve script named `data` which can iterate over MIME parts and rewrite their contents:

 例如，將 script設定為表達式`"'data'"`會執行一個名為`data`的 Sieve 腳本，該腳本可以遍歷MIME個部分並重寫其內容：

```sieve
require ["envelope", "variables", "replace", "mime", "foreverypart", "editheader", "extracttext"];

if envelope :domain :is "to" "foobar.net" {
    set "counter" "a";
    foreverypart {
        if header :mime :contenttype "content-type" "text/html" {
            extracttext :upper "text_content";
            replace "${text_content}";
        }
        set :length "part_num" "${counter}";
        addheader :last "X-Part-Number" "${part_num}";
        set "counter" "${counter}a";
    }
}
```

### Milter｜軍隊

 Milter filters are defined as MtaMilter objects. Each configured filter can inspect and potentially modify the message, adding, changing, or removing headers, altering the body, or rejecting the message outright. For details see the Milter section.

 Milter 過濾器被定義為 MtaMilter物件。每個已配置的過濾器都可以檢查並可能修改郵件，例如新增、變更或刪除郵件頭、修改郵件正文，或直接拒絕郵件。詳情請參閱 Milter部分。

### MTA Hooks｜MTA掛鉤

 MTA Hooks provide an HTTP-based alternative to milter. They are defined as MtaHook objects and can inspect or modify messages through a JSON protocol. For details see the MTA Hooks section.

 MTA鉤子提供了一個基於HTTP milter 替代方案。它們被定義為 MtaHook對象，並且可以透過JSON協定檢查或修改訊息。有關詳細信息，請參閱 MTA鉤子部分。

## Spam filtering｜垃圾郵件過濾

 Whether to run the spam filter on incoming messages is controlled by enableSpamFilter, an expression that returns a boolean. The default policy enables the filter for unauthenticated sessions \(`is_empty(authenticated_as)`\). To restrict filtering to a specific listener only:

 是否對傳入郵件運行垃圾郵件過濾器由enableSpamFilter控制，該表達式傳回布林值。預設策略對未經驗證的會話啟用過濾器\( `is_empty(authenticated_as)` \)。若要將過濾限制為僅針對特定監聽器：

```json
{
  "enableSpamFilter": {"else": "listener == 'smtp'"}
}
```

## Message limits｜訊息限制

 Message limits prevent abusive use of a single session and protect against message loops. Relevant fields are maxMessages \(maximum number of messages per SMTP session, default 10\), maxMessageSize \(maximum size of a single message in bytes, default 104857600, 100 MB\), and maxReceivedHeaders \(maximum number of `Received` headers allowed in a message, which helps prevent message loops, default 50\):

 訊息限制可防止濫用單一會話並防止訊息循環。相關欄位包括 maxMessages （每個SMTP的最大訊息數，預設值為 10）、maxMessageSize （單一訊息的最大大小，以位元組為單位，預設值為 104857600 MB `maxReceivedHeaders` \]\([https://stalw.art/docs/ref/object/mta-stage-data#maxreceivedheaders](https://stalw.art/docs/ref/object/mta-stage-data#maxreceivedheaders)\) （訊息中允許的最大`Received`頭數，有助於防止訊息循環，預設值為 50）：

```json
{
  "maxMessages": {"else": "10"},
  "maxMessageSize": {"else": "104857600"},
  "maxReceivedHeaders": {"else": "50"}
}
```

## Headers｜標題

 Headers automatically added to accepted messages are controlled by the following fields, each an expression returning a boolean unless noted:

 自動新增至已接收郵件中的標頭由下列欄位控制，除非另有說明，否則每個欄位都是傳回布林值的運算式：

- addReceivedHeader: add a `Received` header containing the client IP address and TLS information.
addReceivedHeader : 新增包含客戶端IP位址和TLS訊息的`Received`標頭。
- addReceivedSpfHeader: add a `Received-SPF` header with SPF results.
addReceivedSpfHeader : 新增`Received-SPF`標頭，包含SPF結果。
- addAuthResultsHeader: add an `Authentication-Results` header with DMARC, DKIM, SPF, ARC, and iprev results.
addAuthResultsHeader : 添加`Authentication-Results`標頭，包含DMARC, DKIM, SPF, ARC和 iprev 結果。
- addMessageIdHeader: add a `Message-ID` header when the message lacks one.
addMessageIdHeader : 當郵件缺少`Message-ID`標頭時，加入此標頭。
- addDateHeader: add a `Date` header when the message lacks one.
addDateHeader : 當郵件缺少`Date`標頭時，加入此標頭。
- addReturnPathHeader: add a `Return-Path` header containing the address specified in `MAIL FROM`.
addReturnPathHeader : 新增一個`Return-Path`標頭，其中包含`MAIL FROM`中指定的位址。
- addDeliveredToHeader: add a `Delivered-To` header containing the recipient address. This field is a plain boolean; default `true`.
addDeliveredToHeader : 新增包含收件人地址的`Delivered-To`標頭。此欄位為純布林值；預設值為`true` 。
The default policy for every expression-valued header is to add it only when `local_port == 25`. The following example adds `Received`, `Received-SPF`, and `Authentication-Results` on the SMTP listener; lets submission listeners generate `Message-ID` and `Date` when absent; always adds `Delivered-To`; and never adds `Return-Path`:
 對於每個表達式值標頭，預設策略是僅當存在`local_port == 25`時才新增。以下範例在SMTP監聽器上新增`Received`, `Received-SPF`和`Authentication-Results` ；允許提交監聽器在`Message-ID`和`Date`不存在時產生它們；始終添加`Delivered-To` ；並且從不添加`Return-Path`

```json
{
  "addReceivedHeader": {
    "match": {"0": {"if": "listener == 'smtp'", "then": "true"}},
    "else": "false"
  },
  "addReceivedSpfHeader": {
    "match": {"0": {"if": "listener == 'smtp'", "then": "true"}},
    "else": "false"
  },
  "addAuthResultsHeader": {
    "match": {"0": {"if": "listener == 'smtp'", "then": "true"}},
    "else": "false"
  },
  "addMessageIdHeader": {
    "match": {"0": {"if": "listener == 'smtp'", "then": "false"}},
    "else": "true"
  },
  "addDateHeader": {
    "match": {"0": {"if": "listener == 'smtp'", "then": "false"}},
    "else": "true"
  },
  "addReturnPathHeader": {"else": "false"},
  "addDeliveredToHeader": true
}
```
