# Destinations｜目的地

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\)

A destination describes one backend the proxy can route to. It bundles together the host to connect to, the per-protocol ports and TLS modes that host listens on, how the proxy authenticates the backend’s certificate, and how the real client’s identity is conveyed to that backend. Every routing decision the proxy makes resolves to the name of a destination, and the mapping and routing layers ultimately exist to pick which destination handles each account.

 目標位址描述了代理伺服器可以路由到的後端伺服器。它包含了要連接的主機、主機監聽的協定連接埠和TLS模式、代理伺服器如何驗證後端伺服器的證書，以及如何將真實客戶端的身份傳遞給後端伺服器。代理伺服器所做的每個路由決策都會解析為一個目標位址的名稱，而映射和路由層最終用於選擇哪個目標位址來處理每個帳戶。

 Destinations are declared as named tables, where the name is the identifier referenced by `routing.default_destination`, by mapping entries, and by HTTP routes:

 目的地被宣告為命名表，其中名稱是`routing.default_destination` 、映射條目和HTTP路由所引用的標識符：

```toml
[destination.legacy]
host = "10.0.1.10"
tls_server_name = "mail.legacy.example.com"
proxy_protocol = true

[destination.legacy.protocol.imap]
port = 993
tls = "implicit"

[destination.legacy.protocol.submission]
port = 587
tls = "starttls"
```

## Host and endpoints｜主機和端點

 The `host` key gives the backend address as either a hostname or a literal IP address. When a hostname is supplied, the proxy resolves it at connection time, which allows the underlying address to change without restarting the proxy.

`host`鍵提供後端位址，可以是主機名，也可以是IP位址。如果提供的是主機名，代理程式會在連接時解析它，這樣底層位址就可以更改而無需重啟代理。

 Each protocol the backend serves is declared as a sub-table under `protocol`, naming the port and the TLS mode for that leg. The recognized protocols are `imap`, `pop3`, `managesieve`, `submission`, `smtp`, `lmtp` and `http`. The TLS mode is one of:

 後端支援的TLS協定都宣告為`protocol`下的子表，其中列出了連接埠號碼和該連結的TLS模式。已識別的協議包括`imap`, `pop3`, `managesieve`, `submission`, `smtp`, `lmtp`和`http`模式為下列之一：

- `implicit`: the proxy opens a TLS connection directly to the backend port.
`implicit` ：代理直接開啟到後端連接埠的TLS連接。
- `starttls`: the proxy connects in cleartext and issues the protocol’s STARTTLS command to upgrade the connection before sending credentials.
`starttls` ：代理以明文連接，並在發送憑證之前發出協議的STARTTLS命令來升級連接。
- `plain`: the proxy connects in cleartext and does not upgrade.
`plain` ：代理以明文連接，不會升級。
A destination only needs to declare the protocols it will actually receive. The default destination must declare every interactive protocol that any listener accepts, since a connection that resolves to no explicit mapping falls back to it; this is enforced at startup.
 目標位址只需聲明它實際接收的協定即可。預設目標位址必須聲明所有監聽器接受的互動式協議，因為如果連接解析到沒有明確映射的協議，則會回退到該預設目標位址；此規則在啟動時強制執行。

```toml
[destination.legacy.protocol.pop3]
port = 995
tls = "implicit"

[destination.legacy.protocol.managesieve]
port = 4190
tls = "starttls"

[destination.legacy.protocol.http]
port = 443
tls = "implicit"
```

## Backend certificate verification｜後端證書驗證

 By default the proxy verifies each backend’s TLS certificate against the host’s platform trust store, exactly as an ordinary client would, using the expected server name. The expected name is taken from `tls_server_name` if set, otherwise from `host`. When the host is given as an IP address and any of its legs use TLS, `tls_server_name` is required, because an IP address cannot be matched against a certificate’s subject names; this is checked at startup.

 預設情況下，代理會根據主機的平台信任儲存來驗證每個後端的 TLS 證書，就像一般用戶端一樣，使用預期的伺服器名稱。若設定的話，預期名稱取自`tls_server_name`，否則取自`host`。當主機作為 IP 位址給出且其任何分支時，需要使用TLS, `tls_server_name`，因為 IP 位址無法與憑證的使用者名稱相符；這是在啟動時檢查的。

```toml
[destination.new]
host = "10.0.1.20"
tls_server_name = "mail.new.example.com"
```

Two alternatives to platform verification are available for backends whose certificates are not issued by a public authority:

 對於憑證並非由公共機構核發的後端伺服器，有兩種替代平台驗證的方法：

- `tls_pinned_cert_sha256` pins the backend to a specific certificate by its SHA-256 fingerprint, given as 64 hexadecimal characters \(colons are permitted and ignored\). The connection succeeds only if the backend presents exactly that certificate. This is the recommended way to authenticate a backend that uses a self-signed or privately issued certificate.
`tls_pinned_cert_sha256`透過後端憑證的SHA -256 指紋（64 個十六進位字符，允許使用冒號，但會被忽略）將後端憑證綁定到特定憑證。只有當後端提供的憑證與該指紋完全一致時，連線才能成功。這是一種驗證使用自簽名憑證或私下頒發憑證的後端憑證的建議方法。
- `tls_allow_invalid_certs` disables certificate verification entirely.
`tls_allow_invalid_certs`完全禁用憑證驗證。

```toml
[destination.new]
host = "10.0.1.20"
tls_server_name = "mail.new.example.com"
tls_pinned_cert_sha256 = "aa:bb:cc:dd:..."
```

Setting `tls_allow_invalid_certs = true` makes the proxy-to-backend leg unauthenticated, which means real client credentials are forwarded over a connection that could be intercepted by a machine-in-the-middle. The proxy logs a warning at startup for every destination with this flag set. It is acceptable only on a trusted, isolated network segment, and certificate pinning should be preferred wherever possible.

 設定`tls_allow_invalid_certs = true`會使代理到後端的連線未經驗證，這表示真實的用戶端憑證會透過可能被中間人攔截的連線來轉送。代理程式會在啟動時針對每個設定了此標誌的目標位址記錄警告。此設定僅適用於受信任的、隔離的網路段，並且應盡可能優先使用憑證綁定。

 When the backend requires mutual TLS, a client certificate and key are supplied with `tls_client_cert` and `tls_client_key`; both must be set together.

 當後端需要相互TLS時，客戶端憑證和金鑰會與`tls_client_cert`和`tls_client_key`一起提供；兩者必須同時設定。

## Client identity forwarding｜客戶端身份轉發

 Because the proxy terminates the client connection and opens a fresh one to the backend, the backend would otherwise see the proxy’s address rather than the client’s. Two independent mechanisms convey the real client identity, selected per destination by the `forwarding` key \(and, for the PROXY protocol, by `proxy_protocol`\):

 由於代理會終止客戶端連接並開啟新的後端連接，否則後端看到的將是代理的地址而不是客戶端的地址。有兩種獨立的機制傳遞真實的客戶端身份，每個目標地址的客戶端身份由`forwarding`金鑰選擇（對於PROXY協議，則由`proxy_protocol`金鑰選擇）：

- `forwarding = "proxy"` prefixes the backend connection with a PROXY protocol v2 header carrying the original source and destination addresses. This is the appropriate choice for Stalwart backends and any server that understands the PROXY protocol.
`forwarding = "proxy"`在後端連接前新增一個PROXY協定 v2 頭部，其中包含原始來源位址和目標位址。這對於 Stalwart 後端以及任何支援PROXY協定的伺服器來說都是合適的選擇。
- `forwarding = "xclient"` instead announces the client over the application protocol itself, using the `XCLIENT` command for SMTP, POP3 and ManageSieve, and the `ID` command for IMAP. This is the appropriate choice for Dovecot and Postfix backends.
`forwarding = "xclient"`則透過應用層協定本身來通告客戶端，對於SMTP, POP3和 ManageSieve 使用`XCLIENT`指令，對於IMAP使用`ID`指令。這對於 Dovecot 和 Postfix 後端來說是合適的選擇。
- `forwarding = "none"` sends no client metadata.
`forwarding = "none"`不發送客戶端元資料。
When `forwarding` is not set, the proxy infers a mode from `proxy_protocol`: if `proxy_protocol = true` \(the default\) it behaves as `proxy`, otherwise as `none`. A `forwarding` value may also be overridden for an individual protocol leg inside its `[destination.<id>.protocol.]` table. The mechanics of each mode, including which attributes are sent, are detailed under Routing.
 當未設定`forwarding`時，代理從`proxy_protocol`推斷模式：若`proxy_protocol = true`（預設），則其行為為`proxy`，否則為`none`。 `forwarding` 值也可以被其 `[destination.<id>.protocol.<proto>]` 表內的單一協議段覆蓋。每種模式的機制，包括發送哪些屬性，詳見路由。

 For HTTP destinations, the `forwarded` boolean controls whether the proxy appends the client address to the `Forwarded` and `X-Forwarded-For` request headers before relaying to the backend. This is separate from the PROXY protocol and is the usual way to convey the client address to an HTTP/JMAP backend.

 對於HTTP目標， `forwarded`布爾值控制代理是否在將請求轉送到後端之前，將客戶端位址附加到`Forwarded`和`X-Forwarded-For`請求頭中。這與PROXY協定無關，是向HTTP/JMAP後端傳遞客戶端位址的常用方法。

## Plaintext credentials｜明文憑證

 Several protocols carry credentials in the clear once the connection is established. To prevent passwords from being forwarded over an unencrypted backend leg, the proxy refuses, at startup, any destination that exposes a credential-bearing protocol \(IMAP, POP3, ManageSieve, submission or HTTP\) with `tls = "plain"`, unless `allow_plaintext_auth = true` is set on that destination. Even with the override in place, the proxy still asserts at connection time that the egress leg is encrypted before sending credentials, so the override is meant for backends reached over an already-secure channel such as a loopback interface or an encrypted tunnel.

 某些協定在連線建立後會以明文形式傳輸憑證。為了防止密碼透過未加密的後端連結，代理程式會在啟動時拒絕任何暴露帶有憑證的協定（ IMAP, POP3 、ManageSieve、submission 或HTTP ）的目標位址，除非該目標位址設定了`tls = "plain"` 。即使啟用了此`allow_plaintext_auth = true`設置，代理程式仍然會在連接時斷言出口連結已加密，然後再發送憑證。因此，此覆蓋設定僅適用於透過已安全的通道（例如環回介面或加密隧道）存取的後端。

```toml
[destination.local]
host = "127.0.0.1"
allow_plaintext_auth = true

[destination.local.protocol.imap]
port = 143
tls = "plain"
```

## Health and resilience｜健康與韌性

 Each destination has an associated health state that acts as a circuit breaker. When a backend connection fails, the destination’s consecutive-failure counter is incremented; once it reaches `server.host_down_threshold`, the destination is marked down for `server.host_down_cooldown`, during which new connections to it are rejected immediately rather than waiting for a timeout. The first connection after the cooldown elapses is allowed through as a probe, and a success resets the counter. Setting the threshold to `0` disables this behavior. The current health of every destination is visible through the management API, which can also reset a destination’s health on demand.

 每個目標伺服器都有一個關聯的健康狀態，起到斷路器的作用。當後端連線失敗時，目標伺服器的連續失敗計數器會遞增；一旦達到`server.host_down_threshold` ，該目標伺服器將被標記為處於`server.host_down_cooldown`狀態，在此期間，所有新的連線都會立即被拒絕，而不是等待逾時。冷卻時間結束後，第一個連接會被允許作為探測連接通過，如果連接成功，計數器將被重置。將閾值設為`0`可以停用此行為。每個目標伺服器的目前健康狀態都可以透過管理API查看，也可以根據需要重設目標伺服器的健康狀態。

 Not every failed backend connection is evidence that the backend is unhealthy. A backend that has banned an abusive client address rejects precisely those connections the proxy opens on that client’s behalf, because the proxy forwards the real client address; the backend is behaving correctly and is serving every other account normally. To keep a single client from taking a destination offline for everyone, the proxy classifies each failure by the stage it occurred at. A failure while connecting to the host \(DNS resolution, the TCP connection itself, or the overall establishment timeout\) happens before the backend learns which client is behind the proxy, so it counts as host-level evidence and reaches the threshold on its own. A failure after that point \(the TLS handshake, the greeting, or the backend closing the connection\) is attributed to the client that triggered it, and such failures mark the destination down only once the streak spans at least `server.host_down_min_clients` distinct client addresses. A genuine outage affects every client and still trips the breaker after `host_down_threshold` failures; a banned or misbehaving client never does. Setting `host_down_min_clients = 0` restores counting by failures alone.

 並非所有後端連線失敗都表示後端運作不正常。如果後端已封鎖某個惡意用戶端位址，則會拒絕代理伺服器代表該用戶端建立的連接，因為代理伺服器會轉送真實的用戶端位址；後端運作正常，能夠為其他所有帳號提供服務。為了防止單一客戶端導致目標伺服器對所有使用者離線，代理伺服器會根據故障發生的階段對其進行分類。連接主機時發生的故障（ DNS解析、 TCP連線本身或整體建立逾時）發生在後端伺服器獲知代理伺服器背後的客戶端之前，因此屬於主機層級的故障，並自行達到閾值。此後發生的故障（ TLS握手、問候或後端關閉連接）則歸因於觸發故障的客戶端，並且只有當連續故障跨越至少`server.host_down_min_clients`個不同的客戶端位址時，才會將目標伺服器標記為離線。真正的網路中斷會影響所有客戶端，並且在發生`host_down_threshold`故障後仍然會導致斷路器跳閘；被封鎖或行為異常的客戶端則不會。設定`host_down_min_clients = 0`可以恢復僅根據故障次數進行計數。

 The number of distinct client addresses in the current failure streak is reported as `failure_sources` by the management API, alongside `host_level_failure`, which indicates whether the streak includes a connect-stage failure. A destination showing a climbing failure counter with `failure_sources` stuck at 1 is being hit by one banned or broken client, not by a failing backend.

 當前故障連發中不同客戶端位址的數量由管理指標API報告為`failure_sources` ，同時`host_level_failure`則指示該連發是否包含連接階段故障。如果目標位址的故障計數器持續上升，而`failure_sources`一直停留在1，則表示該目標位址正受到某個被封鎖或損壞的客戶端的攻擊，而非後端伺服器故障。

 Within the `backend_timeout` window, a connection attempt that fails for a retryable reason is retried up to `server.backend_connect_retries` times with a short delay between attempts. When the backend ultimately cannot be reached, the client receives a protocol-appropriate temporary-failure response rather than an abrupt disconnect.

 在`backend_timeout`視窗內，如果連線嘗試因可重試的原因而失敗，則會重試最多`server.backend_connect_retries`次，每次重試之間會有短暫的延遲。如果最終無法連接到後端，客戶端將收到符合協定的臨時故障回應，而不是突然斷開連線。

## Source addresses｜來源位址

 The `source_ips` key pins the local address the proxy binds before connecting to the backend. When more than one address is listed, the proxy selects among those matching the backend’s address family in round-robin fashion, which spreads outbound connections across several local addresses. This is useful when the backend applies per-source connection limits or when outbound traffic must originate from specific addresses for firewall or routing reasons.

`source_ips`鍵用於鎖定代理伺服器在連接後端之前綁定的本地位址。如果列出了多個位址，代理伺服器會以輪詢方式從與後端位址族相符的位址中選擇，從而將出站連線分散到多個本機位址。當後端伺服器對每個來源的連線數有限制，或出於防火牆或路由原因，出站流量必須來自特定位址時，此功能非常有用。

```toml
[destination.legacy]
host = "10.0.1.10"
source_ips = ["10.0.2.5", "10.0.2.6"]
```

## Hiding backend authentication errors｜隱藏後端身份驗證錯誤

 By default, when the backend rejects the replayed authentication, the proxy passes the backend’s failure response back to the client verbatim. Setting `hide_auth_errors = true` on a destination replaces the backend’s message with a generic authentication-failure response for the protocol in use. This prevents a backend from leaking distinguishing details \(such as whether an account exists\) through its error text, at the cost of less specific diagnostics for legitimate users.

 預設情況下，當後端拒絕重播的身份驗證時，代理會將後端的失敗回應原封不動地傳回給客戶端。在目標端設定`hide_auth_errors = true`會將後端訊息替換為目前所用協定的通用身份驗證失敗回應。這可以防止後端透過錯誤文字外洩區分性資訊（例如帳戶是否存在），但代價是合法用戶獲得的診斷資訊不夠具體。
