# Configuring the proxy｜配置代理

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[guide｜指導\\\]\\\(&lt;000 目錄.md#c-38&gt;\\\)

The proxy is what makes the source and the new deployment appear as a single server to clients. It terminates every protocol on the public ports, identifies the account behind each connection, and forwards the session to whichever server currently holds that account. This step writes its configuration but does not start it; like the previous steps, it has no effect on existing clients and carries no downtime.

 代理伺服器的作用是使來源伺服器和新部署的伺服器對客戶端看起來像是同一個伺服器。它會終止公共連接埠上的所有協議，識別每個連接背後的帳戶，並將會話轉發到目前持有該帳戶的伺服器。此步驟會寫入其配置，但不會啟動代理伺服器；與先前的步驟一樣，它不會影響現有客戶端，也不會造成任何停機時間。

 This page explains the decisions behind it and the operational pieces that have to be put in place around it. A complete, annotated configuration is published for each source, and a ready-to-edit copy ships in the proxy repository. The general reference for every option is the proxy configuration section.

 本頁面解釋了背後的決策以及圍繞這些決策需要部署的操作元件。每個來源都發布了完整的帶註釋的配置，代理存儲庫中也提供了一個可直接編輯的副本。所有選項的通用參考是代理 配置部分。

**Older Stalwart**

**資深中堅份子**

 The configuration for two Stalwart deployments is published as the Upgrading Stalwart example, and a ready-to-edit copy ships as [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.stalwart-upgrade.toml). Its two destinations are named `old` and `new`, which are the destination names used throughout the rest of this guide.

 兩個 Stalwart 部署的配置已發佈為 升級 Stalwart範例，並提供了一個可編輯的副本，編號為 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.stalwart-upgrade.toml) 。其兩個目標位置分別命名為`old`和`new` ，這也是本指南其餘部分所使用的目標位置名稱。

**Dovecot / Postfix**

 The configuration for a Dovecot and Postfix source is published as the Migrating from Dovecot example, and a ready-to-edit copy ships as [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.dovecot-postfix.toml). Its two destinations are named `legacy` \(the source\) and `stalwart` \(the new deployment\); wherever the rest of this guide names the destinations `old` and `new`, substitute `legacy` and `stalwart`.

 Dovecot 和 Postfix 來源的配置已發佈為 從 Dovecot 遷移範例，並提供可編輯的副本作為 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.dovecot-postfix.toml)提供。其兩個目標分別命名為`legacy` （源）和`stalwart` （新部署）；本指南其餘部分中凡是目標名稱為`old`和`new`地方，請替換為`legacy`和`stalwart` 。

## Shape of the configuration｜配置形狀

 Three choices define the migration topology and are worth understanding before editing the file.

 三個選擇定義了遷移拓撲結構，在編輯檔案之前值得了解這些選擇。

 The default destination is the source. Routing is driven by a mapping table that lists, for each account, which server holds it, and any account absent from the table resolves to this default. At the start of the migration the table is empty and every account therefore resolves to the source, which is correct because that is where every account still lives.

 預設目標伺服器是來源伺服器。路由由一個映射表驅動，該表列出了每個帳戶所在的伺服器，任何不在表中的帳戶都會解析到此預設值。遷移開始時，該表為空，因此每個帳戶都會解析到來源伺服器，這是正確的，因為所有帳戶仍然位於來源伺服器上。

 The pass-through destination for raw SMTP is the new deployment. Port 25 carries no login to route on, so it is handed in its entirety to a single backend. Directing it to the new server is what allows split delivery to work, since the new server is the one configured to deliver locally or relay as appropriate. This is independent of the per-account routing that governs the interactive protocols.

 原始資料SMTP的直通目標是新部署的伺服器。連接埠25不承載任何登入訊息，因此所有數據都直接傳遞給單一後端伺服器。正是由於新伺服器配置為根據情況進行本地傳輸或中繼，才使得拆分傳輸得以實現。這與管理互動式協定的按帳戶路由無關。

 How the proxy announces each connection to its backends, and what HTTP routing it needs, depends on the source:

 代理如何向其後端通告每個連接，以及它需要哪些HTTP路由，取決於來源：

**Older Stalwart**

**資深中堅份子**

 Both backends are addressed with `forwarding = "proxy"` and `proxy_protocol = true`, so the proxy announces the real client to each Stalwart deployment over a PROXY protocol header, matching the trust configured on the servers. On the HTTP leg, `forwarded = true` records the client address in the `Forwarded` and `X-Forwarded-For` headers.

 兩個後端都使用`forwarding = "proxy"`和`proxy_protocol = true`進行尋址，因此代理透過PROXY協定頭向每個 Stalwart 部署通告真實客戶端，以符合伺服器上配置的信任關係。在HTTP連結中， `forwarded = true`將客戶端位址記錄在`Forwarded`和`X-Forwarded-For`標頭中。

 Because both deployments serve HTTP and JMAP, the configuration includes HTTP routing rules, described in detail in the example. In summary, the few login and discovery paths that are unique to each Stalwart version are pinned to the deployment that serves them, the shared OAuth token endpoint is split by the web client it came from, and every other request is routed by the account its credentials identify.

 由於兩個部署都服務於HTTP和JMAP ，因此配置中包含HTTP路由規則，具體內容請參考範例。簡而言之，每個 Stalwart 版本特有的少數登入和發現路徑被綁定到服務它們的部署，共享的 OAuth 令牌端點根據其來源的 Web 用戶端進行劃分，而所有其他請求則根據其憑證所標識的帳戶進行路由。

**Dovecot / Postfix**

 The new Stalwart backend is addressed with `forwarding = "proxy"` and `proxy_protocol = true`, and `forwarded = true` on its HTTP leg, so the proxy announces the real client to it over a PROXY protocol header. The source backend instead uses `forwarding = "xclient"`, because Dovecot and Postfix learn the real client address from the XCLIENT command and the IMAP ID rather than from a PROXY header. This matches the XCLIENT trust configured on the source.

 新的 Stalwart 後端使用`forwarding = "proxy"`和`proxy_protocol = true`進行尋址，其HTTP鏈路使用`forwarded = true` ，因此代理透過PROXY協定頭向其通告真實客戶端位址。來源後端則使用`forwarding = "xclient"` ，因為 Dovecot 和 Postfix 從XCLIENT指令和IMAP ID而不是PROXY頭部取得真實客戶端位址。這與源端配置的XCLIENT信任相符。

 Dovecot and Postfix serve no HTTP or JMAP, so there are no per-source web paths to pin and no HTTP routing rules are needed for the source. All HTTP and JMAP belong to the new server, which serves the web interface once accounts begin to move; an HTTP listener routing entirely to the new deployment can be added when a single hostname for web access is wanted, and can be omitted until then.

 Dovecot 和 Postfix 不提供HTTP或JMAP服務，因此無需為每個來源設定 Web 路徑，也無需為來源配置HTTP路由規則。所有HTTP和JMAP都屬於新伺服器，該伺服器會在帳戶開始遷移後提供 Web 介面服務；如果需要使用單一主機名稱進行 Web 訪問，則可以新增一個HTTP監聽器，將其路由到新部署；在此之前，可以省略此監聽器。

## Mapping file｜映射文件

 The mapping file is the live record of which accounts have been migrated. It is referenced from the configuration, and its initial contents depend on whether the source serves a web interface that has to be reachable from the start:

 映射檔案即時記錄了哪些帳戶已移轉。它在配置中被引用，其初始內容取決於來源是否提供必須從一開始就可存取的 Web 介面：

**Older Stalwart**

**資深中堅份子**

 The file starts out containing only the two entries that let the web interfaces sign in, which map each version’s OAuth client to its deployment:

 文件最初只包含兩個條目，用於讓 Web 介面登錄，這兩個條目將每個版本的 OAuth 用戶端映射到其部署：

```
webadmin          old
stalwart-webui    new
```

**Dovecot / Postfix**

 The file starts out empty, because the source serves no web interface that needs routing. Every account therefore falls through to the default destination, the source, until it is migrated:

 該檔案初始為空，因為來源端沒有需要路由的 Web 介面。因此，所有帳戶都會預設路由到來源端，直到遷移完成為止：

```
# identifier              destination
```

No account entries are added yet. Accounts are added to this file, or set through the management API, as they are migrated, which the migration step covers. Keeping the file under version control or a backup is worthwhile, because it is the authoritative list of what has moved.

 目前尚未新增任何帳戶條目。帳戶會隨著遷移過程添加到此文件中，或透過管理步驟API進行設置，遷移過程由 遷移步驟涵蓋。對該檔案進行版本控製或備份非常重要，因為它是已遷移內容的權威清單。

## Certificates and the public hostname｜憑證和公共主機名

 The proxy presents a certificate to clients for the public hostname they already use, so the certificate and key for that hostname are placed where the configuration expects them. This is the same certificate the source presents today; reusing it means clients see no change. The proxy terminates both implicit TLS and STARTTLS with it.

 代理伺服器會向用戶端提供其已使用的公共主機名稱的證書，因此該主機名稱的證書和金鑰會放置在配置預期的位置。這與來源伺服器目前提供的憑證相同；重複使用該憑證意味著客戶端不會感受到任何變更。代理伺服器會使用此憑證終止隱式的TLS和STARTTLS連線。

 The public hostname itself is not repointed at the proxy yet. That repointing, whether through DNS or by moving the address, happens at the cutover, so that the switch from the source to the proxy is a single deliberate action.

 公用主機名稱本身尚未重新指向代理伺服器。無論是透過DNS或透過移動位址，重新指向代理伺服器的操作都會在切換時進行，因此從來源伺服器到代理伺服器的切換是一次性的明確操作。

## Management endpoint｜管理端點

 The proxy exposes a small management API, protected by a bearer token, for changing mappings, invalidating caches and disconnecting accounts. A token of at least the configured minimum length is generated and stored in the file the configuration names, and the endpoint is bound to a loopback or management-only address. The migration step uses this API to cut accounts over, so confirming the token works against the running proxy is part of the next stage.

 代理伺服器公開了一個受持有者令牌保護的小型管理介面API ，用於更改映射、使快取失效和斷開帳戶連線。系統會產生一個長度至少達到配置最小值的令牌，並將其儲存在設定檔中，該介面綁定到一個回環位址或僅用於管理的位址。遷移步驟使用此API來切換帳戶，因此，確認令牌對正在運行的代理伺服器有效是下一階段的工作內容。

## Rollback｜復原

 The proxy has only been configured, not started, and the public hostname still resolves to the source, so there is nothing serving clients to roll back. Abandoning the migration here means the configuration file is simply never used. The proxy is first put into the serving path in the next step, which is also where the rollback procedure for a live proxy is described.

 代理伺服器僅已配置，尚未啟動，公網主機名稱仍解析到來源伺服器，因此無需回滾任何用戶端服務。在此處放棄遷移意味著設定檔將永遠不會被使用。下一步會將代理伺服器加入到服務路徑中，同時也會介紹運行中代理伺服器的回溯流程。
