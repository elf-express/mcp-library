# Search store｜搜尋商店

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[storage｜貯存\\\]\\\(&lt;000 目錄.md#c-72&gt;\\\)

Full-text search \(FTS\) indexes message bodies, attachments, contacts, and calendar events so that search queries return quickly across large mailboxes. The backend used for full-text indexing is configured independently from the data store, allowing the search engine to be chosen to match query volume, language requirements, and operational constraints.

 全文搜尋 \( FTS \) 會對郵件正文、附件、聯絡人和日曆事件進行索引，從而確保在大郵箱中也能快速返回搜尋結果。用於全文索引的後端獨立於資料儲存進行配置，因此可以根據查詢量、語言要求和操作限制選擇合適的搜尋引擎。

 Backend selection is made on the SearchStore singleton \(found in the WebUI under Settings › Storage › Search Store\). The object is a multi-variant type. The supported variants are:

 後端選擇在 SearchStore單例物件上進行（可在 WebUI 的「設定」&gt;「儲存」&gt;「搜尋儲存」中找到）。該物件為多變體類型。支持的變體包括：

- ElasticSearch: a distributed, RESTful search engine.
ElasticSearch ：一個分散式、RESTful 搜尋引擎。
- Meilisearch: a fast, relevance-focused search engine with minimal configuration.
美利搜尋 : 一款速度快、相關性高的搜尋引擎，配置極少。
- The `Default` variant, which uses the configured data store as the full-text index. Supported for all data store variants, it stores indexes directly in the database using bloom filters.
`Default`變體使用已配置的資料儲存作為全文索引。它支援所有資料儲存變體，並使用布隆過濾器將索引直接儲存在資料庫中。
- FoundationDB, PostgreSQL, and MySQL may also be selected as dedicated search backends when their indexing characteristics are preferred.
當需要優先考慮索引特性時，也可以選擇 FoundationDB、PostgreSQL 和 MySQL 作為專用搜尋後端。
## Choosing a search store｜選擇搜尋商店

 The internal \(data-store-backed\) full-text index offers several advantages:

 內部（資料儲存支援的）全文索引有以下幾個優點：

- **Privacy**: indexes are kept in the database using bloom filters, a space-efficient probabilistic data structure that allows membership testing without exposing indexed tokens directly. While bloom filters do not encrypt data, they obscure individual terms.
**隱私保護**：資料庫中的索引使用布隆過濾器進行儲存。布隆過濾器是一種節省空間的機率資料結構，允許在不直接暴露索引詞項的情況下進行成員資格測試。雖然布隆過濾器不會加密數據，但它會模糊單字項。
- **Automatic multi-language support**: message language is detected before indexing, and a language-appropriate analyser is applied.
**自動多語言支援**：在建立索引之前偵測訊息語言，並套用對應的語言分析器。
- **Simplicity**: no additional services are required.
**簡單易用**：無需額外服務。
External engines offer their own strengths:
 外置引擎具有其自身的優勢：

- **Advanced text analysis and relevance scoring**: synonyms, custom analysers, and sophisticated ranking algorithms.
**進階文字分析和相關性評分**：同義詞、自訂分析器和複雜的排名演算法。
- **Ranking and sorting flexibility**: more control over how results are ordered, combining text relevance with structured fields.
**排名和排序的彈性**：對結果的排序方式有更大的控制權，將文字相關性與結構化欄位結合。
- **Storage efficiency**: purpose-built index structures designed for full-text search.
**儲存效率**：專為全文搜尋而設計的專用索引結構。
When encryption at rest is enabled, only message headers are stored in the full-text index.
 啟用 靜態加密時，全文索引中僅儲存訊息標頭。

### Limitations｜限制

 Every FTS backend involves trade-offs. No single engine is optimal for every deployment; each backend makes design choices that affect scalability, accuracy, resource usage, and query expressiveness. Administrators should consider these in the context of expected mail volume, query patterns, and operational constraints.

 每個FTS後端都存在權衡取捨。沒有哪個引擎能夠完美適用於所有部署；每個後端的設計選擇都會影響可擴展性、準確性、資源利用率和查詢表達能力。管理員應結合預期郵件量、查詢模式和維運限制來考慮這些因素。

 The following table summarises the primary limitations of each supported engine:

 下表總結了各支援引擎的主要限制：

| Full Text Search Engine 全文搜尋引擎 | Key Limitations 主要限制 |
| --- | --- |
| Elasticsearch 彈性搜尋 | Memory intensive and Java based, which can increase operational complexity and resource usage. 記憶體密集且基於 Java，這會增加操作複雜性和資源使用量。 |
| Meilisearch Meil​​search | Single-node architecture and limited support for complex, deeply nested query expressions. 單節點架構，並有限支援用於複雜、深度嵌套的查詢表達式。 |
| PostgreSQL | Maximum indexable email content size of approximately 650 KB per message. 最大可索引電子郵件內容大小約為 每封郵件 650 KB 。 |
| MySQL | No stemming support and no support for indexing multiple languages within the same column. 不支援詞幹擷取且不支援在同一列中索引多種語言。 |
| Internal FTS 內部FTS | Higher write amplification compared to external full text search backends. 與外部全文搜尋後端相比，寫入放大率更高。 |

These limitations are not defects but consequences of architectural choices. If search accuracy, language support, scalability, or operational simplicity is a critical requirement, evaluating multiple backends may be necessary.

 這些限制並非缺陷，而是架構選擇的必然結果。如果搜尋準確性、語言支援、可擴展性或操作簡便性是關鍵需求，則可能需要評估多個後端方案。

## Configuration｜配置

 To change the search backend, update the SearchStore singleton and select the appropriate variant. Variant-specific fields such as url, httpAuth, numShards, and numReplicas apply to the ElasticSearch variant; url, pollInterval, and maxRetries apply to the Meilisearch variant. See the SearchStore reference for the full field list per variant.

 若要變更搜尋後端，請更新 SearchStore 單例並選擇對應的變體。變體特有的字段，例如 url 、 httpAuth 、 numReplicas和\([https://stalw.art/docs/ref/object/search-store#numshards](https://stalw.art/docs/ref/object/search-store#numshards)\) `numShards` ElSearch2 `url` \]\([https://stalw.art/docs/ref/object/search-store#url](https://stalw.art/docs/ref/object/search-store#url)\) 、pollInterval和 maxRetries適用於 Meil​​​​isearch 變體。有關每個變體的完整字段列表，請參閱 SearchStore 參考 。

### Index configuration｜索引配置

 Which entities are indexed, and which of their fields, is controlled through the [Search](https://stalw.art/docs/ref/object/search) object \(found in the WebUI under Settings › Search\). Indexing for each entity type can be enabled or disabled independently through [indexEmail](https://stalw.art/docs/ref/object/search#indexemail), [indexContacts](https://stalw.art/docs/ref/object/search#indexcontacts), [indexCalendar](https://stalw.art/docs/ref/object/search#indexcalendar), and [indexTelemetry](https://stalw.art/docs/ref/object/search#indextelemetry).

 哪些實體被索引，以及它們的哪些欄位被索引，由 [Search](https://stalw.art/docs/ref/object/search)物件（在 WebUI 的「設定 › 搜尋」下找到）控制。可以透過 [indexEmail](https://stalw.art/docs/ref/object/search#indexemail) 、 [indexContacts](https://stalw.art/docs/ref/object/search#indexcontacts) 、 [indexCalendar](https://stalw.art/docs/ref/object/search#indexcalendar)和 [indexTelemetry](https://stalw.art/docs/ref/object/search#indextelemetry) 。

 The fields indexed per entity are controlled through [indexEmailFields](https://stalw.art/docs/ref/object/search#indexemailfields), [indexContactFields](https://stalw.art/docs/ref/object/search#indexcontactfields), [indexCalendarFields](https://stalw.art/docs/ref/object/search#indexcalendarfields), and [indexTracingFields](https://stalw.art/docs/ref/object/search#indextracingfields). Each accepts a list of field names; if the list is empty, all supported fields for that entity are registered.

 每個實體索引的欄位透過 [indexEmailFields](https://stalw.art/docs/ref/object/search#indexemailfields) 、 [indexContactFields](https://stalw.art/docs/ref/object/search#indexcontactfields) 、 \[ `indexCalendarFields` \([https://stalw.art/docs/ref/object/search#indextracingfields](https://stalw.art/docs/ref/object/search#indextracingfields)\) \([https://stalw.art/docs/ref/object/search#indexcalendarfields\)和](https://stalw.art/docs/ref/object/search#indexcalendarfields%2529%2525E5%252592%25258C) \[ `indexTracingFields`每個控制項都接受一個欄位名稱清單；如果清單為空，則註冊該實體的所有支援欄位。

### Default language｜預設語言

 When language detection fails \(for example, when the text is too short or ambiguous\), the server falls back to the language configured in [defaultLanguage](https://stalw.art/docs/ref/object/search#defaultlanguage) on the Search object. The default is `"en_US"`. The set of languages considered by the detector can be restricted through [supportedLanguages](https://stalw.art/docs/ref/object/search#supportedlanguages).

 當語言偵測失敗時（例如，文字太短或意義模糊），伺服器將回退到搜尋物件 [defaultLanguage](https://stalw.art/docs/ref/object/search#defaultlanguage)中配置的語言。預設值為`"en_US"` 。可以透過 [supportedLanguages](https://stalw.art/docs/ref/object/search#supportedlanguages)來限制偵測器考慮的語言集。
