# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[routing｜路由\\\]\\\(&lt;000 目錄.md#c-46&gt;\\\)

Routing is the sequence of steps the proxy performs between accepting a client connection and bridging it to a backend. The same outline applies to every interactive protocol, with per-protocol details covered on the IMAP, POP3, ManageSieve, SMTP and HTTP pages. This page describes the shared flow and the cross-cutting mechanisms: how the routing identifier is extracted, how authentication is replayed, how the client’s identity is forwarded to the backend, and how TLS is bridged on each leg.

 路由是指代理伺服器在接受客戶端連線並將其橋接到後端之間執行的一系列步驟。所有交互式協議都遵循相同的流程，具體協議細節請參見 IMAP 、 POP3 、ManageSieve 、SMTP和 HTTP頁面。本頁面將介紹共享流程和關鍵機制：如何提取路由標識符、如何重播身份驗證、如何將客戶端身份轉發到後端，以及如何在每個鏈路上橋接TLS 。

## Connection flow｜連結流程

 For the interactive protocols, a connection proceeds through the following stages:

 對於互動式協議，連接過程分為以下階段：

1. **Pre-authentication.** The proxy presents its greeting and capabilities, optionally negotiates STARTTLS, and reads the client’s authentication command. This dialogue is answered by the proxy itself, using the configured capabilities, because the backend has not yet been chosen.
**預認證。**代理伺服器會顯示其問候語和功能，並可選擇性地協商STARTTLS ，然後讀取客戶端的認證命令。由於後端尚未選定，因此代理伺服器會使用已配置的功能來回應此對話。
2\. **Identifier extraction.** From the authentication command the proxy derives a routing identifier, normalizes it, and strips any master-user suffix.
**標識符提取。** 代理從身份驗證命令中匯出路由標識符，對其進行規範化，並移除任何主用戶後綴。
3\. **Resolution.** The identifier is looked up in the mapping store, yielding a destination, or the default destination if there is no explicit mapping.
**解析。** 在 映射儲存中尋找標識符，得到一個目標位址，如果沒有明確映射，則得到預設目標位址。
4\. **Backend connection.** The proxy dials the destination’s endpoint for the protocol in use, sending a PROXY protocol header or application-level forwarding metadata as configured, and negotiating TLS on the backend leg.
**後端連接。** 代理撥號到目標端的所用協定端點，發送配置的PROXY協定頭或應用層轉發元數據，並在後端鏈路上協商TLS 。
5\. **Authentication replay.** The proxy replays the client’s authentication to the backend and observes the result.
**身份驗證重播** 代理伺服器將客戶端的身份驗證請求重播到後端，並觀察結果。
6\. **Bridging.** On success, the two connections are spliced and the session continues directly between client and backend until either side closes or the idle timeout elapses.
**橋接。**成功後，兩個連線將合併，會話將直接在客戶端和後端之間繼續進行，直到任一端關閉或空閒逾時為止。
The SMTP and LMTP pass-through protocols skip stages 1, 2, 3 and 5: they are bridged as an opaque stream to a fixed destination, as described on the SMTP page.

 SMTP和LMTP直通協議跳過了階段 1、2、3 和 5：它們作為不透明流橋接到固定目的地，如 SMTP頁所述。

## Identifier extraction｜標識符提取

 The routing identifier is the account name the proxy uses to look up a destination. How it is obtained depends on the authentication method:

 路由標識符是代理伺服器用於尋找目標位址的帳戶名稱。其取得方式取決於身份驗證方法：

- For password-based authentication \(SASL `PLAIN`, and the protocol-specific login commands\), the identifier is the authentication username the client supplies.
對於基於密碼的身份驗證（ SASL `PLAIN`和特定於協定的登入命令），識別碼是用戶端提供的身份驗證使用者名稱。
- For `OAUTHBEARER` and `XOAUTH2`, the identifier is the username carried in the authentication frame when present.
對於`OAUTHBEARER`和`XOAUTH2` ，標識符是身份驗證幀中攜帶的使用者名稱（如果存在）。
- For a bearer token that carries no separate username, the proxy inspects the token itself. Stalwart access tokens, recognizable by their `sw1.` prefix, encode the account address directly and are decoded without interpreting the token as a JWT. Otherwise the token is treated as a JWT and the identifier is read from its claims, trying the configured `jwt_username_claim` first and then a series of common fallback claims \(`email`, `preferred_username`, `upn`, `unique_name`, `sub`\), accepting the first whose value looks like an address.
對於不包含單獨使用者名稱的持有者令牌，代理程式會檢查令牌本身。堅固型存取權杖（可透過其`sw1.`前綴識別）直接編碼帳戶位址，解碼時不會將其解釋為JWT 。否則，令牌將被視為JWT ，並從其聲明中讀取標識符，首先嘗試配置的`jwt_username_claim` ，然後嘗試一系列常見的備用聲明（ `email`, `preferred_username`, `upn`, `unique_name`, `sub` ），並接受第一個值看起來像地址的聲明。
After extraction the identifier is normalized according to the mapping configuration and has any master-user suffix removed before lookup. An identifier containing control characters, spaces or quotes is rejected, and the connection receives a backend-unavailable response rather than being routed, which prevents malformed identifiers from being injected into the forwarding metadata sent to the backend.
 提取後，標識符會根據 mapping配置進行規範化，並在查找前移除所有主用戶後綴。包含控製字元、空格或引號的標識符將被拒絕，連接將收到後端不可用的回應，而不是被路由，這可以防止將格式錯誤的標識符注入到發送到後端的轉發元資料中。

 The token or password itself is never used for routing beyond extracting the identifier, and is forwarded to the backend unchanged for the backend to validate.

 除了提取識別碼之外，令牌或密碼本身絕不會用於路由，而是原封不動地轉送給後端進行驗證。

## Authentication replay｜身份驗證重播

 The proxy does not verify credentials; it relays them to the backend and lets the backend decide. After connecting to the destination it reconstructs the client’s authentication command in the form the backend expects and sends it, then reads the backend’s response. A success is passed back to the client and the session is bridged; a failure is returned to the client \(verbatim, or replaced with a generic message when the destination sets `hide_auth_errors`\), the backend connection is dropped, and the proxy resumes its own pre-authentication dialogue. The client may authenticate again on the same connection, and every attempt is routed and replayed on its own, so a second attempt for a different account reaches that account’s destination. Backend rejections count towards the listener’s `max_auth_attempts`, which closes the connection once the limit is reached.

 代理伺服器不驗證憑證；它將憑證轉發給後端，由後端決定是否允許存取。連接到目標伺服器後，代理伺服器會按照後端期望的格式重構客戶端的身份驗證命令並發送，然後讀取後端的回應。如果回應成功，則返回給客戶端並建立會話；如果回應失敗，則返回給客戶端（原樣返回，或當目標伺服器設定了`hide_auth_errors`時替換為通用訊息），後端連接被斷開，代理伺服器恢復其自身的預先身份驗證對話。用戶端可以在同一連線上再次進行身份驗證，每次嘗試都會獨立路由和重播，因此，針對不同帳戶的第二次嘗試將到達該帳戶的目標伺服器。後端拒絕次數計入監聽器的`max_auth_attempts`限制，一旦達到限制，連線將被關閉。

 Because the proxy holds the credentials only for the duration of this exchange and never writes them anywhere, the backend remains the sole authority on authentication. The proxy refuses to send credentials over an unencrypted backend leg: before replaying authentication it asserts that the egress connection is encrypted, unless the destination has explicitly opted into plaintext authentication for a backend reached over an otherwise-secure channel.

 由於代理伺服器僅在本次通訊期間持有憑證，且不會將其寫入任何位置，因此後端伺服器仍然是身分驗證的唯一權威。代理伺服器拒絕透過未加密的後端連結傳送憑證：在重播身分驗證之前，它會聲明出口連線已加密，除非目標伺服器明確選擇對透過安全通道存取的後端伺服器進行明文驗證。

 When a backend is unreachable or has been marked down by the health circuit breaker, the proxy returns a protocol-appropriate temporary-failure response so that clients retry later rather than treating the condition as an authentication error.

 當後端無法存取或已被 health斷路器標記為宕機時，代理會傳回協定適當的臨時故障回應，以便用戶端稍後重試，而不是將此情況視為驗證錯誤。

## Forwarding client identity｜轉發客戶端身份

 Since the backend sees a connection originating from the proxy, the proxy conveys the real client address and related metadata using one of two mechanisms, chosen per destination by the `forwarding` setting described under Destinations.

 由於後端看到連接源自代理，代理使用兩種機制之一傳遞真實的客戶端位址和相關元數據，具體機制由 目的地下的`forwarding`設定根據目的地選擇。

### PROXY protocol｜PROXY協議

 With `forwarding = "proxy"`, the proxy prefixes the backend connection with a PROXY protocol version 2 header carrying the original source and destination socket addresses, before any application data. The backend reads this header and attributes the session to the real client. This is transparent to the application protocol and is the appropriate choice for Stalwart and any backend that understands the PROXY protocol. When the client and backend belong to different address families, the proxy emits an `UNKNOWN` header rather than misrepresenting the addresses.

 使用`forwarding = "proxy"` ，代理程式會在後端連接前新增一個PROXY協定版本2頭部，其中包含原始的來源套接字位址和目標套接字位址，位於任何應用程式資料之前。後端讀取此頭部並將會話歸屬到真正的客戶端。這對應用程式協定是透明的，並且是Stalwart以及任何理解PROXY協議的後端的合適選擇。當客戶端和後端屬於不同的地址族時，代理會發出`UNKNOWN`頭部，而不是錯誤地表示地址。

### XCLIENT and IMAP ID｜XCLIENT和IMAP ID

 With `forwarding = "xclient"`, the proxy announces the client over the application protocol instead. For SMTP, POP3 and ManageSieve it issues an `XCLIENT` command carrying attributes such as the client address and port, the destination address and port, a session identifier and the transport security, and for SMTP additionally the client’s HELO name and protocol. For IMAP, which has no `XCLIENT` command, it sends an `ID` command conveying the equivalent information as `x-originating-ip` and related fields. This is the appropriate choice for Dovecot and Postfix backends, which support these extensions.

 對於`forwarding = "xclient"` ，代理伺服器會透過應用層協定通告客戶端。對於SMTP, POP3和ManageSieve，它會發出`XCLIENT`命令，其中包含客戶端位址和連接埠、目標位址和連接埠、會話標識符以及傳輸安全資訊等屬性；對於SMTP ，還會額外包含客戶端的HELO名稱和協定。對於沒有`XCLIENT`指令的IMAP ，它會傳送`ID`指令，其中包含與`x-originating-ip`及其相關欄位相同的資訊。這對於支援這些擴充的Dovecot和Postfix後端來說是合適的選擇。

 The proxy only sends forwarding commands a backend has advertised support for, and for SMTP it filters the attributes down to those the backend’s `XCLIENT` announcement lists, since some servers reject unknown attributes. Crucially, the login attribute is never forwarded: the proxy always replays the authentication exchange itself, so pre-authenticating the backend through `XCLIENT LOGIN` would be both unnecessary and unsafe.

 代理伺服器僅傳送後端已宣告支援的轉送指令，且對於SMTP ，它會將屬性過濾到後端`XCLIENT`公告清單中所列的屬性，因為某些伺服器會拒絕未知屬性。至關重要的是，登入屬性永遠不會被轉送：代理伺服器總是會自行重播身分驗證交換，因此透過`XCLIENT LOGIN`預先驗證後端既不必要也不安全。

### HTTP forwarding headers｜HTTP轉發頭

 HTTP destinations do not use the PROXY protocol or `XCLIENT`. Instead, when the destination sets `forwarded = true`, the proxy appends the client address to the `Forwarded` and `X-Forwarded-For` request headers before relaying. Inbound forwarding headers from clients are trusted or stripped according to the listener’s `forwarded` setting. This is detailed on the HTTP routing page.

 HTTP目標位址不使用PROXY協定或`XCLIENT` 。相反，當目標位址設定`forwarded = true`時，代理程式會在轉送之前將客戶端位址附加到`Forwarded`和`X-Forwarded-For`請求頭中。來自客戶端的入站轉發頭是否被信任取決於監聽器的`forwarded`設定。詳情請參閱 HTTP路由頁。

## TLS bridging｜TLS橋接

 The client-facing and backend-facing legs of a session are encrypted independently. The client leg is governed by the listener’s `tls` mode and the inbound certificates; the backend leg is governed by the protocol endpoint’s `tls` mode and the destination’s verification settings. The two need not match: a client may connect over implicit TLS while the proxy reaches the backend over STARTTLS, or the reverse.

 會話的客戶端部分和後端部分是獨立加密的。客戶端部分由監聽器的`tls`模式和入站 證書控制；後端部分由協議端點的`tls`模式和目標 驗證設定控制。兩者不必完全匹配：客戶端可以透過隱式TLS連接，而代理可以透過STARTTLS連接到後端，反之亦然。

 With an `implicit` backend leg, the proxy performs a TLS handshake immediately after connecting. With a `starttls` backend leg, the proxy connects in cleartext, confirms the backend advertises STARTTLS, issues the upgrade command, and only then performs the handshake; if the backend fails to advertise or accept STARTTLS, the connection is aborted rather than continuing in cleartext. With a `plain` leg, the connection is never encrypted, and the proxy will refuse to replay credentials over it unless the destination has set `allow_plaintext_auth`.

 使用`implicit`後端連線時，代理程式會在連線後立即執行TLS握手。使用`starttls`後端連接時，代理會以明文方式連接，確認後端已發布STARTTLS後，發出升級命令，然後才執行握手；如果後端未能發布或接受STARTTLS連接，則連接會中止，而不是繼續以明文方式連接。使用`plain`連線時，連線始終未加密，除非目標已設定`allow_plaintext_auth` ，否則代理程式將拒絕透過該連線重播憑證。

## Loop prevention｜迴路預防

 Because the proxy forwards a decremented time-to-live in its `XCLIENT` and `ID` metadata, and because a misconfiguration could in principle point a destination back at one of the proxy’s own listeners, two safeguards detect routing loops. Before dialing, the proxy rejects any destination endpoint whose address and port coincide with one of its own bound listeners. For `XCLIENT` forwarding, it also rejects a connection whose forwarded time-to-live \(`server.proxy_ttl`, decremented at each hop\) has been exhausted, which breaks a loop formed by a chain of proxies.

 由於代理伺服器會在其`XCLIENT`和`ID`資料中轉送遞減的生存時間（TTL），且理論上配置錯誤可能導致目標位址指向代理伺服器本身的監聽器，因此採用了兩項安全措施來偵測路由迴路。在撥號之前，代理伺服器會拒絕任何位址和連接埠與其本身綁定監聽器重合的目標端點。對於`XCLIENT`轉發，它還會拒絕轉發的TTL（ `server.proxy_ttl` ，每次躍點遞減）已耗盡的連接，從而打破由代理伺服器鏈形成的環路。
