# HTTP

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[routing｜路由\\\]\\\(&lt;000 目錄.md#c-46&gt;\\\)

The HTTP listener proxies web traffic, which for Stalwart means the JMAP API, the autodiscovery and `.well-known` endpoints, the administrative interface and WebSocket connections. Unlike the mail protocols, HTTP has no single authentication step at the start of the connection; each request may carry its own credentials, and a single connection may be reused for many requests. Routing is therefore driven by per-request rules that examine the request and decide which destination handles it.

 HTTP監聽器代理 Web 流量，對於 Stalwart 而言，這意味著代理JMAP API 、自動發現端點和`.well-known`端點、管理介面以及 WebSocket 連線。與郵件協定不同， HTTP在連線開始時沒有單一的身份驗證步驟；每個請求都可以攜帶自己的憑證，並且單一連線可以被多個請求重複使用。因此，路由由每個請求的規則驅動，這些規則會檢查請求並決定由哪個目標處理它。

## Route rules｜路由規則

 HTTP routes are declared as an ordered list of `[[http.route]]` entries. Each entry has a glob pattern matched against the request path, and either pins the request to a fixed destination or extracts an identifier from the request and resolves it through the mapping store. The first matching rule wins, so more specific patterns should precede broader ones.

 HTTP路由被宣告為一個有序的`[[http.route]]`條目列表。每個條目都有一個與請求路徑匹配的 glob 模式，該模式要么將請求綁定到固定的目標地址，要么從請求中提取標識符並通過 映射存儲解析該請求。第一個匹配的規則優先，因此更具體的模式應該優先於更廣泛的模式。

```toml
[[http.route]]
match = "/.well-known/**"
destination = "legacy"

[[http.route]]
match = "/**"
extract = { from = "authorization" }
fallback = "default"
```

A rule with a `destination` key pins every matching request to that destination regardless of who is making it, which suits path-based endpoints such as autodiscovery that are not tied to a particular account. A rule with an `extract` block instead derives an account identifier from the request and routes it the same way the mail protocols do; the optional `fallback` names the destination to use when no identifier can be extracted. Patterns are matched against the path with and without a trailing slash, so a rule for `/api` also matches `/api/`.

 帶有`destination`鍵的規則會將所有符合的請求鎖定到該目標位址，無論請求者是誰，這適用於基於路徑的端點，例如不綁定到特定帳戶的自動發現。帶有`extract`塊的規則則會從請求中派生出帳戶標識符，並以與郵件協議相同的方式進行路由；可選的`fallback`用於指定在無法提取標識符時要使用的目標地址。模式匹配會針對有或沒有尾部斜線的路徑進行，因此`/api`的規則也匹配`/api/` 。

## Identifier extraction｜標識符提取

 The `extract` block names where in the request the account identifier is found:

`extract`區塊名稱，其中包含請求中的帳戶識別碼：

- `from = "authorization"` reads the `Authorization` header. A `Basic` credential is decoded and the login portion \(before the colon\) is used, lowercased. A `Bearer` token is decoded the same way as for the mail protocols: a Stalwart `sw1.` token yields the account address directly, and any other token is interpreted as a JWT and the identifier read from its claims.
`from = "authorization"` 讀取`Authorization` 標頭。 `Basic` 憑證被解碼並使用小寫的登入部分（冒號之前）。 `Bearer` 令牌的解碼方式與郵件協議相同：Stalwart `sw1.` 令牌直接產生帳戶位址，任何其他令牌都被解釋為 JWT 以及從其聲明中讀取的標識符。
- `from = "query"` reads a named query-string parameter, given by `param`, with URL decoding applied. This is useful for endpoints such as OAuth authorization that carry a `login_hint`.
`from = "query"`讀取由`param`給出的命名查詢字串參數，並套用URL解碼。這對於帶有`login_hint`的端點（例如 OAuth 授權）非常有用。
- `from = "header"` reads a named request header, given by `header`.
`from = "header"`讀取由`header`給的命名請求頭。
- `from = "body"` applies a regular expression, given by `regex`, to the request body and uses the first capture group, with form decoding applied. This supports form-encoded login endpoints such as a token exchange that carries the username in the request body.
`from = "body"`將`regex`給出的正規表示式應用於請求體，並使用第一個捕獲組，同時套用表單解碼。這支援表單編碼的登入端點，例如請求體中包含使用者名稱的令牌交換。

```toml
[[http.route]]
match = "/oauth/authorize"
extract = { from = "query", param = "login_hint" }
fallback = "default"

[[http.route]]
match = "/auth/token"
extract = { from = "body", regex = "username=([^&]+)" }
```

When extraction reads from the body, the proxy buffers the request body up to `http.body_extract_cap` \(64 KB by default\) so the pattern can be applied, then forwards it; body extraction is therefore the only mode that requires reading the body before routing.

 當從正文中讀取提取資料時，代理會將請求正文緩衝到`http.body_extract_cap` （預設為 64 KB ），以便應用模式，然後轉發；因此，正文提取是唯一需要在路由之前讀取正文的模式。

## Inbound and outbound forwarding headers｜入站和出站轉送標頭

 By default the proxy strips any `Forwarded` and `X-Forwarded-For` headers a client sends, so a client cannot forge a forwarding chain. A listener that genuinely sits behind a trusted front-end can preserve them by setting `forwarded = "trust"` on the listener. Independently, when the resolved destination sets `forwarded = true`, the proxy appends the real client address to both headers before relaying, so the backend learns the client’s address. These two settings are separate: the listener setting governs what is accepted from clients, and the destination setting governs what the proxy adds toward the backend.

 預設情況下，代理程式會移除客戶端發送的所有`Forwarded`和`X-Forwarded-For`標頭，以防止客戶端偽造轉送鏈。真正位於可信任前端之後的監聽器可以透過設定`forwarded = "trust"`來保留這些標頭。此外，當解析後的目標設定了`forwarded = true`時，代理會在轉送之前將真實的客戶端位址附加到這兩個標頭中，以便後端獲知客戶端的位址。這兩個設定是相互獨立的：監聽器設定控制從客戶端接收哪些訊息，而目標設定控制代理程式新增到後端的資訊。

## Connection handling｜連接處理

 The proxy maintains HTTP keep-alive, serving multiple requests on one client connection and reusing the backend connection while requests continue to resolve to the same destination. If a later request on a kept-alive connection resolves to a different destination, the proxy responds with a misdirected-request status and closes, since a single backend connection cannot serve two destinations. The connection is pinned the same way to the first account whose credentials it carries, so a request presenting a different account also receives a misdirected-request status; requests that carry no identifier are unaffected. The number of requests served on one connection is bounded by `http.max_keepalive_requests`, and an idle kept-alive connection is closed after `http.keepalive_timeout`.

 代理伺服器維護HTTP keep-alive連接，在同一個客戶端連接上處理多個請求，並在請求解析到相同目標位址時重用後端連接。如果後續在 keep-alive 連接上的請求解析到不同的目標位址，代理伺服器會返回「請求重定向」狀態並關閉連接，因為單一後端連接無法同時服務兩個目標位址。連線會以相同的方式綁定到它所承載憑證的第一個帳戶，因此，使用不同帳戶的請求也會收到「請求重定向」狀態；不包含任何識別碼的請求不受影響。單一連線上處理的請求數量受`http.max_keepalive_requests`限制，空閒的 keep-alive 連線會在`http.keepalive_timeout`之後關閉。

 Once a request identifies an account, the connection is registered against it, so `POST /connections/kick` disconnects it. The registration survives a WebSocket upgrade, which is how a kick reaches a JMAP-over-WebSocket session.

 一旦請求識別出某個帳戶，連線就會註冊到該帳戶上，因此`POST /connections/kick`會中斷連線。註冊資訊在WebSocket升級後仍然存在，這就是踢出作業如何到達JMAP基於WebSocket的會話的原因。

 Several HTTP features that change the shape of a response are handled transparently. An `Expect: 100-continue` request is acknowledged so the client proceeds to send its body. A `101 Switching Protocols` response to a WebSocket upgrade causes the proxy to stop interpreting the stream and bridge the two connections opaquely, which is how JMAP-over-WebSocket sessions are carried. A server-sent-events response is streamed to the client without buffering. Chunked and length-delimited bodies are relayed in both directions, and the request and response heads are bounded by `http.max_head_size`.

 幾個改變反應形狀的HTTP特徵是透明處理的。 `Expect: 100-continue` 請求被確認，因此客戶端繼續發送其正文。對 WebSocket 升級的 `101 Switching Protocols` 回應會導致代理停止解釋流並以不透明的方式橋接兩個連接，這就是 JMAP-over-WebSocket 會話的承載方式。伺服器傳送的事件回應會串流到客戶端，無需緩衝。分塊和長度分隔的主體在兩個方向上中繼，請求和回應頭以`http.max_head_size`為界。
