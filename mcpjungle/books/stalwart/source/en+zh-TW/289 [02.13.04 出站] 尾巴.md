# Queues｜尾巴

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[mta｜捷運\\\]\\\(&lt;000 目錄.md#c-47&gt;\\\) › \\\[outbound｜出站\\\]\\\(&lt;000 目錄.md#c-52&gt;\\\)

Queues are the holding area for outbound messages. When a message arrives, it is placed in a queue until it can be delivered to its final destination. Stalwart supports an unlimited number of virtual queues, so administrators can create and configure multiple queues with different settings and behaviours. This allows separate queues for different classes of traffic, each processed with its own concurrency and retry characteristics.

 隊列是存放出站訊息的區域。當訊息到達時，它會被放入佇列，直到可以發送到最終目的地。 Stalwart 支援無限數量的虛擬佇列，因此管理員可以建立和配置多個具有不同設定和行為的佇列。這允許為不同類型的流量建立單獨的佇列，每個佇列都具有自己的並發性和重試特性。

 Queues in Stalwart are distributed and fault-tolerant, meaning they can be spread across multiple cluster nodes and continue operating even if one or more nodes fail.

 Stalwart 中的佇列是分散式的，並且具有容錯性，這意味著它們可以分佈在多個叢集節點上，即使一個或多個節點發生故障，它們也能繼續運作。

## Virtual queues｜虛擬佇列

 A virtual queue is a logical delivery queue used to isolate and manage groups of outbound messages. Each virtual queue must be explicitly defined because each allocates a fixed number of delivery threads per cluster node; creating queues at runtime could exhaust memory or threads during peak load.

 虛擬隊列是一種邏輯傳遞佇列，用於隔離和管理出站訊息組。每個虛擬佇列都必須明確定義，因為每個虛擬佇列都會為每個叢集節點分配固定數量的傳遞執行緒；在運行時建立佇列可能會在高峰負載期間耗盡記憶體或執行緒。

 Virtual queues control how messages are delivered based on attributes such as message type, source, or priority. An operator might configure one queue with high concurrency for bulk transactional mail and another for latency-sensitive user mail. Common uses include:

 虛擬佇列根據訊息類型、來源或優先權等屬性控制訊息的傳遞方式。運營商可以配置一個高並發佇列用於批量事務郵件，另一個佇列用於對延遲敏感的使用者郵件。常見用途包括：

- Separating remote and local deliveries so that internal and external flows can be tuned independently.
將遠端和本地交付分開，以便可以獨立調整內部和外部流程。
- Isolating messages by priority, for example giving certain users or services preferential delivery scheduling.
依優先權隔離訊息，例如給予某些使用者或服務優先發送安排。
- Preventing control traffic \(DSNs, DMARC aggregate reports, TLS failure reports\) from interfering with the delivery of regular user messages by placing them in low-priority or throttled queues.
防止控制流量（DSN、 DMARC聚合報告、 TLS故障報告）幹擾常規用戶訊息的傳遞，方法是將它們放入低優先級或限速隊列中。
- Applying custom retry policies for specific domains or types of content.
針對特定網域或內容類型套用自訂重試策略。
Each message recipient is assigned to a virtual queue through the scheduling strategy, which can dynamically select a queue using message metadata and delivery context. This allows context-aware queueing logic that adapts to system demand and operational policy.
 每個訊息接收者都透過 調度策略被指派到一個虛擬佇列，該策略可以根據訊息元資料和傳遞上下文動態選擇隊列。這使得隊列邏輯能夠感知上下文，並適應系統需求和運作策略。

## Configuration｜配置

 A virtual queue is defined as an MtaVirtualQueue object \(found in the WebUI under Settings › MTA › Outbound › Virtual Queues\). The relevant fields are:

 虛擬佇列定義為 MtaVirtualQueue物件（可在 WebUI 的「設定」&gt; MTA &gt;「出站」&gt;「虛擬佇列」中找到）。相關欄位如下：

- name: unique identifier for the queue. Maximum 8 characters, to keep the internal representation compact.
name : 佇列的唯一識別碼。最多 8 個字符，以保持內部表示的緊湊性。
- threadsPerNode: maximum number of concurrent delivery threads allocated to this queue on each cluster node. Default 25.
threadsPerNode : 每個叢集節點上分配給此佇列的最大並發交付執行緒數。預設值為 25。
- description: short description used to identify the queue in the UI.
description : 用於標識UI中的隊列的簡短描述。
Queue names must be unique and should follow a consistent naming convention. Once defined, virtual queues are selected by scheduling strategies, which route messages into the appropriate delivery path based on conditions such as sender, recipient, message size, or classification.
 佇列名稱必須唯一，並應遵循一致的命名規則。定義完成後，虛擬佇列將由調度策略（ \([https://stalw.art/docs/mta/outbound/schedule](https://stalw.art/docs/mta/outbound/schedule)\) ）選擇，調度策略會根據寄件者、收件者、訊息大小或分類等條件將訊息路由到對應的傳遞路徑。

 For example, a virtual queue named `fast` with 1000 delivery threads per cluster node:

 例如，一個名為`fast`的虛擬佇列，每個叢集節點有1000個交付執行緒：

```json
{
  "name": "fast",
  "threadsPerNode": 1000,
  "description": "High-throughput queue for transactional mail"
}
```

A virtual queue must exist before any scheduling strategy can reference it. Defining a queue allocates a dedicated delivery thread pool on every node in the cluster; threadsPerNode determines the maximum number of concurrent delivery attempts from that queue per node.

 虛擬隊列必須先存在，任何調度策略才能引用它。定義佇列會在叢集中的每個節點上分配一個專用的交付執行緒池；threadsPerNode決定了每個節點從該佇列同時進行的最大交付嘗試次數。
