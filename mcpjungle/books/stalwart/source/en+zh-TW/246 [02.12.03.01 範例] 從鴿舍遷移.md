# Migrating from Dovecot｜從鴿舍遷移

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[examples｜範例\\\]\\\(&lt;000 目錄.md#c-43&gt;\\\)

This example fronts a legacy mail stack \(Dovecot serving IMAP, POP3 and ManageSieve, with Postfix handling submission\) and a new Stalwart server with a single proxy, migrating accounts from the legacy stack to Stalwart one at a time. Every account initially resolves to the legacy backend through the default destination, and as each mailbox is migrated it is given an explicit mapping to Stalwart. Clients keep their existing settings throughout. A ready-to-edit copy of the proxy configuration ships in the proxy repository as [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.dovecot-postfix.toml), and the backend changes are collected in [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf).

 此範例前端使用舊版郵件堆疊（Dovecot 服務IMAP, POP3和 ManageSieve，Postfix 處理郵件提交），後端使用一台新的 Stalwart 伺服器，並設定一個代理程式。遷移過程中，將帳戶從舊版堆疊逐一遷移到 Stalwart。每個帳號最初都透過預設目標解析到舊版後端，隨著每個信箱的遷移，系統會為其指派一個明確的 Stalwart 對應。客戶端的現有設定將保持不變。代理程式配置的可編輯副本已包含在代理程式儲存庫中，編號為 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/config.dovecot-postfix.toml) ，後端變更則收集在 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf)中。

 The defining characteristic of this scenario is that the legacy backend speaks the Dovecot and Postfix conventions: it expects the client’s real address to arrive through the XCLIENT command \(and the IMAP ID command\), not through a PROXY protocol header. The legacy destination therefore uses `forwarding = "xclient"`, while the Stalwart destination uses `forwarding = "proxy"`. The backends are reached over TLS on the classic ports, and the legacy server presents a self-signed certificate that the proxy either pins by fingerprint or, on a trusted internal network, accepts without verification.

 此場景的關鍵特徵在於，傳統後端遵循 Dovecot 和 Postfix 的約定：它期望客戶端的真實位址透過XCLIENT命令（以及IMAP ID命令）傳遞，而不是透過PROXY協議頭傳遞。因此，傳統目標伺服器使用`forwarding = "xclient"` ，而 Stalwart 目標伺服器使用`forwarding = "proxy"` 。後端伺服器透過TLS在傳統連接埠上進行通信，傳統伺服器提供一個自簽名證書，代理伺服器可以透過指紋驗證該證書，或在受信任的內部網路上直接接受該證書而無需驗證。

## Proxy configuration｜代理配置

```toml
[server]
hostname = "mail.example.com"

[tls.certificate.default]
cert = "/etc/proxy/tls/fullchain.pem"
key = "/etc/proxy/tls/privkey.pem"
default = true

[mapping]
source = "file"
normalize = "lowercase"

[mapping.file]
path = "/etc/proxy/mappings.tsv"

[routing]
default_destination = "legacy"
smtp_passthrough_destination = "stalwart"

# Legacy Dovecot + Postfix backend, announced over XCLIENT and the IMAP ID command.
[destination.legacy]
host = "legacy.internal.example.com"
tls_server_name = "legacy.internal.example.com"
forwarding = "xclient"
tls_allow_invalid_certs = true
# Prefer pinning the legacy certificate instead of accepting any:
# tls_pinned_cert_sha256 = "aa:bb:...:99"

[destination.legacy.protocol.imap]
port = 143
tls = "starttls"
[destination.legacy.protocol.pop3]
port = 110
tls = "starttls"
[destination.legacy.protocol.submission]
port = 587
tls = "starttls"
[destination.legacy.protocol.managesieve]
port = 4190
tls = "starttls"

# New Stalwart backend, announced over the PROXY protocol.
[destination.stalwart]
host = "new.internal.example.com"
tls_server_name = "new.internal.example.com"
forwarding = "proxy"
proxy_protocol = true
forwarded = true

[destination.stalwart.protocol.imap]
port = 993
tls = "implicit"
[destination.stalwart.protocol.pop3]
port = 995
tls = "implicit"
[destination.stalwart.protocol.submission]
port = 587
tls = "starttls"
[destination.stalwart.protocol.managesieve]
port = 4190
tls = "starttls"
[destination.stalwart.protocol.smtp]
port = 25
tls = "plain"

# Client-facing listeners on the familiar ports.
[listener.imaps]
protocol = "imap"
bind = ["0.0.0.0:993", "[::]:993"]
tls = "implicit"
[listener.imap]
protocol = "imap"
bind = ["0.0.0.0:143", "[::]:143"]
tls = "starttls"
[listener.pop3s]
protocol = "pop3"
bind = ["0.0.0.0:995", "[::]:995"]
tls = "implicit"
[listener.pop3]
protocol = "pop3"
bind = ["0.0.0.0:110", "[::]:110"]
tls = "starttls"
[listener.submission]
protocol = "submission"
bind = ["0.0.0.0:587", "[::]:587"]
tls = "starttls"
[listener.submissions]
protocol = "submission"
bind = ["0.0.0.0:465", "[::]:465"]
tls = "implicit"
[listener.managesieve]
protocol = "managesieve"
bind = ["0.0.0.0:4190", "[::]:4190"]
tls = "starttls"
[listener.smtp]
protocol = "smtp"
bind = ["0.0.0.0:25", "[::]:25"]
tls = "plain"

[admin]
bind = "127.0.0.1:9443"
tls = "implicit"
bearer_token_file = "/etc/proxy/admin.token"
```

Dovecot and Postfix serve no HTTP or JMAP, so no HTTP listener is defined. Once accounts are on Stalwart, JMAP and the web interface are served by the new server; an HTTP listener routing to `stalwart` can be added at that point if a single hostname for web access is wanted.

 Dovecot 和 Postfix 不提供HTTP或JMAP服務，因此未定義HTTP監聽器。帳戶遷移到 Stalwart 後， JMAP和 Web 介面將由新伺服器提供服務；如果需要使用單一主機名稱進行 Web 訪問，則可以在此時添加一個路由到`stalwart`的HTTP監聽器。

## Trusting the proxy on the legacy backend｜信任傳統後端上的代理

 The XCLIENT mechanism only conveys the real client address if the legacy stack is told to trust the proxy. Without that trust, logins still succeed, but Dovecot and Postfix record the proxy’s address as the client rather than the real one. The proxy’s address is added to Dovecot’s trusted networks and to Postfix’s authorized XCLIENT hosts, scoped to the proxy alone so that other hosts cannot spoof a client address. The full set of changes is in [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf).

 XCLIENT機制僅在傳統協定堆疊被指示信任代理程式時才會傳遞真實的客戶端位址。如果沒有這種信任，登入仍然會成功，但 Dovecot 和 Postfix 會將代理程式的位址記錄為用戶端位址，而不是真實的用戶端位址。代理程式的位址會被加入到 Dovecot 的受信任網路和 Postfix 的授權XCLIENT主機清單中，並且僅限於該代理，以防止其他主機偽造客戶端位址。完整的更改集位於 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf)中。

 In Dovecot, in `dovecot.conf` or a file under `conf.d`:

 在 Dovecot 中，位於`dovecot.conf`或`conf.d`下的某個文件：

```
login_trusted_networks = 203.0.113.10/32
```

In Postfix, applied with `postconf` or added to `main.cf`:

 在後綴中，可與`postconf`一起使用，或加到`main.cf`中：

```
smtpd_authorized_xclient_hosts = 203.0.113.10/32
```

The address `203.0.113.10` is a placeholder and must be replaced with the proxy’s actual address. After the change, Dovecot is reloaded with `doveadm reload` and Postfix with `postfix reload`.

 位址`203.0.113.10`是一個佔位符，必須替換為代理的實際位址。更改後，Dovecot將使用`doveadm reload`重新加載，Postfix將使用`postfix reload`重新加載。

 Whether the trust is in effect can be confirmed by signing in through the proxy and reading the Dovecot login line. The `rip=` field shows the real client address when XCLIENT is honoured, and the proxy’s address when it is not.

 可以透過代理登入並查看 Dovecot 登入資訊來確認信任是否生效。當 XCLIENT 生效時， `rip=`欄位顯示真實的客戶端位址；當 XCLIENT 未生效時，則顯示代理程式的位址。

## Reading mailboxes during migration｜遷移期間讀取郵箱

 The migration tool, Vandelay, reads each legacy mailbox over IMAP and writes it to Stalwart. So that it can read any mailbox without each user’s password, Dovecot is given a master user, which Vandelay authenticates as on behalf of the account being migrated. The master user and the separator that joins it to the target login are configured as shown in [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf):

 遷移工具 Vandelay 透過IMAP讀取每個舊郵箱並將其寫入 Stalwart。為了無需每個用戶的密碼即可讀取任何郵箱，Dovecot 被賦予一個主用戶，Vandelay 會代表被遷移的帳戶使用該主用戶進行身份驗證。主用戶及其與目標登入名稱連接的分隔符號的設定方式如 [resources/dovecot-postfix-trust.conf](https://github.com/stalwartlabs/proxy/blob/main/resources/dovecot-postfix-trust.conf)所示：

```
auth_master_user_separator = %

passdb {
  driver = passwd-file
  master = yes
  args = scheme=PLAIN username_format=%u /etc/dovecot/master-users
}
```

With a master user named `vmadmin`, Vandelay reads alice’s mailbox by authenticating as `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%vmadmin` with vmadmin’s password. Mail is read with `vandelay import imap` and sieve scripts with `vandelay import managesieve`; calendars and contacts are read with `vandelay import caldav` and `import carddav` when the deployment runs a CalDAV/CardDAV server. The archive is then written to Stalwart with `vandelay export`. Because Dovecot accepts ordinary direct connections as well as proxied ones, Vandelay can read the legacy stack directly rather than through the proxy. The complete, ordered procedure is in the migration guide.

 使用名為`vmadmin`的主用戶，Vandelay 透過`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%vmadmin`身份和 vmadmin 的密碼進行身份驗證來讀取 alice 的郵箱。郵件使用`vandelay import imap`讀取，Sieve 腳本使用`vandelay import managesieve`讀取；日曆和聯絡人使用`vandelay import caldav`和`import carddav`讀取（當部署執行 CalDAV/CardDAV 伺服器時）。然後，歸檔檔案使用`vandelay export`寫入 Stalwart。由於 Dovecot 接受普通的直接連接以及代理連接，因此 Vandelay 可以直接讀取舊版堆疊，而無需通過代理。完整的操作步驟請參閱遷移指南 。

## Mapping file｜映射文件

 The mapping file starts empty, so every account falls through to `legacy`. As mailboxes are migrated to Stalwart, a line is added for each:

 映射檔案初始為空，因此所有帳戶都預設指向`legacy` 。隨著郵箱遷移到 Stalwart，每個郵箱都會新增一行：

```
# identifier              destination
[email protected]         stalwart
[email protected]          stalwart
```

## Incoming mail｜接收郵件

 The configuration routes incoming mail on port 25 to Stalwart through the pass-through destination, declared with `smtp_passthrough_destination = "stalwart"` and the `smtp` protocol on that destination. Stalwart performs split delivery: mail for an account already migrated is delivered locally, and mail for an account still on the legacy stack is relayed back to Postfix, which delivers it through its existing virtual transport. Because pass-through sessions are not authenticated, they are bridged as a stream and are not routed per account.

 此配置將連接埠 25 上的入站郵件透過直通目標路由至 Stalwart，該直通目標宣告為`smtp_passthrough_destination = "stalwart"` ，並在該目標上使用`smtp`協定。 Stalwart 執行分流投遞：已遷移帳戶的郵件在本機上投遞，而仍在舊版協定堆疊上的帳戶的郵件則轉回 Postfix，由 Postfix 透過其現有的虛擬傳輸進行投遞。由於直通會話未經身份驗證，因此它們以流的形式進行橋接，而不是按帳戶進行路由。

## Cutting an account over｜切斷帳戶

 When an account’s mailbox has been copied to Stalwart, its mapping is set to `stalwart` and any live session is disconnected so that it reconnects to the new server:

 當帳戶的郵箱被複製到 Stalwart 時，其映射設定為`stalwart` ，並且任何即時會話都會斷開連接，以便重新連接到新伺服器：

```bash title=&amp;quot;Terminal window&amp;quot;
TOKEN=$(cat /etc/proxy/admin.token)
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]&destination=stalwart"
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]"
```

When the mapping store is a flat file edited by hand rather than through the API, the file is reloaded and the account’s cache entry invalidated after the line is appended:

 當映射儲存是手動編輯的平面檔案而不是透過API編輯時，在追加行後，檔案會被重新加載，並且帳戶的快取條目會失效：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" https://127.0.0.1:9443/mappings/reload
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/cache/[email protected]"
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]"
```

The end-to-end migration of an account, including copying its data, validating it and rolling it back, follows the same shape as the migration guide, with the legacy-specific reads described above in place of the JMAP reads used between two Stalwart servers.

 帳戶的端對端遷移，包括複製其數據、驗證數據和回滾數據，與 遷移指南遵​​循相同的格式，只是用上面描述的舊版特定讀取代替了兩個 Stalwart 伺服器之間使用的JMAP讀取。
