# LDAP Server｜LDAP伺服器

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[auth｜認證\\\]\\\(&lt;000 目錄.md#c-3&gt;\\\) › \\\[backend｜後端\\\]\\\(&lt;000 目錄.md#c-6&gt;\\\)

LDAP \(Lightweight Directory Access Protocol\) is an open, vendor-neutral protocol used to access and manage directory information services. LDAP directories such as OpenLDAP and Microsoft Active Directory store user credentials and metadata in a hierarchical form that can be queried efficiently, and are commonly used to centralise authentication across multiple systems.

 LDAP（輕量級目錄存取協議）是一種開放的、供應商中立的協議，用於存取和管理目錄資訊服務。 LDAP 目錄（例如 OpenLDAP 和 Microsoft Active Directory）以分層形式儲存使用者憑證和元數據，可以有效地查詢，並且通常用於跨多個系統集中身份驗證。

 Stalwart integrates with LDAP directories for account authentication and lookup. With an LDAP directory configured, the server can reuse existing account records and group policies. Stalwart is compatible with LDAP directories that follow RFC 4511, including OpenLDAP and Active Directory.

 Stalwart 與LDAP目錄集成，用於帳戶身份驗證和查找。配置LDAP目錄後，伺服器可以重複使用現有的帳戶記錄和群組原則。 Stalwart 與遵循RFC 4511 標準的LDAP目錄相容，包括 OpenLDAP 和 Active Directory。

 An LDAP integration is represented by the LDAP variant of the Directory object \(found in the WebUI under Settings › Authentication › Directories\).

 LDAP整合由 Directory物件的LDAP變體表示（可在 WebUI 的「設定 › 驗證 › 目錄」下找到）。

## Account provisioning｜帳戶配置

 Accounts are not copied from the directory in advance. Stalwart materialises a local account the first time it needs one, either when the user authenticates or when a message arrives for their address and the directory confirms it as a valid recipient. This second trigger is what makes just-in-time provisioning workable for LDAP: an account that has never signed in can still receive mail, because the directory can be queried for the address on demand.

 帳戶不會預先從目錄複製。 Stalwart 會在首次需要時建立本機帳戶，例如使用者驗證時，或有郵件傳送至該位址且目錄確認為有效收件者時。正是這第二個觸發條件使得即時配置對於LDAP而言成為可能：即使從未登入過的帳戶也能接收郵件，因為可以根據需要查詢目錄中的位址。

 The gap it leaves is at the other end of the account’s life. Just-in-time provisioning never removes anything, because a deleted directory entry simply stops appearing in query results rather than announcing itself. A departed user’s mailbox persists, continues to accept mail, and continues to count against licensed mailbox limits until an administrator removes it.

 它留下的缺口出現在帳戶生命週期的另一端。即時配置不會真正刪除任何內容，因為已刪除的目錄條目只是不再出現在查詢結果中，而不會發出任何通知。離職用戶的郵箱仍然存在，繼續接收郵件，並繼續佔用許可的郵箱容量，直到管理員將其刪除。

 Where that matters, SCIM provisioning can be enabled per domain so that the identity provider suspends and deletes accounts explicitly. Doing so makes SCIM authoritative for the accounts in that domain and stops just-in-time synchronisation from writing to them. Provisioning models compares the two and covers how authority is assigned.

 在需要時，可以針對每個網域啟用 SCIM配置 ，以便身分提供者明確暫停和刪除帳戶。這樣做會使SCIM成為該網域中帳戶的權威機構，並阻止即時同步寫入這些帳戶。 配置模型對兩者進行了比較，並介紹如何分配權限。

## Connection details｜連線詳情

 The minimum required configuration for LDAP is the URL of the directory server. The URL is set through url; a typical value is `"ldap://localhost:389"` for an unencrypted connection to a server on the same host.

 LDAP的最低設定要求是目錄伺服器的URL透過 \[ URL \]`url`設定；對於與同一主機上的伺服器建立的未加密連接\([https://stalw.art/docs/ref/object/directory#url\)典型值為\`"ldap://localhost:389"\`](https://stalw.art/docs/ref/object/directory#url%2529%2525E5%252585%2525B8%2525E5%25259E%25258B%2525E5%252580%2525BC%2525E7%252582%2525BA%252560%252522ldap://localhost:389%252522%252560) 。

 Related connection fields on the LDAP variant of the Directory object are:

 Directory 物件LDAP變體的相關連接欄位有：

- url: URL of the LDAP server.
url: URL的LDAP伺服器。
- useTls: whether to negotiate TLS on the connection. Default `false`.
useTls : 是否協商連接上的TLS 。預設值為`false` 。
- allowInvalidCerts: whether to accept invalid TLS certificates. Default `false`.
allowInvalidCerts : 是否接受無效的TLS證書。預設值為`false` 。
- timeout: connection timeout, in milliseconds. Default `30000` \(30 seconds\).
timeout : 連接逾時，以毫秒為單位。預設值為`30000` \(30 秒\)。
For example:
 例如：

```json
{
  "@type": "Ldap",
  "description": "Corporate LDAP",
  "url": "ldap://localhost:389",
  "timeout": 30000,
  "useTls": false,
  "allowInvalidCerts": false
}
```

## Default bind credentials｜預設綁定憑證

 Binding is the operation by which an LDAP client authenticates to the directory. To query the directory and validate account entries, Stalwart needs to bind using a service account that holds sufficient privileges to search the directory tree.

 綁定是指LDAP客戶端對目錄進行身份驗證的操作。為了查詢目錄並驗證帳戶條目，Stalwart需要使用具有足夠權限搜尋目錄樹的服務帳戶進行綁定。

 Service-account credentials are configured through:

 服務帳戶憑證透過以下方式設定：

- bindDn: the distinguished name of the account used to connect to the directory.
bindDn : 用於連接到目錄的帳戶的專有名稱。
- bindSecret: the secret associated with `bindDn`. Accepts a direct value, an environment-variable reference, or a file reference.
bindSecret : 與`bindDn`關聯的金鑰。接受直接值、環境變數引用或文件引用。
For example:
 例如：

```json
{
  "@type": "Ldap",
  "bindDn": "cn=admin,dc=example,dc=org",
  "bindSecret": {
    "@type": "Value",
    "secret": "password"
  }
}
```

If `bindDn` is left unset, the server attempts anonymous queries. Some directories allow that for basic lookups, but most require an authenticated bind. Without valid credentials, authentication or address validation may fail.

 如果未設定`bindDn` ，伺服器將嘗試匿名查詢。某些目錄允許進行基本查找，但大多數目錄需要經過身份驗證的綁定。如果沒有有效的憑證，身份驗證或地址驗證可能會失敗。

 Even when users authenticate by binding as themselves, the service-account bind is still required for non-authentication operations such as retrieving account metadata and validating email addresses and domains.

 即使使用者透過綁定自身進行身份驗證，對於檢索帳戶元資料、驗證電子郵件地址和網域等非身份驗證操作，仍需要服務帳戶綁定。

## Authentication methods｜身份驗證方法

 Stalwart supports two authentication modes against an LDAP directory, selected by the bindAuthentication boolean on the Directory object.

 Stalwart 支援針對LDAP目錄的兩種驗證模式，由 Directory 物件上的 bindAuthentication布爾值選取。

 In some LDAP environments, particularly hardened OpenLDAP setups and Active Directory, password hashes are not returned even to a privileged service account. In those environments Stalwart cannot compare a stored hash against the password supplied by the user, so it must authenticate by attempting to bind directly as the user. If the bind succeeds, the credentials are considered valid.

 在某些LDAP環境中，尤其是在強化型OpenLDAP配置和Active Directory環境中，即使是特權服務帳戶也不會傳回密碼雜湊值。在這些環境中，Stalwart無法將儲存的雜湊值與使用者提供的密碼進行比較，因此必須嘗試以使用者身分直接綁定進行身份驗證。如果綁定成功，則認為憑證有效。

### Service-account bind \(hash comparison\)｜服務帳戶綁定（哈希比較）

 When bindAuthentication is set to `false`, Stalwart uses the service account \(`bindDn` / `bindSecret`\) to search for the user entry, reads the password hash from the attribute configured by attrSecret, and compares it against the password supplied at login. This mode only works if the LDAP server exposes password hashes in a format that Stalwart recognises.

 當 bindAuthentication設定為`false`時，Stalwart 使用服務帳戶 \( `bindDn` / `bindSecret` \) 尋找使用者條目，從 attrSecret組設定值的屬性中讀取其設定值，並將其設定時所提供的密碼值將其設定值。此模式僅在LDAP伺服器以 Stalwart 可識別的格式公開密碼雜湊值時才有效。

 For example:

 例如：

```json
{
  "@type": "Ldap",
  "bindAuthentication": false,
  "attrSecret": {"userPassword": true}
}
```

This mode is only suitable when the LDAP server returns password hashes to the bind account. When the directory does not permit this \(for example, in many Active Directory environments\), use bind authentication instead.

 此模式僅適用於LDAP伺服器向綁定帳戶傳回密碼雜湊值的情況。如果目錄不允許這樣做（例如，在許多Active Directory環境中），請改用綁定驗證。

### Bind authentication｜綁定身份驗證

 When bindAuthentication is set to `true` \(the default\), Stalwart authenticates users by attempting to bind as the user themselves, using the password supplied at login. If the bind succeeds, the credentials are accepted. No password hash is read from the directory.

 當 bindAuthentication設定為`true` （預設值）時，Stalwart 會嘗試使用登入時提供的密碼以使用者身分進行綁定，以此來驗證使用者身分。如果綁定成功，則接受憑證。不會從目錄中讀取密碼雜湊值。

 In this mode, the user’s distinguished name is located by running the filterLogin search using the service account; the `?` placeholder in the filter is replaced with the login value. Once the DN is known, Stalwart attempts the user bind. Because the password hash is not available, Stalwart relies on the attrSecretChanged attribute \(by default `pwdChangeTime`\) to detect password changes and invalidate cached OAuth tokens.

 在此模式下，透過使用服務帳戶執行 filterLogin搜尋來尋找使用者的專有名稱；篩選器中的`?`佔位符將被替換為登入值。一旦確定了DN ，Stalwart 就會嘗試進行使用者綁定。由於密碼雜湊不可用，Stalwart 依賴 attrSecretChanged屬性（預設為`pwdChangeTime` ）來偵測密碼變更並使快取的 OAuth 令牌失效。

 For example:

 例如：

```json
{
  "@type": "Ldap",
  "bindAuthentication": true,
  "filterLogin": "(&(objectClass=inetOrgPerson)(mail=?))",
  "attrSecretChanged": {"pwdChangeTime": true}
}
```

## Lookup filters｜尋找過濾器

 Two LDAP filters drive account resolution: a login filter used at authentication time, and a mailbox filter used during email delivery.

 兩個LDAP過濾器驅動帳戶解析：一個登入過濾器用於身份驗證時，一個郵箱過濾器用於電子郵件傳遞期間。

- filterLogin: locates the LDAP entry that matches the login value supplied by the user. Default `"(&(objectClass=inetOrgPerson)(mail=?))"`.
filterLogin : 尋找與使用者提供的登入值相符的LDAP條目。預設值為`"(&(objectClass=inetOrgPerson)(mail=?))"` 。
- filterMailbox: locates a user or group entry that matches a recipient email address or alias. Default `"(|(&(objectClass=inetOrgPerson)(|(mail=?)(mailAlias=?)))(&(objectClass=groupOfNames)(|(mail=?)(mailAlias=?))))"`.
filterMailbox : 尋找與收件者電子郵件地址或別名相符的使用者或群組條目。預設值為`"(|(&(objectClass=inetOrgPerson)(|(mail=?)(mailAlias=?)))(&(objectClass=groupOfNames)(|(mail=?)(mailAlias=?))))"` 。
- filterMemberOf: locates the groups an account belongs to when group membership is not carried on the account entry. The `?` is replaced with the account DN. Default `"(&(objectClass=groupOfNames)(member=?))"`.
filterMemberOf：當帳戶條目中不包含群組成員身分時，定位帳戶所屬的群組。 `?` 替換為帳戶DN。預設`"(&(objectClass=groupOfNames)(member=?))"`。
Each filter contains a `?` placeholder that the server replaces at runtime: the login value for `filterLogin`, the recipient address for `filterMailbox`, or the account DN for `filterMemberOf`.
 每個過濾器都包含一個`?`佔位符，伺服器會在運行時替換它： `filterLogin`的登入值， `filterMailbox`的收件者地址，或`filterMemberOf`的帳戶DN 。

 For example:

 例如：

```json
{
  "@type": "Ldap",
  "filterLogin": "(&(|(objectClass=posixAccount)(objectClass=posixGroup))(uid=?))",
  "filterMailbox": "(&(|(objectClass=posixAccount)(objectClass=posixGroup))(|(mail=?)(mailAlias=?)))"
}
```

## Base DN｜底座DN

 Searches start from a base distinguished name configured through baseDn. The base DN sets the scope of every query and should be narrow enough to limit the search surface but broad enough to cover all relevant accounts.

 搜尋從透過 baseDn配置的基本專有名稱開始。基本專有名稱DN設定每個查詢的範圍，它應該足夠窄以限制搜尋範圍，但又應該足夠寬以涵蓋所有相關帳戶。

 For example, `"dc=example,dc=org"` restricts lookups to entries under the `example.org` organisation.

 例如， `"dc=example,dc=org"`將查找限制在`example.org`組織下的條目。

## Object attributes｜物件屬性

 LDAP schemas vary between servers, so Stalwart has to be told which attributes to read for each piece of account information. The mapping is carried on the LDAP variant of the Directory object through the following fields:

 LDAP不同伺服器的架構各不相同，因此必須告知 Stalwart 要讀取每個帳戶資訊的哪些屬性。映射關係透過目錄物件的LDAP變體上的以下欄位來實現：

 Each of these fields is a set of attribute names.

 這些欄位中的每一個都是一組屬性名稱。

- attrClass: attribute\(s\) carrying the account’s object class. Defaults to `{"objectClass": true}`. An account entry is treated as an individual unless its class matches groupClass, which defaults to `"groupOfNames"`.
attrClass : 承載帳戶物件類別的屬性。預設為`{"objectClass": true}` 。除非帳戶條目的類別與 groupClass匹配（預設為`"groupOfNames"` ），否則該帳戶條目將被視為個體。
- attrDescription: attribute\(s\) used as the account description. Default `{"description": true}`.
attrDescription : 用作帳戶描述的屬性。預設值為`{"description": true}` 。
- attrSecret: attribute carrying the password hash, used only when `bindAuthentication` is `false`. Default `{"userPassword": true}`.
attrSecret : 攜帶密碼哈希的屬性，僅當`bindAuthentication`為`false`時使用。預設值為`{"userPassword": true}` 。
- attrSecretChanged: attribute carrying the last password-change timestamp \(or version value\), used to invalidate OAuth tokens in bind-authentication mode. Default `{"pwdChangeTime": true}`.
attrSecretChanged : 攜帶上次密碼變更時間戳記（或版本值）的屬性，用於在綁定驗證模式下使 OAuth 令牌失效。預設值為`{"pwdChangeTime": true}` 。
- attrMemberOf: attribute\(s\) listing the groups an account belongs to. Default `{"memberOf": true}`.
attrMemberOf : 列出帳戶所屬群組的屬性。預設值為`{"memberOf": true}` 。
- attrEmail: attribute carrying the primary email address. Default `{"mail": true}`.
attrEmail : 包含主要電子郵件地址的屬性。預設值為`{"mail": true}` 。
- attrEmailAlias: attribute carrying email aliases. Default `{"mailAlias": true}`.
attrEmailAlias : 攜帶電子郵件別名的屬性。預設值為`{"mailAlias": true}` 。
There is no attribute mapping for the account’s login name or for a per-account disk quota: the login name is resolved from the entry returned by filterLogin, and disk quotas are held on the Account and Tenant objects rather than read from the directory \(see Quotas\).
 帳戶登入名稱或每個帳戶的磁碟配額沒有屬性對應：登入名稱是從 filterLogin傳回的條目解析的，磁碟配額保存在 Account和 Tenant物件中， \([https://stalw.art/docs/auth/authorization/quotas\)不是從目錄中讀取。](https://stalw.art/docs/auth/authorization/quotas%2529%2525E4%2525B8%25258D%2525E6%252598%2525AF%2525E5%2525BE%25259E%2525E7%25259B%2525AE%2525E9%25258C%252584%2525E4%2525B8%2525AD%2525E8%2525AE%252580%2525E5%25258F%252596%2525E3%252580%252582)

 For example:

 例如：

```json
{
  "@type": "Ldap",
  "attrClass": {"objectClass": true},
  "attrDescription": {"principalName": true, "description": true},
  "attrSecret": {"userPassword": true},
  "attrMemberOf": {"memberOf": true, "otherGroups": true},
  "attrEmail": {"mail": true},
  "attrEmailAlias": {"mailAlias": true}
}
```
