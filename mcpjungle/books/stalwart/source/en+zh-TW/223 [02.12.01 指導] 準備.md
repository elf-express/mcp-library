# Preparation｜準備

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[guide｜指導\\\]\\\(&lt;000 目錄.md#c-38&gt;\\\)

The migration relies on four components running alongside the existing deployment: the new Stalwart server, the Stalwart command-line interface, the migration proxy and Vandelay. This stage installs all four. None of them touches the live server, so the entire stage is performed without downtime and without any change visible to existing clients.

 此次遷移依賴與現有部署並行運行的四個元件：新的 Stalwart 伺服器、Stalwart 命令列介面、遷移代理程式和 Vandelay。此階段將安裝所有這四個組件。由於它們都不會影響生產伺服器，因此整個階段無需停機，現有客戶端也不會感知到任何變化。

 The guide assumes an existing, running self-hosted mail server, referred to throughout as the source: either a Stalwart deployment of version 0.15 or below, or a Dovecot and Postfix stack such as Mail-in-a-Box or mailcow. The goal is to move its accounts onto a fresh installation of the latest Stalwart release, referred to as the new deployment.

 本指南假設您已擁有一個正在執行的自託管郵件伺服器（以下簡稱「來源」）：可以是版本為0.15或更低的 Stalwart 部署，也可以是 Dovecot 和 Postfix 的組合，例如 Mail-in-a-Box 或 mailcow。目標是將這些帳戶遷移到最新 Stalwart 版本的全新安裝（以下簡稱「新部署」）。

## Planning the addresses｜規劃地址

 The proxy will eventually take over the public ports that the source currently answers on, so the source and the new deployment need to be reachable at addresses of their own that the proxy can forward to. A common arrangement gives each an internal hostname, for example `source.internal.example.org` and `new.internal.example.org`, while the public hostname that clients already use, such as `mail.example.org`, is repointed to the proxy at the cutover. Deciding on these addresses now makes the configuration that follows straightforward. No public DNS change is made yet; the public hostname continues to resolve to the source until the cutover.

 代理最終會接管來源伺服器目前使用的公共端口，因此來源伺服器和新部署都需要擁有各自的位址，以便代理可以轉送流量。常見的做法是為每個伺服器指派一個內部主機名，例如`source.internal.example.org`和`new.internal.example.org` ，而客戶端已使用的公用主機名稱（例如`mail.example.org` ）則會在切換時重新指向代理程式。確定這些位址後，後續的配置將變得非常簡單。目前尚未更改公共主機名稱DNS ；在切換之前，該公共主機名稱仍會解析到來源伺服器。

## Installing the new Stalwart deployment｜安裝新的 Stalwart 部署

 The new deployment is installed as a normal, fresh Stalwart server following the standard [installation instructions](https://stalw.art/docs/install/platform/) for the target platform. It is installed on its own host or address rather than over the existing server, because both deployments must run at the same time. The initial setup creates an administrator account, which the later steps use to create domains and accounts and to configure split delivery.

 新部署將依照目標平台的標準[安裝說明](https://stalw.art/docs/install/platform/)進行安裝，如同安裝一台全新的 Stalwart 伺服器。它安裝在獨立的獨立主機或位址上，而不是覆蓋現有伺服器，因為兩個部署必須同時運作。初始設定會建立管理員帳戶，後續步驟將使用該帳戶建立網域和帳戶，並配置分割交付。

 The configuration model, the administration interface and the storage layout changed substantially after version 0.15. Becoming familiar with the latest release before relying on it in production is strongly recommended. The configuration and management sections describe the current model, and the next step of this guide assumes a working understanding of how the new server is administered.

 自版本0.15起，配置模型、管理介面和儲存佈局均發生了顯著變化。強烈建議在生產環境中使用最新版本之前，先熟悉其操作。 配置和管理部分介紹了當前模型，本指南的下一步假設您已對新伺服器的管理方式有所了解。

## Installing the command-line interface｜安裝命令列介面

 The Stalwart command-line interface administers the new deployment and applies the account-creation plans produced during the migration. It is installed by following its installation instructions. The interface is schema-driven: it reads the server’s schema on connection and derives its commands from it, so the version installed works against the new deployment without further configuration.

 Stalwart 命令列介面用於管理新部署，並​​套用遷移過程中產生的帳戶建立計畫。它按照其安裝說明進行安裝。此介面基於模式驅動：它會在連接時讀取伺服器的模式並從中派生命令，因此安裝的版本無需額外配置即可用於新部署。

## Installing the migration proxy｜安裝遷移代理

 The migration proxy is installed on the host that will front the public ports, following the proxy installation instructions. Installing it does not start it with a working configuration yet; the proxy is configured in a later step and is only started at the cutover. Until then its presence has no effect on the running system.

 遷移代理安裝在將要連接公共連接埠的主機上，請依照代理安裝說明進行操作。安裝完成後，代理程式不會立即啟動並運行；代理程式的配置將在後續步驟中進行，並且僅在系統切換時啟動。在此之前，代理程式的存在對正在運行的系統沒有任何影響。

## Installing Vandelay｜安裝 Vandelay

 Vandelay performs the per-account data transfer. It is installed on an administrative host that can reach both deployments, following its installation instructions. Vandelay is a single self-contained binary and stores each account it processes in a local archive file, so the host it runs on needs enough disk space to hold the largest mailbox being migrated at any one time.

 Vandelay 執行按帳戶進行的資料傳輸。它安裝在可以存取兩個部署環境的管理主機上，具體安裝步驟請參考其安裝說明是一個獨立的二進位文件，它會將處理的每個帳戶儲存在本地歸檔文件中，因此運行它的主機需要足夠的磁碟空間來容納任何給定時間要遷移的最大郵箱。

## Rollback｜復原

 Nothing installed in this stage alters the source or the path that clients take to it. Abandoning the migration here requires no rollback: the additional components can simply be left unused or removed, and the source continues to operate exactly as before.

 此階段安裝的任何內容都不會改變原始程式碼或用戶端存取原始程式碼的路徑。在此放棄遷移無需回滾：只需將新增元件棄用或移除，原始程式碼將繼續按原樣運行。
