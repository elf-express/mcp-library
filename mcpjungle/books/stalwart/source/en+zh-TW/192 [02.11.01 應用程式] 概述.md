# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[management｜管理\\\]\\\(&lt;000 目錄.md#c-31&gt;\\\) › \\\[applications｜應用程式\\\]\\\(&lt;000 目錄.md#c-32&gt;\\\)

Stalwart can download and host one or more single-page applications \(SPAs\) directly from the server. Each hosted application is configured on the Application object \(found in the WebUI under Settings › Web Applications\) and is served alongside the regular HTTP endpoints, without the need for a separate web server or reverse proxy in front.

 Stalwart 可以直接從伺服器下載並託管一個或多個單頁應用程式 \(SPA\)。每個託管的應用程式都在 Application物件（可在 WebUI 的「設定」&gt;「Web 應用程式」下找到）中進行配置，並與常規的HTTP端點一起提供服務，無需單獨的 Web 伺服器或反向代理。

 The built-in WebUI is itself an Application: a single bundle mounted at both `/admin` \(the administration console\) and `/account` \(the user self-service portal\). Operators can register additional Applications on the same server, for example third-party management dashboards or self-hosted front-ends for the JMAP, CalDAV, CardDAV, and WebDAV stacks.

 內建的 WebUI本身就是一個應用程式：一個同時掛載到`/admin` （管理控制台）和`/account` （用戶自助服務入口網站）的單一軟體包。營運商可以在同一台伺服器上註冊其他應用程序，例如第三方管理儀表板或JMAP 、CalDAV、CardDAV 和 WebDAV 協定堆疊的自架前端。

## What an Application is｜什麼是應用程式

 An Application is a static SPA bundle, distributed as a zip archive, that the server downloads and unpacks locally. Once unpacked, the server serves the application’s files in response to HTTP requests whose path matches one of the configured mount paths. The bundle is identified by the resourceUrl field, which points to the archive that will be fetched \(for example the latest GitHub release of the WebUI\), and by the description field, which carries a short human-readable label used in the management interfaces.

 應用程式是一個靜態的SPA包，以 zip 壓縮包的形式分發，伺服器會下載並在本地解壓縮。解壓縮後，伺服器會回應HTTP請求，提供應用程式的文件，前提是請求路徑與已配置的掛載路徑之一相符。該套件由 resourceUrl字段標識，該字段指向將要獲取的壓縮包（例如，WebUI 的最新 GitHub 版本），以及 description字段標識，該字段包含一個簡短易讀的標籤，用於管理界面。

 Individual Applications can be disabled without removing them from the configuration by clearing the enabled flag. A disabled Application is not downloaded and is not served, but its configuration is retained.

 可以透過清除 enabled標誌來停用單一應用程序，而無需將其從配置中移除。禁用的應用程式不會被下載或提供服務，但其配置將被保留。

## Mount paths｜掛載路徑

 Each Application is mounted at one or more URL path prefixes, listed on the urlPrefix field. The server matches incoming HTTP requests against the configured prefixes and routes them to the corresponding bundle. A single Application may declare multiple prefixes, which is how the WebUI is exposed at both `/admin` and `/account` from the same deployment.

 每個應用程式都掛載到一個或多個路徑前綴URL ，這些前綴列在 urlPrefix欄位中。伺服器會將傳入的HTTP請求與配置的前綴進行匹配，並將它們路由到相應的捆綁包。單一應用程式可以聲明多個前綴，這就是為什麼 WebUI 可以從同一部署同時在`/admin`和`/account`上公開的原因。

 Mount paths are local to the server’s HTTP namespace and must not collide with the API endpoints used by JMAP, WebDAV, or the `.well-known` URIs. A path collision between two Applications, or between an Application and a server-provided endpoint, is rejected at configuration time.

 掛載路徑位於伺服器的HTTP命名空間內，不得與JMAP 、WebDAV或`.well-known` URI所使用的API端點衝突。兩個應用程式之間或應用程式與伺服器提供的端點之間的路徑衝突將在配置時被拒絕。

## The unpack directory｜解壓縮目錄

 The unpacked bundle is written to a working directory on the local filesystem, named by the unpackDirectory field. When the field is empty the system temporary directory is used, which on Linux means `/tmp`.

 解壓縮後的套件被寫入本機檔案系統上的一個工作目錄，該目錄由 unpackDirectory欄位命名。當該欄位為空時，則使用系統暫存目錄，在 Linux 系統中，這意味著`/tmp` 。

 Leaving it empty is a poor choice on any host that sweeps `/tmp`. `systemd-tmpfiles-clean` deletes files by access time, and most of an SPA bundle consists of chunks that are only loaded on particular screens, so they are never read again after the first visit and age out while the entry point and the login page stay fresh. The result is a server that appears to work until an operator opens a section it has not served in a while, and the browser reports that it could not fetch a dynamically imported module. Restarting clears it, because startup unpacks the bundle again, and it comes back on the same schedule. Point `unpackDirectory` at a persistent path, for example `/var/lib/stalwart/webui`, on any deployment where `/tmp` is swept or mounted `noexec`.

 在任何會根據存取時間刪除檔案的主機上，將`/tmp`. `systemd-tmpfiles-clean`留空都是一個糟糕的選擇SPA包的大部分內容都只在特定螢幕上加載，因此在首次訪問後就不會再被讀取，並會隨著時間推移而過期，而入口點和登錄頁面則保持最新狀態。結果是，伺服器看起來運作正常，直到操作員開啟一個一段時間未造訪的頁面，瀏覽器才會報告無法取得動態匯入的模組。重新啟動伺服器可以解決這個問題，因為啟動時會重新解包，然後它會按照相同的時間表恢復。在任何部署中，如果`/tmp`被清理或掛載到`noexec` ，則應將`unpackDirectory`指向一個持久路徑，例如`/var/lib/stalwart/webui` 。

 The server creates the directory if it is missing, including any missing parents, but it does so as the user the service runs as. On a package installation that user is `stalwart`, so a directory under `/var/lib` that is owned by `root` will fail to unpack until its ownership is corrected.

 如果目錄缺失，伺服器會建立該目錄（包括任何缺少的父目錄），但它是以服務運行使用者的身分執行此操作的。在軟體包安裝過程中，該用戶是`stalwart` ，因此，如果`/var/lib`下的目錄的所有者是`root` ，則該目錄將無法解包，直到其所有權被更正為止。

 Within `unpackDirectory` the server keeps one subdirectory per Application record, and one subdirectory below that per unpacked bundle. Files are written under numeric names, and the mapping back to the names in the archive is held in memory only. A bundle extracted by hand into `unpackDirectory` is therefore never served, no matter where under it the files are placed. To install a bundle without outbound access to the publisher, stage the `.zip` on an internal HTTPS server and point resourceUrl at it.

 在`unpackDirectory`目錄下，伺服器為每個應用程式記錄維護一個子目錄，每個解壓縮後的軟體包又在其下方維護一個子目錄。檔案以數字名稱寫入，與歸檔檔案中的名稱的映射關係僅保存在記憶體中。因此，無論檔案位於`unpackDirectory`目錄下的哪個位置，手動提取到該目錄下的軟體包都不會被提供服務。若要在無法存取發布伺服器的情況下安裝軟體包，請將`.zip`目錄暫存到內部HTTPS伺服器上，並將 resourceUrl指向該目錄。

## Relationship to listeners｜與聽眾的關係

 Applications are served over HTTP traffic, but they do not themselves open sockets. The sockets are owned by the NetworkListener object \(found in the WebUI under Settings › Network › Listeners\). Any listener configured with the protocol variant set to `http` will route requests whose path matches a registered mount to the corresponding Application. In a typical deployment a single HTTPS listener carries the JMAP, WebDAV, and Application traffic together; no per-Application listener is required.

 應用程式透過HTTP流量提供服務，但它們本身並不會打開套接字。套接字由 NetworkListener物件擁有（可在 WebUI 的「設定」&gt;「網路」&gt;「監聽器」中找到）。任何配置了 protocol變體並設定為`http`監聽器，都會將路徑與已註冊掛載點相符的請求路由到對應的應用程式。在典型的部署中，單一HTTPS監聽器會同時承載JMAP 、WebDAV 和應用程式流量；無需為每個應用程式單獨配置監聽器。

 When access control rules are in force, requests to Application mount paths are filtered alongside the rest of the HTTP surface. Operators restricting public exposure can therefore confine an Application \(for example `/admin`\) to a private listener while leaving the remaining HTTP endpoints reachable over the public one.

 當 存取控制規則生效時，對應用程式掛載路徑的請求將與HTTP的其他介面一起進行過濾。因此，限制公共存取的操作人員可以將應用程式（例如`/admin` ）限制在私有監聽器中，同時保持其餘HTTP端點可透過公共端點存取。

## Installing an Application｜安裝應用程式

 An Application is installed by creating an Application record with the bundle’s download URL in resourceUrl, the desired mount paths in urlPrefix, and a short description. The server then fetches the archive, unpacks it into the working directory, and begins serving the files; the Updates page covers how a bundle is refreshed afterwards. The same workflow is exposed through the WebUI, through `stalwart-cli`, and directly over the JMAP API on the `x:Application/set` method.

 應用程式的安裝方式為：在 resourceUrl中建立 Application記錄，其中包含軟體包的下載位址URL ，在`description` `urlPrefix` \([https://stalw.art/docs/ref/object/application#urlprefix](https://stalw.art/docs/ref/object/application#urlprefix)\) \([https://stalw.art/docs/ref/object/application#description\)說明。伺服器隨後會取得歸檔文件，將其解壓縮到工作目錄，並開始提供文件服務；\\[Updates\\]](https://stalw.art/docs/ref/object/application#description%2529%2525E8%2525AA%2525AA%2525E6%252598%25258E%2525E3%252580%252582%2525E4%2525BC%2525BA%2525E6%25259C%25258D%2525E5%252599%2525A8%2525E9%25259A%2525A8%2525E5%2525BE%25258C%2525E6%25259C%252583%2525E5%25258F%252596%2525E5%2525BE%252597%2525E6%2525AD%2525B8%2525E6%2525AA%252594%2525E6%252596%252587%2525E4%2525BB%2525B6%2525EF%2525BC%25258C%2525E5%2525B0%252587%2525E5%252585%2525B6%2525E8%2525A7%2525A3%2525E5%2525A3%252593%2525E7%2525B8%2525AE%2525E5%252588%2525B0%2525E5%2525B7%2525A5%2525E4%2525BD%25259C%2525E7%25259B%2525AE%2525E9%25258C%252584%2525EF%2525BC%25258C%2525E4%2525B8%2525A6%2525E9%252596%25258B%2525E5%2525A7%25258B%2525E6%25258F%252590%2525E4%2525BE%25259B%2525E6%252596%252587%2525E4%2525BB%2525B6%2525E6%25259C%25258D%2525E5%25258B%252599%2525EF%2525BC%25259B%25255BUpdates%25255D)\(&lt;193 \[02.11.01 應用程式\] 更新.md&gt;\)頁面介紹了軟體包後續的更新方式。同樣的流程也可透過 WebUI `stalwart-cli` ）以及直接透過`x:Application/set` JMAP API來實現。

## Outbound network requirement｜出站網路需求

 Each Application’s bundle is fetched over HTTPS from the resourceUrl configured on its record, so outbound HTTPS connectivity from the Stalwart host to that URL is a hard requirement for the Application to be served. When the very first download of an Application fails, no previously installed bundle exists to fall back to and HTTP requests against the Application’s mount paths return `404 Not Found` until the next refresh succeeds.

 每個應用程式的軟體包都透過HTTPS從其記錄中配置的 resourceUrl獲取，因此，從 Stalwart 主機到該URL的出站HTTPS連接是應用程式正常運作的硬性要求。如果應用程式的首次下載失敗，則沒有先前安裝的軟體包可供回退， HTTP對應用程式掛載路徑的請求將返回`404 Not Found`直到下次刷新成功。

 For deployments behind a restrictive egress firewall, the firewall must allow HTTPS from the Stalwart host to whatever hosts serve each configured `resourceUrl`. When outbound internet access is not permitted at all, the bundle can be staged on an internal HTTPS server and the resourceUrl field updated to point at the internal location, after which the server refreshes from there instead.

 對於部署在限制性出口防火牆後的場景，防火牆必須允許 Stalwart 主機`resourceUrl` HTTPS服務的主機。如果完全禁止出站互聯網訪問，則可以將軟體包暫存在內部HTTPS伺服器上，並將 resourceUrl字段更新為指向該內部位置，之後伺服器將從該位置刷新。

 The bundle URL of the built-in WebUI and the specific symptom that misconfiguring this requirement produces are documented under the WebUI overview.

 內建 WebUI 的捆綁包URL以及錯誤配置此要求所產生的具體症狀已記錄在 WebUI 概述中。

## Bundle format｜捆綁格式

 An Application bundle is a `.zip` archive that must contain an `index.html` at its root. When the archive is unpacked, the server rewrites the `` tag in `index.html` to match the mount path the bundle is served from, so the same archive can be mounted at `/admin`, `/account`, or any other prefix without being repackaged. Assets referenced by relative URLs inside the bundle therefore resolve correctly regardless of the mount path.

 應用程式包是一個`.zip`歸檔文件，其根目錄必須包含一個`index.html`標籤。當歸檔檔案解壓縮時，伺服器會重寫`index.html`中的``標籤，使其與應用程式套件的掛載路徑相符。因此，同一個歸檔檔案可以掛載到`/admin`, `/account`或任何其他前綴，而無需重新打包。這樣，無論掛載路徑如何，包內透過相對 URL 引用的資源都能正確解析。

 No checksum or signature verification is performed on the downloaded archive. Applications are intended to be installed from trusted sources only; the transport is always HTTPS, but the contents of the bundle are not cryptographically validated against an external manifest.

 下載的壓縮包不會進行校驗和或簽章驗證。應用程式僅建議從可信任來源安裝；傳輸協定始終為HTTPS ，但軟體包內容不會根據外部清單進行加密驗證。

 Because no bundle-level signature is checked, only install Applications whose resourceUrl points at a source operated by a trusted publisher. A malicious bundle served from a hostile origin would be unpacked and served just like any other Application.

 由於未檢查捆綁包層級的簽名，因此僅安裝\([https://stalw.art/docs/ref/object/application#resourceurl\)受信任發布者營運的來源的應用程式。來自\`resourceUrl\`來源的惡意捆綁包將像其他任何應用程式一樣被解包和運行。](https://stalw.art/docs/ref/object/application#resourceurl%2529%2525E5%25258F%252597%2525E4%2525BF%2525A1%2525E4%2525BB%2525BB%2525E7%252599%2525BC%2525E5%2525B8%252583%2525E8%252580%252585%2525E7%252587%25259F%2525E9%252581%25258B%2525E7%25259A%252584%2525E4%2525BE%252586%2525E6%2525BA%252590%2525E7%25259A%252584%2525E6%252587%252589%2525E7%252594%2525A8%2525E7%2525A8%25258B%2525E5%2525BC%25258F%2525E3%252580%252582%2525E4%2525BE%252586%2525E8%252587%2525AA%252560resourceUrl%252560%2525E4%2525BE%252586%2525E6%2525BA%252590%2525E7%25259A%252584%2525E6%252583%2525A1%2525E6%252584%25258F%2525E6%25258D%252586%2525E7%2525B6%252581%2525E5%25258C%252585%2525E5%2525B0%252587%2525E5%252583%25258F%2525E5%252585%2525B6%2525E4%2525BB%252596%2525E4%2525BB%2525BB%2525E4%2525BD%252595%2525E6%252587%252589%2525E7%252594%2525A8%2525E7%2525A8%25258B%2525E5%2525BC%25258F%2525E4%2525B8%252580%2525E6%2525A8%2525A3%2525E8%2525A2%2525AB%2525E8%2525A7%2525A3%2525E5%25258C%252585%2525E5%252592%25258C%2525E9%252581%25258B%2525E8%2525A1%25258C%2525E3%252580%252582)

## Multiple mount paths for a single Application｜單一應用程式的多個掛載路徑

 The built-in WebUI is modelled as one Application with two entries in urlPrefix, `/admin` and `/account`; the prefixes are URL-path aliases for the same bundle rather than two separate installations. Additional Applications can follow the same pattern when several aliases need to resolve to the same files.

 內建的 WebUI 被建模為一個應用程序，在 \[ `urlPrefix` \] 中有兩個條目： \([https://stalw.art/docs/ref/object/application#urlprefix](https://stalw.art/docs/ref/object/application#urlprefix)\), `/admin`和`/account` ；前綴URL是同一個軟體包的路徑別名，而不是兩個獨立的安裝。當多個別名需要解析到相同的檔案時，其他應用程式可以遵循相同的模式。
