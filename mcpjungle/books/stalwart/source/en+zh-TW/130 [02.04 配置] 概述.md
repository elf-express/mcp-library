# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[configuration｜配置\\\]\\\(&lt;000 目錄.md#c-18&gt;\\\)

Stalwart is configured through a small startup file called `config.json` and a database that holds everything else. When the server starts, it reads `config.json` to learn where the database is, connects to it, and loads the rest of its configuration from there. Every setting \(domains, accounts, TLS certificates, SMTP rules, rate limits, and so on\) lives in that database as a structured object.

 Stalwart 的配置是透過一個名為`config.json`的小型啟動檔案和一個儲存所有其他配置的資料庫完成的。伺服器啟動時，它會讀取`config.json`來確定資料庫的位置，連接到該資料庫，並從中載入其餘配置。所有設定（網域名稱、帳戶、 TLS憑證、 SMTP規則、速率限制等等）都以結構化物件的形式儲存在該資料庫中。

 Those objects are not edited by hand. The server exposes them over a JMAP API, and two tools make that API easy to use:

 這些物件並非手動編輯。伺服器透過JMAP API介面公開它們，而兩個工具使API介面的使用變得簡單：

 The WebUI is the browser-based administration console. It includes a setup wizard for first-time installations and forms for every configurable object. Most operators only ever need this.

 WebUI是基於瀏覽器的管理控制台。它包含首次安裝的設定精靈以及每個可配置物件的表單。大多數操作員只需要這些功能。

 The CLI \(`stalwart-cli`\) calls the same JMAP API from the command line. It is the right tool for scripting, automation, and declarative deployments on platforms such as NixOS, Ansible or Terraform.

 CLI \( `stalwart-cli` \) 從命令列呼叫相同的JMAP API 。它是用於在 NixOS、Ansible 或 Terraform 等平台上進行腳本編寫、自動化和聲明式部署的理想工具。

 This arrangement differs from the traditional model of a Unix daemon driven by a large configuration file. The trade-off is that every setting is validated before it is saved, changes propagate across every node in a cluster, and backing up or cloning a deployment becomes a single operation against the API.

 這種安排與由大型設定檔驅動的傳統 Unix 守護程式模型不同。其優點是，每個設定都會在保存之前進行驗證，更改會傳播到叢集中的每個節點，並且備份或克隆部署成為針對API的單一操作。

## Configuration file｜設定檔

 The path to `config.json` is passed on the command line with `--config`:

`config.json`的路徑透過命令列`--config`傳遞：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart --config /etc/stalwart/config.json
```

The file contains a single DataStore object telling Stalwart where its database lives. A minimal file for a single-node installation backed by RocksDB looks like this:

 該檔案包含一個 DataStore對象，用於告知 Stalwart 其資料庫的位置。一個基於 RocksDB 的單節點安裝的最小設定檔如下所示：

```json
{"@type":"RocksDb","path":"/var/lib/stalwart/"}
```

RocksDB is the default backend variant and works well for most single-node deployments; PostgreSQL, MySQL, SQLite and FoundationDB are also supported. Each variant has its own set of fields, documented on the DataStore reference page.

 RocksDB 是預設的後端資料庫，適用於大多數單節點部署；此外，還支援 PostgreSQL、MySQL、SQLite 和 FoundationDB。每種資料庫都有其自身的欄位集，詳情請參閱 DataStore參考頁。

 Once the server is running, `config.json` is rarely touched again. The datastore location is the only setting that cannot be changed through the API, because the API itself is served out of the datastore.

 伺服器運行後， `config.json`很少再被修改。資料儲存位置是唯一無法透過API更改的設置，因為API本身就是從資料儲存中提供服務的。

## Applying changes｜應用程式變更

 Not every setting becomes active the moment it is saved.

 並非所有設定都會在儲存後立即生效。

 Directory data \(accounts, domains, mailing lists, aliases, group memberships\) takes effect immediately. Saving one of these objects invalidates the affected cache entries on the local node and broadcasts the invalidation to the rest of the cluster, so the next lookup already sees the new value.

 目錄資料（帳戶、網域、郵件清單、別名、群組成員關係）會立即生效。保存這些物件之一會使本機節點上受影響的快取條目失效，並將失效資訊廣播到叢集中的其他節點，以便下次查找時能夠看到新值。

 Server configuration that is compiled into the running core does not. Listeners, MTA rules and expressions \(routing, queue and TLS strategies, address rewriting, DKIM signing\), directory backends and telemetry settings are parsed once into an in-memory snapshot, and saving the object updates the database without rebuilding that snapshot. The new value applies only after a ReloadSettings action, which rebuilds the snapshot and broadcasts the reload to every node:

 編譯到運行核心中的伺服器配置不會受到影響。監聽器、 MTA規則和表達式（路由、佇列和TLS策略、位址重寫、 DKIM簽章）、目錄後端和遙測設定會被解析一次並儲存到記憶體快照中，儲存物件會更新資料庫，而無需重建該快照。新值僅在執行 ReloadSettings 操作後生效，該操作會重建快照並將重新載入資訊廣播到每個節點：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli create Action/ReloadSettings
```

The same action is available in the WebUI under Management, Actions. TLS certificates, lookup stores and blocked IP lists have their own narrower reload actions, which are cheaper than a full settings reload.

 WebUI 中的「管理」、「操作」下也提供相同的操作。 TLS 憑證、尋找儲存和封鎖的 IP 清單都有自己的更窄的重新載入操作，這比完整設定重新載入更便宜。

## Safe defaults｜安全預設值

 Stalwart exposes over 2,400 individual settings, spread across 117 JMAP configuration objects, which the WebUI surfaces across 176 screens \(one form per singleton, and a form plus a list view for every collection\). In addition to those settings, the server defines 659 permissions, 339 metrics, and 671 event types that can be granted, scoped, or matched against alerting and logging rules independently.

 Stalwart 公開了超過 2400 個獨立設置，分佈在 117 個JMAP配置物件中，這些設定透過 WebUI 在 176 個螢幕上呈現（每個單例對應一個表單，每個集合對應一個表單和一個清單視圖）。除了這些設定之外，伺服器還定義了 659 個權限、339 個指標和 671 個事件類型，這些權限、指標和事件類型可以獨立地被授予、限定範圍，或與警告和日誌記錄規則進行比對。

 At first encounter this surface can feel overwhelming, but new operators are not expected to walk through it. Every setting ships with a safe default chosen to produce a hardened, production-ready configuration on the very first start: TLS is required on the listeners where it should be, authentication policy is strict, rate limits are conservative, spam filtering is active with sensible thresholds, logging is enabled, and so on. There is no need to audit every field to check that it makes sense; the defaults are already sound. Attention can be focused exclusively on the aspects of the deployment that require customisation.

 初次接觸時，這套系統介面可能會讓人感到不知所措，但新維運人員無需逐一摸索。每個設定都預設了安全的預設值，確保首次啟動即可獲得一套安全可靠、可用於生產環境的配置：監聽器上已啟用TLS如適用），身份驗證策略嚴格，速率限制保守，垃圾郵件過濾已啟用並設定了合理的閾值，日誌記錄已啟用等等。無需逐一檢查每個欄位是否合理；預設值已經足夠完善。您可以將精力集中在需要自訂的部署方面。

 The default value of every field, along with its type and a short description, is documented on the object’s page in the schema reference.

 每個欄位的預設值、類型和簡短描述都記錄在物件的 模式參考頁面中。

## Recovery & Bootstrap modes｜恢復模式和引導模式

 If `config.json` is absent, Stalwart starts in bootstrap mode and exposes an initial setup flow served from the browser. If `config.json` is present but the deployment requires maintenance, Stalwart can be started in recovery mode to suspend all services and expose only the management API. Both modes, along with a few cluster-related behaviours, are controlled by a handful of environment variables. For platforms such as NixOS, Ansible and Terraform, the declarative deployments page describes how to manage `config.json` and the rest of the configuration as code.

 如果`config.json`不存在，Stalwart 將以 引導模式啟動，並透過瀏覽器提供初始設定流程。如果`config.json`存在，但部署需要維護，則可以以 恢復模式啟動 Stalwart，暫停所有服務，僅提供管理API 。這兩種模式以及一些群集相關行為均由少量 環境變數控制。對於 NixOS、Ansible 和 Terraform 等平台，聲明式部署頁面介紹如何以程式碼形式管理`config.json`和其餘設定。
