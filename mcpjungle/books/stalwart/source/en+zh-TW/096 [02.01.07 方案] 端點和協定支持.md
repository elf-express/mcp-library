# Endpoints and protocol support｜端點和協定支持

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[auth｜認證\\\]\\\(&lt;000 目錄.md#c-3&gt;\\\) › \\\[scim｜方案\\\]\\\(&lt;000 目錄.md#c-10&gt;\\\)

Every SCIM endpoint is served under `/scim/v2` on the standard HTTP listeners. Requests and responses use the `application/scim+json` media type, including error responses, as required by [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644) section 8.1. A `OPTIONS` request to any path under the base returns `204 No Content`, which satisfies clients that probe with a preflight request before their first call.

 每個SCIM端點都由標準HTTP監聽器在`/scim/v2`下提供服務。請求與回應（包括錯誤回應）皆使用`application/scim+json`媒體類型，符合 [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644)節8.1的要求。對基址下任何路徑的`OPTIONS`請求都會回傳`204 No Content` ，這滿足了在首次呼叫之前使用預檢請求進行探測的客戶端的需求。

## Endpoints｜終點

| Endpoint 端點 | Methods 方法 | Authentication 驗證 |
| --- | --- | --- |
| `/scim/v2/Users` | `GET`, `POST` | Bearer token 持有者代幣 |
| `/scim/v2/Users/{id}` | `GET`, `PUT`, `PATCH`, `DELETE` | Bearer token 持有者代幣 |
| `/scim/v2/Users/.search` | `POST` | Bearer token 持有者代幣 |
| `/scim/v2/Groups` | `GET`, `POST` | Bearer token 持有者代幣 |
| `/scim/v2/Groups/{id}` | `GET`, `PUT`, `PATCH`, `DELETE` | Bearer token 持有者代幣 |
| `/scim/v2/Groups/.search` | `POST` | Bearer token 持有者代幣 |
| `/scim/v2/.search` | `POST` | Bearer token 持有者代幣 |
| `/scim/v2/Bulk` | `POST` | Bearer token 持有者代幣 |
| `/scim/v2/ServiceProviderConfig` | `GET` | None 無 |
| `/scim/v2/ResourceTypes`, `/scim/v2/ResourceTypes/{id}` | `GET` | None 無 |
| `/scim/v2/Schemas`, `/scim/v2/Schemas/{urn}` | `GET` | None 無 |
| `/scim/v2/Me` | any 任意 | Returns `501` 回傳`501` |

The three discovery endpoints are readable without authentication, which is permitted by RFC 7644 and expected by clients that probe a target before credentials have been configured. They expose the shape of the service and no account data. Where even that is unwanted, restrict the path by address as described under Restricting network access. Filtering is not accepted on the discovery endpoints; a `filter` parameter there is refused with `403 Forbidden`.

 三個發現端點無需身份驗證即可讀取，這符合RFC 7644 的規定，也是客戶端在配置憑證之前探測目標時所期望的。它們暴露服務的結構，但不暴露任何帳戶資料。如果連這些資訊都不希望暴露，請依照限制網路存取中的說明，透過位址限制路徑。發現端點不支援過濾； `filter`參數會被`403 Forbidden`拒絕。

`/Me` is defined by RFC 7644 section 3.11 as an alias for the resource belonging to the authenticated subject. Stalwart returns `501 Not Implemented`, which the specification explicitly sanctions. The endpoint exists for end-user self-service, whereas a SCIM client authenticates as a machine principal whose subject is the integration’s own service account, and not a provisionable user.

`/Me`由RFC 7644 節3.11定義為已認證主體所屬資源的別名。 Stalwart 傳回`501 Not Implemented` ，該值已在規範中明確認可。此端點用於最終用戶自助服務，而SCIM客戶端則以機器主體身份進行身份驗證，其主體是整合自身的服務帳戶，而不是可配置用戶。

 Requests to any unrecognised path under `/scim/v2` return `404 Not Found`, and a recognised path called with an unsupported method returns `405 Method Not Allowed` with an `Allow` header naming the methods that are accepted.

 對`/scim/v2`下任何未識別路徑的請求將返回`404 Not Found` ，而使用不支援的方法呼叫已識別路徑將返回`405 Method Not Allowed`並在`Allow`標頭中列出可接受的方法。

## Advertised capabilities｜廣告宣傳的功能

`GET /scim/v2/ServiceProviderConfig` reports what the server supports. The values are fixed:

`GET /scim/v2/ServiceProviderConfig`報告伺服器支援的功能。這些值是固定的：

| Capability 能力 | Value 價值 |
| --- | --- |
| `patch` | Supported 支持 |
| `bulk` | Supported, at most 1000 operations and 1 MiB per request 支持，每次請求最多 1000 次操作和 1 MiB 數據 |
| `filter` | Supported, at most 200 results 支持，最多顯示 200 個結果 |
| `changePassword` | Not supported 不支援 |
| `sort` | Supported 支持 |
| `etag` | Supported 支持 |
| `pagination` | Index and cursor, default page 100, maximum page 200, index by default 索引與遊標，預設頁碼 100，最大頁碼 200，預設索引 |
| `authenticationSchemes` | OAuth bearer token only 僅限 OAuth 持有者令牌 |
| `interopProfileConformant` | `false`, see [schema handling](#schema-handling) `false` ，參見[模式處理](#schema-handling) |

`changePassword` reports whether a SCIM client may set the `password` attribute on a user it provisions. In this deployment model the identity provider holds the credential and Stalwart validates against it over OIDC, so there is no password to push and the attribute is absent from the published User schema.

`changePassword`報告客戶端SCIM是否可以設定其配置使用者的`password`屬性。在此部署模型中，身分提供者持有憑證，Stalwart 透過OIDC對其進行驗證，因此無需推送密碼，且已發布的 User 架構中不存在該屬性。

## Schema handling｜模式處理

`GET /scim/v2/Schemas` returns the attribute definitions the server actually honours, derived from its own account model. It is the authoritative statement of what Stalwart stores, and attribute mapping explains what each attribute does once it arrives.

`GET /scim/v2/Schemas`傳回伺服器實際遵循的屬性定義，這些定義源自於伺服器本身的帳戶模型。它是 Stalwart 儲存內容的權威聲明，而 屬性映射則解釋了每個屬性到達後的具體作用。

 Requests are not required to confine themselves to that set. RFC 7643 section 4.1 defines a User resource considerably larger than any mail server implements, and RFC 7644 section 3.1 states plainly that a client “does not need to remove” attributes the server will not act on, adding that a client “SHOULD NOT expect a service provider to return SCIM resources with exactly the same schema and values as submitted”. Identity providers are built on that assumption: none of them shapes its request body from the target’s `/Schemas` document.

 請求不必局限於該集合。 RFC 7643節 4.1 定義了一個比任何郵件伺服器實現的資源都大得多的使用者資源，並且 RFC 7644節 3.1 明確指出客戶端“無需移除”伺服器不會處理的屬性，並補充說客戶端“SHOULD NOT 預計服務提供者將返回 SCIM 資源應具有與提交內容完全相同的模式和值」。身分提供者正是基於此假設而建構的：它們都不會根據目標資源的模式和值來調整請求體。 `/Schemas` 文件.

 Stalwart therefore accepts and discards the attributes of the core RFC 7643 User and Group schemas that it does not implement, and the enterprise user extension, in `POST`, `PUT` and `PATCH` request bodies alike. They are neither stored nor returned. The one that is not merely discarded is the structured name: where `displayName` and `name.formatted` are both absent, `name.givenName` and `name.familyName` are joined and stored as the display name, so an account provisioned by a client that sends only structured name parts is not left nameless.

 因此，Stalwart 會接受並丟棄其未實現的RFC 7643 使用者和群組模式以及企業用戶擴充的屬性，無論這些屬性是在`POST`, `PUT`或`PATCH`請求體中。它們既不會被存儲，也不會被返回。唯一不會被丟棄的是結構化名稱：當`displayName`和`name.formatted`都不存在時， `name.givenName`和`name.familyName`會被合併並儲存為顯示名稱，因此，由僅發送結構化名稱部分的客戶端配置的帳戶不會沒有名稱。

 An attribute that belongs to no schema Stalwart recognises is still refused, with `400 Bad Request` and a `scimType` of `invalidSyntax`. A misspelled mapping such as `dispalyName`, an unrecognised schema URI, a duplicated attribute, and a missing `schemas` value are all refused the same way.

 不屬於 Stalwart 可識別的任何模式的屬性仍然會被拒絕，例如`400 Bad Request`和`scimType`為`invalidSyntax` 。拼字錯誤的映射（例如`dispalyName` 、無法辨識的模式URI 、重複的屬性以及缺失的`schemas`值都會以相同的方式被拒絕。

 The [SCIM interoperability profile](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/) section 5.3 requires every undefined attribute to be rejected. Stalwart follows RFC 7644 where the two disagree, and reports `interopProfileConformant` as `false`. Every other requirement of that profile is met. Why undefined attributes are accepted sets out the reasoning.

[SCIM互通性規範](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/)部分5.3要求拒絕所有未定義的屬性。 Stalwart 在兩者不一致的地方遵循RFC 7644，並將`interopProfileConformant`報告為`false` 。該規範的其他所有要求均已滿足。 未定義屬性被接受的原因闡述了其理由。

## Filtering｜濾

 Filters are accepted on `GET /Users`, `GET /Groups`, and the `/.search` endpoints. Two operators are supported, `eq` and `and`, which is exactly what the interoperability profile mandates and exactly what identity providers send in practice. Every other operator, including `ne`, `co`, `sw`, `ew`, `gt`, `lt`, `pr`, `or`, and `not`, is refused with `400 Bad Request` and a `scimType` of `invalidFilter`. The full grammar is parsed before the request is rejected, so the error names the unsupported construct.

`GET /Users`, `GET /Groups`和`/.search`端點接受過濾器。支援兩個運算子： `eq`和`and` ，這與互通性規範的要求以及身分提供者實際發送的內容完全一致。所有其他運算符，包括`ne`, `co`, `sw`, `ew`, `gt`, `lt`, `pr`, `or`和`not` ，都會被拒絕，並返回`400 Bad Request`和`scimType`或`invalidFilter` 。請求被拒絕之前會解析完整的語法，因此錯誤訊息會指出不支援的構造。

 The attributes that can be filtered are:

 可篩選的屬性包括：

| Resource 資源 | Attributes 屬性 |
| --- | --- |
| User 用戶 | `id`, `externalId`, `userName`, `emails`, `emails.value`, `active`, `displayName`, `name.formatted`, `groups`, `groups.value` |
| Group 組 | `id`, `externalId`, `displayName`, `members`, `members.value` |

Filtering on any other attribute is refused with `invalidFilter`. Value filters of the form `attr[sub eq "x"]` are not accepted inside a `filter` parameter, though they are supported in `PATCH` paths, where clients genuinely need them.

 使用 `invalidFilter` 拒絕對任何其他屬性進行過濾。 `attr[sub eq "x"]` 形式的值過濾器在 `filter` 參數內不被接受，儘管它們在 `PATCH` 路徑中受支援，而客戶端真正需要它們。

 Most filters resolve against an index. `active`, `displayName`, and `name.formatted` cannot be fully answered from an index, so they are evaluated after the indexed part of the filter has narrowed the candidate set. If more than 200 candidates remain at that point, the request is refused with `400 Bad Request` and a `scimType` of `tooMany`, and the message asks for a narrower filter. Combining such an attribute with an indexed one using `and` avoids the condition.

 大多數過濾器`name.formatted` `active`, `displayName`完全從索引中獲取答案，因此它們會在過濾器的索引部分縮小候選集之後進行評估。如果此時剩餘的候選結果超過 200 個，則請求將被拒絕，並返回`400 Bad Request`和`scimType` `tooMany` ，同時提示請求使用更精確的過濾器。使用`and`將此類屬性與索引屬性結合使用可以避免這種情況。

## Sorting and pagination｜排序和分頁

`sortBy` accepts `id` and, for users, `userName`; `sortOrder` accepts `ascending` and `descending`. Sorting by any other attribute is refused with `invalidValue`, because the server sorts from an index.

`sortBy`接受`id` ，對於用戶， `userName`; `sortOrder`接受`ascending`和`descending` `invalidValue`按任何其他屬性排序，因為伺服器是從索引排序的。

 Both pagination styles defined for SCIM are available. Index-based pagination follows RFC 7644 section 3.4.2.4, using `startIndex` and `count`, and the response reports `totalResults`, `startIndex`, and `itemsPerPage`. Cursor-based pagination follows [RFC 9865](https://www.rfc-editor.org/rfc/rfc9865): the client sends `cursor` and the response returns `nextCursor` until the result set is exhausted. A page holds 100 resources unless `count` says otherwise, and 200 is the maximum. A cursor is bound to the query that produced it, so presenting one alongside a changed filter or sort order is rejected.

 SCIM定義的兩種分頁方式均可使用。基於索引的分頁遵循RFC 7644 節3.4.2.4 ，使用`startIndex`和`count` ，回應報告`totalResults`, `startIndex`和`itemsPerPage` 。基於遊標的分頁遵循 [RFC 9865](https://www.rfc-editor.org/rfc/rfc9865) ：客戶端發送`cursor` ，回應回傳`nextCursor` ，直到結果集耗盡。除非`count`另有規定，否則每頁包含 100 個資源，最大值為 200。遊標與產生它的查詢綁定，因此，如果同時提交一個已更改篩選條件或排序順序的遊標，則會被拒絕。

## Entity tags and concurrency｜實體標籤和並發性

 Every resource carries a `meta.version` entity tag, returned in the `ETag` header as well as the body. The value is derived from the content of the resource, so it changes when the resource changes and does not change when it does not; for groups it covers the membership as well as the group’s own attributes.

 每個資源都附有一個`meta.version`實體標籤，該標籤會同時出現在`ETag`請求頭和請求體中。此標籤的值取決於資源的內容，因此當資源發生變化時，該標籤的值也會隨之變化；對於群組而言，該標籤的值涵蓋了群組成員關係以及群組本身的屬性。

`If-None-Match` on a `GET` returns `304 Not Modified` when the resource is unchanged, which lets a client poll cheaply. `If-Match` on a `PUT`, `PATCH`, or `DELETE` returns `412 Precondition Failed` when the resource has changed since it was read, which prevents two overlapping synchronisation cycles from overwriting each other. Requests that omit the header proceed unconditionally.

 當資源未發生變化時， `If-None-Match`對`GET`的請求會回傳`304 Not Modified` ，這使得客戶端可以低成本地進行輪詢。當資源自上次讀取以來發生更改時， `If-Match`對`PUT`, `PATCH`或`DELETE`請求會返回`412 Precondition Failed` ，這可以防止兩個重疊的同步週期相互覆蓋。省略此標頭的請求將無條件地繼續執行。

`meta.lastModified` is not emitted, because Stalwart does not record a modification timestamp on accounts. `meta.created` is present. Clients that use timestamps for incremental synchronisation should use entity tags instead.

`meta.lastModified` 不會發出，因為 Stalwart 不會記錄帳戶的修改時間戳。 `meta.created` 存在。使用時間戳進行增量同步的客戶端應使用實體標籤。

## Bulk operations｜散裝作業

`POST /scim/v2/Bulk` accepts up to 1000 operations in a single request, subject to a 1 MiB payload limit, and supports `failOnErrors` and `bulkId` forward references so that a user can be created and added to a group created in the same request. Each operation reports its own status, so a partial failure does not discard the successful operations.

`POST /scim/v2/Bulk`允許在單一請求中執行最多 1000 個操作，有效負載大小限制為 1 MiB，並支援`failOnErrors`和`bulkId`前向引用，以便在同一請求中建立使用者並將其新增至已建立的群組。每個操作都會報告其自身的狀態，因此部分操作失敗不會導致已成功的操作被丟棄。

 The endpoint exists because the IPSIE profile requires it and because provisioning scripts can use it directly.

 該端點存在是因為IPSIE配置檔案需要它，並且配置腳本可以直接使用它。

## Query by POST｜查詢者POST

`POST /scim/v2/Users/.search` and `POST /scim/v2/Groups/.search` accept the same parameters as a `GET` query, carried in a `SearchRequest` body instead of the query string. `POST /scim/v2/.search` runs the query across both resource types and returns a single combined `ListResponse`.

`POST /scim/v2/Users/.search` 和 `POST /scim/v2/Groups/.search` 接受與 `GET` 查詢相同的參數，在 `SearchRequest` 主體中而不是查詢字串中攜帶。 `POST /scim/v2/.search` 跨兩種資源類型執行查詢並傳回單一組合`ListResponse`。

 RFC 7644 section 7.5.2 warns against placing personal data in request URIs, and Stalwart records request URIs in its telemetry, so `GET /Users?filter=emails eq "[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)"` writes an address into the trace log where the equivalent `.search` request does not.

 RFC 7644 節7.5.2警告不要將個人資料放在請求 URI 中，而 Stalwart 會將請求 URI 記錄在其遙測資料中，因此`GET /Users?filter=emails eq "[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)"`會將地址寫入日誌，而等效的`.search` 。

## Errors｜錯誤

 Errors are returned as SCIM error documents carrying an HTTP status, a `detail` string, and, where the specification defines one, a `scimType`.

 錯誤以SCIM錯誤文檔的形式傳回，其中包含HTTP狀態、 `detail`字串，以及（如果規範定義了） `scimType` 。

| Status 狀態 | `scimType` | Cause 原因 |
| --- | --- | --- |
| `400` | `invalidSyntax` | Malformed body, an attribute or schema URI belonging to no known schema, a duplicated attribute, or a missing `schemas` value 正文格式錯誤，屬性或模式URI不屬於任何已知模式，屬性重複，或缺少`schemas`值 |
| `400` | `invalidFilter` | Unsupported operator or attribute in a filter 過濾器中不支援的運算子或屬性 |
| `400` | `invalidPath` | Unsupported `PATCH` path, or a value filter where one is not accepted 不支援的`PATCH`路徑，或不接受的值過濾器 |
| `400` | `invalidValue` | A value the server cannot accept, including a domain not open to SCIM 伺服器無法接受的值，包括對SCIM不開放的域 |
| `400` | `tooMany` | A filter matching more than 200 candidates before a non-indexed attribute is evaluated 在評估未索引屬性之前，先篩選出符合超過 200 個候選值的篩選器 |
| `400` | `mutability` | An attempt to modify a read-only attribute 嘗試修改唯讀屬性 |
| `401` |  | Missing, malformed, or expired bearer token, or HTTP Basic authentication 缺少、格式錯誤或已過期的持有者令牌，或HTTP基本驗證 |
| `403` |  | Valid credential lacking a required permission, or the Community Edition 有效憑證缺少所需權限，或社群版 |
| `404` |  | Unknown resource, unknown endpoint, or a resource outside the caller’s tenant 未知資源、未知端點或呼叫者租用戶以外的資源 |
| `405` |  | Method not supported by the endpoint; the `Allow` header lists what is 端點不支援此方法； `Allow`標頭列出了 |
| `409` | `uniqueness` | An address or group name that is already in use 已使用的地址或群組名稱 |
| `412` |  | An `If-Match` precondition that no longer holds 不再成立的`If-Match`前提條件 |
| `413` |  | A payload above the endpoint’s size limit 酬載超過端點大小限制 |
| `429` |  | Rate limit exceeded; a `Retry-After` header states when to retry 速率限制已超出； `Retry-After`標頭指示何時重試 |
| `501` |  | `/Me` |

A resource belonging to another tenant returns `404`, not `403`, so that tenant boundaries do not leak the existence of accounts.

 屬於其他租戶的資源返回`404` ，而不是`403` ，這樣租戶邊界就不會洩漏帳戶的存在。
