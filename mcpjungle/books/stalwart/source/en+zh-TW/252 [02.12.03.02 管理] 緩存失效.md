# Cache invalidation｜緩存失效

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[management｜管理\\\]\\\(&lt;000 目錄.md#c-44&gt;\\\)

The proxy caches the result of every mapping lookup in memory so that established accounts resolve without consulting the mapping store. The cache is what keeps the store off the hot path, but it also means that a change to a mapping does not take effect instantly: an account already in the cache continues to resolve to its old destination until the cached entry expires. During a migration cutover, where an account is moved and should immediately follow to its new backend, the cache is invalidated to force the account to be re-resolved at once.

 代理會將每次映射查找的結果快取到記憶體中，這樣已建立的帳戶無需存取映射儲存\([https://stalw.art/docs/migration/proxy/mappings/\)解析。快取機制避免了映射儲存成為熱路徑，但也意味著映射的變更不會立即生效：快取中已有的帳戶會繼續解析到其舊目標，直到快取條目過期。在遷移切換期間，如果帳戶被遷移並應立即遷移到新的後端，則快取會被失效，以強制帳戶立即重新解析。](https://stalw.art/docs/migration/proxy/mappings/%2529%2525E8%2525A7%2525A3%2525E6%25259E%252590%2525E3%252580%252582%2525E5%2525BF%2525AB%2525E5%25258F%252596%2525E6%2525A9%25259F%2525E5%252588%2525B6%2525E9%252581%2525BF%2525E5%252585%25258D%2525E4%2525BA%252586%2525E6%252598%2525A0%2525E5%2525B0%252584%2525E5%252584%2525B2%2525E5%2525AD%252598%2525E6%252588%252590%2525E7%252582%2525BA%2525E7%252586%2525B1%2525E8%2525B7%2525AF%2525E5%2525BE%252591%2525EF%2525BC%25258C%2525E4%2525BD%252586%2525E4%2525B9%25259F%2525E6%252584%25258F%2525E5%252591%2525B3%2525E8%252591%252597%2525E6%252598%2525A0%2525E5%2525B0%252584%2525E7%25259A%252584%2525E8%2525AE%25258A%2525E6%25259B%2525B4%2525E4%2525B8%25258D%2525E6%25259C%252583%2525E7%2525AB%25258B%2525E5%25258D%2525B3%2525E7%252594%25259F%2525E6%252595%252588%2525EF%2525BC%25259A%2525E5%2525BF%2525AB%2525E5%25258F%252596%2525E4%2525B8%2525AD%2525E5%2525B7%2525B2%2525E6%25259C%252589%2525E7%25259A%252584%2525E5%2525B8%2525B3%2525E6%252588%2525B6%2525E6%25259C%252583%2525E7%2525B9%2525BC%2525E7%2525BA%25258C%2525E8%2525A7%2525A3%2525E6%25259E%252590%2525E5%252588%2525B0%2525E5%252585%2525B6%2525E8%252588%25258A%2525E7%25259B%2525AE%2525E6%2525A8%252599%2525EF%2525BC%25258C%2525E7%25259B%2525B4%2525E5%252588%2525B0%2525E5%2525BF%2525AB%2525E5%25258F%252596%2525E6%2525A2%25259D%2525E7%25259B%2525AE%2525E9%252581%25258E%2525E6%25259C%25259F%2525E3%252580%252582%2525E5%25259C%2525A8%2525E9%252581%2525B7%2525E7%2525A7%2525BB%2525E5%252588%252587%2525E6%25258F%25259B%2525E6%25259C%25259F%2525E9%252596%252593%2525EF%2525BC%25258C%2525E5%2525A6%252582%2525E6%25259E%25259C%2525E5%2525B8%2525B3%2525E6%252588%2525B6%2525E8%2525A2%2525AB%2525E9%252581%2525B7%2525E7%2525A7%2525BB%2525E4%2525B8%2525A6%2525E6%252587%252589%2525E7%2525AB%25258 ## Cache lifetimes｜緩存生命週期

 The cache distinguishes three kinds of result, each with its own lifetime configured under `[mapping]`:

 快取區分三種結果，每種結果都有自己的生命週期，在`[mapping]`下配置：

- A **resolved** mapping is held for `positive_ttl` \(10 minutes by default\). An account with an explicit destination stays resolved to it for this long.
**已解析的**映射將保留 `positive_ttl`（預設為 10 分鐘）。具有明確目的地的帳戶會在這麼長時間內保持解析狀態。

- A **fall-through** to the default destination is held for `negative_ttl` \(30 seconds by default\). The shorter lifetime means that giving an account a new explicit mapping takes effect quickly, since the previous fall-through expires soon.
預設目標位址的**回退**狀態會保留`negative_ttl` （預設為30秒）。較短的保留期意味著，為帳戶設定新的明確對應會迅速生效，因為先前的回退狀態很快就會過期。
- A **transient** result, produced when the store is unreachable, is held for only a few seconds, so the store is retried promptly.
當商店無法訪問時產生的**瞬態**結果只會保留幾秒鐘，以便及時重試訪問商店。
These lifetimes are bound at startup and require a restart to change. The natural consequence is that, without intervention, a migrated account picks up its new destination within `positive_ttl` if it had an explicit mapping, or within `negative_ttl` if it was previously falling through to the default. Invalidation is the way to make the change immediate.
 這些生命週期在啟動時即被綁定，需要重新啟動才能更改。自然而然地，如果沒有乾預，遷移後的帳戶會在`positive_ttl`內（如果之前有明確映射）或`negative_ttl`內（如果之前默認使用預設映射）獲取到新的目標位置。失效機制可以使變更立即生效。

## Forcing re-resolution｜強制重新解析

 A single account is re-resolved immediately by invalidating its cache entry through the management API:

 透過 管理API使單一帳戶的快取條目失效，即可立即重新解析該帳戶：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST \
  -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/cache/[email protected]"
```

The next connection for that account misses the cache, consults the store, and picks up its new destination. The same endpoint with no `identifier` parameter clears the entire cache, which forces every account to be re-resolved on its next connection; this is appropriate after a bulk update to the mapping table.

 該帳戶的下一個連接會錯過緩存，轉而查詢存儲，並獲取新的目標地址。如果同一個端點沒有`identifier`參數，則會清除整個緩存，強制每個帳戶在下次連接時重新解析；這在映射表進行批量更新後是合理的。

## Reloading the mapping table｜重新載入映射表

 Invalidation only clears cached lookups; it does not re-read the underlying store. For the file source, where the mapping table is loaded into memory at startup, editing the file on disk additionally requires a reload to take effect:

 失效操作只會清除快取的查找結果；它不會重新讀取底層儲存。對於 檔案來源 ，由於映射表在啟動時載入到記憶體中，因此編輯磁碟上的檔案也需要重新載入才能生效：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST \
  -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/mappings/reload"
```

A reload re-reads and validates the file, replacing the in-memory table only if the file is valid. The Redis and SQL sources read from their database on each cache miss, so they have nothing to reload; for them, invalidating the cache is sufficient to surface a change made directly in the store.

 重新載入操作會重新讀取並驗證文件，僅當文件有效時才會取代記憶體中的表。 Redis 和SQL資料源在每次快取未命中時都會從資料庫讀取數據，因此它們無需重新加載；對它們而言，使快取失效就足以反映直接在儲存中所做的更改。

 A typical bulk cutover therefore updates the mapping table \(regenerating the file and reloading it, or writing the new rows to Redis or SQL\), then invalidates the cache so the changes take effect without waiting for entries to expire.

 因此，典型的批次切換會更新映射表（重新產生檔案並重新加載，或將新行寫入 Redis 或SQL ），然後使快取失效，以便更改生效而無需等待條目過期。
