# Roles｜角色

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[cluster｜簇\\\]\\\(&lt;000 目錄.md#c-12&gt;\\\) › \\\[configuration｜配置\\\]\\\(&lt;000 目錄.md#c-13&gt;\\\)

In a clustered deployment, background and maintenance tasks must run regularly to keep the system healthy and secure. To distribute this operational workload across the cluster, Stalwart models each role as a named profile applied to one or more nodes.

 在叢集部署中，後台任務和維護任務必須定期運行，以確保系統健康安全。為了將這些運維工作負載分配到叢集的各個節點，Stalwart 將每個角色建模為一個命名配置文件，並應用於一個或多個節點。

 Roles are defined through ClusterRole objects \(found in the WebUI under Settings › Cluster › Roles\). Each role selects a set of tasks and network listeners, and nodes that start up with a given role name run only the tasks and listeners enabled for that role. This distributes work evenly and lets administrators keep resource-intensive tasks on dedicated hardware.

 角色透過 ClusterRole物件定義（可在 WebUI 的「設定」&gt;「叢集」&gt;「角色」中找到）。每個角色選擇一組任務和網路監聽器，以特定角色名稱啟動的節點僅執行為該角色啟用的任務和監聽器。這樣可以平衡分配工作負載，並允許管理員將資源密集型任務保留在專用硬體上。

 Each ClusterRole carries the following fields:

 每個叢集角色都包含以下欄位：

- name: a unique identifier for the role \(read-only\).
name : 角色的唯一識別碼（唯讀）。
- description: a human-readable description.
description : 人類可讀的描述。
- tasks: a ClusterTaskGroup selecting which cluster tasks the role enables. The variants are `EnableAll`, `DisableAll`, `EnableSome`, and `DisableSome`; the `EnableSome` and `DisableSome` variants carry a set of task types via `taskTypes`.
tasks : a ClusterTaskGroup選擇角色啟用的叢集任務。變體為`EnableAll`, `DisableAll`, `EnableSome`和`DisableSome` ； `EnableSome`和`DisableSome`變體透過`taskTypes`承載一組任務類型。
- listeners: a ClusterListenerGroup selecting which network listeners the role enables. The variants mirror those of `tasks`, with a `listenerIds` field referencing NetworkListener ids.
listeners : ClusterListenerGroup選擇角色啟用的網路監聽器。這些變體與`tasks`的變體類似，但`listenerIds`字段引用 NetworkListener id。
A node is assigned to a role through the STALWART\_ROLE environment variable, which names the ClusterRole whose tasks and listeners the node should run.
 透過 STALWART\_ROLE環境變數將節點指派給一個角色，該環境變數指定了節點應該運行的任務和監聽器的 ClusterRole。

## Available tasks｜可用任務

 The tasks that a role can enable or disable are drawn from the `ClusterTaskType` enumeration on the ClusterRole object:

 角色可以啟用或停用的任務取自 ClusterRole物件上的`ClusterTaskType`枚舉：

- `storeMaintenance`: purges expired data from the data store, keeping it compact and performant.
`storeMaintenance` ：從資料儲存中清除過期數據，使其保持緊湊和高效能。
- `accountMaintenance`: cleans up deleted accounts, old changelog entries, and related records.
`accountMaintenance` ：清理已刪除的帳戶、舊的變更日誌條目和相關記錄。
- `metricsCalculate`: calculates and aggregates metrics and statistics for the cluster.
`metricsCalculate` ：計算並彙總群集的指標和統計資料。
- `metricsPush`: exports metrics to external monitoring or visualisation systems.
`metricsPush` ：將指標匯出到外部監控或視覺化系統。
- `pushNotifications`: delivers push notifications to subscribed clients.
`pushNotifications` ：向已訂閱的客戶發送推播通知。
- `searchIndexing`: performs full-text search indexing on new or modified content.
`searchIndexing` ：對新增或修改的內容執行全文搜尋索引。
- `spamClassifierTraining`: runs spam classifier training. Only one node should run this task at a time to avoid conflicting model updates.
`spamClassifierTraining` ：運行垃圾郵件分類器訓練。為避免模型更新衝突，每次只能有一個節點執行此任務。
- `outboundMta`: processes outbound mail through the MTA queue.
`outboundMta` ：透過MTA隊列處理出站郵件。
- `taskQueueProcessing`: executes queued background tasks.
`taskQueueProcessing` ：執行已排隊的後台任務。
- `taskScheduler`: schedules recurring and deferred tasks. ACME renewal, iMIP processing, calendar-alert dispatch, and similar time-driven jobs are dispatched by the task scheduler.
`taskScheduler`：安排重複任務和延遲任務。 ACME 更新、iMIP 處理、日曆警報排程和類似的時間驅動作業由任務排程器調度。
Task assignment is driven entirely by the ClusterRole object and the `STALWART_ROLE` environment variable. The role named in `STALWART_ROLE` selects both which tasks the node runs and which listeners it exposes, so a single role definition captures the full workload of a given node.
 任務分配完全由 ClusterRole 物件和 `STALWART_ROLE` 環境變數驅動。 `STALWART_ROLE` 中命名的角色選擇節點運行的 tasks 以及它公開的 listeners，因此單個角色定義可以捕獲給定節點的全部工作負載。

## Push notification sharding｜推播通知分片

 Push notification delivery must be sharded so that each subscriber receives exactly one notification across the cluster. A node is placed in a specific shard by setting the STALWART\_PUSH\_SHARD environment variable. Nodes in the same shard cooperate to deliver the subset of notifications assigned to that shard. Sharding is configured exclusively through this environment variable; ClusterRole does not carry shard groupings.

 推播通知必須分片，以確保叢集中的每個訂閱者都能收到一則通知。透過設定環境變數 STALWART\_PUSH\_SHARD ，可以將節點指派到特定的分片中。同一分片中的節點會協同工作，共同推送分配給該分片的通知子集。分片配置完全透過此環境變數實現；ClusterRole 不包含分片分組資訊。

## Example｜例子

 A simple two-role deployment might define a `frontend` role that serves client-facing listeners but runs no background tasks, and a `maintenance` role that runs every background task but exposes no client listeners:

 一個簡單的雙角色部署可能定義一個`frontend`角色，該角色服務於面向客戶端的監聽器，但不運行任何後台任務；以及一個`maintenance`角色，該角色運行所有後台任務，但不暴露任何客戶端監聽器：

```json
{
  "name": "frontend",
  "description": "Serves IMAP, JMAP, SMTP and WebDAV traffic",
  "tasks": {
    "@type": "DisableAll"
  },
  "listeners": {
    "@type": "EnableAll"
  }
}
```

```json
{
  "name": "maintenance",
  "description": "Runs store maintenance, indexing, and metrics",
  "tasks": {
    "@type": "EnableSome",
    "taskTypes": {
      "storeMaintenance": true,
      "accountMaintenance": true,
      "searchIndexing": true,
      "metricsCalculate": true,
      "metricsPush": true
    }
  },
  "listeners": {
    "@type": "DisableAll"
  }
}
```

Nodes that start with `STALWART_ROLE=frontend` run only the network listeners, while nodes started with `STALWART_ROLE=maintenance` run only the selected background tasks.

 以`STALWART_ROLE=frontend`開頭的節點僅運行網路監聽器，而以`STALWART_ROLE=maintenance`開頭的節點僅運行選定的後台任務。

## Best practices｜最佳實踐

 Role planning should start from the resource profile of each task. Tasks such as `searchIndexing` and `spamClassifierTraining` tend to be CPU- and I/O-intensive; `metricsCalculate` and scheduled maintenance are lighter but time-sensitive. Assigning resource-heavy roles to nodes with sufficient computational capacity and isolating them from latency-sensitive workloads helps keep the cluster responsive.

 角色規劃應從每個任務的資源配置入手。諸如`searchIndexing`和`spamClassifierTraining`之類的任務往往是CPU且I/O密集型任務； `metricsCalculate`和計劃維護任務則資源消耗較小，但對時間要求較高。將資源密集型角色分配給運算能力充足的節點，並將其與對延遲敏感的工作負載隔離，有助於保持叢集的回應速度。

 In high-availability deployments, critical tasks should run on multiple nodes so that the failure of one does not stop routine maintenance. Where duplicate work is a concern, for example push notifications, sharding through `STALWART_PUSH_SHARD` prevents the same work from being done twice.

 在高可用性部署中，關鍵任務應在多個節點上運行，以確保即使一個節點發生故障，日常維護也不會中斷。對於重複工作較為棘手的情況，例如推播通知，透過`STALWART_PUSH_SHARD`進行分片可以避免重複執行相同的工作。

 When sharding, aim for an even distribution of nodes across shards. Each shard should have similar computational resources to prevent uneven load. In smaller deployments a single shard may be sufficient.

 分片時，應盡量使節點在各分片間均勻分佈。每個分片應擁有相似的計算資源，以防止負載不均。在規模較小的部署中，單一分片可能就足夠了。

 Role assignments should be reviewed as the cluster evolves. Changes in user population, message volume, or data growth may shift the optimal distribution of responsibilities. Regular audits of node health, performance metrics, and quota utilisation help identify when roles should be reassigned, split, or consolidated.

 隨著集群的發展，角色分配應定期審查。使用者數量、訊息量或資料成長的變化都可能導致職責分配的最佳狀態改變。定期審核節點健康狀況、效能指標和配額使用情況有助於確定何時需要重新分配、分割或合併角色。
