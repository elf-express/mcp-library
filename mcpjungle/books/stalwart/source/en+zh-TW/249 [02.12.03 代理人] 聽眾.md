# Listeners｜聽眾

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\)

A listener is a socket the proxy accepts client connections on, bound to one protocol. Listeners are declared as named tables under `[listener.*]`; the name is an arbitrary label used in logs and has no other significance. A typical deployment declares one listener per protocol and port, often with both an implicit-TLS and a STARTTLS variant of the same protocol so that clients using either convention are served.

 監聽器是代理伺服器接受客戶端連線的套接字，綁定到一個協定。監聽器在`[listener.*]`下宣告為命名表；名稱是日誌中使用的任意標籤，沒有其他意義。典型的部署會為每個協定和連接埠宣告一個監聽器，通常會同時包含相同協定的隱式變體TLS和STARTTLS ，以便為使用任一約定的用戶端提供服務。

```toml
[listener.imap]
protocol = "imap"
bind = ["0.0.0.0:993", "[::]:993"]
tls = "implicit"

[listener.imap-starttls]
protocol = "imap"
bind = ["0.0.0.0:143", "[::]:143"]
tls = "starttls"
```

## Listener options｜監聽器選項

| Key 鍵 | Default 預設值 | Description 描述 |
| --- | --- | --- |
| `protocol` | required 必填 | One of `imap`, `pop3`, `managesieve`, `submission`, `smtp`, `lmtp` or `http`. `imap`, `pop3`, `managesieve`, `submission`, `smtp`, `lmtp`或`http`之一。 |
| `bind` | required 必填 | List of socket addresses to listen on. At least one is required. 要監聽的套接字位址清單。至少需要一個。 |
| `tls` | required 必填 | `implicit`, `starttls` or `plain`. `implicit`, `starttls`或`plain` 。 |
| `proxy_protocol` | `off` | Whether to accept a PROXY protocol header from the connecting peer: `off`, `optional` or `required`. 是否接受來自連接對等方的PROXY協議頭： `off`, `optional`或`required` 。 |
| `proxy_trusted` | empty 空 | CIDR ranges allowed to send a PROXY header. Required when `proxy_protocol` is not `off`. CIDR允許發送PROXY標頭的範圍。當`proxy_protocol`不是`off`時為必填項。 |
| `max_connections` | `8192` | Maximum number of simultaneous connections on this listener. 此監聽器的最大並發連接數。 |
| `preauth_timeout` | `30s` | Time limit for the client to complete the pre-authentication dialogue. 客戶完成預先認證對話的時限。 |
| `max_auth_attempts` | `3` | Number of authentication failures tolerated before the connection is dropped. 連線中斷前可容忍的身份驗證失敗次數。 |
| `forwarded` | `off` | For HTTP listeners, whether inbound `Forwarded` and `X-Forwarded-For` headers from the client are trusted. 對於HTTP監聽器，判斷來自客戶端的入站`Forwarded`和`X-Forwarded-For`標頭是否可信。 |

The `bind` list accepts both IPv4 and IPv6 addresses, so binding a protocol on `0.0.0.0` and `[::]` serves clients on both stacks. Binding privileged ports below 1024 requires the proxy to hold the `CAP_NET_BIND_SERVICE` capability, which the supplied service unit and container image already arrange.

`bind`清單同時接受 IPv4 和 IPv6 位址，因此在`0.0.0.0`和`[::]`上綁定協定可以為使用這兩個協定堆疊的用戶端提供服務。綁定 1024 以下的特權連接埠需要代理具備`CAP_NET_BIND_SERVICE`能力，而提供的服務單元和容器鏡像已經具備此能力。

## Transport modes｜運輸方式

 The `tls` mode determines how the connection begins. With `implicit`, the proxy performs a TLS handshake immediately upon accepting the connection, which is the convention for ports such as 993 \(IMAPS\), 995 \(POP3S\) and 465 \(submissions\). With `starttls`, the connection begins in cleartext and the client may upgrade it with the protocol’s STARTTLS command, the convention for ports such as 143, 110 and 587. With `plain`, the connection is never encrypted; this is intended for the SMTP and LMTP pass-through protocols on trusted networks, and for backends reached over an already-secure channel.

`tls`模式決定了連結的建立方式。使用`implicit`時，代理會在接受連接後立即執行TLS握手，這是 993 \( IMAPS \)、995 \( POP3S \) 和 465（提交）等端口的慣例。使用`starttls`時，連線以明文形式建立，客戶端可以使用協定的STARTTLS指令進行加密，這是 143、110 和 587 等連接埠的慣例。使用`plain`時，連線始終不加密；這適用於受信任網路上的SMTP和LMTP直通協議，以及透過已安全通道存取的後端。

 The pass-through protocols `smtp` and `lmtp` cannot use `starttls`, because the proxy bridges them as an opaque byte stream rather than terminating the protocol, and therefore cannot intercept a STARTTLS command to perform the upgrade. This combination is rejected at startup; `plain` or `implicit` must be used instead. The distinction between the interactive and pass-through protocols is explained under Routing.

 直通協議`smtp`和`lmtp`不能使用`starttls` ，因為代理會將它們作為不透明的位元組流橋接，而不是終止協議，因此無法攔截STARTTLS命令來執行升級。此組合在啟動時會被拒絕；必須改用`plain`或`implicit` 。互動式協定和直通協定之間的差異在路由中進行了解釋。

 Every interactive protocol a listener accepts must be declared on the default destination, since connections without an explicit mapping fall back to it. A listener for a protocol the default destination does not offer is rejected at startup.

 監聽器接受的每個互動式協定都必須在預設目標伺服器上聲明，因為沒有明確映射的連線會回退到該預設目標伺服器。如果預設目標伺服器不支援某個協議，則監聽器會在啟動時被拒絕。

## Connection limits and timeouts｜連線限制和逾時

`max_connections` caps the number of concurrent connections a listener will serve; once the limit is reached, further connections are dropped until existing ones close. `preauth_timeout` bounds the time a client has to authenticate, which limits how long a half-open connection can hold resources before the proxy abandons it. `max_auth_attempts` closes a connection after the configured number of authentication failures, counting both the commands the proxy rejects itself and the credentials the backend rejects. This slows down credential-guessing against the proxy and bounds the number of backend connections one client connection can open.

`max_connections`限制監聽器可服務的並發連接數；一旦達到限制，後續連接將被斷開，直到現有連接關閉`preauth_timeout`限制客戶端的身份驗證時間，從而限制半開連線在代理放棄之前可以佔用資源的時間`max_auth_attempts`在達到配置的身份驗證失敗次數後關閉連接，失敗次數包括代理自身拒絕的命令和後端拒絕的憑證。這可以減緩針對代理的憑證猜測攻擊，並限制單一客戶端連線可以開啟的後端連線數。

## Accepting the PROXY protocol｜接受PROXY協議

 When the proxy itself sits behind a load balancer or another proxy, the connecting peer is not the real client, and the client’s true address arrives in a PROXY protocol header. Setting `proxy_protocol` to `optional` or `required` instructs the listener to read that header and adopt the addresses it carries. The `proxy_trusted` list names the CIDR ranges permitted to send such a header and is mandatory whenever `proxy_protocol` is enabled, so that an untrusted client cannot spoof its address.

 當代理本身位於負載平衡器或另一個代理程式後面時，連接對等點不是真正的客戶端，且客戶端的真實位址到達PROXY協定標頭。將`proxy_protocol`設定為`optional`或`required`指示偵聽器讀取該標頭並採用其所攜帶的位址。 `proxy_trusted` 清單指定了允許發送此類標頭的 CIDR 範圍，並且每當啟用 `proxy_protocol` 時都是強制的，以便不受信任的客戶端無法欺騙其地址。

```toml
[listener.imap]
protocol = "imap"
bind = ["0.0.0.0:993"]
tls = "implicit"
proxy_protocol = "required"
proxy_trusted = ["10.0.0.0/8"]
```

With `optional`, a header from a trusted peer is honored and its absence is tolerated; a connection from outside the trusted ranges is served using its real socket address. With `required`, a trusted peer that fails to send a valid header is rejected, and an untrusted peer is rejected outright. This inbound PROXY handling is independent of the PROXY headers the proxy emits toward backends, which are configured per destination.

 對於`optional` ，來自受信任對等方的頭部資訊會被接受，即使缺少該頭部資訊也會被容忍；來自受信任範圍之外的連接將使用其真實的套接字位址進行服務。對於`required` ，如果受信任對等方未能發送有效的頭部訊息，則會被拒絕；對於不受信任的對等方，則會被直接拒絕。這種入站PROXY處理方式獨立於代理向後端發送的PROXY頭部訊息，後者是針對每個 目標進行配置的。

 For HTTP listeners, the `forwarded` key plays an analogous role at the application layer: when set to `trust`, inbound `Forwarded` and `X-Forwarded-For` headers are preserved and extended; when `off`, they are stripped so that a client cannot inject a forged forwarding chain. This is described further on the HTTP routing page.

 為了 HTTP 聽眾們 `forwarded` 鍵在應用程式層扮演類似的角色：當設定為 `trust`入站 `Forwarded` 和 `X-Forwarded-For` 標頭會被保留和擴展；當 `off`它們被剝離，以防止客戶端注入偽造的轉發鏈。這在\[此處\]中有更詳細的描述。HTTP 路由\]\([https://stalw.art/docs/migration/proxy/routing/http](https://stalw.art/docs/migration/proxy/routing/http)\) 頁。

## Advertised capabilities and banners｜廣告宣傳的功能和橫幅

 For the interactive protocols, the proxy conducts the pre-authentication dialogue itself rather than relaying it to a backend, since the backend is not selected until the client has authenticated. As a result, the greeting banner, the advertised protocol extensions, and the offered authentication mechanisms are produced by the proxy and are configurable under `[capabilities.*]`. Each interactive protocol has its own table: `[capabilities.imap]`, `[capabilities.pop3]`, `[capabilities.submission]` and `[capabilities.managesieve]`.

 對於互動式協議，代理伺服器會自行執行預認證對話，而不是將其轉發給後端，因為後端只有在客戶端完成認證後才會被選擇。因此，歡迎橫幅、已發布的協議擴展以及提供的認證機制均由代理伺服器生成，並可在`[capabilities.*]`中進行配置。每個互動式協定都有其自身的配置表： `[capabilities.imap]`, `[capabilities.pop3]`, `[capabilities.submission]`和`[capabilities.managesieve]` 。

 The defaults advertise a broad, modern capability set and are suitable for most deployments; customization is mainly useful to match what a particular backend supports or to constrain the authentication mechanisms on offer. The common keys are:

 預設設定提供了一套全面且現代化的功能集，適用於大多數部署環境；自訂設定主要用於匹配特定後端支援的功能或限制可用的身份驗證機制。常用鍵包括：

- `sasl`: the list of SASL mechanisms advertised. The defaults are `PLAIN`, `LOGIN`, `OAUTHBEARER` and `XOAUTH2`, which matches what Stalwart itself advertises on TLS-protected ports. The supported values are exactly those four, and a name outside that set, or a name repeated within the list, is rejected at startup. The proxy intercepts and replays these mechanisms regardless of the backend: `LOGIN` in particular is conducted by the proxy as its usual two-prompt exchange and reconstructed into a `PLAIN` challenge, so the backend leg never receives `LOGIN`. Removing `LOGIN` from the list stops it from being advertised and causes an attempt to use it to be rejected, which is appropriate where every client is known to support `PLAIN`; it should be kept where legacy clients such as Outlook 2019 for macOS, which authenticate with `LOGIN` and do not fall back, must keep working.
`sasl` ：已通告的SASL機制清單。預設值為`PLAIN`, `LOGIN`, `OAUTHBEARER`和`XOAUTH2` ，這與 Stalwart 本身在受TLS保護的連接埠上通告的機制一致。支援的值恰好是這四個，超出此範圍的名稱或在清單中重複的名稱將在啟動時被拒絕。代理會攔截並重播這些機制，而無需考慮後端：特別是`LOGIN`代理會將其作為通常的雙提示交換執行，並重構為`PLAIN`挑戰，因此後端永遠不會收到`LOGIN` 。從清單中刪除`LOGIN`會阻止它被宣傳，並導致嘗試使用它時被拒絕，這適用於已知每個客戶端都支援`PLAIN`情況；對於使用`LOGIN`進行身份驗證且不回退的舊版客戶端（例如 macOS 版 Outlook 2019），應該保留它，以便它們能夠繼續工作，以便它們能夠繼續工作，以便它們能夠繼續工作，以便它們能夠繼續工作，以便它們能夠繼續工作。
- `allow_plain_auth_without_tls`: whether cleartext authentication \(`PLAIN` and `LOGIN`, and the IMAP `LOGIN` and POP3 `USER`/`PASS` commands\) is permitted before TLS is established. The default is `false`, which causes the proxy to advertise `LOGINDISABLED` and to reject cleartext authentication with a privacy-required error until the connection is encrypted.
`allow_plain_auth_without_tls` ：是否允許在建立TLS連接之前進行明文認證（ `PLAIN`和`LOGIN`以及IMAP `LOGIN`和POP3 `USER`/`PASS`命令）。預設值為`false` ，這將導致代理伺服器通告`LOGINDISABLED`並拒絕明文認證，同時傳回「需要隱私」錯誤，直到連線加密為止。
- `banner`: the greeting text presented on connection.
`banner` ：連接時顯示的問候語。

```toml
[capabilities.imap]
banner = "Stalwart IMAP4rev2 at your service."
allow_plain_auth_without_tls = false
sasl = ["PLAIN", "LOGIN", "OAUTHBEARER", "XOAUTH2"]
```

The IMAP table additionally accepts `advertise`, the list of capability tokens announced in the greeting and in response to the `CAPABILITY` command. The ManageSieve table accepts `sieve`, the list of supported Sieve extensions, and `implementation`, the implementation string reported to clients. The submission table accepts `ehlo`, the list of ESMTP keywords announced in the `EHLO` response.

 IMAP表也接受`advertise` ，即在問候語和對`CAPABILITY`命令的回應中宣布的功能令牌清單。 ManageSieve 表接受`sieve` ，即支援的 Sieve 擴充列表，以及`implementation` ，即報告給客戶端的實作字串。提交表接受`ehlo` ，即在`EHLO`回應中宣布的ESMTP關鍵字列表。

 Whether cleartext authentication is permitted is computed from `allow_plain_auth_without_tls` together with whether the connection is already encrypted, so on an implicit-TLS listener cleartext mechanisms are always available, while on a STARTTLS listener they only become available after the upgrade unless the override is set.

 是否允許明文認證由`allow_plain_auth_without_tls`以及連接是否已加密來計算，因此在隱式TLS監聽器上，明文機制始終可用，而在STARTTLS監聽器上，除非設定了覆蓋，否則只有在升級後才能使用。

## OAuth identity claim｜OAuth身份聲明

 When clients authenticate with an OAuth bearer token rather than a password, the proxy derives the routing identifier from a claim inside the token. The `[oauth]` table selects which claim to read:

 當用戶端使用 OAuth 持有者令牌而非密碼進行身份驗證時，代理程式會從令牌內部的聲明中衍生出路由識別碼`[oauth]`表用於選擇要讀取的宣告：

```toml
[oauth]
jwt_username_claim = "email"
```

The default claim is `email`. For tokens that are not standard JWTs, including Stalwart’s own access tokens, the proxy applies built-in extraction rules described under Routing. The claim setting only affects how the routing identifier is determined; the token itself is forwarded unchanged for the backend to validate.

 預設宣告為`email` 。對於非標準 JWT 令牌（包括 Stalwart 自有的存取權杖），代理程式會套用 路由中所述的內建提取規則。聲明設定僅影響路由標識符的確定方式；令牌本身會原封不動地轉送給後端進行驗證。
