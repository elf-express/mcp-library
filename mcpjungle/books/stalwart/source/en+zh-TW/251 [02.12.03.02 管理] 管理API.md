# Management API｜管理API

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[management｜管理\\\]\\\(&lt;000 目錄.md#c-44&gt;\\\)

The management API is a small HTTP interface for inspecting and adjusting a running proxy. It exposes statistics, mapping management, cache control, connection control and configuration reload. The API is optional and is only available when an `[admin]` table is present in the configuration.

 管理API是一個小型HTTP介面，用於檢查和調整正在運行的代理程式。它提供統計、映射管理、快取控制、連接控制和配置重新載入。 API 是可選的，僅當配置中存在 `[admin]` 表時才可用。

## Enabling the API｜啟用API

 The `[admin]` table configures the listener and its authentication:

`[admin]`表配置監聽器及其驗證：

```toml
[admin]
bind = "127.0.0.1:9443"
tls = "implicit"
bearer_token_file = "/etc/proxy/admin.token"
min_token_len = 32
lockout_threshold = 5
lockout_duration = "5m"
```

| Key 鍵 | Default 預設值 | Description 描述 |
| --- | --- | --- |
| `bind` | required 必填 | Address the management listener binds to. 管理監聽器綁定的位址。 |
| `tls` | `implicit` | Must be `implicit`; plaintext administration is rejected. 必須為`implicit` ；明文管理將被拒絕。 |
| `bearer_token_file` | unset 未設定 | Path to a file containing the bearer token. 包含持有者令牌的檔案路徑。 |
| `bearer_token` | unset 未設定 | Inline bearer token. 內聯持有人令牌。 |
| `min_token_len` | `32` | Minimum acceptable token length. 可接受的最小令牌長度。 |
| `lockout_threshold` | `5` | Failed attempts from one address before it is locked out. 某個位址被鎖定前嘗試連線的失敗次數。 |
| `lockout_duration` | `5m` | How long a locked-out address is refused. 被鎖定的位址會被拒絕多久？ |

The listener always uses TLS; a configuration that sets `tls` to anything other than `implicit` is rejected at startup, so the API is never served in the clear. The bearer token may be supplied from a file, inline, or through the `PROXY_ADMIN_TOKEN` environment variable, which takes precedence over both; at least one source must be present, and the token must be at least `min_token_len` characters. Binding to the loopback address, as in the example, keeps the API reachable only from the host; binding to a routable address exposes it to the network and should be done only on a trusted segment.

 監聽器始終使用TLS ；如果將`tls`設定為除`implicit`以外的任何值，則在啟動時將拒絕該配置，因此API永遠不會以明文形式提供。持有者令牌可以從檔案、內聯或透過`PROXY_ADMIN_TOKEN`環境變數提供，其中環境變數的優先權高於前兩者；必須至少存在一個來源，且令牌長度必須至少為`min_token_len`個字元。如範例所示，綁定到回環位址可確保API只能從主機存取；綁定到可路由位址會將其暴露給網絡，因此只能在受信任的網段上進行。

 Repeated authentication failures from a single address are counted, and once `lockout_threshold` is reached that address is refused for `lockout_duration`, which slows brute-force attempts against the token.

 單一地址的重複身份驗證失敗將被計數，一旦達到`lockout_threshold` ，該地址將被拒絕進行`lockout_duration` ，這減緩了對令牌的暴力破解嘗試。

## Authentication｜驗證

 Every endpoint except the health check requires a bearer token in the `Authorization` header. The token is compared in constant time. Because the listener uses TLS with a certificate that may be internally generated, the examples below use `curl -k` to skip certificate verification; in a deployment with a trusted certificate on the management listener this is unnecessary.

 除了健康檢查之外，所有端點都需要在`Authorization`標頭中包含持有者令牌。令牌的比較時間是恆定的。由於監聽器使用TLS標頭，而該標頭可能包含內部產生的證書，因此以下範例使用`curl -k`標頭來跳過證書驗證；在管理監聽器上已配置受信任證書的部署環境中，則無需進行此操作。

```bash title=&amp;quot;Terminal window&amp;quot;
TOKEN=$(cat /etc/proxy/admin.token)
curl -sk -H "Authorization: Bearer $TOKEN" https://127.0.0.1:9443/stats
```

## Endpoints｜終點

### Health｜健康

`GET /healthz` returns `200 OK` and requires no authentication. It is intended for liveness probes.

`GET /healthz`返回`200 OK` ，無需身份驗證。它用於活體檢測。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk https://127.0.0.1:9443/healthz
```

### Statistics｜統計數據

`GET /stats` returns the cache and connection counters as JSON: cumulative cache hits and misses, the hit rate as a percentage, the number of cached entries, and the number of active connections.

`GET /stats`返回快取和連線計數器，如JSON所示：累計快取命中和未命中次數、命中率（百分比）、快取條目數和活動連線數。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -H "Authorization: Bearer $TOKEN" https://127.0.0.1:9443/stats
```

```json
{
  "cache_hits": 18234,
  "cache_misses": 412,
  "hit_rate_pct": 97.79,
  "cache_entries": 380,
  "active_connections": 27
}
```

### Destinations｜目的地

`GET /destinations` lists every destination with its consecutive-failure count and whether it is currently marked down by the health circuit breaker. Each entry also reports `failure_sources`, the number of distinct client addresses in the current failure streak, and `host_level_failure`, which is true when the streak includes a failure at the connect stage. Together they separate a failing backend from a backend that is rejecting one banned client, as described under Destinations.

`GET /destinations`列出了每個目標伺服器及其連續故障次數，以及該伺服器目前是否已被健康熔斷器標記為故障。每個條目也報告`failure_sources` ，即當前故障連串中不同客戶端位址的數量，以及`host_level_failure` ，當連串故障包含連接階段的故障時，該值為真。它們共同用於區分故障後端和拒絕單一被封禁客戶端的後端，如 目標伺服器中所述。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -H "Authorization: Bearer $TOKEN" https://127.0.0.1:9443/destinations
```

```json
{
  "destinations": [
    {
      "destination": "legacy",
      "consecutive_failures": 12,
      "failure_sources": 1,
      "host_level_failure": false,
      "down": false
    }
  ]
}
```

`POST /destinations/reset?destination=<id>` clears a destination’s failure count and down state, returning it to service immediately.

`POST /destinations/reset?destination=<id>`清除目的地的故障計數和停機狀態，使其立即恢復服務。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/destinations/reset?destination=legacy"
```

### Mappings｜對應

`GET /mappings?identifier=<id>` reports how an identifier resolves: the normalized form, the destination it maps to, whether that is the default \(a fall-through\), and whether the result is currently cached. This is the diagnostic for confirming where a given account will be routed.

`GET /mappings?identifier=<id>`報告標識符的解析方式：規範化形式、其映射到的目標位址、是否為預設位址（回退位址）以及結果是否已快取。此診斷資訊用於確認給定帳戶的路由目標。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]"
```

```json
{
  "identifier": "[email protected]",
  "normalized": "[email protected]",
  "destination": "stalwart",
  "routed_to_default": false,
  "cached": true
}
```

`PUT /mappings?identifier=<id>&destination=<dest>` creates or replaces a mapping and invalidates the cached entry for that identifier, so the change takes effect on the next connection. The store must be writable and the destination must be declared; otherwise the request is refused.

`PUT /mappings?identifier=<id>&destination=<dest>`建立或取代映射，並使該標識符的快取條目失效，以便變更在下次連線時生效。儲存必須可寫，並且必須聲明目標位址；否則請求將被拒絕。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]&destination=stalwart"
```

`DELETE /mappings?identifier=<id>` removes a mapping and invalidates its cached entry; the account then falls through to the default destination.

`DELETE /mappings?identifier=<id>`刪除映射並使其快取條目失效；然後帳戶將轉至預設目的地。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X DELETE -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]"
```

Writes are only accepted when the mapping store supports them: the file and Redis sources are always writable, while a SQL source is writable only when both `upsert_query` and `delete_query` are configured. A write against a read-only store returns a not-implemented response.

 只有當映射儲存支援寫入操作時，寫入操作才會被接受：檔案和 Redis 來源始終可寫，而SQL來源僅在同時配置了`upsert_query`和`delete_query`時才可寫。對唯讀儲存執行寫入操作會傳回「未實現」的回應。

`POST /mappings/reload` re-reads the mapping store from its source. This is meaningful for the file source, which is loaded into memory at startup; the Redis and SQL sources read on each lookup and return success without doing anything.

`POST /mappings/reload`從其來源重新讀取映射儲存。這對於在啟動時載入到記憶體中的檔案來源來說是有意義的；Redis 和SQL來源在每次查找時讀取映射並返回成功，而不執行任何操作。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  https://127.0.0.1:9443/mappings/reload
```

### Cache｜快取

`POST /cache/invalidate?identifier=<id>` drops the cached entry for one account; with no `identifier` parameter it clears the whole cache. The cache invalidation page covers when to use each form.

`POST /cache/invalidate?identifier=<id>`刪除一個帳戶的快取條目；如果沒有`identifier`參數，則會清除所有快取。 快取失效頁面介紹了何時使用每種表單。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/cache/[email protected]"
```

### Connections｜連接

`POST /connections/kick?identifier=<id>` disconnects all currently bridged sessions for an account and reports how many were terminated. A mail session is registered once the backend accepts its authentication, and an HTTP connection once one of its requests identifies an account, which covers JMAP-over-WebSocket sessions after the upgrade. This is useful to force a migrated account off its old backend immediately, so its next connection re-resolves to the new destination.

`POST /connections/kick?identifier=<id>`斷開帳戶目前所有橋接會話，並報告已終止的會話數量。後端接受身份驗證後，郵件會話即被註冊； HTTP連接一旦其請求識別出帳戶，連接即被註冊，這涵蓋了升級後的JMAP基於 WebSocket 的會話。這有助於強制遷移後的帳戶立即脫離其舊後端，以便其下一個連線重新解析到新的目標。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]"
```

`POST /connections/delay?identifier=<id>&seconds=<n>` holds back new logins for an account for the given number of seconds, pausing each new session briefly before it is established. An HTTP connection is held once one of its requests identifies the account. This smooths a cutover by letting in-flight operations settle before the account begins connecting to its new backend.

`POST /connections/delay?identifier=<id>&seconds=<n>` 在給定的秒數內保留帳戶的新登錄，在建立每個新會話之前短暫暫停它。一旦其中一個請求識別出帳戶，就會保持 HTTP 連線。這樣可以在帳戶開始連接到新後端之前解決正在進行的操作，從而平滑切換。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]&seconds=30"
```

### Configuration reload｜配置重新載入

`POST /config/reload` re-reads and validates the configuration file, swapping the running configuration only if it is valid. The response notes which settings require a restart instead. See Management for the reload semantics.

`POST /config/reload`重新讀取並驗證設定文件，僅當配置有效時才替換運行配置。響應會指出哪些設定需要重新啟動。有關重新載入的語義，請參閱管理 。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  https://127.0.0.1:9443/config/reload
```
