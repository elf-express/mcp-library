# Docker

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[install｜安裝\\\]\\\(&lt;000 目錄.md#c-29&gt;\\\) › \\\[platform｜平台\\\]\\\(&lt;000 目錄.md#c-30&gt;\\\)

Stalwart is distributed as a multi-architecture Docker image that bundles the server binary and a minimal Debian runtime, covering JMAP, IMAP, POP3, SMTP, WebDAV, and the management HTTP interface. The image is published to both Docker Hub and GitHub Container Registry.

 Stalwart 以多架構 Docker 映像的形式分發，該映像捆綁了伺服器二進位和精簡的 Debian 執行環境，涵蓋JMAP, IMAP, POP3, SMTP 、WebDAV 和管理HTTP介面。該映像已發佈到 Docker Hub 和 GitHub 容器註冊表。

 The `latest` tag tracks the newest release and moves forward as new versions ship. For production deployments, pin to a `v<major>.<minor>` tag such as `v0.16`. The CI publishes this short form in addition to the full `v<major>.<minor>.<patch>` tag and `edge` \(latest build from the main branch\), so picking the short form keeps deployments on a single minor series and avoids breaking semver changes on upgrade.

`latest`標籤用於追蹤最新版本，並隨著新版本的發布而更新。對於生產環境部署，請鎖定到`v<major>.<minor>`標籤，例如`v0.16` CI除了發布完整的`v<major>.<minor>.<patch>`標籤和`edge` （主分支的最新構建版本）之外，還會發布此簡短版本號。因此，選擇簡短版本號碼可確保部署版本始終位於同一次版本系列中，並避免在升級時破壞語意化版本控制 \(semver\) 規​​範。

```bash title=&amp;quot;Terminal window&amp;quot;
$ docker pull stalwartlabs/stalwart:v0.16
```

Replace `v0.16` with the current stable release if a newer minor version has shipped. For installations that use FoundationDB as the main data store, see [FoundationDB](#foundationdb) under *Additional topics* below.

 如果已發布較新的次要版本，請將 `v0.16` 替換為目前穩定版本。使用 FoundationDB 作為主資料儲存的安裝，請參閱下方的*其他主題*下的 [FoundationDB](#foundationdb)。

## Start the container｜啟動容器

 The image declares two volumes for configuration and data persistence. The volume `/etc/stalwart` is intended for the configuration file, while `/var/lib/stalwart` is meant for application data.

 該鏡像聲明了兩個卷，分別用於配置和資料持久化。卷`/etc/stalwart`用於存放設定文件，而磁碟區`/var/lib/stalwart`用於存放應用程式資料。

 The data volume is only written to when Stalwart uses a local storage backend such as RocksDB. Deployments that rely exclusively on external stores \(S3, PostgreSQL, MySQL, Redis, Azure Blob, NATS\) can leave the data volume empty. Application logs are written to the container’s standard output and captured by Docker’s log driver, so no dedicated log volume is required.

 只有當 Stalwart 使用本機儲存後端（例如 RocksDB）時，才會寫入資料卷。完全依賴外部儲存（S3、PostgreSQL、MySQL、Redis、Azure Blob、 NATS ）的部署可以將資料卷留空。應用程式日誌會寫入容器的標準輸出，並由 Docker 的日誌驅動程式捕獲，因此無需專用的日誌磁碟區。

 Create named Docker volumes and start the container with the full set of mail and management ports published to the host:

 建立命名 Docker 卷，並啟動容器，同時將全部郵件和管理連接埠發佈到主機：

```bash title=&amp;quot;Terminal window&amp;quot;
$ docker volume create stalwart-etc
$ docker volume create stalwart-data
$ docker run -d --name stalwart \
    --restart unless-stopped \
    -p 443:443 -p 8080:8080 \
    -p 25:25 -p 587:587 -p 465:465 \
    -p 143:143 -p 993:993 \
    -p 110:110 -p 995:995 \
    -p 4190:4190 \
    -v stalwart-etc:/etc/stalwart \
    -v stalwart-data:/var/lib/stalwart \
    stalwartlabs/stalwart:v0.16
```

Publishing every port is not required. Internal deployments that only need, for example, submission \(`587`\) and IMAPS \(`993`\) can prune the list accordingly. Refer to the securing your server documentation for guidance on which ports to expose.

 並非所有連接埠都需要公開。例如，內部部署可能只需要公開`587`和 P117 端口，而IMAPS則需要公開 P18 和`993`端口，因此可以根據需要精簡端口列表。有關需要公開哪些連接埠的指南，請參閱 保護您的伺服器文件。

 The image runs as an unprivileged `stalwart` user \(UID 2000\). Docker’s default capability set is sufficient for binding ports below 1024 on Linux: the binary carries the `cap_net_bind_service` file capability, so no `--cap-add` or `--privileged` flag is needed. Starting the container with `--cap-drop NET_BIND_SERVICE` causes the binary to fail at exec time.

 鏡像以非特權使用者（ `stalwart` UID 2000）身分運作。 Docker 的預設權限集足以綁定 Linux 系統上低於 1024 的連接埠：此二進位檔案具備`cap_net_bind_service`檔案權限，因此無需使用`--cap-add`或`--privileged`標誌。使用`--cap-drop NET_BIND_SERVICE`啟動容器會導致二進位檔案在執行時失敗。

 When the host port mapping is not `443`, or a reverse proxy fronts the container on a different URL, pass the public-facing URL through `STALWART_PUBLIC_URL` so that discovery documents publish the URL clients actually use. For example: `-e STALWART_PUBLIC_URL=https://mail.example.com:8443`. The variable accepts a full base URL with scheme, host, optional port, and optional path prefix \(e.g. `https://example.com/mail`\). It does not change which ports the container itself binds to; those continue to be controlled by `-p` and the NetworkListener objects. See Public URLs for the full reference.

 當主機連接埠對映不是`443` ，或反向代理在不同的URL上為容器提供前端服務時，請將面向公眾的URL傳遞給`STALWART_PUBLIC_URL`以便發現文件發佈客戶端實際使用的URL連接埠。例如： `-e STALWART_PUBLIC_URL=https://mail.example.com:8443` 。此變數接受一個完整的基本URL其中包含協定、主機、可選連接埠和可選路徑前綴（例如`https://example.com/mail` ）。它不會更改容器本身綁定的連接埠；這些連接埠仍然由`-p`和 NetworkListener物件控制。完整參考，請參閱 公用 URL 。

 The example above uses named Docker volumes, which are populated with the correct ownership automatically. When bind-mounting host directories instead \(for example `-v /srv/stalwart/config:/etc/stalwart`\), the host directory must be owned by UID 2000 so the service account can read and write it. Run `chown 2000:2000 /srv/stalwart/config /srv/stalwart/data` on the host before starting the container.

 上述範例使用了命名 Docker 卷，這些卷會自動填入正確的所有權。如果改為綁定掛載主機目錄（例如`-v /srv/stalwart/config:/etc/stalwart` ），則主機目錄的擁有者必須為UID 2000，以便服務帳戶可以對其進行讀寫操作。在啟動容器之前，請在主機上運行`chown 2000:2000 /srv/stalwart/config /srv/stalwart/data` 。

## Retrieve the administrator credentials｜取得管理員憑證

 After the container starts for the first time, Stalwart runs in **bootstrap mode**. A temporary administrator account is generated with a random password and the credentials are written to the container’s standard error. Bootstrap mode is a transient phase intended only to reach the setup wizard, after which a permanent administrator account is provisioned.

 容器首次啟動後，Stalwart 會以**引導模式**運作。系統會產生一個帶有隨機密碼的臨時管理員帳戶，並將憑證寫入容器的標準錯誤輸出。引導模式是一個過渡階段，僅用於引導程式執行到設定精靈，之後才會配置永久管理員帳戶。

 Print the container logs and locate the bootstrap banner:

 列印容器日誌並找到引導程式橫幅：

```bash title=&amp;quot;Terminal window&amp;quot;
$ docker logs stalwart 2>&1 | grep -A8 'bootstrap mode'
```

The block to look for looks like this:

 需要尋找的區塊如下：

```
════════════════════════════════════════════════════════════
🔑 Stalwart bootstrap mode - temporary administrator account

   username: admin
   password: XXXXXXXXXXXXXXXX

Use these credentials to complete the initial setup at the
/admin web UI. Once setup is done, Stalwart will provision a
permanent administrator and this temporary account will no
longer apply.
════════════════════════════════════════════════════════════
```

Copy the 16-character password from the `password:` line. This is the only time the value appears in the logs.

 從`password:`行複製16個字元的密碼。這是該值唯一一次出現在日誌中。

 To avoid relying on a log-extracted temporary password, a fixed credential can be set at container start time. Pass the value via `-e`, for example `-e STALWART_RECOVERY_ADMIN=admin:mySecretPass`. The administrator credentials will match the configured value and no temporary password will be generated. The same variable can also be placed in a Docker Compose `environment:` block or sourced from a Compose `env_file:` entry.

 為了避免依賴從日誌中提取的臨時密碼，可以在容器啟動時設定固定憑證。例如，可以透過`-e`傳遞該值，如`-e STALWART_RECOVERY_ADMIN=admin:mySecretPass` 。管理員憑證將與配置的值匹配，不會產生臨時密碼。此變數也可以放在 Docker Compose `environment:`程式碼區塊中，或從 Compose `env_file:`條目中取得。

## Open the setup wizard｜打開安裝精靈

 With the bootstrap credentials in hand, open a web browser and navigate to:

 取得到引導程式憑證後，開啟網頁瀏覽器並導航至：

```
http://<hostname>:8080/admin
```

Replace `<hostname>` with the hostname or IP address of the machine running Stalwart. On the machine itself, `http://127.0.0.1:8080/admin` works for local access. Sign in using `admin` as the username and the temporary password retrieved in the previous step; the setup wizard appears automatically.

 將`<hostname>`替換為運行 Stalwart 的電腦的主機名稱或IP位址。在電腦本身上， `http://127.0.0.1:8080/admin`用於本地存取。使用`admin`作為使用者名稱和上一步中取得的臨時密碼登入；設定精靈將會自動出現。

 The wizard presents five screens plus a final confirmation. Every field has a sensible default, so most installations only need to enter their hostname and domain and click through the rest. Deployments that prefer to skip the wizard entirely and drive the same configuration from the CLI should consult [Non-interactive setup](#non-interactive-setup) under *Additional topics* below.

 此嚮導顯示五個螢幕以及最終確認。每個欄位都有一個合理的預設值，因此大多數安裝只需輸入主機名稱和網域，然後按一下其餘部分。希望完全跳過精靈並從CLI驅動相同配置的部署應參考下面的*其他主題*下的[非互動設定](#non-interactive-setup)。

### Step 1 of 5: Server identity｜步驟 1（共 5 步）：伺服器身份

 Two required fields plus two optional toggles.

 兩個必填欄位和兩個可選切換欄位。

- **Server hostname:**
**伺服器主機名稱：**> The public hostname this Stalwart server answers to, for example \\\`mail.example.com\\\`. This value appears in SMTP greetings, outgoing message headers, and TLS certificate requests. It must be a valid domain name resolving via public DNS to this server’s IP address. For test or internal deployments, Stalwart accepts the RFC 6761 reserved TLDs \\\(\\\`.test\\\`, \\\`.local\\\`, \\\`.localhost\\\`, \\\`.invalid\\\`, \\\`.example\\\`\\\); add the hostname to \\\`/etc/hosts\\\` or to the private DNS zone that serves the deployment.
 此 Stalwart 伺服器回應的公共主機名，例如\`mail.example.com\` 。此值出現在SMTP問候語、外寄郵件頭和TLS憑證請求中。它必須是一個有效的域名，能夠透過公共DNS解析到此伺服器的IP位址。對於測試或內部部署，Stalwart 接受RFC 6761 個保留頂級網域名稱 \( \`.test\`, \`.local\`, \`.localhost\`, \`.invalid\`, \`.example\` \)；將主機名稱新增至\`/etc/hosts\`或用於部署的私人DNS區域。

 By default, this hostname also becomes the base URL published in OAuth, OIDC, and JMAP discovery documents, served over HTTPS on port \`443\`. Reverse-proxy deployments, custom HTTPS ports, and path-prefixed mounts should set \[\`STALWART\_PUBLIC\_URL\`\]\(&lt;133 \[02.04 配置\] 環境變數.md#public-urls&gt;\) to override the published base URL; see \[Reverse proxy\]\(&lt;469 \[02.15.02 反向代理\] 概述.md&gt;\).

 預設情況下，此主機名稱也成為 OAuth OIDC \([https://stalw.art/docs/configuration/environment-variables#public-urls\\](https://stalw.art/docs/configuration/environment-variables#public-urls%255C)\) URL JMAP HTTPS \`443\` \`STALWART\_PUBLIC\_URL\` HTTPS URL名稱；請參閱 \[反向代理\]\(&lt;469 \[02.15.02 反向代理\] 概述.md&gt;\) 。

- **Default email domain:**
**預設電子郵件網域：**> The primary domain this installation will serve, for example \\\`example.com\\\`. Must be a valid domain name. Additional domains can be added at any time after setup. For test deployments, use a \\\`.test\\\` domain \\\(e.g. \\\`example.test\\\`\\\).
 此安裝將服務於主域，例如\`example.com\` 。必須是有效的域名。設定完成後，可以隨時新增其他網域。對於測試部署，請使用\`.test\`域（例如\`example.test\` ）。

- **Automatically obtain TLS certificate**:
**自動取得TLS證書**：> Leave enabled to have Stalwart request a free TLS certificate for the server hostname from Let’s Encrypt using the ACME protocol. This is the recommended option for most deployments, because mail and web clients can then connect securely on the very first start without any additional steps. Disable the checkbox only if a certificate will be uploaded manually later, or if TLS is terminated by a reverse proxy in front of Stalwart.
 啟用此選項後，Stalwart 將使用ACME協定向 Let's Encrypt 請求伺服器主機名稱的免費TLS憑證。對於大多數部署，這是建議選項，因為郵件和 Web 用戶端無需任何額外步驟即可在首次啟動時安全連線。只有稍後需要手動上傳證書，或TLS協定由 Stalwart 前面的反向代理終止時，才應取消選取此核取方塊。

- **Generate email signing keys:**
**產生電子郵件簽章金鑰：**> Leave enabled to have Stalwart generate DKIM signing keys for the default domain. DKIM cryptographically signs outgoing messages and significantly improves the chances that they are accepted by remote servers rather than classified as spam. Disable only when DKIM keys are managed externally.
 保持啟用狀態，讓 Stalwart 為預設域產生 DKIM 簽章金鑰。 DKIM 對傳出郵件進行加密簽名，並顯著提高遠端伺服器接受郵件而不是被分類為垃圾郵件的機會。僅當DKIM金鑰由外部管理時停用。


 When the *automatically obtain TLS certificate* option is enabled and an automatic DNS provider is selected in [Step 5](#step-5-of-5-automatic-dns-management), Stalwart validates certificate requests with the DNS-01 challenge, which does not require any ports to be reachable from the internet. When DNS management is left manual in Step 5, Stalwart falls back to the TLS-ALPN-01 challenge, which Let’s Encrypt validates by connecting directly to the server on **TCP port 443**. In that case, before restarting the server after the wizard, make sure that the machine is reachable from the public internet on port 443, that no reverse proxy or load balancer is intercepting the connection, and that the server hostname entered above resolves to this machine in public DNS. See ACME challenge types for the full picture.

 當啟用*自動取得TLS憑證*選項並在[步驟5](#step-5-of-5-automatic-dns-management)中選擇自動DNS提供者時，Stalwart會使用DNS-01質詢來驗證憑證要求，這不需要可從網路存取任何連接埠。當在步驟 5 中將DNS 管理保留為手動時，Stalwart 會退回到TLS-ALPN-01 挑戰，Let’s Encrypt 透過直接連接到 **TCP 連接埠 443** 上的伺服器來驗證該挑戰。在這種情況下，在嚮導之後重新啟動伺服器之前，請確保可以透過連接埠 443 從公共 Internet 存取該計算機，沒有反向代理或負載平衡器攔截該連接，並且上面輸入的伺服器主機名稱在公共DNS 中解析為該計算機。請參閱ACME挑戰類型以了解完整情況。

### Step 2 of 5: Storage｜步驟 2（共 5 步）：存儲

 Storage is split into four independent stores. All four default to RocksDB on local disk, which is the recommended configuration for single-node installations and requires no action. Each store can be moved to an external backend later through the WebUI without reinstalling.

 儲存分為四個獨立的儲存庫。所有四個儲存庫預設都使用本機磁碟上的 RocksDB，這是單節點安裝的建議配置，無需任何操作。每個儲存庫都可以稍後透過 WebUI 遷移到外部後端，而無需重新安裝。

- **Main data storage:**
**主要資料儲存：**> Where structured data lives: email metadata, calendar events, address book entries, mailbox state, and every server settings object. The default is RocksDB. PostgreSQL, MySQL, SQLite, and FoundationDB are available for larger deployments or when a specific database is mandated by operations policy.
 結構化資料儲存位置：電子郵件元資料、行事曆事件、通訊錄項目、郵件信箱狀態以及所有伺服器設定物件。預設資料庫為 RocksDB。對於規模較大的部署或營運策略要求使用特定資料庫的情況，可以使用 PostgreSQL、MySQL、SQLite 和 FoundationDB。

- **Attachment and file storage:**
**附件和文件存儲：**> Where the raw bytes of email messages, attachments, and other large files are stored. Leave set to \\\*Use Data Store\\\* to keep blobs alongside metadata; switch to a dedicated backend such as S3 or Azure Blob Storage for deployments with many attachments or when long-term object storage is preferable.
 用於儲存電子郵件、附件和其他大型文件的原始位元組資料。如果選擇“使用資料儲存體”，則可將資料區塊與元資料儲存；對於包含大量附件或需要長期物件儲存的部署，請切換至專用後端，例如 S3 或 Azure Blob 儲存。

- **Full-text search index:**
**全文檢索索引：**> Where the full-text search index is kept so that users can search across message bodies and attachments. Leave set to \\\*Use Data Store\\\* for single-node deployments; point to a dedicated search backend \\\(Elasticsearch or Meilisearch\\\) when the search workload is large enough to warrant it.
 全文搜尋索引存放於此，以便使用者可以搜尋郵件正文及其附件。對於單節點部署，請將其設定為「使用資料儲存」；當搜尋工作負載足夠大時，請指向專用的搜尋後端（Elasticsearch 或 Meil​​​​isearch）。

- **Cache and temporary data:**
**快取和臨時資料：**> Where short-lived state lives: session caches, rate-limit counters, authentication tokens. Leave set to \\\*Use Data Store\\\* for a single node; point to Redis for faster lookups and especially for multi-node deployments where cache state must be shared across the cluster.
 用於儲存短生命週期狀態的地方：會話快取、速率限制計數器、身份驗證令牌。對於單節點環境，請保留「使用資料儲存」選項；對於需要更快查找速度的多節點部署（尤其是在叢集中需要共享快取狀態的情況下），請指向 Redis。


### Step 3 of 5: Account directory｜步驟 3（共 5 步）：帳戶目錄

 Stalwart can source user accounts from its own internal directory or delegate authentication to an external identity provider.

 Stalwart 可以從其內部目錄中取得使用者帳戶，也可以將身分驗證委託給外部身分提供者。

- **Directory type:**
**目錄類型：**> Leave set to \\\*Use the Internal Directory\\\* for the simplest installation: accounts are created and managed through the WebUI, and the wizard generates an administrator credential on the final screen. Select an external directory \\\(OIDC, LDAP, or SQL\\\) for single sign-on or for integration with an existing identity system.
 為簡化安裝，請將設定保留為「使用內部目錄」：帳戶透過 WebUI 建立和管理，精靈會在最後一個畫面上產生管理員憑證。選擇外部目錄（OIDC, LDAP， 或者 SQL用於單一登入或與現有身分系統整合。


 The choice here affects the final screen. With the internal directory, a generated administrator credential is printed when the wizard finishes. With an external directory, no credential is generated; the administrator must be promoted after the first sign-in \(see [External directory promotion](#external-directory-promotion) below for the procedure\).

 此處的選擇會影響最終螢幕。使用內部目錄時，精靈完成後會列印產生的管理員憑證。使用外部目錄時，不會產生憑證；管理員必須在首次登入後提升權限（有關步驟，請參閱下文「[外部目錄提升](#external-directory-promotion) 」）。

### Step 4 of 5: Logging｜步驟 4（共 5 步）：日誌記錄

**Log destination.** Where the server writes log messages, traces, and diagnostic events.

**日誌目標位置。** 伺服器將日誌訊息、追蹤資訊和診斷事件寫入此位置。

- *Log File* writes rotating log files to disk under the data directory. This is appropriate whenever the server has persistent disk and rotation is handled directly by Stalwart.
*日誌檔案* 會將輪換日誌檔案寫入磁碟的資料目錄下。當伺服器使用持久性磁碟且 Stalwart 直接處理輪替時，此方法適用。
- *Console* writes log lines to standard output. Select this for containerised deployments so the orchestrator’s log driver \(Docker, Kubernetes, and so on\) can capture them.
*控制台*會將日誌行寫入標準輸出。對於容器化部署，請選擇此選項，以便編排器的日誌驅動程式（Docker、Kubernetes 等）可以擷取這些日誌。
Additional destinations \(OpenTelemetry, journald, remote webhooks\) can be added after setup through the Tracer object.
 設定完成後，可透過 Tracer物件新增其他目標（OpenTelemetry、journald、遠端 webhook）。

 Docker users should select **Console** here. A file-based logger inside a container writes to an ephemeral filesystem that is lost on every container restart; the Console logger emits structured log lines to standard output, which Docker captures through its log driver.

 Docker 使用者應在此處選擇**控制台**。容器內部的基於檔案的日誌記錄器會將資料寫入臨時檔案系統，每次容器重新啟動後檔案系統都會遺失；而控制台日誌記錄器會將結構化的日誌行輸出到標準輸出，Docker 會透過其日誌驅動程式擷取這些日誌。

### Step 5 of 5: Automatic DNS management｜步驟 5（共 5 步）：自動DNS管理

 The DNS records a mail server needs \(SPF, DKIM, DMARC, MX, MTA-STS, autoconfig, and so on\) can either be published manually by the operator or generated and maintained by Stalwart on the operator’s behalf.

 郵件伺服器所需的DNS記錄（ SPF, DKIM, DMARC, MX, MTA-STS 、自動設定等）既可以由操作員手動發布，也可以由 Stalwart 代表操作員產生和維護。

**DNS server type.** Leave set to *Manual DNS Server Management* to keep full control of the DNS records. Select a supported provider \(Cloudflare, AWS Route 53, Google Cloud DNS, etc, or a BIND-compatible server via RFC 2136\) to have Stalwart publish and update the zone entries automatically through the provider’s API. See DNS provider integration for the supported providers and the credentials each one needs. The choice is not final; provider integration can be enabled, disabled, or changed later.

 \**DNS 伺服器類型。 \*\* 保留設定為「手動」。 DNS 伺服器管理* 以保持對伺服器的完全控制 DNS 記錄。選擇一個受支援的提供者（Cloudflare， AWS 53號公路，Google雲 DNS等等，或者一個 BIND透過相容伺服器 RFC 2136\) 使 Stalwart 透過提供者自動發布和更新區域條目 API。 看 DNS 提供者集成 對於支援的提供者及其所需的憑證，請參閱相關資訊。此選擇並非最終確定；提供者整合可以稍後啟用、停用或變更。

#### Retrieving the DNS zone file｜正在檢索DNS區域文件

 When manual management is kept, Stalwart still generates the full set of records that must be published and makes them available as a ready-to-import zone file.

 如果採用手動管理，Stalwart 仍然會產生必須發佈的完整記錄集，並將其作為可匯入的區域文件提供。

 From the WebUI, open the Domain list \(found in the WebUI under Management › Domains › Domains\), click the three-dot menu next to the relevant domain, and select **View DNS Zone file**. The returned zone file can be pasted into the DNS provider’s control panel or imported as a zone template where the provider supports it. See Setting up DNS for a per-record explanation of what each entry does.

 從 WebUI 中，開啟網域清單（可在 WebUI 的管理 › 網域 › 網域下找到），按一下相關網域旁的三點選單，然後選擇 **檢視 DNS 區域檔案**。傳回的區域檔案可以貼上到DNS提供者的控制面板中或作為提供者支援的區域範本匯入。請參閱設定DNS，以了解每個條目的作用的每筆記錄的說明。

 The same records can also be retrieved from the command line; see [Retrieving DNS records via CLI](#retrieving-dns-records-via-cli) under *Additional topics* below.

 也可以從命令列檢索相同的記錄；請參閱下面的*其他主題*下的[透過CLI檢索DNS記錄](#retrieving-dns-records-via-cli)。

**內部目錄。** 此精靈會列印新管理員帳號的電子郵件地址和隨機產生的密碼，例如：

 請記下這兩個訊息。密碼僅顯示在此畫面上，之後無法從伺服器日誌中找回。伺服器重啟後（請參閱下文「平台特定的重啟」部分），可以使用這些憑證登入 Web 使用者介面。

**外部目錄\(OIDC / LDAP / SQL\)。**此處不會產生管理員憑證，因為外部目錄中的帳戶在至少經過一次身份驗證之前不會在本機存在。首次登入後需手動升級管理員；有關流程，請參閱下方*其他主題*下的[外部目錄升級](#external-directory-promotion)。

## Troubleshooting｜故障排除

### Certificate warning on first sign-in｜首次登入時收到憑證警告

 When *automatically obtain TLS certificate* was enabled in Step 1 of the wizard, the certificate from Let’s Encrypt can take a minute or two to be issued after the restart. While the request is still in flight, the browser may show a warning because the server is presenting a self-signed fallback certificate. Accepting that warning for the initial sign-in is safe; the warning disappears once the ACME certificate has been installed and the page is reloaded. When the certificate option was disabled, the self-signed fallback remains in place until a certificate is uploaded or a reverse proxy terminates TLS in front of the server.

 當在精靈的步驟 1 中啟用*自動取得TLS憑證*時，重新啟動後可能需要一兩分鐘才能頒發來自 Let’s Encrypt 的憑證。當請求仍在進行中時，瀏覽器可能會顯示警告，因為伺服器正在提供自簽署的後備憑證。接受初始登入的警告是安全的；安裝ACME憑證並重新載入頁面後，警告就會消失。當憑證選項被停用時，自簽章回退將保持不變，直到上傳憑證或反向代理程式在伺服器前面終止TLS。

### HTTPS not yet reachable｜HTTPS尚無法連接

 If the configured hostname does not yet resolve in DNS, port `443` is not reachable from the browser, or the deployment cannot present a trusted certificate for any other reason, sign in at `http://<host>:8080/admin` for as long as `STALWART_RECOVERY_ADMIN` is set in the service environment. Once HTTPS is in place, switch to `https://<hostname>/admin` and disable the HTTP listener as described in [Next steps](#next-steps).

 若設定的主機名稱在DNS中仍無法解析，或瀏覽器無法存取連接埠`443` ，或部署因任何其他原因無法提供受信任的證書，請在服務環境中設定`STALWART_RECOVERY_ADMIN`期間，登入`http://<host>:8080/admin` 。一旦HTTPS就位，請切換到`https://<hostname>/admin`並按照 [後續步驟](#next-steps)中的說明禁用HTTP監聽器。

 If the HTTP listener has already been disabled and the deployment is locked out \(for example because the configured hostname is no longer reachable, the external OIDC provider is down, or the administrator account was deleted\), start the server in recovery mode \(`STALWART_RECOVERY_MODE=1`\). Recovery mode re-enables the HTTP listener on port `8080` with the path-relative issuer used during bootstrap and accepts the credentials in `STALWART_RECOVERY_ADMIN`, regardless of the directory state. Restart without the flag once normal sign-in is restored.

 如果HTTP監聽器已停用且已部署已被鎖定（例如，由於設定的主機名稱不再可存取、外部OIDC提供者已關閉或管理員帳戶已被刪除），請以 復原模式 \( `STALWART_RECOVERY_MODE=1` \) 啟動伺服器。恢復模式會使用引導期間使用的路徑相對頒發者重新啟用連接埠`8080`上的HTTP監聽器，並接受`STALWART_RECOVERY_ADMIN`中的憑證，而不管目錄狀態如何。恢復正常登入後，無需使用該標誌即可重新啟動。

### Reverse proxy｜反向代理

 When Stalwart sits behind a reverse proxy \(NGINX, Traefik, Caddy, HAProxy, or similar\) and the wizard or first sign-in does not behave as expected, the issue is almost always that the URL Stalwart publishes in its OAuth and JMAP discovery documents does not match the URL clients reach the proxy on. Set STALWART\_PUBLIC\_URL to the public-facing base URL \(scheme, host, port if non-`443`, path if mounted under a prefix\) and restart the server. For example, `STALWART_PUBLIC_URL=https://mail.example.com:8443` for a proxy listening on port `8443`, or `https://example.com/mail` for a path-prefixed mount. The full reverse-proxy model \(HTTP vs HTTPS upstream, Proxy Protocol, and per-product configuration for NGINX / Caddy / Traefik / HAProxy\) is documented under Reverse proxy › Overview.

 當 Stalwart 位於反向代理（ NGINX ，例如 Traefik、Caddy、HAProxy 或類似服務）之後，且嚮導或首次登入未按預期運行時，問題幾乎總是出在 Stalwart 在其 OAuth 和發現文件中發布的URL JMAP客戶端連接到代理的與客戶URL不匹配。請將 STALWART\_PUBLIC\_URL設定為面向公眾的基本URL （方案、主機、連接埠（如果非`443` ）、路徑（若掛載在前綴下）），然後重新啟動伺服器。例如，對於監聽埠`8443`的代理，請設定`STALWART_PUBLIC_URL=https://mail.example.com:8443`對於帶有路徑前綴的掛載，請設定`https://example.com/mail` 。完整的反向代理模型（ HTTP與HTTPS上游、代理協議以及NGINX / Caddy / Traefik / HAProxy 的每個產品配置）記錄在 反向代理 › 概述下。

 For issues that go beyond initial setup \(email delivery, DMARC, authentication, and so on\), consult the general troubleshooting guide or the FAQ.

 對於超出初始設定（電子郵件發送、 DMARC 、身份驗證等）的問題，請參閱一般故障排除指南或FAQ 。

## Additional topics｜其他主題

### External directory promotion｜外部目錄推廣

 When the wizard is completed with an external directory \(OIDC, LDAP, or SQL\), no administrator credential is generated on the final screen, because an account from the external directory does not exist locally until it has authenticated at least once. The administrator must be promoted manually after the first sign-in using the existing recovery admin credentials. The procedure, carried out after the platform-specific restart, is:

 當精靈使用外部目錄（ OIDC, LDAP或SQL ）完成操作後，最終螢幕上不會產生管理員憑證，因為外部目錄中的帳戶在至少驗證一次之前不會在本機存在。首次使用現有恢復管理員憑證登入後，必須手動提升管理員權限。此過程在平台特定的重啟後執行，具體步驟如下：

1. Keep `STALWART_RECOVERY_ADMIN=<username>:` set in the service environment. The variable is honoured while the server is running normally, so this does not require recovery mode.
請在服務環境中保持`STALWART_RECOVERY_ADMIN=<username>:`設定有效。伺服器正常運作時，此變數會生效，因此無需進入復原模式。
2. Have the account that will become the administrator sign in once through the WebUI. Any successful authentication against the directory provisions the account locally in Stalwart.
使用將成為管理員的帳戶透過 WebUI 登入一次。任何針對目錄的成功身份驗證都會在 Stalwart 中本機配置該帳戶。
3. Sign in as the recovery administrator in a separate browser session and assign the appropriate administrator role to the newly provisioned account, either through the WebUI or through the CLI.
在單獨的瀏覽器會話中以恢復管理員身份登錄，並透過 WebUI 或透過CLI將適當的管理員角色指派給新配置的帳戶。
4. Sign in as the promoted account to confirm that the assignment took effect.
使用已提升的帳號登錄，以確認該分配已生效。
5. Remove `STALWART_RECOVERY_ADMIN` from the service environment and restart the server so that the backdoor credential is no longer active.
從服務環境中移除`STALWART_RECOVERY_ADMIN`並重新啟動伺服器，使後門憑證不再處於活動狀態。
### FoundationDB

 A separate build with FoundationDB support is available for installations that use FoundationDB as the main data store. The default build does not include FoundationDB because multiple FoundationDB client versions exist and a single default would break deployments that rely on a different client.

 對於使用 FoundationDB 作為主要資料儲存的安裝，我們提供了一個單獨的包含 FoundationDB 支援的版本。預設版本不包含 FoundationDB，因為存在多個 FoundationDB 用戶端版本，而使用單一的預設版本會破壞依賴不同用戶端的部署。

**Linux / macOS.** Run the installation script with the `--fdb` flag:

**Linux / macOS。** 執行安裝腳本時請使用`--fdb`標誌：

```bash title=&amp;quot;Terminal window&amp;quot;
$ sudo sh install.sh --fdb
```

**Docker.** No pre-built FoundationDB image is published. To produce a FoundationDB-enabled image, use the `Dockerfile.fdb` file available in the [stalwartlabs/stalwart](https://github.com/stalwartlabs/stalwart) repository as a starting point.

**Docker。**目前沒有發布預先建置的 FoundationDB 映像。若要產生啟用 FoundationDB 的鏡像，請使用 [stalwartlabs/stalwart](https://github.com/stalwartlabs/stalwart)倉庫中提供的`Dockerfile.fdb`檔案作為起點。

 啟用DNS管理時，也可以從命令列取得 Stalwart 產生的區域檔案。列出已配置的域，並讀取所需域的 dnsZoneFile字段：
