# Blob store｜Blob 商店

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[storage｜貯存\\\]\\\(&lt;000 目錄.md#c-72&gt;\\\)

The blob store holds the large binary objects managed by the server: raw email messages, Sieve scripts, and other files. Every blob is addressed by a content hash \(BLAKE3\) derived from the object’s bytes, so two uploads with identical content share a single physical object. This content-addressed model enables straightforward deduplication across users and mailboxes.

 Blob 儲存用於存放伺服器管理的大型二進位物件：原始電子郵件、Sieve 腳本和其他檔案。每個 Blob 都由一個內容雜湊值（ BLAKE3 ）定址，該雜湊值源自物件的位元組，因此內容相同的兩個上傳檔案共用同一個實體物件。這種基於內容尋址的模型能夠輕鬆地跨使用者和郵箱進行去重。

 Backend selection is made on the BlobStore singleton \(found in the WebUI under Settings › Storage › Blob Store\). The object is a multi-variant type; each variant carries its own fields. The supported variants are:

 後端選擇在 BlobStore單例物件上進行（可在 WebUI 的「設定」&gt;「儲存」&gt;「Blob 儲存」中找到）。此物件為多變體類型；每個變體都包含其自身的欄位。支持的變體包括：

- S3-compatible storage: for Amazon S3, Google Cloud Storage, MinIO, and other S3-compatible services.
S3 相容儲存 : 適用於 Amazon S3、Google Cloud Storage、MinIO 和其他 S3 相容服務。
- Azure Blob Storage: for the Azure-native object storage service.
Azure Blob 儲存體 ：適用於 Azure 原生物件儲存服務。
- Filesystem: direct storage on the server’s local filesystem, suitable for single-node installations.
檔案系統 : 直接儲存在伺服器的本機檔案系統上，適用於單節點安裝。
- The `Default` variant, which reuses the configured data store as the blob store; useful for installations that prefer to minimise the number of external dependencies.
`Default`變體將配置的資料儲存重用於 blob 儲存；適用於希望最大限度減少外部相依性數量的安裝。
- For distributed installations, FoundationDB, PostgreSQL, and MySQL are also available as blob store variants; configuration mirrors the equivalent DataStore variants.
對於分散式安裝，FoundationDB、PostgreSQL 和 MySQL 也可用作 blob 儲存變體；配置與對應的 DataStore 變體類似。
## Configuration｜配置

 To change the blob store backend, update the BlobStore singleton and select the appropriate variant. Variant-specific fields such as bucket, region, and secretKey apply to the S3 variant; path and depth apply to the FileSystem variant; and so on. See the BlobStore reference for the full field list per variant.

 若要變更 Blob 儲存後端，請更新 BlobStore 單例並選擇對應的變體。特定於變體的字段，例如 bucket 、region和`depth` `secretKey` \([https://stalw.art/docs/ref/object/blob-store#path](https://stalw.art/docs/ref/object/blob-store#path)\) \([https://stalw.art/docs/ref/object/blob-store#secretkey](https://stalw.art/docs/ref/object/blob-store#secretkey)\) \]適用於 S3 變體；\[ `path` \([https://stalw.art/docs/ref/object/blob-store#depth\)適用於](https://stalw.art/docs/ref/object/blob-store#depth%2529%2525E9%252581%2525A9%2525E7%252594%2525A8%2525E6%252596%2525BC) FileSystem 變體；依此類推。有關每個變體的完整字段列表，請參閱 BlobStore 參考 。

## Compression｜壓縮

 Blob compression is controlled through the Email object \(found in the WebUI under Settings › Email › Defaults, Settings › Email › Encryption, Settings › Email › Limits, Settings › Email › Storage\) via the compressionAlgorithm field. The setting applies to every blob written to the store \(messages, attachments, Sieve scripts, and any other stored binary\). The default is LZ4. Setting the field to `"none"` disables compression; setting it to `"lz4"` enables [LZ4](https://en.wikipedia.org/wiki/LZ4_%2528compression_algorithm%2529) compression.

 Blob 壓縮透過 Email物件（可在 WebUI 的「設定」&gt;「電子郵件」&gt;「預設值」、「設定」&gt;「電子郵件」&gt;「加密」、「設定」&gt;「電子郵件」&gt;「限制」和「設定」&gt;「電子郵件」&gt;「儲存」中找到）的 \[ `compressionAlgorithm` 」&gt;「 \([https://stalw.art/docs/ref/object/email#compressionalgorithm\)此設定適用於寫入儲存的每個](https://stalw.art/docs/ref/object/email#compressionalgorithm%2529%2525E6%2525AD%2525A4%2525E8%2525A8%2525AD%2525E5%2525AE%25259A%2525E9%252581%2525A9%2525E7%252594%2525A8%2525E6%252596%2525BC%2525E5%2525AF%2525AB%2525E5%252585%2525A5%2525E5%252584%2525B2%2525E5%2525AD%252598%2525E7%25259A%252584%2525E6%2525AF%25258F%2525E5%252580%25258B) blob（郵件、附件、Sieve 腳本以及任何其他儲存的二進位檔案）。預設值為LZ4 。將此欄位設為`"none"`將停用壓縮；將其設為`"lz4"`將啟用 [LZ4](https://en.wikipedia.org/wiki/LZ4_%2528compression_algorithm%2529) 壓縮。

## Maintenance｜維護

 Temporary blobs uploaded through the JMAP upload endpoint are retained for a limited period \(their Time-To-Live\). Once the TTL expires without the blob being referenced, the server’s scheduled clean-up task removes them, reclaiming storage.

 透過JMAP 上傳端點上傳的臨時 blob 會保留一段有限的時間（即其生存時間）。一旦TTL過期且 blob 未被引用，伺服器的計劃清理任務就會將其刪除，從而回收儲存空間。

 The clean-up schedule is managed through the DataRetention object \(found in the WebUI under Settings › Storage › Data Retention › Archiving, Settings › Storage › Data Retention › Data Cleanup, Settings › Storage › Data Retention › Auto-Expunge, Settings › Storage › Data Retention › Telemetry\) via the blobCleanupSchedule field, which accepts a cron expression. The default runs daily at 04:00.

 清理計畫透過 DataRetention物件進行管理（該物件可在 WebUI 的「設定」&gt;「儲存」&gt;「資料保留」&gt;「歸檔」、「設定」&gt;「儲存」&gt;「資料保留」&gt;「資料清理」、「設定」&gt;「儲存」&gt;「資料保留」&gt;「儲存」&gt;「資料保留」&gt;「資料清理」、「設定」&gt;「儲存」&gt;「資料保留」&gt;「預設值」&gt;「遙測」 `blobCleanupSchedule` \]\([https://stalw.art/docs/ref/object/data-retention#blobcleanupschedule\)字段實現的，該字段接受一個](https://stalw.art/docs/ref/object/data-retention#blobcleanupschedule%2529%2525E5%2525AD%252597%2525E6%2525AE%2525B5%2525E5%2525AF%2525A6%2525E7%25258F%2525BE%2525E7%25259A%252584%2525EF%2525BC%25258C%2525E8%2525A9%2525B2%2525E5%2525AD%252597%2525E6%2525AE%2525B5%2525E6%25258E%2525A5%2525E5%25258F%252597%2525E4%2525B8%252580%2525E5%252580%25258B) cron 表達式。預設運行時間為每天 04:00。
