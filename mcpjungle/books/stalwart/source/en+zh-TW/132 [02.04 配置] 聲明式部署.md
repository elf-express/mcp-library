# Declarative deployments｜聲明式部署

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[configuration｜配置\\\]\\\(&lt;000 目錄.md#c-18&gt;\\\)

Operators who manage infrastructure with tools such as NixOS, Ansible, Terraform or Pulumi typically describe the desired state in a text file and let the tool converge the system toward it. Stalwart supports this workflow, with one notable detail: the declarative surface is split between the `config.json` file and the CLI. A plan built from `upsert` operations is idempotent: re-applying it reconciles the existing objects in place rather than recreating them, so the same plan can run on every rebuild and converge to the same state.

 使用 NixOS、Ansible、Terraform 或 Pulumi 等工具管理基礎設施的維運人員通常會在文字檔案中描述期望狀態，然後讓工具引導系統向該狀態收斂。 Stalwart 支援這個工作流程，但有一個值得注意的細節：聲明式介面被拆分到`config.json`檔案和 CLI檔案之間。由`upsert`操作構建的計劃是冪等的：重新應用該計劃會就地協調現有對象，而不是重新創建它們，因此同一個計劃可以在每次重建時運行並收斂到相同的狀態。

 The `config.json` file is a plain text file that the configuration management tool can render and place on disk. It only needs to contain the DataStore object, so it is small and rarely changes after the initial deployment. It can be templated from the platform’s variables and written to `/etc/stalwart/config.json` \(or wherever the `--config` flag points\) with whichever file-writing primitive the tool offers.

`config.json`文件是一個純文字文件，配置管理工具可以將其渲染並儲存到磁碟。它只需要包含 DataStore對象，因此文件很小，並且在初始部署後很少更改。它可以根據平台變數進行模板化，並使用工具提供的任何檔案寫入原語寫入到`/etc/stalwart/config.json` （或`--config`標誌指向的任何位置）。

 Everything else lives in the database and is managed through the JMAP API. The CLI provides two commands designed specifically for this workflow. The apply command takes a JSON plan describing a batch of upsert, update, create and destroy operations and runs them against the server in dependency-aware order. For declarative use the plan is normally just `upsert` operations \(which create or reconcile each object by a natural key\) plus singleton `update` operations. It is the command invoked from an Ansible task, a Terraform `local-exec` provisioner, a NixOS systemd one-shot service, or a Pulumi `Command` resource. The snapshot command performs the inverse operation: it walks a live deployment and emits a plan in the same format, which is useful for configuration backups, promoting state from staging to production, and capturing a manually assembled initial configuration so that subsequent changes can be driven declaratively.

 其他所有內容都位於資料庫中，並透過 JMAP API 進行管理。 CLI 提供了兩個專門為此工作流程設計的指令。 apply 指令採用 JSON 計畫來描述一批更新插入、更新、建立和銷毀操作，並以依賴關係感知的順序對伺服器運行它們。對於聲明性使用，計劃通常只是 `upsert` 操作（透過自然鍵建立或協調每個物件）加上單例 `update` 操作。它是從 Ansible 任務、Terraform `local-exec` 設定程式、NixOS systemd 一次性服務或 Pulumi `Command` 資源呼叫的命令。 snapshot 命令執行逆操作：它執行即時部署並以相同格式發出計劃，這對於配置備份、將狀態從暫存狀態提升到生產狀態以及捕獲手動組裝的初始配置以便可以以聲明方式驅動後續更改非常有用。

 Both commands are documented in the CLI reference with worked examples for Ansible, Terraform, NixOS, Pulumi and common CI systems. The general pattern, regardless of the platform, remains the same: render a plan from the platform’s templates, pass it to `stalwart-cli apply`, and surface the exit status as the step’s result.

 這兩個指令在CLI參考文件中均有詳細說明，並提供了Ansible、Terraform、NixOS、Pulumi和常見CI系統的範例。無論平台如何，通用模式都相同：從平台模板產生計劃，將其傳遞給`stalwart-cli apply` ，並將退出狀態作為步驟的結果傳回。

 The typical sequence for a fully automated deployment is to template `config.json` onto the host, start Stalwart once with `STALWART_RECOVERY_MODE=1` and a `STALWART_RECOVERY_ADMIN` supplied from a secrets manager, run `stalwart-cli apply` against the recovery listener to load the initial configuration, and then restart Stalwart without the recovery variables to bring the server up normally. From that point onward, every subsequent change is another `apply` against the running server.

 全自動部署的典型流程是：首先，將模板`config.json`部署到主機上；然後，使用`STALWART_RECOVERY_MODE=1`和從密鑰管理器提供的`STALWART_RECOVERY_ADMIN`啟動一次 Stalwart；接著，針對恢復監聽器運行`stalwart-cli apply`加載初始配置；最後，在不使用變量加載的變量。此後，每次變更都需要針對正在運行的伺服器執行另一次`apply` 。
