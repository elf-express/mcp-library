# Migrating accounts｜遷移帳戶

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[guide｜指導\\\]\\\(&lt;000 目錄.md#c-38&gt;\\\)

With the proxy live and every account still served from the source, accounts are now moved one at a time. Moving an account recreates it on the new server, copies its data across with Vandelay, and then flips its mapping so the proxy routes it to the new server. Everything except the final flip happens while the account continues to be served from the source, so the work is invisible to the account’s owner until the moment of the switch, which disconnects any live session and lets it reconnect to the new server automatically. There is no downtime; an account is either served by the source or, after its switch, by the new deployment.

 代理伺服器已上線，所有帳戶仍由原伺服器提供服務，現在帳戶將逐一遷移。遷移帳戶時，會在新伺服器上重新建立該帳戶，使用 Vandelay 複製其數據，然後切換其映射關係，使代理伺服器將其路由到新伺服器。除了最後的映射切換之外，所有操作都在帳戶繼續由原始伺服器提供服務的情況下完成，因此帳戶所有者在切換完成之前不會察覺到任何變更。切換完成後，所有正在運行的會話將斷開，並允許其自動重新連接到新伺服器。整個過程不會造成任何停機時間；帳戶要么由原始伺服器提供服務，要么在切換完成後由新部署提供服務。

 The procedure below moves a single account and is repeated for each. It is written for an account whose address is `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`. The data that has to survive the move is the account’s mail, its mailboxes and their structure, its sieve scripts, its contacts and address books, its calendars and events, and its files, all of which Vandelay carries. Where a step differs by source, a tabbed block shows each variant; selecting the source once carries the choice through the page. The destination names `old` and `new` used below are those of the Stalwart configuration; for a Dovecot and Postfix source they are `legacy` and `stalwart`.

 以下步驟用於移轉單一帳戶，並針對每個帳戶重複執行。此步驟以地址為`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`的帳戶為例。遷移過程中需要保留的資料包括帳戶的郵件、郵箱及其結構、Sieve腳本、聯絡人和地址簿、日曆和事件以及文件，所有這些資料都由Vandelay負責遷移。如果某個步驟因來源而異，則會使用選項卡式區塊顯示每種變體；選擇來源一次，該選擇將應用於整個頁面。下文中使用的目標名稱`old`和`new`是Stalwart配置中的名稱；對於Dovecot和Postfix來源，它們分別是`legacy`和`stalwart` 。

## Directing the administrator session｜指導管理員會話

**Older Stalwart**

**資深中堅份子**

 The migration tools authenticate as an administrator and connect to the proxy on the public hostname, exactly as a client would. The proxy therefore routes them by the administrator’s login, which means the proxy has to be told which deployment an administrative session should reach. This is done with a single mapping entry for the administrator account, pointed at the source while data is being read from it and at the new server while data is being written to it.

 遷移工具會以管理員身份進行身份驗證，並透過公用主機名稱連接到代理伺服器，就像客戶端一樣。因此，代理伺服器會根據管理員的登入資訊進行路由，這意味著必須告知代理伺服器管理工作階段應連接到哪個部署。這可以透過為管理員帳戶建立一個映射條目來實現：在從來源伺服器讀取資料時指向來源伺服器，在向新伺服器寫入資料時指向新伺服器。

 The proxy’s management API sets the entry. The administrator token authorises the call:

 代理的管理API設定了該條目。管理員令牌授權調用：

```bash title=&amp;quot;Terminal window&amp;quot;
TOKEN=$(cat /etc/proxy/admin.token)
admin_route() {
  curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
    "https://127.0.0.1:9443/mappings?identifier=admin&destination=$1"
}
```

`admin_route old` and `admin_route new` then point the administrative session at the chosen deployment before each tool is run. When the migration of all accounts is complete the entry is removed, which the finalizing step covers.

`admin_route old`和`admin_route new`隨後將管理會話指向所選部署，然後再執行每個工具。所有帳戶遷移完成後，該條目將被刪除，這由 最終步驟完成。

**Dovecot / Postfix**

 For a Dovecot and Postfix source the migration tools do not need to be routed through the proxy. The source is read directly with the master user configured on the source’s configuration page, and the new account is created and filled by administering the new server directly at its internal address. Neither operation passes through the proxy, so no administrator mapping entry is required.

 對於 Dovecot 和 Postfix 來源，遷移工具無需通過代理程式。系統會使用在來源設定頁面\([https://stalw.art/docs/migration/guide/configure-source/dovecot-postfix/\)中設定的主用戶直接讀取來源，並透過直接在新伺服器的內部位址上管理該伺服器來建立和填寫新帳戶。這兩個操作都不經過代理，因此無需管理員映射條目。](https://stalw.art/docs/migration/guide/configure-source/dovecot-postfix/%2529%2525E4%2525B8%2525AD%2525E8%2525A8%2525AD%2525E5%2525AE%25259A%2525E7%25259A%252584%2525E4%2525B8%2525BB%2525E7%252594%2525A8%2525E6%252588%2525B6%2525E7%25259B%2525B4%2525E6%25258E%2525A5%2525E8%2525AE%252580%2525E5%25258F%252596%2525E4%2525BE%252586%2525E6%2525BA%252590%2525EF%2525BC%25258C%2525E4%2525B8%2525A6%2525E9%252580%25258F%2525E9%252581%25258E%2525E7%25259B%2525B4%2525E6%25258E%2525A5%2525E5%25259C%2525A8%2525E6%252596%2525B0%2525E4%2525BC%2525BA%2525E6%25259C%25258D%2525E5%252599%2525A8%2525E7%25259A%252584%2525E5%252585%2525A7%2525E9%252583%2525A8%2525E4%2525BD%25258D%2525E5%25259D%252580%2525E4%2525B8%25258A%2525E7%2525AE%2525A1%2525E7%252590%252586%2525E8%2525A9%2525B2%2525E4%2525BC%2525BA%2525E6%25259C%25258D%2525E5%252599%2525A8%2525E4%2525BE%252586%2525E5%2525BB%2525BA%2525E7%2525AB%25258B%2525E5%252592%25258C%2525E5%2525A1%2525AB%2525E5%2525AF%2525AB%2525E6%252596%2525B0%2525E5%2525B8%2525B3%2525E6%252588%2525B6%2525E3%252580%252582%2525E9%252580%252599%2525E5%252585%2525A9%2525E5%252580%25258B%2525E6%252593%25258D%2525E4%2525BD%25259C%2525E9%252583%2525BD%2525E4%2525B8%25258D%2525E7%2525B6%252593%2525E9%252581%25258E%2525E4%2525BB%2525A3%2525E7%252590%252586%2525EF%2525BC%25258C%2525E5%25259B%2525A0%2525E6%2525AD%2525A4%2525E7%252584%2525A1%2525E9%25259C%252580%2525E7%2525AE%2525A1%2525E7%252590%252586%2525E5%252593%2525A1%2525E6%252598%2525A0%2525E5%2525B0%252584%2525E6%2525A2%25259D%2525E7%25259B%2525AE%2525E3%252580%252582)

 If a tool is nonetheless pointed at the public hostname rather than at a server’s own address, the proxy routes it by the `admin` login like any other account, and a mapping entry for `admin` pointed at `stalwart` steers it to the new server while writing. The token that authorises such a call is read once for the management calls used later in this page:

 如果某個工具指向的是公共主機名稱而不是伺服器本身的位址，代理伺服器會像處理其他帳戶一樣，透過`admin`登入名稱路由該工具，並透過指向`admin`的`stalwart`映射條目，在寫入資料時將其引導至新的伺服器。用於授權此類呼叫的令牌會被讀取一次，供本頁後續使用的管理呼叫使用：

```bash title=&amp;quot;Terminal window&amp;quot;
TOKEN=$(cat /etc/proxy/admin.token)
```

## Recreating the account on the new server｜在新伺服器上重新建立帳戶

**Older Stalwart**

**資深中堅份子**

 The account is recreated from its definition on the source, preserving its password so that the owner notices no change in credentials. A small script reads the account from the source’s management API and produces a plan that the command-line interface applies. The script is published in the proxy repository as [resources/migrate\_v015\_to\_plan.py](https://github.com/stalwartlabs/proxy/blob/main/resources/migrate_v015_to_plan.py).

 該帳戶根據其在來源端的定義重新創建，並保留其密碼，因此帳戶所有者不會注意到憑證的任何變更。一個小腳本從來源端的管理API讀取該帳戶，並產生一個命令列介面應用的計畫。此腳本以 [resources/migrate\_v015\_to\_plan.py](https://github.com/stalwartlabs/proxy/blob/main/resources/migrate_v015_to_plan.py)形式發佈在代理程式儲存庫中。

 The account is read from the source, so the administrative session is pointed there first. The script is given the source’s administrator credentials and the identifier of the domain as it exists on the new server, because that domain was already created during the new server’s configuration and the plan has to reference it rather than create it again. The domain identifier is read from the new server, then supplied to the script:

 帳戶資訊從來源伺服器讀取，因此管理會話首先指向來源伺服器。腳本需要來源伺服器的管理員憑證以及新伺服器上的網域標識符，因為該網域已在新伺服器配置期間創建，計劃必須引用它，而不是再次建立。網域識別碼從新伺服器讀取，然後提供給腳本：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli query Domain --where name=example.org --fields id

admin_route old
python3 migrate_v015_to_plan.py alice \
  --url https://mail.example.org \
  --user admin --password "$OLD_ADMIN_PASSWORD" \
  --existing-domain example.org=<domain-id> \
  --output alice-plan.ndjson
```

The `<domain-id>` is the value the query printed. Supplying it tells the script to reference the existing domain on the new server rather than emit an instruction to create it, which would fail because the domain already exists.

`<domain-id>`是查詢輸出的值。提供此值會指示腳本引用新伺服器上已存在的網域，而不是發出建立網域的指令，因為建立網域會失敗，因為該網域已存在。

 The script writes a plan describing the account: its name, its domain, its password and any aliases it carried. Passwords are copied as stored hashes rather than in clear, so the original password continues to work without ever being known to the migration. The plan is then applied to the new server, which is where the account is created, so the administrative session is pointed there:

 腳本會編寫一個計劃，描述帳戶資訊：帳戶名稱、網域名稱、密碼以及所有別名。密碼以雜湊值的形式存儲，而非明文形式，因此原始密碼可以繼續使用，且遷移過程不會取得原始密碼。然後，該計劃會被套用到新伺服器（帳戶建立於該伺服器上），從而將管理會話指向該伺服器。

```bash title=&amp;quot;Terminal window&amp;quot;
admin_route new
stalwart-cli apply --file alice-plan.ndjson
```

**Dovecot / Postfix**

 A Dovecot and Postfix source has no Stalwart management API to read, so the account is recreated on the new server from the source’s own user directory. Where that directory lives depends on the deployment: a `passwd-file`, an LDAP or SQL backend, or the user list a distribution such as Mail-in-a-Box or mailcow maintains. The account is created on the new server with the command-line interface. Stalwart identifies an account by the bare local part of its address together with the identifier of its domain, so the domain identifier is read from the new server first, exactly as in the proxy-based flow:

 Dovecot 和 Postfix 來源伺服器沒有 Stalwart 管理目錄API可供讀取，因此會在新伺服器上從來源伺服器本身的使用者目錄重新建立帳戶。此目錄的位置取決於部署方式：可以是`passwd-file` 、 LDAP或SQL後端，也可以是 Mail-in-a-Box 或 mailcow 等分發包維護的使用者清單。帳戶在新伺服器上透過命令列介面建立。 Stalwart 透過帳戶位址的本機部分及其網域標識符來識別帳戶，因此首先從新伺服器讀取網域標識符，這與基於代理程式的流程完全相同：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli query Domain --where name=example.org --fields id
```

The original password is preserved when the source exposes its stored hash. Stalwart recognises the common crypt formats, so a secret that begins with a recognised prefix, such as `$6$` for sha512-crypt, `$2` for bcrypt or `$argon2`, is stored verbatim and continues to verify the owner’s existing password; a secret supplied in clear is hashed on creation. The hash read from the source directory is supplied as the account’s password credential, so the account is created complete in a single call:

 當來源暴露其儲存的雜湊值時，原始密碼得以保留。 Stalwart 能夠識別常見的加密格式，因此，以可識別前綴開頭的密鑰（例如`$6$`代表`$2` -crypt， `$argon2`代表所有者的現有密碼；從來源目錄讀取的雜湊值將作為帳戶的密碼憑證，因此只需一次呼叫即可完成帳戶建立：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli create Account/User \
  --field name=alice \
  --field 'domainId=<domain-id>' \
  --field description="Alice" \
  --field 'credentials={"0":{"@type":"Password","secret":"$6$rounds=5000$..."}}'
```

The `<domain-id>` is the value the query printed. When the source does not expose usable hashes, a temporary password is set in the same field and the owner is asked to reset it after migration. Aliases the account carried on the source are recreated alongside it with the same interface.

`<domain-id>`是查詢輸出的值。當來源系統不提供可用的雜湊值時，會在相同欄位中設定臨時密碼，並要求擁有者在遷移後重設密碼。來源系統帳戶的別名也會使用相同的介面重新建立。

 After the account is created its credentials must be made effective immediately, because the new server caches the absence of an account it has never seen. Invalidating the caches forces the new account and its password to be recognised on the next authentication attempt:

 帳戶建立完成後，其憑證必須立即生效，因為新伺服器會快取從未見過的帳戶資訊。清除快取可以強制新帳戶及其密碼在下次身份驗證嘗試中被識別：

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli create Action --json '{"@type":"InvalidateCaches"}'
```

Skipping this invalidation is the most common reason a freshly created account appears to reject its correct password, because a stale negative cache entry continues to answer until it expires.

 跳過此失效步驟是新建立的帳戶似乎拒絕其正確密碼的最常見原因，因為過期的否定快取條目會繼續回應，直到過期為止。

## Copying the account data｜複製帳戶數據

 The account now exists on the new server but is empty. Vandelay fills it by reading the account from the source into a local archive and then writing that archive onto the new server. The archive is an ordinary file that holds one account; keeping it until the migration of this account has been validated provides a local copy of everything that was moved.

 該帳戶現已存在於新伺服器上，但內容為空。 Vandelay 會將帳戶從來源伺服器讀取到本機檔案中，然後將該檔案寫入新伺服器，從而填入該帳戶。此存檔是一個普通文件，僅包含一個帳戶；保留該文件直到帳戶遷移驗證完成，即可提供所有已遷移內容的本機副本。

**Older Stalwart**

**資深中堅份子**

 Reading from the source is done with the source’s administrator credentials, with the administrative session pointed at the source. The account is named as it is known on the source, which for a server that predates e-mail-address logins is the bare account name:

 從來源伺服器讀取資料時，需要使用來源伺服器的管理員憑證，且管理會話必須指向該來源伺服器。帳戶名稱與來源伺服器上的名稱一致，對於早於電子郵件地址登入的伺服器而言，該名稱就是裸帳號名稱：

```bash title=&amp;quot;Terminal window&amp;quot;
admin_route old
export VANDELAY_PASSWORD="$OLD_ADMIN_PASSWORD"

vandelay import jmap \
  --url https://mail.example.org \
  --auth-basic admin \
  --account-name alice \
  alice.sqlite
```

This reads the account’s mail, mailboxes, sieve scripts, contacts and calendars over JMAP. Files are handled separately. Older Stalwart releases implement an earlier draft of the JMAP file specification that Vandelay’s JMAP file transfer does not recognise, so the account’s files are read from the source over WebDAV instead, into the same archive. The WebDAV path addresses the account’s file area on the source:

 此操作透過JMAP讀取帳戶的郵件、郵箱、Sieve 腳本、聯絡人和日曆。文件單獨處理。較早的 Stalwart 版本實現了JMAP文件規範的早期草案，Vandelay 的JMAP文件傳輸無法識別，因此帳戶文件改為透過 WebDAV 從來源讀取到同一個歸檔文件中。 WebDAV 路徑指向來源上帳戶的檔案區域：

```bash title=&amp;quot;Terminal window&amp;quot;
vandelay import webdav \
  --url https://mail.example.org/dav/file/alice/ \
  --auth-basic admin \
  alice.sqlite
```

**Dovecot / Postfix**

 A Dovecot and Postfix source is read over IMAP for mail and over ManageSieve for sieve scripts, using the master user configured on the source. Because the source accepts direct connections, Vandelay reads it at its own address rather than through the proxy. The master user is presented as `<account>%<master-user>`, here `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%vmadmin`, with the master user’s password:

 使用來源上配置的主用戶，透過IMAP讀取 Dovecot 和 Postfix 來源中的郵件，並透過 ManageSieve 讀取 Sieve 腳本。由於來源接受直接連接，Vandelay 直接在其自身位址讀取，而不是透過代理。主用戶顯示為`<account>%<master-user>` ，此處為`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%vmadmin` ，並附有主用戶的密碼：

```bash title=&amp;quot;Terminal window&amp;quot;
export VANDELAY_PASSWORD="$MASTER_PASSWORD"

vandelay import imap \
  --url imaps://source.internal.example.org \
  --auth-basic '[email protected]%vmadmin' \
  alice.sqlite

vandelay import managesieve \
  --url sieve://source.internal.example.org \
  --auth-basic '[email protected]%vmadmin' \
  alice.sqlite
```

Calendars and contacts are read with `vandelay import caldav` and `vandelay import carddav` when the deployment runs a CalDAV or CardDAV server such as SOGo, Radicale or Baikal, against that server’s address. A Dovecot and Postfix stack serves no files, so there is no file import on the source side.

 當部署環境運行 CalDAV 或 CardDAV 伺服器（例如 SOGo、Radicale 或 Baikal）並連接到該伺服器位址時，日曆和聯絡人將透過`vandelay import caldav`和`vandelay import carddav`讀取。 Dovecot 和 Postfix 協定堆疊不提供檔案服務，因此來源端無需匯入檔案。

 The contents of the archive can be inspected before it is written anywhere, which is a useful confirmation that the expected data was read:

 在將存檔內容寫入任何位置之前，可以對其進行檢查，這有助於確認是否已讀取預期資料：

```bash title=&amp;quot;Terminal window&amp;quot;
vandelay inspect alice.sqlite
```

The archive is then written onto the new server. Writing uses the new server’s administrator credentials and names the account by its full e-mail address as it is known there:

 然後將存檔寫入新伺服器。寫入作業使用新伺服器的管理員憑證，並使用該帳戶在新伺服器上的完整電子郵件地址命名該帳戶：

**Older Stalwart**

**資深中堅份子**

```bash title=&amp;quot;Terminal window&amp;quot;
admin_route new
export VANDELAY_PASSWORD="$NEW_ADMIN_PASSWORD"

vandelay export \
  --url https://mail.example.org \
  --auth-basic admin \
  --account-name [email protected] \
  alice.sqlite
```

**Dovecot / Postfix**

```bash title=&amp;quot;Terminal window&amp;quot;
export VANDELAY_PASSWORD="$NEW_ADMIN_PASSWORD"

vandelay export \
  --url https://new.internal.example.org \
  --auth-basic admin \
  --account-name [email protected] \
  alice.sqlite
```

Vandelay matches the account’s standard mailboxes against those the new account already has, so the inbox, sent, drafts and other default folders are reused rather than duplicated, and the messages are placed inside them. Mail, sieve scripts, contacts, calendars and, for a Stalwart source, files are all written across. Because Vandelay reconciles rather than blindly inserts, re-running the export after an interruption completes it without creating duplicates.

 Vandelay 會將帳戶的標準郵箱與新帳戶已有的郵箱進行匹配，因此收件匣、已發送郵件、草稿箱和其他預設資料夾會重複使用，而不是重複創建，郵件也會放入這些資料夾中。郵件、篩選腳本、聯絡人、日曆以及（對於 Stalwart 來源）檔案都會被同步寫入。由於 Vandelay 採用的是協調而非盲目插入的方式，因此在導出中斷後重新運行導出操作可以順利完成，而不會創建重複項。

## Routing the account to the new server｜將帳戶路由到新伺服器

 At this point the account exists on both servers: the copy on the source is intact and the new copy is a faithful reproduction of it. The switch is made by flipping the account’s mapping to the new server. Both the e-mail address and, if the source allowed it, the bare account name are pointed at the new server so that either login form follows. Any live session is then disconnected so that it reconnects through the new mapping:

 此時，該帳戶同時存在於兩台伺服器上：來源伺服器上的副本完好無損，新伺服器上的副本則是其完整複製。切換操作透過將帳戶的映射關係切換到新伺服器來實現。電子郵件地址以及（如果來源伺服器允許）帳號名稱都會指向新伺服器，以便兩種登入方式都能生效。所有正在進行的會話隨後都會斷開連接，以便透過新的映射關係重新連接。

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]&destination=new"
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/mappings?identifier=alice&destination=new"
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]"
```

From this moment the account is served by the new deployment. Its mail, web client and every protocol follow the same mapping, so a client reconnecting after the disconnection lands on the new server without any reconfiguration. Inbound mail for the account, which was being relayed to the source, is now recognised by the new server as a local account and delivered locally instead, with no change required.

 從現在起，該帳戶將由新部署的伺服器提供服務。其郵件、Web 用戶端以及所有協定都遵循相同的映射關係，因此斷開連接後重新連接的用戶端無需任何重新配置​​即可連接到新伺服器。先前轉發到來源伺服器的帳戶入站郵件，現在會被新伺服器識別為本機帳號並直接投遞到本機，無需任何變更。

## Validating the migrated account｜驗證已移轉的帳戶

 Validation confirms that the account works on the new server and that its data arrived intact, and it is done before moving on, because an account is far easier to roll back immediately than after its owner has begun using it on the new server.

 驗證確認該帳戶在新伺服器上可以正常運作，且其資料已完整到達。此操作在繼續操作之前完成，因為帳戶一旦恢復，立即恢復比在帳戶所有者開始在新伺服器上使用帳戶後再恢復要容易得多。

 Authentication is confirmed by signing in through the proxy with the account’s original password, which now reaches the new server. An IMAP session lists the migrated mailboxes and their message counts:

 透過使用帳戶的原始密碼透過代理登入來確認身份驗證，該密碼現在已到達新伺服器。 IMAP 會話列出了遷移的郵箱及其郵件計數：

```bash title=&amp;quot;Terminal window&amp;quot;
openssl s_client -quiet -connect mail.example.org:993 <<'EOF'
a1 LOGIN [email protected] "password"
a2 LIST "" "*"
a3 STATUS INBOX (MESSAGES)
a4 LOGOUT
EOF
```

The other data types are confirmed over JMAP, which the new server serves regardless of what the source was. A session request returns the account’s identifier, and method calls against it report the number of e-mails, contacts, calendar events and files, which are compared against what the account held on the source:

 其他資料類型透過JMAP進行確認，無論資料來源是什麼，新伺服器都會提供該服務。會話請求會傳回帳戶標識符，針對該標識符的方法呼叫會報告電子郵件、聯絡人、日曆事件和文件的數量，這些數量會與來源帳戶中儲存的資料進行比較：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -u '[email protected]:password' https://mail.example.org/.well-known/jmap
```

Opening the account in a real mail client and in the web interface, sending a message to it and reading existing mail, is the final confirmation that the migration succeeded for this account. Only then is the next account migrated.

 在實際的郵件用戶端和網頁介面中開啟帳戶，向其發送郵件並閱讀現有郵件，才能最終確認該帳戶遷移成功。只有確認無誤後，才能移轉下一個帳戶。

## Login names after migration｜遷移後的登入名

 The latest Stalwart releases identify accounts by their full e-mail address. An account that signed in to the source with a bare name continues to work after migration because the new server appends the account’s domain to a bare login, turning `alice` into `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`, provided a default domain is configured. Pointing both the bare name and the e-mail address at the new server in the mapping, as shown above, keeps either login form working through the proxy. Account owners can be advised to switch to the full e-mail address at their convenience, but nothing forces an immediate change.

 最新版本的 Stalwart 使用完整的電子郵件地址來識別帳戶。如果一個帳戶之前使用裸名登錄，那麼在遷移後它仍然可以正常工作，因為新伺服器會將帳戶的網域附加到裸名登入資訊後，例如將`alice`變為`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`前提是已配置預設網域）。如上所示，在映射中同時將裸名和電子郵件地址指向新伺服器，可以確保兩種登入方式都能透過代理程式正常運作。可以建議帳戶擁有者在方便的時候切換到使用完整的電子郵件地址，但不會強制要求立即變更。

## Rollback｜復原

 An account can be returned to the source at any time, because the copy on the source was never removed. The migration only ever copied data, so the source still holds the account exactly as it was at the moment of the copy.

 帳戶可以隨時恢復到來源系統，因為來源系統上的副本從未被刪除。遷移過程僅複製了數據，因此來源系統仍然保留複製時帳戶的原始狀態。

 The immediate rollback reverses the mapping, pointing the account back at the source and disconnecting its current sessions:

 立即回滾操作會反轉對應關係，將帳戶指向來源帳戶並中斷其目前工作階段：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/[email protected]&destination=old"
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/mappings?identifier=alice&destination=old"
curl -sk -X POST -H "Authorization: Bearer $TOKEN" \
  "https://127.0.0.1:9443/connections/[email protected]"
```

If the rollback happens immediately after the switch, before the account has received or created anything on the new server, this is all that is required: the copy on the source is complete and current. If the account was active on the new server for a while, any mail or other data that arrived there after the switch exists only on the new server and has to be carried back.

 如果回滾發生在切換之後，即在帳戶尚未在新伺服器上接收或建立任何內容之前，則只需確保來源伺服器上的副本完整且最新即可。如果帳戶在新伺服器上已啟動一段時間，則切換後到達該伺服器的任何郵件或其他資料都僅存在於新伺服器上，必須將其還原。

**Older Stalwart**

**資深中堅份子**

 Carrying data back is done by reversing the Vandelay direction, reading the account from the new server and writing it onto the source, with the administrative session pointed appropriately:

 將資料回傳是透過反轉 Vandelay 的方向來實現的，從新伺服器讀取帳戶並將其寫入來源伺服器，同時正確指向管理會話：

```bash title=&amp;quot;Terminal window&amp;quot;
admin_route new
VANDELAY_PASSWORD="$NEW_ADMIN_PASSWORD" vandelay import jmap \
  --url https://mail.example.org --auth-basic admin \
  --account-name [email protected] alice-back.sqlite

admin_route old
VANDELAY_PASSWORD="$OLD_ADMIN_PASSWORD" vandelay export \
  --url https://mail.example.org --auth-basic admin \
  --account-name alice alice-back.sqlite
```

Mail, mailboxes, sieve scripts, contacts and calendars are carried back this way. Files are the exception: the source’s earlier JMAP file draft does not accept the files Vandelay writes, so any file created or changed on the new server after the switch cannot be written back automatically and has to be copied by hand over WebDAV from the new server to the source. For this reason, rolling an account back is simplest when done promptly, before significant new data accumulates on the new server.

 郵件、郵箱、Sieve腳本、聯絡人和日曆都可以透過這種方式恢復。文件是個例外：來源伺服器早期的JMAP文件草稿不接受Vandelay寫入的文件，因此切換後在新伺服器上建立或更改的任何文件都無法自動寫回，必須透過WebDAV手動從新伺服器複製到來源伺服器。因此，回滾帳戶的最佳方法是在新伺服器上累積大量新資料之前及時操作。

**Dovecot / Postfix**

 Vandelay’s export writes onto a Stalwart server over JMAP, not onto a Dovecot and Postfix stack, so the account cannot be carried back to the source with a reverse export. The source still holds the complete copy made at migration, so an immediate rollback by remapping loses nothing; only the mail and other items that arrived on the new server after the switch are at stake. They are recovered by reading the account from the new server into a Vandelay archive and converting that archive to a Maildir tree with the `export_archive.py` script in the Vandelay repository’s `scripts/` directory. The account has already been remapped to the source by the calls above, so the new server is read at its own address rather than through the proxy:

 Vandelay 的匯出操作會將資料寫入 Stalwart 伺服器（透過JMAP介面），而不是 Dovecot 和 Postfix 協定棧，因此無法透過反向匯出將帳戶還原到來源伺服器。來源伺服器仍然保留在遷移時創建的完整副本，因此透過重新映射立即回滾不會丟失任何內容；只有切換後到達新伺服器的郵件和其他項目會受到影響。恢復這些項目需要將帳戶從新伺服器讀取到 Vandelay 歸檔檔案中，然後使用 Vandelay 儲存庫`scripts/`目錄中的`export_archive.py`腳本將該歸檔檔案轉換為 Maildir 樹。由於帳戶已透過上述呼叫重新對應到來源伺服器，因此新伺服器的讀取操作直接在其自身位址進行，而不是透過代理伺服器：

```bash title=&amp;quot;Terminal window&amp;quot;
export VANDELAY_PASSWORD="$NEW_ADMIN_PASSWORD"
vandelay import jmap \
  --url https://new.internal.example.org \
  --auth-basic admin \
  --account-name [email protected] \
  alice-back.sqlite

python3 export_archive.py alice-back.sqlite alice-rollback
```

The script writes the archive’s mail under `alice-rollback/mail/` in Maildir layout, preserving the folder structure and the seen, answered, flagged, draft and deleted flags, and writes the account’s calendars, contacts, sieve scripts and files alongside it. The `mail/` tree is then merged into the account’s Maildir on the source, which makes the messages that arrived on the new server appear there. The archive holds the whole account as it stood on the new server, not only the messages added after the switch, so the merge is restricted to what the source does not already have, for example by matching on `Message-ID`, to avoid reintroducing duplicates of the mail that was migrated. Rolling an account back is therefore simplest when done promptly, before significant new data accumulates on the new server.

 腳本會將歸檔郵件以 Maildir 版面配置寫入`alice-rollback/mail/`目錄，保留資料夾結構以及已讀、已回覆、已標記、草稿和已刪除的標記，並將帳戶的行事曆、聯絡人、Sieve 腳本和檔案也寫入其中。然後， `mail/`樹會被合併到來源伺服器上帳戶的 Maildir 目錄中，這樣新伺服器上收到的郵件就會出現在該目錄中。歸檔保留了帳戶在新伺服器上的完整狀態，而不僅僅是切換後新增的郵件，因此合併作業僅限於來源伺服器上不存在的內容，例如透過符合`Message-ID`目錄，以避免重新引入已遷移郵件的重複項。因此，回滾帳戶的最佳方式是在新伺服器上累積大量新資料之前及時執行。

 Once the account is serving from the source again and its recent data has been carried back, the new copy can be left in place for a later retry or removed.

 一旦帳戶再次從來源端提供服務並且其最近的資料已恢復，則可以將新副本保留下來以便稍後重試，或將其刪除。
