# Starting the proxy｜啟動代理

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[guide｜指導\\\]\\\(&lt;000 目錄.md#c-38&gt;\\\)

This step brings the combined system online. The source’s staged settings are applied, the proxy is started, and the public hostname is repointed from the source to the proxy. When it is finished every account is still served from the source, exactly as before, but every connection now passes through the proxy. No account has been migrated yet. This is the moment to confirm that each protocol works end to end before any data is moved.

 此步驟使合併系統上線。來源系統的預先配置設定將被套用，代理伺服器將被啟動，公共主機名稱將從來源伺服器重新指向代理伺服器。完成後，所有帳戶仍將像之前一樣從來源伺服器提供服務，但所有連線現在都將透過代理伺服器。此時尚未移轉任何帳戶。在遷移任何資料之前，務必確認每個協定都能端到端正常運作。

 A short interruption occurs during this step, lasting only as long as it takes to apply the source’s staged settings, start the proxy and repoint the hostname. It is the only planned downtime in the migration, and its length depends on the source: a Stalwart source is restarted, while a Dovecot and Postfix source is only reloaded.

 此步驟中會出現短暫中斷，持續時間僅夠套用來源伺服器的暫存設定、啟動代理伺服器並重新指向主機名稱。這是遷移過程中唯一計劃內的停機時間，其時長取決於來源伺服器：Stalwart 來源伺服器會重啟，而 Dovecot 和 Postfix 來源伺服器只會重新載入。

## Sequence｜順序

**Older Stalwart**

**資深中堅份子**

 The order of operations matters, because the moment the source is restarted it begins to expect the PROXY protocol on its listeners and stops accepting direct client connections from the proxy’s network. The three actions are therefore performed in close succession.

 操作順序至關重要，因為一旦來源伺服器重啟，它就會開始在其監聽器上期望使用PROXY協議，並停止接受來自代理網路的直接客戶端連線。因此，這三個操作必須緊密地依序執行。

 First, the source is restarted so that the proxy-protocol listener settings take effect along with the reloadable settings staged earlier. A restart rather than a reload is required because the listeners only reinterpret their sockets on a full restart.

 首先，需要重新啟動來源伺服器，以便代理協定監聽器設定以及先前預先設定的可重載設定生效。之所以需要重啟而不是重新加載，是因為監聽器只有在完全重啟後才會重新解析其套接字。

 Second, the proxy is started. It binds the public mail and HTTP ports and begins answering, resolving every account to the source because the mapping table contains no account entries yet.

 其次，代理伺服器啟動。它綁定公共郵件和HTTP連接埠並開始回應，將每個帳戶解析到來源位址，因為映射表中還沒有任何帳戶條目。

 Third, the public hostname is repointed to the proxy. Whether this is done by changing a DNS record or by moving the public address onto the proxy host, it is the action that actually moves clients from the source to the proxy. Until it happens, clients still reach the source’s address directly, which now refuses them because it expects the PROXY protocol, so the repointing should follow the restart promptly.

 第三，將公網主機名稱重新指向代理伺服器。無論是透過更改DNS記錄或將公網位址移至代理主機，此操作都會真正將客戶端從來源伺服器轉移到代理伺服器。在此之前，客戶端仍然會直接存取來源伺服器的位址，但由於來源伺服器現在需要PROXY協議，因此會拒絕這些要求。所以，在伺服器重新啟動後，應該立即進行主機名稱重新指向。

**Dovecot / Postfix**

 Because trusting the proxy for XCLIENT and the IMAP ID is permissive, the source keeps accepting ordinary direct connections throughout, so the order of operations is not time-critical the way it is for a Stalwart source.

 因為信任XCLIENT和IMAP ID的代理是允許的，所以來源始終接受普通的直接連接，因此操作順序不像 Stalwart 來源那樣具有時間關鍵性。

 First, the source’s staged settings are applied by reloading both servers, with `doveadm reload` for Dovecot and `postfix reload` for Postfix. This causes no interruption: the source continues serving existing clients exactly as before, now additionally honouring XCLIENT and the IMAP ID from the proxy.

 首先，透過重新載入兩個伺服器來應用來源伺服器的暫存設置，其中 Dovecot 伺服器使用`doveadm reload` ，Postfix 伺服器使用`postfix reload` 。這不會造成任何中斷：來源伺服器會繼續像以前一樣為現有客戶端提供服務，同時還會額外遵循代理伺服器的XCLIENT和IMAP ID設定。

 Second, the proxy is started. It binds the public mail and HTTP ports and begins answering, resolving every account to the source because the mapping table contains no account entries yet.

 其次，代理伺服器啟動。它綁定公共郵件和HTTP連接埠並開始回應，將每個帳戶解析到來源位址，因為映射表中還沒有任何帳戶條目。

 Third, the public hostname is repointed to the proxy. Whether this is done by changing a DNS record or by moving the public address onto the proxy host, it is the action that actually moves clients from the source to the proxy. Because the source still accepts direct connections, there is no window in which it refuses clients, so the only interruption is the brief moment of the repoint itself.

 第三，將公網主機名稱重新指向代理伺服器。無論是透過更改DNS記錄或將公網位址移至代理主機，此操作都會將客戶端從來源伺服器轉移到代理伺服器。由於來源伺服器仍然接受直接連接，因此不會出現拒絕客戶端連接的情況，唯一的中斷就是重新指向公網主機名稱時的短暫瞬間。

 Once the proxy is answering on the public hostname, inbound mail on port 25 flows to the new server, which delivers locally for any migrated account and relays everything else to the source. With nothing migrated yet, every message is relayed to the source, which is the same destination it would have reached before, so mail delivery continues uninterrupted.

 一旦代理伺服器開始回應公用主機名，連接埠 25 上的入站郵件就會流向新伺服器。新伺服器會將已移轉帳號的郵件投遞到本機，並將其他所有郵件轉送至來源伺服器。由於目前還沒有任何帳戶遷移，所有郵件都會被轉發到來源伺服器（也就是郵件之前到達的相同目的地），因此郵件投遞不會中斷。

## Confirming the proxy is healthy｜確認代理伺服器運作正常

 Before testing individual protocols, the proxy’s own management endpoint confirms that it started cleanly and can reach both backends. The endpoint is reached with its bearer token on the management address configured for it:

 在測試各個協定之前，代理伺服器本身的管理端點會確認已正常啟動並可存取兩個後端。此端點透過配置的管理位址上的持有者令牌進行存取：

```bash title=&amp;quot;Terminal window&amp;quot;
TOKEN=$(cat /etc/proxy/admin.token)
curl -sk -H "Authorization: Bearer $TOKEN" https://127.0.0.1:9443/stats
```

The proxy’s log records each backend connection it makes and the routing decision behind it, which is the first place to look if a test below does not behave as expected.

 代理的日誌記錄了它建立的每個後端連接及其背後的路由決策，如果下面的測試沒有按預期運行，這是首先要查看的地方。

## Testing each protocol from the command line｜從命令列測試每個協議

 Each test below connects to the public hostname, so it exercises the whole path: the client reaches the proxy, the proxy resolves the account to the source, and the proxy forwards the session to it. An account that lives on the source is used throughout; substitute a real login and password.

 以下每個測試都連接到公用主機名，因此會遍歷整個路徑：客戶端連接到代理伺服器，代理伺服器將帳戶解析到來源伺服器，然後代理伺服器將會話轉送到來源伺服器。測試全程使用來源伺服器上的帳戶；請替換為真實的登入名稱和密碼。

 IMAP over implicit TLS is tested by opening a session and authenticating. A successful login that lists mailboxes confirms the IMAP path:

 透過開啟會話並進行身份驗證來測試IMAP相對於隱式TLS的驗證。成功登入並列出信箱即可確認IMAP路徑：

```bash title=&amp;quot;Terminal window&amp;quot;
openssl s_client -quiet -connect mail.example.org:993 <<'EOF'
a1 LOGIN [email protected] "password"
a2 LIST "" "*"
a3 LOGOUT
EOF
```

POP3 over implicit TLS is confirmed the same way on its own port:

 POP3相對於隱式TLS的確認方式相同，均在其自身端口上進行：

```bash title=&amp;quot;Terminal window&amp;quot;
openssl s_client -quiet -connect mail.example.org:995 <<'EOF'
USER [email protected]
PASS password
STAT
QUIT
EOF
```

SMTP submission with STARTTLS is confirmed by negotiating TLS and authenticating. The login and password are combined into the PLAIN credential first:

 透過協商TLS和驗證STARTTLS來確認SMTP提交。登入名稱和密碼先組合成PLAIN憑證：

```bash title=&amp;quot;Terminal window&amp;quot;
printf '\[email protected]\0password' | base64
openssl s_client -quiet -starttls smtp -connect mail.example.org:587 <<'EOF'
EHLO test
AUTH PLAIN <base64-from-above>
QUIT
EOF
```

ManageSieve is confirmed by connecting, upgrading to TLS and authenticating; a successful response to `AUTHENTICATE` lists the account’s scripts.

 透過連接、升級到TLS和驗證來確認ManageSieve；對`AUTHENTICATE`的成功回應列出了帳戶的腳本。

**Older Stalwart**

**資深中堅份子**

 JMAP is confirmed by requesting the session resource with HTTP Basic authentication. A JSON document naming the account’s primary accounts confirms that the proxy routed the request and that the backend answered:

 JMAP 透過使用 HTTP 基本驗證請求會話資源來確認。命名該帳戶的主要帳戶的 JSON 文件確認代理路由了請求並且後端回答了：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -u '[email protected]:password' https://mail.example.org/.well-known/jmap
```

The web interface is confirmed by opening the public hostname in a browser and signing in. Because the source’s login endpoints are pinned to it, the source’s administration interface loads and authenticates.

 透過在瀏覽器中開啟公用主機名稱並登入來確認 Web 介面。由於來源的登入端點已綁定到該介面，因此來源的管理介面會載入並進行身份驗證。

**Dovecot / Postfix**

 Dovecot and Postfix serve no JMAP and no web interface, so there is nothing to test on the source over HTTP at this stage. JMAP and the web interface become relevant only once accounts are on the new server, which serves them; they are confirmed as part of validating each migrated account.

 Dovecot 和 Postfix 不提供JMAP服務，也沒有 Web 介面，因此現階段無法透過HTTP對來源進行任何測試JMAP和 Web 介面只有在新伺服器上建立帳戶並提供服務後才變得相關；它們會在驗證每個已遷移帳戶時進行確認。

## Testing split delivery｜測試拆分交付

 Split delivery is what carries inbound mail during the migration, so it is tested before relying on it. The new server’s behaviour was configured earlier; this test confirms it works through the live system. A message is delivered to port 25 of the public hostname for an account that still lives on the source, and is then expected to arrive in that account’s mailbox after the new server relays it. Sending the message can be done with any SMTP client; a manual session makes each step visible:

 分流投遞用於遷移期間的入站郵件傳輸，因此在正式啟用前需要進行測試。新伺服器的行為已事先配置；此測試旨在確認其在生產系統中運作正常。郵件會投遞到來源伺服器上仍存在的帳戶的公共主機名稱的 25 端口，然後預期在新伺服器轉送後到達該帳戶的郵箱。可以使用任何SMTP客戶端發送郵件；手動會話可顯示每個步驟：

```bash title=&amp;quot;Terminal window&amp;quot;
openssl s_client -quiet -connect mail.example.org:25 <<'EOF'
EHLO test.example
MAIL FROM:<[email protected]>
RCPT TO:<[email protected]>
DATA
Subject: Split delivery test

This message should reach alice through the relay.
.
QUIT
EOF
```

The recipient is accepted by the new server, which finds that the address is not a local account but belongs to a local domain, and relays it to the source, where the account receives it. Confirming that the message appears in the account’s mailbox, through the IMAP test above or a real client, proves the inbound path. A message generated by external senders during testing is commonly classified as spam because it lacks the usual authentication, so the destination mailbox’s spam folder is checked as well as the inbox.

 新伺服器接受收件人，發現該地址並非本機帳戶，而是屬於本機網域，並將其轉發給來源帳戶，來源帳戶收到郵件。透過上述IMAP測試或使用真實客戶端確認郵件出現在帳戶信箱中，即可驗證入站路徑。測試期間由外部寄件者產生的郵件通常會被歸類為垃圾郵件，因為它缺少常規的身份驗證，因此除了收件匣之外，還會檢查目標郵箱的垃圾郵件資料夾。

 If a test account has already been created on the new server, addressing a second message to it confirms the other half of split delivery: the new server recognises the address as local and delivers it without relaying.

 如果已經在新伺服器上建立了測試帳戶，請向該帳戶發送第二則訊息即可確認拆分投遞的另一半：新伺服器會將該位址識別為本機位址，並直接投遞而無需中繼。

## Continue only after real clients work｜只有在真正的客戶完成工作後才能繼續。

 The command-line tests confirm the plumbing, but real mail clients exercise authentication mechanisms, capability negotiation and TLS settings that a manual session does not. Before any account is migrated, a real IMAP or JMAP client, a real submission client and, where applicable, the web interface should each be exercised against the public hostname with a genuine account. Migrating an account is reversible, but discovering a protocol problem after several mailboxes have moved is far more disruptive than discovering it now, while every account is still on the source and the whole change amounts to repointing a hostname.

 命令列測試驗證了底層架構，但真正的郵件用戶端會執行手動會話無法執行的驗證機制、功能協商和TLS設定。在遷移任何帳戶之前，應使用真實的IMAP或JMAP客戶端、真實的提交客戶端以及（如適用）Web介面，分別使用真實帳戶對公共主機名稱進行測試。帳戶遷移是可逆的，但如果在多個郵箱遷移後才發現協定問題，其破壞性遠大於現在發現問題（此時所有帳戶仍位於來源主機名稱上，整個變更僅相當於重新指向主機名稱）。

## Rollback｜復原

 Rolling back at this stage is straightforward because no data has moved. The source still holds every account exactly as it did before the cutover, so returning to it is a matter of taking the proxy back out of the path.

 現階段回滾非常簡單，因為沒有任何資料移動。來源伺服器上仍然保留切換前的所有帳戶，因此只需將代理從路徑中移除即可恢復到來源伺服器。

**Older Stalwart**

**資深中堅份子**

 The public hostname is repointed from the proxy back to the source’s address, which sends clients to the source directly again. The proxy is then stopped. Finally, on the source, the settings that enable the PROXY protocol on its listeners are cleared and the server is restarted, so that it once again accepts ordinary direct connections from clients:

 代理伺服器將公共主機名稱重新指向來源伺服器的位址，這樣客戶端就可以再次直接連接到來源伺服器。然後停止代理伺服器。最後，在來源伺服器上，清除其監聽器上啟用PROXY協定的設置，並重新啟動伺服器，使其再次接受來自客戶端的普通直接連線：

```bash title=&amp;quot;Terminal window&amp;quot;
curl -sk -u "$AUTH" -H 'Content-Type: application/json' "$OLD/api/settings" -d '[
  {"type":"clear","prefix":"server.listener.imaptls.proxy"},
  {"type":"clear","prefix":"server.listener.imap.proxy"},
  {"type":"clear","prefix":"server.listener.pop3s.proxy"},
  {"type":"clear","prefix":"server.listener.pop3.proxy"},
  {"type":"clear","prefix":"server.listener.submission.proxy"},
  {"type":"clear","prefix":"server.listener.submissions.proxy"},
  {"type":"clear","prefix":"server.listener.sieve.proxy"},
  {"type":"clear","prefix":"server.listener.https.proxy"},
  {"type":"clear","prefix":"server.listener.http.proxy"}
]'
```

The remaining staged settings, which disable the inbound authentication checks and route outbound mail through the new server, are harmless to leave in place if the source is to keep running standalone, but they can be cleared in the same way for a complete return to the original configuration. Once the source has restarted and the hostname points back to it, the system is exactly as it was before the migration began.

 剩餘的階段性設定（例如停用入站身份驗證檢查並將出站郵件路由到新伺服器）如源伺服器繼續獨立運行，則無需更改，也不會造成任何影響；但也可以按照相同的方式清除這些設置，以完全恢復到原始配置。來源伺服器重新啟動且主機名稱重新指向它之後，系統將恢復到遷移開始之前的狀態。

**Dovecot / Postfix**

 The public hostname is repointed from the proxy back to the source’s address, which sends clients to the source directly again, and the proxy is then stopped. Because trusting the proxy for XCLIENT never stopped the source from accepting direct connections, no restart is needed: the source is already serving clients normally the moment the hostname points back to it.

 代理伺服器會將公網主機名稱重新指向來源伺服器的位址，這樣客戶端就會再次直接連接到來源伺服器，然後代理伺服器就會停止運作。由於信任代理伺服器對XCLIENT的存取從未阻止來源伺服器接受直接連接，因此無需重啟代理伺服器：主機名稱重新指向來源伺服器後，來源伺服器就已經可以正常為客戶端提供服務了。

 The trust and master-user settings staged earlier are harmless to leave in place once the proxy is gone, since no traffic arrives from its address any longer. For a complete return to the original configuration they are removed as described on the source’s configuration page, clearing `login_trusted_networks` and the master `passdb` from Dovecot and `smtpd_authorized_xclient_hosts` from Postfix, and both servers are reloaded.

 先前設定的信任和主用戶設定不會造成任何影響，因為代理伺服器移除後，其位址不再接收任何流量。要完全恢復到原始配置，請按照來源伺服器配置頁面上的說明移除這些設置，具體操作為：從 Dovecot 中清除`login_trusted_networks`和主伺服器`passdb` ，從 Postfix 中清除`smtpd_authorized_xclient_hosts` ，然後重新載入這兩個伺服器。
