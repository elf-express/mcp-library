# Setting up DNS｜設定DNS

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[install｜安裝\\\]\\\(&lt;000 目錄.md#c-29&gt;\\\)

Correctly configured DNS records are essential for email delivery, client compatibility, and transport security. The records listed below direct incoming mail, authenticate outgoing messages, enforce TLS, advertise policy to remote senders, and allow mail clients to discover and connect to the server automatically.

 正確配置的DNS記錄對於電子郵件的送達、客戶端相容性和傳輸安全性至關重要。以下列出的記錄用於定向接收郵件、驗證發送郵件、強制執行TLS 、向遠端寄件者通告策略，並允許郵件用戶端自動發現並連接到伺服器。

## Automatic or manual publication｜自動或手動出版

 Stalwart offers two ways to publish the records a domain needs.

 Stalwart 提供了兩種發布域所需記錄的方式。

 The recommended path is **automatic DNS management**. When a domain is linked to a DnsServer object configured for a supported provider, Stalwart publishes the full record set against the provider’s API the first time the domain is created and keeps it in sync over time. Updates driven by events such as DKIM key rotation or a change to the MTA-STS policy propagate without manual intervention. The set of supported providers and the discovery protocol used is described under DNS provider integration; the fields that link a specific domain to a provider are documented on DNS record setup.

 建議路徑是**自動DNS管理**。當網域名稱連結到為受支援提供者配置的DnsServer物件時，Stalwart 會在網域名稱首次建立時，將完整的記錄集發佈到該提供者的API ，並保持其長期同步。由諸如DKIM金鑰輪換或MTA-STS策略更改等事件驅動的更新無需人工幹預即可傳播。受支援的提供者集和使用的發現協議在DNS提供者整合中進行了描述；將特定網域連結到提供者的欄位在DNS記錄設定中進行了說明。

 If the DNS provider is not supported, or when manual control over the zone is preferred, the same records can be obtained from the WebUI under the domain’s management page, or exported as a zone file through the CLI. The resulting records can then be pasted into the provider’s DNS control panel.

 如果DNS提供者不受支持，或者當需要手動控制區域時，可以從域的管理頁面下的 WebUI獲取相同的記錄，或者透過 CLI將其匯出為區域文件。然後，可以將產生的記錄貼到提供者的DNS控制面板中。

 The remainder of this page describes each record type and its role. The examples assume the domain `example.org` and the host `mail.example.org`.

 本頁剩餘部分將介紹每種記錄類型及其作用。範例假設域為`example.org` ，主機為`mail.example.org` 。

## Mail Exchange \(MX\) records｜郵件交換（ MX ）記錄

 MX records specify which host is responsible for receiving email for a domain. These records direct incoming traffic to the mail server.

 MX記錄指定哪個主機負責接收某個網域的電子郵件。這些記錄將傳入流量定向到郵件伺服器。

```
MX  example.org.  10 mail.example.org.
```

Email for `example.org` is directed to `mail.example.org` with a priority of `10`. When several MX records are published, the lowest priority value is tried first; higher values act as fallbacks.

 發送至`example.org`的電子郵件將轉寄至`mail.example.org` ，優先順序為`10` 。當發布多個MX記錄時，將首先嘗試優先順序最低的記錄；優先順序較高的記錄將作為備用記錄。

## DKIM records｜DKIM記錄

 DomainKeys Identified Mail \(DKIM\) adds a digital signature to outgoing messages, proving that a message was sent by an authorised mail server for the domain and that it was not modified in transit. DKIM uses TXT records that publish the public keys used to verify those signatures.

 DomainKeys Identified Mail \( DKIM \)為外發郵件添加數位簽名，證明郵件是由該網域的授權郵件伺服器發送的TXT DKIM發布用於驗證這些簽章的公鑰。

```
TXT  202404e._domainkey.example.org.  v=DKIM1; k=ed25519; h=sha256; p=N/BkJD6xbEiMb39v7JW6AwdPHO5gKB3fcCnod4zQ31U=
TXT  202404r._domainkey.example.org.  v=DKIM1; k=rsa; h=sha256; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEAqlddLN3BjInvBqI1KpdouG7feBsEt5t233jWQJW7FaY7sR/MfWNxuzTObLoZ3l76DFq3xPjVhmy/YYiOAnMOtq9hUFqgBVTSwUNHYPz1YUEcrI5+Ban7P7LV8kggvTAaWhAI3iSXJIFaUq78K8YYr/zrGyBlg5HCPpd+DMRAB8j1ID8bcWFaVebwAOrartXOO/f8Bn9jrRrLhjP3c8UlmkJLXkSncXPp69R9VpevrKJtpBjaFxKtx7DXGie821MHuWJ7pWMdU1Uf3z8UBKF9bnrCZ5v0SdiaFkPXR1Iiq/gR6bMwdlWvST9V6ePnqZqX+Iv4FA28byOot73/CIINFwIDAQAB
```

Each DKIM record corresponds to a cryptographic key and is referenced by a selector such as `202404e` or `202404r`. When keys are rotated, the new selector is published alongside the retiring one until the transition is complete.

 每個DKIM記錄對應一個加密金鑰，並由`202404e`或`202404r`等選擇器引用。當密鑰輪換時，新的選擇器會與即將停用的選擇器一起發布，直到過渡完成。

## SPF records｜SPF記錄

 The Sender Policy Framework \(SPF\) tells receiving servers which hosts are permitted to send mail for a domain. SPF policies are published as TXT records.

 寄件者策略框架 \(SPF\) 告訴接收伺服器哪些主機可以為某個網域傳送郵件。 SPF 政策作為 TXT 記錄發布。

```
TXT  mail.example.org.  v=spf1 a ra=postmaster -all
TXT  example.org.  v=spf1 mx ra=postmaster -all
```

These policies indicate that mail may originate from the host matched by the domain’s `A` record \(or MX record, for the apex domain\), and that messages from any other source should be rejected.

 這些策略表明，郵件可以來自域的`A`記錄（或根域的MX記錄）匹配的主機，並且應拒絕來自任何其他來源的訊息。

## DMARC record｜DMARC記錄

 Domain-based Message Authentication, Reporting, and Conformance \(DMARC\) builds on SPF and DKIM, instructing receiving servers how to handle a message that fails authentication and where to send aggregate and forensic reports.

 基於網域的訊息認證、報告和一致性 \( DMARC \)建立在SPF和DKIM的基礎上，指示接收伺服器如何處理認證失敗的訊息以及將總結報告和取證報告發送到哪裡。

```
TXT  _dmarc.example.org.  v=DMARC1; p=reject; rua=mailto:[email protected]; ruf=mailto:[email protected]
```

The example tells receiving servers to reject unauthenticated messages and to deliver aggregate \(`rua`\) and forensic \(`ruf`\) reports to the postmaster address.

 此範例指示接收伺服器拒絕未經驗證的訊息，並將聚合（ `rua` ）和取證（ `ruf` ）報告傳送至郵政管理員地址。

## MTA-STS records｜MTA-STS記錄

 Mail Transfer Agent Strict Transport Security \(MTA-STS\) requires that inbound SMTP connections from compliant senders take place over TLS with a valid certificate matching a known host.

 郵件傳輸代理嚴格傳輸安全 \( MTA-STS \)要求來自合規寄件人的入站SMTP連接透過TLS進行，並使用與已知主機相符的有效憑證。

```
CNAME  mta-sts.example.org.  mail.example.org.
TXT  _mta-sts.example.org.  v=STSv1; id=16561011793845132961
```

The CNAME record points to the host that serves the MTA-STS policy document; the TXT record carries the policy version and a stable identifier used by remote servers to detect changes.

 CNAME記錄指向提供MTA-STS策略文件的主機； TXT記錄包含策略版本和遠端伺服器用於偵測更改的穩定識別碼。

## TLS Reporting \(TLS-RPT\) record｜TLS報告 \( TLS-RPT \) 記錄

 SMTP TLS Reporting lets remote servers deliver daily reports describing failed TLS negotiations to the target domain.

 SMTP TLS報告允許遠端伺服器提供每日報告，描述與目標網域TLS協商失敗。

```
TXT  _smtp._tls.example.org.  v=TLSRPTv1; rua=mailto:[email protected]
```

The record specifies the address at which the domain is willing to receive such reports, making it easier to detect and diagnose TLS problems affecting inbound mail.

 此記錄指定了域願意接收此類報告的位址，從而更容易檢測和診斷影響入站郵件的TLS問題。

## SRV records for client services｜SRV客戶服務記錄

 SRV records advertise the hostnames and ports that mail clients should use for each protocol.

 SRV記錄會公佈郵件用戶端應該為每個協定使用的主機名稱和連接埠。

```
SRV  _imap._tcp.example.org.  0 1 143 mail.example.org.
SRV  _imaps._tcp.example.org.  0 1 993 mail.example.org.
SRV  _submissions._tcp.example.org.  0 1 465 mail.example.org.
SRV  _submission._tcp.example.org.  0 1 587 mail.example.org.
```

These records let clients that support SRV-based discovery locate the server without the user entering host and port information manually.

 這些記錄允許支援基於SRV的發現的客戶端在用戶無需手動輸入主機和連接埠資訊的情況下定位伺服器。

## Autoconfiguration records｜自動配置記錄

 Autoconfiguration allows a mail client to retrieve its settings from the domain without manual entry. The legacy Mozilla autoconfig and Microsoft Autodiscover formats expect to find their endpoints on dedicated subdomains, typically pointed at the mail host:

 自動設定允許郵件用戶端無需手動輸入即可從網域中擷取其設定。傳統的 Mozilla 自動設定和 Microsoft 自動發現格式期望在專用子網域上找到其終端點，這些子網域通常指向郵件主機：

```
CNAME  autoconfig.example.org.  mail.example.org.
CNAME  autodiscover.example.org.  mail.example.org.
```

The newer PACC protocol does not require its own subdomain; compliant clients fetch the configuration from `https://example.org/.well-known/user-agent-configuration.json` directly.

 較新的PACC協定不需要自己的子域；符合規範的客戶端直接從`https://example.org/.well-known/user-agent-configuration.json`取得配置。

## Certificate Authority Authorization \(CAA\) records｜證書核發機關授權 \( CAA \) 記錄

 CAA records tell certificate authorities which of them are allowed to issue TLS certificates for a domain. When a CA \(including those used by ACME clients\) receives a certificate request, it consults the target domain’s CAA records and refuses the request if it is not listed. Publishing CAA records narrows the set of authorities that could legitimately issue a certificate for the domain, which reduces the risk of an unauthorised or mistakenly issued certificate.

 CAA記錄告知憑證授權單位哪些機構有權為某網域核發TLS憑證。當CA機構（包括ACME客戶端使用的機構）收到憑證要求時，它會查詢目標網域的CAA記錄，如果目標網域不在清單中，則會拒絕該要求。發布CAA記錄可以縮小有權為該網域核發憑證的機構範圍，從而降低未經授權或錯誤核發憑證的風險。

```
CAA  example.org.  0 issue "letsencrypt.org"
CAA  example.org.  0 iodef "mailto:[email protected]"
```

The first record authorises Let’s Encrypt to issue certificates for `example.org`. The second specifies the address at which violations or misissuance notifications can be reported. When Stalwart obtains certificates through an ACME provider, the corresponding CAA record lists that provider’s authorisation identifier, for example `letsencrypt.org` for Let’s Encrypt. Additional `issue` entries can be added when more than one CA is used, and an `issuewild` entry can further restrict wildcard certificates.

 第一筆記錄授權 Let's Encrypt 為`example.org`頒發證書。第二筆記錄指定了違規或錯誤核發通知的檢舉地址。當 Stalwart 透過 ACME提供者取得證書時，對應的CAA記錄會列出該提供者的授權標識符，例如 Let's Encrypt 的`letsencrypt.org` 。當使用多個CA時，可以新增額外的`issue`條目，而`issuewild`條目可以進一步限制通配符憑證。

## TLSA records \(DANE\)｜TLSA記錄 \( DANE \)

 TLSA records are part of DNS-based Authentication of Named Entities \(DANE\). They cryptographically link the mail server’s TLS certificate to its DNS records, allowing remote servers to verify that the certificate presented during SMTP delivery matches the one published by the domain. Publishing TLSA records is optional but recommended for inbound transport security.

 TLSA記錄是基於DNS命名實體驗證 \( DANE \) 的一部分。它們以加密方式將郵件伺服器的TLS憑證與其DNS記錄連結起來，從而允許遠端伺服器驗證在SMTP投遞期間提供的憑證是否與網域發布的憑證相符。發布TLSA記錄是可選的，但建議發布以確保入站傳輸安全。

```
TLSA  _25._tcp.mail.example.org.  3 0 1 064dbc632f1ba7d0a2a3faeadeedfebd6f90f850dfb852c97ee9df9b6e5c5e7c
...
```

One or more TLSA records can be published depending on the certificate management strategy in use. When keys are not rotated frequently, a single record with a usage of `3` \(DANE-EE\) is usually sufficient. For frequent rotations, publishing several TLSA records in parallel provides resilience and avoids service interruptions during key transitions.

 根據所使用的憑證管理策略，可以發布一條或多筆TLSA記錄。如果金鑰輪換頻率不高，通常只需發布一筆使用`3` （ DANE-EE ）的記錄即可。對於頻繁輪換的情況，並行發布多個TLSA記錄可以提高彈性，並避免金鑰切換期間的服務中斷。

 Correct DNS configuration is central to secure and reliable mail server operation. When automatic DNS management is used, Stalwart keeps the full record set in sync with server state. When records are managed manually, propagation should be verified after every change using the standard DNS lookup tools.

 正確的配置DNS對於郵件伺服器的安全可靠運作至關重要。當使用自動管理DNS時，Stalwart 會保持完整的記錄集與伺服器狀態同步。當手動管理記錄時，每次變更後都應使用標準的查詢工具DNS驗證變更是否生效。
