# Maintenance｜維護

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[email｜電子郵件\\\]\\\(&lt;000 目錄.md#c-22&gt;\\\) › \\\[settings｜設定\\\]\\\(&lt;000 目錄.md#c-24&gt;\\\)

Stalwart includes an automated maintenance process that manages and optimises the use of server space. The process runs on a schedule to maintain the performance and reliability of the mail server, and performs several functions across user accounts.

 Stalwart 包含一個自動化維護流程，用於管理和最佳化伺服器空間的使用。此流程按計劃運行，以維護郵件伺服器的效能和可靠性，並跨使用者帳戶執行多項功能。

 It permanently removes emails that users have marked for deletion, reclaiming space occupied by unwanted emails. It expunges old messages from the “Deleted Items”（已刪除項目） and “Junk Mail”（垃圾郵件） folders on a retention policy, preventing these folders from accumulating indefinitely. It also removes old entries from the changelog used by synchronisation features such as the IMAP CONDSTORE extension and JMAP, which keeps the synchronisation mechanisms efficient and bounds their storage cost.

 它會永久刪除使用者標記為已刪除的電子郵件，從而釋放被不需要的郵件佔用的空間。它會根據保留策略清除“Deleted Items”（已刪除項目）和“Junk Mail”（垃圾郵件）資料夾中的舊郵件，防止這些資料夾無限期地堆積郵件。它還會從同步功能（例如IMAP CONDSTORE 擴充和JMAP ）使用的變更日誌中刪除舊條目，從而保持同步機制的高效運作並控制其儲存成本。

 Maintenance schedules and retention durations are configured on the DataRetention singleton \(found in the WebUI under Settings › Storage › Data Retention › Archiving, Settings › Storage › Data Retention › Data Cleanup, Settings › Storage › Data Retention › Auto-Expunge, Settings › Storage › Data Retention › Telemetry\).

 維護計畫與保留期限在 DataRetention單例中配置（在 WebUI 的「設定 › 儲存 › 資料保留 › 歸檔」、「設定 › 儲存 › 資料保留 › 資料清理」、「設定 › 儲存 › 資料保留 找到資料儲存 ›「保留資料」、「保留資料」。

## Schedule｜行程

 The data-store clean-up schedule is controlled by dataCleanupSchedule, which takes a `Cron` value. The default runs daily at 02:00.

 資料儲存清理計畫由 dataCleanupSchedule控制，其取值為`Cron` 。預設運行時間為每天 02:00。

 For example, to run the clean-up every day at midnight:

 例如，每天午夜進行清理工作：

```json
{
  "dataCleanupSchedule": {"@type": "Daily", "hour": 0, "minute": 0}
}
```

Related schedules on the same object include expungeSchedule \(auto-expunge run frequency, default daily at 00:00\) and blobCleanupSchedule \(blob-store clean-up, default daily at 04:00\).

 同一物件上的相關計畫包括 expungeSchedule （自動清除運行頻率，預設每天 00:00）和 blobCleanupSchedule （blob 儲存清理，預設每天 04:00）。

## Auto-Expunge｜自動清除

 Auto-expunge automates the management of email storage by systematically removing older messages from the “Deleted Items”（已刪除項目） and “Junk Mail”（垃圾郵件） folders within all user accounts. This keeps mailboxes organised and bounds server storage usage.

 自動清除功能透過系統地從所有使用者帳戶的“Deleted Items”（已刪除項目）和“Junk Mail”（垃圾郵件）資料夾中刪除舊郵件，實現電子郵件儲存的自動化管理。這有助於保持郵箱的整潔有序，並控制伺服器儲存空間的使用。

 The retention period is controlled by expungeTrashAfter, which expects a duration in milliseconds. The default is `2592000000` \(30 days\): messages older than thirty days are expunged from those folders on the next run of expungeSchedule. Setting expungeTrashAfter to `null` disables auto-expunge.

 保留期限由 expungeTrashAfter控制，該參數接受以毫秒為單位的持續時間。預設值為`2592000000` （30 天）：超過 30 天的郵件將在下次執行 expungeSchedule時從對應資料夾中刪除。將 expungeTrashAfter設定為`null`可停用自動刪除功能。

 For example, to retain deleted and junk messages for thirty days before expunging:

 例如，將已刪除郵件和垃圾郵件保留三十天後再徹底清除：

```json
{
  "expungeTrashAfter": 2592000000
}
```

## Changes History｜變更歷史

 Stalwart maintains a changelog, known as the changes history, which is used for synchronisation between the server and client email applications. The changelog is consumed by modern email clients over JMAP and by IMAP clients that support the `CONDSTORE`/`QRESYNC` extensions.

 Stalwart 維護一個變更日誌，稱為變更歷史記錄，用於伺服器和用戶端電子郵件應用程式之間的同步。現代電子郵件用戶端透過JMAP協定讀取此變更日誌，支援`CONDSTORE`/`QRESYNC`擴充的IMAP客戶端也讀取此變更日誌。

 The changes history records modifications to mailboxes and messages, allowing clients to synchronise changes efficiently without fetching a full snapshot of the mailbox state each time. Keeping the changelog bounded conserves disk space and maintains server performance.

 變更歷史記錄會記錄郵箱和郵件的修改情況，使用戶端能夠有效率地同步變更，而無需每次都取得郵箱狀態的完整快照。控制變更日誌的大小可以節省磁碟空間並保持伺服器效能。

 The number of changes retained per account is controlled by maxChangesHistory, which defaults to `10000`. Setting the value to `null` disables the cap.

 每個帳戶保留的更改次數由 maxChangesHistory控制，預設值為`10000` 。將該值設為`null`可停用此限制。

 For example:

 例如：

```json
{
  "maxChangesHistory": 10000
}
```
