# RCPT stage｜RCPT階段

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[mta｜捷運\\\]\\\(&lt;000 目錄.md#c-47&gt;\\\) › \\\[inbound｜入站\\\]\\\(&lt;000 目錄.md#c-51&gt;\\\)

The `RCPT TO` command specifies the recipient of an email message during the SMTP message transfer. It is used in conjunction with the `MAIL FROM` command. After the command is issued, the SMTP server responds with a status code indicating whether the recipient is valid and the server is willing to accept the message. If the recipient is valid, the SMTP client proceeds with the `DATA` command.

`RCPT TO`指令用於在SMTP郵件傳輸過程中指定郵件收件者。它與`MAIL FROM`命令配合使用。發出該指令後， SMTP伺服器會傳回一個狀態碼，指示收件者是否有效以及伺服器是否願意接收郵件。如果收件人有效， SMTP客戶端將繼續執行`DATA`指令。

 RCPT-stage behaviour is configured on the MtaStageRcpt singleton \(found in the WebUI under Settings › MTA › Session › RCPT TO Stage\).

 RCPT -階段行為在 MtaStageRcpt單例上配置（在 WebUI 的設定 › MTA › 會話 › RCPT TO階段下找到）。

## Directory｜目錄

 Handling of local accounts relies on a configured directory, which performs the following roles:

 本機帳戶的處理依賴已配置的 目錄 ，該目錄執行以下角色：

- **Identifying local domains**: messages destined for these domains are accepted for local processing and storage.
**識別本機網域**：發送至這些網域的訊息將被接受進行本機處理和儲存。
- **Validating recipients**: the directory confirms whether a recipient address corresponds to a valid local account before the server accepts the message.
**驗證收件者**：在伺服器接受郵件之前，目錄會確認收件者位址是否與有效的本機帳戶相符。
- **Verifying addresses**: the SMTP `VRFY` command queries the directory to confirm that an address is valid.
**驗證位址**： SMTP `VRFY`指令查詢目錄以確認位址是否有效。
- **Expanding addresses**: the SMTP `EXPN` command retrieves the actual delivery addresses when a single address is aliased to a group.
**擴充位址**：當單一位址別名化為群組時， SMTP `EXPN`指令會擷取實際的投遞位址。
Without a directory, Stalwart cannot accept mail for local delivery, except in the case where [relay functionality](#relay) is enabled so that messages can be forwarded to another server.
 如果沒有目錄，Stalwart 無法接受本地投遞的郵件，除非啟用了 [中繼功能](#relay) ，以便將郵件轉送到另一台伺服器。

 The directory that validates a given recipient is detected automatically from the recipient domain: Stalwart matches the RCPT address against the configured Domain objects and routes the lookup to the directoryId associated with that domain, falling back to the internal directory when no explicit directory is set. MtaStageRcpt exposes no per-stage directory override.

 用於驗證給定收件人的目錄由收件人域自動檢測：Stalwart 將RCPT地址與配置的 Domain對象進行匹配，並將查找路由到與該域關聯的 directoryId ，如果未顯示到內部目錄，則回顯目錄。 MtaStageRcpt 不提供按階段覆蓋目錄的功能。

### Split-delivery relaying｜分流式中繼

 In split-delivery setups, Stalwart sits in front of another server that hosts a subset of a domain’s mailboxes. Messages for recipients that are not present in the local directory can be forwarded upstream by setting allowRelaying to `true` on the matching Domain object. With that flag set, recipients that do not resolve to a local account are accepted and relayed rather than rejected with an unknown-recipient error.

 在分流投遞架構中，Stalwart 位於另一台伺服器的前端，該伺服器託管著網域郵箱的子集。對於本機目錄中不存在的收件人，可以透過在符合的 Domain物件上將 allowRelaying設定為`true`來將郵件轉送至上游。設定此標誌後，無法解析到本機帳戶的收件者將被接受並轉發，而不是被拒絕並傳回未知收件者錯誤。

## Relay｜中繼

 Relaying is the process of transferring an email from one mail server to another. When relaying is enabled, Stalwart acts as an intermediary, accepting messages from sending clients or servers and forwarding them to their ultimate destination. This is useful when Stalwart is deployed as a front-end server in a larger email infrastructure, but it must be restricted to authorised senders or networks to prevent open-relay abuse.

 郵件中繼是指將電子郵件從一個郵件伺服器轉送到另一個郵件伺服器的過程。啟用郵件中繼後，Stalwart 將充當中間人，接收來自發送用戶端或伺服器的郵件，並將其轉發到最終目的地。當 Stalwart 作為前端伺服器部署在大型郵件基礎設施中時，此功能非常有用，但必須將其限制為僅限授權的寄件者或網絡，以防止濫用開放式中繼功能。

 The allowRelaying field on MtaStageRcpt accepts an expression that determines whether the SMTP server accepts messages for non-local domains. The default policy only allows relaying when the session is authenticated:

 MtaStageRcpt 上的 allowRelaying字段接受一個表達式，該表達式確定SMTP伺服器是否接受來自非本地域的訊息。預設策略僅允許在會話通過身份驗證後進行轉送：

```json
{
  "allowRelaying": {
    "match": {"0": {"if": "!is_empty(authenticated_as)", "then": "true"}},
    "else": "false"
  }
}
```

This controls relaying for entirely non-local domains. Relaying to unknown recipients within a domain that is otherwise local is governed by the domain-level allowRelaying flag described above.

 這控製完全非本地域的轉送。對於本地域內未知接收者的轉發，則由上述域級 allowRelaying標誌控制。

## Subaddressing｜子尋址

 Subaddressing, also known as plus addressing or detailed addressing, allows the creation of dynamic, disposable email addresses under a primary email address. By adding a `+` sign and any string of text to the local part of an address \(for example `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`\), messages sent to any of these variants are all delivered to the same mailbox. This makes it easier to filter and sort incoming mail, for example to separate subscriptions from personal correspondence.

 子地址（也稱為附加地址或詳細地址）允許在主電子郵件地址下建立動態的、一次性的電子郵件地址。透過在地址的本地部分添加`+`符號和任意文字字串（例如`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` ），發送到這些變體的任何郵件都會被投遞到同一個郵箱。這使得篩選和分類收到的郵件變得更加容易，例如將訂閱郵件與私人信件分開。

 Subaddressing is configured per domain on the Domain object \(found in the WebUI under Management › Domains › Domains\) through the subAddressing field. The field is a multi-variant value with three variants:

 子位址的配置在 Domain物件（位於 WebUI 的「管理 › 域 › 域」下）中透過 subAddressing欄位進行。此欄位是一個多變量值，包含三個變數：

- `Enabled`: standard `+` subaddressing is applied. This is the default.
`Enabled` ：採用標準`+`子定址。這是預設值。
- `Disabled`: the `+` separator is not treated as a subaddress marker; the full local part is used for delivery.
`Disabled` ： `+`分隔符號不被視為子位址標記；完整的本地部分用於投遞。
- `Custom`: a custom rule is applied through the `customRule` expression, which receives the recipient local part as `rcpt` and returns the rewritten local part. The domain is preserved by the server and is not part of the value passed in or out. For example, to strip an alias prefix so that `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` delivers to `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`:
`Custom` ：透過`customRule`表達式應用自訂規則，此表達式接收收件者本地部分為`rcpt` ，並傳回重寫的本地部分。網域由伺服器保留，不包含在傳入或傳出的值中。例如，要去除別名前綴，使`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`投遞到`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` ：

```json
{
  "subAddressing": {
    "@type": "Custom",
    "customRule": {
      "match": {"0": {"if": "matches('^([^.]+)\\.([^.]+)$', rcpt)", "then": "$2"}},
      "else": "rcpt"
    }
  }
}
```

The backslash in the regex is doubled above because the rule is shown as part of a JSON document, where JSON string escaping consumes one of the two. The expression field in the WebUI takes the text exactly as typed and applies no such unescaping, so the same rule is entered there with a single backslash:

 上面的正規表示式中出現了兩個反斜杠，因為該規則顯示在JSON文檔中，而JSON字串轉義會消耗掉其中一個。 WebUI 中的表達式欄位會直接接受輸入的文本，不會進行任何轉義，因此在那裡輸入的相同規則只使用一個反斜線：

```
matches('^([^.]+)\.([^.]+)$', rcpt)
```

See escaping backslashes for details.

 有關詳細信息，請參閱 轉義反斜線 。

## Catch-all addresses｜兜底地址

 A catch-all address receives all messages sent to non-existent addresses within a domain, preventing loss of mail due to misspellings. The catch-all recipient is configured per domain on the Domain object through the catchAllAddress field, which holds the destination email address that receives mail for unknown local recipients.

 一個「全收件匣」位址會接收所有寄到網域內不存在位址\([https://stalw.art/docs/ref/object/domain#catchalladdress\)郵件，從而防止因拼字錯誤而導致郵件遺失。每個網域的「全收件匣」收件者透過](https://stalw.art/docs/ref/object/domain#catchalladdress%2529%2525E9%252583%2525B5%2525E4%2525BB%2525B6%2525EF%2525BC%25258C%2525E5%2525BE%25259E%2525E8%252580%25258C%2525E9%252598%2525B2%2525E6%2525AD%2525A2%2525E5%25259B%2525A0%2525E6%25258B%2525BC%2525E5%2525AD%252597%2525E9%25258C%2525AF%2525E8%2525AA%2525A4%2525E8%252580%25258C%2525E5%2525B0%25258E%2525E8%252587%2525B4%2525E9%252583%2525B5%2525E4%2525BB%2525B6%2525E9%252581%2525BA%2525E5%2525A4%2525B1%2525E3%252580%252582%2525E6%2525AF%25258F%2525E5%252580%25258B%2525E7%2525B6%2525B2%2525E5%25259F%25259F%2525E7%25259A%252584%2525E3%252580%25258C%2525E5%252585%2525A8%2525E6%252594%2525B6%2525E4%2525BB%2525B6%2525E5%25258C%2525A3%2525E3%252580%25258D%2525E6%252594%2525B6%2525E4%2525BB%2525B6%2525E8%252580%252585%2525E9%252580%25258F%2525E9%252581%25258E) catchAllAddress欄位進行配置，該欄位保存著接收發送至未知本機收件者郵件的目標電子郵件地址。

 For example, to route all unmatched recipients on `example.org` to `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`:

 例如，將`example.org`上所有未匹配的收件者路由到`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` ：

```json
{
  "name": "example.org",
  "catchAllAddress": "[email protected]"
}
```

When `catchAllAddress` is left unset, messages to unknown local recipients are rejected.

 當`catchAllAddress`未設定時，發送給未知本地收件人的訊息將被拒絕。

## Address rewriting｜地址重寫

 The rewrite field accepts an expression that can modify the recipient address. Typical uses include correcting common misspellings, obfuscating the original recipient’s address for privacy, or redirecting mail traffic from one address to another. For background on the expression-based rewrite model see the address rewriting documentation.

 rewrite欄位接受一個表達式，該表達式可以修改收件者位址。典型用途包括更正常見的拼字錯誤、為了保護隱私而模糊原始收件者地址，或將郵件從一個地址重新導向到另一個地址。有關基於表達式的重寫模型的背景信息，請參閱 地址重寫文檔。

 For example, the following configuration rewrites `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` to `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` for local domains only:

 例如，以下配置僅針對本地域將`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`重寫為`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` ：

```json
{
  "rewrite": {
    "match": {"0": {"if": "is_local_domain(rcpt_domain) & matches('^([^.]+)\\.([^.]+)@(.+)$', rcpt)", "then": "$1 + '+' + $2 + '@' + $3"}},
    "else": "false"
  }
}
```

As above, the doubled backslash belongs to the JSON encoding; in the WebUI expression field the regex is written `^([^.]+)\.([^.]+)@(.+)$`. See escaping backslashes.

 如上所述，雙反斜杠屬於JSON編碼；在 WebUI 表達式欄位中，正規表示式寫為`^([^.]+)\.([^.]+)@(.+)$` 。參見 轉義反斜線 。

## Sieve script｜篩選腳本

 Running Sieve at the RCPT stage opens up uses that the delivery-time Sieve runtime cannot satisfy. Recipients can be rejected based on criteria such as the recipient domain; address rewriting can correct common misspellings or redirect mail; and policies such as greylisting \(temporarily rejecting mail from unknown sources and asking the sender to retry\) can be implemented against the envelope before the message body is accepted.

 在RCPT階段運行Sieve可以實現一些在投遞時Sieve運行時無法滿足的功能。例如，可以根據收件人網域等標準拒絕收件人；地址重寫可以糾正常見的拼寫錯誤或重定向郵件；此外，還可以在接受郵件正文之前，對信封實施諸如灰名單（暫時拒絕來自未知來源的郵件並要求發件人重試）之類的策略。

 The script field selects the Sieve script to run at this stage. A common use is greylisting, implemented by storing a `remote_ip.sender.recipient` triplet in a store and rejecting the first attempt with a `422` temporary failure; the client then retries, and legitimate senders succeed while most spam sources do not.

 script欄位用於選擇在此階段運行的 Sieve 腳本 。常見的用法是灰名單機制，其實現方式是將`remote_ip.sender.recipient`三元組存儲在存儲中，並在第一次嘗試時返回`422`臨時錯誤；客戶端隨後重試，合法發件人可以成功，而大多數垃圾郵件來源則無法成功。

 For example, the following expression runs a `greylist` Sieve script only for unauthenticated sessions:

 例如，下列表達式僅對未經驗證的會話執行`greylist` Sieve 腳本：

```json
{
  "script": {
    "match": {"0": {"if": "is_empty(authenticated_as)", "then": "'greylist'"}},
    "else": "false"
  }
}
```

A companion `greylist` Sieve script stores the triplet in a store and rejects the first attempt. The first argument of query names the SQL store holding the `greylist` table, `sql` in the example below; passing the empty string selects the default data store. The `?` placeholders use SQLite or MySQL syntax; on PostgreSQL use `$1`, `$2`, … instead, since the query is passed to the database driver verbatim:

 配套的 `greylist` Sieve 腳本將三元組儲存在儲存中並拒絕第一次嘗試。 query的第一個參數命名保存`greylist`表的SQL存儲，在下面的範例中為`sql`；傳遞空字串選擇預設資料儲存。 `?`佔位符使用 SQLite 或 MySQL 語法；在 PostgreSQL 上使用 `$1`, `$2`, … 來代替，因為查詢被逐字傳遞到資料庫驅動程式：

```sieve
require ["variables", "vnd.stalwart.expressions", "envelope", "reject"];

set "triplet" "${env.remote_ip}.${envelope.from}.${envelope.to}";

if eval "!query('sql', 'SELECT 1 FROM greylist WHERE addr = ? LIMIT 1', [triplet])" {
    eval "query('sql', 'INSERT INTO greylist (addr) VALUES (?)', [triplet])";
    reject "422 4.2.2 Greylisted, please try again in a few moments.";
}
```

## Limits｜限制

 Recipient-handling limits are configured via maxRecipients \(maximum number of recipients allowed per message, default 100\), maxFailures \(maximum number of invalid-recipient errors allowed before the session is disconnected, default 5\), and waitOnFail \(amount of time to wait after an invalid recipient is received, default 5 seconds\):

 收件人處理限制通過maxRecipients （每個訊息允許的最大收件人數量，預設值為 100），maxFailures （會話斷開前允許的最大無效收件者錯誤次數，預設為 5），以及 waitOnFail （收到無效收件人後等待的時間，預設為 5 秒）：

```json
{
  "maxRecipients": {"else": "25"},
  "maxFailures": {"else": "5"},
  "waitOnFail": {"else": "5s"}
}
```
