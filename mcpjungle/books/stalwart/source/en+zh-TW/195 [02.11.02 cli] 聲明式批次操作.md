# Declarative bulk operations｜聲明式批次操作

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[management｜管理\\\]\\\(&lt;000 目錄.md#c-31&gt;\\\) › \\\[cli\\\]\\\(&lt;000 目錄.md#c-33&gt;\\\)

The `apply` command takes an NDJSON file describing a batch of `upsert`, `reconcile`, `update`, `create`, and `destroy` operations, and applies them to the server in dependency-aware order. It is intended as the integration surface for infrastructure-as-code tooling \(Ansible, Terraform, NixOS, Pulumi, …\) and for one-shot deployments / migrations performed by hand or by CI.

`apply`指令接受一個NDJSON文件，該文件描述了一批`upsert`, `reconcile`, `update`, `create`和`destroy`操作，並按照依賴關係感知的順序將它們應用到伺服器。它旨在作為基礎設施即代碼工具（Ansible、Terraform、NixOS、Pulumi 等）的整合接口，以及用於手動或透過CI執行的一次性部署/遷移。

 The primary operation is `upsert`: it matches each object in the plan against the live server \(by a natural key such as a domain’s `name`\) and either updates the existing object in place or creates it if absent. A plan built from `upsert` operations is **idempotent**: applying it once or many times converges to the same server state, with no deletions and no duplicate objects. This is the operation snapshot emits, and the shape every infrastructure-as-code integration below uses.

 主要操作是`upsert` ：它將計劃中的每個對象與實時伺服器進行匹配（透過自然鍵，例如域的`name` ），並就地更新現有對象，如果對像不存在則創建它。由`upsert`操作建構的計畫是**冪等的**：應用一次或多次都會收斂到相同的伺服器狀態，不會刪除任何對象，也不會出現重複對象。這是snapshot發出的操作，也是下列所有基礎設施即程式碼整合所使用的結構。

`reconcile` extends `upsert` with deletion: it does everything `upsert` does and additionally destroys every existing object of the type that the plan did **not** match, converging the type to exactly the set described in the plan. Where `upsert` only ever adds or updates, `reconcile` also removes, so it closes the one gap `upsert` leaves open \(a renamed or dropped object is not left behind\). See [Reconciling to exact state](#reconciling-to-exact-state).

`reconcile` 透過刪除擴展了`upsert`：它執行`upsert` 所做的所有操作，並另外銷毀計劃**不**匹配的類型的每個現有對象，將類型準確地收斂到計劃中描述的集合。 `upsert` 只添加或更新，`reconcile` 也會刪除，因此它彌補了 `upsert` 留下的空白（不會留下重新命名或刪除的物件）。請參閱[協調到準確狀態](#reconciling-to-exact-state)。

 For interactive use cases see the per-command pages: Creating objects, Updating objects, Removing objects.

 有關互動式用例，請參閱每個指令的頁面：建立物件 、更新物件 、刪除物件 。

## Synopsis｜概要

```
stalwart-cli apply ( --file | --stdin )
                   [--dry-run]
                   [--continue-on-error]
                   [--quiet]
                   [--json]
                   [--progress]
```

| Option 選項 | Effect 效果 |
| --- | --- |
| `--file <path>` | Read the plan from an NDJSON file. 請從NDJSON檔案讀取計畫。 |
| `--stdin` | Read the plan from standard input \(NDJSON\). 從標準輸入（ NDJSON ）讀取計畫。 |
| `--dry-run` | Parse and validate the plan, then print it; no requests are sent. 解析並驗證計劃，然後列印；不發送任何請求。 |
| `--continue-on-error` | Do not abort on the first failed operation; report all errors at the end and exit non-zero. 不要因第一次操作失敗而中止；將所有錯誤報告到最後，並以非零值退出。 |
| `--quiet` | Suppress per-operation log lines; print only the final summary. 禁止顯示每次操作的日誌行；僅列印最終摘要。 |
| `--json` | Emit one NDJSON record per completed operation to stdout, plus a summary record at the end. The plan header and any progress lines remain on stderr. 每個已完成的操作向標準輸出 \(stdout\) 發送一條NDJSON記錄，並在最後發送一筆匯總記錄。計劃頭和任何進度行保留在標準錯誤輸出 \(stderr\) 中。 |
| `--progress` | Print one extra line per request batch during large `destroy`, `create`, `upsert`, and `reconcile` operations. 在大型`destroy`, `create`, `upsert`和`reconcile`操作期間，每個請求批次額外列印一行。 |

Exactly one of `--file` and `--stdin` must be supplied.

`--file`和`--stdin`中必須提供其中一個。

## How it works｜工作原理

 The plan is **NDJSON: one operation per line, no enclosing array. Blank lines are ignored; surrounding whitespace on a line is tolerated. Each operation is one of five types: `upsert`, `reconcile`, `update`, `create`, or `destroy`. The CLI processes the plan in**three passes:

 計劃是**NDJSON：每行一次操作，沒有封閉數組。空白行被忽略；一行中周圍的空白是可以接受的。每個操作都是五種類型之一：`upsert`, `reconcile`, `update`, `create`或`destroy`。 CLI 在**三次中處理計劃：

1. **Destroy pass \(reverse order\).**Every `destroy` operation is executed in**reverse** of its position in the plan. All other operations are skipped during this pass. This is what makes dependency-aware teardowns possible: when a plan lists `Domain`, then `Account`, then `DkimSignature` \(parents first\), the reverse pass tears them down in `DkimSignature`, `Account`, `Domain` order, satisfying foreign-key constraints. Most plans contain no destroys at all; the pass is a no-op for them. See [Teardown with destroy](#teardown-with-destroy).
**銷毀過程（反向執行）。**每個`destroy`操作都會按照其在計劃中的位置的**相反**順序執行。在此過程中，所有其他操作都會被跳過。這使得依賴感知清理成為可能：當一個計劃列出`Domain` 、 `Account`和`DkimSignature` （先列出父級）時，反向執行過程會按照`DkimSignature`, `Account`, `Domain`順序銷毀它們，從而滿足外鍵約束。大多數計劃根本不包含任何銷毀操作；對於這些計劃，此過程為空操作。請參閱 [使用銷毀操作的清理](#teardown-with-destroy) 。
2\. **Apply pass \(plan order\).** All `upsert`, `reconcile`, `update`, and `create` operations run in the order they appear in the plan. Destroys are skipped during this pass, and the delete half of each `reconcile` is deferred to pass 3. This ordering is what allows objects to reference each other: a `Domain` can be upserted in operation 1 and then referenced by an `Account` in operation 2.
**應用傳遞（計劃順序）。** 所有`upsert`, `reconcile`, `update`和`create`操作均依其在計畫中出現的順序執行。此傳遞期間會跳過銷毀操作，每個`reconcile`的刪除部分會延遲到傳遞 3 執行。這種順序允許物件相互引用： `Domain`可以在操作 1 中被插入更新，然後在操作 2 中被`Account`引用。
3\. **Reconcile cleanup pass \(reverse order\).**The objects each `reconcile` marked for deletion \(existing objects the plan did not match\) are destroyed now, with the reconciles processed in**reverse** of their plan position. Deferring the deletes until after the whole apply pass, and running them children-first, means a dependent is repointed or removed before the object it referenced is deleted, so a leaked parent is not blocked by a leaked child. A plan with no `reconcile` operations skips this pass.
**協調清理階段（反向執行）。**每個`reconcile`標記為刪除的物件（計劃不匹配的現有物件）現在將被銷毀，協調操作將按照其計劃位置的**相反**順序進行處理。將刪除操作延遲到整個應用階段之後，並優先處理子對象，意味著在刪除其引用的對象之前，依賴對象會被重新指向或移除，因此洩漏的父對像不會被洩漏的子對象阻塞。沒有`reconcile`操作的計畫將跳過此階段。


 The three passes let a single plan file describe a teardown followed by a rebuild, and let a `reconcile` add, update, and delete in one declarative sweep. For the common non-destructive case \(declaring desired state with `upsert` and re-applying it\) the plan is a flat list of `upsert` and singleton `update` operations and only the second pass does any work.

 這三個步驟允許單一計劃檔案描述拆卸和重建過程，並允許`reconcile`在一次聲明式操作中完成新增、更新和刪除。對於常見的非破壞性情況（使用`upsert`聲明所需狀態並重新應用），計劃是一個包含`upsert`和單例`update`操作的扁平列表，只有第二個步驟會執行實際操作。

### Stop on first error \(default\)｜遇到第一個錯誤就停止（預設）

 If any operation fails \(HTTP error, JMAP method-level error, or any per-object SetError such as `validationFailed` or `objectIsLinked`\), the CLI prints the error and exits non-zero. The remaining operations are not attempted.

 若任何操作失敗（ HTTP錯誤、 JMAP方法級錯誤，或任何物件級 SetError，例如`validationFailed`或`objectIsLinked` ）， CLI將列印錯誤資訊並以非零值退出。剩餘的操作將不再嘗試執行。

 This default is chosen deliberately for IaC contexts: a partially-applied plan is usually worse than no apply at all, and a failed step almost always indicates a bug in the plan or a server-side conflict that needs investigation before proceeding.

 特意為 IaC 上下文選擇了此預設值：部分應用程式的計劃通常比完全不應用更糟糕，而失敗的步驟幾乎總是表明計劃中存在錯誤或伺服器端衝突，需要在繼續之前進行調查。

 To override, pass `--continue-on-error`, in which case every operation is attempted and the final summary reports the count of successes and failures. The exit code is still non-zero when at least one failed.

 若要覆寫預設行為，請傳遞`--continue-on-error` ，在這種情況下，系統會嘗試執行所有操作，最終結果會報告成功和失敗的次數。即使至少有一次操作失敗，退出代碼仍然不為零。

### Idempotent re-runs｜冪等重播

 Use `upsert` operations to make a plan re-runnable. An `upsert` matches each object in its `value` map against the live server using a **match key** \(see [Matching](#matching)\); if a match is found the object is updated in place, otherwise it is created. Because nothing is destroyed and an existing object is never duplicated, applying the same `upsert` plan once or a hundred times converges to the same server state. This is the shape stalwart-cli snapshot emits, and the shape used in the [annotated example](#annotated-example) below.

 使用`upsert`操作使計劃可重新運行。 `upsert`使用**匹配鍵**將其`value`映射中的每個對象與實時伺服器進行匹配（請參閱[匹配](#matching)）；如果找到匹配，則就地更新對象，否則創建對象。因為沒有任何東西被破壞，並且現有物件永遠不會重複，所以應用相同的`upsert`計劃一次或一百次會收斂到相同的伺服器狀態。這是stalwart-cli snapshot發出的形狀，以及下面的[註釋範例](#annotated-example)中使用的形狀。

 This sidesteps the problems that a `create`-only or `destroy` \+ `create` plan has:

 這樣就避免了僅提供`create`或`destroy` \+ `create`套餐的方案所存在的問題：

- A `create`-only plan succeeds on the first run and fails on the second: re-creating the same `Domain`, `AllowedIp`, `Certificate`, etc. trips the server’s primary-key constraints, and re-creating types that have no such constraint produces duplicate rows.
僅使用`create`的計畫在第一次運行時成功，但在第二次運行時失敗：重新建立相同的`Domain`, `AllowedIp`, `Certificate`等會觸發伺服器的主鍵約束，而重新建立沒有此類約束的類型會產生重複行。
- A `destroy` \+ `create` plan can be re-run, but it tears down and rebuilds the world on every apply. That cannot work for an object another object depends on: a `Domain` referenced by an `Account`, a `DkimSignature`, or the non-nullable `SystemSettings.defaultDomainId` cannot be destroyed while the reference exists \(the destroy fails with `objectIsLinked`\). `upsert` reconciles such an object in place instead, leaving its id and its dependents untouched.
`destroy` \+ `create`計劃可以重新運行，但它會在每次應用時拆除並重建世界。這不適用於另一個物件所依賴的物件：由`Account`、`DkimSignature`所引用的`Domain`或不可為空的`SystemSettings.defaultDomainId`在引用存在時無法銷毀（銷毀失敗並顯示`objectIsLinked`）。 `upsert` 會在適當的位置協調這樣的對象，使其 id 及其相依性保持不變。
`apply` does **not** diff the desired value against the current one. An `upsert` whose match key finds an existing object always issues the `update`, even when no field changed; the run reports it as updated and the resulting state is identical. Idempotency here means the end state converges, not that an unchanged re-run is a no-op.
`apply` **不會** 將期望值與目前值進行比較。匹配鍵找到已存在物件的`upsert`總是會發出`update` ，即使沒有欄位變更；運行會將其報告為已更新，且結果狀態相同。這裡的冪等性指的是最終狀態收斂，而不是指未更改的重新運行是空操作。

 A practical consequence worth noting: an `upsert` preserves the server-assigned id of a matched object, so external systems that cache Stalwart ids keep working across re-applies \(unlike a `destroy` \+ `create`, which assigns fresh ids each time\).

 值得注意的一個實際後果是： `upsert`保留了匹配物件的伺服器分配的 ID，因此快取 Stalwart ID 的外部系統在重新應用後可以繼續工作（與`destroy` \+ `create`不同，後者每次都會分配新的 ID）。

#### Matching｜匹配

 The match key for an `upsert` is resolved in this order:

`upsert`的匹配鍵依以下順序解析：

1. **Explicit `matchOn`.** If the operation carries a `matchOn` list of property names, those properties are the key. An object in the `value` map matches an existing object when every listed property is equal. Every property in `matchOn` must be present in each object body, or the operation errors.
**顯式 `matchOn`。** 如果操作攜帶 `matchOn` 屬性名稱列表，則這些屬性是關鍵。當每個列出的屬性都相等時，`value`映射中的物件與現有物件相符。 `matchOn`中的每個屬性都必須存在於每個物件體中，否則操作會出錯。
2. **The schema’s label property.** If `matchOn` is omitted, the CLI uses the type’s label property \(the field the WebUI lists objects by, for example `name` on `Domain`\). snapshot writes this `matchOn` explicitly so plans are self-describing.
**模式的​​標籤屬性。** 如果省略`matchOn` ，則CLI使用類型的標籤屬性（WebUI 用來列出物件的字段，例如`name`在`Domain`上）。 snapshot明確地寫入此`matchOn` ，以便計劃能夠自我描述。
3. **Value match.**If the type has no label property and no `matchOn` was given, the CLI matches by comparing every non-secret scalar field \(string, number, boolean, enum, datetime\) of the body against existing objects. A `warning` is printed, because this match is not convergent: changing any compared field means the body no longer matches the old object, so a**new** object is created instead of the old one being updated. For any type you re-apply, supply an explicit `matchOn` \(or rely on a label property\) rather than value matching. `reconcile` never selects this mode on its own, since a by-value non-match would delete the old object; request it there with `"matchOn": "*"`, which also overrides the label property on types that have one.
**值匹配。**如果類型沒有標籤屬性且沒有給出 `matchOn`，則 CLI 透過將主體的每個非秘密標量欄位（字串、數字、布林值、枚舉、日期時間）與現有物件進行比較來進行比對。列印一個`warning`，因為這個匹配不收斂：更改任何比較字段意味著主體不再與舊物件匹配，因此創建一個**新**物件而不是更新舊物件。對於您重新套用的任何類型，請提供明確的 `matchOn` （或依賴標籤屬性）而不是值匹配。 `reconcile` 永遠不會自行選擇此模式，因為按值不匹配會刪除舊物件；使用 `"matchOn": "*"` 請求它，這也會覆蓋具有標籤屬性的類型。
A property the body sets to `null` compares equal to one the server omits, and vice versa. Under value matching and `scope` comparison a property the body omits entirely also compares equal to a server `null`; under an explicit `matchOn` a body cannot omit a match property at all, since that is an error. Stalwart returns unset nullable fields as explicit `null`s, so without this an unchanged plan would read as drifted on re-apply.

 請求體設定的屬性`null`與伺服器省略的屬性相等，反之亦然。在值匹配和比較`scope`下，請求體完全省略的屬性也與伺服器的屬性`null`相等；在明確比較`matchOn`下，請求體不能省略匹配屬性，因為這會報錯。 Stalwart 會將未設定的可空字段作為明確比較`null` ）傳回，因此如果沒有此設置，未更改的計劃在重新應用時會顯示為已更改。

 If the match key matches **more than one** existing object the operation errors as ambiguous, rather than guessing which one to update. This holds for value matching too: taking the first of several identical candidates would mean `reconcile` destroys the others. For multi-variant types, each body must carry its `@type`, and matching is done within that variant.

 如果匹配鍵與**多個**現有物件匹配，則操作會因匹配不明確而報錯，而不是猜測要更新哪個物件。值匹配也遵循此規則：如果從多個相同的候選對像中選取第一個，則`reconcile`會銷毀其他對象。對於 多變體類型 ，每個實體都必須攜帶其自身的`@type` ，匹配在該變體內部進行。

 A `matchOn` may include a **reference field**. When a match-key property is a reference \(an `ObjectId`, such as `Account.domainId`\) and its value in the body is a `#<id>` reference, the CLI resolves that reference to the real server id before comparing it against existing objects. This makes the effective primary key expressible: matching an `Account` on `["name", "domainId"]` where `domainId` is `#dom-a` compares against the domain’s actual id, whether it was created earlier in the plan or matched from the live server. A `#`-shaped value in a non-reference field is treated as a literal, not a reference. A `#<id>` in a match key that no earlier operation produced is a hard error \(caught upfront, so `--dry-run` reports it too\).

`matchOn`可以包含一個**引用欄位**。當匹配鍵屬性是一個引用（ `ObjectId` ，例如`Account.domainId` ）且其在請求體中的值也是一個引用時， `#<id>` CLI先將該引用解析為實際的伺服器 ID，然後再與現有物件進行比較。這使得有效主鍵可以表達：匹配`Account`和`["name", "domainId"]` ，其中`domainId`是`#dom-a`並與域的實際 ID 進行比較，無論該 ID 是在計劃的早期階段創建的，還是從實時伺服器匹配而來。非引用欄位中的`#`形值將被視為字面值，而不是引用。匹配鍵中出現`#<id>`且先前的操作沒有產生過該錯誤，這是一個硬錯誤（會提前捕獲，因此`--dry-run`也會報告該錯誤）。

 When an `upsert` updates a matched object, server-set and immutable fields in the body are dropped from the patch \(the server would reject them\); only mutable fields are sent.

 當`upsert`更新符合的物件時，伺服器設定的欄位和不可變欄位將從修補程式中刪除（伺服器會拒絕它們）；只有可變欄位會被傳送。

#### Teardown with destroy｜拆除與摧毀

`destroy` remains available for the cases where deletion is the intent: removing objects a plan no longer owns, or wiping a type before a migration. It is not part of the idempotent re-run flow above. See [the destroy reference](#destroy) and [Operational guidance](#operational-guidance).

`destroy`仍然適用於以刪除為目的的情況：移除計劃不再擁有的對象，或在遷移之前清除類型。它不屬於上述冪等重運行流程的一部分。請參閱[destroy參考](#destroy)和[操作指南](#operational-guidance) 。

- **Server-assigned ids change** across a destroy-and-recreate, so external systems that cache Stalwart ids must look them up again afterwards.
**伺服器指派的 ID 在銷毀和重新建立過程中會發生變化**，因此快取 Stalwart ID 的外部系統之後必須重新查找它們。
- **Destroy filters scope the teardown.** `{"@type":"destroy","object":"Domain","value":{"name":"example.com"}}` only removes the named domain. `{"@type":"destroy","object":"Domain"}` \(no `value`\) removes every domain on the server. Choose the filter to match the slice of state the plan owns; an unfiltered destroy in a plan that only declares one domain will silently delete every other domain on the server.
**銷毀過濾器範圍為拆卸。** `{"@type":"destroy","object":"Domain","value":{"name":"example.com"}}` 僅刪除指定域。 `{"@type":"destroy","object":"Domain"}`（無`value`）刪除伺服器上的每個網域。選擇過濾器來匹配計劃擁有的狀態切片；計劃中僅聲明一個網域的未經過濾的銷毀將默默地刪除伺服器上的所有其他網域。
### Reconciling to exact state｜與確切狀態相符

`upsert` never deletes, so it cannot express “these are the only objects of this type that should exist”. Re-applying an `upsert` plan after removing an entry leaves the old object in place: if you rename a domain from `example.org` to `example.net` and re-apply, you end up with **both**. `reconcile` closes that gap. It performs the same match-update-or-create as `upsert`, then destroys every existing object of the type that no entry in the plan matched. The result is that the type converges to exactly the plan:

`upsert`從不刪除，因此它無法表達「這些是該類型唯一應該存在的物件」。在刪除條目後重新套用`upsert`計畫會將舊物件保留在原處：如果您將網域從`example.org`重命名為`example.net`並重新套用，最終會同時得到**兩者**。 `reconcile`彌補了這一缺陷。它執行與`upsert`相同的匹配-更新-或-創建操作，然後銷毀計劃中沒有任何條目匹配的同類型現有物件。結果是，該類型最終完全收斂到計劃中定義的類型：

```json
{"@type":"reconcile","object":"Domain","matchOn":["name"],"value":{"dom-a":{"name":"example.net"}}}
```

Applying this leaves `example.net` as the **only** domain: it is created \(or matched and updated\) if present in the plan, and every other domain is destroyed. Re-applying is idempotent. An empty `value` \(`"value":{}`\) is therefore valid for `reconcile` \(it means “this type should have no objects”\), whereas `upsert` rejects it.

 應用此規則後， `example.net`成為**唯一**域：如果計劃中存在該域，則創建它（或匹配並更新它），其他所有域都將被銷毀。重新應用此規則是冪等的。因此，空的`value` \( `"value":{}` \) 對`reconcile`有效（這表示「此型別不應包含任何物件」），而`upsert`則拒絕它。

 Because `reconcile` deletes, a few rules keep it safe:

 因為`reconcile`會刪除數據，所以需要遵守以下幾條規則以確保安全：

- **A match key is required by default.`reconcile` does not silently fall back to the by-value matching that `upsert` allows: an operation with no `matchOn` on a type that also has no label property is rejected at plan time. Value matching treats any drifted field as a non-match, which under `reconcile` means deleting the existing object and recreating it under a new id. Pass `"matchOn": "*"` to request value matching explicitly. Be aware of what it costs: on a type with a unique constraint, the recreate collides with the old object \(whose deletion is deferred to the cleanup pass\) and the operation fails with `primaryKeyViolation`. Value matching is dependable for re-applying an**unchanged plan, not for absorbing drift; an explicit `matchOn` is almost always the better answer.
**預設情況下需要匹配鍵。`reconcile`不會像`upsert`允許的那樣靜默回退到按值匹配：對於沒有`matchOn`且沒有 label 屬性的類型，操作將在計劃時被拒絕。值匹配會將任何漂移的欄位視為不匹配，根據`reconcile` ，這表示刪除現有物件並使用新的 ID 重新建立它。傳遞`"matchOn": "*"`以明確請求值匹配。請注意其代價：對於具有唯一約束的類型，重新建立操作會與舊物件（其刪除操作會延遲到清理階段）發生衝突，且操作會失敗並傳回`primaryKeyViolation` 。值匹配適用於重新應用**未更改的計劃，但不適用於吸收漂移；顯式`matchOn`幾乎總是更好的選擇。

- **A reconcile covers the whole type unless you scope it.** By default every unmatched object of the type is deleted, including variants the plan does not mention. Add a `scope` to narrow what the operation owns: a flat map of property/value pairs an object must match \(all of them\) to be part of the operation at all.
**除非您指定範圍，否則協調操作會涵蓋整個類型。** 預設情況下，該類型的所有未匹配物件都會被刪除，包括計劃中未提及的變體。新增`scope`可以縮小操作的範圍：一個扁平化的屬性/值對映射，物件必須匹配所有屬性/值對才能參與操作。
- **Renames are delete-and-recreate.** The match key *is* the object’s identity. Changing the value of a match-key property means the old object no longer matches any entry, so it is deleted and a new object is created with a fresh server id. If you need to preserve the id across a rename, key on a stable property rather than the one being renamed.
**重新命名操作會刪除並重新建立物件。**匹配鍵*就是*物件的標識。更改匹配鍵屬性的值意味著舊物件不再與任何條目匹配，因此它會被刪除，並建立具有全新伺服器 ID 的新物件。如果需要在重新命名過程中保留 ID，請使用穩定的屬性作為鍵，而不是使用正在重新命名的屬性。

- **A blocked delete fails the run.** If an object the plan wants to delete is still referenced elsewhere \(for example a `Domain` pinned by an `Account`\), the destroy fails with `objectIsLinked` and the operation is reported as failed, exactly as a `destroy` would. `reconcile` does not force-delete.
**阻止的刪除會導致運行失敗。** 如果計劃要刪除的物件仍在其他地方引用（例如，由 `Account` 固定的 `Domain`），則銷毀會失敗並顯示 `objectIsLinked`，並且操作將報告為失敗，與 `destroy` 完全相同。 `reconcile` 不強制刪除。
#### Scoping an operation with `scope`｜使用`scope`進行操作範圍界定

`scope` is what makes `upsert` and `reconcile` usable for a type you only partly own. It declares the slice of the type the operation is responsible for, and it governs **both** halves of that responsibility: an entry may only match an existing object inside the scope, and a `reconcile` only deletes unmatched objects inside the scope. Everything outside is not the operation’s business, so it is neither matched nor deleted.

`scope`使得`upsert`和`reconcile`可以用於你僅部分擁有的類型。它聲明了操作負責的類型切片，並控制了該職責的**兩部分**：條目只能匹配作用域內的現有對象，而`reconcile`只刪除作用域內未匹配的對象。作用域外的所有內容都不屬於該操作的職責範圍，因此既不會被配對也不會被刪除。

 That is why `scope` is meaningful on `upsert` too, which never deletes anything. Restricting what an entry may match stops an operation reaching across into a slice it does not own. `MemoryLookupKey` is a good example: its label property is `key` alone, so a plan with no `matchOn` matches on `key` across every namespace and can silently update a row belonging to someone else. A scope makes that impossible regardless of the match key.

 這就是為什麼 `scope` 對 `upsert` 也有意義，它永遠不會刪除任何內容。限制條目可以匹配的內容會阻止操作觸及它不擁有的切片。 `MemoryLookupKey` 是一個很好的例子：它的標籤屬性是 `key` ，因此沒有 `matchOn` 的計劃在每個命名空間中與 `key` 匹配，並且可以默默地更新屬於其他人的行。無論匹配鍵如何，作用域都使得這種情況變得不可能。

 It compares property values for equality only: there is no negation, set membership, or comparison operator, so ownership has to be expressible as “every object where these properties equal these values”.

 它只比較屬性值是否相等：沒有否定、集合成員關係或比較運算符，因此所有權必須能夠表達為「這些屬性等於這些值的每個物件」。

 The scope is evaluated **client-side**, against the objects the operation already fetched to resolve matches. That is deliberate, and unlike the server-side filter accepted by `destroy`: Stalwart rejects server-side filters on `@type` for several multi-variant types \(`MtaRoute`, `SpamTag`, `Tracer`\), which are exactly the types most in need of per-variant scoping. Evaluating locally makes `@type` work uniformly.

 作用域的評估是在**客戶端**進行的，評估對像是操作已取得的用於解析匹配項的對象。這是有意為之，與`destroy`接受的伺服器端過濾器不同：Stalwart拒絕`@type`對幾種多變體類型（ `MtaRoute`, `SpamTag`, `Tracer` ）的伺服器端過濾器，而這些類型恰恰是最需要按變體進行作用域劃分的類型。本地評估使得`@type`能夠統一工作。

 Converge only the `Local` routes and leave every `Mx` route alone:

 僅匯聚`Local`路由，而保留所有`Mx`路由不變：

```json
{"@type":"reconcile","object":"MtaRoute","matchOn":["name"],"scope":{"@type":"Local"},"value":{"r-a":{"@type":"Local","name":"internal.example.com"}}}
```

Combined with an empty `value`, a scope expresses “this slice should be empty”:

 與空的`value`結合使用，作用域表示「此切片應為空」：

```json
{"@type":"reconcile","object":"MtaRoute","matchOn":["name"],"scope":{"@type":"Mx"},"value":{}}
```

A scope on several properties requires all of them to match, which is how you converge one namespace of a keyed lookup table without touching the others:

 對多個屬性進行作用域控制時，要求所有屬性都匹配，這樣才能在不影響其他屬性的情況下，統一鍵控查找表的一個命名空間：

```json
{"@type":"reconcile","object":"MemoryLookupKey","matchOn":["namespace","key"],"scope":{"namespace":"spam-traps"},"value":{"lk-a":{"namespace":"spam-traps","key":"foo@*","isGlobPattern":true},"lk-b":{"namespace":"spam-traps","key":"bar@*","isGlobPattern":true}}}
```

That single operation replaces the `destroy` \+ `upsert` pair the same intent used to require, and it is better behaved: the `destroy` half of that pair tore down every row in the namespace and rebuilt it, so unchanged rows got new server ids on every apply. `reconcile` updates the rows that matched in place and only deletes what the plan dropped.

 該單一操作取代了 `destroy` \+ `upsert` 對，其意圖與 require 相同，並且表現更好：該對的 `destroy` 一半刪除了命名空間中的每一行並重建它，因此未更改的行在每次應用時都會獲得新的伺服器 ID。 `reconcile` 更新就地匹配的行，並且僅刪除計劃刪除的內容。

 Scope values on reference properties resolve `#<id>` references, so a scope can name an object an **earlier** operation produced \(`{"domainId": "#dom-a"}`\). It cannot name one the same operation creates, because the scope is resolved before that operation matches or creates anything; both `--dry-run` and the real run reject that. A `scope` on any operation other than `upsert` or `reconcile` is rejected rather than silently ignored, and so is any unrecognised key at the top level of an operation: a misspelled `scope` would otherwise be dropped silently and widen a `reconcile` to the whole type.

 引用屬性上的作用域值會解析`#<id>`引用，因此作用域可以命名一個**較早**操作產生的物件 \( `{"domainId": "#dom-a"}` \)。它不能命名同一操作所建立的對象，因為作用域是在該操作匹配或建立任何對象之前解析的； `--dry-run`和實際運行都會拒絕這種情況。除`upsert`或`reconcile`之外的任何操作上的`scope`都會被拒絕，而不是被靜默忽略，操作頂層任何無法識別的鍵也會被拒絕：拼寫錯誤的`scope`否則會被靜默擴展到，並將`reconcile` 。

 Plan-time checks stop a scope from failing quietly, because a scope that matches nothing looks exactly like a successful reconcile:

 計劃時檢查可以防止範圍悄無聲息地失敗，因為與任何內容都不匹配的範圍看起來與成功的協調完全一樣：

- **Keys and `@type` values are validated.** A key must be `@type` or a property the type declares \(in any of its variants\), and an `@type` value must name a declared variant of a multi-variant type. A typo in either is an error, and so is an operator-form key borrowed from `destroy`: `{"nameContains": "spam-"}` is rejected rather than silently matching nothing. `destroy`’s filter and `scope` are not the same language.
**鍵和 `@type` 值經過驗證。** 鍵必須是 `@type` 或類型宣告的屬性（在其任何變體中），且 `@type` 值必須命名多變體類型的已宣告變體。任何一個中的拼字錯誤都是錯誤，從`destroy`: `{"nameContains": "spam-"}`借用的運算符形式密鑰也被拒絕，而不是默默地匹配任何內容。 `destroy`的濾鏡和`scope`不是同一種語言。
- **`null` values are rejected.** A comparison treats an absent property and a `null` one as equal, so `{"description": null}` would match every object that leaves the property unset, widening the scope instead of narrowing it. Scope on a property that is actually set instead.
**`null`值被拒絕。** 比較時，缺少的屬性和`null`屬性被視為相等，因此`{"description": null}`會匹配所有未設定該屬性的對象，從而擴大範圍而不是縮小範圍。應該針對實際已設定的屬性進行比較。
- **Entries must be inside their own scope.** An entry that contradicts the scope \(an `Mx` body under `"scope":{"@type":"Local"}`\) could never match an existing object, so it would be created again on every apply. It is rejected, and belongs in its own operation.
**條目必須位於其自身的作用域內。** 與作用域相衝突的條目（例如，位於`Mx`下的`"scope":{"@type":"Local"}`主體）永遠無法匹配現有對象，因此每次應用操作都會重新建立該條目。該條目將被拒絕，並應位於其自身的操作中。
An entry that simply *omits* a scoped property is fine: it inherits it. The scope is filled into the entry before the duplicate-entry check, before matching and before creation, so an object created by a scoped operation lands inside that scope. A server-derived \(`ServerSet`\) property cannot be scoped on, because the create path strips it and the object would land outside the scope it was declared under. `{"scope":{"namespace":"spam-traps"},"value":{"lk":{"key":"foo@*"}}}` creates the key in `spam-traps` without repeating the namespace in every entry.
 如果條目只是*省略*了作用域屬性，這沒問題：它會繼承該屬性。作用域會在重複條目檢查之前、符合之前和建立之前填入條目中，因此由作用域操作建立的物件會位於該作用域內。伺服器派生的（`ServerSet`\) 屬性無法設定作用域，因為建立路徑會將其剝離，導致物件超出其宣告的作用域。 `{"scope":{"namespace":"spam-traps"},"value":{"lk":{"key":"foo@*"}}}` 建立密鑰 `spam-traps` 無需在每個條目中重複命名空間。

 A `reconcile`’s deletions are computed while the operation runs but carried out in the cleanup pass, so two rules keep the deferred list honest. An object is dropped from it if **any other operation in the plan** created, matched, or updated it, in either order: a plan never deletes an object it also wrote. And an object already destroyed by an earlier `reconcile` in the same run is not destroyed twice.

`reconcile` 的刪除是在操作運行時計算的，但在清理過程中執行，因此有兩個規則使延遲清單保持誠實。如果**計劃中的任何其他操作**以任一順序建立、匹配或更新對象，則該對象將從其中刪除：計劃永遠不會刪除它也寫入的對象。並且在同一次運行中已被較早的 `reconcile` 銷毀的物件不會被銷毀兩次。

`reconcile` is **not** emitted by snapshot, which stays non-destructive \(`upsert`-only\) so that restoring a snapshot never deletes objects the snapshot happened to omit. Author `reconcile` by hand when converging a type to an exact, plan-owned set is the intent.

`reconcile` **不是** 由 snapshot 發出，它保持非破壞性（僅`upsert`-），因此恢復快照永遠不會刪除快照碰巧忽略的對象。意圖是在將類型收斂到精確的、計劃擁有的集合時手動編寫`reconcile`。

### Cross-operation references｜交叉操作參考

 The plan can express references between objects that have not been created yet by using the JMAP `#<id>` reference syntax. Two distinct mechanisms cooperate:

 此方案可以使用JMAP `#<id>`引用語法來表達尚未建立的物件之間的參考。兩種不同的機制協同工作：

- **Refs in values** \(`"domainId": "#dom-a"`\): the CLI never rewrites these. It collects them recursively from every string value and every object key, and forwards them to the server in the request-level `createdIds` map. The server resolves `#dom-a` to the real id assigned during the matching `create`. This works across separate JMAP requests, including across batches.
**值中的引用** \( `"domainId": "#dom-a"` \)： CLI不會重寫這些引用。它會遞歸地從每個字串值和每個物件鍵中收集這些引用，並將它們轉發到請求層級的`createdIds`映射中。伺服器會將`#dom-a`解析為符合期間指派的真實 ID `create` 。這適用於不同的JMAP請求，包括跨批次請求。
- **Refs as the `id` of an `update`** \(`"id": "#dom-a"`\): JMAP does not resolve `#`-prefixed update keys server-side. The CLI resolves these client-side from the id map populated during earlier `create` and `upsert` operations. If the reference does not match any prior create or upsert, the CLI errors before sending the request.
**參考 `update`** \(`"id": "#dom-a"`\) 的 `id`：JMAP 無法解析伺服器端以 `#`\\ 為前綴的更新。 CLI 從早期 `create` 和 `upsert` 操作期間填滿的 id 對應解析這些客戶端。如果引用與任何先前的建立或更新插入不匹配，則在發送請求之前會出現CLI錯誤。


 An `upsert` or `reconcile` registers a client id \(`#dom-a`\) the same way a `create` does, whether the object was matched or freshly created, so later operations can reference it regardless of whether this run created it or reconciled an existing one. This is what lets a snapshot’s singleton `update` set `"defaultDomainId": "#domain-b"` and have it resolve to the already-present domain on a re-apply.

 無論物件是匹配的還是新建的， `upsert`或`reconcile`都會註冊一個客戶端 ID \( `#dom-a` \)，其方式與`create`相同。這樣，後續操作就可以引用它，而無需考慮本次運行是建立了該物件還是協調了現有物件。這使得快照的單例`update`可以設定`"defaultDomainId": "#domain-b"` ，並在重新應用時解析到已存在的域。

 Refs work in:

 裁判的工作內容包括：

- String values, anywhere in the value tree \(`"domainId": "#dom-a"`\).
字串值，位於值樹中的任何位置（ `"domainId": "#dom-a"` ）。
- Object **keys** \(set-of-id and map-of-id forms\): `{ "memberGroupIds": { "#grp-sales": true, "#grp-support": true } }`.
物件**鍵**（id 集合和 id 映射形式）： `{ "memberGroupIds": { "#grp-sales": true, "#grp-support": true } }` 。
- The `id` field of an `update` operation \(resolved client-side as described above\).
`update`操作的`id`字段（如上所述在客戶端解析）。
Refs do **not** work for:
 裁判不為以下機構工作：

- The `id` field of an `update` operation when no matching `create` or `upsert` exists in the same plan \(the CLI surfaces a clear error in this case\).
當同一計劃中不存在匹配的`create`或`upsert`時， `update`操作的`id`字段（在這種情況下， CLI會顯示一個明顯的錯誤）。
#### References and tenants｜推薦人和租戶

 Resolving a reference is not the same as the server accepting it. An object that belongs to a tenant \(it sets `memberTenantId`\) may only reference other objects **in that same tenant**. This applies to every tenant-scoped type, including `DnsServer`, `AcmeProvider`, `Directory`, `Role`, `DkimSignature`, `MailingList`, `OAuthClient` and `Account`. There is no notion of a global resource that tenanted objects can borrow: a `DnsServer` with no `memberTenantId` is visible to administrators but cannot be referenced by a `Domain` that sets one.

 解析引用並不等於伺服器接受該引用。屬於某個租用戶的物件（設定了`memberTenantId` ）只能引用**同一租用戶**內的其他物件。這適用於所有租戶範圍的類型，包括`DnsServer`, `AcmeProvider`, `Directory`, `Role`, `DkimSignature`, `MailingList`, `OAuthClient`和`Account` 。不存在租用戶物件可以藉用的全域資源：一個沒有`memberTenantId`的`DnsServer`對管理員可見，但不能被設定了`Domain`的物件參考。

 A plan that mixes the two is rejected at apply time with `invalidForeignKey`:

 混合了這兩種方案的計劃在申請時會被拒絕，並顯示`invalidForeignKey` ：

```
✗ upsert Domain: Domain: create failed for `domain-a` (operation #3): error: invalidForeignKey |   Object id:   DnsServer#i1nk7i22boqc (plan reference #dnsserver-ovh)
```

The `(plan reference #...)` suffix names the plan reference that produced the rejected server id, so the offending line can be found without looking the id up on the server. The CLI annotates ids this way in any `set` failure whose value referenced them, covering `Object id`, `Existing id` and `Linked by`.

`(plan reference #...)`後綴指定了產生被拒絕伺服器 ID `set` CLI中引用它們的 ID，涵蓋`Object id`, `Existing id`和`Linked by` 。

 The fix is to place the referenced object in the same tenant as the objects that use it, giving each tenant its own copy:

 解決方法是將被引用的物件放置在與使用它的物件相同的租戶中，從而為每個租戶提供一個副本：

```
{"@type":"upsert","object":"Tenant","matchOn":["name"],"value":{"tenant-a":{"name":"a"}}}
{"@type":"upsert","object":"DnsServer","matchOn":["description"],"value":{"dnsserver-ovh":{"@type":"Ovh","memberTenantId":"#tenant-a","description":"ovh (tenant a)","applicationKey":"...","ovhEndpoint":"ovh-eu"}}}
{"@type":"upsert","object":"Domain","matchOn":["name"],"value":{"domain-a":{"memberTenantId":"#tenant-a","name":"a.com","dnsManagement":{"@type":"Automatic","dnsServerId":"#dnsserver-ovh"}}}}
```

When several tenants each need their own copy of a shared configuration, give each copy its own client id and a per-tenant natural key, and consider a [scope](#scoping-an-operation-with-scope) of `{"memberTenantId": "#tenant-a"}` so each tenant’s operation only matches and converges its own slice.

 當多個租戶各自需要共享配置的副本時，為每個副本分配一個客戶端 ID 和一個租戶自然鍵，並考慮 [scope](#scoping-an-operation-with-scope) `{"memberTenantId": "#tenant-a"}` ，以便每個租戶的操作僅匹配並收斂其自己的切片。

### Dependency ordering｜依存關係排序

 Because the CLI does not know the dependency graph in advance, plan authors are responsible for ordering operations correctly:

 由於CLI事先不知道依賴關係圖，因此計畫制定者有責任正確地對操作進行排序：

- **Upserts,**reconciles**, and**creates must be ordered parents-first. A `Domain` upsert must appear before an `Account` upsert that references the domain via `"domainId": "#..."`. This also covers references in a `reconcile` match key: the parent must be produced before the child op that keys on it. The delete half of a `reconcile` needs no ordering care, because it is deferred to the final children-first pass.
**更新插入、**協調**和**創建必須按父母優先的順序進行。 `Domain` 更新插入必須出現在透過 `"domainId": "#..."` 引用域的 `Account` 更新插入之前。這也涵蓋了 `reconcile` 匹配鍵中的引用：父操作必須在對其進行鍵控的子操作之前產生。刪除一半的`reconcile`不需要排序，因為它被推遲到最後的子優先遍歷。

- **Updates** must come after the upsert or create of the object they patch \(or reference an existing server id directly\). Singleton updates that reference other objects \(for example `SystemSettings` pointing at `defaultDomainId`\) belong at the end, after the objects they point to.
**更新**操作必須發生在被更新物件（或直接引用現有伺服器 ID）的 upsert 或 create 操作之後。引用其他物件的單例更新（例如`SystemSettings`指向`defaultDomainId` ）應放在最後，即它們所指向的物件之後。

- **Destroys, when present, must be listed**in the same order as the creates/upserts. The reverse pass will then take them down children-first, matching foreign-key constraints.
**銷毀操作（如果存在）必須**按照建立/更新操作的順序排列。反向傳遞時，會優先刪除子項，以符合外鍵約束。
A common pitfall with teardowns: writing destroys in reverse-of-creates order \(children-first\) makes the apply *re-reverse* them at runtime to parents-first, which fails on `objectIsLinked`. The fix is to write destroys forwards \(parents-first\); the apply does the reversal.

 清理作業的一個常見陷阱：以與建立順序相反的順序（先處理子程序）編寫銷毀操作，會導致執行時間應用銷毀操作時再次反轉順序，改為先處理父進程，導致操作失敗。 `objectIsLinked`解決方法是先執行銷毀操作（父級優先），然後執行 apply 操作來反轉銷毀操作。

### Batching｜批量處理

 The CLI splits large operations into batches sized by the server’s `maxObjectsInSet` \(typically 500\), so an `upsert` or `create` of 5,000 objects is sent in batches of 500. The first batch of a given object type sees only the previously-tracked `createdIds`. Each completed batch contributes its newly-assigned ids to the global tracker, so subsequent batches \(and subsequent operations\) can reference them.

 CLI將大型作業拆分成若干批次，批次大小由伺服器的`maxObjectsInSet` （通常為 500）決定。因此，包含 5000 個物件的`upsert`或`create`會以 500 個物件為一批發送。對於給定的物件類型，第一個批次只能看到先前追蹤過的`createdIds` 。每個完成的批次都會將其新分配的 ID 新增至全域追蹤器中，以便後續批次（以及後續操作）可以引用它們。

 To resolve matches, an `upsert` or `reconcile` first reads the existing objects of the type once \(paginated by `maxObjectsInGet`\) and caches them for the run, then issues the `create` and `update` batches. A `reconcile` reuses that same cached read to compute which existing objects were not matched, and destroys them in `maxObjectsInSet` batches during the cleanup pass.

 為了解決比賽， `upsert` 或者 `reconcile` 首先讀取該類型的現有物件一次（按頁碼分頁） `maxObjectsInGet`）並緩存它們以供運行，然後發出 `create` 和 `update` 批次。 `reconcile` 它重複使用相同的快取讀取結果來計算哪些現有物件未匹配，並銷毀它們。 `maxObjectsInSet` 清理過程中的批次。

 For destroys, ids are first collected by paginating the corresponding `query` \(anchor-based, in `maxObjectsInGet` increments\), then destroyed in `maxObjectsInSet` batches.

 對於銷毀操作，首先透過對應的`query`進行分頁（基於錨點，以`maxObjectsInGet`遞增）來收集 id，然後分批銷毀`maxObjectsInSet`批。

## File format｜文件格式

 A plan is **NDJSON**: every non-blank line is a JSON object describing one operation. Each operation has a discriminator `@type` field and an `object` field; the remaining fields depend on `@type`. Lines are processed in file order; blank lines and surrounding whitespace are ignored. There is no enclosing array.

 計劃是**NDJSON**：每一行非空行都是一個JSON對象，描述一個操作。每個操作都有一個鑑別器`@type`字段和一個`object`字段；其餘字段取決於`@type` 。行按文件順序處理；空白行及其周圍的空白字元將被忽略。沒有封閉數組。

### Annotated example｜附註解的範例

 A re-runnable plan: `upsert` the objects \(parents first\), then point the singleton at one of them. Applying it twice converges to the same state.

 可重複運行的計畫： `upsert`遍歷物件（先遍歷父物件），然後將單例指向其中一個物件。應用兩次即可收斂到相同的狀態。

```
# Upsert objects, parents-first. matchOn names the natural key.
{"@type":"upsert","object":"Domain","matchOn":["name"],"value":{"dom-a":{"name":"example.com","description":"Primary corporate domain"},"dom-b":{"name":"example.net"}}}
{"@type":"upsert","object":"Account","matchOn":["name"],"value":{"grp-sales":{"@type":"Group","name":"sales","domainId":"#dom-a"}}}

# Singleton update, last: it references a domain upserted above.
{"@type":"update","object":"SystemSettings","value":{"defaultDomainId":"#dom-a"}}
```

\(Annotation lines starting with `#` are shown above for clarity; the actual NDJSON parser does **not** accept comments. Every non-blank line must be a JSON object.\)

 （為了清晰起見，上面顯示了以`#`開頭的註解行；實際的NDJSON解析器**不**接受註解。每個非空白行都必須是一個JSON物件。）

 On the first apply, no `example.com`/`example.net` domain exists, so both are created and `#dom-a` resolves to the new `example.com`. On the second apply, the `matchOn: ["name"]` key finds the existing domains and they are updated in place; `#dom-a` resolves to the same id, so `defaultDomainId` stays valid and nothing is duplicated or destroyed.

 第一次應用時，不存在`example.com`/`example.net`域，因此創建了這兩個域，並且`#dom-a`解析為新的`example.com` 。第二次應用時， `matchOn: ["name"]`鍵找到了現有域，並對其進行了就地更新； `#dom-a`解析為相同的 ID，因此`defaultDomainId`保持有效，沒有任何內容被複製或刪除。

 A complete obfuscated example plan is included with these docs at [example-bulk-plan.ndjson](https://stalw.art/docs/management/cli/example-bulk-plan.ndjson).

 這些文件中包含一個完整的混淆範例計劃，位於 [example-bulk-plan.ndjson](https://stalw.art/docs/management/cli/example-bulk-plan.ndjson) 。

### Encoding of values｜值的編碼

 The `value` of each operation is a configuration object body, encoded as described in Object encoding: list and set fields are JSON objects rather than arrays, and durations and sizes are integers. A payload that gets this wrong is rejected with `invalidPatch | Invalid value for object property`, naming the offending property. Running snapshot against a configured server prints a plan in the canonical encoding.

 每个操作的`value`都是一个配置对象主体，其编码方式如 对象编码中所述：列表和集合字段是JSON对象而非数组，持续时间和大小是整数。如果有效負載的編碼有誤，則會被拒絕，並顯示`invalidPatch | Invalid value for object property`錯誤訊息，指出出錯的屬性。對已設定的伺服器運作 snapshot會以規範編碼列印計畫。

#### `upsert`

| Field 欄位 | Type 類型 | Required 必填 | Notes 備註 |

| `object` | string 字串 | yes 是 | Object type name \(`x:` prefix optional\). Singletons are rejected: use `update`. 物件類型名稱（ `x:`前綴可選）。單例模式將被拒絕：請使用`update` 。 |
| `matchOn` | array of string, or `"*"` 字串數組，或`"*"` | no 無 | Property names forming the [match key](#matching), or `"*"` to match by value explicitly. | `scope` | object 物件 | no 否 | Flat property/value map restricting which existing objects an entry may match. See [Scoping an operation](#scoping-an-operation-with-scope). If omitted, the whole type is in scope. 扁平屬性/值映射，限制條目可以符合哪些現有物件。參見[操作範圍](#scoping-an-operation-with-scope) 。由於`upsert`從不刪除，它只會縮小匹配範圍。如果省略，則整個類型都在範圍內。 |
| `value` | object 物件 | yes 是 | Map of client id -&amp;gt; object body. Each body must include every property named in `matchOn`, and `@type` for multi-variant objects. References use `#<id>`. 客戶端 ID 到物件主體的對應。每個主體必須包含`matchOn`中列出的所有屬性，對於多變體對象，還必須​​包含`@type`中列出的所有屬性。引用使用`#<id>` 。 |

For each object in `value`, the CLI looks for an existing object matching the [match key](#matching): if found it issues an `update` \(server-set and immutable fields are dropped from the patch\); if not, it issues a `create`. The map keys are client-assigned ids that may be referenced elsewhere as `#<key>`, whether the object ends up matched or created. As with `create`, a single leading `#` on a map key is stripped, so `{"dom-a": {...}}` and `{"#dom-a": {...}}` are equivalent.

 對於`value`中的每個對象，CLI會尋找與[匹配鍵](#matching)匹配的現有對象：如果找到，則發出`update` （伺服器設定的字段和不可變字段將從補丁中移除）；否則，發出`create` 。映射鍵是客戶端分配的ID，無論物件最終是匹配還是創建，都可以在其他地方引用`#<key>` 。與`create`一樣，映射鍵上的單一前導`#`會被移除，因此`{"dom-a": {...}}`和`{"#dom-a": {...}}`是等效的。

 An `upsert` reads the existing objects of the type once to resolve matches, then maps to JMAP `Object/set` requests with `create` and `update` populated. Batching is handled automatically. An empty `value`, an empty `matchOn`, an entry outside the operation’s own `scope`, or an `upsert` of a singleton each fail before any operation in the plan runs. An ambiguous match \(the key matches more than one existing object\) and a `matchOn` property missing from a body are detected while the operation runs, so earlier operations in the plan will already have been applied.

`upsert`讀取一次該類型的現有物件以解析匹配項，然後映射到JMAP `Object/set`請求，其中`create`和`update`已填入。批次自動處理。如果`value`為空、 `matchOn`為空、條目位於操作自身`scope`之外，或`upsert`為單例，則在計劃中的任何操作運行之前都會失敗。如果匹配不明確（鍵匹配多個現有物件）或請求體缺少`matchOn`屬性，則會在操作運行時檢測到，因此計劃中較早的操作已被執行。

#### `reconcile`

| Field 欄位 | Type 類型 | Required 必填 | Notes 備註 |
| --- | --- | --- | --- |
| `@type` | `"reconcile"` | yes 是 |  |
| `object` | string 字串 | yes 是 | Object type name \(`x:` prefix optional\). Singletons are rejected: use `update`. 物件類型名稱（ `x:`前綴可選）。單例模式不被接受：請使用`update` 。 |
| `matchOn` | array of string, or `"*"` 字串數組，或`"*"` | no 無 | Property names forming the [match key](#matching), or `"*"` to match by value explicitly. If omitted, the type’s label property is used. | `scope` | object 物件 | no 否 | Flat property/value map restricting the slice of the type this operation owns, for matching **and**deletion. An object must match every property listed. | `value` | object 物件 | yes 是的 | Map of client id -&amp;gt; object body, same shape as `upsert`. May be empty \(`{}`\) to mean “nothing in scope should exist”. Each body must include every property named in `matchOn`, and `@type` for multi-variant objects. 客戶端id -&amp;gt; 物件體的映射，與`upsert`形狀相同。可能為空（`{}`），表示「範圍內不應存在任何內容」。每個主體必須包含 `matchOn` 和`@type` 中命名的每個屬性（對於多變體物件）。 |

`reconcile` runs the `upsert` logic \(match, then update or create each entry\), then destroys every existing object in scope that no entry matched. See [Reconciling to exact state](#reconciling-to-exact-state) for the full semantics. The deletes are deferred to the cleanup pass \(run after the whole apply pass, in reverse plan order\), so a `reconcile` can add, update, and remove in one operation without ordering the deletes by hand. A `reconcile` on a singleton, an empty `matchOn`, a `scope` that is not an object or that names an unknown property or a null value, an entry outside its own scope, or a type that would fall back to by-value matching without asking for it each fail with a clear error before any operation in the plan runs. A delete blocked by a live reference fails with `objectIsLinked`, exactly as `destroy` does.

`reconcile` 運行 `upsert` 邏輯（匹配，然後更新或建立每個條目），然後銷毀範圍內沒有條目匹配的每個現有物件。有關完整語義，請參閱[協調到準確狀態](#reconciling-to-exact-state)。刪除被推遲到清理過程（在整個應用過程之後以相反的計劃順序運行），因此 `reconcile` 可以在一個操作中添加、更新和刪除，而無需手動排序刪除。單例上的 `reconcile`、空的 `matchOn`、不是物件或命名未知屬性或空值的 `scope`、其自身範圍之外的條目或將回退到按值匹配而不詢問它的類型，在計劃中的任何操作運行之前都會失敗並出現明顯的錯誤。被即時引用阻止的刪除失敗並顯示 `objectIsLinked`，與`destroy` 完全相同。

#### `create`

| Field 欄位 | Type 類型 | Required 必填 | Notes 備註 |
| --- | --- | --- | --- |
| `@type` | `"create"` | yes 是 |  |
| `object` | string 字串 | yes 是 | Object type name \(`x:` prefix optional\). 物件類型名稱（ `x:`前綴可選）。 |
| `value` | object 物件 | yes 是 | Map of client id -&amp;gt; object body. Each body must include `@type` for multi-variant objects. References use `#<id>`. 客戶端 ID 到物件主體的對應。對於多變量對象，每個主體必須包含`@type` 。引用使用`#<id>` 。 |

The map keys are client-assigned ids. They may be referenced elsewhere as `#<key>`. As a convenience, the CLI strips a single leading `#` from create-map keys, so `{"dom-a": {...}}` and `{"#dom-a": {...}}` are equivalent.

 映射鍵是客戶端指派的 ID。它們在其他地方可能被引用為`#<key>` 。為了方便起見， CLI從建立映射鍵中去掉一個前導的`#` ，因此`{"dom-a": {...}}`和`{"#dom-a": {...}}`是等效的。

 A `create` operation maps directly to one or more JMAP `Object/set` requests with `create` populated. Batching is handled automatically. Unlike `upsert`, a `create` is not re-runnable: a second apply trips a primary-key violation or produces duplicate rows. Reach for `create` only in one-shot plans; prefer `upsert` for anything re-applied.

`create`操作直接對應到一個或多個JMAP `Object/set`請求，其中`create`已填入。批量處理自動完成。與`upsert`不同， `create`不可重複運行：第二次應用會觸發主鍵衝突或產生重複行。僅在一次性計劃中使用`create` ；對於任何需要重複應用的操作，建議使用`upsert` 。

#### `update`

| Field 欄位 | Type 類型 | Required 必填 | Notes 備註 |
| --- | --- | --- | --- |
| `@type` | `"update"` | yes 是 |  |
| `object` | string 字串 | yes 是 |  |
| `id` | string or null 字串或 null | required for non-singletons 非單例模式必需 | **Top-level sibling of `value`, not a key inside `value`.**May be a `#<id>` reference to an object created earlier in the plan. May be `null` or omitted for singletons. **`value`的頂級同級元素，不是`value`內部的鍵。** 可以是`#<id>`對計畫中先前建立的物件的參考。單例模式可以省略`null`或為空。 |
| `value` | object 物件 | yes 是 | JMAP patch object. Top-level keys may be JSON pointers \(`"aliases/2/name"`\). JMAP修補物件。頂層鍵可以是JSON指針（ `"aliases/2/name"` ）。 |

`update` corresponds to a single JMAP `Object/set` with `update` populated. Patches use the JMAP semantics: only changed fields are sent; sub-fields can be addressed with `/`-separated paths; `null` removes a value.

`update`對應於一個JMAP `Object/set`其中`update`已填入。補丁使用JMAP語意：僅傳送已變更的欄位；子欄位可以使用`/` \\ 分隔的路徑進行定址； `null`刪除一個值。

 A singleton update omits the top-level `id` field \(or sets it to `null`\):

 單例更新會省略頂層`id`字段（或將其設為`null` ）：

```json
{"@type":"update","object":"SystemSettings","value":{"defaultDomainId":"#dom-a"}}
```

A non-singleton update sets the top-level `id` field to the id of the object being patched. The id may be a `#<id>` reference to an object created earlier in the same plan:

 非單例更新會將頂層`id`欄位設定為被修補物件的 ID。該 ID 可以是`#<id>`對同一計劃中先前建立的物件的參考：

```json
{"@type":"update","object":"Domain","id":"#dom-a","value":{"description":"Renamed"}}
```

Or a literal server-assigned id, for patching an existing object the plan does not create:

 或使用伺服器分配的字面 ID，用於修補計劃未建立的現有物件：

```json
{"@type":"update","object":"Domain","id":"k1234abcd","value":{"description":"Renamed"}}
```

Note that `id` is a top-level field of the operation, alongside `@type`, `object`, and `value`. It is not a key inside `value`. \(The map-keyed shape, where ids are keys of `value`, is the `create` convention; conflating the two is a common mistake when writing the first non-singleton update.\)

 請注意， `id`是操作的頂級字段，與`@type`, `object`和`value`並列。它不是`value`內部的鍵。 （以 id 为键的映射结构，即`value`的键，是`create`约定；在编写第一个非单例更新时，混淆这两种约定是一个常见的错误。）

 For multi-variant changes \(where the entire variant is being switched\), pass the new variant’s body as a single value rather than patching individual sub-paths \(see Updating objects for the rationale\).

 對於多變體變更（整個變體都被切換），將新變體的主體作為單一值傳遞，而不是修補各個子路徑（有關理由，請參閱更新物件 ）。

#### `destroy`

| Field 欄位 | Type 類型 | Required 必填 | Notes 備註 |
| --- | --- | --- | --- |
| `@type` | `"destroy"` | yes 是 |  |
| `object` | string 字串 | yes 是 | Singletons cannot be destroyed. 單例不能被銷毀。 |
| `value` | object or null 物件或 null | no 沒有 | JMAP filter object. `{}` or `null` matches every instance of the type. JMAP 過濾物件。 `{}` 或 `null` 符合該類型的每個實例。 |

Destroys are *filter-based*, not id-based: the CLI runs a paginated `Object/query` with the supplied filter, then destroys every returned id in batches. To delete a specific known id, use a filter that matches it \(e.g. `{"name": "..."}`\) or the standalone delete command.

 銷毀操作是基於*過濾器*的，而不是基於 ID 的： CLI會使用提供的過濾器運行分頁的`Object/query` ，然後分批銷毀每個返回的 ID。若要刪除特定的已知 ID，請使用與其相符的篩選器（例如`{"name": "..."}` ）或獨立的 delete指令。

 The set of filterable properties is whatever the server’s `Object/query` accepts for the type. Most user-facing properties \(`name`, `domainId`, etc.\) are universally supported. Filtering on the `@type` discriminator works for some multi-variant types \(notably `Account`\) but not all. If a destroy fails with `unsupportedFilter: Filter on property @type is not supported or invalid`, drop the `@type` clause and either destroy all variants of the parent \(omit `value`\) or filter on a regular property.

 可過濾屬性集取決於伺服器對類型接受的`Object/query`值。大多數面向使用者的屬性（例如`name`, `domainId` ）都普遍受支援。基於`@type`鑑別器的過濾適用於某些多變體類型（尤其是`Account` ），但並非所有類型都適用。如果銷毀操作因`unsupportedFilter: Filter on property @type is not supported or invalid`而失敗，則刪除`@type`子句，並銷毀父類型的所有變體（省略`value` ），或基於常規屬性進行過濾。

## Output｜輸出

### Human \(default\)｜人類（預設）

```yaml
Plan: 0 destroy, 1 update, 0 create, 3 upsert, 0 reconcile (7 objects)
✓ upserted Domain (2)
✓ upserted Account (2)
✓ upserted DkimSignature (3)
✓ updated SystemSettings (1)
Done: 0 destroyed, 4 updated, 4 created (0 failed)
```

An `upsert` \(or `reconcile`\) line shows the total objects handled; in the `Done:` summary those split into `created` \(no existing match\) and `updated` \(matched and reconciled\). Here the seven upserted objects landed as four creates and three updates, plus the one singleton update. A `reconcile` that deletes also prints a cleanup line during the final pass, for example `✓ reconcile removed Domain (2)`, and those deletions are tallied under `destroyed` in the summary. The `Plan:` line and the `Done:` line are written to **stderr** so that `--json` output stays clean for downstream tools.

`upsert`（或`reconcile`）線顯示處理的物件總數；在`Done:`摘要中，它們分為`created`（沒有現有匹配）和`updated`（匹配並協調）。這裡，七個更新插入的物件以四個創建和三個更新的形式落地，再加上一個單例更新。刪除的`reconcile`也會在最後一遍期間列印清理行，例如`✓ reconcile removed Domain (2)`，並且這些刪除記錄在摘要中的`destroyed`下。 `Plan:` 行和 `Done:` 行寫入 **stderr**，以便 `--json` 輸出對下游工具保持乾淨。

### NDJSON \(`--json`\)

 One record per completed operation, plus a `summary` record:

 每個已完成的操作記錄一條，外加一條`summary`記錄：

```
{"op":"upsert","object":"Domain","index":0,"count":2,"status":"ok"}
{"op":"upsert","object":"Account","index":1,"count":2,"status":"ok"}
{"op":"update","object":"SystemSettings","index":2,"count":1,"status":"ok"}
{"op":"summary","plan":{"destroys":0,"updates":1,"creates":0,"create_objects":0,"upserts":2,"upsert_objects":4,"reconciles":0,"reconcile_objects":0},"done":{"destroyed":0,"updated":3,"created":2,"failed":0}}
```

This is the recommended mode for CI pipelines and IaC providers. The plan header and any progress lines remain on stderr; only the records above appear on stdout. The summary’s `plan` block counts the planned operations \(`upserts`, `upsert_objects`, `reconciles`, and `reconcile_objects` alongside the create/update/destroy counts\); the `done` block counts the actual outcome, where an upsert’s or reconcile’s objects are tallied under `created` or `updated`.

 這是推薦用於CI管道和 IaC 提供者的模式。計劃頭和任何進度行保留在 stderr 上；只有上面的記錄會出現在 stdout 上。摘要的`plan`塊統計計劃的操作（ `upserts`, `upsert_objects`, `reconciles`和`reconcile_objects`以及創建/更新/銷毀計數）； `done`塊統計實際結果，其中 upsert 或 reconcile 操作的對象數量分別在`created`或`updated`

 A `reconcile` op emits its `create`/`update` record during the apply pass and, if it deleted anything, a second record during the cleanup pass carrying `"stage":"cleanup"` and the destroyed count:

`reconcile`操作在應用階段發出其`create`/`update`記錄，如果它刪除了任何內容，則在清理階段發出第二個記錄，該記錄攜帶`"stage":"cleanup"`和已銷毀計數：

```
{"op":"reconcile","object":"Domain","index":0,"count":1,"status":"ok"}
{"op":"reconcile","stage":"cleanup","object":"Domain","index":0,"destroyed":2,"status":"ok"}
```

### Dry run｜試運行

```bash title=&amp;quot;Terminal window&amp;quot;
stalwart-cli apply --file plan.ndjson --dry-run
```

```yaml
Plan: 0 destroy, 1 update, 0 create, 3 upsert, 0 reconcile (7 objects)
(dry run: no changes will be made)
```

`--dry-run` validates that the plan parses, that every referenced object type exists in the schema, and that the structural rules are respected \(singleton / id rules, no `upsert` or `reconcile` of a singleton, non-empty `value` and `matchOn` where required, and that a `reconcile` has a usable match key\). It also resolves the plan’s `#<id>` references in match keys offline, walking operations in plan order: a `matchOn` reference to an id that no earlier operation produces is rejected at dry-run time, so this class of error no longer waits until apply. It does not contact the server beyond fetching the schema \(which is normally cached\), so match resolution against live data \(whether an object exists, whether a match is ambiguous, what a `reconcile` would delete\) is still only checked at apply time.

`--dry-run` 驗證計畫是否解析成功，所有引用的物件類型是否都存在於模式中，以及結構規則是否被遵守（單例/ID規則，無 `upsert` 或者 `reconcile` 單元素，非空 `value` 和 `matchOn` 在需要的地方，以及 `reconcile` 具有可用的匹配鍵）。它也解決了計劃的問題。 `#<id>` 離線匹配鍵中的引用，按計劃順序執行操作：a `matchOn` 在試運行階段，先前操作未產生的 ID 的參考會被拒絕，因此這類錯誤不再等待應用操作。它不會像獲取模式（通常已緩存）那樣與伺服器通信，因此不會針對即時資料進行匹配解析（物件是否存在、匹配是否模糊、具體情況如何）。 `reconcile` （會被刪除）仍然只在應用時進行檢查。

## Integrating with infrastructure-as-code｜與基礎設施即程式碼集成

 The CLI is designed to work as the lowest-level building block under whatever orchestration tool fits the platform. The pattern in every case is the same: render a JSON plan from the platform’s templates / variables, pipe or pass it to `stalwart-cli apply`, and surface the exit status.

 CLI的設計目標是作為任何適合該平台的編排工具的底層建構模組。其模式始終相同：從平台的模板/變數渲染JSON計劃，將其傳遞給`stalwart-cli apply` ，並返回退出狀態。

### Ansible

 Use `ansible.builtin.template` to render a plan from a Jinja2 template, then `ansible.builtin.command` to apply it. A minimal playbook:

 使用`ansible.builtin.template`從 Jinja2 模板渲染計劃，然後使用`ansible.builtin.command`應用該計劃。一個最簡操作手冊：

```yaml
- name: Deploy Stalwart configuration
  hosts: mail
  vars:
    stalwart_url: "https://mail.example.com"
    domains:
      - { name: "example.com", description: "Primary" }
      - { name: "example.net", description: "Transactional" }

  tasks:
    - name: Render plan
      ansible.builtin.template:
        src: stalwart-plan.ndjson.j2
        dest: /tmp/stalwart-plan.ndjson
      register: plan

    - name: Apply plan
      ansible.builtin.command: >
        stalwart-cli apply --file /tmp/stalwart-plan.ndjson --json
      environment:
        STALWART_URL: "{{ stalwart_url }}"
        STALWART_USER: "{{ stalwart_admin_user }}"
        STALWART_PASSWORD: "{{ stalwart_admin_password }}"
      register: result
      changed_when: result.rc == 0 and ('"created":' in result.stdout or '"updated":' in result.stdout)
      failed_when: result.rc != 0

    - name: Show summary
      ansible.builtin.debug:
        msg: "{{ result.stdout_lines | last | from_json }}"
```

`stalwart-plan.ndjson.j2` \(one JSON object per line, no enclosing array\):

`stalwart-plan.ndjson.j2` （每行一個JSON對象，無封閉數組）：

```jinja
{"@type":"upsert","object":"Domain","matchOn":["name"],"value":{
{%- for d in domains -%}
"dom-{{ loop.index }}":{"name":"{{ d.name }}","description":"{{ d.description }}"}{% if not loop.last %},{% endif %}
{%- endfor -%}
}}
```

The single `upsert` line is idempotent: the first apply creates the domains, every later apply matches them by `name` and reconciles their fields. No teardown loop is needed.

 單行`upsert`是冪等的：第一次 apply 操作建立域，之後每次 apply 操作都透過`name`來匹配這些域並協調它們的欄位。無需清理循環。

 Use `--dry-run` in a `check` task for `--check` Ansible runs.

 在`check`任務中使用`--dry-run`以運行`--check` Ansible。

### Terraform

 Two patterns are supported.

 支援兩種模式。

**As an `external` data source** \(read-only views of state\) and a `terraform_data` resource that runs the apply on changes:

**作為`external`資料來源**（狀態的唯讀視圖）和`terraform_data`資源，在發生變更時執行應用操作：

```hcl
locals {
  ops = [
    {
      "@type" = "upsert"
      object  = "Domain"
      matchOn = ["name"]
      value = {
        for d in var.domains :
        "dom-${d.id}" => { name = d.name, description = d.description }
      }
    },
    {
      "@type" = "update"
      object  = "SystemSettings"
      value = {
        defaultDomainId = "#dom-${var.default_domain_id}"
        defaultHostname = var.hostname
      }
    },
  ]
# Render as NDJSON: one JSON object per line, no enclosing array.
  plan = join("\n", [for op in local.ops : jsonencode(op)])
}

resource "terraform_data" "stalwart_apply" {
  triggers_replace = [local.plan]

  provisioner "local-exec" {
    command     = "stalwart-cli apply --stdin --json"
    interpreter = ["/bin/sh", "-c"]
    environment = {
      STALWART_URL      = var.stalwart_url
      STALWART_USER     = var.stalwart_admin_user
      STALWART_PASSWORD = var.stalwart_admin_password
    }
    stdin = local.plan
  }
}
```

`triggers_replace` ensures the apply re-runs whenever the rendered plan changes. Because the plan is built from `upsert` operations, a re-run reconciles the existing Stalwart objects in place rather than recreating them, so re-applying after an unrelated change is safe.

`triggers_replace`確保在渲染計畫發生變更時重新運行。由於該計劃由`upsert`操作構建，因此重新運行會就地協調現有的 Stalwart 對象，而不是重新創建它們，所以在發生無關更改後重新應用是安全的。

 For a more idiomatic Terraform integration \(typed resources, real drift detection, partial applies\), wrap the CLI in a small custom provider written in Go that shells out to `stalwart-cli` for the actual operations.

 為了實現更地道的 Terraform 整合（類型化資源、真正的漂移偵測、部分應用），將CLI包裝在一個用 Go 編寫的小型自訂提供者中，該提供者會呼叫`stalwart-cli`來進行實際操作。

### NixOS

 Define a NixOS module that materialises the plan as a derivation and runs it via a `systemd.services.<name>.serviceConfig.ExecStart`:

 定義一個 NixOS 模組，將計劃具體化為派生並透過`systemd.services.<name>.serviceConfig.ExecStart`運行它：

```nix
{ config, lib, pkgs, ... }:

let
  cfg = config.services.stalwart-bootstrap;
# NDJSON: one operation per line, no enclosing array.
  planText = lib.concatMapStringsSep "\n"
    (op: builtins.toJSON op) cfg.plan;
  plan = pkgs.writeText "stalwart-plan.ndjson" planText;
in
{
  options.services.stalwart-bootstrap = {
    enable = lib.mkEnableOption "Stalwart configuration bootstrap";
    url = lib.mkOption { type = lib.types.str; };
    credentialsFile = lib.mkOption {
      type = lib.types.path;
      description = "EnvironmentFile with STALWART_USER and STALWART_PASSWORD (or STALWART_TOKEN).";
    };
    plan = lib.mkOption {
      type = lib.types.listOf lib.types.attrs;
      description = "List of stalwart-cli apply operations.";
    };
  };

  config = lib.mkIf cfg.enable {
    systemd.services.stalwart-bootstrap = {
      description = "Stalwart configuration bootstrap";
      wantedBy = [ "multi-user.target" ];
      after = [ "network-online.target" ];
      wants = [ "network-online.target" ];
      serviceConfig = {
        Type = "oneshot";
        EnvironmentFile = cfg.credentialsFile;
        Environment = "STALWART_URL=${cfg.url}";
        ExecStart = "${pkgs.stalwart-cli}/bin/stalwart-cli apply --file ${plan}";
        RemainAfterExit = true;
      };
    };
  };
}
```

Consumers then write:

 消費者隨後寫道：

```nix
services.stalwart-bootstrap = {
  enable = true;
  url = "https://mail.example.com";
  credentialsFile = "/run/secrets/stalwart-admin";
  plan = [
    { "@type" = "upsert";
      object  = "Domain";
      matchOn = [ "name" ];
      value   = { dom-a = { name = "example.com"; }; };
    }
    { "@type" = "update";
      object  = "SystemSettings";
      value   = { defaultDomainId = "#dom-a"; defaultHostname = "mail.example.com"; };
    }
  ];
};
```

The plan is regenerated and re-applied on every NixOS rebuild. Because it is built from `upsert` operations, each rebuild reconciles the existing objects in place rather than recreating them, so repeated rebuilds converge instead of failing on the second run. Combine with `agenix` or `sops-nix` for the credentials file. Use `--dry-run` in a separate `nixos-test` to validate plans in CI.

 每次 NixOS 重建時，都會重新產生並套用該計劃。由於它是基於`upsert`操作構建，因此每次重建都會就地協調現有對象，而不是重新創建它們，所以重複重建能夠收斂，而不會在第二次運行時失敗。將`agenix`或`sops-nix`結合使用以處理憑證檔案。在單獨的`nixos-test`中使用`--dry-run`來驗證CI中的計劃。

## Operational guidance｜操作指南

- **Prefer `upsert` for anything re-applied.** A plan of `upsert` and singleton `update` operations converges on every run. Reserve `create` for one-shot plans and `destroy` for deliberate teardowns.
**對於重新應用的任何內容，首選 `upsert`。** `upsert` 和單例 `update` 操作的計劃在每次運行時都會收斂。為一次性計劃保留`create`，為故意拆解保留`destroy`。
- **Reach for `reconcile` only when the plan owns the whole type.** `reconcile` deletes every object of the type the plan does not list, so use it when the plan is the single source of truth for that type \(and when you want a removed entry to be deleted, not left behind\). If other tooling or operators also manage objects of that type, prefer `upsert` plus explicit `destroy` operations so you delete only what the plan owns. Always give `reconcile` an explicit `matchOn`, and review a `--dry-run` before applying.
**僅當計劃擁有整個類型時才使用`reconcile` 。** `reconcile`會刪除計劃未列出的所有該類型的對象，因此僅當計劃是該類型的唯一資料來源時才使用它（並且當您希望刪除的條目被徹底刪除，而不是保留下來時）。如果其他工具或運算子也管理該類型的對象，則建議使用`upsert`並配合顯式的`destroy`操作，以便僅刪除計劃擁有的內容。始終為`reconcile`提供顯式的`matchOn` ，並在應用之前查看`--dry-run` 。
- **Give each re-applied type a stable match key.** Rely on the type’s label property or set an explicit `matchOn`; avoid the by-value fallback for anything you re-apply, since a changed field there creates a duplicate instead of updating. See [Matching](#matching).
**為每個重新套用的類型指定一個穩定的匹配鍵。** 依賴類型的標籤屬性或明確設定`matchOn` ；避免對任何重新套用的內容使用按值回退，因為更改該欄位會建立重複項而不是更新。參見 [匹配](#matching) 。
- **Generate, review, apply.** Treat the plan file as an artifact: render it from templates, commit the rendered version \(or its diff\) for review, then apply.
**生成、審查、應用。** 將計劃檔案視為工件：從範本渲染它，提交渲染後的版本（或其差異）以供審查，然後套用。
- **Use `--dry-run` in pull requests.** Every plan change should pass a `--dry-run` before merging.
**請在拉取請求中使用`--dry-run` 。** 每個計劃變更在合併之前都應該通過`--dry-run` 。
- **Never embed real secrets in committed plans.** Use placeholders that the renderer substitutes from a secrets manager \(Vault, sops, SSM, …\). Plans containing private keys, password hashes, or license tokens should never be checked in unencrypted.
**切勿將真實密鑰嵌入已提交的計劃中。** 使用佔位符，由渲染器從金鑰管理器（Vault、sops、 SSM等）中取代。包含私鑰、密碼雜湊或許可證令牌的計劃絕不應以未加密的形式提交。
- **Keep a tenant’s objects self-contained.** A tenanted object can only reference objects in its own tenant, so each tenant needs its own copy of any configuration its objects point at. See [References and tenants](#references-and-tenants).
**保持租戶對象的獨立性。** 租用戶物件只能引用其自身租戶中的對象，因此每個租戶都需要其物件指向的任何配置的獨立副本。參見[引用和租戶](#references-and-tenants) 。
- **For teardowns, keep the destroy list in creates order.** When a plan does include `destroy` operations, list them parents-first \(the same order as the corresponding upserts/creates\); the reverse pass takes them down children-first. If a destroy fails with `objectIsLinked`, an earlier entry is too far down the tree \(children-first ordering\): re-order so parents come first.
**對於清理操作，請保持銷毀清單按建立順序排列。** 當計劃包含`destroy`操作時，請按父節點優先的順序排列（與對應的插入/建立操作順序相同）；反向操作則按子節點優先的順序排列。如果銷毀操作因`objectIsLinked`而失敗，則說明先前的條目在樹中的位置太靠下（子節點優先的順序）：請重新排序，使父節點排在前面。
