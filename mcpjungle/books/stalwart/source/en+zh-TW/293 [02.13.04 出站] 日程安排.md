# Scheduling｜日程安排

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[mta｜捷運\\\]\\\(&lt;000 目錄.md#c-47&gt;\\\) › \\\[outbound｜出站\\\]\\\(&lt;000 目錄.md#c-52&gt;\\\)

A scheduling strategy defines the policies and behaviour that govern how outbound message deliveries are managed over time. Scheduling strategies control which virtual queue a message uses, how often delivery is retried after a failure, when delayed delivery-status notifications are generated, and when undeliverable messages are expired and bounced to the sender.

 調度策略定義了管理出站訊息傳遞的策略和行為。調度策略控制訊息使用哪個虛擬佇列、失敗後重試傳遞的頻率、何時產生延遲傳遞狀態通知，以及何時使無法傳遞的訊息過期並退回給寄件者。

 Scheduling strategies are defined as MtaDeliverySchedule objects \(found in the WebUI under Settings › MTA › Outbound › Delivery Schedules\) and selected dynamically at runtime via the schedule expression on MtaOutboundStrategy; see Strategies for details.

 調度策略定義為 MtaDeliverySchedule物件（可在 WebUI 的「設定 › MTA › 出站 › 交付計畫」下找到），並在運行時透過 MtaOutboundStrategy  上的排程表達式上的排程\]\([https://stalw.art/docs/mta/outbound/strategy](https://stalw.art/docs/mta/outbound/strategy)\)

 Each scheduling strategy controls the following aspects:

 每種調度策略都控制以下幾個面向：

- **Virtual queue assignment**: determines which virtual queue a message recipient is placed into for delivery.
**虛擬隊列分配**：決定訊息接收者被放入哪一個虛擬隊列進行傳遞。
- **Retry intervals**: specify how frequently the MTA retries delivery after a failed attempt.
**重試間隔**：指定MTA在投遞失敗後重試投遞的頻率。
- **Delay notifications**: control when delayed delivery-status notifications \(DSNs\) are generated and sent to the sender.
**延遲通知**：控制何時產生延遲的交付狀態通知 （DSN）並發送給寄件者。
- **Expiration**: defines how long the system should continue retrying before considering the message undeliverable.
**過期時間**：定義系統在認為訊息無法送達之前應繼續重試多久。
## Queue｜佇列

 Each scheduling strategy must be associated with a virtual queue, which determines where recipients are placed for delivery processing. The queueId field references the MtaVirtualQueue object to use. Different scheduling strategies can reference different queues to isolate message classes.

 每種調度策略都必須關聯一個虛擬佇列 ，該佇列決定收件人在投遞處理過程中被放置在哪個佇列中。 queueId字段引用要使用的MtaVirtualQueue物件。不同的調度策略可以引用不同的佇列來隔離訊息類別。

 Each recipient is evaluated independently and placed into the appropriate queue based on the selected strategy, so local deliveries can be processed separately from remote ones, or high-importance messages can bypass a congested general-purpose queue. The referenced virtual queue must exist before the scheduling strategy can be applied, as queues are not created automatically.

 每個收件人都會被獨立評估，並根據所選策略被放入相應的佇列中，這樣本地郵件和遠端郵件就可以分開處理，或者高優先級郵件可以繞過擁塞的通用佇列。由於佇列不會自動建立，因此必須先存在指定的虛擬佇列，調度策略才能生效。

## Retries｜重試

 When a delivery attempt fails temporarily \(for example because the remote server is unavailable\), the MTA retries delivery later. Retry timing is controlled by the retry field, which is a multi-variant value: the `Default` variant uses the built-in retry schedule, and the `Custom` variant carries a list of `MtaDeliveryScheduleInterval` entries under `intervals`, each with a `duration` field.

 當投遞嘗試暫時失敗時（例如，由於遠端伺服器無法使用）， MTA稍後會重試投遞。重試時間由 retry字段控制，該字段是一個多變量值： `Default`變量使用內建的重試計劃，而`Custom`變量在`intervals`變量使用內建的`MtaDeliveryScheduleInterval`變量在`duration`

 With intervals such as 2 minutes, 5 minutes, 10 minutes, 15 minutes, 30 minutes, 1 hour and 2 hours, delivery is retried 2 minutes after the first failure, 5 minutes after that, and so on. When the list is exhausted, the last duration is reused for all subsequent attempts, until the message is delivered, expires, or exceeds the maximum number of delivery attempts. Retries are scheduled independently for each recipient.

 郵件投遞會以 2 分鐘、5 分鐘、10 分鐘、15 分鐘、30 分鐘、1 小時和 2 小時等間隔重試。首次投遞失敗後，郵件會在 2 分鐘後重試一次，第二次重試後 5 分鐘重試一次，以此類推。當所有重試間隔都用完後，會重複使用最後一次重試的間隔時間，直到郵件成功投遞、過期或達到最大投遞次數限制。每位收件人的重試時間都是獨立安排的。

## Delay notifications｜延遲通知

 Delayed Delivery Status Notifications \(DSNs\) inform the sender that a message has not yet been delivered but is still being retried. These notifications are useful for alerting users to delivery delays before the final expiration.

 延遲投遞狀態通知 \(DSN\) 會告知寄件者郵件尚未送達，但仍在重試發送。這些通知有助於在最終過期前提醒用戶郵件投遞延遲的情況。

 Delay notifications are configured via notify, which accepts the same multi-variant shape as `retry`: the `Default` variant uses the built-in schedule and the `Custom` variant carries an `intervals` list. Durations are measured from the moment the message enters the queue; for example intervals of 1 day and 3 days send a delay DSN one day and three days after queue entry, provided the message is still undelivered.

 延遲通知透過 notify進行配置，其接受與`retry`相同的多變體格式： `Default`變體使用內建調度，而`Custom`變體攜帶一個`intervals`列表。持續時間從訊息進入佇列的那一刻開始計算；例如，1 天和 3 天的間隔分別會在訊息進入佇列一天和三天後發送延遲DSN ，前提是訊息仍未送達。

 Each interval triggers at most one notification. These delay notifications are separate from the final bounce message, which is sent when the message is permanently undeliverable.

 每個時間間隔最多觸發一則通知。這些延遲通知與最終退信不同，最終退信是在郵件永久無法送達時發送的。

## Expiration｜到期日

 Message expiration determines how long the MTA should continue attempting delivery before giving up and returning a bounce DSN to the sender. Expiration is configured via expiry, a multi-variant field with two variants:

 郵件過期時間決定了MTA在放棄投遞並向寄件人返回退信 DSN之前應持續嘗試投遞多長時間。過期時間透過 expiry進行配置，這是一個多變量字段，包含兩個變數：

- `Ttl`: Time-To-Live. The message expires after a fixed duration, regardless of the number of delivery attempts. Carries an `expire` duration in milliseconds \(default 3 days, `259200000`\).
`Ttl` ：生存時間。訊息會在固定時間後過期，與投遞嘗試次數無關。包含一個以毫秒為單位的`expire`持續時間（預設為3天， `259200000` ）。
- `Attempts`: Attempt-based. The message expires after a specified number of failed delivery attempts, regardless of how much time has passed. Carries a `maxAttempts` count \(default 5\).
`Attempts` ：基於嘗試次數。無論經過多少時間，訊息在指定次數的投遞失敗後都會過期。帶有`maxAttempts`計數（預設值為 5）。
TTL-based expiration suits deployments where guaranteed delivery within a fixed time window is important; attempt-based expiration suits environments where retry frequency may vary, but a maximum effort should be enforced.
 基於TTL過期機制適用於在固定時間窗口內保證交付的部署；基於嘗試的過期機制適用於重試頻率可能變化但應強制執行最大努力的環境。

 A schedule that expires messages after 4 days with custom retry intervals:

 一個定時發送的郵件，4天後過期，並可自訂重試間隔：

```json
{
  "name": "local",
  "queueId": "<MtaVirtualQueue id>",
  "retry": {
    "@type": "Custom",
    "intervals": {
      "0": {"duration": 120000},
      "1": {"duration": 300000},
      "2": {"duration": 600000},
      "3": {"duration": 900000},
      "4": {"duration": 1800000},
      "5": {"duration": 3600000},
      "6": {"duration": 7200000}
    }
  },
  "notify": {
    "@type": "Custom",
    "intervals": {
      "0": {"duration": 86400000},
      "1": {"duration": 259200000}
    }
  },
  "expiry": {"@type": "Ttl", "expire": 345600000}
}
```

Values on this page follow the object encoding rules: list and set fields are JSON objects rather than arrays, and durations and sizes are integers.

 本頁上的值遵循 物件編碼規則：列表和集合字段是JSON物件而不是數組，持續時間和大小是整數。

 A schedule that gives up after 15 delivery attempts uses the `Attempts` variant instead:

 若投遞嘗試次數達到 15 次後放棄，則改用`Attempts`變體：

```json
{
  "name": "relay",
  "queueId": "<MtaVirtualQueue id>",
  "retry": {"@type": "Default"},
  "notify": {"@type": "Default"},
  "expiry": {"@type": "Attempts", "maxAttempts": 15}
}
```

## Examples｜範例

### Queues by message type｜按訊息類型排隊

 Different message types \(DSNs, reports, auto-generated notifications, local deliveries, general outbound mail\) can be placed into separate virtual queues. The schedule expression on MtaOutboundStrategy branches on context variables \(`is_local_domain(rcpt_domain)`, `source == 'dsn'`, `source == 'report'`, `source == 'autogenerated'`\) and selects the appropriate scheduling-strategy name. Each referenced MtaDeliverySchedule sets queueId to a different MtaVirtualQueue \(`local`, `dsn`, `report`, `autogen`, `remote`\), and each virtual queue has an appropriate threadsPerNode value.

 不同類型的訊息（DSN、報告、自動產生的通知、本地投遞、一般出站郵件）可以放入不同的虛擬佇列中。 MtaOutboundStrategy上的調度表達式會根據上下文變數 \( `is_local_domain(rcpt_domain)`, `source == 'dsn'`, `source == 'report'`, `source == 'autogenerated'` \) 進行分支，並選擇對應的調度策略名稱。每個引用的 MtaDeliverySchedule都會將 queueId設定為不同的 MtaVirtualQueue \( `local`, `dsn`, `report`, `autogen`, `remote` \)，且每個虛擬佇列有一個對應的`threadsPerNode` 3403 3403 \([https://stalw.art/docs/ref/object/mta-virtual-queue#threadspernode](https://stalw.art/docs/ref/object/mta-virtual-queue#threadspernode)\)

 The schedule expression:

 日程表達式：

```json
{
  "schedule": {
    "match": {
      "0": {"if": "is_local_domain(rcpt_domain)", "then": "'local'"},
      "1": {"if": "source == 'dsn'", "then": "'dsn'"},
      "2": {"if": "source == 'report'", "then": "'report'"},
      "3": {"if": "source == 'autogenerated'", "then": "'autogen'"}
    },
    "else": "'remote'"
  }
}
```

Paired with five MtaVirtualQueue objects \(`local`/1000, `dsn`/50, `report`/10, `autogen`/20, `remote`/1000 threads per node\) and five MtaDeliverySchedule objects whose queueId points at the matching queue.

 與五個 MtaVirtualQueue 物件（ `local` /1000、 `dsn` /50、 `report` /10、 `autogen` /20、 `remote` /100 個物件配對的五個執行詞 queueId指向匹配的隊列。

### Priority-based delivery queues｜基於優先權的配送隊列

 Delivery priority can be driven by the `MT-PRIORITY` SMTP extension. A schedule expression that branches on `priority == 1` and `priority == 3` selects `high-priority`, `low-priority`, or `normal-priority` scheduling strategies. The high-priority strategy uses a short retry interval \(`Custom` variant with a single 1 minute interval\) and a high-concurrency virtual queue; the low-priority strategy throttles retries \(a single 30 minute interval\) and uses a queue with very few threads.

 交付優先順序可由`MT-PRIORITY` SMTP擴充驅動。基於`priority == 1`和`priority == 3`分支的調度表達式會選擇`high-priority`, `low-priority`或`normal-priority`調度策略。高優先權策略使用較短的重試間隔（ `Custom`變體，單次1分鐘間隔）和高並發虛擬佇列；低優先權策略限制重試次數（單次30分鐘間隔）並使用執行緒數極少的佇列。

```json
{
  "schedule": {
    "match": {
      "0": {"if": "priority == 1", "then": "'high-priority'"},
      "1": {"if": "priority == 3", "then": "'low-priority'"}
    },
    "else": "'normal-priority'"
  }
}
```

The `high-priority` MtaDeliverySchedule uses `retry = {"@type": "Custom", "intervals": {"0": {"duration": 60000}}}` \(1 minute\) against a 2000-thread `high-priority` virtual queue; `low-priority` uses `retry = {"@type": "Custom", "intervals": {"0": {"duration": 1800000}}}` \(30 minutes\) against a 2-thread `low-priority` virtual queue; `normal-priority` uses the default schedule against a 100-thread `normal-priority` virtual queue.

`high-priority` MtaDeliverySchedule 使用`retry = {"@type": "Custom", "intervals": {"0": {"duration": 60000}}}` （1 分鐘）針對 2000 個執行緒的`high-priority`虛擬佇列； `low-priority`使用`retry = {"@type": "Custom", "intervals": {"0": {"duration": 1800000}}}` （30 分鐘）針對 2 個執行緒使用`low-priority` 300033 的 23130度`normal-priority`個執行緒的`normal-priority`虛擬隊列。

### VIP client queue｜VIP客戶端佇列

 Messages involving VIP clients can be routed to a dedicated queue. The schedule expression invokes `sql_query` against a lookup store to check whether sender or recipient is listed in a VIP table, and selects a `vip-client` scheduling strategy when it matches. The VIP scheduling strategy targets a high-concurrency queue and uses aggressive retry intervals; the default scheduling strategy targets a smaller queue with the standard retry schedule.

 涉及VIP客戶端的訊息可以路由到專用佇列。調度表達式針對查找儲存呼叫`sql_query`來檢查發件人或收件人是否在VIP表中列出，並在匹配時選擇`vip-client`調度策略。 VIP調度策略針對高並發佇列，採用激進的重試間隔；預設調度策略針對具有標準重試計畫的較小佇列。

 The `?` placeholders below use SQLite or MySQL syntax; on PostgreSQL use `$1`, `$2`, … instead, since the query is passed to the database driver verbatim.

 下面的`?`佔位符使用 SQLite 或 MySQL 語法；在 PostgreSQL 上，請改用`$1`, `$2` , …，因為查詢會原封不動地傳遞給資料庫驅動程式。

```json
{
  "schedule": {
    "match": {
      "0": {"if": "sql_query('my-db', 'SELECT 1 FROM vip_clients WHERE email = ? OR email = ?', [rcpt, sender])", "then": "'vip-client'"}
    },
    "else": "'default'"
  }
}
```

The `vip-client` MtaDeliverySchedule targets a 1000-thread `vip` virtual queue with intervals of 1 minute, 5 minutes and 10 minutes \(`{"0": {"duration": 60000}, "1": {"duration": 300000}, "2": {"duration": 600000}}`\); `default` targets a 100-thread `default` virtual queue with the standard retry schedule.

`vip-client` MtaDeliverySchedule 針對一個 1000 線程的`vip`虛擬隊列，間隔分別為 1 分鐘、5 分鐘和 10 分鐘（ `{"0": {"duration": 60000}, "1": {"duration": 300000}, "2": {"duration": 600000}}` ）； `default`針對一個`default`的標準重試。
