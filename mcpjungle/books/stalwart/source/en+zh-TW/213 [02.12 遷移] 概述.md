# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\)

Moving a populated mail system onto Stalwart involves two distinct problems. The first is mechanical: every account’s data, its mail, calendars, contacts, filters and stored files, has to be copied from the old system into the new one without loss. The second is operational: while that copying is in progress some accounts still live on the old system and others have already moved, yet users expect to keep sending and receiving mail throughout. Stalwart addresses these two problems with two complementary tools, a migration proxy and a migration utility called Vandelay, which together make it possible to migrate from a legacy mail server or an older Stalwart deployment onto the latest Stalwart version without downtime.

 將一個已部署郵件系統的系統移轉到 Stalwart 會遇到兩個截然不同的問題。第一個是技術層面的問題：每個帳戶的數據，包括郵件、日曆、聯絡人、過濾器和儲存的文件，都必須從舊系統無損複製到新系統。第二個是營運層面的問題：在資料複製過程中，部分帳戶仍然保留在舊系統上，而其他帳戶已經遷移完畢，但用戶仍希望能夠繼續收發郵件。 Stalwart 透過兩個互補的工具——遷移代理和名為 Vandelay 的遷移實用程式——來解決這兩個問題。這兩個工具協同工作，使得從舊版郵件伺服器或舊版 Stalwart 部署遷移到最新版 Stalwart 成為可能，且無需停機。

## Migration proxy｜遷移代理

 The [migration proxy](https://stalw.art/docs/proxy) is a multi-protocol mail proxy that sits in front of one or more mail backends and decides, per account, which backend a given connection belongs to. It terminates IMAP, POP3, ManageSieve, SMTP submission, SMTP and LMTP, and HTTP \(JMAP\) sessions, identifies the account behind each connection from the credentials the client already presents, and bridges the session to whichever backend currently holds that account’s data. Because the routing decision is made from existing credentials, no client reconfiguration is needed: users keep the same server name, ports and passwords while the proxy quietly sends them to the right system.

[遷移代理](https://stalw.art/docs/proxy)是一個多協定郵件代理，它位於一個或多個郵件後端伺服器的前端，並根據每個帳戶的情況，決定給定連接屬於哪個後端伺服器。它會終止IMAP, POP3 、ManageSieve、 SMTP submission、 SMTP和LMTP以及HTTP \( JMAP \) 會話，根據客戶端已提供的憑證已識別每個橋接器的憑證，並將該帳戶在本機後面識別。由於路由決策是基於現有憑證做出的，因此無需重新配置用戶端：使用者保留相同的伺服器名稱、連接埠和密碼，而代理伺服器會靜默地將它們傳送到正確的系統。

 This is what keeps a migration invisible. A single hostname continues to answer on the familiar ports, and a mapping table records which backend each account lives on. As accounts are moved, their entries are flipped from the old destination to the new one, and the affected clients follow without noticing. The proxy speaks to legacy backends using the conventions they expect and understands Stalwart’s own OAuth tokens and JMAP traffic, so it can front a mix of a legacy server and Stalwart, or an old and a new Stalwart, at the same time.

 這正是實現無縫遷移的關鍵。同一個主機名稱繼續在熟悉的連接埠上回應請求，映射表記錄每個帳戶所在的後端。帳戶遷移時，其項目會從舊目標伺服器切換到新目標伺服器，受影響的用戶端會在不知不覺中完成遷移。代理伺服器使用舊後端伺服器期望的約定與其通信，並能理解 Stalwart 自身的 OAuth 令牌和JMAP流量，因此它可以同時處理舊伺服器和 Stalwart 的混合連接，或同時處理新舊 Stalwart 的混合連接。

## Migration utility｜遷移工具

[Vandelay](https://stalw.art/docs/import-export) is a one-shot account-migration utility, the JMAP analogue of `imapsync` generalised to every data type a JMAP account can hold. It performs the actual copying of an account in two independent halves joined by a local SQLite file called the archive. The import half reads a source account, over JMAP, IMAP, CalDAV, CardDAV, WebDAV, ManageSieve, a local Maildir, a Google Takeout export, or Microsoft Exchange, and records its complete contents in the archive. The export half reads that archive and reconciles its contents onto a target JMAP server such as Stalwart. Both halves are convergent, so an interrupted or repeated run resumes and captures only what has changed, which is what lets an account be moved incrementally rather than in a single fragile operation.

[Vandelay](https://stalw.art/docs/import-export)是一個一次性帳戶遷移工具，它是`imapsync`的JMAP版本，但支援JMAP帳戶可能包含的所有資料類型。它將帳戶的實際複製過程分為兩個獨立的部分，並透過一個名為「歸檔」的本機 SQLite 檔案連接起來。匯入部分讀取來源帳戶，來源帳戶可以透過JMAP, IMAP 、CalDAV、CardDAV、WebDAV、ManageSieve、本地 Maildir、Google Takeout 匯出或 Microsoft Exchange 等方式獲取，並將全部內容記錄到歸檔檔案中。匯出部分讀取該歸檔文件，並將其內容同步到目標JMAP伺服器（例如 Stalwart）。兩個部分是同步的，因此即使中斷或重複運行，也能恢復並僅捕獲已更改的內容，這使得帳戶可以增量遷移，而不是一次性完成。

## Zero-downtime migration｜零停機遷移

 The two tools divide the work cleanly. Vandelay moves the data while the proxy moves the traffic. A migration proceeds account by account: the proxy keeps a given account pointed at the old backend while Vandelay imports its data and exports it onto the new Stalwart server, and only once that account’s data is fully in place is its proxy mapping flipped to the new backend. Because Vandelay’s import is convergent, a final catch-up run just before the cut-over captures anything that arrived during the copy, so the switch is seamless and no mail is lost. Repeating this for every account migrates an entire deployment, whether from a legacy mail server or from an earlier Stalwart version, with users experiencing no interruption to service.

 這兩個工具將工作清楚地劃分開來。 Vandelay 負責遷移數據，而代理負責遷移流量。遷移過程逐一帳戶進行：代理程式會將特定帳戶指向舊後端，而 Vandelay 則匯入該帳戶的資料並將其匯出到新的 Stalwart 伺服器。只有當該帳戶的資料完全就位後，才會將其代理映射切換到新的後端。由於 Vandelay 的導入是收斂式的，因此在切換之前會進行一次最終的追趕運行，以捕獲複製過程中到達的所有內容，從而確保切換過程無縫銜接，不會丟失任何郵件。對每個帳戶重複此操作，即可遷移整個部署，無論其來源是舊版郵件伺服器還是早期版本的 Stalwart，使用者都不會感受到任何服務中斷。

## Step-by-step guidance｜逐步指導

 This page describes how the proxy and Vandelay fit together. The [Migration Guide](https://stalw.art/docs/guide) walks through the procedure in full, with the concrete steps for staging the proxy, capturing and restoring each account with Vandelay, performing the catch-up run, and cutting accounts over to the new backend one at a time for a zero-downtime migration.

 本頁面介紹了代理伺服器和 Vandelay 如何協同工作。 [遷移指南](https://stalw.art/docs/guide)詳細講解了整個遷移過程，包括代理伺服器的部署、使用 Vandelay 捕獲和恢復每個帳戶、執行追趕運行，以及將帳戶逐個切換到新的後端，從而實現零停機遷移的具體步驟。
