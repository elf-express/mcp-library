# SMTP and submission｜SMTP和提交

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[routing｜路由\\\]\\\(&lt;000 目錄.md#c-46&gt;\\\)

The proxy handles SMTP in two distinct modes. Authenticated message submission is treated like the other interactive protocols: the proxy terminates the session, identifies the account from the authentication, and routes to the resolved backend. Mail transfer between servers \(the SMTP and LMTP protocols used for incoming mail and local delivery\) is instead bridged as an opaque stream to a single fixed destination, because such sessions are not authenticated and carry no account identity to route on.

 代理以兩種不同的模式處理SMTP 。經過驗證的訊息提交與其他互動式協定的處理方式相同：代理程式終止會話，根據身分驗證識別帳戶，並將請求路由到已解析的後端。伺服器之間的郵件傳輸（用於接收郵件和本地投遞的SMTP和LMTP協定）則以不透明流的形式橋接到單一固定目標，因為此類會話未經身份驗證，且不包含任何可用於路由的帳戶識別資訊。

## Submission｜提交

 A submission listener serves authenticated clients sending outbound mail, typically on port 587 with STARTTLS or port 465 with implicit TLS. On connection the proxy sends a `220` greeting naming the configured hostname, and answers `EHLO`/`HELO`, `NOOP`, `RSET`, `STARTTLS` and `QUIT` itself during pre-authentication. The `EHLO` response advertises the keywords from `[capabilities.submission]` together with the available `AUTH` mechanisms, and `STARTTLS` on a STARTTLS listener before the upgrade.

 提交偵聽器為經過驗證的用戶端發送出站郵件提供服務，通常在帶有 STARTTLS 的連接埠 587 上或具有隱式 TLS 的連接埠 465 上。連線時，代理程式會傳送一個 `220` 問候語，命名配置的主機名，並在預先驗證期間自行應答 `EHLO`/`HELO`, `NOOP`, `RSET`, `STARTTLS` 和 `QUIT`。 `EHLO` 回應在升級之前在 STARTTLS 偵聽器上通告來自 `[capabilities.submission]` 的關鍵字以及可用的 `AUTH` 機制和 `STARTTLS`。

 Authentication uses the ESMTP `AUTH` command with a SASL mechanism, one of `PLAIN`, `LOGIN`, `OAUTHBEARER` or `XOAUTH2`, the initial response supplied inline or after a `334` continuation. `AUTH LOGIN` is advertised on the `EHLO` response whenever `LOGIN` appears in the `sasl` list and cleartext authentication is permitted on the connection, which keeps clients that only implement `LOGIN`, such as Outlook 2019 for macOS, working through the proxy. The proxy sends the base64 `Username:` and `Password:` challenges itself, accepts the base64 username as an initial response when the client sends one, honours `*` as an abort, and reconstructs the exchange as a `PLAIN` challenge, so the backend leg only ever sees `PLAIN`. Cleartext `PLAIN` and `LOGIN` are gated on transport security and refused with an encryption-required response until the connection is secured, unless `allow_plain_auth_without_tls` is set. The routing identifier is extracted from the credentials as described under Routing.

 身份驗證使用 ESMTP `AUTH` 帶有命令的 SASL 機制，其中之一 `PLAIN`, `LOGIN`, `OAUTHBEARER` 或者 `XOAUTH2`初始回應以內聯方式或在之後提供 `334` 續。 `AUTH LOGIN` 在以下平台刊登廣告： `EHLO` 回應 `LOGIN` 出現在 `sasl` 連線上允許清單和明文身份驗證，這使得僅實現清單身份驗證的用戶端能夠正常運作。 `LOGIN`例如 macOS 版 Outlook 2019，它透過代理伺服器運作。代理伺服器發送 base64 編碼的資料。 `Username:` 和 `Password:` 自我挑戰，接受客戶端發送的 base64 使用者名稱作為初始回應，並予以尊重 `*` 作為中止操作，並將交換過程重構為 `PLAIN` 挑戰，因此後端腿只會看到 `PLAIN`明文 `PLAIN` 和 `LOGIN` 除非連線安全性得到保障，否則連線會受到傳輸安全限制，並被拒絕，且需要加密才能連線。 `allow_plain_auth_without_tls` 已設定。路由標識符是從憑證中提取的，具體方法請參閱\[路由\]部分。\([https://stalw.art/docs/migration/proxy/routing/](https://stalw.art/docs/migration/proxy/routing/)\).

 Having resolved the destination, the proxy connects to its submission endpoint, reads the `220` greeting, sends its own `EHLO`, and on a STARTTLS endpoint negotiates the upgrade and re-issues `EHLO`. When the destination uses `XCLIENT` forwarding and the backend advertises `XCLIENT`, the proxy issues an `XCLIENT` command, restricted to the attributes the backend announced support for, carrying the client address and port, the destination address and port, the client’s HELO name, the protocol and the transport security; it then re-issues `EHLO` so the session reflects the forwarded identity. Finally it replays the client’s `AUTH` command, relays the result, and bridges the session, after which the client and backend exchange the `MAIL`, `RCPT` and `DATA` phases directly.

 解析出目標位址後，代理連接到其提交端點，讀取`220`問候語，發送自身的`EHLO`問候語，並在STARTTLS端點上協商升級並重新發出`EHLO`問候語。當目標使用`XCLIENT`轉發且後端通告`XCLIENT`轉發時，代理髮出`XCLIENT`命令，該命令僅包含後端通告支援的屬性，並攜帶客戶端位址和連接埠、目標位址和連接埠、客戶端的HELO 、協定和客戶端位址和連接埠、目標位址和連接埠、客戶端的`EHLO` 、協定和通訊關係。最後，它重播客戶端的`AUTH`指令，轉送結果，並橋接會話，之後客戶端和後端直接交換`MAIL`, `RCPT`和`DATA`階段。

## SMTP and LMTP pass-through｜SMTP和LMTP直通

 An `smtp` or `lmtp` listener handles unauthenticated mail transfer: incoming mail from other servers on port 25, or local delivery over LMTP. These sessions have no login to identify an account, so they are not routed per account. Instead the entire session is bridged verbatim to the destination named by `routing.smtp_passthrough_destination`, with the proxy acting as a transparent relay that does not interpret the SMTP dialogue.

`smtp`或`lmtp`監聽器處理未經驗證的郵件傳輸：來自其他伺服器的 25 連接埠郵件，或透過LMTP進行的本地投遞。這些會話沒有登入資訊來識別帳戶，因此不會按帳戶進行路由。相反，整個會話會原封不動地橋接到`routing.smtp_passthrough_destination`指定的目標位址，代理伺服器充當透明中繼，不解釋SMTP對話。

```toml
[routing]
default_destination = "legacy"
smtp_passthrough_destination = "stalwart"
```

Because the proxy does not terminate the protocol in this mode, it cannot intercept a STARTTLS command, and so pass-through listeners may use only `plain` or `implicit` transport, never `starttls`; the STARTTLS combination is rejected at startup. The pass-through destination must declare the `smtp` protocol, and additionally the `lmtp` protocol if any LMTP listener is configured; both requirements are checked at startup. Client identity is still conveyed to the backend according to the destination’s `forwarding` setting, so a PROXY protocol header can preserve the original sending server’s address for the backend’s own policy checks.

 由於代理在此模式下不會終止協議，因此無法攔截STARTTLS命令，所以直通監聽器只能使用`plain`或`implicit`傳輸協議，而不能使用`starttls` ； STARTTLS組合在啟動時會被拒絕。直通目標必須聲明`smtp`協議，如果配置了任何LMTP監聽器，則還必須聲明`lmtp`協議；這兩個要求都會在啟動時進行檢查。客戶端身分仍會根據目標的`forwarding`設定傳遞給後端，因此PROXY協定頭可以保留原始發送伺服器的位址，以供後端進行策略檢查。

 The pass-through destination is configured like any other destination; only its role differs, in that it receives every pass-through session rather than being selected by a mapping lookup.

 直通目的地配置方式與其他 目的地相同；只是它的角色不同，因為它接收每個直通會話，而不是透過映射查找來選擇。
