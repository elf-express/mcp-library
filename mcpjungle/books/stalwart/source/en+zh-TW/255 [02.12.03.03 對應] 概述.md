# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[mappings｜對應\\\]\\\(&lt;000 目錄.md#c-45&gt;\\\)

A mapping associates an account identifier with the destination that currently holds that account’s data. Mappings are the heart of the proxy’s routing: when a client authenticates, the proxy derives an identifier from the credentials, looks it up in the mapping store, and sends the session to whichever destination the lookup returns. Accounts without an explicit mapping fall through to the default destination, which makes incremental migration straightforward. At the start every account resolves to the default \(the old system\), and each account is given an explicit mapping to the new destination as its mailbox is moved.

 對應將帳戶識別碼與目前儲存該帳戶資料的目標位置關聯起來。映射是代理路由的核心：當客戶端進行身份驗證時，代理會根據憑證派生出一個標識符，在映射儲存中尋找該標識符，並將會話傳送到查找結果傳回的目標位置。沒有明確映射的帳戶將預設發送到目標位置，這使得增量遷移變得簡單。初始階段，每個帳戶都解析到預設位置（舊系統），隨著郵箱的遷移，每個帳戶都會被賦予指向新目標位置的明確對應。

 The mapping store is selected with the `source` key under `[mapping]`, and may be a flat file, a Redis database, or a SQL database. This page describes the behavior common to all three: how identifiers are normalized, how results are cached, and how the default destination and master users are handled. The source-specific pages cover the configuration of each store.

 映射儲存透過`[mapping]`下的`source`鍵選擇，可以是平面檔案\([https://stalw.art/docs/migration/proxy/mappings/file](https://stalw.art/docs/migration/proxy/mappings/file)\) 、Redis 資料庫\([https://stalw.art/docs/migration/proxy/mappings/redis\)或SQL資料庫。本頁描述了\(https://stalw.art/docs/migration/proxy/mappings/sql\)三種儲存方式的共同行為：標識符的規範化方式、結果的快取方式以及預設目標使用者和主使用者的處理方式。特定於資料來源的頁面介紹了每種儲存方式的配置。](https://stalw.art/docs/migration/proxy/mappings/redis%2529%2525E6%252588%252596SQL%2525E8%2525B3%252587%2525E6%252596%252599%2525E5%2525BA%2525AB%2525E3%252580%252582%2525E6%25259C%2525AC%2525E9%2525A0%252581%2525E6%25258F%25258F%2525E8%2525BF%2525B0%2525E4%2525BA%252586%2528https://stalw.art/docs/migration/proxy/mappings/sql%2529%2525E4%2525B8%252589%2525E7%2525A8%2525AE%2525E5%252584%2525B2%2525E5%2525AD%252598%2525E6%252596%2525B9%2525E5%2525BC%25258F%2525E7%25259A%252584%2525E5%252585%2525B1%2525E5%252590%25258C%2525E8%2525A1%25258C%2525E7%252582%2525BA%2525EF%2525BC%25259A%2525E6%2525A8%252599%2525E8%2525AD%252598%2525E7%2525AC%2525A6%2525E7%25259A%252584%2525E8%2525A6%25258F%2525E7%2525AF%252584%2525E5%25258C%252596%2525E6%252596%2525B9%2525E5%2525BC%25258F%2525E3%252580%252581%2525E7%2525B5%252590%2525E6%25259E%25259C%2525E7%25259A%252584%2525E5%2525BF%2525AB%2525E5%25258F%252596%2525E6%252596%2525B9%2525E5%2525BC%25258F%2525E4%2525BB%2525A5%2525E5%25258F%25258A%2525E9%2525A0%252590%2525E8%2525A8%2525AD%2525E7%25259B%2525AE%2525E6%2525A8%252599%2525E4%2525BD%2525BF%2525E7%252594%2525A8%2525E8%252580%252585%2525E5%252592%25258C%2525E4%2525B8%2525BB%2525E4%2525BD%2525BF%2525E7%252594%2525A8%2525E8%252580%252585%2525E7%25259A%252584%2525E8%252599%252595%2525E7%252590%252586%2525E6%252596%2525B9%2525E5%2525BC%25258F%2525E3%252580%252582%2525E7%252589%2525B9%2525E5%2525AE%25259A%2525E6%252596%2525BC%2525E8%2525B3%252587%2525E6%252596%252599%2525E4%2525BE%252586%2525E6%2525BA%252590%2525E7%25259A%252584%2525E9%2525A0%252581%2525E9%25259D%2525A2%2525E4%2525BB%25258B%2525E7%2525B4%2525B9%2525E4%2525BA%252586%2525E6%2525AF%25258F%2525E7%2525A8%2525AE%2525E5%252584%2525B2%2525E5%2525AD%252598%2525E6%252596%2525B9%2525E5%2525BC%25258F%2525E7%25259A%252584%2525E9%252585%2 ## The mapping table｜映射表

 Configuration of the store lives under `[mapping]`, and the chosen source’s own section provides its connection details:

 商店的配置位於`[mapping]`下，所選來源的自身部分提供了其連接詳細資訊：

```toml
[mapping]
source = "file"
normalize = "lowercase"
negative_ttl = "30s"
positive_ttl = "10m"

[mapping.file]
path = "/etc/proxy/mappings.tsv"
```

The general keys under `[mapping]` are:

`[mapping]`下的通用鍵如下：

| Key 鍵 | Default 預設值 | Description 描述 |
| --- | --- | --- |
| `source` | required 必填 | `file`, `redis` or `sql`. `file`, `redis`或`sql` 。 |
| `normalize` | `none` | Identifier normalization applied before lookup: `none` or `lowercase`. 尋找前應用標識符規範化： `none`或`lowercase` 。 |
| `positive_ttl` | `600s` | How long a resolved mapping is cached. 已解析映射的快取時間。 |
| `negative_ttl` | `30s` | How long the absence of a mapping \(a fall-through to default\) is cached. 映射缺失（回退到預設值）的快取時間。 |
| `cache_max_entries` | `1000000` | Maximum number of cached entries. 快取條目的最大數量。 |
| `lookup_timeout` | `5s` | Time limit for a single store lookup. 單次店鋪查詢的時間限制。 |

The destination named by `routing.default_destination` is where any account without an explicit mapping is sent, and is configured under `[routing]` rather than `[mapping]`:

`routing.default_destination`指定的目的地是所有沒有明確映射的帳戶的發送目的地，並且是在`[routing]`下配置的，而不是在`[mapping]`下配置的：

```toml
[routing]
default_destination = "legacy"
```

## Identifier normalization｜標識符規範化

 E-mail addresses and login names are frequently presented with inconsistent casing by different clients. Setting `normalize = "lowercase"` lowercases every identifier before it is looked up and before it is stored, so that `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` and `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` resolve to the same entry. With the default of `none`, identifiers are matched exactly as presented. Lowercase normalization is recommended for e-mail-addressed accounts; the normalization choice must be consistent with how identifiers are written into the store.

 不同用戶端經常使用不一致的大小寫形式顯示電子郵件地址和登入名稱。設定`normalize = "lowercase"`會在尋找和儲存標識符之前將其全部轉換為小寫，以確保`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`和`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`指向同一個條目。使用預設值`none`時，標識符將按原樣匹配。建議對電子郵件地址帳戶使用小寫規範化；規範化方式必須與識別碼寫入儲存的方式保持一致。

## Caching｜快取

 Lookups are served from an in-memory cache so that the backing store is consulted only on the first connection for an account and then at most once per cache lifetime thereafter. This keeps the store off the hot path for established users and is what makes the proxy efficient as a cache-locality router. Three kinds of result are cached with different lifetimes:

 查詢結果來自記憶體緩存，因此後端儲存僅在帳戶首次連接時訪問，之後在快取生命週期內最多訪問一次。這避免了後端儲存成為舊用戶存取的熱點路徑，也正是代理程式作為快取本地化路由器高效運作的原因。快取結果分為三種類型，每種類型的快取生命週期各不相同：

- A **resolved** mapping is held for `positive_ttl`. This is the steady-state case for an account that has an explicit destination.
`positive_ttl`已建立**已解析**映射。這是具有明確目標的帳戶的穩定狀態。
- A **fall-through** to the default destination is held for `negative_ttl`, which is shorter by default so that newly added mappings take effect quickly. When an account is migrated and given an explicit mapping, existing clients pick up the change within this window.
對於`negative_ttl` ，會保留一個預設目標位址的**回退**機制，該機制預設時間較短，以便新新增的映射能夠快速生效。當帳戶遷移並被賦予明確的對應時，現有用戶端會在該時間視窗內套用變更。
- A **transient** result, produced when the store cannot be reached or the lookup times out, is held for only a few seconds. The connection is routed to the default destination so that service is not interrupted, and the short lifetime ensures the store is retried promptly once it recovers.
當無法存取儲存庫或尋找逾時時，會產生一個**臨時**結果，該結果僅保留幾秒鐘。連線會被路由到預設目標，以確保服務不會中斷，而短暫的生命週期則保證了儲存庫恢復後會立即重試。
The `cache_max_entries` cap bounds memory use; once reached, the cache evicts entries according to its usage policy. The cache can be inspected and invalidated through the management API, which is the mechanism for forcing an account to be re-resolved immediately rather than waiting for its entry to expire.
`cache_max_entries`限制了記憶體使用量；一旦達到上限，快取將根據其使用策略驅逐條目。可以透過 管理API來檢查和使快取失效，該機制可以強制立即重新解析帳戶，而不是等待其條目過期。

 If a lookup returns a destination that is not declared in the configuration, the proxy logs a warning and routes the connection to the default destination rather than to the unknown name, so that a stale or mistyped store entry cannot send traffic to a non-existent backend.

 如果尋找傳回的目標未在設定中聲明，代理程式會記錄警告並將連線路由到預設目標而不是未知名稱，這樣，過時的或拼字錯誤的儲存條目就不會將流量傳送到不存在的後端。

## Master users｜進階用戶

 Legacy systems often allow an administrator to log in to another user’s mailbox by appending a separator and the administrator’s own credentials to the login name, a convention known as a master user. The proxy understands this so that the routing identifier is derived from the mailbox being accessed rather than from the combined login string. The `master_user_separators` key under `[routing]` lists the separators to recognize; the default is a single `%`.

 舊系統通常允許管理員透過在登入名稱後附加分隔符號和管理員自己的憑證來登入其他使用者的郵箱，這種約定稱為主使用者。代理程式了解這一點，因此路由標識符是從正在存取的郵箱而不是從組合的登入字串派生的。 `[routing]`下的`master_user_separators`鍵列出了要識別的分隔符號；預設為單一`%`。

```toml
[routing]
default_destination = "legacy"
master_user_separators = ["%", "*"]
```

When a login name such as `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%admin` is presented, the proxy splits on the first occurrence of any configured separator and uses the left-hand portion, `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`, as the routing identifier, so the session is routed to the mailbox owner’s destination. The full login string, including the master-user suffix, is still forwarded to the backend unchanged for authentication.

 當輸入類似`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)%admin`的登入名稱時，代理伺服器會根據首次出現的已配置分隔符號進行分割，並將左側部分`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)`用作路由標識符，從而將會話路由到郵箱所有者的目標位址。完整的登入字串（包括主用戶後綴）仍會原封不動地轉送到後端進行身份驗證。
