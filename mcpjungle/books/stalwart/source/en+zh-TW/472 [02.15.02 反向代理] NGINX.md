# NGINX

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[server｜伺服器\\\]\\\(&lt;000 目錄.md#c-62&gt;\\\) › \\\[reverse proxy｜反向代理\\\]\\\(&lt;000 目錄.md#c-64&gt;\\\)

[NGINX](https://nginx.org/) is a web server that also functions as a reverse proxy, load balancer, and HTTP cache. The `stream` module extends it with TCP / UDP proxying, which is what Stalwart needs for the mail ports.

[NGINX](https://nginx.org/) 是一個 Web 伺服器，也充當反向代理、負載平衡器和 HTTP 快取。 `stream` 模組透過 TCP / UDP 代理對其進行了擴展，這正是 Stalwart 郵件端口所需的。

 Stalwart can sit behind NGINX for both HTTP and mail traffic. The example below uses TCP-passthrough on every port, so NGINX hands the TLS connection to Stalwart untouched and the original client IP is preserved through the Proxy Protocol. HTTP-upstream patterns \(NGINX terminating TLS for the WebUI and forwarding plain HTTP to Stalwart’s port `8080`\) are also supported and produce identical OAuth, OIDC, and JMAP discovery responses; see How discovery URLs are composed for the full model and set the STALWART\_PUBLIC\_URL variable to the URL clients reach NGINX on whenever it differs from `https://<defaultHostname>` on port `443`.

 Stalwart 可以位於NGINX之後，用於HTTP和郵件流量。下面的範例在NGINX連接埠上使用TCP -passthrough，因此NGINX將TLS連接原封不動地傳遞給 Stalwart，並且原始客戶端IP透過 代理協定. HTTP -upstream TLS並將純文字HTTP轉送到 Stalwart 的連接埠`8080` ）得以保留，並且產生相同的 OAuth、 OIDC和JMAP發現回應；有關完整模型，請參閱 如何組成發現 URL \[ `STALWART_PUBLIC_URL` \([https://stalw.art/docs/configuration/environment-variables#public-urls\)變數設定為URL客戶端在連接埠\`https://](https://stalw.art/docs/configuration/environment-variables#public-urls%2529%2525E8%2525AE%25258A%2525E6%252595%2525B8%2525E8%2525A8%2525AD%2525E5%2525AE%25259A%2525E7%252582%2525BAURL%2525E5%2525AE%2525A2%2525E6%252588%2525B6%2525E7%2525AB%2525AF%2525E5%25259C%2525A8%2525E9%252580%2525A3%2525E6%25258E%2525A5%2525E5%25259F%2525A0%252560https://)<defaulthostname>` `443\`同時存取NGINX 。

 Stalwart accepts the Proxy Protocol header when the source address is listed in proxyTrustedNetworks on the SystemSettings singleton \(found in the WebUI under Settings › Network › Services, Settings › Network › General\) or in overrideProxyTrustedNetworks on the matching NetworkListener.

 當來源位址列於 proxyTrustedNetworks的 SystemSettings單例（可在 WebUI 的「設定 › 網路 › 服務」或「設定 › 網路 › 常規」中找到）或列於符合\([https://stalw.art/docs/ref/object/network-listener#overrideproxytrustednetworks](https://stalw.art/docs/ref/object/network-listener#overrideproxytrustednetworks)\) \[ `overrideProxyTrustedNetworks` \([https://stalw.art/docs/ref/object/network-listener\)時，Stalwart](https://stalw.art/docs/ref/object/network-listener%2529%2525E6%252599%252582%2525EF%2525BC%25258CStalwart) 接受代理協議標頭。

## Configuration｜配置

 NGINX must be built with `--with-stream` for TCP proxying to be available.

 NGINX必須與`--with-stream`一起構建， TCP代理功能才能可用。

```title=&amp;quot;/etc/nginx/nginx.conf&amp;quot;
# Load the required modules
load_module modules/ngx_stream_module.so;

events {
    worker_connections 1024;
}

# Stream configuration
stream {
# Proxy SMTP
    server {
        listen 25;
        proxy_pass 127.0.0.1:10025;
        proxy_protocol on;
    }

# Proxy IMAPS
    server {
        listen 993;
        proxy_pass 127.0.0.1:10993;
        proxy_protocol on;
    }

# Proxy SMTPS
    server {
        listen 465;
        proxy_pass 127.0.0.1:10465;
        proxy_protocol on;
    }

# Proxy HTTPS
    server {
        listen 443;
        proxy_pass 127.0.0.1:10443;
        proxy_protocol on;
    }
}
```

The `proxy_protocol on` directive emits a Proxy Protocol header toward Stalwart on every forwarded connection. The `proxy_protocol` flag is intentionally absent from each `listen` line: that flag tells NGINX to *expect* an incoming Proxy Protocol header from the client, which mail and HTTP clients do not send. Add it only when another Proxy-Protocol-aware proxy sits in front of NGINX.

`proxy_protocol on` 指令在每個轉送的連線上向 Stalwart 發出代理協定標頭。每個 `listen` 行中故意不存在 `proxy_protocol` 標誌：此標誌告訴 NGINX *期望*來自客戶端的傳入代理協議標頭，而郵件和 HTTP 用戶端不會發送該標頭。僅當另一個支援代理協定的代理程式位於 NGINX 前面時才新增它。
