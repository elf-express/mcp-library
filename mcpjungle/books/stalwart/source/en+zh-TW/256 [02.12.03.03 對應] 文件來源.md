# File source｜文件來源

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[proxy｜代理人\\\]\\\(&lt;000 目錄.md#c-42&gt;\\\) › \\\[mappings｜對應\\\]\\\(&lt;000 目錄.md#c-45&gt;\\\)

The file source reads mappings from a plain text file on the local filesystem. It is the simplest store to operate, has no external dependencies, and is well suited to deployments where the set of mappings is managed by configuration management or generated by a migration script. The file is loaded into memory at startup and can be reloaded at runtime, so lookups never touch the disk on the hot path.

 檔案來源從本機檔案系統上的純文字檔案中讀取對應。它是操作最簡單的儲存方式，沒有外部依賴項，非常適合映射集由組態管理或由遷移腳本產生的部署場景。該檔案在啟動時加載到記憶體中，並且可以在運行時重新加載，因此查找操作永遠不會存取熱路徑上的磁碟。

```toml
[mapping]
source = "file"
normalize = "lowercase"

[mapping.file]
path = "/etc/proxy/mappings.tsv"
```

The only key is `path`, the location of the mapping file.

 唯一的關鍵是`path` ，即映射檔案的位置。

## File format｜文件格式

 Each line maps one identifier to one destination, separated by whitespace \(a tab or spaces\). Blank lines and lines beginning with `#` are ignored, so the file can be commented. The destination on each line must be the name of a declared destination; a line referencing an unknown destination causes the proxy to refuse to start, which catches typos before they can affect routing.

 每行將一個標識符對應到一個目標位址，位址之間以空格（製表符或空格）分隔。空白行和以`#`開頭的行會被忽略，因此可以對檔案進行註解。每行的目標位址必須是已宣告的目標位址名稱；如果某行指向未知目標位址，代理程式將拒絕啟動，這樣可以在拼字錯誤影響路由之前將其擷取。

```
# identifier            destination
[email protected]    legacy
[email protected]       stalwart
[email protected]        stalwart
```

Identifiers are stored after the configured normalization is applied, so with `normalize = "lowercase"` the keys are lowercased as the file is read; the identifiers written in the file should match the normalization in use.

 標識符是在應用配置的規範化之後存儲的，因此對於`normalize = "lowercase"` ，讀取文件時鍵會轉換為小寫；寫入文件的標識符應與正在使用的規範化相匹配。

## Runtime updates｜運行時更新

 The file source is writable, which means the management API can add and remove mappings as well as read them. When a mapping is changed through the API, the proxy rewrites the file atomically by writing to a temporary file and renaming it into place, so the file on disk always remains a complete and consistent snapshot. Entries are written sorted, one per line, separated by a tab.

 檔案來源是可寫的，這意味著管理API可以新增和刪除映射，也可以讀取它們。當透過API更改映射時，代理會以原子方式重寫文件，方法是寫入一個臨時文件並將其重新命名到原始位置，從而確保磁碟上的文件始終保持完整一致的快照。條目按排序寫入，每行一個，並用製表符分隔。

 The file can also be edited directly and then reloaded without restarting the proxy, by issuing a `POST /mappings/reload` request to the management API. A reload re-reads the file from disk and validates every destination, replacing the in-memory table only if the new file is valid; a file with an unknown destination is rejected and the previous table is kept. This makes bulk updates safe: a migration tool can regenerate the file and trigger a reload, and a malformed regeneration will not take the proxy out of service. Note that a reload replaces the table wholesale, so the cache may still hold previously resolved entries until they expire or are invalidated.

 也可以直接編輯該文件，然後透過向管理伺服器API發送`POST /mappings/reload`請求來重新加載，而無需重啟代理。重新載入會從磁碟重新讀取檔案並驗證每個目標位置，僅當新檔案有效時才替換記憶體中的表；目標位置未知的檔案將被拒絕，並保留先前的表。這使得批量更新安全可靠：遷移工具可以重新生成文件並觸發重新加載，即使重新生成的文件格式錯誤，也不會導致代理停止服務。請注意，重新載入會完全替換表，因此快取可能仍然會保留先前已解析的條目，直到它們過期或失效。
