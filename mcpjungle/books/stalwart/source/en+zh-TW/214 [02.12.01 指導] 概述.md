# Overview｜概述

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[migration｜遷移\\\]\\\(&lt;000 目錄.md#c-37&gt;\\\) › \\\[guide｜指導\\\]\\\(&lt;000 目錄.md#c-38&gt;\\\)

This guide describes how to migrate a running, self-hosted mail server to the latest Stalwart release. It covers two kinds of source. The first is an older Stalwart deployment, of version 0.15 or below: the releases that followed 0.15 introduced extensive changes to the configuration model, the storage layout and the administration interfaces, which makes an in-place upgrade across that boundary impractical for a populated server. The second is an on-premise stack built on Dovecot and Postfix, which is the basis of many self-hosted systems including Mail-in-a-Box, mailcow and other Docker-based distributions. In both cases the migration runs the existing server, referred to throughout as the source, and a new Stalwart deployment side by side, and moves accounts from one to the other gradually, so that the change can be verified account by account and reversed at any point before it is finalized.

 本指南說明如何將正在執行的自託管郵件伺服器遷移到最新的 Stalwart 版本。它涵蓋兩種類型的來源伺服器。第一種是較舊的 Stalwart 部署，版本為0.15或更低：後續版本0.15對配置模型、儲存佈局和管理介面進行了大量更改，因此對於已部署郵件的伺服器而言，直接升級是不切實際的。第二種是基於 Dovecot 和 Postfix 建置的本機部署環境，這是許多自架系統（包括 Mail-in-a-Box、mailcow 和其他基於 Docker 的發行版）的基礎。在這兩種情況下，遷移過程都會同時執行現有伺服器（以下簡稱來源伺服器）和新的 Stalwart 部署，並將帳戶逐步從來源伺服器遷移到新部署，以便在最終完成遷移之前，可以逐個帳戶驗證變更並隨時撤銷。

 The guide applies to any source that can be placed behind the proxy, that is, an on-premise server whose network and ports the operator controls. A hosted service such as Google Workspace or Microsoft 365 cannot be fronted this way and follows a different model that is outside the scope of this guide.

 本指南適用於任何可置於代理伺服器之後的資源，即營運商控制其網路和連接埠的本機伺服器。託管服務（例如 Google Workspace 或 Microsoft 365）無法以這種方式進行前端配置，它們遵循不同的模型，不在本指南的討論範圍之內。

 The migration is built around two tools. The migration proxy sits in front of both servers and decides, from the credentials each client already presents, which of the two currently holds a given account. Because the routing decision is made from the login itself, clients keep the same hostname, ports and passwords throughout the migration and require no reconfiguration. Vandelay is the data mover: it reads an account from the source into a local archive and writes that archive onto the new deployment, one account at a time.

 遷移過程圍繞著兩個工具。 遷移代理位於兩台伺服器的前端，根據每個客戶端已提供的憑證，判斷目前哪個伺服器持有特定帳戶。由於路由決策是基於登入訊息，因此客戶端在整個遷移過程中無需重新配置主機名稱、連接埠和密碼。 Vandelay是資料遷移器：它將帳戶從來源伺服器讀取到本機存檔，然後將該檔案逐個帳戶寫入新的部署環境。

## How the migration is structured｜遷移是如何組織的

 The new deployment becomes the public mail exchanger for the entire duration of the migration. All inbound mail on port 25 is delivered to the new server, which performs split delivery: a message for an account that has already been moved is delivered locally, while a message for an account that still lives on the source is relayed there. This arrangement means that mail never has to be re-pointed mid-migration. The new server is the single front door from the moment the proxy goes live, and the relay quietly fills the gap for accounts that have not been moved yet.

 在整個遷移過程中，新的部署將成為公用郵件交換器。所有透過 25 連接埠收到的郵件都會被投遞到新伺服器，新伺服器採用分流投遞：已移轉帳號的郵件在本機投遞，​​而仍在原伺服器的帳號的郵件則會轉送至新伺服器。這種安排意味著在遷移過程中無需重新指向郵件伺服器。從代理伺服器上線的那一刻起，新伺服器就成為唯一的入口，而轉送伺服器則默默地填補了尚未遷移帳戶的郵件投遞空白。

 Interactive sessions, by contrast, are routed per account. IMAP, POP3, ManageSieve, SMTP submission and, where the source serves them, JMAP and HTTP connections are resolved through a mapping table: an account with no entry resolves to the source, and an account that has been migrated resolves to the new deployment. Moving an account is therefore a matter of copying its data and then flipping a single mapping entry, after which that account’s clients follow to the new server on their next connection.

 相比之下，互動式會話是按帳戶路由的。 IMAP, POP3、ManageSieve、SMTP 提交以及來源為其提供服務的JMAP 和 HTTP 連接透過映射表進行解析：沒有條目的帳戶解析為來源，已遷移的帳戶解析為新部署。因此，行動帳戶就是複製其數據，然後翻轉單一映射條目，之後該帳戶的用戶端在下一次連線時跟隨到新伺服器。

 Because migration is a copy rather than a move, the source retains a complete copy of every account until it is decommissioned. This is what makes the process reversible: until an account accumulates new data on the new server, rolling it back is simply a matter of routing it to the source again.

 由於遷移是複製而非移動，來源伺服器會保留每個帳戶的完整副本，直到該帳戶被停用。這使得遷移過程可逆：在帳戶於新伺服器上累積新資料之前，回滾操作只需將其重新路由到來源伺服器即可。

## The steps｜步驟

 The migration proceeds through the following stages, each documented on its own page.

 遷移過程分為以下幾個階段，每個階段都在單獨的頁面上進行了記錄。

 The process begins with preparation, which installs the new Stalwart deployment, the command-line interface, the migration proxy and Vandelay. It continues with configuring the new deployment for its role as the split-delivery front, configuring the proxy to route between the two servers, and configuring the source server to accept the proxy and the relay, where the precise changes depend on whether the source is an older Stalwart or a Dovecot and Postfix stack. With everything in place, starting the proxy brings the combined system online with every account still served from the source, and provides the tests that confirm each protocol works before any account is moved. Migrating accounts then covers the end-to-end move of a single account, including validation and rollback, and is repeated for every account. Once the source is empty, finalizing the migration removes the proxy and lets the new deployment answer clients directly. A troubleshooting reference collects the problems most likely to arise along the way.

 此流程首先進行準備工作（ \([https://stalw.art/docs/migration/guide/preparation/](https://stalw.art/docs/migration/guide/preparation/)\) ），安裝新的 Stalwart 部署、命令列介面、遷移代理程式和 Vandelay。接下來進行設定新部署（ \([https://stalw.art/docs/migration/guide/configure-new/](https://stalw.art/docs/migration/guide/configure-new/)\) ），使其作為拆分交付前端；配置代理（ \([https://stalw.art/docs/migration/guide/configure-proxy/](https://stalw.art/docs/migration/guide/configure-proxy/)\) ），使其在兩台伺服器之間進行路由；以及配置來源伺服器\([https://stalw.art/docs/migration/guide/configure-source/](https://stalw.art/docs/migration/guide/configure-source/)\) ），使其接受代理和中繼。具體配置取決於來源伺服器是較舊的 Stalwart 版本還是 Dovecot 和 Postfix 堆疊。一切就緒後，啟動代理程式（ \([https://stalw.art/docs/migration/guide/cutover/](https://stalw.art/docs/migration/guide/cutover/)\) ）即可啟動合併系統，所有帳戶仍由來源伺服器提供服務，並在遷移任何帳戶之前進行測試，以確認每個協定都能正常運作。遷移帳戶\([https://stalw.art/docs/migration/guide/migrate-accounts/](https://stalw.art/docs/migration/guide/migrate-accounts/)\) ）則涵蓋單一帳戶的端對端遷移，包括驗證和回滾，並對每個帳戶重複此程序。來源伺服器清空後，完成遷移會移除代理，讓新部署直接回應客戶端請求。 故障排除參考資料收集了遷移過程中最可能出現的問題。

## Downtime｜停機時間

 The preparatory stages carry no downtime. Installing the new deployment, configuring it, configuring the proxy and preparing the source all happen alongside the live server without affecting it, because none of these actions change the path that existing clients take to reach their mailboxes. The configuration changes applied to the source do not take effect until its configuration is reloaded or, for the settings that need it, until it is restarted, which is deliberately deferred to the cutover.

 準備階段不會造成任何停機時間。新部署的安裝、設定、代理程式設定和來源伺服器準備工作均與生產伺服器並行進行，不會對其造成任何影響，因為這些操作都不會改變現有用戶端存取郵件信箱的路徑。應用於來源伺服器的設定變更只有在重新載入其配置後才會生效；對於需要重新啟動的設置，則需要重新啟動伺服器才能生效，而重新啟動操作會刻意推遲到切換階段進行。

 A short interruption occurs at the cutover, when the source is reloaded or restarted and the proxy takes over the public ports. From that point clients connect to the proxy rather than to the source directly. The interruption lasts only as long as it takes to apply the source’s staged settings and start the proxy, and once the proxy is live every account continues to be served from the source exactly as before. Migrating individual accounts after that introduces no further downtime: each account is briefly disconnected when its mapping is flipped and reconnects to the new deployment automatically.

 在切換過程中，由於來源伺服器需要重新載入或重啟，並且代理伺服器會接管公共端口，因此會出現短暫的服務中斷。此時，客戶端將連接到代理伺服器，而不是直接連接到來源伺服器。服務中斷的時間僅限於應用程式來源伺服器的預置設定並啟動代理伺服器所需的時間。代理伺服器啟動後，所有帳戶將繼續像以前一樣從來源伺服器獲得服務。之後遷移單一帳戶不會造成任何額外的停機時間：每個帳戶在映射切換時會短暫斷開連接，然後自動重新連接到新的部署。

## A note on account names｜關於帳戶名稱的說明

 The latest Stalwart releases require account names to be full e-mail addresses. A source that addressed an account by a bare local part, such as `alice`, whether an older Stalwart that predates e-mail-address logins or a Dovecot stack configured with short user names, will have that account become `[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` on the new server, where `example.org` is the account’s domain. Clients that signed in with a bare account name will need to sign in with the full e-mail address once their account has been migrated. The proxy can be told to accept both login forms during the transition, which is described in the steps that follow.

 最新版的 Stalwart 要求帳號名稱必須是完整的電子郵件地址。如果帳戶名稱僅包含本地部分（例如`alice` ，無論是較早版本（不支援電子郵件地址登入）的 Stalwart，還是配置了短用戶名的 Dovecot 堆疊，在新伺服器上，該帳戶名稱都會變為`[[email protected]](https://stalw.art/cdn-cgi/l/email-protection)` ，其中`example.org`是帳戶的網域名稱。使用帳戶名稱登入的用戶端在帳戶遷移後需要使用完整的電子郵件地址登入。代理伺服器可以設定為在遷移過程中接受這兩種登入方式，具體步驟如下。
