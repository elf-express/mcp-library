# Keycloak｜鑰匙斗篷

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[auth｜認證\\\]\\\(&lt;000 目錄.md#c-3&gt;\\\) › \\\[scim｜方案\\\]\\\(&lt;000 目錄.md#c-10&gt;\\\) › \\\[providers｜供應商\\\]\\\(&lt;000 目錄.md#c-11&gt;\\\)

Keycloak is a common choice as the OpenID Connect provider in front of Stalwart, and that part of the integration is straightforward: it is covered under the OIDC directory backend and needs no SCIM at all. Provisioning is the harder half, and the answer as of Keycloak 26.7 is less convenient than for the hosted identity providers.

 Keycloak 是 Stalwart 前端 OpenID Connect 供應商的常用選擇，這部分整合非常簡單：它包含在 OIDC目錄後端中，完全不需要SCIM 。配置才是更複雜的部分，截至 Keycloak 26.7 ，其解決方案不如託管身分提供者那麼方便。

## Keycloak does not push SCIM｜Keycloak 不會推送SCIM

 Keycloak’s own SCIM support runs in the opposite direction to what a Stalwart deployment needs. The `scim-api` feature introduced in Keycloak 26.6 and promoted to preview in 26.7 makes **Keycloak** a SCIM service provider, so that an upstream system such as Entra ID can provision users into a Keycloak realm. It exposes `/realms/{realm}/scim/v2` on the Keycloak side. It does not send anything anywhere, and it plays no part in provisioning Stalwart.

 Keycloak 本身的SCIM支援與 Stalwart 部署的需求方向相反。 Keycloak 26.6中引入的`scim-api`功能（在26.7中升級為預覽版）使 **Keycloak** 成為SCIM服務提供商，以便 Entra 等上游系統ID可以將用戶配置到 Keycloak 域中。它在 Keycloak 端公開`/realms/{realm}/scim/v2` 。它不會向任何地方發送任何數據，也不參與 Stalwart 的配置。

 An outbound SCIM client, which is what would push Keycloak’s users into Stalwart, has been stated by the Keycloak project as a future direction but is not present in 26.7. Since this is an area of active development, check the [Keycloak release notes](https://www.keycloak.org/documentation) before assuming the position below still holds.

 Keycloak 專案曾表示，出站客戶端SCIM是未來發展方向之一，它將促使 Keycloak 用戶遷移到 Stalwart，但該客戶端在26.7中尚未實作。由於該領域仍在積極開發中，請在確認以下觀點是否仍然成立之前，請查閱 [Keycloak 版本說明](https://www.keycloak.org/documentation) 。

## Community extensions｜社區拓展

 Outbound provisioning from Keycloak today requires a third-party extension deployed into the Keycloak server. Two are maintained well enough to consider, and both have significant caveats.

 目前從 Keycloak 出站配置需要將第三方擴充部署到 Keycloak 伺服器。有兩個擴充維護良好，值得考慮，但它們都存在一些重大缺陷。

 The longest-established is `mitodl/keycloak-scim`, which installs an event listener, a user federation provider, and a database table mapping Keycloak identifiers to remote SCIM identifiers. It is the more widely deployed of the two, and it is also the more troubled: at the time of writing its issue tracker carries open reports that user deletion fails before the request is sent, that provisioning is silently skipped for users whose email address is unverified, and that group synchronisation does not work. It is built against the Keycloak 25 extension interfaces. Its licensing is stated inconsistently between its repository metadata and its README, which is worth resolving before deploying it anywhere that matters.

`mitodl/keycloak-scim`是歷史最悠久的版本，它安裝了一個事件監聽器、一個用戶聯合提供者以及一個將 Keycloak 標識符映射到遠端SCIM標識符的資料庫表。它是兩個版本中部署更廣泛但問題也更多：截至撰寫本文時，其問題追蹤器中存在用戶刪除請求在發送之前失敗、電子郵件地址未驗證的用戶配置被靜默跳過以及群組同步無法正常工作等未解決的問題。它基於 Keycloak 25 擴充介面建置。其儲存庫元資料和README中的授權聲明不一致，因此在將其部署到任何重要位置之前，有必要解決此問題。

 The more recent `Termindiego25/keycloak-scim-outbound` targets current Keycloak, sends cleaner SCIM payloads, and offers a per-group provisioning scope and a choice between deactivation and deletion on deprovisioning. It performs no initial synchronisation at all: only events occurring after it is enabled are propagated, so an existing realm has to be seeded some other way. It is a young project with little deployment behind it.

 最新的`Termindiego25/keycloak-scim-outbound`版本針對目前的 Keycloak 平台，發送更簡潔的SCIM有效負載，並提供基於群組的配置範圍，以及在取消配置時選擇停用或刪除的選項。它完全不執行初始同步：僅傳播啟用後發生的事件，因此現有領域必須透過其他方式進行初始化。這是一個尚處於早期階段的項目，部署經驗尚淺。

 Neither is endorsed by the Keycloak project, neither supports OAuth client credentials \(both take a static bearer token, which suits Stalwart’s API keys\), and neither implements bulk operations.

 兩者都未獲得 Keycloak 專案的認可，兩者都不支援 OAuth 用戶端憑證（兩者都接受靜態 bearer token，這符合 Stalwart 的 API keys ），而且兩者都不實現批量操作。

 Both projects populate `name.givenName` and `name.familyName` when creating a user, because both were written against the full RFC 7643 User schema, and neither exposes attribute mapping in its configuration. Stalwart does not store structured name parts, but it accepts them: where the payload carries no `displayName` or `name.formatted`, the given and family names are joined and stored as the account’s display name. See schema handling. No patched build is needed, and nothing has to be trimmed.

 這兩個項目在創建用戶時都會填充`name.givenName`和`name.familyName` ，因為它們都是基於完整的RFC 7643 用戶模式編寫的，並且它們的配置中都沒有公開屬性映射。 Stalwart 不儲存結構化名稱部分，但它接受它們：如果有效負載不包含`displayName`或`name.formatted` ，則名字和姓氏會合併並儲存為帳戶的顯示名稱。參見 模式處理 。無需打補丁構建，也無需進行任何修剪。

## Alternatives to a SCIM extension｜SCIM擴展的替代方案

 Where an extension is unsuitable for the reasons above, three options work today, and the right one depends on what the deployment actually needs from provisioning.

 如果由於上述原因擴充程式不適用，目前有三種選擇，而正確的選擇取決於部署實際需要的配置。

**Rely on just-in-time provisioning and pre-create accounts.** For an OIDC-backed domain this is the configuration described under Provisioning models. Accounts are created ahead of first login through the WebUI, the JMAP API, or the CLI, and removed the same way. The bulk apply command accepts an NDJSON plan, which makes this scriptable against whatever system owns the joiner and leaver process.

**依賴即時配置和預先建立帳戶。** 對於由OIDC支援的域，此配置在 配置模型中描述。帳戶在首次登入之前透過 WebUI 、 JMAP API或 CLI創建，並以相同方式刪除。 bulk apply命令接受NDJSON計劃，這使得可以針對擁有加入和離開流程的任何系統編寫腳本來執行此操作。

**Drive Stalwart’s administrative API from Keycloak events.** Where Keycloak is already the system of record, a small service subscribed to its admin events can call Stalwart’s JMAP administration API directly. This is more work than a SCIM connector but avoids the extensions entirely, and it has full access to Stalwart’s account model, which is wider than the subset SCIM exposes. An API key with the `sysAccount` permissions is the appropriate credential.

**透過 Keycloak 事件驅動 Stalwart 的管理API 。** 如果 Keycloak 已經是記錄系統，則訂閱其管理事件的小型服務可以直接呼叫 Stalwart 的JMAP管理API 。這比使用SCIM連接器要複雜一些，但完全避免了擴展，並且能夠完全訪問 Stalwart 的帳戶模型，該模型比SCIM公開的子集更廣泛。具有`sysAccount`權限的 API金鑰是適當的憑證。

**Provision from the system upstream of Keycloak.** In deployments where Keycloak federates an upstream directory or HR system that has its own SCIM client, point that client at Stalwart directly. Keycloak continues to handle authentication, and provisioning bypasses it. This is the closest equivalent to the Entra ID and Okta configurations. Check for it before writing any code.

**從 Keycloak 上游系統進行配置。** 在 Keycloak 聯合了上游目錄或擁有自身客戶端的HR系統的部署中，請將該客戶端直接指向 Stalwart。 Keycloak 將繼續處理身份驗證，配置過程將繞過它。這與 Entra ID和 Okta 的配置最為接近。在編寫任何程式碼之前，請檢查是否存在此SCIM 。

## If an extension is used anyway｜如果無論如何都要使用擴充功能

 Deploy the extension, then create one test user and read the request in Stalwart’s telemetry or in the extension’s own logging before enabling it for the realm. The failure modes are quiet: a rejected request typically appears in the extension’s log as a warning and nowhere else, and neither extension retries after an HTTP error, so a change lost to a rejection is lost permanently.

 部署擴充功能後，建立一個測試用戶，並在啟用該擴充功能之前，從 Stalwart 的遙測資料或擴充程式本身的日誌中讀取請求。失敗模式是靜默的：被拒絕的請求通常只會在擴充功能的日誌中顯示為警告，而不會出現在其他任何地方；此外，擴充功能在出現HTTP錯誤後都不會重試，因此因請求被拒絕而遺失的變更將永久遺失。

 Three of Stalwart’s behaviours show up in those logs. A creation returns `201 Created` with the complete resource including its `id`, which is what both extensions store in order to address the account later; an extension that fails to record it will silently no-op on every subsequent update. Stalwart accepts the string forms `"true"` and `"false"` for `active` in a `PATCH` operation as well as JSON booleans, so an extension that sends the value as a string works without modification. And the response will not echo the structured name back: `givenName` and `familyName` are consumed on the way in and the account carries a single display name, so an extension that compares its own view against the response sees a difference there on every cycle. Neither extension reconciles on that field, so this is a reading artefact, not a loop.

 日誌中顯示了 Stalwart 的三種行為。建立操作會傳回包含完整資源的`201 Created` ，其中包括其`id` ，擴充功能會儲存這些資訊以便後續存取帳戶；如果擴充功能未能記錄這些信息，則在每次後續更新時都會靜默執行空操作。 Stalwart 接受字串形式的`"true"`和`"false"`作為`active` `PATCH`值，以及布林值JSON ，因此，以字串形式傳送值的擴充程式無需修改即可正常運作。此外，回應不會回顯結構化名稱： `givenName`和`familyName`在傳入時已被消耗，帳戶只有一個顯示名稱，因此，將自身視圖與回應進行比較的擴展程序在每個週期都會發現差異。這兩個擴充功能在該欄位上都無法協調一致，因此這是一個讀取錯誤，而不是循環錯誤。

 Scope provisioning to a dedicated Keycloak group, not the whole realm, where the extension supports it, and schedule a periodic full synchronisation as the reconciliation mechanism, since neither extension reconciles on its own.

 將範圍配置到專用的 Keycloak 群組，而不是整個領域（如果擴充功能支援的話），並安排定期完全同步作為協調機制，因為這兩個擴充功能都無法自行協調。
