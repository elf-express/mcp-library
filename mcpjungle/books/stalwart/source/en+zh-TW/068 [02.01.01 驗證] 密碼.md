# Passwords｜密碼

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[auth｜認證\\\]\\\(&lt;000 目錄.md#c-3&gt;\\\) › \\\[authentication｜驗證\\\]\\\(&lt;000 目錄.md#c-4&gt;\\\)

Account passwords can be stored in the internal directory or in an external directory such as LDAP or SQL. The server supports multiple password hashing schemes, and accounts may hold more than one password hash simultaneously. Storing passwords in plain text is possible but strongly discouraged.

 帳戶密碼可以儲存在內部目錄或外部目錄（例如LDAP或SQL ）中。伺服器支援多種密碼雜湊方案，帳戶可以同時儲存多個密碼雜湊值。雖然可以以明文形式儲存密碼，但強烈建議不要這樣做。

 Each hash type is identified by a specific prefix, which is how the server recognises the hashing method in use. If a stored password does not match a known hash prefix, it is compared as plain text.

 每種雜湊類型都由一個特定的前綴標識，伺服器正是透過這個前綴來識別所使用的雜湊方法。如果儲存的密碼與已知的雜湊前綴不匹配，則會將其作為明文進行比較。

 Password hashing and the password policy enforced on the internal directory are both configured on the Authentication singleton \(found in the WebUI under Settings › Authentication › General\). The hashing algorithm is selected through passwordHashAlgorithm, which accepts `argon2id` \(the default\), `bcrypt`, `scrypt`, or `pbkdf2`. The specific policy fields are discussed in the next section.

 內部目錄的密碼雜湊和密碼原則均在 Authentication單例中設定（可在 WebUI 的「設定」&gt;「驗證」&gt;「常規」中找到）。哈希演算法透過 passwordHashAlgorithm選擇，可接受`argon2id` （預設值）、 `bcrypt`, `scrypt`或`pbkdf2` 。具體的策略欄位將在下一節中討論。

 The server recognises stored password hashes produced by the following schemes:

 伺服器能夠識別以下方案產生的已儲存密碼雜湊值：

- **Argon2:** Winner of the 2015 Password Hashing Competition. Identified by the prefix `"$argon2"`.
**Argon2：** 2015 年密碼哈希競賽的獲勝者。前綴為`"$argon2"` 。
- **PBKDF2:** Key derivation function defined in RSA Laboratories’ PKCS series. Identified by the prefix `"$pbkdf2"`.
**PBKDF2 :** RSA實驗室的PKCS系列中定義的關鍵推導函數。以前綴`"$pbkdf2"`標識。
- **Scrypt:** Key derivation function originally developed for the Tarsnap backup service. Identified by the prefix `"$scrypt"`.
**Scrypt：** 最初為 Tarsnap 備份服務開發的金鑰衍生函數。以前綴`"$scrypt"`標識。
- **bcrypt:** Password hashing method based on the Blowfish cipher, with a salt and a configurable cost factor. Identified by the prefix `"$2"`.
**bcrypt：**一種基於 Blowfish 密碼的密碼雜湊方法，帶有鹽值和可設定的成本因子。其字首為`"$2"` 。

- **SHA-512 Crypt and SHA-256 Crypt:** SHA-based password hashing schemes producing 512-bit and 256-bit hashes. Identified by the prefixes `"$6$"` and `"$5$"`.
**SHA -512 加密和SHA -256 加密：** 基於SHA的密碼雜湊方案，產生 512 位元和 256 位元雜湊值。分別以`"$6$"`和`"$5$"`為前綴進行標識。
- **SHA-1 Crypt:** Older password hashing scheme producing a 160-bit hash. Identified by the prefix `"$sha1"`.
**SHA -1 加密：** 較舊的密碼雜湊方案，產生 160 位元雜湊值。由前綴`"$sha1"`標識。
- **MD5-based hash:** Older and weaker hash function producing a 128-bit hash. Identified by the prefix `"$1"`.
**MD5哈希：** 較舊且較弱的雜湊函數，產生 128 位元雜湊值。以前綴`"$1"`標識。
- **BSDi Crypt \(Enhanced DES-based hash\):** Slight modification of the original Unix crypt function. Identified by the prefix `"_"`.
**BSDi Crypt（增強型DES雜湊）：** 原始 Unix crypt 函數的稍微修改。以前綴`"_"`標識。
- **Base64-encoded SHA-1, Salted SHA-1, SHA-256, Salted SHA-256, SHA-512, Salted SHA-512, MD5:** Identified by a prefix in curly braces, such as `"{SHA}"` or `"{SSHA}"`. The salted variants use a random salt to mitigate pre-computed lookup attacks.
**Base64編碼的SHA-1、加鹽SHA-1、SHA-256、加鹽SHA-256、SHA-512、加鹽SHA-512、MD5：** 透過花括號中的前綴進行標識，例如`"{SHA}"`或`"{SSHA}"` 。加鹽變體使用隨機鹽值來緩解預先計算的查找攻擊。
- **Unix Crypt:** Traditional Unix password hashing. Identified by the prefix `"{CRYPT}"` or `"{crypt}"`.
**Unix Crypt：**傳統的Unix密碼雜湊。以`"{CRYPT}"`或`"{crypt}"`為前綴標識。

- **Plain Text:** Passwords stored without hashing. Identified by the prefixes `"{PLAIN}"`, `"{plain}"`, `"{CLEAR}"`, or `"{clear}"`. Not recommended.
**明文：** 未經雜湊處理的密碼。以`"{PLAIN}"`, `"{plain}"`, `"{CLEAR}"`或`"{clear}"`為前綴標識。不建議使用。
## Password policy｜密碼原則

 The policy that applies to passwords set through the internal directory is configured on the Authentication singleton. These checks run when a user creates a new password or an administrator resets one; they do not apply retroactively to existing stored hashes, and they do not apply when credentials are validated against an external directory, which enforces its own policy.

 適用於透過內部目錄設定的密碼的政策在 Authentication單例中設定。這些檢查會在使用者建立新密碼或管理員重設密碼時執行；它們不會追溯應用於已儲存的雜湊值，也不會套用於針對外部目錄驗證憑證的情況，因為外部目錄會強制執行其自身的政策。

 The passwordMinLength and passwordMaxLength fields set the lower and upper bounds on the length of a newly chosen password. The defaults are 8 and 128 characters respectively. The upper bound prevents resource-exhaustion attempts against the hashing function and should be left generous.

 passwordMinLength和 passwordMaxLength字段分別設定新密碼長度的下限和上限。預設值分別為 8 個字元和 128 個字元。上限值可防止對雜湊函數進行資源耗盡攻擊，因此應設定得較為寬鬆。

 Complexity is expressed through passwordMinStrength, which rejects candidates below a configurable level on the zxcvbn scale. The available levels are `zero` \(too guessable\), `one` \(very guessable\), `two` \(somewhat guessable\), `three` \(safely unguessable, the default\), and `four` \(very unguessable\). Using zxcvbn rather than character-class rules allows long passphrases built from common words to pass while short passwords padded with symbols are still rejected.

 複雜度透過 passwordMinStrength來表示，它會拒絕低於 zxcvbn 等級（可設定等級）的候選密碼。可用等級包括`zero` （太容易猜到）、 `one` （非常容易猜到）、 `two` （有點容易猜到）、 `three` （絕對無法猜到，預設值）和`four` （非常難以猜到）。使用 zxcvbn 而不是字元類規則，可以讓由常用字構成的長密碼短語通過驗證，同時仍會拒絕用符號填入的短密碼。

 The passwordDefaultExpiry field sets a default lifetime for passwords stored in the internal directory. When a value is supplied, users are required to choose a new password once this duration has elapsed since their last password change. Leaving the field unset disables default expiry, so passwords remain valid until the user or an administrator rotates them.

 passwordDefaultExpiry欄位用於設定儲存在內部目錄中的密碼的預設有效期限。如果設定了該值，則使用者在上次變更密碼後超過此有效期後必須選擇新密碼。如果未設定此字段，則會停用預設過期功能，密碼將一直有效，直到使用者或管理員手動輪換為止。

 The related fields maxAppPasswords and maxApiKeys cap the number of application passwords and API keys each account may hold; these are separate credentials from the account password and are covered on their own pages.

`maxAppPasswords` \([https://stalw.art/docs/ref/object/authentication#maxapppasswords](https://stalw.art/docs/ref/object/authentication#maxapppasswords)\) `maxApiKeys` \([https://stalw.art/docs/ref/object/authentication#maxapikeys](https://stalw.art/docs/ref/object/authentication#maxapikeys)\) \([https://stalw.art/docs/auth/authentication/app-password](https://stalw.art/docs/auth/authentication/app-password)\) API \([https://stalw.art/docs/auth/authentication/api-key](https://stalw.art/docs/auth/authentication/api-key)\)

 These are the only password policy controls offered by the internal directory. Deployments that require richer policies such as password history, reuse prevention, or character-class rules should delegate authentication to an external identity provider over OIDC and enforce those policies there.

 這些是內部目錄提供的唯一密碼策略控制。如果需要更豐富的策略（例如密碼歷史記錄、防止重複使用或字元類別規則），則應將身分驗證委託給外部身分提供者（透過 OIDC ，並在該提供者處強制執行這些策略。
