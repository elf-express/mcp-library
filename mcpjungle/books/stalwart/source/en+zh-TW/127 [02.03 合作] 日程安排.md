# Scheduling｜日程安排

> 章節：\\\[docs｜文件\\\]\\\(&lt;000 目錄.md#c-2&gt;\\\) › \\\[collaboration｜合作\\\]\\\(&lt;000 目錄.md#c-17&gt;\\\)

Calendar scheduling coordinates meetings and events by automating the exchange of invitations. Rather than relying on manual email, calendar scheduling systems handle communication between organisers and attendees, track participation status, and manage updates and cancellations in real time.

 日曆安排系統透過自動發送邀請函來協調會議和活動。它無需依賴人工郵件，即可處理組織者和參與者之間的溝通，追蹤參與狀態，並即時管理更新和取消。

 Stalwart supports calendar scheduling through two primary mechanisms:

 Stalwart 透過兩種主要機制支援日曆調度：

- **JMAP for Calendars**, which includes built-in support for scheduling operations such as sending invitations, processing responses, and managing event updates using the JMAP protocol.
**JMAP日曆**，它內建了對日程安排操作的支持，例如發送邀請、處理回復以及使用JMAP協議管理事件更新。
- **Scheduling Extensions to CalDAV**, as defined in [RFC 6638](https://datatracker.ietf.org/doc/html/rfc6638). This specification extends the CalDAV protocol to support server-based scheduling operations. Events with attendee information trigger the necessary scheduling logic on the server, including delivery of invitations, processing of replies, and updates to calendars.
**CalDAV 行程擴展**，定義見 [RFC 6638](https://datatracker.ietf.org/doc/html/rfc6638) 。本規範擴展了 CalDAV 協議，使其支援基於伺服器的日程安排操作。包含與會者資訊的事件會觸發伺服器上必要的日程安排邏輯，包括發送邀請、處理回覆以及更新日曆。
Calendar scheduling relies on two core protocols from the iCalendar ecosystem:
 日曆安排依賴 iCalendar 生態系統中的兩個核心協定：

- **iCalendar Transport-Independent Interoperability Protocol \(iTIP\)**, defined in [RFC 5546](https://datatracker.ietf.org/doc/html/rfc5546), describes how scheduling messages \(event invitations, updates, cancellations, and responses\) are structured and processed using the iCalendar data format. It defines a set of methods \(`REQUEST`, `REPLY`, `CANCEL`, and so on\) used to negotiate scheduling operations between organisers and attendees. iTIP itself is transport-agnostic.
**iCalendar 傳輸無關互通協定 \(iTIP\)**，定義於 [RFC 5546](https://datatracker.ietf.org/doc/html/rfc5546) ，描述如何使用 iCalendar 資料格式建構和處理日程安排訊息（活動邀請、更新、取消和回應）。它定義了一組用於在組織者和參與者之間協商日程安排操作的方法（ `REQUEST`, `REPLY`, `CANCEL`等）。 iTIP 本身與傳輸方式無關。
- **iCalendar Message-Based Interoperability Protocol \(iMIP\)**, described in [RFC 6047](https://datatracker.ietf.org/doc/html/rfc6047), specifies how iTIP messages are transported over email \(typically via SMTP\). It supports calendar scheduling between systems that may not implement CalDAV, for example sending a calendar invitation from a CalDAV account to an external recipient via email.
**基於訊息的 iCalendar 互通協定 \(iMIP\)**，在 [RFC 6047](https://datatracker.ietf.org/doc/html/rfc6047)中有詳細描述，它規定了 iTIP 訊息如何透過電子郵件（通常透過SMTP ）傳輸。它支援在可能未實現 CalDAV 的系統之間進行日曆調度，例如，透過電子郵件從 CalDAV 帳戶向外部收件者發送日曆邀請。
When Stalwart encounters a recipient that cannot be reached via CalDAV \(such as an external attendee\), it falls back to iMIP and delivers the scheduling message as an email with an attached `.ics` file.
 當 Stalwart 遇到無法透過 CalDAV 聯繫的收件人（例如外部與會者）時，它會回退到 iMIP，並將日程安排訊息作為帶有附件`.ics`文件的電子郵件發送。

## Enabling scheduling｜啟用日程安排

 Scheduling configuration is carried on the CalendarScheduling singleton \(found in the WebUI under Settings › Calendar & Contacts › Scheduling\). Scheduling is enabled by default so that invitations, participant management, and automated scheduling workflows interoperate with CalDAV clients that implement the Scheduling Extensions \(RFC 6638\) and with email-based iMIP.

 日程安排配置位於 CalendarScheduling單例中（可在 WebUI 的「設定」&gt;「日曆和聯絡人」&gt;「日程安排」中找到）。日程安排功能預設為啟用，以便邀請、參與者管理和自動日程安排工作流程能夠與實現了日程安排擴展 \( RFC 6638\) 的 CalDAV 用戶端以及基於電子郵件的 iMIP 互操作。

 Scheduling can be disabled globally by setting enable to `false`. With that field disabled, Stalwart no longer processes scheduling requests or generates scheduling messages. Events that include attendee information are stored as standard calendar entries, but no invitations, updates, or replies are sent or processed. Both iTIP and iMIP paths are bypassed.

 可以透過將 enable設定為`false`來全域禁用日程安排功能。停用該欄位後，Stalwart 將不再處理日程安排請求或產生日程安排訊息。包含與會者資訊的事件將作為標準日曆條目存儲，但不會發送或處理任何邀請、更新或回應。 iTIP 和 iMIP 路徑都會被繞過。

 Calendar Scheduling can also be enabled or disabled on a per-account basis by setting the appropriate permissions.

 也可以透過設定對應的 權限來按帳戶啟用或停用日曆計劃。

## Automatic event addition｜自動新增事件

 RFC 6638 mandates that CalDAV servers automatically add scheduling messages \(invitations received via iTIP or iMIP\) to the recipient’s calendar. This removes the need for manual review before events appear on the calendar.

 RFC 6638 規定 CalDAV 伺服器必須自動將行程安排訊息（透過 iTIP 或 iMIP 收到的邀請）新增至收件者的行事曆。這樣就無需在活動顯示在日曆上之前進行手動審核。

 Stalwart takes a more deliberate approach. Automatic addition can be convenient, but it creates the potential for calendar spam and undermines user control over which events appear on personal or work schedules.

 Stalwart 採取了一種更為審慎的方式。自動添加雖然方便，但可能會導致日曆內容過多，並削弱使用者對個人或工作日程中顯示哪些事件的控制權。

 By default, Stalwart only adds invitations to calendars automatically when two conditions are met. First, the sender must be authenticated via DMARC, confirming that the message originates from a domain authorised to send on behalf of the claimed sender. Second, the sender must be listed in the recipient’s address book, indicating an established relationship. Together these safeguards support auto-processing of legitimate invitations without compromising account safety.

 預設情況下，Stalwart 僅在滿足兩個條件時才會自動將邀請新增至日曆。首先，寄件者必須透過 DMARC進行身分驗證，以確認郵件來自已取得授權代表寄件者發送郵件的網域。其次，寄件者必須列在收件者的 通訊錄中，表示雙方已建立聯繫。這些安全措施共同確保在不損害帳號安全的前提下，自動處理合法邀請。

 For deployments that wish to conform strictly to RFC 6638 and automatically accept all incoming scheduling messages, set autoAddInvitations to `true`. With that setting enabled, Stalwart accepts all valid iTIP and iMIP invitations without verifying the sender’s authenticity or presence in the address book. This should be used with caution, particularly in open or federated environments.

 對於希望嚴格遵循RFC 6638 並自動接受所有傳入調度訊息的部署，請將 autoAddInvitations設定為`true` 。啟用此設定後，Stalwart 將接受所有有效的 iTIP 和 iMIP 邀請，而無需驗證寄件者的真實性或其在通訊錄中的存在。應謹慎使用此功能，尤其是在開放或聯合環境中。

## Scheduling limits｜調度限制

 To prevent misuse of the calendar scheduling system and to protect server stability, the CalendarScheduling singleton exposes limits on the size and scope of scheduling operations.

 為了防止濫用日曆調度系統並保護伺服器穩定性，CalendarScheduling 單例對調度操作的大小和範圍進行了限制。

### iTIP message size｜iTIP 訊息大小

 itipMaxSize defines the maximum size in bytes of an incoming iTIP message that the server accepts and processes. Messages larger than this limit are rejected before parsing. The default is `524288` \(512 KB\). This guards against excessively large or malformed calendar invitations that could be used to exhaust memory or processing capacity.

 itipMaxSize定義了伺服器接受和處理的傳入 iTIP 訊息的最大位元組數。超過此限制的訊息將在解析前被拒絕。預設值為`524288` \(512 KB \)。這可以防止過大或格式錯誤的日曆邀請耗盡記憶體或處理能力。

### Outbound recipient limit｜出站收件人限額

 maxRecipients limits the number of recipients that a single outbound iTIP scheduling message may include. The default is `100`. Requests that exceed this limit are rejected before delivery. This guards against mass-invitation abuse, where the calendar system might otherwise be used to send messages to a large number of users in a single operation.

 maxRecipients限制單一出站 iTIP 調度訊息可包含的收件者數量。預設值為`100` 。超過此限制的請求將在發送前被拒絕。這可以防止濫用大量邀請功能，避免日曆系統被用於在一次操作中向大量用戶發送訊息。

 In addition to these scheduling-specific limits, all existing MTA-level throttling policies apply to outbound iMIP messages. Outbound scheduling emails are subject to the same rate limits, message size limits, and delivery policies as any other email traffic.

 除了這些針對調度任務的限制外，所有現有的 MTA級限流策略也適用於出站 iMIP 訊息。出站調度郵件與其他郵件流量一樣，受相同的速率限制、訊息大小限制和投遞策略約束。

## Inbox auto-expunge｜收件匣自動清除

 As part of the CalDAV Scheduling Extensions, each account includes a Scheduling Inbox, a special collection where incoming iTIP messages \(invitations, replies, cancellations, updates\) are stored. These messages serve as a log of scheduling activity and are used by calendar clients to synchronise and process meeting-related actions.

 作為 CalDAV 日程安排擴展的一部分，每個帳戶都包含一個日程安排收件箱，這是一個特殊的集合，用於儲存收到的 iTIP 訊息（邀請、回覆、取消、更新）。這些訊息充當日程安排活動的日誌，供日曆用戶端同步和處理與會議相關的操作。

 Not all CalDAV clients reliably delete messages from the Scheduling Inbox after processing them, so the inbox can accumulate outdated or redundant scheduling messages over time. This consumes storage unnecessarily and may cause clients to continue synchronising stale data.

 並非所有 CalDAV 用戶端都能在處理完訊息後可靠地從調度收件匣中刪除訊息，因此收件匣會隨著時間的推移累積過時或冗餘的調度訊息。這會不必要地佔用儲存空間，並可能導致客戶端持續同步過時的資料。

 The retention period for the Scheduling Inbox is controlled by expungeSchedulingInboxAfter on the DataRetention singleton \(found in the WebUI under Settings › Storage › Data Retention › Archiving, Settings › Storage › Data Retention › Data Cleanup, Settings › Storage › Data Retention › Auto-Expunge, Settings › Storage › Data Retention › Telemetry\). The value is a duration in milliseconds; the default is `2592000000` \(thirty days\), meaning messages older than thirty days are removed during the routine auto-expunge run. Leaving the field unset keeps messages in the inbox indefinitely unless removed by the client or the account holder.

 計畫收件匣的保留期限由 \[資料保留\]`expungeSchedulingInboxAfter`單例中的 \[ \([https://stalw.art/docs/ref/object/data-retention](https://stalw.art/docs/ref/object/data-retention)\) \([https://stalw.art/docs/ref/object/data-retention#expungeschedulinginboxafter](https://stalw.art/docs/ref/object/data-retention#expungeschedulinginboxafter)\) （可在 WebUI的「設定」&gt;「儲存」&gt;「資料保留」&gt;「歸檔」、「設定」&gt;「儲存」&gt;「資料保留」&gt;「資料清理」、「設定」&gt;「儲存」&gt;「資料保留」&gt;「自動清除」和「設定」&gt;「儲存」&gt;「資料保留」&gt;「遙測」中找到）。該值以毫秒為單位表示持續時間；預設值為`2592000000` （30 天），這表示超過 30 天的郵件將在例行自動清除期間刪除。如果未設定此字段，則郵件將無限期地保留在收件匣中，除非用戶端或帳戶持有人將其刪除。

## HTTP RSVP

 Stalwart allows participants to respond to calendar invitations using a web link. When enabled, a unique RSVP URL is included in the iMIP invitation email sent to each attendee. Recipients can click the link to accept, decline, or tentatively respond to the invitation through a web interface, without needing a CalDAV-capable client.

 Stalwart 允許與會者使用網頁連結回覆日曆邀請。啟用此功能後，發送給每位與會者的 iMIP 邀請郵件中都會包含一個唯一的RSVP URL 。收件人可以透過網頁介面點擊連結接受、拒絕或初步回覆邀請，無需使用支援 CalDAV 的用戶端。

 This is particularly useful when scheduling with external participants or with clients that do not support calendaring or scheduling protocols.

 在與外部參與者或不支援日曆或日程安排協議的客戶進行日程安排時，這尤其有用。

### Endpoint｜端點

 The RSVP endpoint is accessible at `https://<server-host>/calendar/rsvp`, where `<server-host>` is based on the configured hostname. Accessing this URL serves a self-contained web page; it never records a response by itself, so link scanners and mail gateways that follow links in messages cannot answer on the attendee’s behalf.

 RSVP端點可透過`https://<server-host>/calendar/rsvp`訪問，其中`<server-host>`基於配置的 主機名稱 。造訪此URL會提供一個獨立的網頁；它本身不會記錄回應，因此追蹤訊息中連結的連結掃描器和郵件網關無法代表與會者進行回應。

 The page reads the signed token from the `i` query parameter and calls `POST /api/calendar/rsvp` to do the actual work. That endpoint takes a JSON body and is used twice: first with only the token, to retrieve the invitation details, and then with a participation status, to record the response.

 此頁面從`i`查詢參數中讀取已簽署的令牌，並呼叫`POST /api/calendar/rsvp`執行實際操作。此端點接收一個JSON請求體，並被使用兩次：第一次僅使用令牌，用於檢索邀請詳情；第二次使用參與狀態，用於記錄回應。

```json
{ "token": "<signed token>", "partstat": "accepted", "comment": "Bringing dessert" }
```

`partstat` accepts `accepted`, `declined` or `tentative`, and the optional `comment` is a short note for the organizer. The response is one of `invitation` \(the event details\), `recorded` \(the stored participation status\), or `error` together with a localised `message`.

`partstat`接受`accepted`, `declined`或`tentative` ，可選的`comment`是給組織者的簡短說明。回應可以是`invitation` （活動詳情）、 `recorded` （已儲存的參與狀態）或`error`以及本地化的`message`之一。

 Responses are applied directly to the organizer’s calendar and a reply is placed in their Scheduling Inbox, without an intermediate email.

 回覆將直接應用到組織者的日曆中，回复內容將直接發送到他們的日程安排收件箱，無需中間電子郵件。

### Enabling｜啟用

 HTTP RSVP is enabled by default. The feature is disabled by setting httpRsvpEnable on the CalendarScheduling singleton to `false`. When disabled, RSVP links are no longer included in outgoing iMIP messages and the RSVP endpoint stops serving requests.

 HTTP RSVP預設啟用。若要停用此功能，請將 CalendarScheduling 單例中的 httpRsvpEnable設定為`false` 。停用後， RSVP連結將不再包含在傳出的 iMIP 訊息中，且RSVP端點將停止處理請求。

### Custom URL｜訂製URL

 Stalwart builds the RSVP URL from the configured server.hostname. The base URL used in invitation emails can be overridden by setting httpRsvpUrl. The path component `/calendar/rsvp` is fixed, but the hostname and any prefix path can be customised. This is particularly useful when deploying Stalwart behind a reverse proxy or on a different hostname.

 Stalwart 會依照配置的 server.hostname建構RSVP URL 。邀請郵件中使用的基本路徑URL可以透過設定 httpRsvpUrl來覆寫。路徑組件`/calendar/rsvp`是固定的，但主機名稱和任何前綴路徑都可以自訂。這在將 Stalwart 部署在反向代理程式後或不同的主機名稱時尤其有用。

### Expiration｜到期日

 httpRsvpLinkExpiry defines how long an RSVP link remains valid after being issued. The value is a duration in milliseconds; the default is `7776000000` \(ninety days\). Once expired, the link no longer allows a response.

 httpRsvpLinkExpiry定義了連結在發出後保持有效的時間。該值以RSVP為單位；預設值為`7776000000` （90 天）。連結過期後，將不再允許回應。

 A representative HTTP RSVP configuration:

 典型的HTTP RSVP配置：

```json
{
  "httpRsvpEnable": true,
  "httpRsvpUrl": "https://calendar.example.org/custom-path/calendar/rsvp",
  "httpRsvpLinkExpiry": 604800000
}
```

## Branding and templating｜品牌和模板

 Stalwart supports custom branding and templating for calendar scheduling so that outbound invitations and RSVP responses can be aligned with organisational branding.

 Stalwart 支援自訂品牌和日曆安排模板，以便對外邀請和RSVP回覆可以與組織品牌保持一致。

 This feature is available exclusively in the Enterprise Edition of Stalwart and not included in the Community Edition.

 此功能僅在 Stalwart 的 企業版中提供，社群版不包含此功能。

### Templates｜範本

 Stalwart ships with a built-in default for both the scheduling email and the RSVP web page. Both are set on the CalendarScheduling singleton.

 Stalwart 內建了行程表電子郵件和RSVP網頁的預設設定。兩者都設置在 CalendarScheduling 單例中。

#### iMIP email template｜iMIP電子郵件模板

 The iMIP template renders outbound iMIP scheduling messages \(invitations, updates, cancellations\). Each message contains a rich HTML MIME part rendered from the template, including event details, sender information, and the RSVP link \(if HTTP RSVP is enabled\). A custom template can be supplied through emailTemplate.

 iMIP 範本用於渲染出站 iMIP 調度訊息（邀請、更新、取消）。每個訊息都包含一個由模板渲染的豐富的HTML MIME部分，其中包括事件詳情、發件人信息和RSVP鏈接（如果啟用了HTTP RSVP ）。可透過 emailTemplate提供自訂範本。

#### HTTP RSVP web page｜HTTP RSVP網頁

 The RSVP page is a static HTML document served as-is; it is not rendered from template variables. A replacement page can be supplied through httpRsvpTemplate, and is returned verbatim in place of the built-in one.

 RSVP頁面是一個靜態HTML文檔，直接按原樣提供；它並非由模板變數渲染而成。可以透過 httpRsvpTemplate提供替換頁面，替換頁面將原樣返回以取代內建頁面。

 A custom page is responsible for the whole flow: read the `i` query parameter, call `POST /api/calendar/rsvp` with the token to load the invitation, render it, and post the chosen participation status back. The endpoint returns localised labels alongside the event data, so a custom page does not need to ship its own translations.

 自訂頁面負責整個流程：讀取`i`查詢參數，使用令牌呼叫`POST /api/calendar/rsvp`載入邀請，渲染邀請，並將選擇的參與狀態傳回。該端點會傳回本地化標籤以及活動數據，因此自訂頁面無需自行提供翻譯。

### Logo｜標識

 Both default templates include a logo, which by default is the system-wide branding logo. The logo can be overridden on a per-tenant or per-domain basis, so that different business units or hosted domains display their own branding. For details, refer to the Branding section.

 兩個預設模板都包含一個徽標，預設使用的是系統通用的品牌徽標。您可以按租戶或按網域覆蓋此徽標，以便不同的業務部門或託管網域顯示各自的品牌標識。有關詳細信息，請參閱品牌部分。
