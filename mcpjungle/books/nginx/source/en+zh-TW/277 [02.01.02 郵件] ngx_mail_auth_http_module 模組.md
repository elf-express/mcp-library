Добавляет указанный заголовок к запросам, посылаемым на сервер аутентификации. Заголовок можно использовать в качестве shared secret для проверки, что запрос поступил от nginx. Например:

將指定的標頭新增至傳送至身份驗證伺服器的請求中。此標頭可用作共用金鑰，以驗證請求是否來自 nginx。例如：

> ```
> auth_http_header X-Auth-Key "secret_string";
> ```

Задаёт таймаут общения с сервером аутентификации.

指定與認證伺服器通訊的逾時時間。

#### Протокол｜協定

Для общения с сервером аутентификации используется протокол HTTP. Данные в теле ответа игнорируются, информация передаётся только в заголовках.

HTTP協定用於與認證伺服器通訊。響應體中的資料將被忽略；訊息僅在回應頭中傳輸。

Примеры запросов и ответов:

請求和回應範例：

Запрос:

要求：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: plain # plain/apop/cram-md5/external
>
> 身份驗證方法：plain # plain/apop/cram-md5/external
> Auth-User: user
>
> Auth-User：用戶
> Auth-Pass: password
>
> 授權碼：密碼
> Auth-Protocol: imap # imap/pop3/smtp
>
> 身份驗證協定：imap # imap/pop3/smtp
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> ```

Хороший ответ:

好的回答：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: OK
>
> 身份驗證狀態： OK
> Auth-Server: 198.51.100.1
>
> 認證伺服器： 198.51.100.1
> Auth-Port: 143
>
> 認證埠：143
> ```

Плохой ответ:

錯誤答案：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: Invalid login or password
>
> 身份驗證狀態：登入名稱或密碼無效
> Auth-Wait: 3
>
> 授權等待：3
> ```

Если заголовка “Auth-Wait”（授權等待） нет, то после выдачи ошибки соединение будет закрыто. В текущей реализации на каждую попытку аутентификации выделяется память, которая освобождается только при завершении сессии. Поэтому число неудачных попыток аутентификации в рамках одной сессии должно быть ограничено — после 10-20 попыток (номер попытки передаётся в заголовке “Auth-Login-Attempt”（身份驗證登入嘗試）) сервер должен выдать ответ без заголовка “Auth-Wait”（授權等待）.

如果沒有“Auth-Wait”（授權等待）頭部，則在回傳錯誤後連接將被關閉。在當前實作中，每次身份驗證嘗試都會分配內存，並且只有在會話終止時才會釋放。因此，單一會話中的驗證失敗嘗試次數應受到限制：在 10-20 次嘗試後（嘗試次數包含在“Auth-Login-Attempt”（身份驗證登入嘗試）頭部中），伺服器應傳回不包含“Auth-Wait”（授權等待）頭部的回應。

При использовании APOP или CRAM-MD5 запрос и ответ будут выглядеть так:

使用APOP或CRAM-MD5請求和回應將如下所示：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: apop
>
> 身份驗證方法：apop
> Auth-User: user
>
> Auth-User：用戶
> Auth-Salt: <238188073.1163692009@mail.example.com>
>
> 驗證鹽：< 238188073.1163692009 @mail.example.com>
> Auth-Pass: auth_response
>
> 身份驗證密碼：auth_response
> Auth-Protocol: imap
>
> 身份驗證協定：IMAP
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> ```

Хороший ответ:

好的回答：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: OK
>
> 身份驗證狀態： OK
> Auth-Server: 198.51.100.1
>
> 認證伺服器： 198.51.100.1
> Auth-Port: 143
>
> 認證埠：143
> Auth-Pass: plain-text-pass
>
> 身份驗證密碼：明文密碼
> ```

Если в ответе есть заголовок “Auth-User”（認證用戶）, то он переопределяет имя пользователя, используемое для аутентификации с бэкендом.

如果回應包含“Auth-User”（認證用戶）標頭，則會覆寫用於向後端進行身份驗證的使用者名稱。

Для SMTP в ответе дополнительно учитывается заголовок “Auth-Error-Code”（身份驗證錯誤代碼） — если он есть, то используется как код ответа в случае ошибки. Если его нет, то по умолчанию к “Auth-Status”（身份驗證狀態） будет добавлен код 535 5.7.0.

對於SMTP回應中也會考慮“Auth-Error-Code”（身份驗證錯誤代碼）標頭－如果存在，則將其用作錯誤時的回應碼。如果不存在，則預設會將5.7.0代碼附加到“Auth-Status”（身份驗證狀態） 。

Например, если от сервера аутентификации будет получен ответ:

例如，如果從身份驗證伺服器收到以下回應：

> ```yaml
> HTTP/1.0 200 OK
> Auth-Status: Temporary server problem, try again later
>
> 身份驗證狀態：伺服器暫時出現問題，請稍後重試。
> Auth-Error-Code: 451 4.3.0
>
> 驗證錯誤碼：451 4.3.0
> Auth-Wait: 3
>
> 授權等待：3
> ```

то по SMTP клиенту будет выдана ошибка

然後客戶端將根據SMTP收到錯誤。

> ```
> 451 4.3.0 Temporary server problem, try again later
>
> 451 4.3.0伺服器暫時出現問題，請稍後再試。
> ```

Если при проксировании SMTP не требуется аутентификация, запрос будет выглядеть так:

如果代理SMTP時不需要身份驗證，則請求將如下所示：

> ```yaml
> GET /auth HTTP/1.0
> Host: localhost
>
> 主機：localhost
> Auth-Method: none
>
> 身份驗證方法：無
> Auth-User:
>
> Auth-User：
> Auth-Pass:
>
> 授權碼：
> Auth-Protocol: smtp
>
> 身份驗證協定：smtp
> Auth-Login-Attempt: 1
>
> 身份驗證登入嘗試：1
> Client-IP: 192.0.2.42
>
> 客戶- IP: 192.0.2.42
> Client-Host: client.example.org
>
> 用戶端主機：client.example.org
> Auth-SMTP-Helo: client.example.org
>

Для клиентского соединения по протоколу SSL/TLS (1.7.11) добавляется заголовок “Auth-SSL”（認證-SSL）, и если директива [ssl\_verify\_client](<284 [02.01.02 郵件] 模組 ngx_mail_ssl_module.md#ssl_verify_client>) включена, заголовок “Auth-SSL-Verify”（身份驗證-SSL驗證） содержит результат проверки клиентского сертификата: “`SUCCESS`”, “`FAILED:``*reason*`” и, если сертификат не был предоставлен, “`NONE`”.

對於使用SSL/TLS ( 1.7.11 ) 協議的客戶端連接，會添加“Auth-SSL”（認證-SSL）標頭；如果啟用了 [ssl\_verify\_client](<284 [02.01.02 郵件] 模組 ngx_mail_ssl_module.md#ssl_verify_client>)指令，則“Auth-SSL-Verify”（身份驗證-SSL驗證） `SUCCESS` /3/3」憑證`FAILED:``*reason*` ”，如果沒有提供證書，則為“ `NONE` ”。

> До версии 1.11.7 результат “`FAILED`” не содержал строку `*reason*`.
>
> 在版本1.11.7 「 `FAILED` 」的結果不包含字串`*reason*` 。

Если клиентский сертификат был предоставлен, информация о нём передаётся в следующих заголовках запроса: “Auth-SSL-Subject”, “Auth-SSL-Issuer”（身份驗證 SSL 頒發者）, “Auth-SSL-Serial” и “Auth-SSL-Fingerprint”（身份驗證 SSL 指紋）. Если директива [auth\_http\_pass\_client\_cert](#auth_http_pass_client_cert) включена, сам сертификат передаётся в заголовке “Auth-SSL-Cert”（身份驗證 SSL 憑證）. Протокол и шифр установленного соединения передаются в заголовках “Auth-SSL-Protocol”（身份驗證 SSL 協議） и “Auth-SSL-Cipher”（身份驗證 SSL 密碼） (1.21.2). Запрос будет выглядеть так:

如果提供了用戶端證書，則其資訊會透過以下請求頭傳輸： “Auth-SSL-Subject”, “Auth-SSL-Issuer”（身份驗證 SSL 頒發者）, “Auth-SSL-Serial”和“Auth-SSL-Fingerprint”（身份驗證 SSL 指紋） 。如果啟用了 [auth\_http\_pass\_client\_cert](#auth_http_pass_client_cert)指令，則憑證本身會透過“Auth-SSL-Cert”（身份驗證 SSL 憑證）頭傳送。已建立連線的協定和密碼套件會透過“Auth-SSL-Protocol”（身份驗證 SSL 協議）和“Auth-SSL-Cipher”（身份驗證 SSL 密碼） ( 1.21.2 ) 頭傳輸。請求將如下所示：

При использовании [протокола PROXY](<278 [02.01.02 郵件] 模組 ngx_mail_core_module.md#proxy_protocol>), информация о нём передаётся в следующих заголовках запроса: “Proxy-Protocol-Addr”（代理協定地址）, “Proxy-Protocol-Port”（代理協定連接埠）, “Proxy-Protocol-Server-Addr”（代理協定伺服器位址） и “Proxy-Protocol-Server-Port”（代理協定伺服器連接埠） (1.19.8).
