To configure an HTTPS server, the `ssl` parameter must be enabled on [listening sockets](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>) in the [server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>) block, and the locations of the [server certificate](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate>) and [private key](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate_key>) files should be specified:

要設定HTTPS伺服器，必須在[server](<056 [01.01.03 http] 模組 ngx_http_core_module.md#server>)區塊中的[監聽套接字](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>)上啟用`ssl`參數，並且應指定[伺服器憑證](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate>)和[私鑰](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate_key>)檔案的位置：

> ```
> server {
>
> 伺服器{
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.crt;
>
>     ssl_certificate www.example.com.crt;
>     ssl_certificate_key www.example.com.key;
>     ssl_protocols       TLSv1.2 TLSv1.3;
>
>     ssl_protocols TLSv1.2 TLSv1.3;
>     ssl_ciphers         HIGH:!aNULL:!MD5;
>
>     ssl_ciphers HIGH :!aNULL:! MD5 ;
>     ...
> }
> ```

The server certificate is a public entity. It is sent to every client that connects to the server. The private key is a secure entity and should be stored in a file with restricted access, however, it must be readable by nginx’s master process. The private key may alternately be stored in the same file as the certificate:

伺服器憑證是公開的，會傳送給每個連接到伺服器的用戶端。私鑰是安全的，應該儲存在存取受限的檔案中，但必須能夠被 nginx 的主進程讀取。私鑰也可以與憑證儲存在同一個檔案中。

> ```
>     ssl_certificate     www.example.com.cert;
>
>     ssl_certificate www.example.com.cert;
>     ssl_certificate_key www.example.com.cert;
> ```

in which case the file access rights should also be restricted. Although the certificate and the key are stored in one file, only the certificate is sent to a client.

在這種情況下，也應該限製文件存取權限。雖然憑證和金鑰儲存在同一個文件中，但只有憑證會被傳送給客戶端。

The directives [ssl\_protocols](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_protocols>) and [ssl\_ciphers](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_ciphers>) can be used to limit connections to include only the strong versions and ciphers of SSL/TLS. By default nginx uses “`ssl_protocols TLSv1.2 TLSv1.3`” and “`ssl_ciphers HIGH:!aNULL:!MD5`”, so configuring them explicitly is generally not needed. Note that default values of these directives were [changed](#compatibility) several times.

指令 [ssl\_protocols](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_protocols>)和 [ssl\_ciphers](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_ciphers>)可用於限制連接，使其僅包含SSL/TLS的強版本和密碼套件。 nginx 預設使用“ `ssl_protocols TLSv1.2 TLSv1.3` ”和“ `ssl_ciphers HIGH:!aNULL:!MD5` ”，因此通常無需明確配置它們。請注意，這些指令的預設值已多次變更(https://nginx.org/en/docs/http/configuring_https_servers.html#compatibility) 。

#### HTTPS server optimization｜HTTPS伺服器優化

SSL operations consume extra CPU resources. On multi-processor systems several [worker processes](<125 [01.01 文件] 核心功能.md#worker_processes>) should be run, no less than the number of available CPU cores. The most CPU-intensive operation is the SSL handshake. There are two ways to minimize the number of these operations per client: the first is by enabling [keepalive](<056 [01.01.03 http] 模組 ngx_http_core_module.md#keepalive_timeout>) connections to send several requests via one connection and the second is to reuse SSL session parameters to avoid SSL handshakes for parallel and subsequent connections. The sessions are stored in an SSL session cache shared between workers and configured by the [ssl\_session\_cache](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>) directive. One megabyte of the cache contains about 4000 sessions. The default cache timeout is 5 minutes. It can be increased by using the [ssl\_session\_timeout](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>) directive. Here is a sample configuration optimized for a multi-core system with 10 megabyte shared session cache:

SSL 操作會消耗額外的 CPU 資源。在多處理器系統上，應運行多個[工作進程](<125 [01.01 文件] 核心功能.md#worker_processes>)，不少於可用的CPU核心數量。 CPU 最密集的操作是SSL 握手。有兩種方法可以最大限度地減少每個客戶端的這些操作數量：第一種是啟用 [keepalive](<056 [01.01.03 http] 模組 ngx_http_core_module.md#keepalive_timeout>) 連接以透過一個連接發送多個請求，第二種是重用 SSL 會話參數以避免並行和後續連接的 SSL 握手。會話儲存在工作人員之間共用的 SSL 會話快取中，並由 [ssl\_session\_cache](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_cache>) 指令配置。 1 MB 的快取包含約 4000 個會話。預設快取逾時為 5 分鐘。可以透過使用 [ssl\_session\_timeout](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_session_timeout>) 指令來增加它。以下是針對具有 10 MB 共享會話快取的多核心系統進行最佳化的範例配置：

> ```
> worker_processes auto;
>
> worker_processes 自動；
> 
> http {
>
> http{
>     ssl_session_cache   shared:SSL:10m;
>
>     ssl_session_cache 共享: SSL :10m;
>     ssl_session_timeout 10m;
> 
>     server {
>
>     伺服器{
>         listen              443 ssl;
>
>         監聽 443 ssl；
>         server_name         www.example.com;
>
>         伺服器名稱 www.example.com；
>         keepalive_timeout   70;
>
>         keepalive_timeout 70;
> 
>         ssl_certificate     www.example.com.crt;
>
>         ssl_certificate www.example.com.crt;
>         ssl_certificate_key www.example.com.key;
>         ssl_protocols       TLSv1.2 TLSv1.3;
>
>         ssl_protocols TLSv1.2 TLSv1.3;
>         ssl_ciphers         HIGH:!aNULL:!MD5;
>
>         ssl_ciphers HIGH :!aNULL:! MD5 ;
>         ...
> ```

#### SSL certificate chains｜SSL證書鏈

Some browsers may complain about a certificate signed by a well-known certificate authority, while other browsers may accept the certificate without issues. This occurs because the issuing authority has signed the server certificate using an intermediate certificate that is not present in the certificate base of well-known trusted certificate authorities which is distributed with a particular browser. In this case the authority provides a bundle of chained certificates which should be concatenated to the signed server certificate. The server certificate must appear before the chained certificates in the combined file:

某些瀏覽器可能會對知名憑證授權單位簽發的憑證提出異議，而其他瀏覽器則可能毫無問題地接受該憑證。這是因為頒發機構使用了一個中間憑證對伺服器憑證進行了簽名，而該中間憑證並不存在於特定瀏覽器隨附的知名可信任憑證授權單位的憑證庫中。在這種情況下，頒發機構會提供一組鍊式證書，這些證書應與已簽署的伺服器證書連接起來。在合併後的憑證檔案中，伺服器憑證必須位於鍊式憑證之前：

> ```bash
>
> ````bash
> $ cat www.example.com.crt bundle.crt > www.example.com.chained.crt
> ```

The resulting file should be used in the [ssl\_certificate](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate>) directive:

產生的檔案應在 [ssl\_certificate](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl_certificate>)指令中使用：

> ```
> server {
>
> 伺服器{
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.chained.crt;
>
>     ssl_certificate www.example.com.chained.crt;
>     ssl_certificate_key www.example.com.key;
>     ...
> }
> ```

If the server certificate and the bundle have been concatenated in the wrong order, nginx will fail to start and will display the error message:

如果伺服器憑證和捆綁包的連線順序錯誤，nginx 將無法啟動並顯示錯誤訊息：

> ```
> SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") failed
>
> SSL_CTX_use_PrivateKey_file(" ... /www.example.com.key") 失敗
>    (SSL: error:05800074:x509 certificate routines::key values mismatch)
>
>    （ SSL ：錯誤：05800074：x509 憑證程式::金鑰值不符）
> ```

because nginx has tried to use the private key with the bundle’s first certificate instead of the server certificate.

因為 nginx 嘗試使用捆綁包的第一個憑證中的私鑰，而不是伺服器憑證。

Browsers usually store intermediate certificates which they receive and which are signed by trusted authorities, so actively used browsers may already have the required intermediate certificates and may not complain about a certificate sent without a chained bundle. To ensure the server sends the complete certificate chain, the `openssl` command-line utility may be used, for example:

瀏覽器通常會儲存接收到的、由受信任機構簽署的中間證書，因此常用的瀏覽器可能已經擁有所需的中間證書，並且可能不會對缺少完整證書鏈的證書發出警告。為了確保伺服器發送完整的憑證鏈，可以使用`openssl`命令列實用程序，例如：

> ```bash
>
> ````bash

#### A single HTTP/HTTPS server｜單一HTTP/HTTPS伺服器

It is possible to configure a single server that handles both HTTP and HTTPS requests:

可以設定一台伺服器來處理HTTP和HTTPS請求：

> ```
> server {
>
> 伺服器{
>     listen              80;
>
>     聽 80；
>     listen              443 ssl;
>
>     監聽 443 ssl；
>     server_name         www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate     www.example.com.crt;
>
>     ssl_certificate www.example.com.crt;
>     ssl_certificate_key www.example.com.key;
>     ...
> }
> ```

> Prior to 0.7.14 SSL could not be enabled selectively for individual listening sockets, as shown above. SSL could only be enabled for the entire server using the [ssl](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl>) directive, making it impossible to set up a single HTTP/HTTPS server. The `ssl` parameter of the [listen](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>) directive was added to solve this issue. The use of the [ssl](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl>) directive in modern versions is thus discouraged; it was removed in 1.25.1.
>
> 如上所示， 0.7.14 SSL之前無法針對單一監聽套接字選擇性地啟用SSL指令只能為整個伺服器啟用(https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl) ，因此無法設定單一HTTP/HTTPS伺服器。為了解決這個問題，新增了 [listen](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>)指令的`ssl`參數。因此，不建議在現代版本中使用 [ssl](<098 [01.01.03 http] 模組 ngx_http_ssl_module.md#ssl>)指令；該指令已在1.25.1中移除。

#### Name-based HTTPS servers｜基於名稱的HTTPS伺服器

A common issue arises when configuring two or more HTTPS servers listening on a single IP address:

當配置兩個或多個監聽單一IP位址的HTTPS伺服器時，會出現一個常見問題：

> ```
> server {
>
> 伺服器{
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate www.example.com.crt;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.org;
>
>     伺服器名稱 www.example.org；
>     ssl_certificate www.example.org.crt;
>     ...
> }
> ```

With this configuration a browser receives the default server’s certificate, i.e. `www.example.com` regardless of the requested server name. This is caused by SSL protocol behaviour. The SSL connection is established before the browser sends an HTTP request and nginx does not know the name of the requested server. Therefore, it may only offer the default server’s certificate.

透過此配置，瀏覽器將接收預設伺服器的證書，即`www.example.com`，無論請求的伺服器名稱為何。這是由SSL協議行為引起的。 SSL連線是在瀏覽器發送HTTP請求之前建立的，並且nginx不知道請求的伺服器的名稱。因此，它可能只提供預設伺服器的憑證。

The oldest and most robust method to resolve the issue is to assign a separate IP address for every HTTPS server:

解決此問題的最古老、最可靠的方法是為每個HTTPS伺服器分配一個單獨的IP位址：

> ```
> server {
>
> 伺服器{
>     listen          192.168.1.1:443 ssl;
>
>     監聽192.168.1.1:443 ssl;
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ssl_certificate www.example.com.crt;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen          192.168.1.2:443 ssl;
>
>     監聽192.168.1.2:443 ssl;
>     server_name     www.example.org;
>
>     伺服器名稱 www.example.org；
>     ssl_certificate www.example.org.crt;
>     ...
> }
> ```

#### An SSL certificate with several names｜一份包含多個名稱的SSL證書

There are other ways that allow sharing a single IP address between several HTTPS servers. However, all of them have their drawbacks. One way is to use a certificate with several names in the SubjectAltName certificate field, for example, `www.example.com` and `www.example.org`. However, the SubjectAltName field length is limited.

還有其他方法允許多個HTTPS伺服器共享同一個IP位址。但是，所有這些方法都有其缺點。一種方法是在憑證的 SubjectAltName 欄位中使用多個名稱，例如`www.example.com`和`www.example.org` 。但是，SubjectAltName 欄位的長度是有限制的。

Another way is to use a certificate with a wildcard name, for example, `*.example.org`. A wildcard certificate secures all subdomains of the specified domain, but only on one level. This certificate matches `www.example.org`, but does not match `example.org` and `www.sub.example.org`. These two methods can also be combined. A certificate may contain exact and wildcard names in the SubjectAltName field, for example, `example.org` and `*.example.org`.

另一種方法是使用帶有通配符名稱的證書，例如`*.example.org` 。通配符憑證可以保護指定網域的所有子網域，但僅限於一級。此證書符合`www.example.org` ，但不符`example.org`和`www.sub.example.org` 。這兩種方法也可以結合使用。憑證的 SubjectAltName 欄位可以同時包含精確名稱和通配符名稱，例如`example.org`和`*.example.org` 。

It is better to place a certificate file with several names and its private key file at the *http* level of configuration to inherit their single memory copy in all servers:

最好將包含多個憑證名稱的憑證檔案及其私密金鑰檔案放在 *http* 層級的配置中，以便在所有伺服器上繼承它們的單一記憶體副本：

> ```
> ssl_certificate     common.crt;
>
> ssl_certificate common.crt;
> ssl_certificate_key common.key;
> 
> server {
>
> 伺服器{
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.com;
>
>     伺服器名稱 www.example.com；
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen          443 ssl;
>
>     監聽 443 ssl；
>     server_name     www.example.org;
>
>     伺服器名稱 www.example.org；
>     ...
> }
> ```

#### Server Name Indication｜伺服器名稱指示

A more generic solution for running several HTTPS servers on a single IP address is [TLS Server Name Indication extension](http://en.wikipedia.org/wiki/Server_Name_Indication) (SNI, RFC 6066), which allows a browser to pass a requested server name during the SSL handshake and, therefore, the server will know which certificate it should use for the connection. SNI is currently [supported](http://en.wikipedia.org/wiki/Server_Name_Indication#Support) by most modern browsers and is a mandatory-to-implement extension in TLSv1.3, though may not be used by some old or special clients.

在單一IP上執行多個HTTPS的更通用解決方案是使用伺服器名稱指示擴充功能 ( TLS (http://en.wikipedia.org/wiki/Server_Name_Indication) ( SNI, RFC )，它允許瀏覽器在SSL期間傳遞請求的伺服器名稱，從而使伺服器知道應該使用哪個憑證進行連線。目前，大多數現代瀏覽器都支援SNI (http://en.wikipedia.org/wiki/Server_Name_Indication#Support)而且它是 TLSv1.3 中強制實現的擴展，但某些舊版或特殊用戶端可能不支援。

> Only domain names can be passed in SNI, however some browsers may erroneously pass an IP address of the server as its name if a request includes literal IP address. One should not rely on this.
>
> SNI只能傳遞域名，但如果請求中包含字面地址IP ，某些瀏覽器可能會錯誤地將伺服器位址IP當作名稱傳遞。請勿依賴此行為。

In order to use SNI in nginx, it must be supported in both the OpenSSL library with which the nginx binary has been built as well as the library to which it is being dynamically linked at run time. OpenSSL supports SNI since 0.9.8f version if it was built with config option “--enable-tlsext”. Since OpenSSL 0.9.8j this option is enabled by default. If nginx was built with SNI support, then nginx will show this when run with the “-V” switch:

要在 nginx 中使用SNI ，nginx 二進位檔案建置時所使用的 OpenSSL 函式庫以及執行時間動態連結到的函式庫都必須支援該功能。如果 OpenSSL 在建置時使用了設定選項“--enable-tlsext”，則自0.9版本起，它支援SNI 。自 OpenSSL 0.9版本起，此選項預設為啟用。如果 nginx 在建置時使用了SNI支持，則在使用「-V」開關運行時，nginx 將顯示以下資訊：

> ```bash
>
> ````bash
> $ nginx -V
> ...
> TLS SNI support enabled
>
> TLS SNI支援已啟用
> ...
> ```

However, if the SNI-enabled nginx is linked dynamically to an OpenSSL library without SNI support, nginx displays the warning:

但是，如果啟用了SNI的nginx動態連結到不支援SNI的OpenSSL函式庫，nginx將顯示警告：

> ```
> nginx was built with SNI support, however, now it is linked
>
> nginx 最初是為SNI構建的，但是現在它已鏈接
> dynamically to an OpenSSL library which has no tlsext support,
>
> 動態地傳遞給不支援 tlsext 的 OpenSSL 函式庫，
> therefore SNI is not available
>
> 因此， SNI不可用
> ```

#### Compatibility｜相容性

-   The SNI support status has been shown by the “-V” switch since 0.8.21 and 0.7.62.  
    自0.8.21和0.7.62以來， SNI支持狀態已透過「-V」開關顯示。
-   The `ssl` parameter of the [listen](<056 [01.01.03 http] 模組 ngx_http_core_module.md#listen>) directive has been supported since 0.7.14. Prior to 0.8.21 it could only be specified along with the `default` parameter.  
    [listen] 指令的`ssl`參數自0.7.14起就已支援。在0.8.21之前(https://nginx.org/en/docs/http/ngx_http_core_module.html#listen)它只能與`default`參數一起指定。
-   SNI has been supported since 0.5.23.  
    自0.5.23以來， SNI一直受到支持。
-   The shared SSL session cache has been supported since 0.5.6.  
    自0.5.6以來，一直支援共享的SSL會話快取。

-   Version 1.27.3 and later: the default SSL protocols are TLSv1.2 and TLSv1.3 (if supported by the OpenSSL library). Otherwise, when OpenSSL 1.0.0 or older is used, the default SSL protocols are TLSv1 and TLSv1.1.  
    版本1.27.3及更高版本：預設SSL協定為TLSv1.2及TLSv1.3（若OpenSSL函式庫支援）。否則，當使用1.0.0或更早版本時，預設SSL協定為TLSv1和TLSv1.1。
-   Version 1.23.4 and later: the default SSL protocols are TLSv1, TLSv1.1, TLSv1.2, and TLSv1.3 (if supported by the OpenSSL library).  
    版本1.23.4及更高版本：預設SSL協定為 TLSv1、TLSv1.1、TLSv1.2 和 TLSv1.3（若 OpenSSL 函式庫支援）。
-   Version 1.9.1 and later: the default SSL protocols are TLSv1, TLSv1.1, and TLSv1.2 (if supported by the OpenSSL library).  
    版本1.9.1及更高版本：預設SSL協定為 TLSv1、TLSv1.1 和 TLSv1.2（若 OpenSSL 函式庫支援）。
-   Version 0.7.65, 0.8.19 and later: the default SSL protocols are SSLv3, TLSv1, TLSv1.1, and TLSv1.2 (if supported by the OpenSSL library).  
    版本0.7.65, 0.8.19及更高版本：預設SSL協定為 SSLv3、TLSv1、TLSv1.1 和 TLSv1.2（若 OpenSSL 函式庫支援）。
-   Version 0.7.64, 0.8.18 and earlier: the default SSL protocols are SSLv2, SSLv3, and TLSv1.  
    版本0.7.64, 0.8.18及更早版本：預設SSL協定為 SSLv2、SSLv3 和 TLSv1。

-   Version 1.0.5 and later: the default SSL ciphers are “`HIGH:!aNULL:!MD5`”.  
    版本1.0.5及更高版本：預設的SSL密碼為「 `HIGH:!aNULL:!MD5` 」。
-   Version 0.7.65, 0.8.20 and later: the default SSL ciphers are “`HIGH:!ADH:!MD5`”.  
    版本0.7.65, 0.8.20及更高版本：預設的SSL密碼為「 `HIGH:!ADH:!MD5` 」。
-   Version 0.8.19: the default SSL ciphers are “`ALL:!ADH:RC4+RSA:+HIGH:+MEDIUM`”.  
    版本0.8.19 ：預設的SSL密碼為「 `ALL:!ADH:RC4+RSA:+HIGH:+MEDIUM` 」。
-   Version 0.7.64, 0.8.18 and earlier: the default SSL ciphers are  
    版本0.7.64, 0.8.18及更早版本：預設的SSL密碼為  
    “`ALL:!ADH:RC4+RSA:+HIGH:+MEDIUM:+LOW:+SSLv2:+EXP`”.
