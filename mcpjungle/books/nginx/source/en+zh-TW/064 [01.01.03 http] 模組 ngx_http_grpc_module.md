The `ngx_http_grpc_module` module allows passing requests to a gRPC server (1.13.10). The module requires the [ngx\_http\_v2\_module](<108 [01.01.03 http] 模組 ngx_http_v2_module.md>) module.

`ngx_http_grpc_module`模組允許向 gRPC 伺服器 ( 1.13.10 ) 傳遞請求。此模組需要 [ngx\_http\_v2\_module](<108 [01.01.03 http] 模組 ngx_http_v2_module.md>)模組。

#### Example Configuration｜範例配置

> ```
> server {
>
> 伺服器 {
>     listen 9000;
>
>     聽 9000；
> 
>     http2 on;
>
>     http2 已開啟；
> 
>     location / {
>
>     地點 / {
>         grpc_pass 127.0.0.1:9000;
>
>         grpc_pass 127.0.0.1:9000 ;
>     }
> }
> ```

Defines conditions under which access to a gRPC server is allowed or [denied](#denied). If all string parameters are not empty and not equal to “0” then the access is allowed. The conditions are evaluated each time before a connection to a gRPC server is established. Parameter values can contain variables:

定義允許或拒絕存取 gRPC 伺服器的條件(https://nginx.org/en/docs/http/ngx_http_grpc_module.html#denied) 。如果所有字串參數均不為空且不等於“0”，則允許存取。每次建立與 gRPC 伺服器的連線之前都會評估這些條件。參數值可以包含變數：

> ```
> geo $upstream_last_addr $allow {
>     volatile;
>
>     易揮發的;
>     10.10.0.0/24        1;
> }
>

>
>     http2 已開啟；

>
>     地點 / {
>         grpc_pass           localhost:9000;
>
>         grpc_pass localhost:9000;
>         grpc_allow_upstream $allow;
>         ...
>     }
> }
> ```

Makes outgoing connections to a gRPC server originate from the specified local IP address with an optional port. Parameter value can contain variables. The special value `off` cancels the effect of the `grpc_bind` directive inherited from the previous configuration level, which allows the system to auto-assign the local IP address and port.

使發送至 gRPC 伺服器的出站連線源自指定的本機位址IP連接埠可選。參數值可以包含變數。特殊值`off`會取消從上一配置等級繼承的`grpc_bind`指令的效果，該指令允許系統自動分配本地位址IP和連接埠。

The `transparent` parameter allows outgoing connections to a gRPC server originate from a non-local IP address, for example, from a real IP address of a client:

`transparent`參數允許從非本地IP位址（例如，客戶端的真實IP位址）發出到 gRPC 伺服器的出站連線：

> ```
> grpc_bind $remote_addr transparent;
> ```

In order for this parameter to work, it is usually necessary to run nginx worker processes with the [superuser](<125 [01.01 文件] 核心功能.md#user>) privileges. On Linux it is not required as if the `transparent` parameter is specified, worker processes inherit the `CAP_NET_RAW` capability from the master process. It is also necessary to configure kernel routing table to intercept network traffic from the gRPC server.

為了使此參數生效，通常需要以 [superuser](<125 [01.01 文件] 核心功能.md#user>)權限執行 nginx 工作進程。在 Linux 系統上則無需此操作，因為如果指定了`transparent`參數，工作進程會從主進程繼承`CAP_NET_RAW`權限。此外，還需要設定核心路由表以攔截來自 gRPC 伺服器的網路流量。

Sets the `*size*` of the buffer used for reading the response received from the gRPC server. The first part of the response usually contains a small header; if it exceeds the buffer size, the response is considered [invalid](#invalid_header). The response is passed to the client synchronously, as soon as it is received. By default, the buffer size is equal to one memory page. This is either 4K or 8K, depending on a platform. It can be made smaller, however.

設定用於讀取從 gRPC 伺服器接收的回應的緩衝區大小`*size*` 。反應的第一部分通常包含一個較小的頭部；如果頭部大小超過緩衝區大小，則該反應被視為無效（ (https://nginx.org/en/docs/http/ngx_http_grpc_module.html#invalid_header) ）。回應一旦被接收，就會同步傳遞給客戶端。預設情況下，緩衝區大小等於一個記憶體頁。根據平台的不同，該大小為 4K 或 8K。不過，緩衝區大小可以減少。

停用對來自 gRPC 伺服器的某些回應頭字段的處理。可以忽略以下欄位： “X-Accel-Redirect”（X-Accel-重定向）和“X-Accel-Charset” 。

If not disabled, processing of these header fields has the following effect:

如果未停用，處理這些標頭欄位會產生以下效果：

-   “X-Accel-Redirect”（X-Accel-重定向） performs an [internal redirect](<056 [01.01.03 http] 模組 ngx_http_core_module.md#internal>) to the specified URI;

    “X-Accel-Charset”設定響應的所需 [字元集](<055 [01.01.03 http] 模組 ngx_http_charset_module.md#charset>) 。

Determines whether gRPC server responses with codes greater than or equal to 300 should be passed to a client or be intercepted and redirected to nginx for processing with the [error\_page](<056 [01.01.03 http] 模組 ngx_http_core_module.md#error_page>) directive.

Specifies in which cases a request should be passed to the next server:

指定在哪些情況下應將請求傳遞給下一個伺服器：

`error`

an error occurred while establishing a connection with the server, passing a request to it, or reading the response header;

與伺服器建立連線、向伺服器發送請求或讀取回應標頭時發生錯誤；

`timeout`

a timeout has occurred while establishing a connection with the server, passing a request to it, or reading the response header;

與伺服器建立連線、向伺服器發送請求或讀取回應標頭時發生逾時；

`denied`

the server [denied](#grpc_allow_upstream) the connection (1.29.3);

伺服器[拒絕](#grpc_allow_upstream)連線(1.29.3);

> This parameter is available as part of our [commercial subscription](https://www.f5.com/products/nginx).
>
> 此參數作為我們的[商業訂閱](https://www.f5.com/products/nginx)的一部分提供。

`invalid_header`

a server returned an empty or invalid response;

伺服器傳回了空響應或無效回應；

`http_500`

a server returned a response with the code 500;

伺服器回傳了代碼為 500 的回應；

`http_502`

a server returned a response with the code 502;

伺服器回傳代碼為 502 的回應；

`http_503`

a server returned a response with the code 503;

伺服器回傳了代碼為 503 的回應；

`http_504`

a server returned a response with the code 504;

伺服器回傳代碼為 504 的回應；

`http_403`

a server returned a response with the code 403;

伺服器回傳了代碼為 403 的回應；

`http_404`

a server returned a response with the code 404;

伺服器回傳了代碼為 404 的回應；

`http_429`

a server returned a response with the code 429;

伺服器回傳代碼為 429 的回應；

`non_idempotent`

normally, requests with a [non-idempotent](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2) method (`POST`, `LOCK`, `PATCH`) are not passed to the next server if a request has been sent to an upstream server; enabling this option explicitly allows retrying such requests;

通常，如果請求已傳送至上游伺服器，則使用[非冪等](https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2)方法（`POST`, `LOCK`, `PATCH`）的請求不會傳遞到下一個伺服器；明確啟用此選項允許重試此類請求；

`off`

disables passing a request to the next server.

禁用向下一個伺服器傳遞請求。

One should bear in mind that passing a request to the next server is only possible if nothing has been sent to a client yet. That is, if an error or timeout occurs in the middle of the transferring of a response, fixing this is impossible.

需要注意的是，只有在尚未向客戶端發送任何資料的情況下，才能將請求傳遞給下一個伺服器。也就是說，如果在傳輸回應的過程中發生錯誤或逾時，則無法修復。

The directive also defines what is considered an [unsuccessful attempt](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#max_fails>) of communication with a server. The cases of `error`, `timeout`, `denied` and `invalid_header` are always considered unsuccessful attempts, even if they are not specified in the directive. The cases of `http_500`, `http_502`, `http_503`, `http_504`, and `http_429` are considered unsuccessful attempts only if they are specified in the directive. The cases of `http_403` and `http_404` are never considered unsuccessful attempts.

該指令也定義了與伺服器通訊的[不成功嘗試](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#max_fails>)。 `error`, `timeout`, `denied` 和 `invalid_header` 的情況始終被視為不成功的嘗試，即使它們未在指令中指定。僅當指令中指定時，`http_500`, `http_502`, `http_503`, `http_504`和`http_429`的情況才被視為不成功的嘗試。 `http_403`和`http_404`的案例絕不被認為是不成功的嘗試。

Passing a request to the next server can be limited by [the number of tries](#grpc_next_upstream_tries) and by [time](#grpc_next_upstream_timeout).

將請求傳遞到下一個伺服器可以受到[嘗試次數](#grpc_next_upstream_tries)和[時間](#grpc_next_upstream_timeout)的限制。
