В этом руководстве даётся начальное введение в nginx и описываются некоторые простые задачи, которые могут быть решены с его помощью. Предполагается, что nginx уже установлен на компьютере читателя. Если нет, см. [Установка nginx](<276 [02.01 文件] 安裝 nginx.md>). В этом руководстве описывается, как запустить и остановить nginx и перезагрузить его конфигурацию, объясняется, как устроен конфигурационный файл, и описывается, как настроить nginx для раздачи статического содержимого, как настроить прокси-сервер на nginx, и как связать nginx с приложением FastCGI.

本指南對 Nginx 進行基本介紹，並描述一些可以使用 Nginx 完成的簡單任務。假設讀者的計算機上已安裝 Nginx。如果尚未安裝，請參閱[安裝 Nginx](<276 [02.01 文件] 安裝 nginx.md>) 。本指南將介紹如何啟動和停止 Nginx 以及如何重新載入其配置，解釋設定檔結構，並介紹如何配置 Nginx 以提供靜態內容、如何在 Nginx 上設定代理伺服器以及如何將 Nginx 連接到 FastCGI 應用程式。

У nginx есть один главный и несколько рабочих процессов. Основная задача главного процесса — чтение и проверка конфигурации и управление рабочими процессами. Рабочие процессы выполняют фактическую обработку запросов. nginx использует модель, основанную на событиях, и зависящие от операционной системы механизмы для эффективного распределения запросов между рабочими процессами. Количество рабочих процессов задаётся в конфигурационном файле и может быть фиксированным для данной конфигурации или автоматически устанавливаться равным числу доступных процессорных ядер (см. [worker\_processes](<285 [02.01 文件] 基本功能.md#worker_processes>)).

Nginx 包含一個主流程和多個工作進程。主進程的主要功能是讀取和驗證配置並管理工作進程。工作進程負責實際的請求處理。 Nginx 使用事件驅動模型和作業系統特定的機制來有效地將請求分配給各個工作進程。工作進程的數量在設定檔中指定，可以針對特定配置固定，也可以自動設定為可用處理器核心數（請參閱 [worker\_processes](<285 [02.01 文件] 基本功能.md#worker_processes>) ）。

Как работают nginx и его модули, определяется в конфигурационном файле. По умолчанию, конфигурационный файл называется `nginx.conf` и расположен в каталоге `/usr/local/nginx/conf`, `/etc/nginx` или `/usr/local/etc/nginx`.

nginx及其模組的運作由設定檔決定。預設情況下，設定檔名稱為`nginx.conf` ，位於`/usr/local/nginx/conf`, `/etc/nginx`或`/usr/local/etc/nginx`目錄中。

#### Запуск, остановка, перезагрузка конфигурации｜啟動、停止、重新載入配置

Чтобы запустить nginx, нужно выполнить исполняемый файл. Когда nginx запущен, им можно управлять, вызывая исполняемый файл с параметром `-s`. Используйте следующий синтаксис:

要啟動 nginx，您需要執行其可執行檔。 nginx 運行後，您可以透過呼叫帶有`-s`參數的可執行檔來控制它。使用以下語法：

> ```
> nginx -s сигнал
>
> nginx -s 訊號
> ```

Где *сигнал* может быть одним из нижеследующих:

其中 *signal* 可以是下列幾種情況之一：

-   `stop` — быстрое завершение  
    `stop` - 快速完成
-   `quit` — плавное завершение  
    `quit` — 平滑完成
-   `reload` — перезагрузка конфигурационного файла  
    `reload` — 重新載入設定檔
-   `reopen` — переоткрытие лог-файлов  
    `reopen` — 重新開啟日誌文件

Например, чтобы остановить процессы nginx с ожиданием окончания обслуживания текущих запросов рабочими процессами, можно выполнить следующую команду:

例如，要在等待工作進程完成目前請求的處理期間停止 nginx 進程，您可以執行下列命令：

> ```
> nginx -s quit
>
> nginx -s 退出
> ```

> Команда должна быть выполнена под тем же пользователем, под которым был запущен nginx.
>
> 該指令必須以啟動 nginx 的相同使用者身分執行。

Изменения, сделанные в конфигурационном файле, не будут применены, пока команда перезагрузить конфигурацию не будет вручную отправлена nginx’у или он не будет перезапущен. Для перезагрузки конфигурации выполните:

對設定檔所做的變更不會立即生效，除非您手動向 nginx 發送重新載入設定指令或重新啟動 nginx。若要重新載入配置，請執行：

> ```
> nginx -s reload
>
> nginx -s 重新載入
> ```

Получив сигнал, главный процесс проверяет правильность синтаксиса нового конфигурационного файла и пытается применить конфигурацию, содержащуюся в нём. Если это ему удаётся, главный процесс запускает новые рабочие процессы и отправляет сообщения старым рабочим процессам с требованием завершиться. В противном случае, главный процесс откатывает изменения и продолжает работать со старой конфигурацией. Старые рабочие процессы, получив команду завершиться, прекращают принимать новые запросы и продолжают обслуживать текущие запросы до тех пор, пока все такие запросы не будут обслужены. После этого старые рабочие процессы завершаются.

收到訊號後，主程序會檢查新設定檔的語法，並嘗試套用其中包含的設定。如果成功，主進程會啟動新的工作進程，並向原有的工作進程發送終止請求。否則，主進程會回滾更改，並繼續使用舊配置。原有的工作進程在收到終止命令後，會停止接受新的請求，並繼續處理目前請求，直到所有請求都已處理完畢。之後，原有的工作進程才會終止。

Посылать сигналы процессам nginx можно также средствами Unix, такими как утилита `kill`. В этом случае сигнал отправляется напрямую процессу с данным ID. ID главного процесса nginx записывается по умолчанию в файл `nginx.pid` в каталоге `/usr/local/nginx/logs` или `/var/run`. Например, если ID главного процесса равен 1628, для отправки сигнала QUIT, который приведёт к плавному завершению nginx, нужно выполнить:

您也可以使用 Unix 工具（例如`kill`工具）向 nginx 進程發送訊號。在這種情況下，訊號將直接傳送到具有指定ID. ID主 nginx 進程的進程，預設會寫入`nginx.pid`或`/usr/local/nginx/logs`目錄中的`/var/run`檔案。例如，如果主進程的ID為 1628，則要發送QUIT訊號（這將導致 nginx 優雅地關閉），您可以執行以下命令：

> ```
> kill -s QUIT 1628
> ```

Для просмотра списка всех запущенных процессов nginx может быть использована утилита `ps`, например, следующим образом:

要查看所有正在運行的 nginx 進程的列表，可以使用`ps`工具，例如，如下所示：

> ```
> ps -ax | grep nginx
> ```

Дополнительную информацию об отправке сигналов процессам nginx можно найти в [Управление nginx](<204 [02.01 文件] nginx 管理.md>).

有關向 nginx 進程發送訊號的更多信息，請參閱 [管理 nginx](<204 [02.01 文件] nginx 管理.md>) 。

#### Структура конфигурационного файла｜設定檔結構

nginx состоит из модулей, которые настраиваются директивами, указанными в конфигурационном файле. Директивы делятся на простые и блочные. Простая директива состоит из имени и параметров, разделённых пробелами, и оканчивается точкой с запятой (`;`). Блочная директива устроена так же, как и простая директива, но вместо точки с запятой после имени и параметров следует набор дополнительных инструкций, помещённых внутри фигурных скобок (`{` и `}`). Если у блочной директивы внутри фигурных скобок можно задавать другие директивы, то она называется контекстом (примеры: [events](<285 [02.01 文件] 基本功能.md#events>), [http](<221 [02.01.01 http] 模組 ngx_http_core_module.md#http>), [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>) и [location](<221 [02.01.01 http] 模組 ngx_http_core_module.md#location>)).

nginx 由模組組成，這些模組透過設定檔中指定的指令進行設定。指令分為簡單指令和區塊指令。簡單指令由名稱和參數組成，參數之間以空格分隔，並以分號結尾（ `;` ）。塊指令的結構與簡單指令相同，但名稱和參數後面不是分號，而是一組放在花括號內的附加指令（ `{`和`}` ）。如果區塊指令可以在花括號內指定其他指令，則稱為上下文（例如：[events](<285 [02.01 文件] 基本功能.md#events>) 、[http](<221 [02.01.01 http] 模組 ngx_http_core_module.md#http>) 、[server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>)和 [location](<221 [02.01.01 http] 模組 ngx_http_core_module.md#location>) ）。

Директивы, помещённые в конфигурационном файле вне любого контекста, считаются находящимися в контексте [main](<285 [02.01 文件] 基本功能.md>). Директивы `events` и `http` располагаются в контексте `main`, `server` — в `http`, а `location` — в `server`.

放置在設定檔中任何上下文之外的指令被視為位於 [main 上下文](<285 [02.01 文件] 基本功能.md>)中。指令`events`和`http`位於上下文`main`, `server`中 — 在`http`中，以及`location`位於`server`中。

Часть строки после символа `#` считается комментарием.

`#`符號後面的部分被視為註釋。

#### Раздача статического содержимого｜提供靜態內容

Одна из важных задач конфигурации nginx — раздача файлов, таких как изображения или статические HTML-страницы. Рассмотрим пример, в котором в зависимости от запроса файлы будут раздаваться из разных локальных каталогов: `/data/www`, который содержит HTML-файлы, и `/data/images`, содержащий файлы с изображениями. Для этого потребуется отредактировать конфигурационный файл и настроить блок [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>) внутри блока [http](<221 [02.01.01 http] 模組 ngx_http_core_module.md#http>) с двумя блоками [location](<221 [02.01.01 http] 模組 ngx_http_core_module.md#location>).

nginx 設定的一項重要任務是提供檔案服務，例如圖片或HTML頁面。我們來看一個例子，根據請求的不同，檔案將從不同的本機目錄提供：包含HTML檔案`/data/www` ，以及包含圖片檔案的`/data/images` 。為此，您需要編輯設定文件，並在(https://nginx.org/ru/docs/http/ngx_http_core_module.html#location)兩個 location 區塊(https://nginx.org/ru/docs/http/ngx_http_core_module.html#http) [http 區塊內](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>)一個 [server] 區塊。

Во-первых, создайте каталог `/data/www` и положите в него файл `index.html` с любым текстовым содержанием, а также создайте каталог `/data/images` и положите в него несколько файлов с изображениями.

首先，建立一個目錄`/data/www` ，並在其中放入一個包含任意文字內容的檔案`index.html` ；然後建立一個目錄`/data/images` ，並在其中放入幾個圖片檔案。

Далее, откройте конфигурационный файл. Конфигурационный файл по умолчанию уже включает в себя несколько примеров блока `server`, большей частью закомментированных. Для нашей текущей задачи лучше закомментировать все такие блоки и добавить новый блок `server`:

接下來，開啟設定檔。預設設定檔中已經包含幾個`server`程式碼區塊的範例，大部分已被註解掉。對於我們目前的任務，最好註解掉所有此類程式碼區塊，並新增一個新的`server`程式碼區塊：

> ```
> http {
>     server {
>
>     伺服器 {
>     }
> }
> ```

В общем случае конфигурационный файл может содержать несколько блоков `server`, [различаемых](<272 [02.01.01 http] nginx 如何處理請求.md>) по портам, на которых они [слушают](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>), и по [имени сервера](<273 [02.01.01 http] 伺服器名稱.md>). Определив, какой `server` будет обрабатывать запрос, nginx сравнивает URI, указанный в заголовке запроса, с параметрами директив `location`, определённых внутри блока `server`.

通常，一個設定檔可以包含多個`server`區塊，這些區塊透過它們監聽的連接埠(https://nginx.org/ru/docs/http/request_processing.html)和伺服器名稱(https://nginx.org/ru/docs/http/server_names.html)來區分。在確定哪一個`server`將處理請求後，nginx (https://nginx.org/ru/docs/http/ngx_http_core_module.html#listen)請求頭中指定的URI與`server`塊內定義的`location`指令的參數進行比較。

В блок `server` добавьте блок `location` следующего вида:

在塊`server`中加入以下類型的塊`location` ：

> ```
> location / {
>
> 地點 / {
>     root /data/www;
>
>     根目錄 /data/www;
> }
> ```

Этот блок `location` задаёт “`/`” в качестве префикса, который сравнивается с URI из запроса. Для подходящих запросов добавлением URI к пути, указанному в директиве [root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>), то есть, в данном случае, к `/data/www`, получается путь к запрашиваемому файлу в локальной файловой системе. Если есть совпадение с несколькими блоками `location`, nginx выбирает блок с самым длинным префиксом. В блоке `location` выше указан самый короткий префикс, длины один, и поэтому этот блок будет использован, только если не будет совпадения ни с одним из остальных блоков `location`.

此`location`代碼區塊指定「 `/` 」作為前綴，並與請求中的URI進行比較。對於符合的請求，將URI附加到 [root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>)指令中指定的路徑（在本例中為`/data/www`後，即可得到本地檔案系統中請求檔案的路徑。如果多個`location`程式碼區塊匹配，nginx 將選擇前綴最長的程式碼區塊。上面的`location`代碼塊指定了最短的前綴（長度為 1），因此僅當其他`location`代碼塊均不匹配時才會使用。

Далее, добавьте второй блок `location`:

接下來，新增第二個模組`location` ：

> ```
> location /images/ {
>     root /data;
>
>     根 /data;
> }
> ```

Он будет давать совпадение с запросами, начинающимися с `/images/` (`location /` для них тоже подходит, но указанный там префикс короче).

它將匹配以`/images/`開頭的查詢（ `location /`也適用於它們，但那裡指定的前綴更短）。

Итоговая конфигурация блока `server` должна выглядеть следующим образом:

`server`模組的最終配置應如下所示：

> ```
> server {
>
> 伺服器 {
>     location / {
>
>     地點 / {
>         root /data/www;
>
>         根目錄 /data/www;
>     }
> 
>     location /images/ {
>         root /data;
>
>         根 /data;
>     }
> }
> ```

Это уже работающая конфигурация сервера, слушающего на стандартном порту 80 и доступного на локальном компьютере по адресу `http://localhost/`. В ответ на запросы, URI которых начинаются с `/images/`, сервер будет отправлять файлы из каталога `/data/images`. Например, на запрос `http://localhost/images/example.png` nginx отправит в ответ файл `/data/images/example.png`. Если же этот файл не существует, nginx отправит ответ, указывающий на ошибку 404. Запросы, URI которых не начинаются на `/images/`, будут отображены на каталог `/data/www`. Например, в результате запроса `http://localhost/some/example.html` в ответ будет отправлен файл `/data/www/some/example.html`.

這是一個伺服器的運作配置，它監聽標準連接埠 80，可透過本機的`http://localhost/`存取。對於以`/images/`開頭的URI請求，伺服器會從`/data/images`目錄發送檔案。例如，對於`http://localhost/images/example.png` nginx 將發送檔案`/data/images/example.png` 。如果該檔案不存在，nginx 將傳回 404 錯誤。對於不以`/images/`開頭的URI請求，伺服器會將其對應到`/data/www`目錄。例如，對於`http://localhost/some/example.html`請求，伺服器將發送檔案`/data/www/some/example.html`作為回應。

Чтобы применить новую конфигурацию, запустите nginx, если он ещё не запущен, или отправьте сигнал `reload` главному процессу nginx, выполнив:

若要套用新配置，如果 nginx 尚未執行，請啟動它；或執行下列命令向 nginx 主程序發送`reload`訊號：

> ```
> nginx -s reload
>
> nginx -s 重新載入
> ```

> В случае если что-то работает не как ожидалось, можно попытаться выяснить причину с помощью файлов `access.log` и `error.log` из каталога `/usr/local/nginx/logs` или `/var/log/nginx`.
>
> 如果某些功能沒有如預期運作，您可以嘗試使用`/usr/local/nginx/logs`或`/var/log/nginx`目錄中的`access.log`和`error.log`檔案來找出原因。

#### Настройка простого прокси-сервера｜搭建一個簡單的代理伺服器

Одним из частых применений nginx является использование его в качестве прокси-сервера, то есть сервера, который принимает запросы, перенаправляет их на проксируемые сервера, получает ответы от них и отправляет их клиенту.

nginx 的一個常見用途是將其用作代理伺服器，即接受請求、將請求轉發給代理伺服器、接收代理伺服器的回應並將其發送給客戶端的伺服器。

Мы настроим базовый прокси-сервер, который будет обслуживать запросы изображений из локального каталога и отправлять все остальные запросы на проксируемый сервер. В этом примере оба сервера будут работать в рамках одного экземпляра nginx.

我們將建立一個基本的代理伺服器，用於處理來自本地目錄的圖片請求，並將所有其他請求發送到被代理的伺服器。在本例中，兩個伺服器都將在同一個 nginx 實例中執行。

Во-первых, создайте проксируемый сервер, добавив ещё один блок `server` в конфигурационный файл nginx со следующим содержимым:

首先，透過在 nginx 設定檔中新增另一個`server`程式碼區塊來建立代理伺服器，內容如下：

> ```
> server {
>
> 伺服器 {
>     listen 8080;
>
>     聽 8080；
>     root /data/up1;
>
>     根 /data/up1;
> 
>     location / {
>
>     地點 / {
>     }
> }
> ```

Это будет простой сервер, слушающий на порту 8080 (ранее директива `listen` не указывалась, потому что использовался стандартный порт 80) и отображающий все запросы на каталог `/data/up1` в локальной файловой системе. Создайте этот каталог и положите в него файл `index.html`. Обратите внимание, что директива `root` помещена в контекст `server`. Такая директива `root` будет использована, когда директива `location`, выбранная для выполнения запроса, не содержит собственной директивы `root`.

這將是一個監聽 8080 連接埠的簡單伺服器（之前省略了`listen`指令，因為使用的是標準連接埠 80），並將所有請求對應到本機檔案系統上的`/data/up1`目錄。建立此目錄並將`index.html`檔案放入其中。請注意， `root`指令位於`server`上下文中。當用於處理請求的`location`指令不包含其自身的`root`指令時，將使用此`root`指令。

Далее, используйте конфигурацию сервера из предыдущего раздела и видоизмените её, превратив в конфигурацию прокси-сервера. В первый блок `location` добавьте директиву [proxy\_pass](<248 [02.01.01 http] ngx_http_proxy_module 模組.md#proxy_pass>), указав протокол, имя и порт проксируемого сервера в качестве параметра (в нашем случае это `http://localhost:8080`):

接下來，使用上一節中的伺服器配置並對其進行修改，以建立代理伺服器配置。在第一個`location`程式碼區塊中，新增 [proxy\_pass](<248 [02.01.01 http] ngx_http_proxy_module 模組.md#proxy_pass>)指令，並將代理伺服器的協定、名稱和連接埠作為參數指定（在本例中，它是`http://localhost:8080` ）：

> ```
> server {
>
> 伺服器 {
>     location / {
>
>     地點 / {
>         proxy_pass http://localhost:8080;
>     }
> 
>     location /images/ {
>         root /data;
>
>         根 /data;
>     }
> }
> ```

Мы изменим второй блок `location`, который на данный момент отображает запросы с префиксом `/images/` на файлы из каталога `/data/images` так, чтобы он подходил для запросов изображений с типичными расширениями файлов. Изменённый блок `location` выглядит следующим образом:

我們將修改第二個程式碼區塊`location` ，它目前將帶有`/images/`前綴的查詢映射到`/data/images`目錄中的文件，使其適用於對具有常見檔案副檔名的圖像的查詢。修改後的程式碼區塊`location`如下所示：

> ```
> location ~ \.(gif|jpg|png)$ {
>     root /data/images;
>
>     根目錄 /data/images;
> }
> ```

Параметром является регулярное выражение, дающее совпадение со всеми URI, оканчивающимися на `.gif`, `.jpg` или `.png`. Регулярному выражению должен предшествовать символ `~`. Соответствующие запросы будут отображены на каталог `/data/images`.

此參數為正規表示式，用於匹配所有以`.gif`, `.jpg`或`.png`結尾的URI 。正規表示式必須以`~`字元開頭。匹配的查詢將被映射到`/data/images`目錄。

Когда nginx выбирает блок `location`, который будет обслуживать запрос, то вначале он проверяет директивы [location](<221 [02.01.01 http] 模組 ngx_http_core_module.md#location>), задающие префиксы, запоминая `location` с самым длинным подходящим префиксом, а затем проверяет регулярные выражения. Если есть совпадение с регулярным выражением, nginx выбирает соответствующий `location`, в противном случае берётся запомненный ранее `location`.

當 nginx 選擇`location`程式碼區塊來處理請求時，它首先檢查 [location](<221 [02.01.01 http] 模組 ngx_http_core_module.md#location>)指令中指定的前綴，記住匹配前綴最長的`location`程式碼區塊，然後檢查正規表示式。如果配對成功，nginx 選擇對應的`location`程式碼區塊；否則，使用先前記住的`location`程式碼區塊。

Итоговая конфигурация прокси-сервера выглядит следующим образом:

最終的代理伺服器配置如下所示：

> ```
> server {
>
> 伺服器 {
>     location / {
>
>     地點 / {
>         proxy_pass http://localhost:8080/;
>     }
> 
>     location ~ \.(gif|jpg|png)$ {
>         root /data/images;
>
>         根目錄 /data/images;
>     }
> }
> ```

Этот сервер будет фильтровать запросы, оканчивающиеся на `.gif`, `.jpg` или `.png`, и отображать их на каталог `/data/images` (добавлением URI к параметру директивы `root`) и перенаправлять все остальные запросы на проксируемый сервер, сконфигурированный выше.

此伺服器將過濾以`.gif`, `.jpg`或`.png`結尾的請求，並將它們對應到`/data/images`目錄（透過在`root`指令參數中新增URI ），並將所有其他請求伺服器轉送到上面配置的上游。

Чтобы применить новую конфигурацию, отправьте сигнал `reload` nginx’у, как описывалось в предыдущих разделах.

若要套用新配置，請依照前面章節所述向 nginx 發送`reload`訊號。

Существует [множество](<248 [02.01.01 http] ngx_http_proxy_module 模組.md>) других директив для дальнейшей настройки прокси-соединения.

還有[許多](<248 [02.01.01 http] ngx_http_proxy_module 模組.md>)其他指令可以進一步自訂代理連接。

#### Настройка проксирования FastCGI｜設定 FastCGI 代理

nginx можно использовать для перенаправления запросов на FastCGI-серверы. На них могут исполняться приложения, созданные с использованием разнообразных фреймворков и языков программирования, например, PHP.

Nginx 可用於將請求重新導向至 FastCGI 伺服器。這些伺服器可以運行使用各種框架和編程語言構建的應用程序，例如PHP 。

Базовая конфигурация nginx для работы с проксируемым FastCGI-сервером включает в себя использование директивы [fastcgi\_pass](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_pass>) вместо директивы `proxy_pass`, и директив [fastcgi\_param](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_param>) для настройки параметров, передаваемых FastCGI-серверу. Представьте, что FastCGI-сервер доступен по адресу `localhost:9000`. Взяв за основу конфигурацию прокси-сервера из предыдущего раздела, замените директиву `proxy_pass` на директиву `fastcgi_pass` и измените параметр на `localhost:9000`. В PHP параметр `SCRIPT_FILENAME` используется для определения имени скрипта, а в параметре `QUERY_STRING` передаются параметры запроса. Получится следующая конфигурация:

使用代理 FastCGI 伺服器的基本 nginx 設定涉及使用 `[fastcgi\_pass](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_pass>)指令代替 ` `proxy_pass`指令，並使用 `[fastcgi\_param](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_param>)指令配置傳遞給 FastCGI 伺服器的參數。假設 FastCGI 伺服器可透過`localhost:9000`存取。以上一節的代理伺服器配置為基礎，將`proxy_pass`指令替換為`fastcgi_pass`指令，並將參數改為`localhost:9000` 。在PHP `SCRIPT_FILENAME`參數用於定義腳本名稱，而`QUERY_STRING`參數用於傳遞請求參數。最終配置如下：

> ```
> server {
>
> 伺服器 {
>     location / {
>
>     地點 / {
>         fastcgi_pass  localhost:9000;
>
>         fastcgi_pass localhost:9000;
>         fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
>         fastcgi_param QUERY_STRING    $query_string;
>
>         fastcgi_param QUERY_STRING $query_string;
>     }
> 
>     location ~ \.(gif|jpg|png)$ {
>         root /data/images;
>
>         根目錄 /data/images;
>     }
> }
> ```

Таким образом будет настроен сервер, который будет перенаправлять все запросы, кроме запросов статических изображений, на проксируемый сервер, работающий по адресу `localhost:9000`, по протоколу FastCGI.

這將配置一個伺服器，該伺服器會將靜態映像以外的所有請求重定向到使用 FastCGI 協定在`localhost:9000`運行的代理伺服器。
