#### Introduction｜簡介

Load balancing across multiple application instances is a commonly used technique for optimizing resource utilization, maximizing throughput, reducing latency, and ensuring fault-tolerant configurations.

跨多個應用程式實例進行負載平衡是一種常用的技術，用於最佳化資源利用率、最大化吞吐量、減少延遲和確保容錯配置。

It is possible to use nginx as a very efficient HTTP load balancer to distribute traffic to several application servers and to improve performance, scalability and reliability of web applications with nginx.

可以使用 nginx 作為非常高效的HTTP負載平衡器，將流量分配到多個應用程式伺服器，並使用 nginx 提高 Web 應用程式的效能、可擴充性和可靠性。

#### Load balancing methods｜負載平衡方法

The following load balancing mechanisms (or methods) are supported in nginx:

nginx 支援以下負載平衡機制（或方法）：

-   round-robin — requests to the application servers are distributed in a round-robin fashion,  
    輪詢－向應用程式伺服器發送的請求以輪詢方式分發。
-   least-connected — next request is assigned to the server with the least number of active connections,  
    連線數最少－下一個請求會被指派給活動連線數最少的伺服器。
-   ip-hash — a hash-function is used to determine what server should be selected for the next request (based on the client’s IP address).  
    ip-hash — 雜湊函數用於確定應為下一個請求選擇哪個伺服器（基於客戶端的IP位址）。

#### Default load balancing configuration｜預設負載平衡配置

The simplest configuration for load balancing with nginx may look like the following:

使用 nginx 進行負載平衡的最簡單設定可能如下所示：

> ```
> http {
>
> http{
>     upstream myapp1 {
>
>     上游 myapp1 {
>         server srv1.example.com;
>
>         伺服器 srv1.example.com；
>         server srv2.example.com;
>
>         伺服器 srv2.example.com；
>         server srv3.example.com;
>
>         伺服器 srv3.example.com；
>     }
> 
>     server {
>
>     伺服器{
>         listen 80;
>
>         聽 80；
> 
>         location / {
>
>         地點/{
>             proxy_pass http://myapp1;
>         }
>     }
> }
> ```

In the example above, there are 3 instances of the same application running on srv1-srv3. When the load balancing method is not specifically configured, it defaults to round-robin. All requests are [proxied](<085 [01.01.03 http] 模組 ngx_http_proxy_module.md#proxy_pass>) to the server group myapp1, and nginx applies HTTP load balancing to distribute the requests.

在上面的範例中，同一個應用程式在 srv1-srv3 上運行了 3 個實例。當未明確配置負載平衡方法時，預設採用輪詢（round-robin）。所有請求都透過 [provated](<085 [01.01.03 http] 模組 ngx_http_proxy_module.md#proxy_pass>)代理到伺服器群組 myapp1，然後由 nginx 應用HTTP負載平衡來分發這些請求。

Reverse proxy implementation in nginx includes load balancing for HTTP, HTTPS, FastCGI, uwsgi, SCGI, memcached, and gRPC.

nginx 中的反向代理實作包括對HTTP, HTTPS 、FastCGI、uwsgi、 SCGI 、memcached 和 gRPC 的負載平衡。

To configure load balancing for HTTPS instead of HTTP, just use “https” as the protocol.

要為HTTPS而不是HTTP配置負載平衡，只需使用「https」作為協議即可。

When setting up load balancing for FastCGI, uwsgi, SCGI, memcached, or gRPC, use [fastcgi\_pass](<060 [01.01.03 http] 模組 ngx_http_fastcgi_module.md#fastcgi_pass>), [uwsgi\_pass](<107 [01.01.03 http] 模組 ngx_http_uwsgi_module.md#uwsgi_pass>), [scgi\_pass](<091 [01.01.03 http] 模組 ngx_http_scgi_module.md#scgi_pass>), [memcached\_pass](<079 [01.01.03 http] 模組 ngx_http_memcached_module.md#memcached_pass>), and [grpc\_pass](<064 [01.01.03 http] 模組 ngx_http_grpc_module.md#grpc_pass>) directives respectively.

為 FastCGI、uwsgi、 SCGI 、memcached 或 gRPC 設定負載平衡時，請分別使用 [fastcgi\_pass](<060 [01.01.03 http] 模組 ngx_http_fastcgi_module.md#fastcgi_pass>) 、[uwsgi\_pass](<107 [01.01.03 http] 模組 ngx_http_uwsgi_module.md#uwsgi_pass>) 、[scgi\_pass](<091 [01.01.03 http] 模組 ngx_http_scgi_module.md#scgi_pass>) (https://nginx.org/en/docs/http/ngx_http_memcached_module.html#memcached_pass)和 [grpc\_pass](<064 [01.01.03 http] 模組 ngx_http_grpc_module.md#grpc_pass>)指令。

#### Least connected load balancing｜最少連線負載平衡

Another load balancing discipline is least-connected. Least-connected allows controlling the load on application instances more fairly in a situation when some of the requests take longer to complete.

另一種負載平衡策略是最小連線策略。最小連接策略允許在某些請求需要較長時間才能完成的情況下，更公平地控制應用程式實例上的負載。

With the least-connected load balancing, nginx will try not to overload a busy application server with excessive requests, distributing the new requests to a less busy server instead.

在連線數最少的負載平衡模式下，nginx 會盡量避免用過多的請求使繁忙的應用程式伺服器過載，而是將新的請求分發到不太繁忙的伺服器上。

Least-connected load balancing in nginx is activated when the [least\_conn](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_conn>) directive is used as part of the server group configuration:

當在伺服器群組設定中使用 [least\_conn](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_conn>)指令時，nginx 中的最少連線負載平衡功能將會啟動：

> ```
>     upstream myapp1 {
>
>     上游 myapp1 {
>         least_conn;
>
>         最少連線數；
>         server srv1.example.com;
>
>         伺服器 srv1.example.com；
>         server srv2.example.com;
>
>         伺服器 srv2.example.com；
>         server srv3.example.com;
>
>         伺服器 srv3.example.com；
>     }
> ```

#### Least time load balancing｜最短時間負載平衡

Another load balancing discipline is least-time. Least-time selects the server with the lowest average response time and the lowest number of active connections, taking into account inflight requests.

另一種負載平衡策略是最小回應時間策略。最小回應時間策略會選擇平均回應時間最短、活動連線數最少的伺服器，同時考慮正在處理的請求。

With the least-time load balancing, nginx selects the server based on which of the following parameters is specified in the [least\_time](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_time>) directive:

使用最短時間負載平衡時，nginx 會根據 [least\_time](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_time>)指令中指定的下列哪一個參數來選擇伺服器：

-   `header` — time to receive the first byte from the server,  
    `header` — 從伺服器接收第一個位元組的時間，
-   `last_byte` — time to receive the full response from the server,  
    `last_byte` — 等待伺服器回傳完整回應，
-   `last_byte inflight` — time to receive the full response from the server, taking into account incomplete requests.  
    `last_byte inflight` — 從伺服器接收完整回應所需的時間，考慮到不完整的請求。

Least-time load balancing in nginx is activated when the [least\_time](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_time>) directive is used as part of the server group configuration:

當在伺服器群組配置中使用 [least\_time](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#least_time>)指令時，nginx 中的最短時間負載平衡功能將會啟動：

> ```
>     upstream myapp1 {
>
>     上游 myapp1 {
>         least_time header;
>
>         最少時間標頭；
>         server srv1.example.com;
>
>         伺服器 srv1.example.com；
>         server srv2.example.com;
>
>         伺服器 srv2.example.com；
>         server srv3.example.com;
>
>         伺服器 srv3.example.com；
>     }
> ```

#### Session persistence｜會話持久性

Please note that with round-robin or least-connected load balancing, each subsequent client’s request can be potentially distributed to a different server. There is no guarantee that the same client will be always directed to the same server.

請注意，使用輪詢或最少連線數負載平衡時，每個後續用戶端的請求可能會被指派到不同的伺服器。無法保證同一客戶端始終被導向到同一台伺服器。

If there is the need to tie a client to a particular application server — in other words, make the client’s session “sticky” or “persistent” in terms of always trying to select a particular server — the ip-hash load balancing mechanism can be used.

如果需要將客戶端綁定到特定的應用程式伺服器——換句話說，要使客戶端會話“粘性”或“持久性”，請始終嘗試選擇特定的伺服器——可以使用 ip-hash 負載平衡機制。

With ip-hash, the client’s IP address is used as a hashing key to determine what server in a server group should be selected for the client’s requests. This method ensures that the requests from the same client will always be directed to the same server except when this server is unavailable.

使用 IP 雜湊演算法時，客戶端的IP位址被用作雜湊金鑰，以確定應從伺服器群組中選擇哪個伺服器來處理客戶端的請求。這種方法確保來自同一客戶端的請求始終被定向到同一台伺服器，除非該伺服器不可用。

To configure ip-hash load balancing, just add the [ip\_hash](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#ip_hash>) directive to the server (upstream) group configuration:

要設定 ip-hash 負載平衡，只需將 [ip\_hash](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#ip_hash>)指令新增至伺服器（上游）群組配置中：

> ```
> upstream myapp1 {
>
> 上游 myapp1 {
>     ip_hash;
>
>     IP哈希值；
>     server srv1.example.com;
>
>     伺服器 srv1.example.com；
>     server srv2.example.com;
>
>     伺服器 srv2.example.com；
>     server srv3.example.com;
>
>     伺服器 srv3.example.com；
> }
> ```

#### Weighted load balancing｜加權負載平衡

It is also possible to influence nginx load balancing algorithms even further by using server weights.

也可以透過使用伺服器權重來進一步影響 nginx 負載平衡演算法。

In the examples above, the server weights are not configured which means that all specified servers are treated as equally qualified for a particular load balancing method.

在上面的範例中，伺服器權重沒有配置，這意味著所有指定的伺服器都被視為同樣適用於特定的負載平衡方法。

With the round-robin in particular it also means a more or less equal distribution of requests across the servers — provided there are enough requests, and when the requests are processed in a uniform manner and completed fast enough.

特別是對於輪詢調度來說，這意味著請求在各個伺服器上的分配大致相等——前提是請求足夠多，並且請求以統一的方式處理，並且完成速度足夠快。

When the [weight](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>) parameter is specified for a server, the weight is accounted as part of the load balancing decision.

當為伺服器指定 [weight](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)參數時，該權重將作為負載平衡決策的一部分加以考慮。

> ```
>     upstream myapp1 {
>
>     上游 myapp1 {
>         server srv1.example.com weight=3;
>
>         伺服器 srv1.example.com 權重=3；
>         server srv2.example.com;
>
>         伺服器 srv2.example.com；
>         server srv3.example.com;
>
>         伺服器 srv3.example.com；
>     }
> ```

With this configuration, every 5 new requests will be distributed across the application instances as the following: 3 requests will be directed to srv1, one request will go to srv2, and another one — to srv3.

透過這種配置，每 5 個新請求將如下分配到應用程式實例中：3 個請求將定向到 srv1，1 個請求將定向到 srv2，另一個請求將定向到 srv3。

It is similarly possible to use weights with the least-connected and ip-hash load balancing in the recent versions of nginx.

同樣，在最新版本的 nginx 中，也可以使用權重進行最少連接和 IP 雜湊負載平衡。

#### Health checks｜健康檢查

Reverse proxy implementation in nginx includes in-band (or passive) server health checks. If the response from a particular server fails with an error, nginx will mark this server as failed, and will try to avoid selecting this server for subsequent inbound requests for a while.

nginx 中的反向代理實作包含帶內（或被動）伺服器健康檢查。如果某個伺服器的回應出現錯誤，nginx 會將該伺服器標記為故障，並在一段時間內避免選擇該伺服器處理後續的入站要求。

The [max\_fails](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>) directive sets the number of consecutive unsuccessful attempts to communicate with the server that should happen during [fail\_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>). By default, [max\_fails](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>) is set to 1. When it is set to 0, health checks are disabled for this server. The [fail\_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>) parameter also defines how long the server will be marked as failed. After [fail\_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>) interval following the server failure, nginx will start to gracefully probe the server with the live client’s requests. If the probes have been successful, the server is marked as a live one.

[max_fails](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)指令設定在 [fail_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)時間段內，與伺服器通訊連續失敗的次數。預設情況下，[max_fails](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)設定為 1。設定為 0 時，將停用此伺服器的健康檢查。 [fail_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)參數也定義了伺服器被標記為故障的持續時間。在伺服器故障後的 [fail_timeout](<105 [01.01.03 http] 模組 ngx_http_upstream_module.md#server>)時間間隔之後，nginx 將開始使用正常客戶端的請求優雅地探測伺服器。如果探測成功，則伺服器將被標記為正常。
