#### Определение виртуального сервера по имени｜透過名稱識別虛擬伺服器

nginx вначале решает, какой из серверов должен обработать запрос. Рассмотрим простую конфигурацию, где все три виртуальных сервера слушают на порту \*:80:

nginx 先決定哪個伺服器應該處理請求。考慮一個簡單的配置，其中所有三個虛擬伺服器都偵聽連接埠 \*:80：

> ```
> server {
>
> 伺服器{
>     listen      80;
>
>     聽 80；
>     server_name example.org www.example.org;
>
>     伺服器名稱 example.org www.example.org;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      80;
>
>     聽 80；
>     server_name example.net www.example.net;
>
>     伺服器名稱 example.net www.example.net;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      80;
>
>     聽 80；
>     server_name example.com www.example.com;
>     ...
> }
> ```

В этой конфигурации, чтобы определить, какому серверу следует направить запрос, nginx проверяет только поле “Host”（主持人） заголовка запроса. Если его значение не соответствует ни одному из имён серверов или в заголовке запроса нет этого поля вовсе, nginx направит запрос в сервер по умолчанию для этого порта. В вышеприведённой конфигурации сервером по умолчанию будет первый сервер, что соответствует стандартному поведению nginx по умолчанию. Сервер по умолчанию можно задать явно с помощью параметра `default_server` в директиве [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>):

在此配置中，nginx 僅檢查請求頭中的“Host”（主持人）欄位來決定將請求轉送至哪個伺服器。如果該字段的值與任何伺服器名稱都不匹配，或者請求頭中根本不包含此字段，nginx 會將請求轉發到該連接埠的預設伺服器。在上述配置中，預設伺服器是第一個伺服器，這與 nginx 的預設行為一致。可以使用 [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>)指令中的`default_server`參數明確設定預設伺服器：

> ```
> server {
>
> 伺服器{
>     listen      80 default_server;
>
>     監聽 80 埠預設伺服器；
>     server_name example.net www.example.net;
>
>     伺服器名稱 example.net www.example.net;
>     ...
> }
> ```

> Параметр `default_server` появился в версии 0.8.21. В более ранних версиях вместо него следует использовать параметр `default`.
>
> `default_server`參數是在0.8.21版本中引入的。在早期版本中，應使用`default`參數。

Следует иметь в виду, что сервер по умолчанию является свойством слушающего порта, а не имени сервера. Подробнее это обсуждается ниже.

需要注意的是，預設伺服器是監聽連接埠的屬性，而不是伺服器名稱的屬性。下文將對此進行更詳細的討論。

#### Как предотвратить обработку запросов без имени сервера｜如何阻止處理沒有伺服器名稱的請求

Если запросы без поля “Host”（主持人） в заголовке не должны обрабатываться, можно определить сервер, который будет их отклонять:

如果缺少“Host”（主持人）標頭欄位的請求不應被處理，您可以定義伺服器來拒絕這些請求：

> ```
> server {
>
> 伺服器{
>     listen      80;
>
>     聽 80；
>     server_name "";
>
>     伺服器名稱“”；
>     return      444;
>
>     返回 444；
> }
> ```

Здесь в качестве имени сервера указана пустая строка, которая соответствует запросам без поля “Host”（主持人） в заголовке, и возвращается специальный для nginx код 444, который закрывает соединение.

在這裡，伺服器名稱被設定為空字串，這匹配沒有“Host”（主持人）標頭字段的請求，並返回 nginx 特有的代碼 444，從而關閉連接。

> Начиная с версии 0.8.48 настройка `server_name ""` является стандартной и может явно не указываться. В более ранних версиях в качестве стандартного имени сервера выступало имя машины (hostname).
>
> 從版本0.8.48 `server_name ""`設定已成為預設值，可省略。在早期版本中，機器名稱（主機名稱）用作預設伺服器名稱。

#### Определение виртуального сервера по имени и IP-адресу｜透過名稱和IP位址識別虛擬伺服器

Рассмотрим более сложную конфигурацию, в которой некоторые виртуальные серверы слушают на разных адресах:

讓我們考慮一個更複雜的配置，其中一些虛擬伺服器監聽不同的位址：

> ```
> server {
>
> 伺服器{
>     listen      192.168.1.1:80;
>
>     列表192.168.1.1:80 ;
>     server_name example.org www.example.org;
>
>     伺服器名稱 example.org www.example.org;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      192.168.1.1:80;
>
>     聽192.168.1.1:80 ;
>     server_name example.net www.example.net;
>
>     伺服器名稱 example.net www.example.net;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      192.168.1.2:80;
>
>     聽192.168.1.2:80 ;
>     server_name example.com www.example.com;
>     ...
> }
> ```

В этой конфигурации nginx вначале сопоставляет IP-адрес и порт запроса с директивами [listen](<221 [02.01.01 http] 模組 ngx_http_core_module.md#listen>) в блоках [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>). Затем он сопоставляет значение поля “Host”（主持人） заголовка запроса с директивами [server\_name](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server_name>) в блоках [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server>), которые соответствуют IP-адресу и порту. Если имя сервера не найдено, запрос будет обработан в сервере по умолчанию. Например, запрос `www.example.com`, пришедший на порт 192.168.1.1:80, будет обработан сервером по умолчанию для порта 192.168.1.1:80, т.е. первым сервером, т.к. для этого порта `www.example.com` не указан в списке имён серверов.

在此配置中，nginx 首先將IP位址和連接埠與 [server] 程式碼區塊中的 [listen (https://nginx.org/ru/docs/http/ngx_http_core_module.html#listen)指令進行比對。然後，它將“Host”（主持人）頭字段的值與 [server](<221 [02.01.01 http] 模組 ngx_http_core_module.md#server_name>)區塊中對應的 [ (https://nginx.org/ru/docs/http/ngx_http_core_module.html#server) ] 指令進行匹配。如果找不到伺服器名稱，則請求將由預設IP處理。例如，連接埠(https://nginx.org/ru/docs/http/ngx_http_core_module.html#server)上`www.example.com`請求將由連接埠192.168.1.1:80 192.168.1.1:80預設伺服器（即第一個伺服器）處理，因為`www.example.com`不在該連接埠的伺服器名稱清單中。

Как уже говорилось, сервер по умолчанию является свойством слушающего порта, поэтому у разных портов могут быть определены свои серверы по умолчанию:

如前所述，預設伺服器是監聽連接埠的一個屬性，因此不同的連接埠可以定義自己的預設伺服器：

> ```
> server {
>
> 伺服器{
>     listen      192.168.1.1:80;
>
>     聽192.168.1.1:80 ;
>     server_name example.org www.example.org;
>
>     伺服器名稱 example.org www.example.org;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      192.168.1.1:80 default_server;
>
>     監聽192.168.1.1:80預設伺服器；
>     server_name example.net www.example.net;
>
>     伺服器名稱 example.net www.example.net;
>     ...
> }
> 
> server {
>
> 伺服器{
>     listen      192.168.1.2:80 default_server;
>
>     監聽192.168.1.2:80預設伺服器；
>     server_name example.com www.example.com;
>     ...
> }
> ```

#### Конфигурация простого сайта PHP｜簡易站點配置PHP

Теперь посмотрим на то, как nginx выбирает *location* для обработки запроса на примере обычного простого PHP-сайта:

現在讓我們以一個普通的PHP網站為例，看看nginx是如何選擇處理請求的*location*的：

> ```
> server {
>
> 伺服器{
>     listen      80;
>
>     聽 80；
>     server_name example.org www.example.org;
>
>     伺服器名稱 example.org www.example.org;
>     root        /data/www;
>
>     根目錄 /data/www;
> 
>     location / {
>
>     地點/{
>         index   index.html index.php;
>
>         index index.html index.php;
>     }
> 
>     location ~* \.(gif|jpg|png)$ {
>         expires 30d;
>
>         有效期限30天；
>     }
> 
>     location ~ \.php$ {
>         fastcgi_pass  localhost:9000;
>
>         fastcgi_pass localhost:9000;
>         fastcgi_param SCRIPT_FILENAME
>
>         fastcgi_param 腳本檔名
>                       $document_root$fastcgi_script_name;
>         include       fastcgi_params;
>
>         包含 fastcgi_params；
>     }
> }
> ```

nginx вначале ищет среди всех префиксных location’ов, заданных строками, максимально совпадающий. В вышеприведённой конфигурации указан только один префиксный location “`/`”, и поскольку он подходит под любой запрос, он и будет использован, если других совпадений не будет найдено. Затем nginx проверяет location’ы, заданные регулярными выражениями, в порядке их следования в конфигурационном файле. При первом же совпадении поиск прекращается и nginx использует совпавший location. Если запросу не соответствует ни одно из регулярных выражений, nginx использует максимально совпавший префиксный location, найденный ранее.

nginx 先搜尋所有字串指定的前綴位置，找到最接近的匹配位置。在上面的配置中，只指定了一個前綴位置“ `/` ”，由於它匹配任何請求，因此如果沒有找到其他匹配項，則會使用它。然後，nginx 會按照正規表示式在設定檔中出現的順序檢查它們指定的位置。找到第一個匹配項後，搜尋停止，nginx 使用匹配的位置。如果沒有任何正規表示式與請求匹配，nginx 則使用先前找到的最接近的匹配前綴位置。

Следует иметь в виду, что location’ы всех типов сопоставляются только с URI-частью строки запроса без аргументов. Так делается потому, что аргументы в строке запроса могут быть заданы различными способами, например:

需要注意的是，所有類型的位置資訊都僅與查詢字串中不帶參數的URI部分進行比對。這是因為查詢字串參數可以透過多種方式指定，例如：

> ```
> /index.php?user=john&page=1
> /index.php?page=1&user=john
> ```

Кроме того, в строке запроса можно запросить что угодно:

此外，您可以在查詢字串中請求任何內容：

> ```
> /index.php?page=1&something+else&user=john
> ```

Теперь посмотрим, как бы обрабатывались запросы в вышеприведённой конфигурации:

現在我們來看看在上述配置下請求是如何處理的：

-   Запросу “`/logo.gif`” во-первых соответствует префиксный location “`/`”, а во-вторых — регулярное выражение “`\.(gif|jpg|png)$`”, поэтому он обрабатывается location’ом регулярного выражения. Согласно директиве “`root /data/www`” запрос отображается в файл `/data/www/logo.gif`, который и посылается клиенту.  
    請求“ `/logo.gif` ”匹配前綴位置“ `/` ”和正則表達式“ `\.(gif|jpg|png)$` ”，因此由正則表達式位置進行處理。根據指令“ `root /data/www` ”，該請求被對應到檔案`/data/www/logo.gif` ，然後傳送給客戶端。
-   Запросу “`/index.php`” также во-первых соответствует префиксный location “`/`”, а во-вторых — регулярное выражение “`\.(php)$`”. Следовательно, он обрабатывается location’ом регулярного выражения и запрос передаётся FastCGI-серверу, слушающему на localhost:9000. Директива [fastcgi\_param](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_param>) устанавливает FastCGI-параметр `SCRIPT_FILENAME` в “`/data/www/index.php`”, и сервер FastCGI выполняет указанный файл. Переменная `$document_root` равна значению директивы [root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>), а переменная `$fastcgi_script_name` равна URI запроса, т.е. “`/index.php`”.  
    查詢“`/index.php`”首先也匹配前綴位置“`/`”，其次匹配正規表示式“`\.(php)$`”。因此，它由正規表示式位置處理，並將請求傳遞到偵聽 localhost:9000 的 FastCGI 伺服器。 [fastcgi\_param](<225 [02.01.01 http] ngx_http_fastcgi_module 模組.md#fastcgi_param>)指令將FastCGI參數`SCRIPT_FILENAME`設定為“`/data/www/index.php`”，並且FastCGI伺服器執行指定的檔案。變數`$document_root`等於[root](<221 [02.01.01 http] 模組 ngx_http_core_module.md#root>)指令的值，變數`$fastcgi_script_name`等於請求的URI，即「`/index.php`」。
-   Запросу “`/about.html`” соответствует только префиксный location “`/`”, поэтому запрос обрабатывается в нём. Согласно директиве “`root /data/www`” запрос отображается в файл `/data/www/about.html`, который и посылается клиенту.  
    請求“ `/about.html` ”僅匹配前綴位置“ `/` ”，因此該請求在該位置進行處理。根據「 `root /data/www` 」指令，該請求被對應到檔案`/data/www/about.html` ，然後將該檔案傳送給客戶端。
-   Обработка запроса “`/`” более сложная. Ему соответствует только префиксный location “`/`”, поэтому запрос обрабатывается в нём. Затем директива [index](<236 [02.01.01 http] 模組 ngx_http_index_module.md#index>) проверяет существование индексных файлов согласно своих параметров и директиве “`root /data/www`”. Если файл `/data/www/index.html` не существует, а файл `/data/www/index.php` существует, то директива делает внутреннее перенаправление на “`/index.php`” и nginx снова сопоставляет его с location’ами, как если бы такой запрос был послан клиентом. Как мы видели ранее, перенаправленный запрос будет в конечном итоге обработан сервером FastCGI.  
    處理「 `/` 」請求更為複雜。它僅匹配前綴位置“ `/` ”，因此請求會在該位置進行處理。然後，[index](<236 [02.01.01 http] 模組 ngx_http_index_module.md#index>)指令會根據其參數和「 `root /data/www` 」指令檢查索引檔案是否存在。如果`/data/www/index.html`檔案不存在，但`/data/www/index.php`檔案存在，則該指令會將請求內部重定向到“ `/index.php` ”，nginx 會再次使用位置資訊進行匹配，就好像該請求是由客戶端發送的一樣。正如我們之前所看到的，重定向後的請求最終將由 FastCGI 伺服器處理。
