# WebSocket proxying｜WebSocket代理

> 章節：[en｜在](<000 目錄.md#c-1>) › [docs｜文件](<000 目錄.md#c-2>) › [http](<000 目錄.md#c-5>)

## WebSocket proxying｜WebSocket代理

To turn a connection between a client and server from HTTP/1.1 into WebSocket, the [protocol switch](https://datatracker.ietf.org/doc/html/rfc2616#section-14.42) mechanism available in HTTP/1.1 is used.

要將客戶端與伺服器之間的連線從HTTP/1.1轉換為 WebSocket，可以使用HTTP/1.1中提供的 [協定切換](https://datatracker.ietf.org/doc/html/rfc2616#section-14.42)機制。

There is one subtlety however: since the “Upgrade”（升級） is a [hop-by-hop](https://datatracker.ietf.org/doc/html/rfc2616#section-13.5.1) header, it is not passed from a client to proxied server. With forward proxying, clients may use the `CONNECT` method to circumvent this issue. This does not work with reverse proxying however, since clients are not aware of any proxy servers, and special processing on a proxy server is required.

然而，這裡有一個微妙之處：由於“Upgrade”（升級）是逐跳(https://datatracker.ietf.org/doc/html/rfc2616#section-13.5.1)頭部，它不會從客戶端傳遞到代理伺服器。對於正向代理，客戶端可以使用`CONNECT`方法來規避這個問題。但是，這在反向代理中行不通，因為客戶端不知道任何代理伺服器，而且需要在代理伺服器上進行特殊處理。

Since version 1.3.13, nginx implements special mode of operation that allows setting up a tunnel between a client and proxied server if the proxied server returned a response with the code 101 (Switching Protocols), and the client asked for a protocol switch via the “Upgrade”（升級） header in a request.

自版本1.3.13起，nginx 實現了一種特殊的運行模式，允許在客戶端和代理伺服器之間建立隧道，前提是代理伺服器回傳了程式碼為 101（切換協定）的回應，並且客戶端透過請求中的“Upgrade”（升級）標頭請求了協定切換。

As noted above, hop-by-hop headers including “Upgrade”（升級） and “Connection”（聯繫） are not passed from a client to proxied server, therefore in order for the proxied server to know about the client’s intention to switch a protocol to WebSocket, these headers have to be passed explicitly:

如上所述，包括“Upgrade”（升級）和“Connection”（聯繫）在內的逐跳標頭不會從客戶端傳遞到代理伺服器，因此，為了讓代理伺服器知道客戶端打算將協定切換到WebSocket，必須明確地傳遞這些標頭：

> ```
> location /chat/ {
>     proxy_pass http://backend;
>     # proxy_http_version 1.1; # before version 1.29.7｜proxy_http_version 1.1 ; # 版本1.29.7之前
>     proxy_set_header Upgrade $http_upgrade;
>     proxy_set_header Connection "upgrade";
>
>     proxy_set_header Connection "升級";
> }
> ```

A more sophisticated example in which a value of the “Connection”（聯繫） header field in a request to the proxied server depends on the presence of the “Upgrade”（升級） field in the client request header:

一個更複雜的例子是，發送到代理伺服器的請求中“Connection”（聯繫）標頭欄位的值取決於客戶端請求標頭中“Upgrade”（升級）欄位是否存在：

> ```
> http {
>     map $http_upgrade $connection_upgrade {
>
>     映射 $http_upgrade $connection_upgrade {
>         default upgrade;
>
>         預設升級；
>         ''      close;
>
>         '' 關閉;
>     }
> 
>     server {
>
>     伺服器 {
>         ...
> 
>         location /chat/ {
>             proxy_pass http://backend;
>             # proxy_http_version 1.1; # before version 1.29.7｜proxy_http_version 1.1 ; # 版本1.29.7之前
>             proxy_set_header Upgrade $http_upgrade;
>             proxy_set_header Connection $connection_upgrade;
>         }
>     }
> ```

By default, the connection will be closed if the proxied server does not transmit any data within 60 seconds. This timeout can be increased with the [proxy\_read\_timeout](<085 [01.01.03 http] 模組 ngx_http_proxy_module.md#proxy_read_timeout>) directive. Alternatively, the proxied server can be configured to periodically send WebSocket ping frames to reset the timeout and check if the connection is still alive.

預設情況下，如果代理伺服器在 60 秒內未發送任何數據，連線將關閉。可以使用 `[proxy\_read\_timeout](<085 [01.01.03 http] 模組 ngx_http_proxy_module.md#proxy_read_timeout>)指令增加此逾時時間。或者，可以將代理伺服器配置為定期發送 WebSocket ping 幀來重置逾時時間並檢查連線是否仍然有效。
