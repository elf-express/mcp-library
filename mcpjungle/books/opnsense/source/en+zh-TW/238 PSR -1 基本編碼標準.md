# PSR-1 Basic Coding Standard｜PSR -1 基本編碼標準

> 章節：[Development Manual](<000 目錄.md#c-52>) › [Coding Guidelines](<000 目錄.md#c-53>)

筆記

PSR1和PSR2編碼標準由FIG依據MIT授權提供。

See license details: [http://www.php-fig.org/bylaws/licensing-policies/](http://www.php-fig.org/bylaws/licensing-policies/)

查看許可詳情：[http://www.php-fig.org/bylaws/licensing-policies/](http://www.php-fig.org/bylaws/licensing-policies/)

The original content of this page can be found at [php-fig](http://www.php-fig.org/psr/psr-1/)

本頁原文內容可在 [php-fig](http://www.php-fig.org/psr/psr-1/)找到

This section of the standard comprises what should be considered the standard coding elements that are required to ensure a high level of technical interoperability between shared PHP code.

本標準的這一部分包含了確保共享的PHP代碼之間具有高度技術互通性所需的標準編碼元素。

The key words “MUST”（必須）, “MUST NOT”（不能）, “REQUIRED”（必需的）, “SHALL”（將）, “SHALL NOT”（不得）, “SHOULD”（應該）, “SHOULD NOT”（不應該）, “RECOMMENDED”（受到推崇的）, “MAY”（可能）, and “OPTIONAL”（選修的） in this document are to be interpreted as described in [RFC 2119](http://www.ietf.org/rfc/rfc2119.txt).

本文檔中的關鍵字“MUST”（必須）, “MUST NOT”（不能）, “REQUIRED”（必需的）, “SHALL”（將）, “SHALL NOT”（不得）, “SHOULD”（應該）, “SHOULD NOT”（不應該）, “RECOMMENDED”（受到推崇的）, “MAY”（可能）和“OPTIONAL”（選修的）應依照[RFC](http://www.ietf.org/rfc/rfc2119.txt)中的描述進行解釋。

## 1\. Overview｜1. 概述

-   Files MUST use only `<?php` and `<?=` tags.  
    檔案MUST僅使用`<?php`和`<?=`標籤。
    
-   Files MUST use only UTF-8 without BOM for PHP code.  
    檔案MUST僅使用UTF -8 PHP BOM 。
    
-   Files SHOULD *either* declare symbols (classes, functions, constants, etc.) *or* cause side-effects (e.g. generate output, change .ini settings, etc.) but SHOULD NOT do both.  
    檔案SHOULD *要麼* 宣告符號（類別、函數、常數等），*要麼* 產生副作用（例如產生輸出、更改 .ini 設定等），但SHOULD NOT兩者都做。
    
-   Namespaces and classes MUST follow an “autoloading” PSR: \[[PSR-0](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-0.md), [PSR-4](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-4-autoloader.md)\].  
    命名空間與類別MUST遵循「自動載入」 PSR ：\[[PSR -0](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-0.md) , [PSR -4](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-4-autoloader.md) \]。
    
-   Class names MUST be declared in `StudlyCaps`.  
    類別名稱MUST應在`StudlyCaps`中宣告。
    
-   Class constants MUST be declared in all upper case with underscore separators.  
    類別常數MUST必須全部用大寫字母聲明，並用下劃線分隔。
    
-   Method names MUST be declared in `camelCase`.  
    方法名稱MUST應在`camelCase`中宣告。
    

## 2\. Files｜2. 文件

### 2.1. PHP Tags｜2.1. PHP標籤

PHP code MUST use the long `<?php ?>` tags or the short-echo `<?= ?>` tags; it MUST NOT use the other tag variations.

PHP代碼MUST使用長`<?php ?>`標籤或短迴聲`<?= ?>`標籤；它MUST NOT使用其他標籤變體。

### 2.2. Character Encoding｜2.2 . 字元編碼

PHP code MUST use only UTF-8 without BOM.

PHP代碼MUST僅使用UTF -8 不使用BOM 。

### 2.3. Side Effects｜2.3 . 副作用

A file SHOULD declare new symbols (classes, functions, constants, etc.) and cause no other side effects, or it SHOULD execute logic with side effects, but SHOULD NOT do both.

檔案SHOULD宣告新符號（類別、函數、常數等）且不產生其他副作用，或SHOULD執行有副作用的邏輯，但SHOULD NOT兩者兼而有之。

The phrase “side effects” means execution of logic not directly related to declaring classes, functions, constants, etc., *merely from including the file*.

「副作用」一詞指的是執行與宣告類別、函數、常數等沒有直接關係的邏輯，*僅僅因為包含了該檔案*。

“Side effects” include but are not limited to: generating output, explicit use of `require` or `include`, connecting to external services, modifying ini settings, emitting errors or exceptions, modifying global or static variables, reading from or writing to a file, and so on.

「副作用」包括但不限於：產生輸出、明確使用`require`或`include` 、連接到外部服務、修改ini設定、發出錯誤或異常、修改全域或靜態變數、從檔案讀取或寫入檔案等等。

The following is an example of a file with both declarations and side effects; i.e, an example of what to avoid:

以下是一個同時包含聲明和副作用的文件範例；也就是說，這是一個應該避免的例子：

```php
<?php
// side effect: change ini settings
ini_set('error_reporting', E_ALL);

// side effect: loads a file
include "file.php";

// side effect: generates output
echo "<html>\n";

// declaration
function foo()
{
    // function body
}
```

The following example is of a file that contains declarations without side effects; i.e., an example of what to emulate:

以下範例是一個包含無副作用聲明的文件；也就是說，這是一個需要模仿的範例：

```php
<?php
// declaration
function foo()
{
    // function body
}

// conditional declaration is *not* a side effect
if (! function_exists('bar')) {
    function bar()
    {
        // function body
    }
}
```

## 3\. Namespace and Class Names｜3. 命名空間與類別名

Namespaces and classes MUST follow an “autoloading” PSR: \[[PSR-0](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-0.md), [PSR-4](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-4-autoloader.md)\].

命名空間與類別MUST遵循「自動載入」 PSR : \[[PSR -0](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-0.md) , [PSR -4](https://github.com/php-fig/fig-standards/blob/master/accepted/PSR-4-autoloader.md) \]。

This means each class is in a file by itself, and is in a namespace of at least one level: a top-level vendor name.

這意味著每個類別都位於單獨的檔案中，並且至少位於一個命名空間中：頂級供應商名稱。

Class names MUST be declared in `StudlyCaps`.

類別名稱MUST應在`StudlyCaps`中宣告。

Code written for PHP 5.3 and after MUST use formal namespaces.

為PHP 5.3及之後MUST所寫的程式碼使用正式命名空間。

For example:

例如：

```php
<?php
// PHP 5.3 and later:
namespace Vendor\Model;

class Foo
{
}
```

Code written for 5.2.x and before SHOULD use the pseudo-namespacing convention of `Vendor_` prefixes on class names.

為5.2 .x 和SHOULD之前所寫的程式碼使用類別名稱上的`Vendor_`前綴的偽命名空間約定。

```php
<?php
// PHP 5.2.x and earlier:
class Vendor_Model_Foo
{
}
```

## 4\. Class Constants, Properties, and Methods｜4. 類別常數、屬性與方法

The term “class” refers to all classes, interfaces, and traits.

術語「類別」指的是所有類別、介面和特性。

### 4.1. Constants｜4.1 . 常量

Class constants MUST be declared in all upper case with underscore separators. For example:

類別常數MUST必須全部以大寫字母聲明，並以底線分隔。例如：

```php
<?php
namespace Vendor\Model;

class Foo
{
    const VERSION = '1.0';
    const DATE_APPROVED = '2012-06-01';
}
```

### 4.2. Properties｜4.2 . 屬性

This guide intentionally avoids any recommendation regarding the use of `$StudlyCaps`, `$camelCase`, or `$under_score` property names.

本指南刻意避免對使用`$StudlyCaps`, `$camelCase`或`$under_score`屬性名稱提出任何建議。

Whatever naming convention is used SHOULD be applied consistently within a reasonable scope. That scope may be vendor-level, package-level, class-level, or method-level.

無論採用何種命名約定SHOULD都應在合理的範圍內保持一致。此範圍可以是供應商層級、套件層級、類別層級或方法層級。

### 4.3. Methods｜4.3 . 方法

Method names MUST be declared in `camelCase()`.

方法名稱MUST應在`camelCase()`中宣告。
