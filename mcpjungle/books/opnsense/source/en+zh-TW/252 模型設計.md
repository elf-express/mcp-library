Creating models for OPNsense is divided into two separate blocks:

OPNsense 模型的創建分為兩個獨立的部分：

1.  A PHP class describing the actions on our data (also acts as a wrapper to our data),  
    PHP類描述了對我們資料的操作（也充當我們資料的包裝器），
    
2.  The definition of the data and the rules it should apply to.  
    資料的定義及其適用的規則。
    

Every model’s class should be derived from OPNsense\\Base\\BaseModel, a very simple model without any (additional) logic is defined with:

每個模型的類別都應該派生自 OPNsense\\Base\\BaseModel，這是一個非常簡單的模型，沒有任何（額外的）邏輯，定義如下：

```php
<?php
namespace myVendorName\myModule;

use OPNsense\Base\BaseModel;

class myModel extends BaseModel
{
}
```

This class should be placed inside the model directory of our project, in this case the full path for our class file would be

這個類別應該放在我們專案的模型目錄中，在這種情況下，類別檔案的完整路徑是：

-   /usr/local/opnsense/mvc/app/models/**myVendorName/myModule/myModel.php**
    

When you design a model, the next thing to do is to figure out what data is relevant for your application or module and think of the rules it should comply to (for example, if you need an email address you might want to validate the input). Designing the actual model is as simple as creating an xml file and putting in your structure, the name of our XML file should be the same as the base name of our model suffixed by .xml.

設計模型時，下一步是確定哪些資料與你的應用程式或模組相關，並考慮它應該遵循的規則（例如，如果你需要電子郵件地址，你可能需要驗證輸入）。設計實際的模型非常簡單，只需建立一個 XML 檔案並將你的結構放入其中即可。我們的XML檔案的名稱應該與模型的基本名稱相同，並且加上 .xml 後綴。

Using the same model, we would create the following file:

使用相同的模型，我們將建立以下文件：

-   /usr/local/opnsense/mvc/app/models/**myVendorName/myModule/myModel.xml**
    

And start describing our (information) model, like this:

然後開始描述我們的（資訊）模型，像這樣：

```xml
<model>
    <mount>//myManufacturer/myModule</mount>
    <description>A description of this model (metadata)</description>
    <version>1.0.0</version>
    <items>
        <exampleNumber type="TextField">
            <Mask>/^([0-9]){0,1}$/</Mask>
            <Default>5</Default>
            <ValidationMessage>you should input a number from 0 to 9</ValidationMessage>
        </exampleNumber>
        <contacts>
            <entity type="ArrayField">
                <email type="EmailField">
                    <ValidationMessage>you should input a valid email address!</ValidationMessage>
                </email>
                <name type="TextField"/>
            </entity>
            <someText type="TextField"/>
        </contacts>
    </items>
</model>
```

Now let’s explain what’s happing here one tag at a time.

現在讓我們逐一標籤地解釋一下這裡發生了什麼。

1.  the <model> tag is used for identification of the file. (this is a model file)  
    <model>標籤用於識別文件。 （這是一個模型檔）
    
2.  Next in line is the <mount> tag, this tells the system where this information lives in the configuration file, in this case ROOT\_tag/myManufacturer/myModule  
    接下來是<mount>標籤，它告訴系統此資訊在設定檔中的位置，在本例中ROOT \_tag/myManufacturer/myModule
    
3.  If desired, there is some space reserved to explain the usage of the model, the <description> tag  
    如果需要，可以預留一些空間來解釋模型的用法，即<description>標籤。
    
4.  A version tag is added, which is used to support migrations. These are described in more details in the [migration](<257 遷徙.md>) topic  
    新增了一個版本標籤，用於支援遷移。這些內容在 [migration](<257 遷徙.md>)主題中有更詳細的描述。
    
5.  Last item on the top of our list is the <items> tag, this is where the magic begins.  
    清單頂部的最後一項是<items>標籤，神奇之處就在這裡。
    

The content of a items tag describes the full tree based structure which holds our data, in theory this could be as large as you want it to be, but keep in mind that the content for your model should be logical and understandable. Every node in the tree could have a type, which defines its behavior, nodes without a type are just containers.

items 標籤的內容描述了包含我們資料的完整樹狀結構。理論上，這個結構可以根據需要任意大小，但請記住，模型的內容應該是邏輯清晰、易於理解。樹中的每個節點都可以有一個類型，用於定義其行為；沒有類型的節點只是容器。

From top to bottom we find the following nodes in our tree:

從上到下，我們在樹中找到了以下節點：

-   exampleNumber, defined as a TextField  
    exampleNumber，定義為 TextField
    
    -   Mask, validation can be performed by a regex expression, this sets the expression  
        掩碼驗證可以透過正規表示式執行，這將設定表達式
        
    -   Default, this field is default filled with a number: 5  
        預設情況下，此欄位填入的數字為：5
        
    -   ValidationMessage, when validation fails, this message is returned  
        驗證失敗時，將傳回 ValidationMessage 訊息。
        
-   contacts, this is a container  
    聯絡人，這是一個容器
    
-   entity, is defined as a recurring item, which holds the next items  
    實體被定義為一個循環項，它包含下一個項。
    
-   email, defined as an EmailField  
    電子郵件，定義為 EmailField
    
    -   when validation fails, the **ValidationMessage** is returned  
        驗證失敗時，將傳回 **ValidationMessage**。
        
-   name, defined as a TextField without any validations  
    名稱，定義為一個沒有任何驗證的文字字段
    
-   someText, not part of the entity tag and also defined as text without validation  
    someText，它不是實體標籤的一部分，也被定義為未經驗證的文本
    

The fieldtypes are easily extendable in the base system and all common ones live in their own namespace at *OPNsense\\Base\\FieldTypes* deriving from *BaseField*.

基本系統中的欄位類型很容易擴展，所有常見的欄位類型都位於自己的命名空間 *OPNsense\\Base\\FieldTypes* 中，該命名空間衍生自 *BaseField*。

Note

筆記

When designing application specific fieldtypes, you can point to a field type within the application namespace using a full or partial path.

在設計應用程式特定的欄位類型時，可以使用完整路徑或部分路徑指向應用程式命名空間中的欄位類型。

For example using *Vendor\\Component\\FieldTypes\\MyFieldType* to point to a specific non common field type or *.\\MyFieldType* when linked from the application model itself (which assumes a namespace FieldTypes exists)

例如，可以使用 *Vendor\\Component\\FieldTypes\\MyFieldType* 指向特定的非通用欄位類型，或在從應用程式模型本身連結時使用 *.\\MyFieldType*（假設存在命名空間 FieldTypes）。

## [volatile fields](#id2)｜[易失性場](#id2)

In some cases it can be practical to define fields which act as standard fields, but will not be persisted in the configuration. Examples of this are fields used to generate other type of content, such as a certificate or fields that reflect data stored elsewhere.

在某些情況下，定義一些功能類似於標準欄位但不會被持久化到配置中的欄位會很實用。例如，用於產生其他類型內容（如憑證）的字段，或反映儲存在其他位置的資料的字段。

To make a field volatile, just add the tag `volatile="true"` in the xml clause, for example:

若要將字段設為易失性字段，只需在 XML 子句中新增標籤`volatile="true"` ，例如：

```xml
<serial type="IntegerField" volatile="true"/>
```

## [In memory models](#id4)｜[記憶體模型](#id4)

In same cases it might be practical to use all of the standard model tools, but prevent data from being persisted. For this purpose the memory model may be used. Examples of such applications are diagnostic tools, which do require user input, but is only relevant for that particular call.

在某些情況下，使用所有標準模型工具可能很實用，但需要阻止資料持久化。為此，可以使用記憶體模型。診斷工具就是此類應用的典型例子，它們確實需要使用者輸入，但這些輸入僅與特定呼叫相關。

To use these models, use the following mountpoint: `<mount>:memory:</mount>`

若要使用這些模型，請使用以下掛載點： `<mount>:memory:</mount>`

## [Legacy wrappers](#id5)｜[舊版封裝器](#id5)

While migrating legacy components, sometimes the distance between the current situation (using raw xml access) and the desired one (being a fully validated model) is hard to overcome. It’s not always clear which type of data is being used, and when moving data inside a new model and changing it’s access path, a proper validation is mandatory.

在遷移遺留元件時，有時很難彌合當前狀態（使用原始 XML 存取）與理想狀態（完全驗證的模型）之間的差距。有時很難明確所使用的資料類型，而且當在新模型中移動資料並更改其存取路徑時，必須進行適當的驗證。

When data lives inside it’s own easy to distinct “container”, a standard model may be overlaid. An example of such a case is the static route component. Which underneath looks like this (without payload):

當資料儲存在易於區分的“容器”中時，可以應用標準模型。靜態路由組件就是一個例子。其底層結構如下（不含有效負載）：

```xml
<staticroutes>
   <route/>
   <route/>
</staticroutes>
```

The other case is when a collection of items does not live inside a unique container, for example the following payload:

另一種情況是，當一組項目不位於唯一的容器中時，例如以下有效負載：

```xml
<cert/>
<cert/>
<cert/>
```

Legacy modules would iterate over `$config['cert']` in this case. Since `cert` does not have an upper container the model is able to control in full (as it’s the root of the `config.xml`), we can not overlay a standard model to specify the fields used and their constraints.

在這種情況下，舊版模組會遍歷`$config['cert']` 。由於`cert`沒有模型能夠完全控制的上層容器（因為它是`config.xml`的根），因此我們無法覆蓋標準模型來指定使用的字段及其約束。

This is where our legacy wrapper comes into play. In order to use this feature, you have to use the following mountpoint format:

這時就需要用到我們原有的封裝庫了。若要使用此功能，您必須使用下列掛載點格式：

> `/tag+` << start with an exact path \[`/`\] and end with a plus \[`+`\]
>
> `/tag+` << 以精確路徑開始 \[ `/` \] 並以加號結束 \[ `+` \]

In the “cert” example our mountpoint would like like : `<mount>/cert+</mount>`

在「cert」範例中，我們的掛載點類似： `<mount>/cert+</mount>`

Note

筆記

All used fields still need to be specified, fields left out of the model, will be removed from the configuration in the same way a regular model would act.

所有使用的欄位仍然需要指定，模型中未包含的欄位將以與常規模型相同的方式從配置中刪除。

Note

筆記

As legacy wrappers can not be versioned, migrations do not apply. In the long run it’s always better to use full models, but these constructions offer an option for a “softer landing”.

由於舊版封裝器無法進行版本控制，因此遷移並不適用。從長遠來看，使用完整模型始終是更好的選擇，但這些構造提供了一種「更平滑的過渡」方案。

When target fields contain structures, it is possible to apply an inline conversion using custom (app specific) field types. This pattern is likely best explained with an example.

當目標欄位包含結構時，可以使用自訂（套用特定）欄位類型進行內聯轉換。這種模式最好透過範例來解釋。

Below an example implementation which unpacks multiple `<priv>` tags per user object and converts them to a comma separated lists.

下面是一個範例實現，它將每個使用者物件的多個`<priv>`標籤解包並轉換為逗號分隔的清單。

The first block `actionPostLoadingEvent()` just collects the available options, which is part of the `BaseListField` type. The `setValue()` is where the magic happens, when the input is of type `SimpleXMLElement`, we know this is being set by the loader, if in that case the underlying config contains multiple values, we merge them into a single list.

第一個區塊`actionPostLoadingEvent()`僅收集可用選項，它是`BaseListField`類型的一部分。 `setValue()` 是神奇發生的地方，當輸入是 `SimpleXMLElement` 類型時，我們知道這是由載入器設定的，如果在這種情況下底層配置包含多個值，我們將它們合併到一個清單中。

```php
class PrivField extends BaseListField
{
   protected $internalIsContainer = false;
   private static $priv_list = null;

   protected function actionPostLoadingEvent()
   {
      if (self::$priv_list === null) {
            self::$priv_list = [];
            foreach ((new \OPNsense\Core\ACL())->getPrivList() as $aclKey => $priv) {
               self::$priv_list[$aclKey] = $priv['name'];
            }

      }
      $this->internalOptionList = self::$priv_list;
   }

   /**
   * {@inheritdoc}
   */
   public function setValue($value)
   {
      if (is_a($value, 'SimpleXMLElement') && $value->count() > 1) {
            return parent::setValue(implode(',', (array)$value));
      } else {
            return parent::setValue($value);
      }
   }
}
```

## [Cached data](#id6)｜[快取資料](#id6)

In some cases access to model data requires too much handling for the time the user is willing to wait, in these cases it is possible to serve cached data to the user of the model.

在某些情況下，存取模型資料需要處理的時間過長，使用者可能不願意等待。在這種情況下，可以向模型使用者提供快取資料。

For this purpose, each model node in the config contains a `persisted_at` field with the most recent update time, in which case a static function `getCachedData()` can be used to fetch the data. This quickly checks if an object was changed (via an xpath expression) returning the data of the model in an array structure.

為此，配置中的每個模型節點都包含一個`persisted_at`字段，其中包含最近更新時間。在這種情況下，可以使用靜態函數`getCachedData()`來取得資料。此函數可以快速檢查物件是否已更改（透過 XPath 表達式），並以數組結構傳回模型資料。

Note

筆記

Although the cache will contain programmaticly generated rows using `getStaticChildren()` in `ArrayField`, it can’t automatically figure out if this content has changed.

儘管快取將包含使用`getStaticChildren()`在`ArrayField`中以程式設計方式產生的行，但它無法自動確定此內容是否已更改。

In cases you need to ensure these records are updated as well, you do need to call `flushCacheData()` on the static model. (e.g. `OPNsenseFirewallAlias::flushCacheData()`)

如果您需要確保這些記錄也更新，則需要對靜態模型呼叫`flushCacheData()` 。 （例如`OPNsenseFirewallAlias::flushCacheData()` ）
