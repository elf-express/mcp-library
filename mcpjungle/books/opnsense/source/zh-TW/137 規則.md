## [概述](#id5)

OPNsense 包含一個狀態資料包過濾器，可用於限製或允許來自和/或流向特定網路的流量，以及影響流量的轉送方式（請同時參閱「[Multi WAN](<95 多色WAN.md>)」中基於策略的路由）。

規則部分顯示適用於您的網路的所有策略，並按介面分組。

有兩種實現方式可供選擇：

-   **規則\[新\]**：現代的MVC實現，具有API支持和改進的規則管理
    
-   **規則**：靜態 PHP 頁面，不支援 API
    

提示

**規則\[新\]**將隨著時間的推移取代**規則**，您已經可以使用防火牆 ‣ 規則 ‣ 遷移助手中的幫助程序遷移現有規則。

## [基礎](#id6)

在創建規則之前，最好先了解一些適用於所有規則的基礎知識。

### [狀態](#id7)

預設情況下，規則設定為有狀態（您可以更改它，但會產生後果），這表示連接的狀態已儲存到本機字典中，該字典將在下一個資料包進入時解析。這樣做的結果是，當狀態存在時，防火牆不需要再次處理其所有規則來確定要應用的操作，這具有巨大的效能優勢。

有狀態資料包過濾的另一個優點是，您只需要允許一個方向的流量，即可自動允許同一流的相關資料包返回。下圖顯示了從客戶端到伺服器的 https 流量的 tcp 連接，當不使用有狀態規則時，應允許客戶端在連接埠 443 上將流量傳送到伺服器，而伺服器則返回客戶端（通常是連接埠 >=1024）。

![](<../images/1f4ad8bd-blockdiag-dea26ad7c72648ab145bcbdc066abb.png>)

使用狀態還可以提高安全性，特別是在 TCP 類型流量的情況下，因為也會檢查封包序號和時間戳以便傳遞流量，因此欺騙流量要困難得多。

注意事項

變更規則時，有時需要重設狀態以確保新策略用於現有流量。您可以在防火牆 ‣ 診斷 ‣ 狀態中執行此操作。

注意事項

為了保持狀態，系統需要預留記憶體。預設情況下，系統記憶體的 10% 保留用於狀態，這可以在 Firewall ‣ Settings ‣ Firewall Maximum States 中配置。 （幫助文字顯示您平台上的預設狀態數）

狀態也可以非常方便地隨時找到防火牆上的活躍頂級用戶，我們為此添加了一個易於使用的「會話」瀏覽器。您可以在防火牆 ‣ 診斷 ‣ 會話下找到它。

提示

各國在保護服務免受（分散式）拒絕服務攻擊方面也扮演重要角色（DDOS）。我們文件中提供的相關主題包括「synproxy」狀態、連線限制和 [syncookies](<146 （進階）設定.md#enable-syncookies>)

### [行動](#id8)

規則可以設定為三種不同的操作類型：

-   通過 –> 允許交通
    
-   阻止 –> 拒絕流量，並且不要讓客戶端知道它已被丟棄（這對於不受信任的網路通常是可取的）
    
-   拒絕 –> 拒絕流量並讓客戶端知道。 （只有tcp和udp支援拒絕封包，在TCP的情況下意味著返回`RST`，對於UDP `ICMP UNREACHABLE`則回傳）。
    

對於內部網絡，使用拒絕是可行的，因此客戶端不必在不允許存取時等待逾時。當從不受信任的網路接收資料包時，如果流量不允許，您通常不希望進行回應。

### [加工訂單](#id9)

防火牆規則按每個部分的順序進行處理，首先評估**浮動**規則部分，然後評估屬於**介面組**的所有規則，最後評估所有**介面**規則。

內部（自動）規則通常首先註冊。

![](<../images/21c7e41a-blockdiag-ec0d5aaf9b949b5a5e296533bff3fe.png>)

規則可以設定為`quick`，也可以不設定為quick，預設使用quick。當設定為快速時，規則將根據「第一個匹配」進行處理，這意味著與封包匹配的第一個規則將優先於按順序跟隨的規則。

當`quick`未設定時，最後一場比賽獲勝。這對於定義標準行為的規則很有用。例如，我們的預設拒絕規則使用此屬性（如果沒有規則適用，則丟棄流量）。

注意事項

內部規則使用優先權註冊，浮動使用`200000`，群組使用`300000`，介面規則結合它們出現的順序落在`400000`上。自動規則通常以較高的優先順序（較低的數字）註冊。

警告

**NAT 規則始終在過濾器規則之前處理！** 因此，例如，如果您定義 [NAT ：目的地 NAT（連接埠轉送）規則](<135 網路位址轉換.md#port-forwarding>) *沒有關聯規則*，即 **過濾器規則關聯**設定為**透過**，則結果是，不會套用其他規則！

提示

介面應該顯示所有使用的規則，當有疑問時，您可以隨時檢查`/tmp/rules.debug`中規則集的原始輸出

由於 Firewall ‣ Rules \[new\] 和 Firewall ‣ Rules 實作並存，因此需要一些關於規則處理順序的額外注意事項。

如果 Firewall ‣ Rules \[new\] 過濾規則具有：

> -   定義的單一接口，它是一個**接口規則**
>     
> -   定義的群組接口，它是**組規則**
>     
> -   定義任意數量的接口或一個反向接口，它是一個**浮動規則**
>     

加工順序：

> 1.  系統定義的規則位於規則集的開頭
>     
> 2.  防火牆 ‣ 規則 \[新\] 和 防火牆 ‣ 規則浮動規則
>     
> 3.  防火牆 ‣ 規則\[新\] 與防火牆 ‣ 規則群組規則
>     
> 4.  防火牆 ‣ 規則\[新\]單一介面規則
>     
> 5.  防火牆 ‣ 規則單一介面規則
>     
> 6.  系統定義的規則位於規則集末尾
>     

### [規則順序](#id10)

規則顯示和處理的順序可以按部分自訂：

-   透過規則左側的複選框選擇規則。
    
-   使用規則右側操作選單中的箭頭按鈕可以將所選規則移至按下操作按鈕的規則之前。
    

雖然 Firewall ‣ Rules 中的規則按照它們在設定檔中出現的順序隱式處理，但 Firewall ‣ Rules \[new\] 實作了更明確的 **排序順序**。

**排序順序**將具有以下結構：`200000.0000250`：

> -   `200000` **優先權群組**，定義規則所屬的層次結構。它可能會受到規則中介面的影響。
>     
> -   `.0000250` **序列**，它定義了介面層次結構上下文中規則的確切位置。它可以透過規則內的序列欄位或在此規則之前的移動規則按鈕來影響。
>     

例如，我們建立一些不同的規則：

> -   `200000.0000100`（浮動規則）
>     
> -   `200000.0000200`（浮動規則）
>     
> -   `300000.0000050`（團體規則）
>     
> -   `300000.0000060`（團體規則）
>     
> -   `400000.0002000`（接口規則）
>     
> -   `400000.0003100`（接口規則）
>     

套用篩選器時，規則將按此**排序順序**進行處理。優先級組內的序號越低意味著優先順序越高。

注意事項

序列不必是唯一的，多個規則可以共用相同的編號。但這意味著過濾器的填充順序並不嚴格，就好像所有規則都有唯一的序列一樣。

提示

新增規則時，序列將自動填入唯一的編號。您可以手動變更此數字以調整規則的確切位置，或使用「在此規則之前移動規則」按鈕。

### [方向](#id11)

![](<../images/30557c9a-blockdiag-8fa8f9da13994845cc6c78c64c7b85.png>)

流量可以在`in[coming]`或`out[going]`方向進行匹配，我們預設是在傳入方向上進行過濾。在這種情況下，您可以在流量源自的介面上設定策略。

例如，如果您想要允許來自網際網路上任何主機的 `https` 流量，您通常會在 WAN 介面上設定策略，允許連接埠 `443` 到達相關主機。

注意事項

預設接受離開防火牆的流量（使用非快速規則），當未選取「防火牆 ‣ 設定 ‣ 進階」中的**停用強制網關**時，也會強制執行連線的閘道。

## [實作](#id12)

### [規則\[新\]](#id13)

*規則\[新\]*最初是*防火牆自動化*，具有有限的GUI提供API支持，因為*規則*的靜態php實現缺乏自動化要求。隨著時間的推移，更多的功能被添加，GUI 也被徹底重新設計。其結果是高級搜尋功能、類別資料夾、改進的效能和更好的可見性等長期需求的功能。

您可以在 Firewall ‣ Rules \[new\] 或 Firewall ‣ Automation ‣ Filter 中找到它。

#### [使用者介面](#id14)

我們的概述顯示了適用於所選介面、群組或浮動部分的所有規則。對於每條規則，都提供了一些詳細信息，並且在適用時您可以執行移動、編輯、複製、刪除等操作。

API 訪問在[防火牆](<276 防火牆.md>) API 參考手冊中有更詳細的描述。

[![../_images/firewall_rules_1.png](<../images/06de146a-firewall_rules_1.png>)](https://docs.opnsense.org/_images/firewall_rules_1.png)

##### [介面濾鏡](#id15)

選擇一個介面來過濾目前視圖。可以選擇浮動、分組和單一介面。

如果您選擇「LAN」接口，您將看到影響LAN介面封包決策的所有浮動、群組和單一介面規則。

如果您在選擇介面時建立新規則，它將自動新增到對話方塊中。

##### [類別篩選](#id16)

選擇一個或多個類別來篩選目前視圖。這與介面濾波器的選擇相結合。

可以在 Firewall ‣ Categories 中建立類別，並且可以將不同的邏輯結構分組。

如果您為郵件伺服器建立類別並使用它標記規則，則可以簡單地過濾此標記並僅查看您的郵件伺服器。與介面過濾器一樣，選擇一個或多個標籤會將它們自動新增到新規則中。

##### [樹按鈕](#id17)

根據類別將所有防火牆規則分組到樹中。這些組的作用類似於資料夾，但始終遵循排序順序和順序。群組資料夾不保存在配置中，它們是基於類別的替代視圖。

每當序列中的規則變更類別時，都會建立一個複製第一條規則的類別的新資料夾。若要將類似規則移至同一資料夾中，請變更其順序和類別。但請記住，規則的順序始終與沒有樹視圖時相同。

##### [檢查按鈕](#id18)

檢查按鈕將顯示所有系統定義的（自動）防火牆規則並顯示規則統計資料。可以隨時啟用它以獲得當前活動規則集的完整視圖。

在檢查模式下，搜尋可以找到別名內的 IP 位址。

規則統計資訊被快取。若要提取最新的統計數據，請按下統計資料列中的刷新按鈕。

**組織**

| **選項**|**描述** |
| --- | --- |

| **排序順序** |處理規則的順序。 |
| **順序** |處理規則的順序。請注意，這不是唯一標識符，當使用可用的“在此規則之前移動規則”按鈕更改規則位置時，系統將自動重新計算規則集。 |

**過濾器**

| **選項**|**描述** |
| --- | --- |

| **版本** |應符合的IP協定版本，例如 IPv4 或 IPv6。 |
| **協議** |應匹配的傳輸協議，例如TCP或UDP。 |
| **ICMP型** |如果傳輸協定是ICMP，則此選項允許您指定ICMP類型。 |
| **ICMPv6 類型** |如果傳輸協定為IPV6-ICMP，則此選項允許您指定ICMP類型。 |
| **反轉來源** |使用此選項可以反轉符合的意義。 |
| **來源** |應符合的來源 IP 位址或別名。 |
| **來源連接埠** |來源連接埠號碼或眾所周知的名稱（imap、imaps、http、https 等），對於範圍，請使用破折號 |
| **反轉目的地** |使用此選項可以反轉匹配的意義。 |
| **目的地** |應符合的目標IP位址或別名。 |
| **目的港** |目標連接埠號碼或眾所周知的名稱（imap、imaps、http、https 等），對於範圍，請使用破折號 |
| **日誌** |記錄此規則處理的資料包 |
| **TCP 旗幟** |使用它來選擇必須設定此規則才能匹配的TCP標誌。 |
| **TCP 標記\[出自\]** |使用它來選擇必須清除此規則才能匹配的TCP標誌。 |
| **TCP 標記任何** |符合 TCP 標誌的任意組合。 |
| **日程** |規則也可以安排在特定日期或時間範圍內激活，您可以在防火牆 ‣ 高級 ‣ 計劃中建立計劃並在規則中選擇一個。如果規則逾時，狀態將被刪除，並且規則將被跳過。這意味著，如果在允許流量的預定規則之後仍然存在符合規則，則將使用它。使用計劃規則時請記住這一點，並圍繞它們仔細建立規則集，例如使用附加的阻止規則。 |
| **轉移至** |將符合此規則的資料包傳送至指定的服務，當該服務未執行時，資料包將被丟棄。 |

**狀態防火牆**

| **選項**|**描述** |
| --- | --- |
| **狀態類型** |要使用的狀態追蹤機制，預設是完整的狀態跟踪，馬虎會忽略序號，對於無狀態規則使用ne。 |
| **國家政策** |選擇如何處理此規則創建的狀態，預設（如高級定義），浮動，在這種情況下狀態在所有介面或介面綁定上都有效。介面綁定狀態更安全，浮動更靈活。 |

| **TCP成立** |狀態超時以秒為單位（僅限TCP）|
| **UDP第一** |第一個 UDP 封包後的狀態逾時（以秒為單位）。 |

#### [轉移到](#id20)

透過轉移，我們可以將額外的策略構造整合到防火牆規則中。帶有「divert-to」的規則可以將所有資料包發送到轉移套接字，[入侵防禦系統](<202 入侵防禦系統.md>)等服務可以在該套接字上偵聽。

與攔截所有流量進行檢查相比，這可以提供更細粒度的控制。它可以提高效能，因為可以排除不一定需要檢查的大流量。

例如，進入服務‣入侵偵測‣管理並將「捕獲模式」設定為「轉移（IPS）」。

然後，建立與應檢查的流量相符的防火牆規則，並在該規則中設定「轉移到」設定。匹配的資料包將被轉移到入侵偵測偵聽的套接字。做出決定後，資料包將被轉送或丟棄。

注意

請記住，當偵聽轉移套接字的服務停止時，防火牆規則將丟棄所有符合的資料包。

## [故障排除](#id24)

在建立規則集時，事情可能會出錯，但了解在哪裡尋找問題跡象總是好的。最常見的錯誤之一是流量與規則不符和/或規則的順序無論出於何種原因都沒有意義。

透過使用「檢查」按鈕，人們可以輕鬆查看是否正在評估規則以及流量是否確實通過了該規則。也可以直接跳到附加狀態以查看您的主機是否按預期位於清單中。

另一個有價值的工具是即時日誌檢視器，為了使用它，請確保為您的規則提供易於閱讀的描述並啟用「日誌」選項。

如果您使用來源路由（基於策略的路由），偵錯有時會變得有點複雜。由於正常的系統路由表可能不適用，因此有助於了解流量實際遵循哪個流。在這種情況下，資料包擷取是一個有用的工具。

這一領域的常見問題包括返回流量使用與其進入的接口不同的接口，因為流量在出去時遵循正常的路由表（回復問題），或者由於過度選擇而離開錯誤的接口（匹配內部流量並強制網關）。

檢查使用的網路遮罩也是一個好主意，打算匹配主機但提供子網是一個很容易犯的錯誤（例如`192.168.1.1/32`與`192.168.1.1/24`實際上是`192.168.1.x`的全部）。

最後但並非最不重要的一點是，記住規則是按順序匹配的，如果沒有指定其他內容，預設（入站）策略是 `block`，因為我們在 `inbound` 上匹配流量，請確保添加流量源自的規則（例如 `lan` 對於離開網路的流量，返回通常應由州允許）。
