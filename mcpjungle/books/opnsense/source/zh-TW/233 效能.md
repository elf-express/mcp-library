# 效能

> 章節：[Troubleshooting](<000 目錄.md#c-50>) › [Topics](<000 目錄.md#c-51>)

## 接收端縮放

### **簡介**

RSS 用於使用雜湊函數在 CPU 核心上分發資料包 - 可以在為您卸載散列的硬體中提供支持，也可以在軟體中提供支援。這個想法是將資料包的 TCP 4 元組（來源位址、來源連接埠、目標位址、目標連接埠）作為輸入，使用內核定義的鍵對該輸入進行雜湊處理，並選擇結果值的 LSB 作為使用者可配置間接表的索引。間接表在引導期間載入到硬體中，並由 NIC 使用來決定使用給定封包中斷哪個 CPU。所有這些都允許相同來源/目的地（也稱為流）的資料包在相同的CPU上一致地排隊。

注意事項

**預設情況下，RSS將被停用，因為它的影響相當深遠。**

僅當您有興趣測試它並查看它是否會增加高負載下的吞吐量時才啟用此功能 - 例如使用IDS/IPS時。

由於我們沒有每種類型的可用硬件，也沒有時間測試所有硬件，因此無法保證 NIC 驅動程式能夠正確處理內核實現，甚至能夠使用它。

RSS 的實作與 [PCBGROUP](https://www.freebsd.org/cgi/man.cgi?query=PCBGROUP) 結合－此實作引入了 CPU 連接關聯性的概念。雖然後者對於 OPNsense 來說不太重要，因為它特別適用於使用套接字在用戶空間中建立的連接（與伺服器相關，而不是中間盒），但透過硬體支援在較低層級上分配工作的想法提供了許多好處。

### **網路卡/驅動**

假設您使用的是支援多個硬體隊列的現代NIC和RSS，NIC的配置將決定封包如何以及通過哪些隊列到達您的系統。這也取決於硬件，並且在每個NIC上都不相同。如果您的驅動程式支援啟用/停用 RSS 的選項，則 sysctl 可調參數將可用。

NIC 可以在無法設定的情況下執行 RSS。如果您想知道是否可以啟用/停用它：

```
sysctl -a | grep rss
```

應顯示透過可調參數公開該選項的任何驅動程式。

驅動程式也可能不會向使用者公開此功能，在這種情況下，您需要使用線上資料表或簡單的 google 搜尋來尋找 NIC/驅動程式是否支援 RSS。例如，igb 預設啟用RSS，但不會在任何配置參數中反映這一點。但是，由於它使用多個隊列：

```yaml
# dmesg | grep vectors

igb0: Using MSI-X interrupts with 5 vectors
igb1: Using MSI-X interrupts with 5 vectors
igb2: Using MSI-X interrupts with 5 vectors
igb3: Using MSI-X interrupts with 5 vectors
```

它很可能具有某種形式的資料包過濾來在硬體佇列上分發資料包。事實上，igb 預設是RSS。

對於大多數 NIC，RSS 是決定使用封包中斷哪個 CPU 的主要方法。未實作任何其他類型過濾器且 RSS 功能遺失或關閉的 NIC 很可能始終僅中斷 CPU 0 – 這將降低因快取行遷移和鎖爭用而導致的潛在吞吐量。如果是這種情況，請保持系統範圍內的RSS禁用。

最後但並非最不重要的一點是要考慮的事實是，驅動程式支援內核內實現的RSS是必須的。正確的驅動程式支援將確保在硬體中設定正確的金鑰和間接表。根據原始碼支援RSS的驅動程式（但大多未經測試）：

-   嗯
    
-   igb -> 測試並工作
    
-   axgbe -> 已測試並工作
    
-   網路服務中心
    
-   伊克斯貝
    
-   伊克斯爾
    
-   CXGBE
    
-   裡奧
    
-   毫升×5
    
-   sfxge
    

### **核心支援**

在內部，FreeBSD 使用 [netisr](https://www.freebsd.org/cgi/man.cgi?format=html&query=netisr\(9\)) 作為抽象層，用於將封包分派到上層協定。在實作中，預設設定是將資料包處理限制為僅一個執行緒。由於 RSS 現在提供了一種將流保持在 CPU 本地的方法，因此應在系統 -> 設定 -> 可調參數中設定以下 sysctls：

-   net.isr.bindthreads = 1
    
-   net.isr.maxthreads = -1
    

第一個選項導致執行緒綁定到CPU，下一個選項將工作流程分配給每個可用的核心。

此外，RSS實作也提供了一些必要的sysctl：

-   net.inet.rss.啟用 = 1
    

確保RSS已啟用。預設情況下停用此功能，以防止未正確實作 RSS 介面的 NIC 出現迴歸。

-   net.inet.rss.bits = X
    

這取決於您擁有的核心數量。預設情況下，此處的位數表示二進位的核心數 x 2。這樣做的目的是為了提供負載平衡，儘管目前沒有實現此目的，因此我們建議將此值設為表示 CPU 核心數量的位數。這意味著我們使用以下值：

-   對於 4 核心系統，使用“2”
    
-   對於 8 核心系統，使用“3”
    
-   對於 16 核心系統，使用“4”
    
-   等等
    

注意事項

請記住在更改`net.inet.rss.enabled`後重新啟動計算機，因為此選項只能在啟動期間設定。

### **驗證設定**

如果使用「enabled」sysctl 啟用RSS，則封包調度策略將從「直接」變為「混合」。如果允許，這將直接在當前上下文上分派資料包，否則它將在其進入的綁定CPU上對資料包進行排隊。請注意，這會增加中斷負載，如“top -P”所示。這僅僅意味著資料包正在CPU調度程序中以最高優先權進行處理 - 這並不意味著CPU承受比正常情況更多的負載。

可以透過執行以下命令來驗證 netisr 是否正常運作：

```
netstat -Q
```

### **關於IPS的注意事項**

當 Suricata 在IPS模式下運作時，Netmap 用於從線路上取得封包進行檢查。預設情況下，OPNsense 已將 Suricata 配置為將通過檢查的封包重新註入主機網路堆疊以用於路由/防火牆目的。目前的 Suricata/Netmap 實作將這種重新註入僅限於一個執行緒。由於新的 Netmap API (V14+) 現在能夠增加此線程計數，因此我們正在努力解決此問題。在此之前，使用 IPS 時，RSS 不會獲得任何好處。
