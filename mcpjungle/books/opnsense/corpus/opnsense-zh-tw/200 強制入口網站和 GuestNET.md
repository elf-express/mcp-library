# 強制入口網站和 GuestNET

**強制入口網站**允許您強制進行身份驗證，或重定向到點擊頁面進行網路存取。這通常用於熱點網絡，但也廣泛用於企業網絡，以在無線或互聯網訪問上提供額外的安全層。



## 概述和術語

### 典型應用

-   訪客網絡
    
-   飯店和露營地無線網路連接
    
-   自備設備 (BYOD)
    

### 範本管理

OPNsense 獨特的範本管理器讓設定您自己的登入頁面成為一項簡單的任務。同時它還提供額外的功能，例如：

-   URL重定向
    
-   您自己的彈出視窗選項
    
-   自訂啟動頁面
    



### 區域管理

每個介面可以設定不同的區域，或者多個介面可以共用一個區域設定。每個區域可以使用不同的強制門戶範本或與其他區域共用。

### 認證

透過 HTTPS 或帶有 URL 重定向到給定頁面的僅啟動入口網站進行安全身份驗證 可以使用不同的來源對區域中的使用者進行身份驗證：

-   LDAP \[微軟活動目錄\]
    
-   半徑，包括會計更新
    
-   本地用戶管理員
    
-   優惠券/門票
    
-   無身份驗證（僅限啟動畫面）
    
-   多個（以上的組合）
    

### 優惠券管理器

OPNsense 的 Captive Portal 具有簡單的憑證建立系統，可將憑證匯出到 csv 文件，以便與您喜愛的應用程式一起使用。透過匯出，您可以透過將憑證與 Microsoft Word 或 LibreOffice 範本合併來列印憑證，並使用您的商標和公司風格創建美觀的講義。

### 超時和歡迎回來

在用戶空閒一定時間（空閒超時）後，可以終止連接，和/或在經過幾分鐘後強制斷開連接，即使用戶仍然處於活動狀態（硬超時）。如果使用者在空閒逾時和/或硬逾時內重新連接，則無需登錄，且使用者可以恢復其活動會話。

### 頻寬管理

內建流量整形器可用於：

-   均勻共享頻寬
    
-   優先考慮協定連接埠號碼和/或IP位址
    

另請參閱：[流量整形](<138 流量整形.md>)

### 門戶旁路

可以將MAC位址和IP位址/網路範圍列入白名單以繞過入口網站。

### 平台整合

透過整合的REST API，強制入口網站應用程式可以與其他服務整合。請參閱：[使用API](<370 使用API.md>)

### IPv6支援

OPNsense Captive Portal 完全支援純 IPv6 和雙棧網路。為了實現這一點，\[漫遊\] 選項可用並在每個區域中預設。 IPv6 協定通常會在客戶端的相同網路介面上使用多個 IPv6 位址。這些可以是連結本地地址、GUA、ULA、臨時/隱私地址或穩定地址。

漫遊允許入口網站註冊客戶端正在使用的任何IP別名，包括 IPv4 位址。一旦客戶端連接，這些IP位址就會在後台收集並授予存取權限。

此外，IPv6 要充分發揮作用，必須符合以下標準：

-   必須啟用 Hostwatch（介面 ‣ 鄰居 ‣ 自動發現）才能收集 IPv6 位址。
    
-   您必須在區域設定中設定 \[主機名稱\]，並確保該主機名稱存在指向正確 IPv6 位址的 DNS 記錄。如果您使用 Unbound，則可以使用 Services ‣ Unbound DNS ‣ General 中的 \[DNS64\] 選項來合成已設定介面的 DNS 記錄。
    

注意事項

收集這些IP位址的後台進程以固定的時間間隔執行此操作。在收集所有位址並授予存取權限之前可能會稍有延遲。

### 現代門戶支持

OPNsense 透過在驗證之前將所有HTTP 流量重定向到本地 Web 伺服器來實現強制門戶，從而向裝置暗示它位於門戶後面。然而，[RFC 8910](https://www.rfc-editor.org/rfc/rfc8910) 引入了一種新的網路標準化方法，以使用 DHCP 通知客戶端入口網站的存在。此外，[RFC 8908](https://www.rfc-editor.org/rfc/rfc8908)描述了由DHCP指向的Web伺服器實現的API標準，客戶端可以在其中取得目前入口網站狀態。 Apple 發布了一份[文件](https://developer.apple.com/news/?id=q78sq5rv)，其中包含更多詳細資訊。

轉向此標準化API的現代客戶端（尤其是 iOS）在連接到僅支援強制重定向的網路時可能會遇到重定向問題，這通常可以透過利用此新標準來解決。

要配置此功能，需要執行幾個步驟：

-   您必須在強制門戶區域上安裝有效的、公開信任的憑證。例如，您可以使用ACME客戶端來自動化此流程。無論重定向方法如何，這樣做都是最佳實踐。
    
-   在強制門戶區域中運行的 DHCPv4 伺服器必須提供選項 114，其中的值必須設定為運行門戶的 OPNsense Web 伺服器：`https://<opnsense-hostname>/api/captiveportal/access/api`。或者，客戶端也可以直接指向重定向的網頁伺服器：`https://<opnsense-hostname>:<8000 + captive portal zone id>/api/captiveportal/access/api`。例如，`https://opnsense.localdomain:8001/api/captiveportal/access/api` 表示區域 1。有關更多詳細信息，請參閱下面的注意塊。若要設定此 DHCP 選項，請參閱對應 DHCP 伺服器的文件。
    

如果強制門戶區域中的設備支援此API，它們將自動使用DHCP選項來確定它們處於強制狀態。請記住，仍然使用強制重定向來實現最大相容性。如果您想專門使用此API標準，則可以覆寫每個區域的防火牆規則並省略重定向規則，請參閱[規則](#rules)。

注意

當用戶端透過入口網站登入後，您的防火牆策略將定義該用戶端可以存取和無法存取的內容。除非您已將 DHCP 選項配置為透過指定連接埠直接指向入口網站 Web 伺服器，否則 `/api/captiveportal/access/api` 端點現在指向連接埠 443 上的常規 OPNsense WebGUI，因為不會重定向經過驗證的用戶端。這也意味著客戶端無法再確定圈養狀態。

如果您想要限制用戶端僅存取此端點，則必須配置正確的轉送規則，如下所示。請注意，這意味著客戶端無法再存取 OPNsense WebGUI，這通常是可取的。

|   |   |
| --- | --- |
| **類型** |目的地NAT（港口轉送）|
| **介面** | <Zone interface> |
| **版本** | IPv4+IPv6 |
| **協議** | TCP |
| **來源** | \_\_captiveportal\_zone\_<zone id> |
| **目的地** |此防火牆 |
| **目標連接埠範圍** | 443 | 443
| **重定向目標IP** | 127.0.0.1 |
| **重定向目標埠** | 8000+<zone id>|
| **NAT 反思** |禁用（高級）|
| **防火牆規則** |通行證 |

注意事項

OPNsense `/api/captiveportal/access/api` 端點傳回以下資訊：

-   客戶此時是否處於「俘虜」狀態。
    
-   門戶網站的URL。
    
-   如果用戶端已通過身份驗證並設定了硬逾時，則此會話還剩多少秒。

## 遷移說明和技術細節

重要

從 OPNsense 社群版 25.1.4 或商業版 25.10 開始，底層強制入口網站實施已從 IPFW 移至 PF。雖然在大多數情況下這沒有實際影響，但此處更詳細地描述了這意味著什麼以及任何不相容性。

先前，我們的 Captive Portal 實作分為兩個元件：IPFW 和 PF。封包將進入一個接口，其中IPFW是第一個處理它們並將流量重定向到門戶的接口。驗證後，將插入一條允許進出該客戶端的所有流量的規則。任何經過IPFW的流量都將由PF處理。對於出站流量來說，情況正好相反。透過將重定向和計費邏輯移至PF，簡化了此過程。

這有多個好處：

-   產生的規則現在在 WebGUI 中可見，並且預設會記錄下來，從而簡化故障排除。
    
-   已通過身份驗證的用戶端清單現在是別名且可見，並且可在規則中使用。別名稱為`__captiveportal_zone_<zoneid>`。
    
-   除非使用自訂整形器規則，否則不需要再載入IPFW，從而顯著降低實現複雜性。
    

以下是唯一的功能/行為變化：

-   如果您在強制門戶區域中定義了轉送規則，將用戶端重定向到HTTP/HTTPS以外的服務，則該規則上的“過濾器規則關聯”選項必須設定為“通過”，以便在重定向後允許此流量；否則，此流量將符合預設的強制門戶阻止規則。此類場景的範例是用戶端 DNS 流量重定向到在本機上執行的 DNS 服務。
    
-   “允許入站”選項已刪除。此選項僅影響 IPFW 規則並控制是否允許來自另一個網路的流量進入強制門戶區域。現在，此行為由流量來源網路的規則集決定。例如，如果根據規則集在任何地方都允許非強制介面上的某個網絡，則該流量也被允許進入強制門戶區域。如果不希望這樣做，則必須在所述介面上配置明確阻止規則。
    
-   除非您要覆蓋（新）自動產生的防火牆規則，否則您不再需要防火牆上DNS（連接埠 53）的明確通過規則，也不再需要強制門戶區域（連接埠 8000-10000）的允許規則。這些現在是預設安裝的。
    

### 強制門戶防火牆規則

執行預設強制門戶區域時，必要的重定向規則會自動安裝在該區域。這些規則比任何使用者定義的規則具有更高的優先權。因此，為了實現靈活性，可以使用區域管理中的「停用防火牆規則」選項來覆寫這些規則。這裡列出了自動產生的規則，以便可以重新建立它們以實現正確的入口網站功能。

#### 將流量重定向到區域網路伺服器

所有前往連接埠 80 的 HTTP 流量都會重新導向至本機主機連接埠 9000 + <zone id>。

所有在連接埠 443 上到達防火牆的 HTTPS 流量都將重定向到本機主機連接埠 8000 + <zone id>。

|   |   |
| --- | --- |
| **類型** |目的地NAT（港口轉送）|
| **介面** | <Zone interface> |
| **協議** | TCP |
| **源反轉** |是的 |
| **來源** | \_\_captiveportal\_zone\_<zone id> |
| **目的地反轉** |是的 |
| **目的地** | \_\_captiveportal\_zone\_<zone id> |
| **目標連接埠範圍** | 80|
| **重定向目標IP** | 127.0.0.1 |
| **重定向目標連接埠** | 9000 + <zone id> |
| **NAT 反思** |禁用（高級）|

|   |   |
| --- | --- |
| **類型** |目的地NAT（港口轉送）|
| **介面** | <Zone interface> |
| **協議** | TCP |
| **源反轉** |是的 |
| **來源** | \_\_captiveportal\_zone\_<zone id> |
| **目的地** |此防火牆 |
| **目標連接埠範圍** | 443 | 443
| **重定向目標IP** | 127.0.0.1 |
| **重定向目標連接埠** | 8000 + <zone id> |
| **NAT 反思** |禁用|

對於 IPv6，必須建立與上述相同的規則，但目的地必須設定為「<Zone interface> 位址」。

HTTP 流量的目標是反向區域別名，因此來自未經身份驗證的用戶端的流量不會重定向到經過身份驗證或明確允許的客戶端/伺服器（區域管理中允許的位址）。如果未經身份驗證的用戶端應該能夠存取同一區域中的伺服器，這非常有用。

注意

如果您使用[OIDC](<50 OpenID 連接.md>) 對於身份驗證， HTTPS 在進行身份驗證之前，請求也會被重新導向。要解決此問題，請建立一個額外的「否 RDR (NOT)」規則**在**另一個之前 NAT 與身分提供者的規則 IP 地址作為目的地。

|   |   |
| --- | --- |
| **類型** |目的地NAT（港口轉送）|
| **沒有 RDR (NOT)** |是的 |
| **介面** | <Zone interface> |
| **協議** | TCP |
| **來源** |任何|
| **目的地** |身分提供者 ip 位址 |
| **目標連接埠範圍** | 443 | 443

#### 未經身份驗證的使用者的預設封鎖規則

根據以下規則，來自非DNS 或造訪入口網站網頁的用戶端的任何流量都會被封鎖。

|   |   |
