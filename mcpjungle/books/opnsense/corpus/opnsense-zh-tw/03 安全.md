## [引言](#id15)

作為一款值得信賴的開源安全產品，我們非常重視安全性，並透過定期發布更新來努力預防潛在安全事件的發生。儘管我們保持謹慎並密切關注安全動態，但有時問題仍然會發生，在這種情況下，了解應對措施至關重要。

## [保持領先](#id16)

儘管我們一直鼓勵大家定期更新，但有時由於各種原因，這是不可能的。

幸運的是，OPNsense 內建了已知漏洞的安全檢查功能，該功能位於我們的韌體模組中。因此，您可以自行驗證繼續使用目前版本一段時間的風險。

您可以透過狀態窗格中的「系統」->「韌體」存取它，「執行審核」按鈕將直接帶您進入安全性報告。

如果一切順利，將會顯示以下報告：

```
***GOT REQUEST TO AUDIT SECURITY***
Currently running OPNsense 22.1.8_1 (amd64/OpenSSL) at Tue May 31 09:01:04 CEST 2022
vulnxml file up-to-date
0 problem(s) in 0 installed package(s) found.
***DONE***
```

筆記

我們不提供社群支持，幫助您評估舊版中出現的問題是否需要立即升級，因為這通常取決於您使用的功能和配置的設定。我們始終建議您升級到最新的社群版或企業版。

警告

請不要向我們報告安全健康檢查中發現的問題，這些問題我們已經知道，並且很可能會在下一個版本中修復。

## [風險評估](#id17)

與所有軟體一樣，了解軟體的開發方式對於評估其使用風險大有裨益。大多數軟體元件都建構在其他元件之上，而每個元件都存在自身的安全挑戰。從架構角度來看，我們力求盡可能減少外部依賴，但顯然，為了實現我們提供的廣泛功能，各種軟體元件不可或缺。

當我們自行添加功能時（在 [第 1 層和第 2 層](<379 支援選項.md>)下支援），我們通常至少會問自己以下問題：

-   我們計劃添加的新組件是否會替換我們已經使用的組件？我們如何確保最終不會只增加一個組件？
    
    -   一個很好的例子就是[tabulator](https://www.tabulator.info/)的使用，它逐漸取代了我們之前使用的 bootgrid。
        
-   該組件的開發進度如何？可以獲得怎樣的支持？
    
-   預計維護負擔有多大？相對於新增功能而言是否合理？
    
    -   當一個函式庫與所用語言中已有的工具相比，提供的功能微乎其微時，為了更好地管理依賴關係，通常最好自己建構和維護這些功能。
        
    -   此外，既然我們已經有一個元件提供了幾乎相同的功能，那麼再增加一個元件還有意義嗎？
        
-   我們能否輕鬆地用替代品替換某個組件，或自行維護軟體？
    
    -   例如，我們之前使用 Phalcon 來支援我們的大部分MVC程式碼，而這些程式碼後來大多已使用標準的PHP程式碼重寫。
        

雖然我們的開發手冊詳細介紹了我們的工作流程，但在這裡簡要概述我們的方法，並重點關注其安全性方面，也並無壞處。技術堆疊中的不同元件在處理安全問題時可能會採用略有不同的方法。在規劃和建造版本時，所有這些問題都會被納入考慮範圍。

### [\[埠\] 外部軟體]( https://docs.opnsense.org/security.html#id19 )

大多數BSD的外部軟體都是透過「連接埠集合」進行管理的，它更像是一本配方手冊，描述如何建立不同的軟體元件。 OPNsense 託管上游集合的（部分）鏡像，並在此基礎上添加了一些我們自己維護的二進位軟體。

為了追蹤漏洞，可以使用 VuXML [4](#id8) .，也可以使用韌體部分的「安全審計」功能直接從 OPNsense 介面查詢。

雖然並非所有已安裝軟體的安全事件都會對您的設定產生影響，但這些資訊可以幫助您了解運行配置所涉及的風險。

以下是透過審核功能提取的報告範例。

```
 python313-3.13.15 is vulnerable:
   Python -- poplib module, when passed a user-controlled command, can have additional commands injected using newlines
   CVE: CVE-2025-15367
   WWW: https://vuxml.FreeBSD.org/freebsd/6d3488ae-2e0f-11f1-88c7-00a098b42aeb.html
```

第一行（1）解釋了該危險指的是哪個軟體包，接下來（2）有一些關於該事件的詳細信息，有助於評估此特定問題是否對您產生影響，當附加一個或多個CVE時，您可以在以下幾行（3）中找到它們，然後是指向更多信息的鏈接（4）。

在製定版本發布計劃時，我們使用相同的資訊來確定對產品的影響。

## [部署注意事項](#id22)

防火牆是一種安全工具，應依照其設計進行部署和操作。雖然 OPNsense 提供了一些機制來幫助保護網路環境，但任何防火牆都無法彌補薄弱的操作規範或過度信任關係。

取得防火牆存取權限的使用者通常會執行管理或維運任務，因此需要更高的信任等級。管理存取權限應僅限於其職責所需的用戶，並且應盡可能遵循最小權限原則分配權限。

僅限受信任的管理員

某些存取控制角色提供的功能可以有效地直接或間接地完全控制系統，因此應該只指派給完全信任的管理員或管理同級人員。

例如， `XMLRPC Library`權限可用於遠端設定同步和自動化，而`System: Configuration: Backups`權限則提供包含敏感資訊的設定匯出檔案的存取權限。實際上，任何授予對配置資料、遠端管理介面、備份材料或自動化機制存取權限的權限都應被視為安全敏感權限，並應謹慎分配。

細粒度的權限和信任

存取控制清單可以提供細粒度的權限，從而提高操作便利性、授權能力和視覺性。根據具體應用場景，這些權限也可以作為有效的安全邊界。

然而，管理員應該考慮角色所賦予的實際功能，而不僅僅依賴單一權限的表面範圍。某些權限看似範圍有限，但實際上卻允許使用者間接地影響或繞過相關的安全控制。

例如，有權管理連接埠轉送規則的使用者可能能夠建立對原本無法存取的系統或服務的存取路徑。

因此，權限分配應同時反映預期任務和對接收權限的使用者的信任程度。

遺留組件

某些遺留元件（URI 以`.php`結尾）源自程式碼庫的早期版本，其驗證和存取控制措施可能不如新元件完善。因此，應盡可能將這些頁面的存取權限限制在完全受信任的管理員範圍內。

管理介面的存取權限應僅限於受信任的網絡，並使用強身份驗證機制進行保護。管理員帳戶應使用唯一密碼，並在支援且適當的情況下使用其他身份驗證因素。

為減少攻擊面，應停用或移除不必要的服務、外掛程式和使用者帳戶。應及時安裝安全性更新和維護更新，以保持系統最新狀態。

定期審查防火牆規則、使用者帳戶、暴露的服務和遠端存取方法，有助於確保配置繼續反映運行要求，並且不會無意中引入安全風險。

應定期建立配置備份並安全存儲，以便在硬體故障、配置錯誤或安全事件發生時能夠快速恢復。應啟用日誌記錄和監控功能，以協助進行故障排除、稽核和異常行為偵測。

安全性不是單一的配置選項或部署步驟，而是一個持續的過程，需要不斷審查、維護和適應不斷變化的需求和威脅。

## [報告事件](#id23)

您可以使用我們的 [GitHub 程式碼庫](https://github.com/opnsense/core/security)回報我們產品的安全事件。您也可以建立一個新的 issue 並選擇“報告安全漏洞”，系統會將您重新導向到同一頁面。此外，您也可以透過 **security**@**opnsense.org** 聯絡我們的安全團隊回報安全問題。

所有報告至少應包含以下資訊：

-   對當前漏洞的清晰描述
    
-   我們產品的哪些版本似乎受到影響
    
-   任何已知的解決方法
    
-   如果可以，請提供一些範例程式碼
    

## [資訊處理政策](#id24)

作為一項一般政策，我們傾向於在經過一段合理的時間後全面披露漏洞信息，以便進行安全的分析和糾正，以及對當前糾正措施進行適當的測試。

為了與其他受影響方協調，我們可能會將部分已獲得的資訊分享給他們，或要求記者這樣做。

如果提交者希望採用協調一致的揭露流程，則應在提交的資料中加以說明，以避免日後產生爭議。

## [第三方安全驗證](#id25)

### [引言](#id26)

在 OPNsense 團隊和社群中，我們花費大量時間來保護我們的軟體並跟上最新的威脅，例如在每次發佈時檢查所用軟體是否符合 CVE，在我們的開發方法中實施最佳實踐，並提供清晰透明的發佈工程。

為了進一步改進這一點，我們決定引入第三方，並由訓練有素的安全專業人員圍繞我們的安全驗證流程來製定方案。

### [商務版](#id27)

由於我們的商業版面向專業用戶，因此提供額外的安全保障措施（例如對該產品進行更全面的測試）是合理的。從我們軟體的生命週期來看，這也是我們目前產品最成熟的階段：

-   開發版本
    
    -   每次發布都會提供，讓玩家可以一窺不久的將來會有哪些新內容。
        
-   社群版
    
    -   當開發版本中的變更得以保留時，這些變更將被納入社群版本，這些變更將經過內部測試，並接受社群成員的回饋。
        
-   商業版
    
    -   功能變更以更保守的方式進行，從開發和社群收集了更多回饋，從而形成了著名的 OPNsense 防火牆的關鍵任務版本。
        

由於安全測試非常耗時，我們力求為每個主要版本提供完整的認證週期。

### [框架/測試類型 ( LINCE )](#id28)

在尋找合適的框架時，我們發現了LINCE方法論。

LINCE是一種輕量級的評估和認證ICT產品的方法，由西班牙國家密碼中心 ([CCN](https://cpstic.ccn.cni.es/en/) ) 創建，基於通用準則原則，並圍繞漏洞分析和滲透測試展開。

LINCE相較於其他方法論的主要優勢在於工作量和時間投入的減少。此外，其應用方式也使得我們能夠更加關注每個產品的關鍵點，更加重視針對實際威脅的特定實用測試，而非繁瑣的文檔編寫或詳盡的功能測試。

由於大多數框架並非旨在經常重複使用，因此我們與 [jtsec](https://www.jtsec.es/)一起提出了一種方法，使得每年進行兩次測試成為可能，這對於與我們的商業版發布保持一致是必要的。

在每個週期中，總有可能出現一些（小的）問題需要解決。根據 jtsec 的規定，OPNsense 團隊會針對發現的問題準備修復方案，並確保這些方案包含在未來的（次要）版本中。

### [流程步驟](#id29)

為了更了解 OPNsense 的某個版本在驗證方面的位置，我們將流程分為以下階段，我們也會在目前版本中註明這些階段。

1.  測試中 - 交付給 jtsec 的軟體，正在進行中（OPNsense 和 jtsec 之間的交互作用）。
    
2.  已測試 - 軟體已驗證/測試，文件尚未發布。
    
3.  LINCE符合要求 - 測試完成，包括一份總結報告（由 jtsec 提供）。
    
4.  認證待定 - 可提供正式認證。
    
5.  LINCE認證 - 由CCN認證。
    

認證步驟每年執行兩次，每次針對商業版版本發布。這個過程相當耗時，但引入了另一個獨立的第三方機構。

### [時間軸](#id30)

第一款獲得全面認證的產品是社群版（ 21.7.1 ），它讓我們深入了解了整個流程，並幫助我們改進了流程，我們希望將這些改進應用於商業版。我們以包含 jtsec 全面測試的版本22.4開啟了這一週期。
