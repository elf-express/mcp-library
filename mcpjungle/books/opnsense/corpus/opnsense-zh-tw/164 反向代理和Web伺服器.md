# 反向代理和Web伺服器


注意事項

所有反向代理都是插件，需要先安裝。

## 為什麼要使用反向代理？

資料包過濾器本身無法決定應用層協定應該如何處理。要進行此類檢查，可以使用深度套件檢測或反向代理。

此外，反向代理還可以實現特定協定的存取控制清單以及其他檢查機制，以保護其背後的應用程式。這些檢查機制包括惡意軟體、垃圾郵件和網路攻擊偵測等。

警告

反向代理可以阻止常見的機器人攻擊，但無法百分之百偵測出惡意流量。尤其是有針對性的攻擊，由於攻擊者已經投入大量精力來阻止偵測，因此反向代理很可能無法被偵測到。切勿將反向代理作為逃避修復根本問題的藉口，例如庫中已知的漏洞、過時的軟體或自身程式碼中的漏洞。

## 條款

**正向代理**

客戶端用於連​​接網際網路的代理伺服器。它通常被企業用於掃描網路流量中的惡意軟體。更多背景信息，請參閱更具體的頁面（[快取代理](<179 快取代理.md>) ）。

**反向代理和網路伺服器**

反向代理是一種軟體，它接收來自客戶端的請求或連接，並將其發送到上游伺服器。如有需要，它可以修改一些資料（例如注入HTTP標頭或執行存取控制）。反向代理可以通用，適用於任何協議，但通常用於HTTP (S)。

反向代理不需要完全了解它正在傳輸的數據，它只需要決定哪個上游負責處理它，以及一些元數據來知道它應該做什麼（例如緩存 Cache-Control 標頭和在HTTP中授權 Authentication 標頭）。

與反向代理不同，Web 伺服器處理請求（Web 伺服器包含 Web 應用程式的業務邏輯），並根據請求發送回應。反向代理（例如 [Varnish](https://varnish-cache.org/) 、[nginx](https://www.nginx.com/resources/wiki/start/topics/examples/reverseproxycachingexample/) ）或正向代理（請參閱 [設定防毒保護](https://docs.opnsense.org/manual/how-tos/proxyicapantivirus.html) 、[設定快取代理](https://docs.opnsense.org/manual/how-tos/cachingproxy.html) ）可能會修改或快取此回應。例如，Web 伺服器可以從本機檔案系統提供名為 index.html 的文件，或處理API端點並傳回結果。 Web 伺服器通常有一個API用來呼叫外部解釋器：

| **API** | **典型用例**|**已實現（範例）** |
| --- | --- | --- |
| FastCGI | PHP ，Rails | PHP-FPM ，nginx，Apache HTTPd |
| AJP | Java 應用伺服器 | Tomcat、JBoss、WildFly、Apache HTTPd ([mod\_jk](https://tomcat.apache.org/connectors-doc/webserver_howto/apache.html) ) |
| (U) WSGI | Python | [Django](https://uwsgi-docs.readthedocs.io/en/latest/tutorials/Django_and_nginx.html)透過UWSGI |

其他方法則直接將解釋器整合到 Web 伺服器中，這些解釋器是用這種語言或 C/C++ 擴充功能編寫的：

| **技術**|**用途** |
| --- | --- |
| 乘客 | 支援多種語言的應用伺服器 |
| nginx [單元](https://unit.nginx.org/) | 支援多種語言的應用伺服器 |
| [Undertow](http://undertow.io/) (Raw、JBoss、WildFly) | Java 應用伺服器 |

**上游、後端**

可用於負載平衡客戶端請求的單一或多個伺服器。上游使用的所有伺服器必須效能相同（例如，使用相同的協定），但無需運行在相同的連接埠上。

**上游伺服器、後端伺服器**

這是您的監聽應用程序，例如連接埠 80 上的 nginx（用於HTTP或TCP 389 上的LDAP伺服器。

**前端（HAProxy）和HTTP （S）/串流媒體伺服器（nginx）**

這些是用於傳入連接的連接埠配置。例如，如果您將連接埠綁定到TCP /80（ HTTP的標準連接埠），您可以決定如何處理此請求。連接也是如此。

**TLS和SSL**

TLS取代了SSL ，它用於保護應用程式協定免受各種攻擊，例如窺探或資料篡改（例如廣告注入、重定向、篡改下載的文件，如可執行文件）。

現代客戶端和伺服器應支援TLS 1.2和TLS 1.3 。其他所有功能都應停用。

## TLS - 不同的使用方法

### 1. 在防火牆上斷開連線（下行和上行都使用TLS ）

在此設定中，我們有兩個受TLS保護的連接。一個是從客戶端到防火牆的連接，另一個是從防火牆到後端的連接。

這種設定的優點在於，您可以根據路徑或其他屬性進行路由，並向客戶端提供另一個憑證。例如，您可以在伺服器上使用內部證書，反向代理程式會向用戶端提供可能受信任的證書，例如 Let's Encrypt 的憑證。這簡化了憑證處理，因為上游用戶端的憑證可能無效（例如已過期）。請注意，不建議停用上游的證書檢查，但在某些情況下可能需要這樣做。

### 2. 解密加密的上游（下游明文，上游TLS受保護）

在大多數情況下，這種設定可能意義不大。但如果您遇到某些軟體不允許使用未加密端口，而某個特定的內部客戶端又不支援該端口的情況，那麼這種設定或許會有幫助。例如，一台機器需要與伺服器通信，但由於硬體不支援，無法使用TLS連接埠。如果您確實需要這樣做，請不要透過互聯網提供該端口，因為上游伺服器可能出於某種原因只支援TLS端口。

### 3. TLS卸載（下游受TLS保護，上游不受保護）

如果支持，應優先選擇這種配置。它的優勢在於，它完全支援客戶端的TLS ，同時在您自己的電腦中心內執行TLS握手時不需要太多的性能。

警告

對於可透過不受信任的網路存取的上游伺服器，請勿使用此方法。在這種情況下，請使用方法 (1) 或 (4)。

### 4. TLS直通

在此模式下，代理只會轉送連接，無法存取加密的有效負載。您無法對協​​議本身進行任何匹配。您可以使用一些擴充標頭（例如SNI來決定使用哪個上游伺服器。如果您只是想要比普通的NAT更好的路由決策，建議使用此設定。

注意事項

即使反向代理擁有伺服器的私鑰，且使用的密碼套件不包含 [PFS](https://en.wikipedia.org/wiki/Forward_secrecy) ，它仍然可以存取加密內容。在其他情況下，只有當其中一方託管金鑰時，連線才能解密。 Firefox 透過環境變數 [SSLKEYLOGFILE](https://developer.mozilla.org/en-US/docs/Mozilla/Projects/NSS/Key_Log_Format)支援此功能。 OPNsense 插件不支援此功能。
