# 基礎與未來

本文解釋了適用的基本編碼指南，並透過解釋遺留程式碼的困難以及與新的[MVC基於](https://en.wikipedia.org/wiki/Model%E2%80%93view%E2%80%93controller)程式碼的互動/遷移來正確看待開發工作。它還解釋了新代碼和舊代碼之間的指南差異。

## PHP代碼

對於 PHP 代碼，適用 [PSR-12](https://www.php-fig.org/psr/psr-12/) 編碼標準。

## 蟒蛇

對於 Python 程式碼，Python 增強建議 (PEP) 適用。詳細資訊請參閱[Python開發者指南](https://www.python.org/dev/)。

## 大樓

有關我們的[架構](<242 大樓.md>)和使用的[組件](<264 組件.md>)的文檔可用。

## 保護使用者輸入

我們的目標是在將用戶輸入註入配置之前對其進行驗證，以便提供更用戶友好的介面並防止將來發生不好的事情。

儘管我們確實知道完美的驗證並不總是可能立即實現（太多的引用約束，並不總是那麼容易捕獲），但最好的做法是問問自己是否可以驗證特定的輸入（如果現在不能，那麼將來呢）。

使用者輸入無法驗證的問題是它最終會咬住你，導致未來的安全問題等待發生（例如，非授權使用者可以編寫將以提升的權限執行的命令，例如我們在 openvpn 中看到了這一點）。

因此，我們不允許將純文字設定資料儲存在我們的配置中（儘管一些遺留元件仍然使用此[opnsense/core#d62015](https://github.com/opnsense/core/commit/d62015df1cdb0c0711b488bd66ced631b9a4f37b)）

注意事項

自訂使用者輸入的功能請求將在我們的公共儲存庫中被拒絕，定義功能應該做什麼也有助於設計正確的功能。

提示

如果需要自訂輸入，在大多數情況下，您可以使用掛鉤在服務中包含其他配置數據，大多數服務都提供此類支援（使用預定義目錄或透過模板系統）。

這可以防止任意用戶添加未定義的配置資料。

我們的模型系統中的不同欄位類型旨在幫助開發人員保護其程式碼免受意外輸入的影響。

## 理想發展

我們理想的 OPNsense 系統看起來像一個標準的 FreeBSD 系統，使用我們的可插拔使用者介面進行管理，它支援真實使用者作為「機器」使用者 (REST)。

開發時我們希望程式碼盡可能乾淨並編碼為DRY（不要重複自己），並且不想在不需要的時候發明輪子。

透過重構命令傳遞到系統 (configd) 的方式，使用者介面應該能夠以非 root 使用者而不是 root 身分運行。

## 現實：逾期維護

事實上，我們分叉了一個很長一段時間沒有程式碼維護的系統，我們需要將其轉換為更結構化的系統。

我們所做的第一件事（在系統的程式設計部分）是圍繞現有框架（[Phalcon](https://phalcon.io/)）建立元件來建立新模組，這些模組可以使用經過驗證的設定資料（來自 config.xml），提供 RESTful API 並使用標準範本（Volt）產生 HTML 輸出。

我們創建了 configd 系統，它可以產生系統配置並使用預先定義的模板執行系統呼叫。然後我們開始將這些新元件用於我們第一個新設計的模組（例如代理和流量整形器）。有關「未來」架構的更多資訊可以在我們的[架構](<242 大樓.md>)文件中找到。

## 策略

我們知道我們不可能在一天之內改變世界，我們有很多遺產可以隨身攜帶，我們的策略由三個部分組成：

**1)** 清理與維護

重組舊（遺留）程式碼，基本上是 src/www、src/etc/inc 中的所有程式碼，使其更好可讀、更易於使用並刪除未使用/不必要的部分。透過這樣做，我們希望稍微延長舊程式碼的生命週期，並最終使新程式碼的轉換更容易。

**2)** 分離

盡可能將系統設定呼叫移至 configd，這使管理員能夠從命令列執行這些命令，並有助於消除將來對 root 使用者存取的需要。 ipsec VICI 實作是此階段的範例。

**3)** 繼續

使用我們的新模組（重新）建立新部件，它提供了分層開發系統來自動支援來自其他系統的API調用和基於XML的模型模板來描述配置資料。

*另請參閱：*

-   [Hello World模組](<366 Hello world 模組和插件.md>)
    
-   [如何使用API](<370 使用API.md>)
    

我們的指南在某種程度上取決於程式碼所處的階段，在編寫新程式碼時，所有操作都應使用API系統來實際更改配置和執行配置任務。當然，他們應該對 PHP 程式碼使用正常的 PSR 編碼標準，並遵循 Python PEP。

當遷移到系統的遺留部分時，我們的目標是盡可能接近PSR1/2，因為我們知道它永遠不會完美。

注意事項

當建立新的（基於MVC）程式碼時，不允許直接包含遺留部分。其主要原因是防止技術債務堆積在新組件中並失去監管。
