# 大樓


OPNsense 專案的主要重點是為您的所有安全應用程式提供一個安全且可管理的平台。這意味著易於維護且無錯誤的高品質軟體。我們認為，擁有一個明確關注點分離的框架對於實現這些目標至關重要。

OPNsense 是 pfSense ® 的一個分支。 pfSense ® 的現有程式碼庫並不總是應用明確的關注點分離。這意味著我們需要將舊的（遺留）程式碼庫過渡到新的程式碼庫，並進行明確的分離。我們選擇了漸進式過渡，以避免大爆炸並保持產品功能豐富，同時提高程式碼品質。這樣可以簡單地添加新功能，同時減少錯誤並縮短上市時間。

本文描述如何實現這一目標。

## 高層架構

[圖：OPNsense Components.svg](https://docs.opnsense.org/_images/OPNsense_Components.svg)

如上面的模型所示，我們的堆疊中有兩個主要區域，使用 PHP/Phalcon 實現的前端和使用 Python 建立的自訂服務的後端。

前端處理使用者互動並與後端服務通訊。應用組態變更、監視和控制 OPNsense 提供的服務是由後端服務完成的。

透過使用完全可配置的後端服務，我們避免了服務的硬編碼並簡化了新功能的實施。

前端堆疊提供了模型驅動的方法來處理配置數據，包括自動驗證。

核心設定檔的操作是在前端模型處理的；後端服務只是所提供資訊的消費者。

## 前端架構

[圖：OPNsense frontend.svg](https://docs.opnsense.org/_images/OPNsense_frontend.svg)

### 路由

OPNsense 框架盡可能使用標準元件；第一層初始化路由，處理請求並根據其 url 將它們傳遞給控制器。使用者內容是使用 Volt 模板（使用 Phalcon）產生的，由控制器選取。

有關 OPNsense 中使用的路由原理的詳細說明，請造訪前端[路由](<259 路由.md>)。

### 控制器和視圖

並非框架的所有部分都已實現，但透過從 OPNsense 專案的基礎派生所有控制器，可以輕鬆擴展和適應未來的需求。有關如何使用視圖實作控制器的文檔，可以在[使用控制器和視圖](<260 使用控制器和視圖.md>)找到。

### 型號

所有模型都是由類別和包含（嵌套）定義的XML的組合來定義的。更多關於定義模型的資訊可以在前端模型頁面[建立模型](<251 創建模型.md>)找到。

### 通訊

與後端服務的通訊是透過 unix 域的套接字處理。

### 核心系統

OPNsense 的核心由幾乎標準的 FreeBSD ® 系統提供支持，並使用 pkg 系統擴展了軟體包。 GIT用於版本控制，儲存庫分為4部分：

-   src：基本 (FreeBSD®) 系統
    
-   ports：包含第三方軟體的 ports 集合
    
-   核心：OPNsense GUI 和系統配置部分
    
-   工具：建構 OPNsense 的簡單工具

## 後端架構

### 中介軟體

[圖：OPNsense backend.svg](https://docs.opnsense.org/_images/OPNsense_backend.svg)

Configd 負責核心系統交互，例如守護進程的啟動和停止以及為所使用的服務和應用程式產生設定檔。

此守護程式偵聽 unix 網域套接字，並能夠執行在其自己的設定目錄（“/usr/local/opnsense/service/conf/actions\_\*.conf”）中定義的操作。

目前守護程式中實作了四種類型的服務：

-   腳本：執行外部 (rc) 腳本，報告成功或失敗
    
-   script\_output：執行外部腳本，報告其內容，通常為json格式
    
-   Stream\_output：開啟後端元件的流
    
-   內嵌：執行內聯操作，這是 configd（最值得注意的範本產生和維護）的一部分。
    

  

模板生成由Jinja2（[https://jinja.palletsprojects.com/en/stable/](https://jinja.palletsprojects.com/en/stable/)）處理，有關如何創建應用程式模板的更多資訊可以在[使用模板](<249 使用模板.md>)找到。

### 營運階段

[圖：OPNsense_operating_events.svg](https://docs.opnsense.org/_images/OPNsense_operating_events.svg)

由於所有早期層都描述瞭如何保存使用者輸入以及如何交換服務訊息，因此在審視防火牆的生命週期時，我們的功能仍然存在差距。到目前為止，我們已經有了手動管理服務和設備的方法，包括按需收集資訊的方法，但仍以相當隔離的方式（透過 api 層觸發的事件）。

這就是 [syshooks](<245 開機自動運轉選項.md>) 和 [plugins](<248 使用插件.md>) 發揮作用的地方，這些提供的機制可確保不同類型的服務可以與可用的共享功能配合。

在啟動和停止防火牆之間，我們可以識別三個階段。通電後，我們正在啟動，當達到這個初始階段時，我們最終會得到一個正在運行的防火牆，其中所有已配置的服務都可用。在一段時間內，可能會發生各種事件，例如有人拉了一條網線又推回去，這就是運行階段。最終，如果有人決定關閉或重新啟動機器，我們將進入關閉階段，讓服務知道我們正在結束操作。

每個階段的更多詳細資訊可以在[概述](<244 概述.md>)文件中找到。

為了避免無休止的依賴循環，服務應該防止掛鉤操作不嚴格需要的事件。例如，當網路介面發生變更時強制重新啟動元件通常表示不遵循設計網路服務的最佳實務。
